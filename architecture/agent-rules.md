# Agent Rules

The following rules are explicitly defined for the agents in the system. These rules govern the behavior, interactions, and responsibilities of agents to ensure a consistent and efficient operation within the architecture.

- Cargo features must be earned. Creating new cargo features can invalidate compilation caches. Cargo features and mise tasks are designed around minimizing re-compilation across task suites. This is important. Wyrd is a big system.
- Raw `sqlx::PgPool` is banned from library code. Two — and only two — connection abstractions are allowed in function signatures and struct fields: `&mut TenantConn<'_>` for tenant-scoped work (RLS-enforced under `wyrd_app`) and `&OperatorPool` for cross-tenant BYPASSRLS work (under `wyrd_platform_admin`). Never `&sqlx::PgPool`, `sqlx::Pool<Postgres>`, a naked `PgConnection`, or a `sqlx::Transaction<'_, Postgres>` handed in by a caller. Pool construction is a boundary concern: only `WyrdPostgres`/`ValaPostgres::connect_from_dsns`/`connect_after_wyrd` (production) and `from_pools` (unit-test fixture) build pools. `PgPool::connect_lazy` and friends are banned inside domain crates. `from_pools` compiles only behind `cfg(test)` / `test-support`, and `check:deps` proves the shipped server never enables `test-support`, so a production caller cannot build. Propagation is enforced by `check:tenant-isolation`, which refuses a raw pool (or `app_pool()` borrow) in production query, auth, and boot code; those callers go through `WyrdPostgres::tenant_conn`, `WyrdPostgres::resolve_tenant_slug`, or an `OperatorPool`.
- A function accepting `&mut TenantConn<'_>` MUST NOT call `conn.commit()` or `conn.rollback()`. The caller opens the transaction (via `TenantConn::acquire` or a handle method like `WyrdPostgres::tenant_conn`) and owns its lifecycle. This preserves composition: a caller can chain N tenant-scoped writes into one atomic transaction without every callee racing to commit early.
- Cross-tier imports go through the owning tier's re-exports, not the underlying crate. Vala and Bifrost code imports `use vala_sql::{TenantConn, OperatorPool, SqlError};` — never `use wyrd_sql::TenantConn;` or `use wyrd_sql::operator_pool::OperatorPool;` from outside `wyrd-sql` itself. The re-exports let the tier own its own surface and version its dependency on `wyrd-sql` independently. The same rule applies to every tier crate.
- Bring types in with `use` and use bare names in signatures. Write `tenant: DataTenantId`, `conn: &mut TenantConn<'_>`, `-> Result<(), SqlError>` — not `tenant: wyrd_spec::DataTenantId`, `conn: &mut vala_sql::TenantConn<'_>`, `-> Result<(), vala_sql::SqlError>`. Fully-qualified paths in signatures are noise that hides which crate owns the type; the `use` block at the top of the file is the correct place to declare that dependency. Applies to struct fields, function parameters, return types, trait bounds, and `where` clauses.
- All `use` statements live at the top of the module (after the `//!` doc comment, before `const`/type/`fn` items). No function-scoped `use sha2::Digest;`, no `use ...` inside an `impl` block, no imports lazily pushed down "next to where they're used." The top-of-file `use` block is the file's dependency manifest — hiding an import inside a function makes the module's real dependency surface impossible to read at a glance and lets the same trait get re-imported in five places. Two narrow exceptions, both with clear justification: (a) `#[cfg(test)] mod tests { use super::*; ... }` — tests are their own scope; (b) `use TraitName as _;` to enable trait methods inside a single generic function where the trait doesn't belong in module scope (rare — prefer the top-level import).
- TenantConn (Postgres RLS) is the load-bearing tenant boundary. Do not add manual per-query tenant filters on a TenantConn path; RLS already enforces it and hand-filtering drifts. Cross-tenant reads/writes require OperatorPool with an explicit admin role, never a widened tenant query.
- Audit records authorization decisions, not engine mechanics. Every decision that evaluates a principal's permission appends one audit row — allowed and denied alike — naming the principal, the permission, the resource, and the outcome. Engine-internal transitions that evaluate no permission (Scribe batch commits, Forge maintenance, Oracle reader protection) are lineage in their own operational tables and never audit.
- There is one audit write path: every audit event is staged in memory on the process `ScribeOutbox`, whose background writer submits it to Scribe as `vala.system.audit_log` rows; a failed write is retried or, when terminal, logged and counted, and never fails the operation. No audit staging table, publisher, WAL, relay, or log sink exists.
- Permissions are blocking; audits are non-blocking. A permission check completes before the operation proceeds or refuses; its decision is staged on the shared Scribe outbox (`AppState::scribe_outbox`, through `wyrd_runtime::audit::AuditStage` in lower crates) and the request never waits for the write. Every audited surface follows this rule, and no error exists to report an audit write failure. A workflow that evaluates permission more than once audits each evaluation at its own commit boundary; do not claim whole-workflow atomicity.
- Tests are inlined into the owning `src/` module (`#[cfg(test)] mod ...`) by default. An external `tests/` file must earn its place: it wires ≥2 non-foundational crates, brings up a real server/gRPC/HTTP surface or spawns the compiled binary, or drives a real external service (Postgres, cloud emulator). Each external file is a separate test binary that links the heavy dep cone; inlined tests compile with the crate and keep the fast lane fast.
- Tests needing Postgres, Docker, or a live server go in `mod pg_tests` (or a `pg_*` file), never the fast lane. The family lanes run `--skip pg_tests` and must stay credential-free and Docker-free.
- Run whole-crate tests through the crate's `mise run` task. The task supplies the DB env, migrations, and generated artifacts. Specifically named Rust tests use an exact `mise exec -- cargo nextest run` command with explicit package, target, features, and test expression; include the repository-managed setup wrapper when needed.
- Every user- or agent-facing capability ships a user-journey test (real SDK → real server). A unit test never substitutes for a missing journey.
- Never circumvent a gate to make it pass: no `#[allow]`, `#[ignore]`, deleting/weakening a test, or broadening a boundary glob to hide a violation. Fix the root cause. Use only a check's own sanctioned mechanism (e.g. a documented per-file allowlist) and only for a legitimately test-only, in-pattern case.
- Clippy lints are diagnostic signals, not paperwork. The workspace `[lints]` table in `Cargo.toml` is the policy: `clippy::pedantic` for every crate, with a short list of workspace-wide exceptions that each carry a comment, plus `unwrap_used` (tests exempt through `clippy.toml`), `allow_attributes_without_reason`, and `unsafe_code = "deny"`. `mise run lints` enforces it with `-D warnings`. Suppress a single site with `#[expect(lint, reason = "...")]` on the narrowest item or statement, so the suppression fails once the lint stops firing. Use `#[allow(..., reason = "...")]` only when the lint fires in some build configurations and not others (wrap it in `cfg_attr` when that is expressible). Each suppression is a last resort; the common lints have a correct fix that is almost always the right answer:
  - `cast_possible_wrap` / `cast_possible_truncation` / `cast_sign_loss` — `as` casts across sign or width are a data-integrity smell. Use `i64::try_from(x)`, `num_traits::ToPrimitive` for float-to-integer conversions, or a domain newtype that already carries the target range. Never `as`-and-suppress. (`cast_precision_loss` is allowed workspace-wide: integer-to-float conversions of counts and sizes are exact below 2^53.)
  - `missing_panics_doc` — the function panics; either add the `# Panics` section documenting the invariant, or (better) return `Result` and stop panicking.
  - `unwrap_used` — convert to a `Result`, use `?`, or reserve `expect` for a true invariant with a message naming the invariant.
  If a lint genuinely does not fit the codebase, raise it in review and change the workspace policy; do not paper over a single call site.
- Never hand-edit generated artifacts: `.pyi` stubs, and JSON schemas under each crate's `schemas/`. Change the source or generator, regenerate, and let `codegen:check` verify. Runtime MCP catalogs are verified by their owning MCP tests, not inferred from the codegen lane.
- Before the server fetches a user- or tenant-supplied URL, SSRF-screen it: resolve DNS, reject if any resolved IP is internal, and pin the connection to the screened address (no re-resolution). Block cloud-metadata/link-local (`169.254.0.0/16`) in every profile; block loopback/private/CGNAT/ULA in Production. A tenant is semi-untrusted relative to the platform network.
- Validate the resolved/effective value, not the literal input. Checking a string then re-resolving is a check-then-use race (DNS rebinding); resolve once, validate, act on that exact result.
- Build scripts (`build.rs`) write generated output to `OUT_DIR`, never into the source tree. Writing into the tree changes a tracked file every build, refingerprints the crate, and forces a full recompile.
- Map columns/fields by name, not positional index, whenever the two schemas can diverge. Positional alignment silently mis-maps fields (a data-corruption class bug).
- Never mention references to plans, tasks, or other agents in the codebase. The code is a permanent artifact; plans and tasks are ephemeral. Do not hardcode plan/task names, IDs, or agent references into the codebase. Use configuration or runtime parameters instead. A maintainer will not have any context about a past plan or task when reading the code later.
- Rust structure follows `AGENTS.md` §5 "Required Struct-Centered Rust Style" as a hard acceptance criterion. Require a concrete owner when behavior retains meaningful state, identity, resources, or invariants across operations, or when the type makes an invalid lifecycle unrepresentable. A free function may coordinate multi-step or async work when its state and lifetime remain caller-owned for that invocation. Reject dependency-threading that duplicates a real owner, but do not invent a struct merely because a function orchestrates several steps. This rule does not justify zero-sized utility structs, god objects, or single-implementation traits.
- Rust documentation follows `AGENTS.md` §16 as a hard acceptance criterion. Every new or materially modified Rust item, including private items, fields, variants, helpers, and tests, requires rustdoc that explains intent, workflow role, operation, and relevant invariants or side effects. Every fallible function requires `# Errors`; document panics and async cancellation or partial-progress behavior when applicable. Missing or placeholder rustdoc is `BLOCK_BEFORE_MERGE`.
- Synchronous Rust is the default. An `async fn` is allowed only when it directly awaits IO or intentionally composes operations that do. Do not make validation, parsing, planning, transformations, or other pure computation async because an async caller invokes it or future IO might be added.
