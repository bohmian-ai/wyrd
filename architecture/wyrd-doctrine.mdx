# Wyrd core doctrine

`architecture/wyrd-design.md` is the active protocol authority. This page is
the public doctrine summary for developers and agents.

## Purpose

Wyrd is open-source verification and assurance infrastructure for AI systems.
It verifies that models, prompts, agents, workflows, and AI services behave as
intended from development through production.

Verification is Wyrd's primary product outcome: observed behavior is evaluated
against declared expectations for exact, versioned system components. Assurance
is the confidence supported by durable evidence that makes those judgments
attributable, reproducible, governable, and auditable.

Wyrd does not become the user's application runtime, training framework,
workflow engine, or cloud platform. User code executes in the user's runtime;
Wyrd declares what matters, observes what happens, evaluates behavior, and
preserves the evidence.

## Verification model

Wyrd owns a complete verification loop:

```text
Cards and Specs declare the system
        ↓
Verification bindings attach Verifiers
        ↓
Runs and Observations record measured behavior
        ↓
Verifiers produce judgments
        ↓
Bifrost, lineage, and audit preserve the evidence
        ↓
Policy governs decisions and Operators react
```

The terms are distinct:

| Term | Meaning |
|---|---|
| Verification | Evaluating observed behavior against declared criteria and producing a judgment. |
| Assurance | Confidence supported by durable verification evidence, provenance, policy decisions, and audit history. |
| Observation | A measured fact. An observation is evidence, not a judgment by itself. |
| Verifier | A reusable, subject-less declaration that interprets observations and produces judgments. |

Cards, registry, lineage, observations, evaluation, drift, policy, audit, and
analytical storage are the substrate of verification. They do not make Wyrd a
passive integration, catalog, or observability product whose purpose is merely
to assemble other tools.

## Object model

Wyrd verification begins with declared intent.

| Layer | Meaning |
|---|---|
| Core nouns | The durable concepts every other layer uses: Card, Spec, Run, Observation. |
| Card kinds | Domain specializations of `Card`; the kind changes the spec, not the ontology. |
| Foundations | Envelope, metadata, `CardRef`, relationship, status, and version. |
| Services | Registry, storage, lineage, policy, install, audit, observability, evaluation, drift, and runtime. |
| Surfaces | HTTP, first-class Rust/Python/TypeScript SDKs, CLI, UI, MCP, IDE integrations, and generated docs. |

Do not skip layers. A service operates on Wyrd foundations. A surface exposes a
service. A card kind specializes `Card`. Runtime details stay behind the
contract that explains them.

```text
Cards declare.
Specs define.
CardRefs connect.
Relationships explain.
Status tracks lifecycle.
Runs record execution.
Observations record measured facts.
Verifiers produce judgments.
Policy governs decisions.
Audit records accountability.
Operators react.
```

## Core nouns

| Noun | What it means in Wyrd |
|---|---|
| Card | A declared thing with identity, kind, version, spec, relationships, and status. |
| Spec | The declared payload that gives a card its kind-specific meaning. |
| Run | One execution of declared behavior. |
| Observation | A measured fact produced by or attached to a run, card, service, or workflow. |

Everything else should first try to fit as a card kind, spec field,
relationship, run, or observation. Add a new noun only when those shapes cannot
express the concept without lying.

## Card kinds

The v1 doctrine has 15 registrable native kinds. `CardKind::External` is a
non-registrable discriminator for foreign schema descriptors, not a Card spec.

| Domain | Kinds |
|---|---|
| Data plane | Data, Model, Artifact, Experiment |
| Agent plane | Prompt, Agent, Workflow, Mcp |
| Composition | Service |
| Governance | Policy, Audit |
| Observability | Verifier, Source |
| Reaction | Trigger, Operator |

Tools are runtime names resolved by Skald's tool registry; they are not Cards.
Sub-agency is an Agent invoking another Agent; it is a relationship, not a
`SubAgent` kind. Skills are not a v1 Card kind.


## Foundations

Every card uses the same envelope:

```yaml
apiVersion: wyrd/v1
metadata:
  space: prod
  name: churn-model
  version: "1.2.0"
  labels:
    domain: churn
    stage: production
  annotations:
    example.com/source: training-job-42
kind: Model
spec:
  ...
relationships: []
status: null
```

`metadata.labels` are short indexed classification fields. Use them for values
humans, agents, policy, or inventory views filter on.

`metadata.annotations` are descriptive metadata fields. Use them for longer
context that should travel with the Card but should not be indexed as a primary
classification field.

`tags` are not Wyrd's public metadata contract. Public Card metadata uses
`labels` and `annotations`.

Authors use `Ref` for durable references and `InlineableRef<T>` only where an
embedded child is part of the declared contract. `Path` is loader-only
authoring syntax. Composite registration may use `Sibling` to distinguish a
same-request target, but the server rewrites it to a UID-bearing `Ref` before
durable persistence. `CardRef` carries `kind`, `name`, one `version` field,
optional `space`, and optional `uid`. The server derives relationships from
these references; users do not author a parallel lineage graph.

A Verifier is a reusable, subject-less peer with one typed Drift or Eval
implementation. Deployment composition binds it through versioned
`verified_by`; runtime observations carry the subject identity used for
evaluation and filtering.

## Service boundaries

Wyrd ships three products from one source tree. `wyrd-spec` is the shared Rust
crate that defines all wire types. Each product depends on it; none owns it.
This is what keeps contracts identical across the HTTP API, SDK, CLI, MCP, and
generated schemas.

| Product | Domain |
|---|---|
| **wyrd** | Registry, lineage, policy, auth, install, audit |
| **vala** | Bifrost OLAP warehouse, observations, drift evaluation, agent eval |
| **skald** | LLM providers, prompt execution, tool registry, agent runtime, workflows |

Services compose foundations instead of inventing private shapes:

- **Registry** stores and validates cards; derives relationships from `CardRef`s; manages version and space isolation.
- **Lineage** reads derived relationships to answer provenance queries.
- **Policy** evaluates CEL rules at register-time (classify), deploy-time (gate), and runtime (invoke).
- **Bifrost / Observability** records runs and observations through Scribe,
  serves interactive and streamed distributed reads through Oracle, promotes
  and rewrites Iceberg data through Forge, and reads external data through
  `Source` cards.

## Runtime boundary

Wyrd records, validates, links, observes, verifies, governs, and exposes AI
system components. User code owns inference loops, training loops, app servers,
agent processes, and deployment mechanics. Wyrd provides the verification and
assurance infrastructure: services emit runtime behavior through Wyrd's native
observation system and bind it to evaluation, lineage, policy enforcement,
drift monitoring, and audit.

Runtime results that persist become runs, observations, artifact cards,
relationships, audit records, or status updates through service-owned paths.

## Public surfaces

The SDK, HTTP API, CLI, IDE integrations, UI, generated schemas, and MCP
tools all project the same card contract. A surface may add ergonomic
shortcuts, but it does not invent new shapes, rename durable fields, or expose
server-internal state. All contracts live on the API wire, making Wyrd language-agnostic.

Rust, Python, and TypeScript are first-class SDK languages. Each SDK provides
idiomatic authoring and client ergonomics over the same server contract, with
generated types, examples, and user-journey coverage. Their packages live under
`sdks/wyrd-sdk-rust`, `sdks/wyrd-sdk-python`, and `sdks/wyrd-sdk-ts`, and all
consume the shared implementations exposed by `wyrd-client`. Language-specific code must be earned by a
foreign-runtime boundary and cannot duplicate HTTP, gRPC, validation, or
durable behavior. Go is planned but does not become first-class until its SDK
and equivalent contract and journey coverage ship.

Existing Rust owner crates may temporarily retain optional Python features.
Only `wyrd-sdk-python` activates and aggregates them; Rust and TypeScript SDKs
do not. New or materially relocated Python logic belongs in the Python SDK,
which is the long-term home for all Python code. This migration direction does
not justify moving otherwise untouched code.

Bifrost follows one client path: each language SDK wraps
`wyrd_client::Bifrost`, which uses the shared `wyrd-client` HTTP and gRPC
transport to call `wyrd-server`.
Scribe, Oracle, and Forge remain server-owned subsystems; Gate is their server
dispatcher, not a role or client type.

The public protocol remains open to every language. A client needs only the
HTTP and MCP contracts, generated schemas, machine-readable documentation, and
stable errors. What a user declares in Rust, Python, or TypeScript remains
recognizable in the HTTP payload, the stored card, the generated schema, and
the MCP tool input.

## What to reject

**Card model**
- Compatibility aliases from predecessor projects
- One-off artifact reference wrappers
- Duplicate public shapes for the same concept
- Authored lineage graphs that bypass `CardRef`s and derived relationships

**Card kinds**
- `Tool`, `Skill`, or `SubAgent` as new v1 public card-kind work

**Public surfaces**
- Per-kind registration methods on card objects
- Server-only fields in client contracts
- Surface-specific vocabulary that diverges from the spec

**Spec discipline**
- Live runtime objects in specs
- Untyped strings where Wyrd has a domain type
- Runtime plugins where a closed enum is the real contract

**Observation model**
- Public event-shaped payloads where `card`, `run`, `observation`, `relationship`,
  `status`, `policy`, or `audit` names the concept more clearly

**Implementation hygiene**
- Hidden side effects during local card construction
- Generated files edited by hand

## Implementation rule

Every implementation should preserve the doctrine:

- verification is the primary product outcome
- assurance claims are backed by durable evidence
- contracts are typed
- specs are declarative
- CardRefs are explicit
- relationships are derived
- observations remain measured facts
- Verifiers produce judgments
- artifacts are cards
- registration is centralized
- runtime behavior stays out of durable specs
- public surfaces use Wyrd vocabulary

If an approved feature exposes a better principle, update this doctrine and
the active design explicitly; do not preserve stale guidance through a
permanent exception. An unexplained conflict remains a blocker.
