## Reachable behavior and whole-workflow reuse

The caller path remains SDK/CLI loader → public composite HTTP registration → canonical graph/external-ref planning → RegistrationWriter → persist_node/ordinary SQL version resolution → registration replay/upload completion → existing CardGraphHydrator → shared typed index → language projection. Direct HTTP reaches the same inline materialization. No SDK synthesizes durable identity, and no hydration or navigation method repairs a graph.

For same-request collision, producer and siblings were traced together: an authored Prompt or first Agent's generated Prompt writes Pending on the same operation; the next generated child calls the same resolver. `latest_stable_in_line` now includes Active rows plus only Pending rows bearing this registration operation ID, and keeps stable/bounds/latest ordering/hash rules. Both matching content reuse and different content advancement therefore use the existing owner. An ordinary exact authored pin still goes through exact spec/artifact comparison, and arbitrary other-operation Pending rows remain excluded from auto/scope selection. This is a narrow extension of normal transaction visibility, not a generated-only cache.

For exact-parent replay, child auto selection was the producer of the false parent drift. The new helper consults only an already existing exact Agent, verifies its stored reference is the generated kind/name/space, and sets that child's exact version. `persist_node` then validates its content with existing hashes; the parent still validates its complete normalized spec. This preserves sibling binding, native Prompt validation and actual parent drift. It does not introduce global historical content search or change fresh Agent child version policy.

For navigation, `TypedCards` already owns exact Agent and Prompt maps; the added view is borrowed and state construction validates it. Python's prior hydration workflow already projected all exact holders, so attaching from its existing Prompt map suffices. TS native retrieves the already selected shared relationship and projects stored envelope data, rather than parsing/reselecting references. `Run::invoke` retains tool refusal, configuration conversion, gateway registry/caller, subject UID/Run ID correlation and error mapping; its only changed payload source is that shared PromptCard. No replacement runtime or loader is warranted.
