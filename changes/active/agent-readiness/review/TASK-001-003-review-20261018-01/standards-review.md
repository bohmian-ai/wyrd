## Material proposed findings

### REPO-001 — New and functionally changed Rust items omit mandatory rustdoc contracts

Classification: **VIOLATION**. Governing rule: AGENTS §16 and agent-rules Rust documentation requirement; missing or incomplete rustdoc on a touched Rust item is explicitly `BLOCK_BEFORE_MERGE`.

Locations and concrete evidence:

- `crates/wyrd/wyrd-cli/src/main.rs:4`: the function materially adds JSON-sensitive tracing policy and still has no function rustdoc. The module's one-line description does not explain the function's crypto-provider initialization, logging selection, dispatch and exit behavior.
- `crates/wyrd/wyrd-cli/src/lib.rs:155–162`: newly added `json_mode_is_read_from_raw_arguments` has a short purpose sentence and assertions, but no `# Panics` naming assertion failure. It is a new test, not an unchanged assertion made visible by a file rename.
- `crates/wyrd/wyrd-cli/tests/card_lifecycle.rs:586–592` and `649–670`: genuinely new `removed_card_verbs_are_usage_errors` and `get_help_describes_one_envelope_without_bundle_options` exercise process helpers and assertions, but omit the required panic conditions.
- `crates/wyrd/wyrd-cli/tests/card_lifecycle.rs:616–631`: the former get-output-directory test is functionally changed to assert pull's Clap refusal instead of the former domain validation result; it has no rustdoc at all.
- `crates/wyrd/wyrd-mcp/tests/bifrost/mcp/discovery.rs:217–246`: newly added `onboarding` documents returned transport/shape errors, but the absent taught terms actually panic through `assert!`. The docs omit that failure mode and misdescribe that part as a returned error.

Consequence: the candidate fails an explicit correctness/merge gate for changed Rust documentation. A maintainer cannot rely on the new entrypoint/test/helper documentation to distinguish returned failures from assertions and understand the new startup output policy. This finding does not allege a runtime functional failure from a missing comment.

Required correction: document those new or functionally changed items substantively in place, including their actual workflow purpose and failure behavior; add `# Panics` wherever these assertions/fixture operations can panic and correct the MCP helper's Errors/Panics distinction. Do not blanket-document unrelated tests, mechanically renamed unchanged test bodies, or all existing progress-renderer internals. Preserve assertions and runtime behavior.

Focused closure proof: source review of the cited items against §16, format/lint through the owning existing lane, and no test weakening. No new runtime test or repository-wide rustdoc checker is needed for this documentation correction.

### REPO-002 — Public bundle errors prescribe an operation that can no longer recover

Classification: **INCORRECT / public-contract regression**. Governing rules: AGENTS §§2,4,9 (surface alignment and public error contract), `references/languages/errors.md` (actionable stable errors), and `references/languages/agent-harness.md` (machine-consumable remediation).

Owning source: `crates/wyrd-spec/src/error.rs:1144` (`SdkUnhydratedArtifact`) and `:1188` (`SdkInvalidStateBundle`). The first says “Run wyrd get without --metadata-only and load the complete bundle”; the second says “Regenerate the bundle with wyrd get and load the complete output.” The former variant's title is directly changed in this range; the new get/pull split makes both existing remediation strings wrong.

Reachable producer-to-consumer path: `Cards::pull(..., BundleMode::MetadataOnly)` creates an intentionally non-runnable bundle → `WyrdState::from_path` → `BundleReader::validate_manifest_header` returns `SdkUnhydratedArtifact`. Malformed/header/identity/artifact validation paths return `SdkInvalidStateBundle`. The derive-backed metadata crosses public Rust/SDK/CLI boundaries and is also emitted by the error-doc generator. `docs/src/content/docs/api/errors.md:309` retains the first bad recovery instruction, and generated full-reference content carries it onward.

Consequence: a user or coding agent follows the machine-provided recovery command and receives one envelope, not a bundle. The artifact directory remains absent/incomplete, and the next state load fails again. This is an actionable-recovery defect, not merely an old word in prose. `card.rs::get`/`dispatch_get` call the envelope reader; only `pull` writes the bundle and accepts `--output-dir`.

Required correction: change both remediation strings at their existing derive-backed source to instruct a complete `wyrd pull` of the desired Service into the explicit output directory, without `--metadata-only`, followed by loading that bundle. Regenerate the consumed error catalog and llms projections through their current generators. Do not hand-edit the generated pages, change error codes, add a get alias, or create a second error mapper.

Focused closure proof: preserve the existing metadata-only/malformed-bundle rejection behavior; assert or inspect that both errors' derive-generated remediation identifies the actual pull operation and destination requirement, and regenerate/check the owning docs/codegen outputs. A narrow assertion in an existing bundle/error test is sufficient if runtime proof is added; no new journey harness is needed.
