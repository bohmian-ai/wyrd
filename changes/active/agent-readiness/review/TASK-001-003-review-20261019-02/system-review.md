### SYS-R2-001 — A Rust telemetry flush failure bypasses the independent ticket drain

Classification: **INCORRECT**; incomplete lifecycle closure of **FIND-TASK-003-1**. Authority: REQ-008/AC-008 visible real startup and flush/shutdown recipe; INV-004 preserves buffered-admission versus durable evidence semantics; the published recipe must use the actual lifecycle owners. This is not a stronger exactly-once or abrupt-exit guarantee.

**Exact location:** `examples/support-desk-app/rust/lib.rs:128–130` in new `SupportDesk::serve`. Public consumers are the `serve` regions embedded by quickstart and record-a-run-and-observations. Although there is no standalone executable invoking this new library method in-tree, TASK-003 explicitly requires these published Rust instructions; they are not a dormant, unrelated helper.

**Producer-to-consumer trace:** `SupportDesk::deploy` starts the state's Bifrost writer at line 96. `answer` admits ticket rows through `run.observe().record` (line 205), independently from completed tracing spans. After graceful HTTP shutdown, `serve` invokes `Telemetry::shutdown`, which calls `SdkTracerProvider::force_flush` and returns its failure as `ClientConfigInvalid`. The locked `opentelemetry_sdk` is 0.31.0; its `BatchSpanProcessor` sends the export result back to `ForceFlush` and returns errors or a force-flush timeout (`trace/span_processor.rs` in the installed source, ForceFlush handling and `force_flush`). Thus collector refusal/unavailability or an export that exceeds its flush budget can make the `?` at line 129 return. `state.shutdown().await` is never evaluated.

**Observable consequence:** graceful application termination can report only a telemetry failure while ticket rows have never had their own drain attempted. HTTP OTLP failure does not establish failure of independent gRPC row ingestion, and even a common outage requires the native drain's actual failure rather than skipping it. The consumed app no longer gives the caller its state for the existing retry-on-ambiguous-drain path. Process exit can lose admitted ticket rows even when the row sink was available. The global telemetry handle's flush does not flush the Bifrost writer: `WyrdState::shutdown` delegates separately to `observe::BifrostLifecycle::shutdown`, then `Bifrost::shutdown`/writer pool drain. No automatic equivalent barrier is called on this early-return path.

**Sibling owners inspected:** Python `PyWyrdState::shutdown` records the telemetry outcome, always calls native shutdown, then settles results (`sdks/wyrd-sdk-python/src/state/mod.rs:316–319`); `TelemetryFlushFailure::settle` owns its runtime projection. The Rust public OTEL owner remains a separate handle. Changing it or adding telemetry ownership to WyrdState/SupportDesk is unnecessary. The current doc assertion explicitly matches the sequential `telemetry.shutdown()?; state.shutdown().await?;` text, so that assertion does not challenge this error flow.

**Smallest correction:** in the example's existing serve lifecycle, retain the telemetry result, attempt native shutdown regardless of that result, and only then return the appropriate existing error. Preserve telemetry-before-native ordering, the actual retained handle, graceful serving, the existing error catalog, and serving-error handling; no shared server fatal boundary, new runtime, public option, retry/backup owner or SDK lifecycle API is required. Correct the assertion/snippet documentation to reflect that both stages are attempted.

**Focused closure proof:** use the existing runtime/mock-export facilities to force the real telemetry flush to fail with a pending ticket row while its native sink can drain; establish that native shutdown is attempted and settles before `serve` returns the telemetry error. Retain normal graceful serving and the serving-failure cleanup source path. Compile/docs checks remain useful regression checks but are insufficient as the only evidence for this negative flow. No full SDK suite, live provider, broad gate or new general fault harness is requested.
