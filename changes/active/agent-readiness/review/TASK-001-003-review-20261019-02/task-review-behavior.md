## New proposed implementation finding

### BEH-R2-001 — Rust onboarding shutdown skips the ticket drain after an OTLP flush failure

**Classification:** INCORRECT/REGRESSION. **Obligation:** REQ-008's complete flush/shutdown recipe, INV-004 safe drain, TASK-003's executable public-API examples. **Changed location:** `examples/support-desk-app/rust/lib.rs:121–135`, specifically `telemetry.shutdown()?` at line 128 before `state.shutdown().await?` at line 129. The entire new `serve` region is embedded in quickstart step 5 and Observe step 4 and exported in llms-full.

**Producer → consumer:** `SupportDesk::answer` at lines 205–211 admits a tickets row to the state writer. `deploy` starts that writer and retains it in SupportDesk. A caller following the newly documented `serve` path serves requests, receives its graceful stop signal, then flushes telemetry. Public Rust `sdks/wyrd-sdk-rust/src/otel.rs::Telemetry::shutdown` at lines 61–68 calls `SdkTracerProvider::force_flush` and returns ClientConfigInvalid for a failed export. Thus an OTLP-only failure, unavailable collector endpoint, or bounded exporter flush failure returns immediately from serve; state shutdown is never invoked. The custom-row transport/drain is a separate capability and may still work. `WyrdState::shutdown` at `state.rs:778–788` explicitly owns the buffered row durability barrier; dropping/exiting without it can lose pending rows. This is a graceful app exit that unnecessarily omits that barrier, not a demand for stronger acknowledgment or zero-loss on abrupt death.

**Sibling owners checked:** Python state shutdown (`sdks/wyrd-sdk-python/src/state/mod.rs:316–320`) captures telemetry outcome, always executes native shutdown, then settles. TypeScript `WyrdState.shutdown` (`wyrd/src/index.ts:2967–2970`) follows the same sequence. Shared state shutdown remains intentionally telemetry-free in Rust. Existing Rust Telemetry is already the correct span owner; moving OTEL into WyrdState or making SupportDesk retain process-global telemetry is unnecessary. The new serve coordinator owns the ordering mistake.

**Observable consequence:** On an ordinary graceful stop with a span export failure, the published Rust recipe returns the telemetry error while still-buffered custom rows receive no drain attempt. Exiting then can lose tickets that could otherwise have reached Bifrost. A green Rust compilation/content check does not execute this branch.

**Smallest required correction:** Keep the existing public Telemetry and WyrdState owners. In the serve coordinator, retain the telemetry outcome, attempt state shutdown regardless of that outcome, then propagate failure without converting it to success. Preserve telemetry-before-row ordering, graceful HTTP completion, serving error handling and existing stable error types; do not add a new SDK lifecycle/transport or retry mechanism. Verify the narrow coordinator behavior with a forced telemetry flush failure and a drain that can succeed: drain must still be attempted, and the call must still report failure. Also cover the ordinary successful exit. The two outcomes can be sequenced directly; no production abstraction is justified merely to inject a test.

This is a new defect introduced by R1's new serve body, not a renamed instance of the previous recipe name/initialization mismatch. No new FIND ID is assigned here; independent validation owns retention/numbering.
