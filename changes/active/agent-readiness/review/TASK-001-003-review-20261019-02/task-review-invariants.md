### INV-R2-001 — diagnostic sink failure still corrupts JSON stderr

Classification **INCORRECT**. Existing stable finding **FIND-TASK-002-1** remains open on its failure path. Obligations REQ-006/AC-007 and R1's whole-stream diagnostic policy.

Location: `crates/wyrd/wyrd-cli/src/lib.rs:136–141`, JSON subscriber construction. Producer: subscriber builder's default internal-error policy; affected consumer: `main` → command dispatch → `CliBoundaryError::print(true)`. Sibling writers are `DevServer::Diagnostics`, which already drops failed diagnostic writes, and human tracing, which legitimately owns human stderr.

Pinned `tracing-subscriber` is 0.3.23 (`Cargo.lock:9550`). Its installed source `src/fmt/mod.rs:466–474` constructs `SubscriberBuilder` with `.log_internal_errors(true)`. `src/fmt/fmt_layer.rs:1049–1054` calls `eprintln!` when the selected writer's `write_all` fails. Merely opening the append file successfully does not prevent a later ENOSPC/quota/device-write failure. The new JSON branch leaves that fallback enabled, so diagnostics again reach stderr before the structured operation error, or accompany a successful result.

Fresh focused reproduction: existing `target/debug/wyrd`, isolated temporary config, synthetic token, `RUST_LOG=debug`, `get --kind Prompt --uid 01890f28-7c4a-7cc3-98e7-4f4a3c2d1b00 --server http://127.0.0.1:1 --format json`, with temporary `logs/cli.log` pointing to the local failing device `/dev/full`. Result: exit 1, stdout 0 bytes, stderr 21 lines, whole-stderr JSON decoding failed; repeated `[tracing-subscriber] Unable to write an event ... No space left on device` precedes the JSON. The existing binary was not rebuilt in this review, so pinned source is primary evidence; the probe independently corroborates it. `/dev/full` is a review-only local failure fixture, not a product mechanism or proposed platform prerequisite.

Smallest correction: use the subscriber's existing `log_internal_errors(false)` policy in the JSON branch so its sink failure cannot escape onto machine stderr. Keep file-open failure as the existing one structured pre-command error, ordinary requested logs in the file, human diagnostics unchanged and foreground child lifetime/routing intact. No second logger, sink framework, command-local scrubber or new configuration is required. A failed diagnostic write may lose diagnostics, as the existing DevServer diagnostic owner already permits; it must not change command/result streams.

Closure proof: focused failed-writer regression that reaches at least one diagnostic event after successful sink setup and asserts whole success/error streams remain clean; preserve existing normal-file retention and no-secret assertions. Use a portable failing-writer seam if adding a cross-platform test; do not make a Linux device a deployment/test prerequisite.

### INV-R2-002 — the new published Rust shutdown skips row drain when telemetry fails

Classification **INCORRECT**. Obligations REQ-008, INV-004, AC-008 and the original TASK-003 complete initialization/shutdown recipe. Relationship: introduced while remedying FIND-TASK-003-1, not the old destructive deploy finding.

Location: `examples/support-desk-app/rust/lib.rs:128–129`, `SupportDesk::serve`; published consumers are the `serve` CodeFromFile region in quickstart step 5 and Observe step 4, then generated llms-full. This method has no in-repository executable caller; the task explicitly requires this public Rust recipe, so its published use is in scope. Existing canonical journey calls its different support-desk implementation and cannot prove the new method's failure handling.

State trace: `SupportDesk::deploy` starts `state.start_bifrost` and retains the state; request handlers buffer ticket records. `serve` installs the public SDK telemetry owner, gracefully completes HTTP serving, then executes `telemetry.shutdown()?`. Public `Telemetry::shutdown` (`sdks/wyrd-sdk-rust/src/otel.rs:61`) calls fallible provider `force_flush`, mapping an export failure to `ClientConfigInvalid`. That error returns from `serve` before `state.shutdown().await`, the only Bifrost drain here (`wyrd-client/src/state.rs:787`). Buffered records have no successful shutdown barrier; dropping the application can lose their tail even when its Bifrost path could still drain. OTLP-specific refusal/export failure need not make the separate writer unavailable. The method's prose promises the two stages and only qualifies row loss when drain fails, but this path never attempts drain.

Sibling ownership: Python/TS managed-state shutdown deliberately settles telemetry failure after always attempting native drain; `TelemetryFlushFailure` in shared state documents that existing policy. Rust's SDK telemetry handle remains application-owned, and Rust `WyrdState::shutdown` properly drains only its own writer. The correction belongs at this new application orchestration, not in either SDK owner or declarative Cards. The existing canonical Rust example explicitly documents its narrower success-only flush; copying its sequential `?` is insufficient for this newly published graceful serving workflow.

Smallest correction: retain the telemetry flush outcome, always attempt `state.shutdown().await` after serving ends, then return the appropriate existing failure without reporting success or silently swallowing it. Keep telemetry handle ownership local to the serving invocation, preserve graceful HTTP settlement, existing serving-error projection and unchanged SDK semantics. This needs no new lifecycle owner, public API, background retry or stronger delivery guarantee. Correct the embedded source assertion, which currently requires the short-circuit sequence literally.

Closure proof: one focused failure-path check at this application orchestration showing that a telemetry flush failure still attempts/settles writer drain and returns failure; retain successful serving/shutdown behavior and the public snippet/compile checks. Compilation and a string assertion alone cannot establish this lifecycle behavior.
