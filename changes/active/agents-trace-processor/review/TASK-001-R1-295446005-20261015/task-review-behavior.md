## Proposed finding

### BEH-R1-001 — Important — REGRESSION: joining an older Python flush can report success without flushing this call's completed spans

Recommended stable ID: **FIND-TASK-001-7**, since the original deadline defect in ID5 is fixed and this is a different success/barrier failure introduced by its correction.

**Location:** `sdks/wyrd-sdk-python/python/wyrd/otel.py:236-247`, especially retaining `self._attempt` when not done; settlement at `:252`. Public consumers are both `sdks/wyrd-sdk-python/src/state/mod.rs:277-280` and `:299-302` through `flush_telemetry:506-527`.

**Violated obligation:** REQ-013 says state flush first flushes completed spans, and AC-009/task scenario 3 requires that explicit lifecycle barrier. A successful shutdown is equally affected. Coalescing must preserve that contract in addition to bounding worker count and wait duration.

**Producer-to-consumer path:** One managed attempt finishes draining the stock BatchProcessor queue. Before `Future.set_result` publishes that attempt's success, another application thread ends a new span and invokes public flush (or retries shutdown after a prior timeout). The existing Future is still pending, so the second call chooses it. Publishing the first attempt's True wakes both callers; no provider flush starts after the second span ended. Binding sees truthy success, performs native drain and can report overall success while that completed span remains queued. The final empty-queue check and Future settlement are separate operations; there is no synchronization with span producers. Both lifecycle siblings share this one producer of invalid success, so fix the managed owner once.

**Validated evidence:** An isolated read-only probe imported candidate `otel.py` and used installed actual `TracerProvider(shutdown_on_exit=False)`, `BatchSpanProcessor(schedule_delay_millis=60000)` and `InMemorySpanExporter`. Python's thread trace hook paused the worker at the return of the real provider force_flush, after it had exported `first` and before managed Future settlement. The main thread ended `second`, then a second caller entered managed force_flush and waited on the same Future; releasing the worker yielded:

```text
{'first_result': [True], 'second_result': [True], 'exported_after_second_flush': ['first']}
```

This is a deterministic scheduling interleaving, not an injected provider result, altered source, real network, new dependency or test-suite execution. The probe then disabled tracing, explicitly flushed the remaining queue and shut its provider down. Candidate stock BatchProcessor `_export(EXPORT_ALL)` loops until queue empty, which means spans arriving while an export is actively draining usually succeed; the demonstrated gap is specifically after its last queue check and before Future settlement. That distinction is why the existing held-export deadline test does not catch it. The appended R1 evidence also discloses that later callers can receive an earlier attempt's outcome, but that disclosure cannot change the approved public barrier.

**Observable consequence:** A caller may query immediately after successful flush and miss its completed framework span; successful shutdown followed by process termination can lose that span. Native observations may already be drained, so this is also a mismatch between the two advertised stages. The stock background exporter may eventually send it, which does not make the explicit successful barrier valid.

**Smallest correction boundary:** Keep the managed owner, stock provider/batch/exporter, synchronous instrumentation and correlation, one in-flight worker, and existing error projection. A call which joins an attempt started before that call cannot treat its success alone as this call's flush barrier. Once that attempt finishes, perform a provider flush covering this caller's invocation before reporting success, or report the existing timeout if the same total existing deadline leaves insufficient time. Serialize through the existing retained owner; do not add an export queue, retries, public timeout or unbounded worker creation, and do not spend a fresh full timeout after waiting. Native drain remains attempted whatever the result.

**Focused closure proof:** Extend the runtime-local managed lifecycle proof with a controlled scheduler/return barrier around actual stock provider flushing: complete a second span before an overlapping lifecycle call, release the old attempt, and assert that the second lifecycle cannot succeed until that second span is exported. Preserve the current timeout/drain/single-worker/correlation tests. This interleaving is runtime-local and does not require a new real-server journey or framework transport fixture.
