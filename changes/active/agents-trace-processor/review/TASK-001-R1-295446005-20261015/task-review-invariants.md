## Producer-to-consumer and ownership audit

Framework execution produces native Pydantic/ADK spans, or Agents callback values. Python `_start` (`otel.py:400-420`) and TS `#start` (`index.ts:2596-2607`) capture active context and choose the first known SDK parent. Correlation processors stamp the start-time Run/Card scope; end callbacks only add final allowlisted metadata/status and end the original span. The bridge maps retain real live identities and earn their state; no second framework runtime or durable identity store is introduced. Shutdown empties the maps and leaves the provider alone. Python serializes map mutations with its callback lock; TS callback mutation occurs synchronously before each returned promise settles.

Python `_session` and TS `config` ask the selected shared client for a current token at export, rather than copying one at setup. The stock OTLP exporter remains the serialization/transport owner. Existing server authorization selects tenant and publisher and checks asserted Card identity; Run/Card values never choose a credential. No changed server, SQL, storage, or tenant-boundary implementation appears in this range.

Both state lifecycle doors flush the retained managed provider before calling the existing native writer lifecycle, then settle through `TelemetryFlushFailure`. The native owner remains `WyrdState`/`BifrostLifecycle`; runtime telemetry failures are not moved into native writer state. Application-owned providers are absent from the retained managed field and are untouched by state lifecycle. Run scope performs no export or shutdown.

The new Python `_ManagedTelemetry` (`otel.py:216-254`) retains a provider, lock and one Future. It is necessary because pinned OTEL 1.42.1 `BatchProcessor.force_flush` ignores its timeout and synchronously exports under `_export_lock`. The wrapper bounds only lifecycle waiting, and uses one daemon worker while the attempt remains in flight. Unlike replacing the provider's multi-processor owner, it leaves synchronous start-context correlation and ordinary span callbacks unchanged. The installed implementation's `EXPORT_ALL` loop continues draining queued items under its stock lock. No bespoke batch queue, retry backlog, new public timeout or executor shutdown join appears. Repeated timed-out calls reuse the same attempt; once it settles a later call starts another. The per-call Future wait releases the GIL. The sibling retained-provider initializer, however, is not similarly atomic (finding INV-R1-001).

TS post-import setup now rechecks its same-state field; there is no further await before synchronous install and field assignment. That closes the precise TS overlap. Local structural callback types remove the optional Agents declaration edge while preserving the exact fields the mapper reads. The actual framework assignment remains in tests. No new abstraction is needed for these fixes.

## Proposed material findings

### INV-R1-001 — Same-state Python initialization is not atomic

- Classification: **INCORRECT**. Severity: Important. New stable candidate: FIND-TASK-001-7; prior FIND-6 specifically corrects the independent TS owner.
- Violated obligation: REQ-012 and AC-008, same-state managed setup is idempotent, including reachable overlapping calls (the same accepted criterion used by prior FIND-6).
- Exact location: `sdks/wyrd-sdk-python/src/state/mod.rs:183-203`; producer in `python/wyrd/otel.py:277-289`.
- Evidence: both calls can observe `self.telemetry.get() == None` before Python provider construction. Construction imports modules and starts a stock batch worker, which can release the GIL. Both create providers; only one wins the OTEL global once. The loser `_start_telemetry` shuts its candidate down and returns None, and the public binding raises 409 even though the winner belongs to the same state. `OnceLock::set` protects publication of the final value, not construction. Source has no atomic get-or-initialize operation. Existing Python setup proof repeats sequentially and tests an independent installer, not two calls on the same owner.
- Fresh proof: a standalone existing-environment subprocess loaded the real public WyrdState over the checked-in complete bundle with the existing Tiny interfaces, explicit offline client and an in-memory exporter. A barrier around stock TracerProvider construction forced only the legitimate concurrent scheduling window; no provider/installer or binding result was replaced. Two ThreadPoolExecutor calls to public `state.start_telemetry()` returned `['WYRD_SDK_409_TELEMETRY_PROVIDER_EXISTS', 'ok']`, with OTEL's rejected override warning. The installed winner was explicitly shut down. Initial probe failed only because PYTHONPATH omitted the test fixture package; the corrected probe supplied the SDK directory and reproduced the behavior.
- Observable consequence: concurrent initialization of one shared application state spuriously fails startup with a provider-conflict error; callers cannot rely on the promised idempotence.
- Selected minimal correction: make initialization atomic at the existing state-owned retained handle, covering check, Python creation and successful publication. Reuse pinned PyO3 0.28.3 `pyo3::sync::PyOnceLock::get_or_try_init(py, ...)`: it serializes initialization while detaching blocked waiters from the interpreter and leaves failure retryable. Keep provider refusal/loser cleanup and error propagation in the existing installer. Do not add a provider registry, global identity lookup, new public state machine, or a blocking std mutex around Python calls; the latter can deadlock while another thread needs the GIL. The existing GC traversal/clear and lifecycle readers continue using this single owner.
- Focused correction proof: deterministic two-thread public setup test pauses one construction long enough for the other call to contend, then allows the sole initialization to finish; both calls succeed, one managed provider/export processor is created, and a separate state's setup still refuses without disturbing it. Keep failure-then-retry and existing cleanup/import tests. This is interpreter-local coordination with no cross-boundary state and can be unit-only; real normal setup/export journeys already exist.
