## Proposed finding SEC-09 — OTLP retry identity omits the new current publisher actor

Classification: REGRESSION / INCORRECT. Proposed new stable finding number: 9 (or the orchestrator's next unused number). Obligation: INV-001 authenticated publisher identity; REQ-011 generic telemetry retains authenticated publisher; current bifrost-design identity/replay contract and telemetry-observations authenticated subject/actor spine.

Location: `crates/vala/vala-bifrost-redux/src/gate/mod.rs:976` and `otlp_batch_id` at lines 131–146; the changed interaction is the separate `attribution: auth.attribution()` at line 988.

Reachable producer-to-consumer path:

1. A subject A can publish directly and through authorized Card-bound actor B using the existing delegated WyrdClient, including the stock span/log/metric exporter factories. Both authenticate as principal A; verified attribution is respectively `(A,A)` and `(A,B)`. Two authorized actors B and C acting for A are equivalent for this issue. Neither case changes tenant or widens permission.
2. Submit the same valid OTLP batch (same trace/span IDs, timestamps, payload and optional Card/Run) through those identities. This is deliberately identical observed work submitted by distinct authenticated publishers, not a claim that two independently generated framework executions naturally have identical span IDs. A collector/exporter can re-export an existing batch with another deliberate delegated client; public OTLP does not prohibit this.
3. Signal projection contains only authored fields plus `card_uid`/`run_id` (`tables/signal.rs:642–655`). Subject/actor are not yet present. `dispatch_canonical` hashes only tenant, **subject principal ID**, table, logical user data and these pre-stamp correlation columns. Thus both publishers receive the identical server-derived batch ID. No actor input exists in that computation.
4. Scribe stamps the differing actor only afterward (`ingress.rs:338–365`, `execution_lanes.rs:1084–1109`). Its logical row identity intentionally excludes *every* managed column (`preprocess.rs:553–565`), including actor. Its SQL fence therefore recognizes the later submission as AlreadyCommitted (`vala-sql/.../scribe_batch_commits.rs::matches_logical/resolve`; `scribe/shards.rs:3643–3656`) and suppresses the second insertion. In-memory duplicate/replay handling uses the same logical identity, so changing shard or retry timing cannot restore the missing publisher.

Observable consequence: OTLP can successfully acknowledge the second publisher's submission while retaining only the first publisher's actor. This is evidence attribution loss, not cross-tenant access. Honest retries with the **same** pair should still converge; changing publisher actor is a different authenticated attribution, just as changing subject is already explicitly protected by the existing Gate batch-ID contract. The new actor propagation was added by imported main, but this is the exact telemetry seam it changes, not an unrelated main feature request.

Smallest testable correction: extend the existing Gate-owned deterministic OTLP identity to bind the verified `Attribution` pair rather than subject alone, using `auth.attribution()` already passed to Scribe. Preserve the existing logical digest, Card/Run digest, request/time exclusion and durable fences; do not add an exporter cache, new replay service, per-framework credential owner, row-level tenant column or a second identity resolver. All three signals share `dispatch_canonical`, so fix once there. Do not change native caller-supplied batch-ID semantics as part of this correction.

Focused closure proof: extend the existing Gate deterministic-identity test to distinguish `(A,A)`, `(A,B)` and `(A,C)` for identical projected rows while keeping retries of each pair stable. Add the smallest existing real OTLP authenticated journey variation that submits one exact batch first as A and then as A-through-B, repeats the latter, and queries subject/actor: retain one row per pair and no duplicate for the repeated pair. Use existing delegation/client/server fixtures; no framework rerun or new harness is needed to demonstrate this server-owned seam. Current ordinary framework journeys cannot detect it because they use direct principals and fresh span identities.
