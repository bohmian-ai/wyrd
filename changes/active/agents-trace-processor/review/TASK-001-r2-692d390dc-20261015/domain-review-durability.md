## Delivery and failure paths

Completed framework callbacks end ordinary OTEL spans; managed batch processors hold them independently of the native observation writer. State flush/shutdown first invokes the retained provider, then drains its existing native writer. The two lanes do not share a queue: native flush cannot rescue a telemetry export already dropped by its stock exporter. Active spans are not ended by state flush. Bridge shutdown separately ends its unfinished spans and clears bridge resources, without closing the provider.

On native transport uncertainty, existing writer ownership remains available for retry on the same state. On successful native shutdown but failed OTEL flush, the writer is closed while the provider remains usable; retrying state shutdown can retry its provider stage and the idempotent native stage. A process kill can still lose in-memory telemetry/native pending work. OTEL sampling/export loss and Bifrost query-cut best effort remain existing limitations, not defects requiring stronger persistence in this task.

## Proposed material findings

### DUR-01 — INCORRECT: Python's managed batch pipeline does not honor a bounded force-flush

- **Obligation:** REQ-013 requires a bounded completed-span flush before the native drain; false timeout/failure must be reported and must not prevent the native drain attempt. AC-009 requires credible failure proof using the real lifecycle mechanism.
- **Location:** `sdks/wyrd-sdk-python/python/wyrd/otel.py:232–234` constructs the default synchronous `TracerProvider` and its `BatchSpanProcessor`; `sdks/wyrd-sdk-python/src/state/mod.rs:506–508` directly calls that provider's `force_flush`. Both `flush` (`:277–280`) and `shutdown` (`:299–302`) depend on this returning before native drain.
- **Evidence:** Locked `sdks/wyrd-sdk-python/uv.lock:2592` and installed SDK metadata both identify OpenTelemetry SDK 1.42.1. Its installed primary source, `.venv/lib/python3.12/site-packages/opentelemetry/sdk/_shared_internal/__init__.py:239–246`, explicitly says `TODO: Fix force flush so the timeout is used` and implements `force_flush` as synchronous `_export(EXPORT_ALL); return True`. `_export` (`:167–199`) acquires `_export_lock`, then exports all batches synchronously. The default `SynchronousMultiSpanProcessor.force_flush` (`opentelemetry/sdk/trace/__init__.py:193–221`) checks the deadline only before each child; it cannot interrupt the blocking batch processor. Thus merely calling the nominally bounded provider API does not enforce the promised bound.
- **Reachability/consequence:** A normal managed Python application with completed spans can call state flush/shutdown during slow OTLP/auth IO or while the batch export lock is held. The batch processor may spend multiple export timeouts draining batches (or wait for an in-flight export) beyond the provider's 30-second force-flush limit; the native observation drain is delayed throughout. Default correlation processor ordering may eventually turn the overrun into `False`, but only after the blocking batch operation returns. The unit injection at `tests/unit/state/test_observe_surface.py:807–813` substitutes a preselected bool/exception and cannot discover this.
- **Minimum correction:** Correct the managed provider composition using an existing stock OTEL mechanism that actually enforces its flush deadline for the locked version. The installed SDK explicitly documents `ConcurrentMultiSpanProcessor` for bounded parallel flush (`trace/__init__.py:299–323`, `:1458–1480`); assess and reuse that supported composition rather than adding a Wyrd queue, retry policy, public timeout, or provider shutdown. Preserve stock best-effort delivery and the global provider's continued usability. If the chosen stock mechanism is insufficient, report the exact limitation rather than silently promising a bound or inventing persistence.
- **Closure proof:** Exercise the actual managed stock processor with an exporter blocked past a short SDK flush bound, release it after observing the state result, and establish the timeout code plus native drain attempt and eventual provider usability. Do not mock `force_flush` to return the desired result. A runtime-local test is allowed by REQ-016; no live provider or new durable queue is necessary.

### DUR-02 — MISSING: managed framework journeys do not prove flush/readback while the state remains usable

- **Obligation:** REQ-016 explicitly requires “flush while alive”; AC-009 requires flush visible while alive with active spans/global provider surviving. AGENTS §11 requires user-facing successful cross-boundary behavior to have journey evidence.
- **Location:** Python `tests/integration/otel/frameworks/app.py:338–344`, consumed by `test_framework_telemetry.py:129–139`; TS `tests/integration/agents-trace-processor.test.ts:203–211` (same shutdown-before-readback pattern in remaining managed cases).
- **Evidence/reachability:** Python launches the framework subprocess, calls `state.shutdown()`, exits, and only then the parent reads Bifrost. TS calls `await state.shutdown()` before querying. No framework journey calls state flush. Neighboring Python local-development/action-timeline journeys also shut down before readback; TS's observation-surface `state.flush()` exercises native backpressure without a managed provider. Unit lifecycle tests use a never-started native writer and substituted provider outcomes. Therefore the implementation-evidence claim that J1/J2/K1/K2 prove readback “after flush” is inaccurate.
- **Consequence:** A regression where managed flush fails to export, closes the writer/provider, or prevents subsequent execution can pass the delivered framework matrix. The new public flush behavior's key distinction from shutdown lacks the required successful journey proof.
- **Minimum correction:** Extend the existing managed framework journeys to read a completed framework turn after `state.flush()` and before shutdown; continue a subsequent turn/write with that same state/provider and finally shut down. Preserve the existing supported setup and real SDK/server readback. Keep an active span open across flush and prove it can finish/export afterward where practical. Application-owned provider journeys remain application-owned; do not make state flush those providers.
- **Closure proof:** Existing Python framework parameter cases and TS OpenAI managed selector assert first-turn readback before shutdown and second-turn readback through the same live provider/state. Native startup is needed for a successful state flush because the approved native not-started refusal remains applicable.
