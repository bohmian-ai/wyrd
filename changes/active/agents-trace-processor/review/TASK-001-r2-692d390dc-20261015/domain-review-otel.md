## Proposed findings

### OTEL-001 — INCORRECT: managed Python flush relies on a timeout the pinned batch processor ignores

- Obligation: REQ-013 / AC-009 requires a bounded managed flush, followed by native drain even on telemetry timeout; no custom export queue/retry or public timeout API.
- Changed location: `sdks/wyrd-sdk-python/src/state/mod.rs:506–510`; affected callers `flush:277–280`, `shutdown:299–302`; pipeline construction `sdks/wyrd-sdk-python/python/wyrd/otel.py:231–234`.
- Evidence: construction uses default `TracerProvider()` and `BatchSpanProcessor`. Pinned `opentelemetry/sdk/trace/__init__.py:1311–1322` selects `SynchronousMultiSpanProcessor`; its `force_flush:193–221` checks deadlines only between processor calls. `sdk/trace/export/__init__.py:232–233` delegates to `BatchProcessor.force_flush`. Pinned `sdk/_shared_internal/__init__.py:239–246` explicitly notes the timeout is unused, synchronously invokes `EXPORT_ALL`, then returns true. `_export:167–184` waits on `_export_lock` and exports all queued batches. Wyrd calls this directly before invoking either native drain.
- Reachable consequence: slow/stalled export or waiting behind an in-progress export holds `state.flush()` / `shutdown()` beyond the documented flush bound and delays native observations behind telemetry. Multiple slow batches can exceed the provider's default 30 seconds; a transport call that never completes prevents the native drain entirely. Existing unit tests replace `provider.force_flush` with immediate false/exception/success and cannot catch this composition defect.
- Smallest correction boundary: make the **managed pipeline's flush composition** actually honor the existing SDK bound using stock OTEL capabilities, preserving synchronous start-time Run correlation and the ordinary batch export path. No new queue, retry subsystem, public timeout option, permanent provider closure, or changes to application-owned providers. The installed SDK has a bounded `ConcurrentMultiSpanProcessor.force_flush` (`sdk/trace/__init__.py:299–325`), but simply replacing the provider's entire processor owner is unsafe: its callbacks run on executor threads (`:263–285`), and correlation with `parent_context=None` currently reads the caller's context. Any reuse must preserve that correlation owner and avoid making ordinary `on_start`/`on_end` wait behind a blocked export. This is a constraint on the correction, not approval of that blind substitution.
- Focused closure proof: use the real managed stock processor with an exporter blocked on a controlled event and a short test-only flush bound; verify timeout error and native drain while export is still blocked, then release it and prove provider usability plus nested/current-context correlation. Do not replace `force_flush` with an immediate fabricated false to prove this gap.
