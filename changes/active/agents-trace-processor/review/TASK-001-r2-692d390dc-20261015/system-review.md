## Proposed findings

### SYS-001 — INCORRECT: Python managed flush has no effective total OTEL deadline

**Obligation:** REQ-013, AC-009 require a bounded managed-provider flush before the native drain; expiration must report `WYRD_SDK_504_TELEMETRY_FLUSH_TIMEOUT` and must not prevent the native drain attempt.

**Changed source:** `sdks/wyrd-sdk-python/src/state/mod.rs:506-510` directly calls `provider.force_flush()`; both newly changed lifecycle callers wait for it before native drain (`:277-280`, `:300-303`). The managed provider is constructed with its default synchronous processor composition in `sdks/wyrd-sdk-python/python/wyrd/otel.py:232-234`.

**Root-cause evidence:** `sdks/wyrd-sdk-python/uv.lock:2591-2593` locks opentelemetry-sdk 1.42.1. Its installed source at `.venv/lib/python3.12/site-packages/opentelemetry/sdk/_shared_internal/__init__.py:239-245` explicitly notes that force_flush does not use its timeout and synchronously drains all queued exports. `_export` at `:167-188` takes an export lock and loops over batches. The SDK's default `SynchronousMultiSpanProcessor.force_flush`, `sdk/trace/__init__.py:193-220`, checks its deadline only between processors; it cannot interrupt that batch drain. These are dependency sources, not proposed edits. The stock implementation is also visible in the [OTEL trace SDK source documentation](https://opentelemetry-python.readthedocs.io/en/latest/_modules/opentelemetry/sdk/trace.html).

**Reachable consequence:** During a slow or unavailable Wyrd dependency, several sequential export batches (or waiting on an already exporting background batch) exceed the provider's nominal 30-second force_flush bound. Continued framework emission can keep the EXPORT_ALL loop busy. The synchronous application `state.flush()`/`shutdown()` remains inside OTEL; native observation queues are not drained at the promised bound. A finite job or pod can reach its termination deadline and lose native rows although the feature expressly promises to attempt that drain after telemetry timeout. The error conversion added here only works after this call returns.

**Sibling/owner analysis:** Both Python public lifecycle methods share `flush_telemetry`; fix the managed Python lifecycle/composition once. Application-owned providers must remain application-owned. TS already uses a distinct OTEL implementation; Rust/log/metric redesign is excluded. Do not add a persistent queue or retry system. Existing SDK `ConcurrentMultiSpanProcessor` has a bounded wait, but blindly replacing the entire provider composition is not safe: it moves Run-correlation hooks to worker threads, and normal `parent_context=None` relies on caller context. Any use of SDK concurrency must also ensure a still-running timed-out export cannot block subsequent synchronous span emission through executor saturation. Preserve correlation and application availability when selecting the smallest existing/runtime mechanism to bound lifecycle waiting.

**Required testable correction:** Make the actual managed Python pipeline enforce its existing configured lifecycle bound, return a false/timeout outcome to the shared catalog conversion, and proceed to native drain while leaving provider/export ownership usable. Preserve origin-context Run correlation, active spans, no new public timeout setting, and no extra exporter queue/retry policy. Add deterministic supporting proof that holds an actual managed processor/export flush beyond a small internal test deadline (release it in cleanup), invokes public state lifecycle without mocking away provider force_flush, observes the 504 and native drain, then releases the export and verifies subsequent span/correlation/flush still works. The existing test at `tests/unit/state/test_observe_surface.py:807-813` replaces `provider.force_flush` entirely and cannot prove this behavior.

### SYS-002 — MISSING: no real journey proves managed flush before shutdown

**Obligation:** REQ-016 explicitly requires successful flush journeys; AC-009 requires visibility while alive and surviving provider/active spans. Unit-only injection is expressly permitted for failure branches, not successful flush.

**Exact sources:** Python framework journeys `tests/integration/otel/frameworks/test_framework_telemetry.py:116-124` wait for `launch()` to finish; the child only calls `state.shutdown()` at `frameworks/app.py:338-344` before returning/exiting. TS `tests/integration/agents-trace-processor.test.ts:203-211` calls state shutdown before readback; edge and gateway cases likewise use shutdown (`:254`, `:334`). No framework integration calls state flush. Owned-provider cases also terminate the provider before query. `server.flush_bifrost()`/`server.flushBifrost()` in reader helpers publishes server state and does not exercise the new SDK method.

**Consequence:** These tests would still pass if the newly changed `state.flush()` omitted OTEL export, closed the provider, or closed the native writer. They establish shutdown export, not the requested live-job lifecycle contract. This is a concrete acceptance gap on a changed public capability, independent of SYS-001.

**Required testable correction:** Extend the existing real-server/framework journey owners, using their existing application/server fixtures, to call managed state flush with the native writer started, query back the completed framework spans before shutdown/process exit, then execute/export additional work and confirm provider and writer remain usable. Keep an active span open across flush to prove it remains active and subsequently ends normally. Retain shutdown coverage. Python subprocess coordination may use the existing app/launch owner; do not add a parallel harness or substitute an in-memory exporter. Cover Python and TS public managed lifecycle surfaces; do not require unrelated full journey suites for this correction.
