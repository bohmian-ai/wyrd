## Proposed findings for validation

### D1 — INCORRECT: discovery recipient throttling exposes whether SMTP was attempted

- Authority: REQ-017 final paragraph: recipient throttles and comparable timing must never expose account existence or delivery; C12 S3 promises silent recipient throttling.
- Location: `crates/wyrd/wyrd-auth/src/social/discovery.rs:86–110`, calling `admit_email` at `social.rs:1553–1610`; `ApplicationMail::send_notice` at `mail.rs:392–423`.
- Starting conditions/trigger: SMTP is configured but slow or refuses a message. Request discovery for an address below its five-message recipient budget, then for the same address after that budget is exhausted, while source admission remains available.
- Expected: recipient suppression and delivery outcome do not distinguish public answers/timing. A deployment-wide outage may have an operator-visible consequence; per-recipient budget state must remain private.
- Actual: below budget `begin_discovery` awaits `send_discovery_proof(...).await?`. A refusing relay produces503; above budget the same request skips SMTP and returns202. A slow healthy relay similarly adds its latency only below budget. This needs no registered account and directly reveals per-address send/budget state. No account-membership leakage is claimed.
- Evidence: the source's `if send` encloses the awaited send and error propagation. The existing C12 budget journey uses healthy Mailpit and checks only status/body/mail count; it cannot detect the status split under failure or recipient-dependent wait.
- Smallest testable correction: keep delivery/suppression outcomes outside the public discovery response distinction at the existing discovery/mail owner, preserving admission-before-send, bounded work, no queue/retry, neutral mail, and no delivery promise. Reuse the existing transient-send mechanism where its responsibility fits; no new durable subsystem is required. Add one focused real HTTP/controlled relay journey comparing below-budget and suppressed requests under delayed/refused SMTP, with identical generic response and comparable timing while observing the send count separately.

### D2 — EVIDENCE_GAP: pre-proof contact/discovery expiry has no executable proof

- Authority: REQ-017 fifteen-minute email-proof lifetime and refusal after expiry; task C12 proof-expiry scenario.
- Location: `social/contacts.rs:206`, `social/discovery.rs:153`, shared `SocialSignIn::require_live` at `social.rs:2157`; task C12 evidence explicitly leaves pre-proof envelope expiry unproven.
- Starting conditions/trigger: a valid bound contact or discovery email envelope reaches its original deadline before its first successful verification, then its actual mail proof is posted.
- Expected: refusal, no contact/revision change, no discovery read authority, and no proof consumption granting renewed time.
- Actual proof: read expiry is tested only by aging an already-spent SQL row; no test exercises the sealed email envelope deadline. The shared source check exists, so this is not an assertion that implementation accepts expired proofs.
- Smallest correction: focused executable proof of first-use expiry through the actual flow, preserving the existing clock owner and no production behavior churn merely to manufacture RED. Test each materially distinct contact mutation/discovery-read outcome with deterministic approved time control or valid elapsed-deadline execution. Do not equate a spent-read expiry test with the earlier email-envelope boundary.
