## Proposed blocking finding INV-1 — Removed platform OIDC sessions can revive when the connection is reinstalled

Classification: **INCORRECT**. Requirement: REQ-018's original connection anchor and invalidation rule, AC-013 connection revision invalidation, and security posture platform console session paragraph requiring that connection replacement refuses anchored sessions. Severity is material security lifecycle correctness: a removed trust configuration must not silently make its old browser authorization valid again when an operator configures a replacement.

Exact locations:

- `crates/wyrd/wyrd-sql/src/queries/platform/identity.rs:141`: `delete_platform_oidc_connection` only executes `DELETE FROM platform.oidc_connection`.
- The same file at line 102: `upsert_platform_oidc_connection` omits `revision` on INSERT; only its conflict update increments it.
- `crates/wyrd/wyrd-sql/migrations/20261123000001_platform_console_sessions.sql:22`: the connection revision defaults to `1`.
- `crates/wyrd/wyrd-sql/src/queries/platform/console.rs:206`: session resolution accepts an OIDC session whenever a current singleton has the saved numeric revision; it has no connection-incarnation/issuer anchor and does not persist invalidation on a failed resolution.
- `crates/wyrd/wyrd-server/src/components/platform/identity.rs:546`: the supported DELETE endpoint calls that deletion owner and commits with no additional invalidation.

Starting conditions and trigger: configure the initial platform OIDC connection (revision 1), sign in a registered operator and retain its still-live cookie. An authorized platform API operator deletes the connection and then configures a connection again before the cookie's idle/absolute deadline. This can be the same issuer, or a different issuer; the reinstated singleton again has revision 1. A request with the old cookie now resolves and reaches authorized platform operations without a new human sign-in.

Expected: removal/replacement permanently invalidates that original connection's browser session; reinstalling configuration cannot restore its authority. Actual source path: deletion leaves the unrevoked session, reinsertion reuses revision 1, resolver's `EXISTS ... revision = s.connection_revision` becomes true again. The old cookie is accepted. The same revision-reuse cause also leaves an unconsumed browser login usable after removal and reinstallation of the same issuer/configuration: `take_platform_login_state` retains the old transaction, `verify_return` sees the same issuer and `complete_browser` sees revision 1 again.

Existing proof does not catch it: `a_registered_operator_signs_in_to_the_console_through_platform_oidc` (`console.rs:885`) exercises a conflict-update replacement that increments revision, while `the_platform_entry_reads_its_sign_in_methods` ends after deletion and never retries an old cookie/state after recreation.

Smallest correction boundary: retire the old OIDC browser sessions and browser login/re-authentication transactions in the existing authorized connection-removal transaction, so the singleton revision may never resurrect their authority. Reuse the current SQL owner, session revocation and login-state lifecycle; do not introduce a new persistence purpose, migration or authentication engine. An equivalent correction that preserves unique incarnations is acceptable, but no schema change is necessary to satisfy this case. Preserve password sessions and CLI/API behavior.

Observable closure: extend a focused real Rust HTTP → repository Postgres/controlled IdP journey to sign in, retain an unfinished browser transaction, remove and reinstall the connection, and assert that the old cookie remains 401 and the old transaction cannot issue/refresh a session. Exercise reinstall with the same issuer (pending-state case) and a different issuer (cookie anchor case); verify new sign-in works and password/API access remains available. A SQL regression can additionally pin the atomic owner effect. This is an implementation defect established from the complete source path, not a claim of a newly executed failing test.
