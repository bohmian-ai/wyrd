## Findings proposed for independent validation

### INV-01 — INCORRECT: sealing-key rotation resets the owned-workspace cap

- **Requirement:** REQ-014 owned-workspace cap: each proven identity may hold at most the configured number of non-retired signup-created tenants, atomically across replicas; creator accounting persists beyond proof purge. Security posture lines 489–506 reiterate keyed creator accounting and the per-identity bound. Supported existing rotation is documented in `AuthConfig` (`crates/wyrd/wyrd-server/src/config.rs:3183`): stage retained keys, switch write key, restart and rewrap, then remove old keys when no sealed value needs them.
- **Location:** `crates/shared/wyrd-crypt/src/lib.rs:301–316`, especially `pseudonym` at line 310; `crates/wyrd/wyrd-auth/src/social.rs:1725–1737`; `crates/wyrd/wyrd-sql/src/queries/platform/provisioning.rs:110–127`.
- **Starting state / trigger:** cap 1, identity S owns one non-retired signup tenant created under sealing write key A. Purge its old attempt (a specifically required supported state). Rotate through the documented keyring procedure to write key B retaining A. S proves its identity again and requests a second workspace. The same split also exists during rolling restart while replicas have different write keys.
- **Expected:** the second claim refuses with `WYRD_AUTH_403_SIGNUP_WORKSPACE_LIMIT`; retaining or rotating encryption keys does not make the existing workspace stop belonging to S for cap accounting.
- **Actual:** `SealingKeyring::pseudonym` derives exclusively from `self.write.1`, deliberately ignoring retained keys. `creator` therefore changes from HMAC-A to HMAC-B. The SQL advisory lock and count both use only that single current pseudonym, and the count finds zero rows stored with HMAC-B. A second claim is admitted; mixed-write-key replicas also take different advisory locks and separate counts. Creator keys are not sealed values, so the existing secret rewrap does not repair them. The task's cycle-3 record explicitly acknowledges this risk; acknowledging it does not waive the cap.
- **Evidence strength:** exact source composition establishes the mismatch, supported rotation path exists in `boot/mod.rs::build_sealing_keyring` (2225–2239), and cycle-8 journey at `tests/integration/platform_admin_e2e/signup.rs:1358` exercises only one write-key namespace. No execution claim is made for the missing rotation case.
- **Consequence:** a supported operator maintenance action silently clears a persistent abuse-control bound; during a rollout the same identity can exceed the bound across replicas.
- **Smallest correction boundary:** preserve one creator-accounting identity and lock domain across the supported deployment key lifecycle at the keyring/pseudonym and SQL-claim owners. Reuse those owners; do not add a global person or unify identities by email. Preserve pseudonymous counters and existing sealing rotation. Checking only the new key, or retaining old keys without matching their creator records, does not close the defect; merely summing held-key matches without a common cross-replica lock is insufficient during rollout. Private helper and storage details remain the implementer's choice within the approved persistence purposes.
- **Closure scenario:** through real signup HTTP, fill a cap, purge the attempt, rotate A→B retaining A using the real server/keyring configuration, and verify the same identity's next claim is forbidden and no new tenant exists. Race two different attempts through replicas spanning the supported rotation and assert the configured bound remains. Verify completion-cookie decryption and ordinary existing tenant login still work. Use a focused server journey under the existing Postgres/server setup wrapper; retain the existing cap/purge journey and keyring unit checks.

### INV-02 — INCORRECT: generic operator creation can restart an expired signup claim

- **Requirement:** REQ-014 crash recovery: only the proven attempt's browser holder may restart its stale signup creation within the five-minute window; after proof expiry nobody may restart it, and the tenant remains non-active failed/provisioning until operator retirement. The task's cycle 7 repeats own-attempt recovery and expired-proof refusal. This finding preserves that settled distinction; it does not request a new retirement workflow.
- **Location:** `crates/wyrd/wyrd-sql/src/queries/platform/provisioning.rs:45–57` (`insert_provisioning_tenant` conflict adoption); caller `crates/wyrd/wyrd-server/src/components/platform/provisioning.rs:203–239` (`claim`) and 262–300 (`provision`); public route `components/platform/routes.rs:235–258` (`create_tenant`).
- **Starting state / trigger:** a visitor's signup claim fails, or remains `provisioning` for more than 15 minutes, and its proof expires. An authenticated operator uses the ordinary `POST /platform/tenants` to create that same slug, without the completion cookie. This is particularly easy after the proof row has been purged; the durable creator marker remains by design.
- **Expected:** ordinary tenant creation does not adopt that signup claim. The expired signup remains non-active until the authorized retirement lifecycle; ordinary operator-created failed claims remain recoverable through their existing path.
- **Actual:** `insert_provisioning_tenant` adopts every `failed` row or stale `provisioning` row on slug conflict. Its WHERE clause checks neither signup ownership nor proof validity. `TenantProvisioning::claim` passes the adopted tenant ID to the ordinary bootstrap owner; `provision` initializes a machine administrative credential and promotes it. Thus a signup tenant explicitly forbidden to restart becomes active through a sibling public operation. The signup-specific claim query correctly checks attempt identity, but it is not the only writer of these directory rows.
- **Evidence strength:** exact public caller-to-SQL-to-promotion path. The current recovery journey (`completion_consumes_either_proof_and_recovers_its_own_claim`, `signup.rs:1097`) tests foreign public proof and expired public completion, including a 20-minute-stale claim near line 1280; it never attempts operator creation against that same slug. The cap journey's operator case near line 1505 uses a fresh slug only.
- **Consequence:** the signed-proof expiry and exclusive resumption boundary can be bypassed using a supported sibling operation; expiry no longer guarantees the non-active state promised by REQ-014.
- **Smallest correction boundary:** make the shared directory adoption owner distinguish signup-created claims from operator-created claims. The creator marker must remain authoritative after `signup_attempt_id` is cleared by purge; guarding only a currently present attempt ID leaves the same gap after cleanup. Refuse ordinary creation's adoption of signup-owned claims, preserve ordinary operator retry/recovery, and retain the same signup attempt's valid recovery path. No new principal, recovery engine, or migration purpose is required by this finding.
- **Closure scenario:** create/stage an interrupted signup through the existing journey fixture, expire its proof and make it stale, then attempt the same slug through authenticated `POST /platform/tenants`. Assert a conflict, unchanged tenant ID/non-active state and no bootstrap credential/User/grant side effects. Repeat after actual bounded attempt purge so FK nulling does not remove ownership protection. Separately retain a successful same-attempt live-proof resume and ordinary operator-owned failed-claim recovery. Use the focused `platform_admin_e2e` server journey with repository Postgres; no broad suite is needed to discover this regression.
