# Independent focused validation: FIND-003-carryover-12

**CONFIRMED: R3 incompletely closes -12 for a callback already exchanging its authorization code when connection removal occurs.** This is the existing original-anchor invalidation obligation, not a new product requirement or a migration issue.

Immutable candidate `5ea7aa8ce310b33dc8cebb139aa5202c7b67b5a4`; prior `dfb3599d5fbfb3d863ecb68382257cb30abfd79b`. Read the task-review skill, SQL AGENTS and platform-console security authority; CodeGraph preceded source tracing. Inspected the direct SQL correction, complete callback-to-session path, affected identity checks and new closure assertions. No runtime reproduction or source change is claimed.

## Source-backed supported interleaving

1. A registered, already pinned operator starts ordinary platform browser OIDC login against the initial connection at revision1. `PlatformLogin::verify_return` (`wyrd-auth/src/platform_login.rs:455–464`) loads that connection and takes the bound login state. `take_platform_login_state` (`wyrd-sql/src/queries/platform/identity.rs:301–325`) uses a `DELETE ... RETURNING` on `pool.pool()`; it finishes before the function continues. Thus the row is already absent and its binding/revision are only in process memory.
2. That callback enters the actual remote code redemption (`platform_login.rs:500–519`). It can naturally wait on a slow provider. There is no held transaction, row lock or shared administrative lock spanning this wait.
3. An authorized API operator removes the connection and reinstalls it while that remote exchange is pending. R3 `delete_platform_oidc_connection` (`identity.rs:145–160`) correctly deletes remaining stored transactions and revokes existing anchored sessions in the authorized removal transaction. It cannot remove the already-consumed transaction or revoke a session not yet created. The HTTP handler commits removal (`wyrd-server/src/components/platform/identity.rs:546–569`); the supported upsert reinstall omits revision on INSERT (`identity.rs:102–132`), restoring the schema default1 (`20261123000001_platform_console_sessions.sql:21`). Principals/pinned identities intentionally survive removal.
4. The delayed provider returns a valid token for the original issuer, nonce and registered subject. `complete_browser` (`platform_login.rs:397–443`) compares the in-memory login revision with the in-memory connection revision; both remain1. It never revalidates durable transaction liveness after redemption.
5. `PlatformSessions::browser_federated` (`platform_sessions.rs:415–434`) now opens a new audited transaction. Its `federated_principal` (`platform_sessions.rs:131–153`) resolves the still-active pinned operator against the original issuer; that check does not establish the current connection incarnation. `create_browser` (`platform_sessions.rs:446–465`) calls the SQL insert, then commits.
6. `insert_platform_browser_session` (`queries/platform/console.rs:148–190`) checks the active principal and merely `EXISTS ... oidc_connection ... revision = $5` for the connection anchor (`:172–173`). The reinstalled revision1 satisfies it. The callback therefore creates a fresh, unrevoked platform browser session after the removal transaction already finished.

No restrictive snapshot or serialization assumption defeats this interleaving: schedule removal and reinstall to finish before the callback opens its final issuance transaction. Deleting the stored login state is irrelevant after the earlier autocommit consumption. A same-issuer reinstall alone demonstrates the defect; a different issuer is not necessary to establish materiality.

Expected behavior under approved REQ-018/AC-013, security posture “Platform console browser sessions,” and R3 scenario1 is that removing/replacing the original trust configuration invalidates its browser authority and unfinished login. Actual behavior lets a previously started callback issue new authority from the removed connection. Ordinary operator maintenance concurrent with a provider response is a supported deployment scenario; no adversarial scheduling or new availability promise is required.

## Why the new test misses it

`platform_admin_e2e::console::removing_platform_oidc_ends_its_sessions_for_good` (`console.rs:930–1041`) starts pending login/reauth transactions, performs removal and reinstall, and only then calls the callback (`:984–1008`). It proves stored-state deletion and already-issued-cookie revocation. It does not start a callback, observe its token request, remove/reinstall during that remote wait, then release the token response. The test's GREEN is valid for its assertions but insufficient to establish complete -12 closure.

## Smallest correction and closure boundary

Complete invalidation at the existing platform login/session/connection SQL owners: final session issuance must depend on durable original-login/connection validity that deletion can permanently invalidate, including a callback already past provider exchange initiation. Reusing login-state ownership until atomic final consumption/session issuance is one existing-store approach; an equivalent complete existing-owner fence is acceptable. Do not rely on deleting only rows that may already have been consumed, on repeated numeric revision1, or on a non-atomic pre-insert recheck. Preserve one-use callbacks, password sessions, separate API/break-glass access and nonblocking audit. Do not hold a database transaction or lock across remote provider IO. This report requires no new migration, persistence purpose or authentication engine.

Extend the existing real HTTP/Postgres/controlled-OIDC journey: begin callback, let the controlled token endpoint signal that redemption has started and delay its response, remove/reinstall through the API, then release the valid original token. Assert callback refusal/no new platform cookie or usable session, and separately confirm fresh login plus password/API access. Keep the current sequential removal regression. This is the narrow testable completion of the existing finding, not a demand for historical RED or a whole-suite rerun.

Skipped runtime execution and other R3 findings. The retained risk is post-removal issuance of fresh browser authority from an already-running old OIDC callback.
