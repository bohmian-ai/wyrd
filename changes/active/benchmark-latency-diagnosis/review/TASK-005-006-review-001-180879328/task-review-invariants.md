## Proposed findings

### INV-001 — Committed pre-upgrade limits disappear from the new baseline

- Classification: **INCORRECT**, TASK-006.
- Violated obligation: revision-7 REQ-031 explicitly preserves committed historical usage and requires restart to load committed shared usage before admission. TASK-006 failure/recovery scenario likewise says restart uses committed totals.
- Exact changed location: `crates/wyrd/wyrd-sql/src/queries/gateway_admission.rs:146-159` (`WINDOWS_SQL`, `CONCURRENCY_SQL`), with migration `20261111000000_gateway_usage_contributions.sql:10-26`.
- Producer-to-consumer proof: the prior release's `gateway_admit`/`gateway_settle` persist requests/tokens in `wyrd.gateway_limit_windows` and active calls in `wyrd.gateway_call_leases` (migrations `20260924000001`, `20261023000001`). The candidate migration creates empty contribution tables and deliberately leaves old tables active for rolling old servers. Candidate `sync_gateway_usage` reads only `gateway_usage_windows` and `gateway_usage_concurrency`; no migration or SQL query transfers/includes the old counters/leases. `GatewayUsage::apply` installs that zero baseline; `admit` then sees free quota for the same tenant and canonical limit key.
- Reachable scenario and consequence: a tenant spends its minute request/token quota on the prior version, then an upgraded process warms during that minute (or old and new processes coexist as explicitly supported by the migration). The new process admits a full additional quota even after successful PostgreSQL refresh. Similarly it ignores committed old-process calls still running under concurrency limits. This is systematic omission of already committed usage, rather than the approved delay before new in-memory contributions become mutually visible. Monetary reservations do not have this defect because spend still reads the shared accounting ledger.
- Materiality: supported deployment/restart crosses a durable-owner boundary and fails the explicit preservation requirement. The accepted crash-loss exception applies to uncommitted memory, not these committed rows.
- Smallest correction: extend the existing background SQL baseline reads to aggregate the retained old-format current-window counters and unexpired old-format call leases alongside the new per-server contributions. Keep new writes exclusively per-server and keep RLS/SQL-owned expiry. Reuse the existing durable owner; do not add a service, dual-write requests, reprice budgets, or change approximate enforcement. Reading retained old rows avoids a new rolling-version coordination protocol or one-shot copy that misses later old-server writes.
- Focused closure proof: through the existing PostgreSQL fixture, seed current old-format window usage and an unexpired old-format lease, warm a new Gateway, and prove those committed facts affect admission. Then exercise old-row update/lease completion plus refresh and a new-server contribution, showing aggregation without double counting or overwriting. Cover another tenant isolation with the same existing fixture. No broad journey suite needed for this correction.
- Burden: bounded SQL read extension and one focused upgrade regression; deletion alone cannot retain usage and an additive migration copy alone cannot cover ongoing old-version writers.
