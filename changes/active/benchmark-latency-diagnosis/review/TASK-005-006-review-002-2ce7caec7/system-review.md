## SYS-R2-001 — A full reload queue can still discard a fenced reload and serve obsolete policy indefinitely

Stable prior ID: **FIND-006-5**; classification **INCORRECT**, incomplete remediation of its original lost-obligation cause. Violated authority: REQ-030 bounded background recovery and generation fencing; INV-001 retained governance/credential/capture semantics; R1 requires a reload to remain owed until current-generation installation or existing cache-miss refusal/recovery. Location: `crates/wyrd/wyrd-server/src/components/gateway/snapshots.rs:79–82,192–215` with consumers `cached:118–123`, `admitted:128–138`.

Supported deployed path:

1. A replica has cached tenant A policy. An A notification advances generation and queues A. Reload worker drains A and starts its asynchronous database load under generation g.
2. During that load, committed configuration changes for 4096 other distinct tenants fill the existing bounded reload set. Notifications advance the global generation, so the A load is correctly fenced. The queue accepts notifications even for tenants outside the snapshot LRU; its bound does not reserve space for drained/in-flight tenants.
3. `install(A,g,Ok(snapshot))` rejects the insertion, then calls `requeue(A)`. `Entries::queue` silently discards A because the set is full. The worker later drains those other tenants and finishes; nothing records an A obligation.
4. A still has the old cached snapshot: fenced success does not pop it. Both admission and listing continue returning it without scheduling reload. A healthy listener and periodic usage refresh do not repair policy. Without another A edit/eviction, obsolete policy persists indefinitely.

This is a bounded-capacity failure path in the existing multi-tenant topology, not an expanded demand to support unlimited cache entries. A slow database load during bulk configuration changes is sufficient. The approved bounded behavior is retryable refusal/recovery, not silently retaining an unusable policy. The meaningful consequence is the same original defect: a replica can indefinitely ignore a committed quota/deployment/credential/capture-policy update. Ordinary approximate usage visibility does not permit that governance failure.

Sibling writers/consumers considered: `invalidate` and cache-miss `admitted` produce queue entries; `reset` queues forgotten snapshots; background `reloads` drains; admin `service::snapshot` can install a generation-matched current snapshot. The common bounded queue is the correction owner. The error-install branch already removes A, so this report does not split it into another finding. Existing A/B tests leave queue capacity and cannot prove this boundary.

Smallest complete correction: retain boundedness and reuse `GatewaySnapshots` cache-miss refusal. When an owed fenced reload cannot be retained for retry, remove the tenant snapshot under the existing cache/queue authority so it cannot keep serving obsolete policy. Subsequent requests remain503 until a background current load installs. An atomic queue-or-forget decision at this owner is sufficient; no larger queue, new retry store, TTL, synchronous database fallback, or consumer guards are justified. Preserve unrelated tenants and listener generation fencing; do not evict a newer successfully installed snapshot blindly if administrative/background writers can race the fallback.

Focused proof: extend the existing in-process snapshot test with cached A, drained A reload, a full queue of other tenant IDs, then fenced A install. Assert A is either retained as owed or unavailable, never indefinitely served from the obsolete snapshot; drain queue and exercise the existing request/background recovery path to a current A snapshot without another A configuration edit. Use the existing bounded cache/fixture and narrow snapshot tests. No broad journeys, new load workload or benchmark is needed.
