## Proposed finding INV-R2-001 — FIND-006-5 remains incomplete when the reload queue fills

Classification: INCORRECT; incomplete prior remediation, not a new product requirement.

**Obligation.** REQ-030, INV-001 and TASK-006-R1 FIND-006-5 require a failed/fenced policy reload to remain recoverable and forbid serving obsolete policy indefinitely. Approved bounded-state behavior uses existing cache-miss 503; it does not permit discarding an owed policy update while continuing to serve that policy.

**Locations.** `crates/wyrd/wyrd-server/src/components/gateway/snapshots.rs:78–82` (`Entries::queue`), `:192–196` (`install` fenced success), `:210–215` (`requeue`), and sibling writer `:261–277` (`invalidate`). Consumer `admitted:128–133` continues returning cached A while live. Worker drains the queue before loading in `reloads:142–148` / `owner.rs:147–150`.

**Reachable producer-to-consumer path.** A is cached; its committed configuration update queues A. Worker drains A and starts a database load. While that load waits, notifications or cold-admission misses for 4,096 other tenant identities fill the bounded queue; notifications advance the global generation. A completes with an obsolete generation, so `insert` refuses it. `install` calls `requeue(A)`, which silently declines A because the queue is full. The previous A snapshot remains cached. After the worker drains/installs the other tenants, no A obligation remains. Normal requests keep reading A via `admitted` and never queue it. Listener heartbeat and usage refresh do not reload this policy; without another A edit, eviction or listener reset, the old routing/credential/capture/quota configuration persists indefinitely.

This is the original lost-obligation consequence at the newly added recovery edge. It matters for a supported multi-tenant server during a configuration batch or delayed snapshot query: bounded capacity must refuse affected work instead of silently losing a committed update. No claim of instantaneous revocation is made; ordinary notification/reload latency remains accepted. Only the indefinite loss blocks.

**Smallest complete correction.** Keep the existing bounded snapshot owner and work queue. At the authoritative queue/cache transition, make inability to retain an owed tenant invalidate its cached snapshot so that it cannot keep serving obsolete policy. A later request then uses existing cache-miss 503 and recovery queuing until capacity is available. Cover every writer of this same obligation, including `invalidate`, rather than adding a consumer guard or unbounded retry queue. Alternatively retaining each obligation until installation is sufficient only if it remains bounded and cannot silently drop cached tenants; a new queue or scheduler is unnecessary. Preserve listener fencing, asynchronous loads and healthy unrelated tenants.

**Focused proof.** Extend the existing snapshot unit test: cache A and a healthy unrelated tenant; drain A reload and record its generation; fill the existing reload queue with other identities through supported queue producers; finish A with the fenced generation. Prove either A is still owed or A cannot serve; after draining pressure and an ordinary A read, prove A reloads the new snapshot without another A configuration write. Also exercise a direct invalidation when the queue is full so the same shared cause is closed once. Check bounded queue size, existing retryable cache-miss behavior and unaffected healthy tenant serving. No 4,096-tenant database fixture, load generator, new harness or broad journey run is needed; the existing in-process snapshot fixture can exercise this exact branch.
