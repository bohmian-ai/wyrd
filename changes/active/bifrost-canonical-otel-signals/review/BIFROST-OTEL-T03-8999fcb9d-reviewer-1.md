#### FIND-BIFROST-OTEL-T03-1 — MAJOR: Trace detail silently succeeds with only the first 1,000 spans

- Obligations: revision-7 `REQ-009`, `INV-002`, `AC-001`; task Scenario 1 and selected contract at lines 111-115; `architecture/references/domain/olap-serving.md` prohibition on representing a truncated result as success.
- Locations: `crates/wyrd/wyrd-server/src/vala_query/routes.rs:786-790,819-825`; `crates/wyrd/wyrd-server/src/vala_query/grpc.rs:323-338`; `crates/wyrd-spec/src/vala/api.rs:416-418,439-460`; `crates/wyrd/wyrd-server/src/query/service.rs:361-376,399-466,509-527`; `crates/wyrd/wyrd-server/tests/pg_router_smoke.rs:908-911`.
- Current flow: both new `GetTrace` adapters call `run_typed_query(..., MAX_QUERY_PAGE_SIZE)`. The shared collector retains `limit + 1`, computes `has_more`, truncates to `limit`, and returns both values. Both adapters discard `has_more` and serialize the truncated batches as a successful non-paginated response.
- Reachable scenario and consequence: a valid trace with 1,001 or more matching spans reaches either HTTP or gRPC. The caller receives `OK` and exactly the first 1,000 spans with no continuation token and no error, although the contract promises one complete authorized cut. This is silent observation loss at a public read boundary.
- Supporting evidence: `MAX_QUERY_PAGE_SIZE` is exactly 1,000; the task removed trace pagination explicitly; the collector's `truncate_batches` is unconditional; the scenario journey asserts only a four-span trace and therefore cannot detect the threshold failure.
- Counterevidence: Oracle still decodes through the terminal frame and enforces the synchronous byte ceiling, so this is not an incomplete-stream or unbounded-collection defect. Those protections do not make the returned row set complete.
- Ponytail recommendation: reuse the existing `run_typed_query` collector and existing result-size refusal. In the HTTP and gRPC `GetTrace` owners, request a row ceiling that does not impose the paginated 1,000-row cap and require the returned `has_more` to be false before serializing success. Do not add trace pagination, another collector, configuration, or a second query path.
- Required outcome: a trace detail call either returns every matching span in its authorized cut or returns the existing bounded-result error; it never returns a successful truncated cut.
- Closure verification: extend the existing server trace-detail owner with a focused 1,001-span HTTP/gRPC proof that asserts full equality or the stable result-too-large refusal, then rerun the exact test through `mise exec -- cargo nextest run --locked -p wyrd-server --features test-support --test pg_router_smoke -E 'test(=<exact-test-name>)' --test-threads=1` under the repository Postgres wrapper.

#### FIND-BIFROST-OTEL-T03-4 — MODERATE: gRPC GetTrace treats malformed timestamps as absent bounds

- Obligations: task selected contract at lines 111-115 (HTTP and gRPC carry the same fields); revision-7 and current externally observable failure contract requiring invalid timestamps to fail with a stable error; `AGENTS.md` public structured-error rule.
- Locations: `crates/wyrd/wyrd-server/src/vala_query/grpc.rs:78-100,307-325`; HTTP comparison at `crates/wyrd/wyrd-server/src/vala_query/routes.rs:791-815`.
- Current flow: the new gRPC handler calls `proto_timestamp`, which converts `DateTime::parse_from_rfc3339(...).ok()` to `Option`. An empty string and a non-empty malformed timestamp both become `None`, so `build_get_trace_plan` cannot distinguish invalid input from an unbounded request.
- Reachable scenario and consequence: a gRPC caller sends `since = "not-a-time"`. Instead of `InvalidArgument`, the server executes the default unbounded/retention-window trace scan and may return a successful result. The equivalent HTTP query is rejected by Axum deserialization, so the two public projections disagree.
- Supporting evidence: the conversion deliberately discards the parse error and no gRPC test sends a malformed non-empty bound.
- Counterevidence: valid RFC3339 values are normalized correctly, and `build_get_trace_plan` rejects a valid parsed `since > until`. Neither path covers syntactically invalid protobuf strings.
- Ponytail recommendation: change the existing protobuf timestamp converter to return `Result<Option<DateTime<Utc>>, Status>`: empty remains `None`, malformed non-empty input becomes `invalid_argument`, and handlers propagate it. Reuse the same converter for the existing window projection where safely in scope; add no new timestamp type or error abstraction.
- Required outcome: malformed non-empty `since` or `until` is rejected before planning with the stable gRPC invalid-argument projection, while empty remains unbounded.
- Closure verification: add one focused gRPC service test for malformed `since` and one for malformed `until`, plus the existing valid-bound ordering assertion; run the exact named `wyrd-server` test through `mise exec -- cargo nextest run --locked`.
