## CONC-002 path and resolution

The path is reachable in production: `ScribeTailResolver::resolve` opens a `LiveTailBatches` producer (`oracle/follower.rs:1039-1058`); `LiveTailPartition::execute` turns it into a DataFusion stream (`follower.rs:1092-1129`); the Scribe peer polls it with `batches.next().await` while its follower admission lease and reader protection are in scope (`wyrd-server/src/oracle/peer_service.rs:340-356`). When the memtable does not already serve a staged generation, `LiveTailBatches::into_stream` enters `reader.run_batches` and advances each window in the same stream poll (`scribe/tail_rpc.rs:618-645`). That call performs `std::fs::File::open`, synchronous Parquet metadata reads, and synchronous `RecordBatchReader` decode (`scribe/staged_tail.rs:59-101`). There is no blocking boundary on this call path.

The 8,192-row window bounds decoded rows held between yields; it does not bound file-open latency, metadata IO, variable-width row bytes, or the time spent skipping windows whose predicate matches no rows. The staged path therefore can monopolize a Tokio worker for a slow local read. A stream drop cannot interrupt a synchronous poll already running; `_staged`, `_open`, `_lease`, and `_reader_protection` remain retained until that poll returns. Oracle's own `tokio::select!` deadline/cancellation (`oracle/live.rs:512-520`) runs in a different request context and may settle the query independently, so the original claim that **Oracle itself** cannot see its deadline until Scribe's read yields is too broad. The concrete gap is delayed Scribe-side ownership release and worker blocking after cancellation/disconnect/deadline. The current staged lease test (`scribe/tail_rpc.rs:1287-1340`) checks ordinary stream drop after a successful read; the live lifecycle journey exercises memtable production. Neither tests cancellation while a staged read is in progress.

**Proposed finding FOLLOW-01 (revised CONC-002): VIOLATION.** `AGENTS.md` §6 requires an explicit blocking strategy in async request paths, and spec REQ-005 requires query cancellation/drop to release live ownership. Correct the Scribe staged producer's blocking Parquet boundary while preserving one-window pull production, bounded buffering, and the existing lease/admission owners. The closure proof is a focused staged-source cancellation/deadline check that observes prompt Scribe lease release without unbounded prefetch. This is task-material because staged authority is an explicit live source in REQ-003 and ordinary cancellation is AC-004. A remedy cannot make an already running synchronous disk operation instantly cancellable; it must ensure request polling and ownership cleanup do not wait for that operation. No new product decision appears necessary.

## CONC-001 and INV-02 relationship

These reports overlap at the same fragment error-identity collapse. Schema mismatch is produced during follower resolution (`oracle/follower.rs:1477-1489`); `PhysicalPlanFollowerError::Resolution(_)` becomes `EligibleSourceLoss` in the Scribe peer (`peer_service.rs:324-335`). Staged open/decode or predicate errors are produced by `StagedTailReader` and become DataFusion stream errors; the same peer maps nearly every such error to `Unavailable` (`peer_service.rs:356-370`). Oracle can treat either as degradable before rows (`oracle/live.rs:530-540`). CONC-001 additionally names a bounded memtable refusal at resolver opening; INV-02 additionally names signed schema checks. These are one fragment-boundary correction: retain enough source failure identity across resolution and stream errors that only genuine source availability can degrade. INV-01's authenticated listing path is a separate producer and is not closed by that fragment correction.

**Result: RESOLVED.** The blocking concern is supported but narrowed to the Scribe poll and resource lifetime; the two fragment-classification findings share one correction boundary. No other findings were investigated.
