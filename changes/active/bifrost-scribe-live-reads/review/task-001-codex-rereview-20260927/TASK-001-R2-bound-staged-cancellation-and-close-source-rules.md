# Make acknowledged writes stageable and live reads query-owned

## Outcome and value

One ingest size setting governs the wire and a derived expanded-data limit. All deterministic size and schema rejection happens before the WAL acknowledgement. Staging, assembly, and publication use soft Parquet tuning targets and cannot strand acknowledged rows with a later Wyrd size refusal. Published and staged queries use async Parquet, existing finite admission, and best-effort query memory accounting. The validated R2 cancellation and source-rule findings close in the same change.

The existing concurrency limits protect a pod, but this task must also measure what one pod can deliver. Run the public-client workload benchmark on this Linux machine with the local process-cluster child in a real 4-CPU/8-GiB cgroup. It reports completed reads per second, latency, refusal, and resource evidence; it does not convert the 500–1,000 reads/second aspiration into an unmeasured promise or a CI gate.

## Decisions: one coherent write-to-read flow

### 1. Before ACK: reject what cannot safely enter

1. Keep exactly one operator-configurable ingest size, scribe.ingest_request_bytes, default 16 MiB. Both ingest HTTP body and ingest gRPC decoded-message ceilings equal this value exactly. Remove the separate 200 MiB generic ingest fallback and 64 KiB allowance. Apply aggregate buffered-byte admission only to ingest routes. Non-ingest public gRPC uses tonic's 4 MiB default; retain any separately justified internal peer-frame bound.
2. Derive one expanded-data ceiling as four times the configured wire ceiling, 64 MiB at defaults; reject multiplication overflow at config validation. **Expanded data** is the sum of Arrow value/offset/validity buffers retained for this request's canonical rows plus buffers for Scribe-managed physical columns, with shared native IPC backing counted once. It excludes the wire copy, schema descriptors, transient decoder objects, WAL workspace, and persistence scratch; the existing Scribe root admission still reserves their simultaneous live-set sum. Native and OTLP final material plans enforce this identical output metric before WAL.
3. Enforce the bound **before oversized allocation** in this order. Native: inspect borrowed IPC buffers and the managed-column projection in ScribeIngressPlanner::plan_native, refuse an above-limit projected output, then reserve the existing root plan, decode, and check actual output before WAL. OTLP protobuf and JSON: their existing wire preflights first compute generated typed-object backing and a conservative projected Arrow-plus-managed-column upper bound including attribute fan-out; each must fit the same derived ceiling, and their combined simultaneous demand is reserved through the existing Gate/Scribe root before generated decode or projection. The row projector checks running actual output before growing a batch. ScribeIngressPlanner::plan_canonical checks final output against the same ceiling before WAL. Keep the current node memory and volume refusal even when both per-request checks pass; 64 MiB is not a cap on total transient process RSS.
4. Once those checks cover all three decoders, remove the 131,072-row and redundant OTLP resources/scopes/records/attributes/value-byte count limits and their operator config fields. Retain structural parser bounds such as native IPC source/depth representability and OTLP value depth as fixed internal shape rules, not extra configurable memory ceilings. Keep timestamp and schema validity. No new per-row limit is added.
5. Validate at most **256 physical Parquet leaf columns, including Scribe-managed columns**, when a table is registered or its schema evolves, including lazy registration, before any write can be ACKed. This replaces the 256-native-field versus 64-file-leaf conflict. Invalid schema gets the existing typed schema refusal.
6. Preserve authentication, tenant authorization, aggregate ingest admission, WAL sync, memtable insertion, and ACK order. All new refusals occur before WAL commit/ACK; never roll back an acknowledged batch by a later size decision.

### 2. After ACK: shape files softly, retain data durably

1. Use parquet-rs WriterPropertiesBuilder::set_max_row_group_bytes(Some(target)) on the shared Scribe staged/assembled and Forge writer recipe. Scribe's target is 128 MiB; Forge's target defaults to 128 MiB and continues to honor the existing per-table write.parquet.row-group-size-bytes override. This is an estimated encoded-size target, not a hard logical-byte or memory limit. Keep parquet-rs defaults: 1,048,576 maximum rows per group, 1,024-row write batch, 1 MiB page target, and 20,000-row page target. A single accepted row or first batch may overshoot the target.
2. Keep the independent whole-file targets configurable through their existing owners. Scribe's staging_target_file_size_bytes defaults to approximately 512 MiB; add WYRD_BIFROST_SCRIBE_STAGING_TARGET_FILE_SIZE_BYTES as an environment override of that same server-config field, with environment taking precedence over TOML. Forge's deployment default is approximately 1 GiB, overridable by WYRD_BIFROST_FORGE_TARGET_FILE_SIZE_BYTES. **Every table**, including built-ins and dynamically registered tables, resolves to that deployment default when it has no explicit write.target-file-size-bytes property; replace Forge's current Iceberg 512 MiB fallback. A table's explicit property wins. Resolve the default at Forge planning time rather than writing it into each table's metadata, so changing the environment default also affects existing tables without an explicit override. ForgeTablePolicy resolves the effective target once from table property or deployment default; its execution, publication context, and audit all use that same value rather than independently re-reading metadata with another fallback. Parse both environment values as positive byte counts at boot and pass them through the existing Scribe geometry and Forge policy validation; do not silently clamp an inconsistent geometry. Both targets are soft: closing a completed group, partition, or final residue can yield a different file size. Do not create parallel target settings. The row-group target does not set either whole-file target.
3. Add one optional compaction_target_file_size_bytes: u64 argument to dynamic table registration, exposed through RegisterTableRequest and the Rust, Python, and TypeScript TableConfig authoring surfaces. Omitted means no explicit Iceberg property, so the table follows Forge's deployment default. Provided means validate intrinsic shape at registration: positive, representable on the platform, safe under Forge's existing oversized-ceiling arithmetic, and greater than the existing default small-file threshold and at least the effective row-group target (128 MiB for a new API-registered table). Do not pass a worker-local ForgeConfig into catalog registration. Forge validates the full current table-property and worker-config combination again when planning; a later operator change that conflicts with a stored override fails maintenance with the existing config error until corrected, without invalidating acknowledged data. Persist a valid explicit target as that table's write.target-file-size-bytes property in the initial Iceberg create transaction. This applies only to caller-owned vala.datasets registration; built-ins follow the deployment default unless their server-owned definition explicitly declares an override. Under the catalog's existing registration advisory lock, omission on an existing table leaves its stored property unchanged; a supplied value must match the existing explicit property or return a typed registration conflict. Apply the same check in the already-exists server branch before returning AlreadyExists. Do not add a separate table-size setting or an update API in this task.
4. Delete BifrostArrowLogicalSizer slicing/bisection, the 32 MiB logical-group/per-row refusal, pending row-group concatenation, the 512-group/64-leaf/file-footer policy refusals, their private recipe and width-profile metadata, and policy-only footer preflight code once no live consumer remains. Preserve standard Parquet parser errors, staged-run digest, authenticated schema checks, and corruption failures. Remove obsolete tests of deleted limits; keep behavior tests.
5. Existing WAL and live memtable authority stay queryable through staging retries. An IO or upload failure after ACK retries via the existing recovery path. Publication never advances past data that has not durably landed. No second WAL, owner index, or new retry scheduler.

### 3. Query: admit, read, account, finish

1. Retain Oracle's existing node/class/tenant slots, bounded wait queue, per-query DataFusion grant over its shared root, spill manager, and Scribe's follower CPU permit and resource lease. Do not add another concurrency setting, fixed scan-worker pool, process-isolation service, RSS victim chooser, or Scribe-owned deadline. The leader continues to own the query deadline and cancellation.
2. Use the existing production parquet-rs async reader for Oracle published and Scribe staged files. Oracle's production published scan is not the test-only DataFusion ParquetSource setup. Scribe reads one leased staged run and one selected row group at a time, with projection and signed predicate preserved; output batch target is 8,192 rows, with a pull/cancellation point after each batch, including an empty filtered batch. Do not collect a file, group, or fragment into RecordBatch vectors or prefetch later groups.
3. Before each selected row-group fetch, reserve its projected column chunks' **encoded bytes to be fetched** against the existing local query/follower grant, using checked arithmetic and the fetched-range reservation pattern Oracle already uses. Hold the reservation while the async reader owns those fetched pages; release it with the group. Charge each actual decoded output batch separately while retained, releasing that charge before pulling another batch. Do not reserve an entire group's uncompressed total: a valid highly compressed file can be read in small batches under the existing grants. Replace Scribe's hard STAGED_FETCH_LIMIT_BYTES refusal and fabricated 64 MiB decode workspace with this grant accounting. Overflow or insufficient grant fails before fetch; an over-budget decoded batch fails at the next safe batch boundary. This is best-effort accounting, not an exact resident-memory measurement.
4. The Scribe output stream owns the follower grant, staged-file lease, and async reader. Delete StagedRunWindows, its synchronous iterator, spawn_blocking/oneshot window handoff, and mechanism-only tests. Drop/cancellation starts no later batch/run and leaves no Wyrd-owned decoder task after admission release. A Tokio file operation already issued may finish with its owned file handle; it must not start more Wyrd work.
5. Resource, decode, schema, predicate, or missing-footer faults while a source is needed fail the whole query; only the approved before-first-row unavailable-source class may Degrade. The leader cancels siblings on Failed. Clients and Drift cannot accept prior frames as a successful partial result.

**Memory claim:** finite admission, DataFusion spill/refusal, and pre-read reservations are best-effort protection for a shared process. DataFusion does not account every Parquet decoder allocation, and an allocation can exceed its estimate before cancellation. This task must not claim a hard pod-survival guarantee. A literal no-pod-death guarantee needs separately memory-limited execution and is not part of the agreed best-effort remediation. The 128 MiB encoded write target and 8,192-row output batch are throughput settings, not hard read-memory caps. A highly compressed group's uncompressed total can exceed a grant yet remain readable as smaller output batches.

### 4. Direct source-rule cleanup

Move the cited function-local imports in oracle/follower.rs and oracle/exec.rs to their module import blocks; use bare imported types in oracle/tail_discovery.rs fields and signatures; make its discover # Errors paragraph name the actual TailReadError classes. Preserve runtime error mapping. This closes FIND-TASK-001-5, -6, and -8 without new abstractions.

- **Raw samples:** they match the report's success counts (512, 388, 488, 471). The 2/5-second smoke shows the same pattern.

Diagnosis (driver `RUST_LOG=debug` in the smoke run):
- Client errors: 19,224 `query peer security validation failed` and 2,737 `query admission rejected`.
- Server errors: 472 `tail ticket replay detected`.
- Nonces are fresh UUIDs, so these are not real replays. Each short query on a live-capable table consumes single-use signed tickets. Their bounded replay caches then fill:
  - Tail discovery: `MAX_REPLAY_NONCES = 256`, tickets live up to 30 s (`wyrd-server/src/oracle/tail_authority.rs`).
  - Peer tickets: `DEFAULT_REPLAY_CAPACITY = 1_024`, 30 s TTL (`wyrd-server/src/oracle/peer_authority.rs`).
- 256 per 30 s is 8.53/s, which matches the measured 8.5/s ceiling.
- `ScribeTailAuthority` reports a full cache as `replay detected` and audits it as a `replay` violation. A caller cannot tell a full cache from a real replay.
- The peer-cache share of the failures is inferred from code; the server does not log each peer `ReplayCapacity` rejection.

Changing either cache bound, or how a full cache is classified, alters tenant and signed-assignment security. That is a material stop condition for this task, so neither was changed. The measured ceiling needs a separate security decision.
