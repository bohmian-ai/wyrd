# Focused follow-up: staged cancellation and resource ownership

**Subject:** `d1ec13200d332745af2fed8069a21d5b5c39cb47..f1f1d5ebd264e8f9ac861ec79c6340da44a7a1a8` at candidate HEAD. Source was read only. **Result: RESOLVED.**

## Path traced

The approved spec revision 3 REQ-003/005, INV-005, and AC-004 require bounded live work under the query and release on cancellation. The original TASK-001 additionally calls for Scribe admission and snapshot ownership on the fragment stream, with no independent tail timeout. The R1 remediation requires blocking staged IO to stay one window per pull and release ownership after an in-flight protected read exits. Governing `AGENTS.md` §6 and `architecture/bifrost-design.md` require an explicit blocking strategy and bounded Scribe live reads.

The production path is `ScribeTailResolver::resolve` → `FetchLiveTailService::open_live_batches` → `LiveTailPartition::execute` → `LiveTailBatches::into_stream` → `StagedRunWindows::open/next` → `StagedTailReader::run_batches`. The Scribe peer acquires `ScribeFollowerLease` in `peer_service.rs:311-317`, then moves it into the output stream at `340-345`; the follower's batches are polled at `353`. That lease owns a concurrency permit and root-accounted memory quantum (`resources.rs:2152-2181,4392-4403`). The staged run's *file-protection* lease is a different value (`hot_source.rs:235-263`). `StagedRunWindows` carries only that file lease into `spawn_blocking` (`staged_tail.rs:132-205`). `run_batches` has one production caller, `StagedRunWindows::open`, and one unit-test caller, `drain` (`staged_tail.rs:446-458`). `try_acquire_follower` has one production caller, the Scribe peer. A query cancellation or client drop drops the Oracle child, its peer response and Scribe output stream; no further `LiveTailBatches` poll occurs.

## Resolution of conflicting claims

1. **Admission versus an in-flight blocking read — the concurrency PASS omits a reachable interval.** If the Scribe output is dropped while `StagedRunWindows::next` awaits a blocking task, its `_lease` is dropped immediately (`peer_service.rs:340-353`), returning both follower permit and root memory grant. The blocking closure keeps its iterator and file lease until `step()` finishes; a closed oneshot only discards the result *after* the step (`staged_tail.rs:174-205`). The unit test explicitly aborts during a held step and checks the staged lease remains (`tail_rpc.rs:1463-1525`), but does not hold or inspect Scribe follower admission. Repeated cancelled fragments can therefore leave multiple active Parquet decodes while new followers acquire the released permits. This is distinct from file-retirement safety: the staged lease protects the file but does not account CPU or decoded Arrow memory. The spec's literal release-on-stream-drop rule and its bounded-resource invariant must be read together: cancellation should stop *future* work promptly, while work that cannot stop until its current step ends must remain accounted during that step. This uses the existing query grant, without adding a Scribe-owned deadline. **Proposed finding FOLLOW-R2-01 (supports INV-R2-02):** keep the existing follower resource grant charged through any already-started blocking window, then release it; prove a held cancelled read prevents replacement admission until its step ends. The exact transfer of the move-only grant across the current owner boundary needs source-level design by the implementer/validator.

2. **One `next()` does not mean one decoded window — DUR-R1-001 is reachable.** `run_batches` wraps the Parquet reader in `map(...).filter(...)` (`staged_tail.rs:85-114`), and `StagedRunWindows::next` invokes that filtered iterator's `next()` once in a blocking task (`174-179`). Rust `filter::next` advances its inner iterator repeatedly until a predicate passes or EOF; each zero-row filtered batch is decoded and discarded within the same step. A valid predicate matching no staged rows can make one step traverse an entire large run. Cancellation closes the receiver but cannot interrupt that synchronous step, so it retains the file lease and blocking worker through all those windows. The existing cancellation test uses no predicate (`tail_rpc.rs:1330-1338,1463-1525`); the zero-row predicate unit test drains the iterator but never cancels (`staged_tail.rs:485-510`). **Proposed finding FOLLOW-R2-02 (supports DUR-R1-001):** make each blocking step advance at most one physical decoded window, including an empty filtered batch, and let the still-live async stream decide whether to request another; prove cancellation after one empty window does not decode the rest of a multi-window run. Preserve error propagation and the externally observed omission of empty result batches.

The two issues compound but have different sources. Removing the iterator's eager skip bounds each step; it does not keep the in-flight step under Scribe admission after stream drop. Retaining admission through the step does not prevent a single filtered step from scanning a whole run. Neither finding requires a new product mode, timeout, persisted state, or public contract. Both remain proposed for independent validation.
