# Bifrost write-path bottleneck analysis

**Scope:** public client → Gate → Scribe → durable ACK. This is a read-only code analysis and recommendation, not a measured write-capacity result or an approved implementation task. No write-capacity benchmark has run.

## Current path

`Bifrost::write_batch` sends one Arrow batch in one gRPC request over a reused client connection. Gate resolves the table, authorizes and durably audits the write, then calls its co-located Scribe in process. Scribe validates and admits the batch, materializes it, routes it by tenant + table + batch ID to one of 16 shard owners, writes and syncs its WAL records, commits the batch identity in PostgreSQL, inserts the rows into memory, and returns the durable ACK. Staging and publication follow later; they are not part of ACK latency.

Sources: `crates/shared/wyrd-queue/src/sealed_sender.rs:72`, `crates/vala/vala-bifrost-redux/src/gate/mod.rs:944`, `crates/vala/vala-bifrost-redux/src/scribe/ingress.rs:385`, `crates/vala/vala-bifrost-redux/src/scribe/routing.rs:11`, `crates/vala/vala-bifrost-redux/src/scribe/shards.rs:3107`.

## Findings and decisions

| Finding | Evidence and practical effect | Recommendation |
| --- | --- | --- |
| **Repeated WAL sync in a group** | A shard groups up to 64 requests, but `append_and_sync_batch_commits` appends a COMMIT and calls `sync_group(&state.touched)` for each new batch. The touched set grows, so previously synced segments are submitted again; `WalWriter::sync_segments` does not skip segments synced by prior calls. This is code-proven repeated IO, though its throughput cost has not been measured. `scribe/shards.rs:3610–3700`; `scribe/wal.rs:2854–2864`. | Append the group's COMMIT records, then invoke `sync_group` once on the distinct touched segments before any ACK. Delete the per-batch sync call and repeated cumulative resync. Keep each batch's PostgreSQL identity fence and ACK only after that batch's fence and memory insertion succeed. |
| **Client and server batch ceilings differ** | The ordinary client defaults to a 4 MiB IPC message ceiling, while Gate accepts 16 MiB wire requests by default. A large logical batch can require more requests and therefore more audit and durable-commit work. `crates/shared/wyrd-queue/src/config.rs:80–94`; `gate/limits.rs:18`. This has not been measured as a throughput limit. | Set the Bifrost client's default message ceiling to the server's 16 MiB default, while preserving caller configuration. Leave the generic queue default alone for unrelated users. Do not exceed the server's configured wire ceiling. |
| **One permission audit per request** | Gate commits an audit event before Scribe work. The append locks one `audit_chain_head` row per tenant until commit, so same-tenant permission decisions serialize. `gate/mod.rs:454–485`; `crates/wyrd/wyrd-server/src/bifrost/gate_audit.rs:9–77`; `crates/vala/vala-sql/src/queries/audit_staging.rs:22–119`. Its measured cost is unknown. | Keep this required authorization audit. Use the existing buffered `insert` producer for small events or send appropriately sized `write_batch` calls. Measure audit time before proposing a change to the permission or audit contract. |
| **One PostgreSQL batch-identity fence per batch** | The COMMIT loop opens and commits a tenant-scoped transaction for each batch. The record enforces durable batch-ID deduplication; groups may contain multiple tenants, so one transaction for an entire group is not a drop-in replacement. `scribe/shards.rs:3724–3790`; `crates/vala/vala-sql/src/queries/scribe_batch_commits.rs:253–311`. Its measured cost is unknown. | Keep the fence. Measure it after removing repeated WAL syncs; change it only with a separate recovery and deduplication design if it proves dominant. |
| **Finite ingest admission** | The server defaults to a 16 MiB wire ceiling and a derived 64 MiB expanded-data ceiling, plus 4,096 global in-flight items, 16 shard owners, and 256 commands per shard mailbox. Batch IDs spread even one hot table across all 16 shards. `gate/limits.rs:18,25`; `scribe/admission.rs:20`; `scribe/shards.rs:402`; `scribe/routing.rs:11–112`. | Keep these resource bounds. They refuse work when memory or queues are genuinely full; the code does not establish a fixed writes-per-second ceiling. |

`write_batch` deliberately sends one caller-built batch per request. The public `insert`/`insert_into` producer already batches small events, sealing by row, byte, or time target; do not add a second hidden batching mechanism to `write_batch`. `crates/shared/wyrd-queue/src/sealed_sender.rs:1–17`; `crates/shared/wyrd-queue/src/config.rs:80–94`.

## Implementation proof

1. **WAL correctness:** test a group containing multiple batches and tenants, a duplicate batch ID, and a failing PostgreSQL fence. Crash after the group COMMIT sync but before all fences, restart, retry the same batch IDs, and prove that every acknowledged batch appears exactly once and no acknowledged rows are lost. Count WAL sync calls: one group sync invocation, syncing each distinct touched segment once, rather than one invocation per batch. Keep the existing pre-ACK durability order.
2. **Client envelope:** test that the Bifrost default accepts an IPC request above the old 4 MiB ceiling and within the 16 MiB server limit, and rejects one above the configured server limit before ACK. Verify that other generic queue users retain their current default.
3. **Latency attribution:** reuse Gate request, Scribe ACK, WAL, and lane telemetry; add timings for Gate authorization/audit, Scribe catalog and materialization, shard wait, WAL slice sync, group COMMIT sync, PostgreSQL fence, and memory insertion. The current queue-wait metric includes preprocessing, so split or relabel it before interpreting it as shard wait. Use bounded metric labels and put request identities in traces only.
4. **Capacity:** reuse `BifrostProcessCluster::start_benchmark` with its real 4 CPU/8 GiB child, public `Bifrost::write_batch`, existing 16,384-row/64-byte-payload fixture, cgroup evidence, and production metric snapshotting. Measure sustained client-call-to-durable-ACK batches/s, rows/s, payload MiB/s, p95/p99, refusals, CPU, memory, WAL syncs/batch, audit time, and fence time. Flush and read back every acknowledged batch. Run the buffered small-event API separately. Keep PostgreSQL and the driver outside the child cgroup, as in the existing query benchmark.

The current query-capacity benchmark only *seeds* data; it reports no sustained write rate. Wyrd has no approved numeric write-throughput target, so code inspection or a read benchmark cannot substantiate a high-throughput write claim. Record the measured capacity and choose a product acceptance target before claiming a write-throughput pass.
