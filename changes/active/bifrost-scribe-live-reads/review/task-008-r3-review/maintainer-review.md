## Proposed finding

### MNT-R3-1 — current live-tail architecture still promises the deleted caps

- **Classification:** INCORRECT documentation / stale contract after an approved behavior change.
- **Location:** `architecture/bifrost-design.md:311–312`, Live tail, recovery, and shutdown: “Projection, signed predicate, physical partition, retained bytes, batch count, deadline, and cancellation are enforced.”
- **Governing requirement:** the current maintainer decision explicitly deletes all live-read batch and byte caps; AGENTS.md §1/§2 make this architecture the active authority, and maintainer-style Documentation requires explanatory prose to describe the operation/invariants accurately. User review scope explicitly includes leftover references to the deleted cap.
- **Evidence and reachability:** this paragraph describes the same authenticated live snapshot opened by `ScribeTailResolver::resolve` → `FetchLiveTailService::open_live_batches` → `ScribeShardRuntime::snapshot` → `Memtable::collect_readable_batches`. The request/cut no longer carries count/byte limits, the collector is now `Vec<ReadableBatch>`, and neither range collector nor merged shard snapshot performs either cap check. `ScribeProviderCut::is_valid` and the v6 signature cover only writer epoch and canonical partition endpoints. Query execution memory governance is a different owner, not the former snapshot cap.
- **Concrete maintenance consequence:** the repository's authoritative live-tail contract still tells a maintainer that two deleted constraints are enforced, despite the supplied diagnosis saying their intentional removal fixes benchmark 503 refusals. Following that sentence would reproduce the removed cap or send a future investigation looking for nonexistent signed bounds. This is a current, task-related contradiction, not an argument against cap deletion.
- **Smallest correction:** edit the live-tail architecture paragraph to describe scope/projection/predicate/epoch/deadline/cancellation validation accurately, explicitly state that the shallow snapshot has no batch/byte cap, and point to the existing query execution memory-pool governance for retained execution allocations. Preserve source ownership, tenant proof, admission, leases, terminal counts and the approved no-cap behavior; no code, new mechanism, test harness or dependency is needed.
- **Focused closure proof:** inspect this paragraph against `ScribeProviderCut`, the proto reservations, the snapshot collector and query memory owner; search current architecture/docs/source for explicit claims that the live snapshot enforces the deleted count/byte limits. Historical change/review evidence and proto reservations are intentional. No runtime test is needed solely for this prose correction; any docs verification remains deferred under the current static-only restriction.
