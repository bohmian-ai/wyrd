## Durable settlement versus graceful transport

The system report's ownership trace is sound. `ReplayBody` (`analytical_transport.rs:240–269,418–432`) retains an `AnalyticalConnectionLease` for the coordinator request lifetime. On connection/body drop, `analytical.rs:3296–3311` calls the synchronous ingress close operation. `close_connection:2017–2030` decrements under the graph mutex and, at zero, transitions the graph to draining with `Cancelled`. The ingress-owned driver performs settlement. `AnalyticalStageIngress::shutdown:2240–2278` closes admission, offers live graph settlements, closes/joins that driver and checks retained ownership before supervisor shutdown. The supervisor retains/joins lifecycle tasks and preserves failed cleanup.

Therefore the new reset does not introduce an alternate cleanup owner, duplicate release or establish acknowledged-data loss. It deliberately feeds the existing loss/cancellation path **earlier**. That path settles a graph as cancelled when its final coordinator connection drops; it does not supply graceful completion of the accepted exchange. Reliable cleanup after a new reset and preservation of the original connection semantics are separate obligations. The PASS reports prove the former and do not refute the latter. Their ordinary peer-loss/caller-cancellation journey exercises failure cleanup, not an active Oracle-only exchange finishing during ordinary transport drain.

The other side is also bounded: the behavior/invariant reports must not be interpreted as requiring an Oracle-only blocked connection to run forever or requiring durable success despite process shutdown. The existing process deadline/abort and later role shutdown remain valid.

## Source-local proposal FUP-R4-001

**Classification:** VIOLATION / REGRESSION. **Discovery equivalents:** B-R4-1, INVARIANT-R4-001. **Violation:** the explicit R4 preservation of Oracle-only private peer/Analytical lifecycle semantics. **Location:** `crates/wyrd/wyrd-server/src/app/server.rs:678`; producer of the broadened loss is the unconditional runner selection, not Analytical lease cleanup.

**Reachable consequence:** during ordinary shutdown of an Oracle-only node, an already admitted private exchange/forward-query response that previously could complete during tonic's graceful transport drain instead receives connection failure at transport-token cancellation. An active coordinator request may drop its lease and enter cancelled settlement before its prior graceful completion. No tenant leak, failed durable cleanup or mandatory-success promise is alleged.

**Smallest safe correction:** reuse the existing selected Scribe/fragment capability at the private listener owner to select cancellation-aware accepted IO only for Scribe-containing fragment-serving listeners. Keep Oracle-only listeners on the existing `serve_grpc_with_listener`. Mixed Oracle/Scribe listeners remain permitted to terminate their shared stopping fragment connections; preserve their existing request/authentication and durable settlement owners. This reuses two existing runners and role composition, needs no protocol/timeout/dependency/new resource owner, and places the correction where unintended loss is produced. Changing Analytical cleanup, delaying all shutdown, replacing pull backpressure, or restoring a cap would not repair this scope violation.

**Focused proof:** static source must show separate routing for an Oracle-only private listener versus a Scribe-containing listener. Once execution is authorized, reuse the real peer harness to exercise an already accepted Oracle-only operation that can finish within ordinary transport drain and require its existing completion/lifecycle behavior. Retain the blocked-Scribe undrained-client stop/release journey and public/mTLS/Analytical loss-settlement checks. Do not replace the existing process deadline or claim completion of an indefinitely blocked Oracle exchange.

This is a bounded correction to honor an existing explicit constraint, not a new concurrency or availability decision. Independent structured validation should deduplicate this proposal with the two discovery IDs. **Conflict status: RESOLVED.**
