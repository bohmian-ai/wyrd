### REPO-002 — Expiry can complete before capture registration and leave retained resources indefinitely

- **Classification:** INCORRECT; resource-lifecycle consequence.
- **Obligation:** `architecture/bifrost-design.md` Durability and visibility states captures expire at the query deadline when release is absent; its Resource and failure invariants require bounded lifetimes and structured release. `architecture/operations/reliability-and-recovery.md` Oracle failure boundaries require cancellation to release query resources. AGENTS §§6/9–12 require the same lifecycle behavior.
- **Changed location:** `crates/vala/vala-bifrost-redux/src/scribe/tail_rpc.rs:814`–`:829`, `FetchLiveTailService::retain`.
- **Producer-to-consumer path:** `capture_active_streams` derives `deadline` before `capture`; `capture` invokes synchronous `LiveCapture::take`, whose lock acquisition and whole-table selection can consume the remaining time. `retain` then spawns the deadline task **before** `CaptureTable::insert`. On the multi-threaded production runtime the timer may already be due, acquire the table shard, remove no entry, log expiry and finish. Registration subsequently inserts the capture with an AbortHandle for an already-finished task. Neither `CaptureTable::insert` nor `get` repairs this state. `ScribeImpl::tail_captures` keeps it for the Scribe lifetime.
- **Sibling writers/consumers inspected:** Production insertion is only `retain`, called by `capture_active_streams`; the extra retain callers are unit helpers/tests. Removal is only the timer and `release_capture`; `open_capture` only reads/clones it. Local and tonic discovery both call capture_active_streams; cancelled/failed remote listings are intentionally allowed to rely on deadline expiry, because the requester may never receive the capture id. Scribe shares the table among all tail-service instances and does not sweep it elsewhere.
- **Observable consequence:** If the response is lost or the query expires/cancels before receiving the capture id, explicit release cannot name it. The one timer already missed it, so Arrow batches and staged-file leases remain retained after deadline; cleanup can remain blocked until Scribe/process teardown. This breaks the bounded-retention guarantee on an ordinary near-deadline query without any malicious peer.
- **Smallest correction boundary:** Fix registration/expiry ordering once in the existing `FetchLiveTailService`/`CaptureTable` owner so a remover cannot finish before its capture becomes visible, including when the supplied deadline has already elapsed by registration. Keep explicit query/binding release checks and existing staged-source lease sharing; do not add polling, a second sweeper, or consumer-by-consumer cleanup guards. Refusing an already elapsed registration is valid but does not alone close a timer/register race across the check.
- **Focused closure proof:** One deterministic local race test with the existing capture/table ownership must arrange expiry at registration and prove no capture/lease remains after the deadline even without explicit release. Keep the existing unreleased-expiry and staged-retention tests green. No new harness/dependency or whole journey suite is needed for this source-local ordering regression.
