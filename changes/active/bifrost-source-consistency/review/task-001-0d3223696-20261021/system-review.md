## Material proposed findings

### SYSTEM-001 — Expiry can run before capture registration and never remove the capture

- Classification: **INCORRECT**; priority: P2.
- Obligation: spec INV-006 and AC-002; task scenario 2 requires deadline expiry / abandoned acquisition to release retained resources. Bifrost design states that retained captures expire at the query deadline.
- Changed location: `crates/vala/vala-bifrost-redux/src/scribe/tail_rpc.rs:814–829`, `FetchLiveTailService::retain`.
- Producer-to-consumer evidence: `capture_active_streams` checks `expires_at` only before `capture()` and synchronous `partition_bytes` (`:698–703`), then calls `retain` (`:735`). `capture` can synchronously acquire memtable/registry locks, copy source references, and return without checking the elapsed deadline (`:777–785`). Thus short-deadline work can reach `retain` with the deadline already due. `retain` spawns the expiry task at `:814`; that task sleeps until the deadline, removes the ID once (`:816`), then exits. Only afterwards does the caller insert the capture into `CaptureTable` (`:821–829`). On the production multi-thread runtime, the spawned task may execute on another worker before insertion. An ordinary scheduling delay between spawn and insert has the same effect even if the deadline was initially future.
- Reachable failure sequence: capture finishes near/after its deadline → expiry task runs and observes no map entry → task exits → capture is inserted → Oracle's listing budget expires or the response is abandoned, so Oracle has no ID to explicitly release. There is no periodic sweep or subsequent expiry attempt: `CaptureTable::get/remove` do not inspect expiry, and `RetainedCapture` stores only the completed timer's abort handle. `release_capture` can remove it only if a caller still has the exact ID. Both local discovery and private gRPC listing reach this one producer; all subsequent follower opens and explicit releases consume the shared table.
- Observable consequence: a timed-out query can retain Arrow buffers and staged-file leases until explicit release or process destruction, violating the bounded lifetime. Publication cleanup waits for those leases in `ClaimPublisher::retire_members:627` / `ScribeHotSourceRegistry::drain_leases`, so the leak can hold stage/claim capacity and eventually backpressure otherwise unrelated ingestion. It does not justify deleting leased files or failing the whole process.
- Smallest safe correction: fix registration/expiry ordering in the existing `FetchLiveTailService` / `CaptureTable` owner so an expiry cannot complete before the entry it must retire is installed, including a deadline reached during registration. Refuse already-expired acquisition without retaining sources. Keep shared-table ownership and the existing read-held lease behavior; do not add a second sweeper or downstream guard to every caller.
- Focused closure proof: extend the nearby capture-expiry unit proof to deterministically exercise expiry becoming due before registration completes and assert zero retained entries plus released staged leases without an explicit release. Preserve the existing proof that an already opened read keeps its lease until that read drops. The current `an_unreleased_capture_expires_at_its_deadline` uses a future one-second timer on a paused current-thread runtime; it cannot expose this interleaving.

### SYSTEM-002 — Failed acquisition waits beyond its deadline for a stalled release RPC

- Classification: **INCORRECT**; priority: P2.
- Obligation: INV-006 / AC-002 and task scenario 2's bounded failed acquisition; the Bifrost design requires all acquisition to stay within the leader's original deadline, with failed releases covered by capture expiry.
- Changed locations: `crates/wyrd/wyrd-server/src/oracle/tail_discovery.rs:280`, `:354–362`, `:399–413`; transport call at `crates/vala/vala-bifrost-redux/src/scribe/tail_rpc.rs:139–155`. The sibling completion/cancellation caller is `oracle/live.rs::LiveCaptures::drop`.
- Producer-to-consumer evidence: `discover` wraps only the listing `join_all` in `timeout(remaining, listings)` (`:354–356`). After that timer has completed, it calls `admit(...).await` (`:362`). If one listing failed or reported a stale epoch while another Scribe retained a capture, `admit` awaits `self.release(...)` (`:280`). `release` awaits a new `join_all` of ReleaseCapture RPCs with no timeout or cancellation (`:399–413`). `TonicTailReadTransport::release_capture` adds no gRPC timeout. `cached_channels` uses `BifrostPeerTls::endpoint`; the underlying `mutually_authenticated_tls_endpoint` constructs TLS but sets no endpoint request timeout. `Oracle::list_live_routes` checks elapsed time only after discovery returns; `build_physical_root`, `run_sql_query`, Gate and the local-forwarder branch do not wrap this whole discovery future in an outer deadline. The HTTP edge timer has already handed off.
- Reachable failure sequence: Scribe A returns a non-empty capture; Scribe B returns a listing error; A then accepts/queues the release RPC but never responds (delayed handler, partition with an established connection, or interrupted dependency/process). The leader waits forever in cleanup even after both the original query deadline and A's capture expiry. This is the new cleanup RPC, not a pre-existing listing timeout. On ordinary plan drop the same release implementation runs detached and can leave a cleanup task/channel alive beyond that deadline as well.
- Observable consequence: a failed public or internal query can remain pending past its advertised deadline; source expiry does not wake the Oracle cleanup future. Repeated failures accumulate pending request/cleanup tasks and channels. The scope is the dependent acquisition and cleanup task; no approved authority permits crashing the server or taking sibling roles down to settle it.
- Smallest safe correction: bound the existing release workflow by the capture/query's original deadline on both failed acquisition and plan-drop paths. When that budget expires, stop waiting, log the failed best-effort release and rely on the already-existing Scribe expiry mechanism. Preserve release of successful peers and the original listing failure classification; do not introduce a new retry loop, new independent tail timeout, or fresh capture.
- Focused closure proof: use the existing peer-discovery fixture with one successful capture, another failed listing, and a ReleaseCapture handler that remains pending. Assert discovery/query settles no later than its original deadline and retained capture resources expire; also assert a normally responsive release still promptly frees the capture. Existing outage injection returns before retaining any peer capture, and existing stalled-listing proof times out inside the listing timer; neither exercises this new cleanup boundary.
