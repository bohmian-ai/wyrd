## Proposed material findings

### BEH-001 — Retained captures can outlive their accounted Arrow memory

- Classification: **INCORRECT**, INV-006 / AC-002 and existing governed-memory architecture.
- Changed location: `crates/vala/vala-bifrost-redux/src/scribe/memtable.rs:1690-1753` (`LiveCapture::take`) and `src/scribe/tail_rpc.rs:805-829` (`retain`).
- Producer-to-consumer evidence: `LiveCapture::take` copies `ReadableSource` references for the whole tenant table; `ReadableSource::capture` at `memtable.rs:1886-1901` stores Arrow batches without a reservation or retained accounting owner. `RetainedCapture` has only query, binding, capture and expiry. Its insertion performs no resource check. Discovery runs in `Oracle::build_physical_root` before `classify_one_build` derives the class and before admission. The Scribe source service also has no resource capability field. `ScribeShardOwner::release_committed_generation_memory` at `shards.rs:2376-2417` returns `token.arrow_bytes` through `ScribeOwnership::release_immutable` before dropping the retired memtable entry, irrespective of outstanding captured references. The capture therefore keeps the actual allocation alive after its original charge is returned.
- Reachable path: an ordinary multi-table query captures table A and waits for table B's unsettled publication, or a classified query queues for admission. A's writable/immutable rows then stage and retire while its retained capture remains. Ingestion can admit replacement bytes under the released root budget although the captured A buffers remain resident until query release/deadline. Repeated captures across generation changes retain multiple such generations; bounded deadline does not restore byte accounting. This path precedes any Scribe follower envelope, so execution-side memory cannot cover it.
- Sibling consumers/writers checked: direct/local and gRPC discovery share `capture_active_streams`; runtime tail services share Scribe's table; rollover and staging/replay retirement use the same Scribe ownership ledger; `open_capture` and `ScribeTailResolver::live_leaf` merely project captured references and do not acquire coverage for the retained whole-table allocation. The existing `MemtableSource` only sizes/distributes input batches.
- Observable consequence: governed-memory telemetry and available capacity understate actual retained allocations; reads can bypass the shared memory bound and make the shared server exceed its intended resident budget while ingestion continues. The count/lease cleanup tests do not prove memory ownership.
- Smallest correction boundary: keep root-backed ownership with the retained memory at the Scribe capture/retirement boundary, using existing `ScribeResources`/`ScribeMemoryLease` and `ScribeOwnership` accounting rather than a new governor, limit, public option or downstream execution guard. A capture must either retain an accounted share/lease until its final relevant owner drops or fail with existing resource vocabulary before retention. Preserve source consistency and avoid releasing a source's last charge while its Arrow remains pinned. The precise private representation is implementation-owned.
- Focused closure proof: hold a real production capture across staging/retirement and admission wait, observe that the shared root still accounts the retained bytes and refuses growth past its existing cap, then release/cancel/expire and prove the charge returns once. Include two overlapping captures so releasing one cannot prematurely uncharge the other. Reuse existing resource-governor test fixtures; no new stress harness or full suite is needed for this gap.

### BEH-002 — Expiry can complete before a capture is inserted

- Classification: **INCORRECT**, INV-006 / AC-002.
- Exact changed location: `crates/vala/vala-bifrost-redux/src/scribe/tail_rpc.rs:812-829`.
- Evidence: `retain` spawns the expiry task at line 814; it sleeps to the deadline, removes the capture ID once and completes. Only afterwards does the retaining task call `captures.insert` at line 821. Tokio's multi-thread runtime can execute the spawned task before the spawning task inserts. `capture_active_streams` checks remaining wall time before synchronous whole-table capture and partition sizing, with no second deadline check before `retain`, so arriving here at/after deadline is reachable, not a test-only state.
- Reachable path: a real capture is delayed by memtable/registry contention or source sizing until its query deadline; on another worker the already-due expiry task removes an absent ID and completes. The original task then inserts that ID and returns a response to a query/RPC that timed out or was cancelled. Oracle never receives the ID to release. The table now retains Arrow references/staged leases with no future expiry task. Even a future open does not rescue cleanup: `open_capture` checks the table/binding/query, not an independently stored deadline.
- Sibling paths checked: all production captures use this one `retain`; release is best effort and expiry is the documented backstop for lost RPC responses, failed releases and dropped queries. The current paused-clock expiry test yields after insertion and cannot exercise removal before insertion.
- Observable consequence: an abandoned deadline-bound acquisition can retain resources indefinitely and prevent staged-file cleanup indefinitely, violating the promised bounded lifetime.
- Smallest correction boundary: make publication into `CaptureTable` and arming/removal ordering race-safe inside the existing retention owner. The expiry action must not be able to finish before the entry it owns is published, and an already-expired acquisition must not leave an unexpired entry. Do not add periodic sweeping or another capture registry; fix the one publication/expiry lifecycle.
- Focused closure proof: deterministic multithread/interleaving proof where the deadline passes before retention publication and expiry gets its turn first; after the abandoned acquisition settles, capture count and staged leases must be zero. Keep the normal explicit-release and expiry proofs.
