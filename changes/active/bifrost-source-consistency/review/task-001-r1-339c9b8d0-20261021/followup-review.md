## Reachable producer-to-failure proof

1. Ordinary freeze inserts a frozen entry into the memtable and returns a clone. `prepare_and_queue_generation` moves the existing charge from Active to Immutable, then constructs a production `ImmutableGeneration`. Cohort rotation reaches the same constructor. The returned frozen clone drops, leaving the memtable as the only charge-slot holder when there are no captures.
2. The constructor's `rows` still reference the same physical Arrow allocations, but no charge slot travels with them. This is not decoding or replacement of those allocations. `submit_front` shares the payload with a persistence job; `process_job` also clones its Arc.
3. `persist_once` stages a frozen snapshot through the CPU lane and marks the generation durable. Its new empty slot provides no original accounting authority. On a successful normal completion, the shard removes its pending payload and records only byte/WAL bookkeeping in `RetainedGeneration`. The worker still retains its Arc while awaiting the visibility acknowledgment.
4. After sending that acknowledgment, the shard can process a queued age/retirement command before the worker resumes. `retire_committed` removes the original memtable entry, transferring its ledger bytes into the original charge slot and immediately dropping that slot if no query holder remains. The worker payload still physically owns the rows. This schedule requires no injected failure, unusual configuration, or public API.
5. Replay gives an even stronger production path without relying on the next command's timing: `handle_persistence_completion` invokes `complete_owned_replay_generation` while local `front.generation` is alive. `complete_replay_generation` calls `release_committed_generation_memory` before using that front again to record stream/key/LSN and advance the next member. The worker also remains parked awaiting acknowledgment. Therefore physical persistence holders definitely coexist with the returned root charge. Startup readiness does not make the shared process budget fictitious; another role or shard can reserve from that root.
6. If a query capture remains, it temporarily masks the missing edge. Once that capture/read is released, its charge can return while the worker still owns its uncharged rows. Correct query propagation alone therefore cannot satisfy the final-holder promise.

Observable consequence: the Scribe/Bifrost root advertises these bytes as reusable while original Arrow allocations remain resident in a production worker/payload. Admission can reuse that capacity. This report asserts a budget/lifetime violation, not row loss, unbounded retention, or a measured OOM.
