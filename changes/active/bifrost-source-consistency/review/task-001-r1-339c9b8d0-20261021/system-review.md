## Material proposed finding

### SYSTEM-R1-001 — Existing committed publication recovery fails when no revision row exists

- Classification: **REGRESSION**, P2. This is a newly identified cumulative-range finding, not a reopening of FIND-1 through FIND-5.
- Violated boundary: REQ-003's recovery rule and preserved existing publication replay/recovery; INV-004's replay-exact revision semantics. The spec defines a node absent from the revision map as revision 0 and prohibits deleting retained analytical data. The existing merged-main durable state is not a mixed-version private protocol.
- Changed location: `crates/vala/vala-bifrost-redux/src/scribe/file_list_writer.rs:553–563`, with migration producer `crates/vala/vala-sql/migrations/20261021000000_bifrost_publication_revision.sql:22–57`.
- Producer: the new migration creates an empty revision table and installs an AFTER INSERT trigger. It does not populate revisions for rows already present in `vala.file_list`. Such rows are normal data created by the recorded base. A crash after an old publication's SQL commit and before cleanup can also leave its durable publication manifest, which the existing restart protocol intentionally replays.
- Reachable recovery path: migrate that database and restart with the retained volume → `ScribeImpl::replay_wal_async` calls `recover_staged_publications` → `ScribeStageMover::recover_publication` identifies the artifact set as `Committed`, verifies its remote bytes, then still calls `reconciler.publish(&publication.rows)` (`persistence.rs:1678–1716`) → `insert_artifact_set_fenced` finds every exact existing row and inserts zero rows → ON CONFLICT fires no insert trigger → the new `fetch_one` requires a revision row that does not exist and returns NoRows. The reconciler reports an unknown outcome; recovery returns the error. Every restart repeats this if the same node/table has no later fresh publication. Readiness cannot open to create that fresh publication as a remedy.
- Observable consequence: previously recoverable, already committed data leaves the Scribe role unready indefinitely after this migration; ingestion and its live-data capability are unavailable until manual database intervention. Boot correctly contains this to the Scribe role and preserves durable files, but that containment does not make a valid recovery failure acceptable. The same SQL owner is used by ordinary claim publication, uncertain-commit retry, and durable manifest recovery, so the correction belongs there rather than in boot or a second recovery branch.
- Smallest testable correction: preserve the already-defined revision-0 initial state for an exact replay whose publication predates revision tracking. At the existing fenced artifact-set SQL owner, allow the validated zero-insert exact replay to return revision 0 when its node/table has no revision row; continue returning an existing revision unchanged, and preserve the required revision row for a fresh insert. Do not invent a publication, delete/reinsert file-list rows, relax replay identity validation, bypass the actor fence, or skip manifest recovery. This needs no public protocol, new durable authority, or availability guarantee.
- Focused proof: use the existing Postgres-backed publication/recovery fixture with an exact committed artifact set created before revision tracking (file-list rows and a retained publication manifest, no revision row). Apply the new migration / equivalent initial state and run the existing recovery owner. It must finish exact replay and cleanup, preserve rows once, leave the absent revision logically 0, and allow the next new publication to create revision 1. Retain ordinary post-migration exact replay, conflicting replay, rollback, and tenant assertions. Current `file_list_publications_advance_their_node_revision` inserts after the trigger exists, so it cannot exercise this state.
