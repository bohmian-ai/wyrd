## Retained finding FIND-TASK-001-1

**Disposition:** CONFIRMED from discovery `DOMAIN-1`. **Classification:** INCORRECT. **Requirement:** REQ-002, and `architecture/bifrost-design.md` mirror lifetime rule at lines 935–936.

**Location:** `crates/vala/vala-bifrost-redux/src/scribe/shards.rs:3705` and `:4318`; `scribe/receipt_cleaner.rs:185`; `scribe/committed_batches.rs:60`; `scribe/ingress.rs:778`.

**Starting conditions and trigger:** A accepts and publishes a batch. B receives the same tenant/principal/table/version/batch retry, and PostgreSQL resolves its attempt as `AlreadyCommitted`. A later deletes the aged, safely handed-off canonical receipt while B stays alive. Resend the batch to B.

**Expected:** B's mirror cannot acknowledge the removed authority. The retry must return to durable arbitration, where the now-unprotected identity may be accepted anew.

**Actual and independent proof:** `append_and_sync_batch_commits` marks `AlreadyCommitted` in `spent_batch_ids`, suppressing rows. `record_committed`, called on the successful group path at `shards.rs:3667`, excludes `accepted_under` and `conflicted` but not that spent duplicate, and records B's mirror entry. The entry has neither ownership coordinates nor expiry; `contains` simply compares stored logical identity. `receipt_streams` and cleaner discovery filter by their own node, and A's deletion only calls A's local `committed.forget`. B's periodic empty/own-node sweeps cannot remove this entry. `committed_duplicate_rows` then matches it, and ingress returns `first_commit=false` without a new shard/SQL attempt. FIFO eviction or restart can end this behavior, but no expiry does; a quiet B retains it indefinitely. The existing two-pod losing-duplicate test demonstrates supported setup but restarts B directly after deletion, so it does not falsify this failure.

**Consequence:** Retry protection extends beyond actual receipt deletion on one live pod, contradicting the explicit finite-authority contract and yielding obsolete duplicate acknowledgements. This is a supported multi-pod path, not hypothetical malformed input.

**Smallest testable correction:** Correct the existing mirror population/lifetime owner so an acceptance whose deletion that mirror cannot observe is not indefinitely authoritative there; reuse shared Scribe arbitration for such retries. Preserve recent matching/conflicting retry semantics and keep new cleanup waits/SQL off ordinary ingress. Do not add a general invalidation ledger or prescribe one implementation signature. Extend a focused two-pod journey to keep B alive after A's own cleaner deletes the receipt, resend to B and assert the actual receipt/new-row result. Internal mirror assertions may support this but cannot replace the real cross-pod journey.

## Retained finding FIND-TASK-001-2

**Disposition:** CONFIRMED from discovery `DOMAIN-2`. **Classification:** INCORRECT. **Requirements:** REQ-008 initial cleanup before fresh admission, REQ-009 continued reads/recovery and no process-readiness coupling; `architecture/bifrost-design.md:1124–1141`.

**Location:** `crates/vala/vala-bifrost-redux/src/scribe/mod.rs:2715`; `scribe/receipt_cleaner.rs:152`; `crates/wyrd/wyrd-server/src/boot/mod.rs:762`.

**Starting conditions and trigger:** A mixed server restarts with independently published accepted rows and an old eligible receipt. A concurrent tenant transaction holds a row lock on that safe receipt, so cleaner DELETE waits while WAL/staged-data recovery can otherwise finish.

**Expected:** Recovery/serving readiness can complete; fresh writes stay retryable-busy while cleanup remains unverified. Only initial write admission depends on the initial cleanup sweep.

**Actual and independent proof:** Cleaner starts during construction (`scribe/mod.rs:1239`). Its sweep takes a whole-sweep mutex then awaits discovery, DELETE and commit. After successful recovery, `replay_wal_async` awaits this same `sweep_and_report` before setting `recovery_ready` or returning. Production boot awaits replay synchronously before activating the role/continuing boot. DELETE has no skip-locked, timeout or cancellation branch; pool defaults bound connection acquisition, not statement/row-lock execution. Thus the recovery call either enters the blocked sweep or queues behind the background sweep's mutex. The catch-and-ignore handles returned errors only; it cannot handle a pending sweep. A cleanup-only row lock therefore holds recovered boot/readiness pending. Existing SQL permission-failure coverage returns promptly and does not cover this path.

**Consequence:** Maintenance contention makes the affected mixed server unavailable despite recovered custody, instead of applying the approved local new-write refusal. No data-loss claim or cluster-wide outage is inferred.

**Smallest testable correction:** Decouple recovered readiness from initial cleanup completion in the existing Scribe/cleaner lifecycle, retaining unverified admission until a current sweep completes. Do not relax actual WAL recovery authority or initial sweep admission safety. A focused real-Postgres restart/startup regression must hold cleanup DELETE pending, observe serving retained reads plus fresh-write busy, release the lock and observe automatic fresh-write admission. This tests the specific required availability boundary rather than merely imposing a preferred timeout.
