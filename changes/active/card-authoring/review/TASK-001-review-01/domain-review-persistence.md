## UID wording assessment for independent validation

REQ-005 says that after publication the graph references the exact registered version, “including the resolved UID where provided by the existing upload result”; Scenario 3 likewise describes substituting the returned exact reference. `upload_artifact` returns a UID-bearing root (`handle.rs:322`), but `declare_authored` discards that return (`handle.rs:358–365`) and sends the prevalidated identity-only external reference. `Artifact::registered` also discards the supplied UID. New architecture prose at `wyrd-design.md:2330–2331` explicitly describes identity-only references.

That is a literal difference from the approved specification's staged-reference wording. It is not a demonstrated persistence-integrity failure: existing loader validation rejects authored UIDs (`wyrd-loader/src/validate.rs:74–79`); doctrine 19 and the established path-resolution contract assign UID pinning to the server before hashing/persistence. The server's existing batch resolution uses tenant/kind/name/version (`wyrd-sql/src/queries/cards/declare.rs:480–520`), and binding overwrites external reference UIDs with that resolved UID (`components/cards/resolve.rs:834–845`). Sending back the upload UID would not currently alter that lookup. The writer rechecks exact preflight UIDs under transaction locks before durable writes (`service.rs:1170–1191`). The parity journey verifies the same persisted exact identities and hashes.

I therefore do not propose a material persistence finding or a new reference contract solely for this spelling difference. The validator should explicitly reconcile the approved wording with the existing authoring/server authority; the implementation's recorded decision and new architecture prose alone cannot approve a changed requirement. This conclusion does not certify that the outgoing graph carries the upload result's UID: it does not.
