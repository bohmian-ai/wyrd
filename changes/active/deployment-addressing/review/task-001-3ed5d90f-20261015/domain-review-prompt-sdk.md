## Proposed retained finding

### P-SDK-R3-01 — FIND-001-13 remainder — MISSING focused journey proof

**Plainly:** TypeScript now exposes media variables, but its journey only checks an empty list, so it still does not prove that an authored media placeholder survives registration and hydration.

**Violated obligation:** R2 FIND-001-13 explicitly says to “include existing media names through existing fixtures”; REQ-008 and AC-004 require derived introspection across all three SDKs. This is a missing explicit proof, not a claim of broken production projection or lost stored JSON.

**Evidence/location:** `sdks/wyrd-sdk-ts/wyrd/tests/integration/register-and-hydrate.test.ts:200–222` loops four forms, all from media-free fixtures, and asserts `hydrated.mediaVariables` equals `[]` at line 219. The actual authored fixture graph at `fixtures/cards/register_and_hydrate/authored-prompts.yaml` references the same four media-free Prompts/Agents. The native projection is correctly reading `prompt.media_variables`; text/schema assertions meaningfully cover their fields, while replacing media_variables with an unconditional empty array would leave all current TS integration assertions green. The implementer evidence explicitly acknowledges the absence of a media placeholder.

**Correction boundary:** Extend the existing registered/hydrated fixture and focused TS journey with a supported nonempty `${media:name}` binding, using the existing shared Prompt grammar and lifecycle projection. Assert the exact derived media name on standalone lookup and Agent-linked navigation and retain the authored spec/hash assertions; retain the current empty/plain-text cases. Do not introduce a parser, new SDK surface, transport, schema or second harness. No production metadata repair is currently indicated by source.

**Focused closure proof:** Re-run the existing exact P8 selector after the nonempty case; demonstrate that dropping/replacing media_variables would fail this assertion. Use existing fixture consumers for applicable narrow checks, without a full journey aggregate. Missing historical RED alone is not a defect.

## Owner-raised Agent run-config normalization

Confirmed behavior: `Agent::from_card:687` uses `run_config_from_agent_run_config_spec`; that conversion starts `RunConfig::default()` with `tool_concurrency_cap: Some(8)` and `max_iterations: 10`. `agent_run_config_spec_from_run_config` unconditionally emits concrete max_iterations and the runtime cap, and `to_spec`/`to_card`/to_yaml/save and Python projections use it. Thus an omitted cap (or omitted full run_config) does not re-emit byte-equivalent authored spec. Runtime semantics still use the existing same default, and the loaded route/provider/model/ref are retained. Also, to_spec resets verified_by to an empty list; this existing runtime projection is not an exact retained-envelope serializer.

This review does **not** promote that question to a blocking new finding. REQ-008's exact authored JSON/hash preservation concerns the two Prompt forms; INV-004/AC-005 require invocation overrides to leave stored Agent/hash unchanged, which does not require re-emitting a runtime Agent as an identical Card. R2's actual loader criterion requires identity/ref/route/provider/model and execution, now meaningfully checked. The old whole-spec assertion exceeded that scoped criterion; its narrowing is disclosed and does not hide route loss. Fixing faithful runtime Agent re-emission, including explicit/default config representation and verification bindings rather than only cap8, should be tracked separately if desired. This conclusion is about approved scope, not an assertion that the save behavior is ideal.
