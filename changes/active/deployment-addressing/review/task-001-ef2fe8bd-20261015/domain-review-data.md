## Material findings

### DATA-001 — INCORRECT — granted batches can hide every open batch behind an unpageable empty result

Location: `crates/wyrd/wyrd-server/src/components/gateway/batches.rs:180` and `:573–614`; supporting SQL owner `crates/wyrd/wyrd-sql/src/queries/gateway.rs` BATCHES_SQL/gateway_batches.

Obligation: REQ-002 requires the same open/granted coverage for invoke-scoped batch visibility; AC-002 requires batch visibility proof. The existing bounded-pagination contract and its test require denied batches not to displace reachable batches.

Reachability and source proof: a principal with ordinary `gateway:invoke` scope `all` is intentionally denied access to a configured `granted` deployment without an object grant (`GatewayInvocation::decide`, invocation.rs:713–738). However, `invocable` returns `None` immediately for that same all grant. `list` therefore asks SQL for an unrestricted tenant page of `limit+1`, calculates `has_more`, and only then loads the deployment snapshot and removes denied rows. Create newer batches on a granted deployment with an explicitly authorized principal, and an older batch on an open deployment; list as an all-only principal with `limit=1`. The first denied batch fills the page. The response has `data: []`, `last_id: null`, `has_more: true`; the caller has no returned cursor with which to reach the open batch. Repeating the request repeats that result. `has_more` also reflects denied rows rather than visible continuation.

Sibling users: deployment- and exact-model-scoped batch pruning still uses the same SQL owner; `/v1/models` filters its complete finite configured-model set before returning and has no page starvation. Direct batch/file reads retain authoritative `decide` and should remain so.

Smallest safe correction: make the existing bounded SQL eligibility pruning account for current deployment open/granted access before LIMIT, using the same loaded tenant snapshot and effective scope semantics already owned by invocation. Retain the final audited per-returned-model decision and one bounded page read; do not add an unbounded scan or weaken granted access. All-plus-specific grants must still include explicitly authorized granted deployments/models.

Focused proof: extend the existing `gateway_batch_listing_is_one_bounded_pruned_read` test with real configured open/granted deployments, all-only and all-plus-explicit callers, and newer denied batches surrounding visible ones. Assert visible page IDs, usable last_id, correct has_more and tenant isolation. Existing test at pg_invocation_tests.rs:4632 has exact-scope pruning and an all caller, but creates no granted deployments, so its all assertion does not exercise the new denial condition. Run its exact Postgres-wrapped nextest selector; no broad new suite is necessary for closure.

### DATA-002 — INCORRECT/REGRESSION — retained GenAI spans identify a deployment as the provider

Location: `crates/wyrd/wyrd-server/src/components/gateway/capture.rs:921`; producer boundary `crates/wyrd/wyrd-gateway/src/engine.rs:494` and AttemptRecord at :337.

Obligation: REQ-001 explicitly separates adapter identity, credential-provider identity and deployment name; telemetry-observations requires meaningful standard signal identity; capture's own spans_batch contract promises standard GenAI provider attributes. Captured evidence must remain accurate after arbitrary deployment names replace provider prefixes.

Reachability and source proof: call an OpenAI adapter named `openai-primary` with capture enabled. The plan correctly addresses `openai-primary/gpt-4o`. AttemptRecord retains only the deployment name and ModelRef, and CallCapture::attempt_span copies them. `otlp_span` now writes `fields.model.deployment` to `gen_ai.provider.name`, so the durably captured trace says provider `openai-primary`, rather than `openai`. This applies to every captured attempt and fallback and to external arbitrary names. `spans_batch` projects it through project_spans and the existing ScribeOutbox into tenant `vala.traces.spans`; query consumers receive the false provider as retained evidence.

Sibling evidence: the same engine's live `attempt_span` already computes provider from `candidate.deployment.adapter.builtin_provider().unwrap_or("openai_compatible")` (engine.rs:680–682). Live and captured representations of the same attempt therefore disagree. Neither deployment name nor model identifier can recover the provider after dispatch.

Consequence: provider-grouped trace queries, comparisons and verification over these retained attributes misclassify calls; two same-adapter deployments appear as unrelated providers. Correct deployment identity already exists as a distinct attempt field and should remain.

Smallest safe correction: carry the actual admitted adapter provider identity with attempt capture facts at the existing engine/CallCapture boundary and use the same adapter-owned mapping as the live span. Preserve the deployment fields and actual per-fallback identity. This needs no new public management option or registry field and must not derive provider from a mutable post-call deployment lookup.

Focused proof: add assertions to the existing capture span projection test using a deployment whose name differs from its OpenAI adapter, and a second/fallback adapter. Assert retained provider is the adapter provider while retained deployment and model remain exact; assert parity with the existing live-span mapping. A focused capture test suffices for the projection seam; the existing real gateway capture journey can assert the same queried retained attribute without a new harness.
