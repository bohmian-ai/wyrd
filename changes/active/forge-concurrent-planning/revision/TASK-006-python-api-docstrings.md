# Complete public Python API docstrings at their sources

## Outcome and Value

Every public Python API in `wyrd` has concise, accurate documentation for
what it does and for each argument's type, meaning, accepted values where
bounded, default behavior, and relevant errors. Redundant prose is removed.
`TableConfig` is the concrete audit example: its seven constructor arguments
are all documented in both runtime help and the published typing surface.
This task follows the owner's explicit Python-documentation directive and
`AGENTS.md` §8; it changes no Forge behavior or approved specification
contract.

## Owners, Scope, Consumers, and Prohibited Changes

- Audit public runtime modules under `sdks/wyrd-sdk-python/python/wyrd/`,
  hand-authored stub sources under `python/wyrd/stubs/`, and Python-visible
  native docs only where a public object has no Python wrapper. Include
  constructors, public methods, functions, properties, and public typed
  structures. Private helpers are outside the sweep unless exposed in help.
- `TableConfig` appears in three Python files by design: the executable class
  in `bifrost/__init__.py`, hand-authored typing source in
  `stubs/bifrost.pyi`, and generated public stub in
  `bifrost/__init__.pyi`. The last file is generated by
  `scripts/assemble_stubs.py`. This is one runtime class, not three runtime
  implementations; do not remove the generated declaration or hand-edit it.
- Do not duplicate a type signature as filler prose. State what the type
  means, what omission does, and any allowed values that are not clear from
  the annotation. Runtime help and generated stubs must agree on semantics.
- No API signature, default, validation, wire contract, or stub-generator
  redesign is authorized solely to improve documentation. Correct discovered
  typing drift through its source, not by editing generated output.

## Approach

1. Inventory every public Python signature and existing docstring, comparing
   the runtime surface with its hand-authored source stub and generated public
   stub. Classify missing, redundant, and contradictory documentation.
2. Document `TableConfig` first, including `model`, `table`,
   `partition_granularity`, `sort_keys`, `bloom_columns`,
   `compaction_target_file_size_bytes`, and `compaction_type`. Explain the
   public layout values and server-default behavior from the actual contract.
3. Complete the same audit across the remaining public modules, editing
   runtime docstrings and source stubs, plus native source docs where they are
   the public help surface. Remove duplicate explanation within a surface.
4. Regenerate public stubs and inspect the resulting diff for semantic and
   signature agreement. Keep generated outputs generator-owned.

## Proof Strategy

This is documentation and generated-artifact work; TDD RED would manufacture
a behavior failure. Review a signature-to-docstring inventory for every public
module, with each argument accounted for and contradictory or repeated prose
resolved. Inspect `help(wyrd.bifrost.TableConfig)` and the generated
`wyrd.bifrost` stub as representative runtime and editor surfaces. Run
`mise run codegen:check`, `mise run py:format:check`, `mise run py:lints`, and
`mise run py:typecheck`. Do not add a permanent docstring linter merely to
verify this sweep.

## Acceptance Criteria

- Every public callable's arguments, including the seven `TableConfig`
  constructor arguments, have accurate type and semantic documentation at
  the public runtime and typing surfaces; optional arguments say what omission
  does. Public return values and material errors are explained where useful.
- Public typed structures describe fields whose meaning or valid values are
  not evident from the type alone. No public docstring conflicts with its
  signature, server-owned defaults, or the API contract.
- Repeated paragraphs that add no information are removed. Required runtime,
  source-stub, and generated-stub copies remain; generated files are produced
  only by codegen.
- All named verification commands pass. No behavior or signature changes are
  hidden inside the documentation sweep.

## Expected Write Set and Consumer Closure

Likely write set: public `python/wyrd/**/*.py` docstrings,
`python/wyrd/stubs/*.pyi` source documentation, Python-visible PyO3 rustdocs
where directly exposed, and generated public `.pyi` outputs after codegen.
The generator changes only if a proven generation defect prevents the source
documentation from reaching the public stub. Python users, `help()`, and
editor/type-checker consumers are the closure.

### `help(wyrd.bifrost.TableConfig)`

Before: the constructor showed `Initialize self.  See help(type(self)) for
accurate signature.` with no argument documentation; the generated stub's
`__init__` was `...` only. After (condensed; runtime help and generated stub carry the same full text):

```text
 |  __init__(self, model, table, partition_granularity=None, sort_keys=None,
 |      bloom_columns=None, compaction_target_file_size_bytes=None,
 |      compaction_type=None)
 |      Declare a table from a Pydantic model class.
 |      ...omitting all layout arguments lets the server choose: hourly
 |      partitions, wyrd_event_time descending nulls last, managed Blooms only.
 |      Args:
 |          model, table, partition_granularity ("hour"|"day"), sort_keys (<=4,
 |          asc|desc, first|last), bloom_columns (managed run_id/card_uid/
 |          principal_id first), compaction_target_file_size_bytes (>= 128 MiB;
 |          default 1 GiB), compaction_type (auto|full|small_files|
 |          files_with_delete; default small_files; copy-on-write -> full)
 |      Raises:
 |          WyrdError: SCHEMA_PARSE / BIFROST_RESERVED_COLUMN / SPEC_400_VALIDATION
```

### Contract Disagreements Found (reported, not resolved)

1. Omitted `compaction_type` default: Forge (`forge/settings.rs`
   `ForgeTableSettings::default`) and approved REQ-013 use `small-files`;
   `wyrd-spec` `RegisterTableRequest`, `BifrostTableDescription`,
   `CompactionTypeWire::Full` rustdoc (and the generated JSON schemas under
   `crates/wyrd-spec/{schemas,tests/schemas}`), and `wyrd-client`
   `TableConfig` rustdoc say `full`. Python docs follow the implementation.
2. `stubs/error.pyi` declares `WyrdError(code, message, *, details,
   remediation)` (and subclasses); runtime is a plain exception that takes no
   keywords and sets no `.code`.
3. `stubs/agent.pyi` `SessionTurn` differs from runtime (keyword-only,
   `call_id` vs `tool_call_id`, `role` type, methods); `Role` lacks `System`;
   `Agent` stub lacks `add_tool`, `set_tools`, `with_*`, `add_*` callback
   methods.
4. Raising in `after_agent`/`after_model`/`after_tool` callbacks reaches
   `unreachable!` in `skald` `loop_runtime.rs` (panic, not `CallbackAborted`);
   returning an `AgentRun` from `after_agent` fails the same way. Rust doc
   claims "raise to abort" for those callbacks.
5. Observer `on_agent_error` gets `SKALD_*` codes while Python raises
   `WYRD_*`; `on_agent_finish` gets `modelstopped` vs `FinishReason`
   `model_stopped`; `on_tool_result(ok=True)` for a skipped tool.
6. `AnthropicSettings.max_tokens` documented default 4096 has no serde
   default; `AnthropicSettings()` would fail to decode.
7. Stub/runtime surface drift: `testing.pyi` lacks 11 runtime methods;
   `state.pyi` `from_path` defaults `...` vs runtime `None`;
   `ModelCardMetadata` stub positional vs runtime keyword-only and declares
   getters runtime lacks; `HuggingfaceInterface` `hf_task` stub default vs
   required; `DataCardMetadata.to_dict` missing in stub; `PromptCardMetadata.prompt`
   absent at runtime; several `Prompt` static helpers and accessor getters
   missing from the stub; `AgentCard.kind` and `run_wyrd_cli` undeclared;
   several `Mapping`/`Sequence` annotations narrower or wider than runtime.
8. `WYRD_GATEWAY_409_RESOURCE_CONFLICT` remediation says pricing versions are
   immutable; the server returns `WYRD_GATEWAY_400_INVALID_CONFIGURATION`.
9. `Cards()` reads `[client] http_url` from `config.toml`; `WyrdClient`/
   `Bifrost` ignore it.
10. `wyrd-cards` `card_ref.rs` says External kinds are not constructable from
    Python; they are.
