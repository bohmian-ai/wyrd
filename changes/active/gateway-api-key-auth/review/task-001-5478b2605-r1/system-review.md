## Material proposed finding

### SYS-001 — A delayed successful exchange can admit a revoked key for a fresh 60 seconds

Classification: **INCORRECT**. Violated obligation: REQ-001, revoking a key takes effect within 60 seconds; task cache acceptance requires a fixed bounded reuse window.

Changed location: `crates/wyrd/wyrd-server/src/components/gateway/api_keys.rs:104-114` and `149-162`.

The cache's age starts with `Instant::now()` only after `TokenGrants::api_key(...).await` completes. The shared grant performs multiple awaits after reading the key: `verify_api_key` reads the active row, `touch_api_key_last_used` updates it, issuer resolution performs further tenant IO, and the caller awaits commit. SQL's active-key lookup is an ordinary MVCC SELECT (`wyrd-sql/src/queries/auth/service_accounts.rs:352-378`), not a lock coupled to revocation. `touch_api_key_last_used` updates by id without rechecking revocation (`416-431`), while both credential revocation writers use `revoke_api_key` (`queries/auth/api_keys.rs:12-33`, called by principal administration and platform provisioning). Thus a concurrent revocation can complete after the grant's active-key lookup; in particular a lookup can see the previous active version while a revocation UPDATE is uncommitted and then wait in the usage UPDATE. The grant's remaining IO/response scheduling can finish after revocation. A later-finishing concurrent exchange also replaces the same cache entry with its own new admission deadline.

Reachable consequence: an exchange observes an active key at t0; revocation becomes committed at t1; the successful grant reaches cache insertion at t2 > t1 after a database/network delay. The new entry is reused until t2+60, so a new request between t1+60 and t2+60 authenticates the revoked key without another grant. The local JWT check does not catch this: tenant tokens carry snapshot authority and normally live five minutes. A request timeout limits an individual delay but cannot make the post-revocation extension zero. This is a security recovery-bound failure, not a requirement for surviving replicas to stay available through the outage.

Smallest correction boundary: keep the existing grant and cache, but establish the non-sliding reuse deadline before starting its asynchronous exchange, and never give a late completion a fresh window at insertion. Preserve the token's own expiry cap and current per-request grant/verification/audit semantics. No distributed invalidation, new key lock, single-flight workflow, persistent cache, process termination or sibling availability change is necessary.

Focused closure proof: a controlled delayed exchange completing after a concurrent revocation must not admit a cache entry reusable beyond the original fixed 60-second window; cover a late completion replacing an existing entry as the same deadline invariant. Use the existing cache/managed grant seams and controlled times rather than host load or a new harness. The current unit test invokes `insert` directly with an already chosen time, and the current journey revokes only after warming has returned, so neither exercises the faulty interval.
