## Independent owner/alternative comparison

1. **Lane composition versus separate engine/runtime owners.** Before the change, HostedBlocks already owned Sandbox, Workspaces and engine composition. Extending it with two private Lane instances preserves that complete workflow. Putting these pools on the queued runner would leave synchronous execution without a shared composition owner; constructing another engine would duplicate authority/evidence/tool wiring. The candidate does neither. Lane is retained resource state, not a forwarding abstraction.
2. **Model permits versus gateway admission.** GatewayInvocation remains the owner of gateway admission, permissions, budget and accounting. That admission has no direct/queued resource selection in this change and is explicitly allowed to remain shared. A lane semaphore ahead of the existing call is the requested additional reservation, not a replacement for gateway governance. The candidate reuses ServerWyrdGatewayCaller, including native dialect projection and response decoding; no parallel provider workflow was added.
3. **Execution permits versus moving runner slots.** The existing runtime builder creates queued capacity shared by runner and group handoff. Retaining that owner while HostedBlocks supplies the new direct permit avoids moving queued lifecycle ownership or acquiring the same slot twice. The two callers select their mode at their established engine-composition calls.
4. **Test saturation versus replacement resource implementations.** Existing sandbox tests can hold real pending Python operations. The new journey needs to hold each admission independently, including model/workspace admissions, without generating load or involving another admission accidentally. Returning the existing owner's OwnedSemaphorePermit exercises its actual counter and adds no fake executor, alternate limiter, or polling registry. The generic hold helper is limited to test-support and shared only across these semaphore owners.
5. **Live log observation versus existing telemetry capture.** The existing LogCapture handles thread-default events; the test server composes and runs tasks on the shared Wyrd runtime (`server.rs::on_shared_runtime`). `shared_process_telemetry_for_test`/TestTraceCapture instead export finished spans, with events exposed only after the owning span finishes (`TestTraceCapture::finished_since`). The model-capacity assertion must observe its wait while the call is still held; waiting for finished-span export would deadlock that proof. Extending the existing LogCapture with global installation supplies the missing live observation without adding a second event storage/parser framework. The journey owns the process subscriber before starting its server.
6. **Journey owner versus testing-library target.** The existing SDK integration target owns fixture declaration, hydration and verification through SDK handles. CapacityDesk reuses those complete workflows, and WyrdTestServer remains the server/lifecycle owner. The test-support crate gains only configuration/hold access, not another SDK harness. The task records the target placement deviation; there is no duplicated production workflow from that choice.
