## Why the proposed blanket timeout is unsafe

1. `gateway/caller.rs:135–185` measures the lane wait, then sends a **duration** to the gateway. `gateway/invocation.rs:565–598` awaits snapshot, possible attribution and routing before `:601` adds that duration to a new `Instant::now()`. `gateway/service.rs:632–662` can use a real tenant checkout and snapshot query/commit. A legitimate near-budget lane wait followed by a delayed cold snapshot can therefore start billable provider work after the original call deadline. The delayed snapshot is excluded from the new test, which uses fast admission and allows a 25% timing margin (`pg_invocation_tests.rs:6125–6153`).
2. The existing `govern` creates a child-token drop guard **after** `admit_call` returns (`invocation.rs:461–489`). Timing out and dropping `run` after that handoff cancels the child. `wyrd-gateway/src/engine.rs:625–655` checks expiry before starting an attempt, but while an attempt is pending, its biased select checks cancellation before the deadline. Expiry implemented as a drop can therefore leave `cancelled` evidence (or return a caller-side generic timeout before the engine reports) instead of the actual deadline's `timed_out` attempt and exact `RemoteProblem` at `pg_invocation_tests.rs:6137–6165`. `respond` deliberately maps these terminal outcomes differently (`invocation.rs:775–783`); neither the caller nor the test should normalize them into one outcome. Genuine external drop/cancellation still needs that guard and precedence.
3. Before handoff the same blanket timeout can interrupt **mutating** ledger admission. `gateway/ledger.rs:417–443` obtains `Admission` only after the call to `GatewayAdmissions::admit` returns. `wyrd-sql/src/queries/gateway_admission.rs:4–7,146–164` explicitly uses an autocommit statement; the mutation can commit before its answer is received. Dropping that future is not a rollback proof and leaves the caller without the admission value needed for normal settlement. Capture-slot reservation is different: it is RAII, waits on the supplied deadline, and returns unused capacity on drop (`wyrd-runtime/src/outbox.rs:475–518,713–724`; `invocation.rs:634–663`).
4. Supplying the absolute deadline alone will stop late dispatch: `CallTask::run` forwards `AdmittedCall.deadline` to the existing engine (`invocation.rs:1245–1262`), whose pre-attempt check rejects an expired call. But that alone can still make the lane and caller await slow admission; it can also delay the caller after the engine stops, because `settle_buffered` awaits settlement at `:1336` before the oneshot send at `:1344` and captures after send at `:1353`. The existing contract deliberately waits for settlement before returning a buffered answer so an immediate next call never sees its own lease, token hold or reservation (`:1285–1294`). An absolute provider deadline and this accounting-before-answer boundary are different guarantees.

## Smallest safe boundary

- The lane caller owns **one monotonic instant** established before waiting. Use `timeout_at` for lane acquisition, retain the existing local `ProviderError::Timeout` while waiting and existing cancellation/permit cleanup. Pass the absolute instant privately to the same `GatewayInvocation` (for example a private/internal bound on the invocation handle). Do not alter `GatewayCallRequest`'s ordinary relative timeout contract, its public callers, or the unbound Skald path. `skald-agent/src/gateway.rs:37–62,73–95` already supplies and classifies the call budget and the gateway deadline code; no new wire error, retry rule, or option is needed.
- At `admit_call` split the reversible preparation from the `self.admit` ledger write at `invocation.rs:629`. Bound the snapshot/authorization/route preparation by the absolute instant, preserve completed decisions/refusals and audits, and reuse the existing capture-slot deadline and staging refusal. Check expiry before beginning the ledger mutation, including after a capture slot arrives. Reuse that exact instant for `AdmittedCall.deadline`; do not derive a fresh duration after the async work. Use the existing `GatewayDeadlineExceeded` problem for gateway deadline expiry and leave ordinary cancellation distinct.
- Once the ledger write starts, keep the existing admission and tracked handoff. If the ledger commits after the deadline, continue into the normal `CallTask` with the original expired instant; the existing engine pre-attempt check yields `TimedOut` with no dispatched attempt. Use the actual `Admission` for ordinary settlement, including release of the actual lease/holds and no billable usage (`ledger.rs:134–144`). Let the normal reply and capture follow. A pending provider attempt expires through the engine’s timer and remains `timed_out`; the genuine external-drop guard remains unchanged.

This is the smallest correction supported by the demonstrated defect and the explicit R4–R7 proof: the budget governs lane waiting and provider work, including reversible gateway preparation; no new provider work can begin after it. Durable admission and settlement may complete after expiry before the caller sees the normal gateway problem and releases its permit. This is the existing accounting order and remains necessary to preserve the immediate-next-call behavior. The ten-minute Skald duration description and R1’s broad “across … invocation” wording should not be read as a new hard reply-time SLA under a stalled database: R5 measures provider deadline/termination and R6 preserves ordinary accounting. If the human authority intends strict caller return even while an admission or settlement statement is in flight, that requirement conflicts with preserving settlement-before-answer. It would need a material decision about immediate retries meeting their own outstanding charges and permit lifetime. Returning a local timeout early would require protecting in-flight admission with tracking and deliberately disarming the guard on deadline so timed-out work still settles; that alternative is feasible but changes the user-visible ordering and is not warranted by this finding. Do not prescribe it or change engine cancellation priority.
