## Proposed material finding

### SYS-R2-001 — Remaining duration is restarted after gateway snapshot admission

- **Classification:** INCORRECT; incomplete **FIND-001-2** closure, not a new gateway redesign obligation.
- **Violated obligation:** remediation FIND-001-2 requires enforcing one original per-call deadline across lane acquisition and the existing governed invocation, including expiry before dispatch, while preserving ordinary gateway lifecycle. R5/R6 require the original bound and cleanup. The Skald call contract calls `timeout` the remaining time the call may take, enforced by its caller (`skald-agent/src/gateway.rs:43–53`).
- **Changed location:** `components/gateway/caller.rs:155–185`, especially passing the captured remaining duration into an unbounded `.run(...).await`. **Relevant consumer:** `components/gateway/invocation.rs:565–568,601`.
- **Producer-to-consumer proof:** caller measures elapsed lane wait and computes `remaining` once. `GatewayInvocation::admit_call` then awaits `GatewayAdministration::snapshot` before constructing its absolute provider deadline as `Instant::now() + request.timeout`. The snapshot's complete body (`service.rs:632–662`) checks the cache, otherwise awaits a real tenant connection, snapshot SQL and commit. Cache misses are ordinary after startup, invalidation or bounded-cache eviction (`snapshots.rs:3–21,79–105`). The tenant pool has its own independent default five-second acquire timeout (`wyrd-sql/src/pool.rs:40–50`), not the caller's remaining duration. Neither `.run` nor this snapshot phase is enclosed in the original caller deadline. After the delayed snapshot succeeds, dispatch receives a newly advanced absolute deadline.
- **Supported material scenario:** a queued Agent has the normal ten-minute Skald call duration and the explicitly supported two-hour execution ceiling. Another call holds its model lane until approximately 599 seconds, leaving approximately one second. A cold/invalidated snapshot then waits two seconds for a tenant-pool checkout, comfortably inside the existing five-second pool bound. The call can dispatch provider work at approximately 601 seconds and receive another approximately one second of execution. It retains the lane and queued runner slot beyond its original bound and can start chargeable provider work after that bound. This requires ordinary model contention plus shared Postgres contention, not unbounded database waits, arbitrary configurable provider timeouts, synthetic load, or a new throughput guarantee.
- **Why this is within remediation:** the prior accepted gateway admission semantics are unchanged and are not independently reopened. The new lane wait can consume almost the entire call budget, so an independently bounded ordinary gateway admission now exceeds the tiny remainder. Subtracting lane time fixes the reported nine-plus-two-minute fast-admission case but does not implement the explicitly selected single original bound. The existing test uses prompt admission and can pass while this path remains reachable.
- **Smallest safe correction boundary:** retain the existing caller as the owner of the original lane-bound duration and bound its lane wait plus existing governed invocation by that original deadline. Keep unbound behavior unchanged. Continue using GatewayInvocation for authorization, provider cancellation and tracked accounting/settlement; do not move those owners, add another scheduler, alter public gateway deadline semantics, or abort tracked settlement. Its existing drop guard cancels admitted work when the enclosing caller expires, while its tracked CallTask continues settlement. A downstream gateway-only change cannot account for the prior lane wait unless its contract is expanded, which is unnecessary here.
- **Focused proof:** extend the existing real caller fixture with a short original budget, spend part waiting for the lane, then keep actual snapshot/tenant-pool admission pending past the original bound. Require timeout and zero provider dispatch before releasing the dependency; release pressure and require following call success and restored permit. Preserve the current hung-provider test's tracked `timed_out` capture and successful next call. This is one local timeout correction and one bounded failure-path assertion, with no new harness/dependency or performance experiment.
