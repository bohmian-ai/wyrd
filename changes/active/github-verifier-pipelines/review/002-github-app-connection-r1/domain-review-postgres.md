## Proposed findings

### PG-1 — INCORRECT — Token mint can complete after disconnect releases the installation

REQ-001, AC-001, the approved connection contract and the security posture require connection use and new source IO to stop on access loss. `GithubConnections::installation_token` reads the slot without a lock and commits the tenant transaction before provider IO (`service.rs:641–645,668`). `fence_and_release` locks only writers that participate in the row lock (`:333–342`). The provider mint independently sends the App-signed request and returns the bearer (`app.rs:374–401`).

Tenant A can begin the mint, then commit a Wyrd disconnect while the provider response is in flight. A Wyrd disconnect releases the SQL association and does not remove the GitHub installation, so GitHub can still grant the token. Tenant B can even claim the installation before A's mint returns. The facility then hands the old tenant a live bearer with source and PR/check authority. The same handoff can bypass a concurrently committed tenant selection change when GitHub still grants the repository. The sequential token refusals in `pg_github_connection.rs:146–178,281` exercise only mints begun after the mutation. Although task 006 supplies the first queue consumer, the approved task explicitly ships and tests the token facility.

Close the check-to-handoff window in `GithubConnections::installation_token` using the existing durable association/access fence. A short tenant read after the provider response can discard a stale response before exposing it, with the association identity and requested repository checked under the current authority. If the mint itself is serialized, use the same slot lock for the bounded mint and its writers so a successful disconnect cannot overtake it. A slot-wide revision change for an unrelated repository must preserve authorization for the requested repository. Prove with a controlled mock mint barrier and a real tenant disconnect or deselection, asserting that the old association cannot hand out a token after the committed fence and that an unrelated repository still works. No queue change or extra storage is needed for this proof.

### PG-2 — INCORRECT — Token and view reinterpret a saved installation on a different configured host

REQ-001 and the connection contract bind provider identity and repository selection to the configured host. `config.rs:2323–2332` defines that host as the web origin's host and optional port. Callback and webhook write/routing paths preserve that host (`service.rs:497–506,570–604` and migration `:42–44`). In contrast, `GithubConnections::view` projects the configured host alongside any associated slot and `installation_token` trusts the saved numeric IDs without checking `slot.host` (`service.rs:176–198,646–668`). The provider mint uses the current App and current API origin (`app.rs:374–378,409–412`).

A deployment can reopen its existing PostgreSQL database with valid configuration for a different GitHub Enterprise Server. Installation and repository numbers are scoped to each GitHub host, so both hosts can have the same numeric pair. The public view presents old repositories as verified for the new host, and the token facility can issue a bearer for a repository that the tenant never authorized on that host when the new App grants it. Provider checks only establish the new App's access and cannot recover the missing tenant selection proof. Compare the persisted host with the current host at the shared view/access boundary and require a new verified association before source access on the replacement host. Keep the existing disconnect path capable of releasing the old slot. Prove with a slot verified against one origin and a replacement mock origin with matching numeric IDs, asserting the view does not attribute the old selection to the new origin and the provider receives no mint request on old authority.

### PG-3 — INCORRECT — Removal of a newly selected repository can be lost across a concurrent reconnect

The task requires revalidation before association, synchronization of provider removals and source fences on access loss. Callback reads the provider repository list and later writes it conditionally against the connection's captured revision (`service.rs:494–508`). `REMOVE_REPOSITORIES_SQL` increments revision only when the incoming IDs overlap the old persisted selection (`queries/github_installations.rs:81–96`), and the webhook acknowledges after that no-op (`service.rs:597–617`). The SQL proof explicitly expects no revision-changing write for an unselected repository (`pg_github_installations.rs:482–488`).

A tenant already selecting A can refresh the same installation when GitHub also allows B. After the callback obtains the new list `{A, B}` but before association writes it, GitHub removes B and the signed webhook runs. B was absent from the old slot, so the webhook leaves its revision untouched. The callback then commits `{A, B}` at that same revision and advertises B as selected and accessible despite the already acknowledged removal. The current token endpoint can later catch GitHub's refusal. It does not repair the incorrect durable selection or the access view handed to subsequent repository resolution tasks.

Advance the callback fence for a removal naming the currently associated installation even if none of its repository IDs has reached the stored selection. Retain the existing list-subtraction behavior, exact tenant/host/installation routing and unaffected repository access. A focused real-Postgres transition test can capture the old slot binding, apply and commit a removal for a newly proposed ID, then attempt to associate using the captured binding and assert it is stale while A remains selected. This uses the existing revision and query owner and needs no independent webhook ledger.

### PG-4 — VIOLATION — New SQL proof reports success without PostgreSQL

`crates/wyrd/wyrd-sql/AGENTS.md:72–77` expressly requires PostgreSQL tests to fail when the environment is absent. All five new `pg_github_installations` cases use `database_url()` to exit successfully before setting up the fixture when `WYRD_DATABASE_URL` is missing (`pg_github_installations.rs:35–38,129–131,213–215,298–300,400–402,536–538`). A selected nextest run can report five passing tests without running any assertions. The recorded `test:sql` command provisions a database (`mise.toml:1590–1606`), so this finding concerns future verification rather than disputing that evidence. Delete the local guard and let `PgFixture::start().expect(...)` enforce the existing dependency. The `pg_*` naming and `test:sql` lane already identify and provision these tests. Run the same focused selector with the repository Postgres wrapper and verify it fails clearly when directly selected without PostgreSQL configuration.
