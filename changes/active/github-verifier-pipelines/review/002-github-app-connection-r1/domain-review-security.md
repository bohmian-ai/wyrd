## Findings

### SEC-1 · INCORRECT · An installation token can be handed off after disconnect has released its association

REQ-001, INV-006, AC-001 and task O19/O22/O23 require active association and a fence before release. In `crates/wyrd/wyrd-server/src/components/github/service.rs:635-668`, token issuance reads the slot and commits before the remote token request. It returns that request's token directly. The disconnect path independently locks and releases the row, then commits at lines 303–319 and 333–342. Webhook suspension and removal also change the slot while the provider request runs at lines 582–609. The comment at lines 325–329 claims these do not interleave with token decisions.

An installation-token request can read the active slot, block on the provider, and resume after a successful Wyrd disconnect and even another tenant's verified claim. Wyrd's disconnect does not uninstall on GitHub, so the old operation receives a usable token that can start new source IO under released authority. The existing integration checks sequential refusals after webhook and disconnect (`tests/integration/pg_github_connection.rs:146-178,281`). Those requests cannot expose this interleaving.

Use the existing slot identity/revision and tenant capability to validate authority again after remote IO, at the credential handoff, and drop the unreturned token when the operation lost its claim. Preserve current access for unrelated repositories. This avoids holding a Postgres transaction across GitHub network latency. Proof should block the mock token response, commit disconnect, release the provider response and assert a typed refusal. Exercise a matching repository removal and an unrelated repository control. Consumers that start work after receiving a credential still need their approved operation-bound fence in later tasks.

### SEC-2 · INCORRECT · A configured host change can use an association verified on another GitHub host

REQ-001 records the verified host as part of durable identity. INV-001 and the GitHub connection contract require stable repository identity and both tenant-selected and current installation access. The database reads the tenant's stored host, and association writes refuse to refresh a different host (`crates/wyrd/wyrd-sql/src/queries/github_installations.rs:124-142,184-189,237-249`). `GithubConnections::view` instead emits the new configured host beside any old installation and repository IDs (`crates/wyrd/wyrd-server/src/components/github/service.rs:176-199`). `installation_token` never checks `slot.host` and uses the current App's API base for the old numeric IDs (`service.rs:635-668`, `app.rs:369-379,409-412`).

After an operator switches to a different GitHub host and restarts against the same database, the service presents the old association as verified on the new host. An installation and repository with coincident numeric IDs on the new independent GitHub host are enough to mint a token without a tenant ever selecting that repository there. Even without collisions, the connection read falsely reports verified identity and access. No special host-management workflow is required to see this path. Hosts are configurable and associations are durable across restart.

Use the existing stored host as the scope for projecting usable associations and admitting token requests. A mismatch should require the ordinary disconnect and verified reconnect, with disconnect still able to release the old slot. Exercise two configured hosts against the same database with matching numeric IDs and verify the old slot neither projects as active on the new host nor triggers a token request there.

### SEC-3 · INCORRECT · OAuth requests the REST vendor media type and assumes a JSON token response

REQ-001 and AC-001 require both entry paths to finish a provider authorization. `GithubApp::exchange_code` uses the shared REST request builder, which sets `Accept: application/vnd.github+json`, then decodes the web OAuth endpoint's response exclusively as JSON (`crates/wyrd/wyrd-server/src/components/github/app.rs:221-241,438-448,470-481`). GitHub's same web token endpoint documents a form-encoded default and `Accept: application/json` for JSON. Octokit's integration guidance specifies JSON media type for that endpoint. A provider following this negotiation can return a successful form body, and Wyrd maps it to `WYRD_GITHUB_503_PROVIDER_UNAVAILABLE` after committing consumption of the state. Both entry paths converge on this exchange. The mock ignores request headers and always returns JSON (`crates/wyrd/wyrd-testing/src/github.rs:531-555`), so green journeys bypass the mismatch. [GitHub web token endpoint response formats](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#2-users-are-redirected-back-to-your-site-by-github) · [Octokit integration handbook](https://github.com/octokit/handbook#oauth-app-authentication-client_idclient_secret)

Negotiate JSON explicitly for the web exchange using the same screened transport, and keep REST media/version headers scoped to REST. Have the existing mock enforce the documented response negotiation, then run the existing callback journey. No fallback decoder is needed.

### SEC-4 · INCORRECT · Valid out-of-order suspension events can leave an active installation fenced indefinitely

Task O21/O22 and AC-001 require synchronized suspension and repository access. In `crates/wyrd/wyrd-server/src/components/github/service.rs:583-609`, Wyrd takes the latest received `suspend` or `unsuspend` action as current. SQL's idempotence predicate compares only the stored boolean (`crates/wyrd/wyrd-sql/src/queries/github_installations.rs:67-78`). GitHub explicitly permits out-of-order deliveries. If it suspends then unsuspends an installation, delivery of `unsuspend` first does nothing against an already-active slot. The later older `suspend` persists a false suspension and makes the token owner refuse before calling GitHub (service lines 658–668). The view stays suspended and eligible work stays blocked with no later event required. The existing journeys deliver transitions in sequence (`pg_github_connection.rs:170-178`, Rust SDK journey lines 484–507). A delayed or redelivered removal can likewise erase a repository after a later callback has already verified the user's selection again, because removal SQL compares only IDs and presence. [GitHub webhook delivery order](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks#webhooks-deliveries-are-out-of-order) · [GitHub webhook redelivery](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks#use-the-x-github-delivery-header)

Treat the signed notification as a trigger to reconcile current suspension using the existing App installation lookup, and apply the result only to the still-matching association. For repository removal, ensure stale deliveries cannot overwrite a later verified selection. Validate the provider's supported ordering or current-access evidence before choosing the smallest correction at that owner. Do not use an `added` event as proof of tenant selection. Exercise a delayed suspend after a newer unsuspend and a delayed removal after reselection against the same existing mock. A delivery-ID dedupe alone does not handle a first delivery out of order.

### SEC-5 · VIOLATION · The transaction-bearing browser setup redirect omits no-store

The first-party browser session rules in `architecture/wyrd-security-posture.md:415-418` require `Cache-Control: no-store` for credential-bearing responses. The setup response contains the raw one-use browser binding credential in `Set-Cookie` and the matching transaction state in its redirect Location. It emits neither the required header nor any other cache-control metadata (`crates/wyrd/wyrd-server/src/components/github/routes.rs:189-207`). The cookie helper supplies credential flags, and the router only adds tracing and request metrics. A configured HTTP cache can store and replay the setup response, retaining both values that bind a credential-bearing transaction to a browser. RFC 9111 specifies that Set-Cookie does not inhibit caching. This is an explicit policy violation even where a given cache would decline a 302 by default. [RFC 9111 §§5.2.2.5 and 7.3](https://www.rfc-editor.org/rfc/rfc9111.html)

Use the existing no-store response owner in `crates/wyrd/wyrd-server/src/auth/oauth.rs:140-151` on the credential-bearing redirect. Assert the served setup response has `Cache-Control: no-store` beside its location and binding cookie. Apply the same header to other responses carrying the transaction state where that existing policy applies.
