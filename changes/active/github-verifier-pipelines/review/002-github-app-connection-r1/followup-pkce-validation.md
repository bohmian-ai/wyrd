# GitHub Enterprise Server PKCE validation

**REVISED.** The documented GitHub App flow on supported GitHub Enterprise Server releases cannot supply the code-to-transaction binding that the candidate's security posture promises. The evidence establishes a security contract conflict. The specific behavior of a running appliance when it receives the extra parameters was outside this validation. Reconciling the configured-host commitment with a verified association on these hosts requires a security decision beyond this task (`SPEC_REVISION_REQUIRED`).

## Provider contract

As of November 10, 2026, supported GitHub Enterprise Server releases are 3.19 through 3.22. The versioned GitHub App user-token web flows omit the PKCE parameters. GitHub's own documentation source resolves the ambiguity in those omissions. The App challenge and verifier rows are gated by the same `pkce_support` feature as the explicit unsupported notice in the OAuth App article. GitHub defines that feature for both GitHub Apps and OAuth apps and enables it for `fpt` and `ghec` only. This establishes the documented support boundary for GitHub Apps independently of any inference from the shared endpoint names. GitHub.com's App article describes S256 and the matching verifier. ## Wyrd path and consequence

`GithubConnections::begin` creates a fresh verifier and stores it in the transaction (`service.rs:255–277`). Both setup paths produce a redirect through `GithubApp::authorize_url`, which always attaches the challenge and S256 method to the configured web origin (`service.rs:355–395`, `app.rs:185–195`). The callback consumes the pending row using the caller's tenant, principal, state, and browser binding, then sends the supplied code with that row's verifier through `GithubApp::exchange_code` (`service.rs:418–451`, `app.rs:221–247`). The provider returns the user token as the only evidence from that exchange. Wyrd uses the token for installation and repository checks and can commit an association for the callback's tenant (`service.rs:452–507`).

PKCE requires the provider to associate the issued code with the original challenge and reject a mismatched verifier. OAuth 2.0 directs authorization and token endpoints to ignore unrecognized parameters. Under the documented non-PKCE provider contract, a successful exchange supplies no proof that the returned authorization code was issued for Wyrd's pending transaction. A tenant connection writer with a fresh, unredeemed code obtained from another authorization for the same deployment App and redirect can present that code with their own valid state and browser binding. These values authenticate the writer's pending transaction while the provider token carries the other user's access. If the installation is accessible to that user, eligible for association, and either matches the hint or is the only accessible installation, the ordinary checks can associate it to the writer's tenant. RFC 9700 describes this confidential-client code injection and the independent protection provided by PKCE. This is a protocol-level security consequence on a supported host, with possession of a valid unredeemed code as a precondition. [RFC 6749 §§3.1–3.2](https://datatracker.ietf.org/doc/html/rfc6749#section-3) · [RFC 7636 §§4.4–4.6](https://datatracker.ietf.org/doc/html/rfc7636#section-4.4) · [RFC 9700 §4.5](https://datatracker.ietf.org/doc/html/rfc9700#section-4.5).

The candidate's configured-host test evidence covers URL shape and redacted host reporting through a mock (task obligation O4). It cannot establish enforcement by GitHub Enterprise Server. No live GitHub Enterprise Server exchange or code-injection reproduction was performed. The evidence does not establish that valid GHES connections fail outright.

## Correction boundary

The configured host's authorization and exchange capability is the relevant boundary. GitHub documents no PKCE switch for these GHES versions. Removing the PKCE parameters or qualifying the posture would leave the code-to-transaction binding unresolved. Refusing these releases would narrow approved host support. The authority establishes neither an exception to the binding nor an alternative provider-backed mechanism for GitHub Enterprise Server. Select the supported host and security contract before assigning implementation remediation. Closure evidence should show that the selected contract both completes legitimate association and rejects a different transaction's code for each provider capability it supports.
