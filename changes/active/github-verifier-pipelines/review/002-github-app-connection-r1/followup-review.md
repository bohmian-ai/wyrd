## First association and association from a released slot

The callback commits consumption of its one-use state, verifies App ownership and suspension, reads user-accessible repositories, and only then enters the tenant transaction that writes the association (`wyrd-server/src/components/github/service.rs:439–451,482–509,531–533`). The installation-to-tenant query matches an already associated host and installation (`wyrd-sql/migrations/20261110000000_github_installations.sql:54–74`). During the first verification-to-commit interval, an authenticated removal, suspension or deletion has no route and returns HTTP 202 (`service.rs:555–581`, `routes.rs:302–315`). A released slot has the same interval since release clears the host and installation ID (`wyrd-sql/src/queries/github_installations.rs:99–109`).

For example, after GitHub answers a first callback with repository B, a repository removal can receive 202 before the callback inserts B. The resulting committed access view is stale. Deletion at that point can leave a claim that the tenant must disconnect before replacing. Source credential issuance still asks GitHub for the exact repository and maps provider refusal to inaccessible (`service.rs:635–668`, `app.rs:369–401`). This establishes stale metadata and the lost routing opportunity. The approved first-association flow calls for provider revalidation before association, and the approved lookup routes existing associations. These obligations give no tenant owner to a pre-association delivery and do not establish atomicity with provider changes.

A second read before commit shortens this interval and leaves the same ordering possible. A read after commit allows stale state to become visible and can leave it behind if the process dies or the provider fails. An atomic guarantee for this first-route interval would require a new durable coordination decision, for example a routable pending claim with rules for visibility, contention, and cleanup, or a new freshness contract for reads. The two associated cases below have corrections within the existing decisions. I am leaving the first-route interval out of their remediation and recording no new first-association finding.

## PG-3 — preserve the callback fence for a routed removal

An associated tenant already selects A. Its callback binds the slot revision, then GitHub answers with A and newly available B. A signed removal of B is routed to the existing tenant, and `REMOVE_REPOSITORIES_SQL` checks overlap against the old stored selection A. The predicate matches zero rows and the handler commits and returns 202. The callback locks the slot, observes its unchanged binding, and commits A and B. The read view and later repository resolution can now treat B as selected after Wyrd acknowledged its removal. Provider refusal during minting does not repair the durable selection. If the removal names a repository already in the stored selection, the SQL already increments the revision and the callback correctly refuses. The SQL test currently asserts that removal of an unselected repository writes nothing. Evidence is in `service.rs:236–254,494–508,597–609`, `queries/github_installations.rs:81–96,219–266` and `wyrd-sql/tests/integration/pg_github_installations.rs:482–488`.

A nonempty removal for the exact associated host/installation must advance the existing revision even if none of the IDs appears in the old selection. Keep subtracting only the removed IDs and keep unrelated A accessible. The callback that has crossed the event takes the existing stale-conflict path and fresh authorization can start at the new revision. If callback publication wins first, the removal subtracts B in the ordinary update. A replay can also invalidate an overlapping callback. That cost is one fresh authorization under the existing conflict behavior, while ordinary source access for unaffected selections continues. This is one SQL owner change with no provider round trip or new persistent state. Focused proof is to capture the revision for A, apply and commit a signed or query-level removal for B, then attempt a write of A and B against the captured revision. Assert the stale result and that A remains selected.

## SYS-02 — reconcile suspension from current GitHub state under a revision check

Once associated, the current webhook assigns suspension from the action string (`service.rs:587–595`). If GitHub suspends and resumes but Wyrd receives the unsuspend first, the old SQL state is active and `SUSPEND_SQL` is a no-op. The late suspend then persists a false suspension (`queries/github_installations.rs:69–78`). GET reports suspended and token access refuses before checking GitHub (`service.rs:177–195,658–668`). That persists until another correction changes the slot. No in-flight callback is needed for this sequence. If a real suspend is committed during a reconnect, the existing suspension change already advances the revision and invalidates the callback. Its incorrect result under reversed delivery comes from treating an action as current state.

Reuse `GithubApp::installation` (`app.rs:250–275`) for current suspension on the two signed notifications. The connection owner captures the exact routed slot and revision in a short tenant read, closes the transaction before provider I/O, and applies the observation in a separate short conditional tenant write. On a changed revision, discard the old observation and re-read provider state for the still-matching association. Exit when the slot no longer matches. Bound contention and return an existing typed failure if a still-matching slot cannot be synchronized. A transient provider failure or an absent App installation supplies no suspension observation. Preserve the separate deletion/release owner. This uses the existing ownership and generation fields, with no new public state or API. GitHub documents manual or scheduled redelivery for failed deliveries. [Failed-delivery handling](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)

The conditional write must fence concurrent observations even when the current provider boolean matches the stored boolean. For example, a suspend handler can read provider suspended and pause while an unsuspend handler reads provider active and sees the old active SQL state. If the latter still does no revision-changing write, the older suspended observation can overwrite it at the same revision. Advance the private revision on a successful observation while preserving the stored suspension instant and view timestamps when the public state stays the same. Exact slot and revision checking also protects the disconnect/reconnect boundary without holding a SQL lock during a provider wait. Extend the existing mock-backed proof with reversed deliveries and a paused older provider response overtaken by a current observation. Assert final active access in both, and retained ownership during genuine suspension.
