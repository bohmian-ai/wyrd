## Proposed material findings

### MNT-001 — Config accepts an RSA public key and discovers the failure at first use

**INCORRECT.** `crates/wyrd/wyrd-server/src/config.rs:2450`, `components/github/app.rs:148` and `:489`, `boot/mod.rs:1323`. Task O3 requires typed validation of invalid present config. The config owner and App constructor each call `EncodingKey::from_rsa_pem`, then the App stores both the PEM in settings and the encoding key. The pinned `jsonwebtoken` 9.3.1 `src/pem/decoder.rs:172` accepts `RsaPublic` and `RsaPrivate` in that call. `src/crypto/rsa.rs:33` first requires a valid RSA signing pair when signing, using `RsaKeyPair::from_der`. The existing checked-in mock's public PEM is a concrete accepted input for the two startup checks. When a callback needs `GithubApp::installation` or background work needs a token, `app_jwt` then classifies the signing failure as `GithubUnavailable`. The deployment therefore starts with a broken App and directs diagnosis to GitHub rather than the misconfigured key.

Keep validation in the config owner and use the already installed signing implementation to prove the parsed key can sign RS256 before accepting it. Give the App the validated key instead of having its constructor parse the PEM again. A config unit case using the existing public half must return `ConfigError::Invalid` naming the App private key; the valid private fixture must still load and complete a signed request. This requires one validation boundary and no new crypto parser.

### MNT-002 — The webhook owner implements HMAC key handling by hand

**DRIFT.** `crates/shared/wyrd-crypt/src/lib.rs:451` and `:478`, `crates/shared/wyrd-crypt/Cargo.toml:13`. Root AGENTS requires reusing installed dependencies before adding new code. The candidate implements the RFC 2104 inner/outer pad, overlong key hashing, zeroization and constant-time comparison in Wyrd. Existing `Cargo.lock:3821` resolves RustCrypto `hmac` 0.12.1 with `digest` 0.10.7, the same digest generation used by the existing `sha2` 0.10. `Hmac<Sha256>` covers arbitrary-length keys and constant-time full-tag verification. The manually written cryptographic primitive adds code a maintainer must review for every security change, and the fixture signer and production verifier share that primitive.

Use the already resolved RustCrypto implementation directly inside `wyrd-crypt`; retain the thin signing and verifying functions used by `GithubApp` and the mock. Drop the new direct `subtle` edge if no longer used there. Keep the existing independent RFC 4231 short/long key and wrong/truncated tag assertions and the signed webhook proof. The correction adds a manifest edge to a package already present and removes custom key padding and comparison logic.

### MNT-003 — A saved association can authorize the same numeric IDs on another host

**INCORRECT.** `crates/wyrd/wyrd-server/src/components/github/service.rs:177` and `:642-669`, `components/github/app.rs:369-402`. REQ-001 and the GitHub connection contract require verified installation and selected repository access under the configured host. SQL persists `GithubInstallationRow.host`, scopes webhook routing by host, and requires matching host plus installation when refreshing a live slot. The token owner uses only installation ID and repository ID from the old slot. The App sends them to the currently configured API origin. Likewise the view advertises the current host while rendering the old slot as active. Reconfiguring a deployment from one GitHub Enterprise host to another leaves the slot durable. If the new host's installation and repository sequences have the same numbers, GitHub's valid current answer concerns a different repository the tenant never selected. Even without matching IDs, the view misstates what has been verified. Numeric identity has meaning within the already-persisted host boundary.

Validate the persisted host against the configured App in the shared owner before projecting an active association or asking GitHub for a token. Use the existing slot and explicit release/reconnect path, without adding host-management machinery. Demonstrate a slot persisted under a different host, a same-number repository at the configured mock, a non-active current-host read and no token request. Retain disconnect as the operation that releases a stale slot. Existing `associate_github_installation` host comparison and exact-host webhook lookup provide nearby patterns.

### MNT-004 — Release claims to serialize token decisions while token issuance uses a detached snapshot

**INCORRECT.** `crates/wyrd/wyrd-server/src/components/github/service.rs:320-345` and `:642-669`. REQ-001 requires disconnect to stop connection use before releasing association, and the outbound credential authority requires minting only while the association and selection are active. `fence_and_release` says a token decision cannot interleave and takes `FOR UPDATE`. `installation_token` uses the unlocked read and commits before it requests the provider token. The SQL slot lock therefore cannot synchronize that request. A token call can reach the mock or GitHub, disconnect can return success and free the claim, and the pending provider response can then return a usable token because tenant-side disconnect does not uninstall the App at GitHub. The same gap permits a token for a locally removed selection if GitHub still grants access. Current server integration exercises operations sequentially and cannot distinguish the gap.

Make the credential release decision authoritative at the existing SQL slot/revision owner. The minimum proof is a deterministic provider pause before the token response, a committed disconnect while the call is pending, and refusal of the stale credential. A focused repair can use the current binding/revision with a final short read after provider IO and before handing out the token, preserving the current bounded IO and avoiding a network wait while holding a DB lock. Keep new calls after release refused before provider IO. State the exact serialization/cancellation boundary in the service rustdoc. If task authority is interpreted to require preventing the provider from even minting during an already-started call, validate the stronger ordering before selecting the correction.

### MNT-005 — SQL outcome rustdoc claims a durability guarantee the method cannot make

**VIOLATION.** `crates/wyrd/wyrd-sql/src/queries/github_installations.rs:169-171`. Root AGENTS and `agent_docs/rust.md` require changed-item rustdoc to explain durability and relevant side effects. `Associated` says it carries the committed slot. `associate_github_installation` runs in the caller's `TenantConn` transaction and does not commit. `GithubConnections::callback` commits separately at `service.rs:531`, and callers can still roll back the SQL outcome. A new caller following this wording could produce a positive receipt before the connection is durable, contradicting INV-003. Correct the variant rustdoc to describe the pending slot and the caller's commit obligation, alongside the behavioral repairs. Existing cross-request read assertions already exercise the commit boundary.

## Calibration and verification limits

GitHub state writes and redecodes the OIDC table's required issuer, client and redirect fields even though its callbacks currently only consume the slot, verifier and hint. These fields resemble the OIDC login binding, but the GitHub transaction does not enforce them. I did not propose a new configuration-generation protocol or a schema change from that observation. The deployed host-identity mismatch in MNT-003 is independently reachable using the installation row already retained by this task.
