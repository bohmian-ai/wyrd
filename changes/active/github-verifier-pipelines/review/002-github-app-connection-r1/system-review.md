## Findings

### SYS-01 — A mint in flight hands out a credential after disconnect

**INCORRECT.** REQ-001, AC-001 and the outbound credential rule at `architecture/wyrd-security-posture.md:735–741` require an active association when authority is issued. In `components/github/service.rs:640–668`, the issuer reads the slot and commits a plain read before it asks GitHub for a token. Meanwhile `disconnect` at lines 307–319,333–342 commits the release and makes the installation claimable by another tenant. GitHub sees the deployment App and still grants access because a Wyrd disconnect does not uninstall the App. When the earlier HTTP call completes, the server returns a usable token from the stale association. The provider read/write credential can then authorize new source IO under the former tenant. The same issue applies to a response delayed across a Wyrd repository-selection or suspension fence.

Use the existing durable slot identity and access state to fence the credential handoff in the token owner. After GitHub replies, verify the same current authorization under tenant SQL before releasing the token to work. Discard any token whose authority disappeared or whose slot was released/replaced. Keep the provider wait outside SQL so a provider outage cannot occupy the shared database pool. This protects the local handoff even if an already-sent provider request finishes. Reuse the bound-server mock and pause a token response, commit disconnect or replacement, then finish the response and assert the former tenant receives a typed refusal. Also assert a still-authorized unrelated repository retains access.

### SYS-02 — A delayed suspension delivery can indefinitely disable active access

**INCORRECT.** AC-001, task O21 and the connection contract require synchronization with the provider's installation state while suspension retains ownership. At `components/github/service.rs:587–595` the handler assigns the state directly from the arriving action. `queries/github_installations.rs:71–78` makes exact repetitions idempotent only while the state still has the same value. If GitHub suspends and then unsuspends, and Wyrd receives the unsuspend first, the late suspend commits a false suspension. The same sequence occurs when an operator redelivers a failed suspend after unsuspend succeeded. GET reports suspended and `installation_token` at lines 658–665 refuses before checking GitHub, even though the provider permits access. The wrong state survives process replacement, so normal token retries cannot recover. GitHub documents that delivery order can differ from event order. [GitHub webhook troubleshooting](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks#webhooks-deliveries-are-out-of-order)

In the existing suspension writer, apply authoritative provider suspension state with protection against a stale concurrent observation. The existing installation read can establish the state and the existing slot revision can condition its application, with a fresh read if the slot changed. Keep transient provider failure scoped to the webhook and document redelivery. No new delivery store or worker is required for this correction. Use the existing mock's independently controllable provider state and send reversed suspend/unsuspend deliveries or redeliver an old suspend after the provider resumes. Assert the final state and token decision match the provider, and that a genuinely suspended installation still reserves ownership.

### SYS-03 — A persisted association can grant authority on the wrong configured host

**INCORRECT.** REQ-001 and INV-001 require the verified host and repository identity to constrain authority. The installation table explicitly scopes installation uniqueness by host. `components/github/service.rs:177–198` labels any persisted installation with the current configured host/App, and lines 640–668 pass the persisted numerical installation and repository IDs to the current App without matching the row's host. The provider URL comes from the current configuration at `app.rs:374–386,410–411`. A process replacement that changes the configured GitHub origin from host A to host B retains the A row. Independent GitHub hosts can assign overlapping IDs. If B's configured App can mint for the matching B IDs, the tenant now obtains B authority without associating that installation or selecting the B repository. The association and webhook paths already compare host in SQL, while the read and token paths can use a different identity.

Match the persisted host against the active App before presenting the slot as a current connection or using it for credentials. Preserve the authorized release path for the existing claim so the tenant can connect again through the normal flow. Seed a verified slot under A, use a replacement App configuration for B with overlapping mock IDs, and assert the view grants no B access and the provider receives no token request. This is a fail-closed authority check and requires no configuration migration feature.

### SYS-04 — Production cannot connect a normally configured private GitHub Enterprise Server

**INCORRECT.** TASK-002 requires conventional configured GitHub Enterprise Server support. The approved design at `approved-runtime-and-github.md:89–102` preserves it, and the operator guide at lines 15–17,46–58 directs such installations to configure their own HTTPS host. `boot/mod.rs:1320–1329` hands the deployment's identity-provider client policy to this operator-configured App. `config.rs:137–150` sets `BlockInternal` for production. `screening.rs:174–190,214–218,241–244,322–328` therefore rejects every DNS answer or literal in private ranges. A correctly registered, reachable, TLS-valid Enterprise Server on a private network passes typed config and boot, then every OAuth exchange returns provider unavailable and no connection can complete. Existing config proof parses a GHES origin, and the provider journeys use the development profile, so neither exercises the deployed policy.

The caller never supplies a provider origin. Use the existing screened transport with internal address support for operator-configured GitHub origins, preserving the production HTTPS check and the shared deny rules for metadata/link-local addresses, redirects and proxies. This is specific to the GitHub App client construction. Tenant-supplied OIDC provider fetches retain their current policy. Verify production HTTPS GHES private address screening and continued blocking of metadata addresses using the existing screening and config test owners.
