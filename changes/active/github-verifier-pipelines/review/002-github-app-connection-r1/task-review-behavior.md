## Proposed findings

### B-001 — INCORRECT — A token can cross a committed access fence

**Obligation:** REQ-001, INV-006, AC-001, O19/O22–O24.

**Evidence and consequence:** `GithubConnections::installation_token` (S:635–668) loads the tenant slot through I:184–189, whose SELECT takes no row lock, commits, and awaits an outbound App token request. Neither success nor failure revalidates the slot. Concurrent disconnect locks and clears the slot (S:303–342, I:326–334), making the same installation reusable. If the provider request is paused after the read, a disconnect can return success and a second tenant can claim the installation before the provider gives the old tenant a fresh valid credential. Wyrd disconnect does not change GitHub installation access, so GitHub can still issue that credential. Refreshing a repository selection can likewise race the old read while the provider still permits the repo. The claimed no-interleaving invariant at S:325–329 is false. Siblings that mutate slot authority are association refresh, suspension, repository removal and installation deletion. No current production work invokes the handoff yet, but it is a required Task 002 facility with explicit fence proof and later consumers depend on it. SRV tests only sequential calls.

**Smallest safe correction and proof:** Reuse the persisted slot authority and check it again at credential handoff after the provider response. Reject the credential if the association changed, is suspended, or no longer selects the requested repository, including a release/reconnect of the same installation. Use the existing revision or equivalent existing row state so an old credential cannot cross the ABA boundary. Avoid holding a database transaction during provider IO. The source operation must take its authority from this handoff at the moment of use. Pause the existing mock token response, commit disconnect, then release the response and assert the old caller receives a typed refusal. Existing sequential tests continue to cover post-release requests and unaffected repositories.

### B-002 — INCORRECT — Persisted installation identity loses its host at consumption

**Obligation:** REQ-001, INV-001, O4/O18/O19.

**Evidence and consequence:** The database treats `(host, installation_id)` as identity (M:43–46). Association writes the verified current host (S:497–505), and signed webhook routing already includes it (S:570–585). In contrast, `view` constructs the current host/App unconditionally and borrows the installation ID and selection from any associated slot (S:177–198). `installation_token` similarly ignores `row.host` (S:640–668), and A:374 sends the numeric installation ID to the current API. If an operator changes the deployment's configured GitHub host, an old verified slot survives. Independent GitHub hosts can assign the same numeric installation and repository IDs. The new App can therefore mint a token for an unrelated repository for the old tenant before any verified association to the new host. The public view already misrepresents the new host's verification even without an ID collision. The provider verifies the new App's access and has no Wyrd association context.

**Smallest safe correction and proof:** Require the persisted host to match the configured host before exposing verified active access or passing IDs into the provider token request. Keep existing tenant-authorized disconnect available to release the old slot. This consumes the identity already stored and requires no new management workflow or persisted fields. Seed a slot for a different host with the configured mock's numeric IDs, then assert inspection does not claim that verified active access, issuance is refused before the mock token endpoint, and disconnect allows a verified reconnect.

### B-003 — INCORRECT — A public RSA key passes private-signing-key validation

**Obligation:** REQ-001, O3/O16.

**Evidence and consequence:** C:2450–2451 and A:148–152 use `jsonwebtoken 9.3.1`'s `EncodingKey::from_rsa_pem` as validation. The installed dependency's `src/encoding.rs:42–45` returns an encoding key from the decoder's DER. Its `src/pem/decoder.rs:64–112,172–179` accepts RSA public PEM, including PKCS#1 `RSA PUBLIC KEY` and PKCS#8 `PUBLIC KEY`. Its `src/crypto/rsa.rs:39–44` first tries to construct an RSA private key pair at signing. An operator who mounts a public PEM in the private-key slot can start the server and receive connect receipts, but callbacks fail at the first App-authenticated provider request with a generic provider-unavailable error. C:6938 tests plain malformed text, which fails an earlier parsing branch.

**Smallest safe correction and proof:** Validate that the PEM can sign with the existing RS256 owner before accepting present configuration. A real local signing validation also catches malformed private DER a label check would admit and requires no new dependency. Add the existing test public PEM to typed config validation and assert a field-specific error. Keep key bytes out of diagnostics and preserve the existing valid-key case.

### B-004 — INCORRECT — OAuth web exchange requests a REST media type and assumes JSON

**Obligation:** REQ-001, AC-001, O7/O8/O10.

**Evidence and consequence:** `exchange_code` constructs a request to the web OAuth endpoint with the common REST request builder (A:221–239, 438–448). It sends `Accept: application/vnd.github+json` and decodes only JSON. GitHub's App OAuth example uses `Accept: application/json` for this endpoint. Its OAuth documentation specifies form encoding as the default for this endpoint and lists `application/json` for JSON negotiation. A read-only protocol probe using synthetic invalid values and identical headers otherwise received plain text with the candidate's media type and JSON with `application/json`; both statuses were 404. This verifies the endpoint distinguishes these media types, while the successful-response consequence follows from the documented contract. The local mock at `wyrd-testing/src/github.rs:531–555` ignores Accept and always sends JSON, hiding the negotiation gap. In both supported browser paths the exchange consumes the one-use transaction before attempting JSON decoding, so a valid authorization can be lost to response format. [GitHub App OAuth example](https://docs.github.com/en/apps/creating-github-apps/writing-code-for-a-github-app/building-a-login-with-github-button-with-a-github-app) · [GitHub OAuth response negotiation](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)

**Smallest safe correction and proof:** Have the OAuth exchange send the documented JSON Accept value, retaining the existing screened transport and REST headers for the REST endpoints. Make the existing mock honor or assert the exchange's Accept value and run one journey through it. A successful live OAuth exchange was outside the review proof.
