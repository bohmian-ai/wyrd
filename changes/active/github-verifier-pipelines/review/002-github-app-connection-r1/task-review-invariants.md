## Proposed findings

### INV-1 — INCORRECT, disconnect can release an installation while an old tenant still acquires authority

**Obligation and location.** REQ-001, AC-001, INV-006, O19 and O22–O24. `service.rs:322-342,635-668` and `slots.rs:99-109`.

**Evidence and consequence.** Begin an installation-token acquisition for tenant A on a selected repository. The ordinary SQL read and commit at :642-645 leave no transaction or row lock during provider I/O. Hold the provider token response. Disconnect A through HTTP or MCP. `fence_and_release` can commit and tenant B can claim the same still-live GitHub installation. Releasing the held provider response still returns a new token to A's caller because :668 has no subsequent local check. This is an explicitly required background authority boundary despite the first queue caller belonging to a later task. GitHub can grant the request because the Wyrd disconnect leaves the provider installation intact. The same stale decision can survive a tenant reselection that removes a repository GitHub still grants. The current sequential test proves nothing about this interleaving.

**Correction and proof.** Fence credential handoff at `GithubConnections::installation_token` against the existing tenant slot and its current identity/revision. Reuse the persisted authority and avoid placing provider latency inside disconnect's critical section. If the slot changed during provider I/O, refuse the stale credential and make any renewed attempt go through the current access decision. Preserve unaffected repositories and never publish provider credentials from an obsolete binding. In the server integration test, pause a scoped token request at the provider, commit disconnect and observe the release, resume the provider response and assert the old request yields no token. The association callback, webhook mutations and release are the other writers of the same slot. No separate cancellation state or queue is required.

### INV-2 — INCORRECT, stored GitHub host does not constrain connection view or token issuance

**Obligation and location.** REQ-001, INV-001, O4, O18, O19. `service.rs:177-198,245-260,369-394,439-451,497-505,641-668`. The host is persisted and scoped into uniqueness and webhook lookup by migration :24-44 and :58-73.

**Evidence and consequence.** Host A and host B can be distinct supported GitHub instances with independent numeric installation and repository IDs. Connect a tenant against host A, then point the operator's App configuration at host B while retaining the database. The read labels host A's verified IDs and selected repository names as host B's. The token owner ignores `slot.host`, so a repository matching the stale numeric ID gets a host-B provider token when B's configured App owns a matching installation. No host-B user has authorized this tenant. Host-B webhooks cannot fence the stale slot, because the lookup correctly includes the stored host. Temporary state also records `issuer`, `client_id` and `redirect_uri` but both setup and exchange ignore those persisted values and use the current App. A setup begun against A can move into B's OAuth flow on a different replica or after restart.

**Correction and proof.** Enforce verified provider identity at the shared service boundary. Require the stored host for active slot projection and credential use, while preserving authorized explicit release of the old slot. Reject a setup or callback whose stored provider configuration no longer matches the configured protocol endpoint/client. Existing slot and login-state fields supply the evidence. Exercise a retained database with two distinct mock hosts sharing numeric IDs. Assert that a host-A association and outstanding transaction authorize no host-B access or credential, and that the tenant can release and explicitly verify the new association. Provider instance IDs are scoped by host in the approved design, so matching numeric IDs cannot substitute for that check.

### INV-3 — INCORRECT, reordered suspension events can strand an active installation

**Obligation and location.** REQ-001, AC-001, O21–O22 and the App design's requirement to synchronize access. `service.rs:587-595,642-668`; `slots.rs:58-78`.

**Evidence and consequence.** Start with an active installation, suspend it at GitHub, then unsuspend it before both deliveries arrive. GitHub documents that deliveries can arrive out of event order. The newer `unsuspend` arrives first, sees an already-active slot, and SQL applies no change. The older `suspend` arrives afterwards and sets `suspended_at`. The installation is now active at GitHub but remains suspended in Wyrd, and token acquisition refuses before asking the provider. Even a successful verified refresh cannot restore it because `ASSOCIATE_SQL` preserves the previous `suspended_at`. The customer must arrange a new webhook or disconnect and re-associate to recover access to every repository. The Rust SDK test drives only suspend followed by unsuspend and does not make the provider's actual state authoritative in either transition.

**Correction and proof.** Make suspension synchronization reflect the current installation authority when consuming transition notifications. Reuse the App-authenticated installation lookup, the slot revision and the existing suspension writer. Guard against an earlier read overwriting a newer slot change and allow an authoritative active refresh to clear stale local suspension. No delivery journal or new public flow is needed. Use the existing mock's provider state and signed delivery helpers to apply a newer unsuspension before an older suspension, then assert both the public active state and continued scoped token issuance.

## Verdict

**FAIL.** Lifecycle proof covers sequential and database claim paths. The proposed blockers concern credential handoff during revocation, use of host-scoped identity and supported provider event ordering.
