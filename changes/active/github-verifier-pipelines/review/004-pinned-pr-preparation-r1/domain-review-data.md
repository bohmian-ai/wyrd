## Concurrency and failure schedules

1. **First publication:** two sessions insert the same full-scope primary key. Unique-index arbitration permits one insertion; the loser returns zero affected rows. Subsequent expected-tree UPDATE reevaluates its predicate after conflicting row updates, so a stale expected tree cannot overwrite a winner.
2. **Touch versus claim:** both write the same record row. If touch wins, PostgreSQL's conflicting-row recheck sees a fresh touched_at and claim skips the record. If claim wins, touch's conflict UPDATE condition sees claimed=true and returns zero rows, mapped to Collecting. Claim retries retain the original touched_at and return the same claimed record under the same grace.
3. **Publication versus collection:** pointer publication does not lock snapshot-record rows; claim uses statement-visible pointer references. This must be evaluated with the library's actual supported protocol: `snapshot.rs:898` touches the record before object IO and pointer publication; `Snapshots::collect` at `snapshot.rs:413-419` explicitly requires grace longer than the longest active build, and repository removal requires no active builds. A build touched first is therefore ineligible for collection until its publication completes; an older record claimed first refuses the build's touch. An interleaving that touches, waits beyond grace, then publishes, or a zero-grace collection concurrent with an active build, violates those existing preconditions and is not a retained material finding. The code does not supply stronger arbitrary-delay/zero-grace concurrent-build guarantees, and this report does not claim them.
4. **Crash during collection:** after claim but before object delete, the claim is returned again. After object delete but before metadata delete, idempotent object deletion permits completion. No rollback of object IO is assumed.
5. **Context expiry versus repeated upsert:** conflict arbitration retains original expiry even after expiration; an already selected expired record cannot be renewed by that upsert. The actual facade mints fresh random context IDs for new publications, so cleanup of an old ID does not delete a newly published context. Concurrent manual reuse of an old context ID after deletion is not the facade's supported publication protocol.
6. **Database failure:** a failed statement/commit becomes Backend; a TenantConn dropped before commit rolls back. The adapter never converts metadata failures to absence or commits a pointer around failed object publication.
