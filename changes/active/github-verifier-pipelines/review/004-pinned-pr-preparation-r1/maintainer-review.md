## Existing complete-owner alternatives and correction burden

- **Source preparation:** the existing `ReviewPipeline`/`Update`/`PrContext` chain already owns snapshot acquisition, overlays, ranking, packing and context publication. The candidate extends this chain; it does not implement those stages in Wyrd. Removing the new comparison stage would lose required pinned full/active comparisons and exact before/after evidence. Reusing only the old `PrContext::run` would reacquire live PR files and lose the supplied comparison baseline.
- **Provider acquisition:** `GitHubClient` already owns authenticated routed transport, identity checks and file validation. `compare_files` lives on that owner and reuses its transport and file validator. The old `compare` serves update/remove/add behavior and lacks the information required here. Unifying the two wire/result projections is a possible refactor, but no concrete task failure or maintenance burden requires it; forcing it would expand the changed update path.
- **Object custody:** `StorageHandle` already owns configured backend IO and `ValidatedPath` owns backend-key projection. The adapter reuses both; conditional create is the missing primitive. Replacing it with `put_object` would weaken immutable-object semantics. A separate backend implementation would duplicate configuration, instrumentation and error behavior.
- **Metadata custody:** existing `ServerPostgres`, `TenantConn` and `OperatorPool` supply connections/capabilities, while SQL query modules own statements. Existing installation rows, Card metadata and Bifrost evidence do not implement the library's snapshot compatibility pointers, object collection claims, or expiring context records. Extending those unrelated records would conflate lifecycles. The new three-table metadata owner is the explicitly directed exception; no generic cache-coordination subsystem is introduced.
- **Tests:** the library's existing `pipeline_journey` and Wyrd's existing integration runners are extended. The small `Custody` fixture owns real dependencies and shared setup; there is no replacement runner, reusable test framework or speculative configuration surface.
