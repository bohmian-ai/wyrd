## Lifecycle preconditions and proof limits

Snapshot collection explicitly requires non-overlapping calls per identity and a grace longer than the longest build (`snapshot.rs:410-418`; `persistence.rs:210-216`). Repository removal requires no build running (`snapshot.rs:441-446`). These are existing caller obligations, not new locks promised by this adapter task. The pipeline touches the candidate record before object IO. Thus, under the documented grace, an in-flight publication's record cannot age into an eligible collection claim. The SQL pointer publication itself does not inspect a record's claimed flag; a hypothetical late publication after claim is not established here as a supported failing path without violating the stated lifecycle precondition. This report does not waive those preconditions for future callers.

Inspection included the library's unchanged persistence, snapshot, context, update and provider dependencies because the new facade/adapters rely on their recovery ordering. Task evidence records successful relevant lanes, but this reviewer did not rerun tests, kill processes, mutate source, generate load, or induce service outages. Static ordering and the cited assertions support this task's bounded adapter acceptance; they do not establish Task 005 execution retention/recovery, production cleanup scheduling, or every cloud provider's crash durability. Those capabilities are not claimed shipped here.
