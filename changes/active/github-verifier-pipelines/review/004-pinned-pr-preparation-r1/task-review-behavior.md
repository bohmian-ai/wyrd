## Proposed finding B-004-1 — pointer publication is not atomic against collection

Classification: **INCORRECT**. Obligation: task storage bullet 3 and W4 explicitly require “atomic collection claims against upserts/pointer publication”; library `SnapshotStore::unreferenced` likewise requires selection/claim atomic against “record upserts and pointer swaps.”

Location: `crates/wyrd/wyrd-sql/src/queries/code_review_cache.rs:28–39,50–59`, called by A `publish_snapshot_pointer` and `unreferenced`.

Source-proven protocol scenario: create an unreferenced snapshot record/object; let collection claim it and pause before deleting the object; publish a pointer to that claimed key using either first publication or the current expected tree; resume collection. Publication succeeds because both pointer statements touch only the pointer table and inspect neither the record's claimed state nor a common serialization authority. Collection deletes the now-published object's bytes and record. Concurrent snapshots of pointer INSERT/SWAP and the record UPDATE similarly have no common conflicting row, so a negative pointer predicate in the collector is not mutual exclusion. No migration trigger or FK supplies the missing coordination.

Producer/consumer trace: library `ColdBuild::publish` (`snapshot.rs:898–919`) touches the record, creates/adopts object bytes, then calls pointer publication; `Snapshots::collect` (:423–437) claims, deletes bytes, then deletes the record. Future pipeline `ensure_snapshot` sees the surviving pointer and does not cold-build; the context path encounters missing snapshot and falls back to scoped context. Therefore cache acceleration/coverage can be lost despite successful pointer publication; the result is not loss of accepted Bifrost execution evidence.

Materiality qualification: ordinary `Snapshots::collect` documents a caller obligation to choose grace longer than its longest build, and remove_repository requires no running build. Those preconditions reduce the ordinary producer race: every normal library publisher touches immediately before object IO. Do **not** claim this necessarily happens under correctly bounded normal collection. This finding rests on the task's explicit stronger metadata atomicity requirement and the direct metadata boundary it explicitly asks to test, rather than inventing an unlimited-build availability guarantee. If approved authority is reconciled to require only the documented grace precondition, reject this finding instead of adding speculative locking. The current task and library protocol explicitly name pointer swaps, so simply calling all existing tests green cannot establish that row.

Existing sibling writers/consumers inspected: first pointer INSERT, tree SWAP, record touch, claim, record/pointer deletion, external ColdBuild/Update publisher and Snapshots collector. Existing publication-competition tests publish pointers without records, and the test called collection_claims_race_touches_and_pointers_and_retries only publishes before collecting. The genuinely concurrent SQL test races touch against claim, not pointer publication.

Minimum correction if retained under the stated contract: enforce the publication/claim invariant at the existing SQL metadata owner, making claim and target-key pointer publication mutually ordered without a transaction across object/GitHub IO. Publication cannot positively acknowledge a record already claimed or deleted. Preserve tree CAS, first-publication competition, tenant/repository scoping, grace and retry. Reuse the existing record/claimed authority; no new service, table, lease framework or Wyrd-side pipeline is justified. A bare unlocked NOT EXISTS/claimed predicate is insufficient for concurrent transactions. Add focused real-PG assertions for publication after claim and an overlapping publication-versus-claim schedule, checking the final pointer/object custody invariant rather than only statement success. This is a bounded SQL/adapters correction; no broader queue journey is required.
