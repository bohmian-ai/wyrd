## Adversarial checks and limits

I traced the apparent gap between a snapshot touch and pointer publication. The SQL pointer write does not itself lock or consult the claimed-record row. However, the existing library explicitly requires `Snapshots::collect` callers to choose grace longer than the longest build and not overlap collection for one identity (`L/src/snapshot.rs:411-416`). Every production publication first refreshes its record (:898), and row-update serialization prevents the claim and that refresh from both succeeding for an aged row. Under those supported lifecycle preconditions, publication cannot become collection-eligible before it completes. A scenario that pauses publication past grace, or publishes directly without the prerequisite touch/create, does not prove a required supported failure. I therefore do not propose new locking or a library protocol redesign. The SQL test named `collection_claims_race_touches_and_pointers_and_retries` establishes static pointer protection and retry, whereas the actual simultaneous SQL test establishes claim-versus-touch; its name alone was not treated as pointer-swap-race proof.

Snapshot corruption/backend failures remain explicit; only a genuine missing cache object takes the existing scoped-context fallback, whose coverage reports the reduced scope (`L/src/pull_request.rs:486-501,335-354`). The accepted execution-evidence contract belongs to subsequent tasks and is not established by cache availability.

Context publication uses a fresh digest-plus-random id, so cleanup of an expired context cannot delete a later ordinary publication of identical bytes (`L/src/context.rs:312-332,430-439`). Repeated metadata upsert deliberately preserves the prior record as well as stamps. Collection deletes object before row; failure leaves discoverable metadata. No changed owner introduces a new clock, index or retry deadline.

No runtime tests, mutation tests, cloud credentials or emulator calls were run by this reviewer.
