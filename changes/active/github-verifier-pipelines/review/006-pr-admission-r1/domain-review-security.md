## Proposed material findings

### SEC-006-1 — INCORRECT: an in-flight admission can recreate work after access loss

**Obligation:** REQ-001/004, INV-001/006, task A10/A12 require disconnect, suspension and repository removal to stop affected unfinished work and fence subsequent work. Security posture requires tenant binding and fencing uncertainty to fail closed.

**Location:** `crates/wyrd/wyrd-server/src/components/github/pull_requests.rs:234-295`, particularly reservation at `:280-283`; access-loss writer `github/service.rs:368-408`; SQL `queries/verifier_executions/pull_requests.rs:125-149,564-643`.

**Reachable trace:** A signed `opened` delivery for a previously unseen PR gets a valid narrowed installation token and completes the token's connection revision check at `service.rs:913-923`. It then awaits the PR HTTP response at `pull_requests.rs:224-226`. Disconnect commits meanwhile: it locks/releases the connection slot and cancels existing executions, but this PR has no row yet. Release does not remove the registered selected Repository/bindings. The old PR response returns; admission opens a new TenantConn, locks only the per-PR advisory lock, sees no history, resolves the still-selected policy and active declaring principal, then inserts reserved rows and hands them through Scribe into runnable work. Neither `targets`, `reserve_pull_request`, `fence_principals` nor activation checks the installation slot/access revision. Repository removal and suspension use the same cancellation boundary and have the same race. A previously minted token is therefore effectively sufficient to admit work after connection use was revoked.

**Consequence/materiality:** An authorized disconnect/removal/suspension can succeed while the stale webhook subsequently creates and executes new affected verification work. This is ordinary concurrency between provider IO and a supported access-revocation action, not hypothetical malicious input. Existing cancellation tests create rows before disconnect; the close race test has a deactivation row, so its timestamp fence does not cover a first admission after access loss.

**Smallest correction boundary:** Reuse the existing connection slot lock/revision/access owners at the final admission transaction. Validate that the observed association still authorizes this repository while holding the slot lock through the reservation/replay decision and commit, ordered against the existing access-loss writers. Keep provider IO outside SQL transactions and retain principal fencing and the existing Scribe handoff. The check belongs at the admission owner because it creates work; adding runner/result guards alone leaves unauthorized durable admission and an incorrect successful receipt. No new table, lifecycle owner or provider transaction is necessary.

**Focused proof:** Use existing `hold_next_pull_request_read()`/`arrived()` control (already used at `pg_github_pull_requests.rs:1237-1249`) on a first open PR. While response is held, commit disconnect, release response, then assert no runnable PR execution was added. Cover removal/suspension through their shared access-loss boundary or equivalent focused case. Also exercise access loss ordered after reservation, asserting cancellation wins and no stale activation revives it.

### SEC-006-2 — MISSING: PR execution inspection omits repository-read authorization

**Obligation:** Security posture `architecture/wyrd-security-posture.md:254-258` explicitly requires current `verifier:read` on the exact Verifier **plus repository read where applicable**. `architecture/wyrd-design.md:1957-1960` requires exact Verifier/repository feature authorization from recorded identities. Task A13 introduces PR source inspection; INV-001 still constrains it.

**Location:** New PR status projection in `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs` (`StatusRow.pull_request` and `execution_status` projection), consumed by `components/verification/service.rs:259-303`; shared receiving gate `components/verification/service/inspection.rs:329-376`.

**Reachable trace:** A tenant caller has a grant to read a bound Verifier but no `cards:read`, the repository's existing read permission (`Permission::card_read()`, `service.rs:212-223` for binding inspection). Given a PR execution ID, `retained()` passes require_verifier, reads queue/retained state, checks only exact verifier_read and returns it. `get_execution()` returns the queue's PR repository identity, PR number, base/head branch names and commits without a repository-read decision. The same Verifier can serve repository-owned bindings; possession of its read grant does not supply the missing independent permission. HTTP/SDK/MCP/CLI consume this shared gate.

**Consequence/materiality:** PR source metadata becomes readable by callers lacking the repository feature's required read permission. This is a concrete authorization omission on a newly shipped public projection, independently of whether an execution ID is difficult to guess; IDs are not credentials.

**Smallest correction boundary:** Extend the existing shared execution-inspection authorization owner to apply and audit the repository's existing read gate for PR executions, using recorded immutable owner/origin identity and no source Card retrieval. Preserve current exact Verifier checks, ordinary non-PR execution reads and normal tenant isolation. No new permission model or SDK-specific checks are needed. Cover sibling retained inspection paths through the shared owner rather than replicating guards in each transport.

**Focused proof:** Read a PR execution with only the exact verifier_read grant and no cards:read: assert permission denied. Add cards:read and assert its existing typed PR inspection succeeds. Keep an ordinary non-PR execution readable under its existing Verifier-only contract.
