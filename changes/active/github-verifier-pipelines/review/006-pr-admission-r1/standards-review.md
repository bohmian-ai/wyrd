**Evidence and locations:**

- `crates/wyrd/wyrd-server/src/components/github/app.rs:670,694`: new `next_page_follows_only_the_next_link` and `page_links_stay_under_the_api_base` contain `expect` and assertions, but no Panics section.
- `crates/wyrd/wyrd-server/src/components/github/pull_requests.rs:552`: new test `event` helper uses `from_value(...).expect(...)` without documenting the invariant/panic.
- `crates/wyrd/wyrd-server/tests/integration/pg_github_pull_requests.rs:171`: new `Deployment::base` calls `base_url().expect("bound")`, without Panics documentation.
- `crates/wyrd/wyrd-sql/tests/integration/pg_verifier_executions.rs:4457,4486`: new `pins` helper constructs checked RepositoryIds with `expect`; `pr_targets` calls existing `background`, whose own Panics section explicitly covers failed SYSTEM provisioning. Neither new caller documents that panic contract.
- `sdks/wyrd-sdk-python/src/testing.rs:1052` and `sdks/wyrd-sdk-ts/native-testing/src/github.rs:100`: new wrapper methods call mock `pull_request_event`, whose documented precondition is that the scripted PR exists and whose `expect` panics otherwise. Wrappers document Errors but omit Panics.
- `crates/wyrd/wyrd-mcp/tests/bifrost/mcp/github.rs:215`: materially changed `an_agent_reads_the_selected_repository_policy` adds PR assertions, and its docs still only describe returned Errors, omitting assertion panics.

**Consequence/materiality:** the candidate does not satisfy the repository's expressly nonwaivable changed-item rustdoc merge gate. For wrappers, the omitted precondition is also observable when a test calls the new method before scripting its PR. No new runtime defect or broad documentation rewrite is alleged.

**Smallest correction:** document the actual panic conditions on these touched items, retaining existing error behavior. Audit the same changed-item set for equivalent omissions in the same bounded correction. If the N-API comments change, regenerate its declaration using the owning task. Do not add suppressions, validators or runtime machinery.

**Closure proof:** source inspection of the named docs and calls, existing format/stub/generated-parity checks for any changed declarations; no new runtime test is needed for documentation alone.

### REPO-006-2 — VIOLATION: new SQL reads decode multiple columns by ordinal

**Rule:** `crates/wyrd/wyrd-sql/AGENTS.md`, Queries: “Map columns by name, never by position.” `agent_docs/rust.md` also requires named mapping when schemas can diverge.

**Location/evidence:** `crates/wyrd/wyrd-sql/src/queries/verifier_executions/pull_requests.rs:469` decodes `BINDINGS_SQL` (`SELECT binding_id, verifier_card_uid`) into `Vec<(Uuid, Uuid)>`; `:501` decodes `DEACTIVATE_SQL` into `Vec<(Uuid, Option<bool>)>`. SQLx tuple FromRow selects by ordinal. The first pair has identical types, so a projection reorder silently exchanges binding and verifier identities. The new module already demonstrates the compliant owner pattern with `GenerationRow`.

**Consequence/materiality:** explicit prohibited SQL mapping enters the new production admission path; it defeats the mandated protection against independently changed projection/decoder order. The current projection order matches and no present runtime misdecode is claimed. This finding rests on the explicit repository constraint, not a speculative input.

**Smallest correction:** decode the named columns at these two query boundaries, using existing SQLx named access or named FromRow values. Keep the public domain results and callers unchanged; no query/helper framework or extra capability is needed. The changed server test helper `Deployment::frozen` (`pg_github_pull_requests.rs:223`) also projects same-typed name/version values positionally; alias/name those columns in the same bounded correction if applying the Rust guide to its query mapping.

**Closure proof:** inspect named decoding; run the existing focused SQL reservation/supersession and end/access-loss tests after the local change. No new integration harness is required.
