## Findings

### SYS-006-1 — INCORRECT: GitHub rate-limited PR reads are acknowledged as successful no-work deliveries

Location: `crates/wyrd/wyrd-server/src/components/github/app.rs:454–459`, consumed by `components/github/pull_requests.rs:224–231` and webhook `service.rs:657–670`.

Violated obligation: A5 / task consequential ACK requires failed GitHub reads to remain non-2xx and retryable; REQ-004 requires eligible source changes and close/draft events to reach admission/cancellation. Positive receipt requires committed admission or durable no-work settlement.

`GithubApp::pull_request` maps both 403 and 404 to `Ok(None)` without examining the cause. `pull_request` returns immediately on None, committing neither admission nor obsolete/refusal/cancellation settlement, and the webhook returns 202. GitHub documents 403 for primary and secondary rate limiting, not just inaccessible content: [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api?apiVersion=2022-11-28). Thus an ordinary eligible PR event arriving while its installation is rate-limited is recorded as answered successfully; `recover_deliveries` excludes it forever because any 2xx attempt is considered done. A close/draft delivery may similarly leave already-running work unfenced, and recovery of an interrupted fanout may leave infinity reservations stranded. No unusual payload or speculative new failure domain is needed.

Sibling boundaries: token acquisition already has a separate inaccessible-repository classification; it is not evidence that a PR-read 403 is authoritative source state. The canonical receipt decision remains `GithubConnections::pull_request`; Scribe, SubmissionSink and queue cannot repair an event discarded before they are called. The existing failed-read test supplies only a server error, so it misses this branch.

Smallest correction: let ambiguous/temporary PR-read forbidden responses remain `GithubUnavailable` rather than interpreting them as absence. Routing 403 through the existing failure decoder is sufficient for the demonstrated case; no new retry subsystem, durable state or generic rate-limit policy is required. Preserve the existing chosen 404/no-work behavior separately. If retaining a special forbidden/no-work classification, establish that classification positively and ensure rate-limit responses take the failure path.

Focused closure proof: a real server route test whose PR read returns rate-limited 403 must answer non-2xx and admit nothing; a subsequent retry after the mock recovers must admit the expected generation. Include a previously admitted close/draft event or interrupted reservation if sharing the same fixture is inexpensive; source tracing establishes the same root cause, so it does not justify separate machinery.

### SYS-006-2 — REGRESSION: recovery scanning consumes the shared shutdown deadline after cancellation

Location: `crates/wyrd/wyrd-server/src/components/github/pull_requests.rs:533–542`, in particular awaiting `recover_deliveries()` inside the tick arm.

Violated boundary: operations shutdown stops new work and cancels or hands off bounded work before durable settlement and release (`deployment-and-release.md:272–275`; Scribe failure boundaries `reliability-and-recovery.md:177–180`). Task 006 extends the existing maintenance owner; its auxiliary provider-recovery work must preserve shared Scribe/verification shutdown.

The outer `select!` observes shutdown only while awaiting a tick. After a tick wins, it awaits the complete paginated scan and all sequential redelivery requests inside that branch; cancellation no longer polls. Every request has the existing ten-second HTTP deadline (`wyrd-auth-oidc/src/screening.rs:24,104–118,163–171`), but the scan can contain 5,000 entries and `recover_deliveries` continues to the next delivery after each failed POST. Four failed requests taking their allowed ten seconds exceed the default 35-second process drain (`wyrd-server/src/config.rs:3449–3455`). Cancelling during the first request therefore does not stop later redelivery requests from starting during shutdown.

`BoundServer::run` includes this worker in the shared JoinSet. `app/supervise.rs:298–316` waits the whole set until the global deadline, then aborts remaining tasks. Only afterwards does `app/server.rs:800–828` drain gateway/MCP/hosted work and flush the Scribe outbox; at an elapsed deadline `:878–895` explicitly aborts Bifrost without role drain. Consequently a GitHub outage/backlog during an ordinary rolling replacement can consume the shutdown budget that unrelated accepted audit, capture and verification writes need. The process remains available while running; the defect is fault propagation into shared lifecycle and durability during replacement, not a reason to crash the server on a provider error.

Smallest correction: make the recovery future itself cancellation-selectable inside the existing worker, as the nearby Scribe publication loop already does (`app/server.rs:586–596`). Dropping this maintenance future is safe: GitHub's delivery log remains progress authority; a POST already sent may finish, and subsequent scans/queue idempotency handle that approved race. No elected scanner, extra worker, new queue or shutdown-budget enlargement is needed. Keep errors local and keep Scribe/verification lifecycle ordering unchanged.

Focused closure proof: hold the log read or a redelivery request, cancel the worker and assert it joins without releasing the held provider response or issuing later redeliveries. Exercise server teardown with that held maintenance operation and an ordinary accepted Scribe write to show the provider operation cannot prevent the existing flush/role-drain phases. This is a targeted changed lifecycle test, not a load benchmark or new SLA.
