## Producer-to-consumer trace and existing owners

1. `components/verification/service/evidence.rs::subscribers` obtains selected binding and unfinished pinned-execution candidates through the existing `VerifierExecutionQueue`. It resolves targets and validates the supplied slot before custody. `DeferredEvidence` stages standalone rows on the existing Scribe outbox and addresses acceptance through existing committed-batch fences. This is not a second execution state owner: evidence exists without an execution, which the pre-existing execution-input row cannot represent without fake execution identity.
2. `runner.rs::deferred` (803–865) reads the exact PR host/repository/head and exact Verifier UID from the claim, then asks custody for that subscriber's accepted rows. It mutates accepted facts only through `RunState::accept_evidence`, not from the publisher or a competing branch writer. The accepted row supplies the input declaration to the same engine used before this task.
3. `VerificationEngine::run` computes absent deferred names, and `drive` (927–1040) keeps nodes referencing those names pending. Ready independent nodes still run. Once all tasks drain, remaining actual consumers produce `Waiting`; unrelated absent slots do not themselves stop a completed graph. Checkpoint restoration still uses the existing invocation and control records, including recorded attempts and settled action results.
4. The engine future and hosted execution resources end before `execute` records `RunState::wait` and awaits `persisted`. `RunState` retains the existing short-lock `Writer` with one coalescing flush. The parked branch reuses the existing claim/lease lifetime and only returns `Transition::Park` after the covered revision is acknowledged. Existing queue `release` refunds that claim and sets a bounded due time; it does not create a replacement execution or admission.
5. Publication makes eligible pending/retrying rows due through `wake_evidence_consumers`; running rows remain owned by their claim. A publication arriving after a running claim's read is recovered by its bounded park recheck. Wake failure does not erase accepted evidence. Claim preparation rereads accepted state and input; the engine restores accepted predecessors and budget.

Existing alternatives were checked: execution-input records require execution identity, while this task requires pre-execution custody; the new custody module therefore has a distinct required job. Existing `RunState`, engine checkpoints, queue release, claims, lease renewal, and Scribe staging remain lifecycle owners. No additional state writer, polling execution, broker, payload mirror, or independent orchestration subsystem is needed or added on these paths.
