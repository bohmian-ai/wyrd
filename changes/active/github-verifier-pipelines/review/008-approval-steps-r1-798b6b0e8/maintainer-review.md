## Existing-owner comparison

The closest pre-existing complete acceptance workflow is `verification/evidence.rs::DeferredEvidence`, not the full-state checkpoint writer. It combines a domain-specific deterministic identity, committed-batch lookup, a query of accepted rows, and an outbox write with a durable ACK. Approval needs the same transport guarantee but a different identity (one occurrence rather than source/input/subscriber), row schema, replay comparator (actor/decision/reason), and queue wake target (one execution rather than subscribers).

The candidate extends the common `ScribeWrite::Evidence` variant into `ScribeWrite::Fenced { table, ... }`, keeps batch splitting/dedup/ACK at `ScribeSink`, and generalizes `evidence_batch_id` into `fenced_batch_id`. `DeferredEvidence` and `ApprovalDecisions` both use that shared owner. The remaining similar read/reservation code is domain orchestration, not a replacement transport or cache. Making `DeferredEvidence` itself accept approval rows would mix unrelated domain APIs; a new generic custody framework is not required to make the current change safe or understandable. No DRIFT finding is proposed on similarity alone.

Likewise `RunState::wait` remains the only writer of pending occurrence state, while `ApprovalDecisions` stores accepted decisions separately. The runner supplies immutable decisions to the existing engine and retains its existing park/claim owners. This is coherent dependency-owning shape.
