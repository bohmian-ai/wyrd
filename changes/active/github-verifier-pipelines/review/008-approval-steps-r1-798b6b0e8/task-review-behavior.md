## Existing owners and new machinery

The execution state writer and `Checkpoints`/`ControlRecord` path already own logical progress and speculative disposition. `RunState::wait` extends this owner for occurrence history, but currently uses only its all-blocked transition. The two findings below concern missing use of that existing lifecycle authority, not a recommendation for a second writer or wait service.

Approval durable acceptance extends the existing Scribe first-wins batch fence through `ScribeWrite::Fenced`; deferred evidence still selects the same table, key and ACK semantics. `ApprovalDecisions` is the coherent approval row/read-back owner; the existing alternative is `DeferredEvidence`, whose source/subscriber matching and payload-admission workflow differ. Sharing the fenced write mechanism while retaining approval-specific receipt semantics is justified; no DRIFT finding merely for a sibling approval owner. A standard `assert` check on `output.status == approved` supplies the requested approval requirement without a new helper abstraction. Typed adapters do not own durable decision behavior.

## Proposed findings

### BEH-008-1 — Reached approvals are hidden until every independent action finishes

Classification: **MISSING**. Violated obligation: task Input → pending occurrence (“When the action becomes pending … The pending identity/message enters live state … Independent branches continue; when all block … park”), REQ-010 server-issued pending identity and REQ-016 inspection.

Exact changed locations: `crates/vala/vala-verify/src/blocks/engine.rs:1095`, `:1078`; `crates/wyrd/wyrd-server/src/verification/runner.rs:579`; `crates/wyrd/wyrd-server/src/verification/state.rs:825`.

Reachable scenario: an ordinary approval step and an independent long-running Agent/code step are runnable together. `member` reaches approval immediately and returns its occurrence. `drive` keeps that occurrence only in its local `awaiting` map. It exposes the map as `EngineError::Waiting` only inside `if tasks.is_empty()`. Only that error reaches runner `state.wait`, where the server ID is issued and the occurrence enters the sole state writer. While the independent action runs, accepted Bifrost state contains no occurrence, inspection lists none, and no caller can obtain its approval ID. If the independent work occupies most or all of the shared execution period, the person gets little or no time to approve a step reached at the start. This changes parallel user work into a serial wait and can make an otherwise valid run time out without offering its approval.

Caller/consumer tracing: `member` → step `Done::Awaiting` → `drive.awaiting` → all-blocked `EngineError::Waiting` → `engine_failure`/`EngineOutcome::Parked` → runner `RunState::wait` → background state writer. Inspection and decision acceptance both resolve only recorded canonical state. No sibling caller records the occurrence sooner. Engine `decisions` is also a run-start snapshot, so merely exposing an ID is insufficient if accepted decisions cannot be consumed by the live sole owner while peers remain active.

Materiality: this is the explicitly required reached-approval/independent-work workflow, not a speculative malformed input. Existing tests settle the independent branch before checking pending occurrences and therefore do not exercise the gap.

Smallest safe correction boundary: use the existing execution state/checkpoint lifecycle to record a reached occurrence at its pending transition, with the same stable server-issued identity, and let the sole execution owner consume an accepted decision while independent work remains live. Keep independent work running and use the existing park handoff only once all work is blocked. Do not add a second full-state writer, an approval wait service, a new SQL call at pending creation, or restart settled/live independent computation. Deferring recording cannot satisfy the stated behavior; a consumer-only inspection workaround has no authoritative occurrence to expose. The burden is one correction to occurrence production/consumption at the existing engine/state seam, propagated through existing inspection/decide consumers.

Focused closure proof: hold one independent action with the existing controllable action fixture, reach approval, observe its canonical ID before releasing the independent action, accept a decision and show its dependent can progress while the held peer remains running. Retain the existing all-blocked resource-release proof and stable-ID replay assertions. No new fault framework is needed.

### BEH-008-2 — A discarded speculative occurrence still accepts a first decision

Classification: **INCORRECT**. Violated obligation: task Decision acceptance requires the “pending, current occurrence” and refuses “stale” occurrences; contracts Human approval requires non-pending occurrence 409 and excludes speculative/obsolete authority.

Exact changed location: `crates/wyrd/wyrd-server/src/components/verification/service/approvals.rs:75` (historical membership accepted as current eligibility) and `:124` (only execution-level open check); associated producer/consumer locations `verification/state.rs:825` and `service/inspection.rs:291`.

Reachable supported sequence:

1. A deferred slot feeds a guard-producing step. A speculative approval's `when` reads that guard step; it has no ordinary dependency on the guard (`Step::prerequisites` excludes speculative `when`), and its own `input_slots` does not inherit the guard step's deferred input. It can therefore be reached while that guard waits. A second independent deferred branch also waits. The whole execution parks, durably recording the approval ID.
2. Publish the guard input with a result making the approval's `when` false. On resumption, the engine records `ControlRecord::Disposition { speculation: Discarded }` for the approval and excludes its contribution. The other deferred branch keeps the same execution open and parked.
3. `RunState::wait` only appends newly reached approvals; it preserves the earlier occurrence. Inspection classifies every undecided historical occurrence as pending whenever the execution is open, without consulting its accepted disposition. A first decision for that ID passes the membership test and `open_for_decision`, then gets durably acknowledged even though the occurrence was already discarded.

Source proof: `engine.rs:1018–1050` explicitly removes awaiting speculative work when its resolved guard does not admit it and records disposition; `step` also restores that disposition and skips the occurrence on later runs. `ExecutionState::speculation` already resolves the accepted authoritative disposition. `RunState::wait` never retires/removes an old entry, and `Retained::approvals`/`undecided` consult only decision presence and execution status. `decide_approval` never reads occurrence disposition. Current pg stale/old-head coverage cancels the entire execution and does not cover this still-open case.

Consequence/materiality: a user is shown a discarded step as needing approval and receives a durable positive decision receipt for a stale occurrence that the engine will never use. The run can also be mislabeled waiting-for-approval based on obsolete history. This directly violates the explicit current/non-pending refusal contract; no claim is made that the already-discarded output escapes the engine's existing speculation fence.

Smallest safe correction boundary: preserve historical occurrence identity and accepted receipts, but derive current decision eligibility from the existing accepted execution lifecycle/disposition authority. Reuse `ExecutionState::speculation` and existing status mechanisms for inspection and fresh decision acceptance, rather than treating membership as a pending marker or duplicating speculative evaluation. Refuse a new decision for a discarded/blocked occurrence with the existing typed 409; keep genuine pending occurrences and identical accepted-receipt replay semantics. No new table, deadline, poller or product decision is needed. Consumer guards are appropriate at inspection/decision boundaries because they project and enforce the already accepted lifecycle, rather than inventing one; alternatively a single shared lifecycle predicate can serve both according to existing local owner patterns.

Focused closure proof: use the existing deferred-publication journey machinery to park a speculative approval, resolve its guard false while another branch stays parked, then inspect and try its old ID. Assert it is no longer presented as pending and a first approve/reject returns `WYRD_VERIFICATION_409_APPROVAL_NOT_PENDING`; the retained branch must remain unaffected and old occurrence history must not become a new identity.
