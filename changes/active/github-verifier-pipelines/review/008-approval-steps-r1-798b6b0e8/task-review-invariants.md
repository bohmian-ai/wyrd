## Proposed findings

### INVREV-01 — MISSING: a reached approval is invisible until every independent action completes

**Violated obligation.** TASK-008 Input → pending explicitly requires the sole state owner to issue the occurrence identity when the approval becomes pending and place identity/message in live state, while independent branches continue. REQ-010 and the Human approval contract require inspection to expose pending occurrences, and REQ-011 allows parking only when nothing remains runnable.

**Locations and producer-to-consumer proof.** `crates/vala/vala-verify/src/blocks/engine.rs:1543–1558` constructs an undecided `ApprovalOccurrence` without checkpointing it. `step` collects these into `Done::Awaiting` (:1408–1420), and `drive` stores them only in its local map (:1095–1098). It returns them only inside `if tasks.is_empty()` (:1068–1083). The only production caller issuing IDs and adding them to live state is runner `execute` at `crates/wyrd/wyrd-server/src/verification/runner.rs:579–581`, after the engine returns. `RunState::wait` (state.rs:814–843) is the only writer of `state.approvals`; `Retained::approvals` (service/inspection.rs:291–321) and decision acceptance (service/approvals.rs:74–87) consult only that accepted state. There is no sibling path registering the pending occurrence sooner.

**Reachable supported scenario and consequence.** A non-speculative root approval runs beside a long independent Agent/code/extraction step. The approval has reached pending immediately, but every inspection throughout the independent work returns no occurrence, and no approval ID can be decided. Only after the independent task finishes can the occurrence enter live/accepted state. If that task uses most or all of the original execution deadline, the human gets little or no opportunity to decide even though the approval was independently ready for the whole interval. This loses the required parallel human/computation journey; it is not merely eventual Scribe visibility, because no state change is staged at all during that interval.

**Smallest safe correction.** Record each reached occurrence through the existing engine checkpoint/live `RunState` owner at the time it becomes pending, retaining the existing asynchronous background flush and accepted-state inspection/acceptance. Keep all-blocked parking separate and reuse its current custody handoff. Do not add a second full-state writer, per-approval service, pending-step SQL or an ACK wait inside the engine. Preserve repeat/fanout identity and speculative disposition semantics. Deleting the action or adding an inspection fallback to process-local engine state cannot satisfy the task's durable identity contract; a bounded existing-owner transition is required.

**Focused closure proof.** Hold one ordinary independent action active while the root approval is reached; observe its exact pending ID/message through accepted-state execution inspection and accept a decision before releasing the independent action. Then release it and verify the same execution consumes the receipt and does not replay settled work. The check must fail if occurrence registration is deferred until all-blocked park. Existing tests only inspect Waiting after independent action completion, so they miss the defect.

### INVREV-02 — INCORRECT: decision admission ignores the Verifier's shorter original deadline

**Violated obligation.** REQ-010/011 and TASK-008 Decision acceptance require refusing decisions after the execution's one original expiration. `architecture/wyrd-design.md:2126–2131` explicitly states both the runtime ceiling and the Verifier's `limits.timeout_seconds` count from admission. This is not a request for a new approval deadline.

**Locations and producer-to-consumer proof.** `crates/wyrd/wyrd-server/src/components/verification/service/approvals.rs:124–129` converts only `state.verification.execution_timeout()` and passes it to `open_for_decision`. The SQL at `crates/wyrd/wyrd-sql/src/queries/verifier_executions/approvals.rs:21–24` accepts any nonterminal row whose `created_at + global_timeout` is future. The existing runtime authority at runner.rs:1450–1460 instead takes the minimum of remaining global timeout and the exact registered Verifier's `limits.timeout_seconds - run.age`; that is the effective original deadline passed into `RunState` and the engine. The decision route does not retrieve/apply that authored limit and `retained` only checks retained/queue state, not this elapsed limit. Inspection likewise derives pending from nonterminal status.

**Reachable supported scenario and consequence.** Declare an approval Verifier with a short authored timeout under a longer server ceiling, let it park, then stop the runtime as the existing restart journey does. After the authored timeout elapses but before the wider runtime timeout, the row remains pending/retrying and an authorized decision returns a durable positive `approved` receipt. On restart the same execution correctly times out under its shorter limit. The accepted decision was therefore taken after the execution had expired, and the receipt falsely represents a current approval occurrence. A worker being stopped is explicitly supported by AC-007, so this is not a hypothetical nanosecond acceptance race.

**Smallest safe correction.** Make external decision admission use the same effective original execution limit as the runner: the minimum of its runtime ceiling and the exact accepted registered Verifier's authored timeout, still measured from original admission on PostgreSQL's clock. Reuse the existing target/spec and SQL deadline owners; do not add a per-approval duration, new clock anchor or extra deadline store. The existing SQL boundary can continue deriving the deadline from a supplied duration. A post-receipt runner check cannot repair acceptance after expiry, and waiting for a worker to mark the row terminal fails the required stopped-runtime case.

**Focused closure proof.** With a shorter authored Verifier timeout and longer runtime ceiling, park the execution, stop its runtime, wait past the authored expiration, and decide through the ordinary route. Assert 409 approval-not-pending and no accepted decision, then restart and observe timeout. Preserve successful before-expiry decisions and original-ID restart behavior. The current expiry journey sets the runtime limit and waits for `timed_out`, so it cannot falsify this mismatch.
