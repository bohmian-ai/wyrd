## Proposed findings

### DATA-R2-001 — INCORRECT: FIND-008-3 remains open when target resolution refuses

Stable prior finding: **FIND-008-3**. Location: `crates/wyrd/wyrd-server/src/components/verification/service/approvals.rs:132–150`, especially `.ok().and_then(|target| target.authored_timeout())`.

REQ-010/011 and the remediation require every fresh decision after the original authored execution expiration to refuse. `VerifierCardCache::resolve` returns `Result<Result<Arc<Target>, EnqueueRefusal>, SqlError>`. A successful registry query can refuse its target; this is distinct from a successfully resolved target with no authored timeout. `Target::resolved` applies `VerificationTarget::refusal` first, which refuses an absent/deleted Verifier, absent/deleted subject, or non-ready baseline. The new `.ok()` erases that distinction, substitutes `None`, and selects the longer runtime ceiling.

Reachable scenario: admit and park a Verifier with a shorter authored limit, stop its worker, then delete its exact subject or its exact Verifier through ordinary Card lifecycle (remove visible inbound references first when required). Card soft-delete updates status and invalidates target cache; it does not cancel queue rows. The application still retains the accepted pending identity. `retained` reads that accepted identity and unfinished queue row; its authorization and `authorize_subject` check permissions and signed scope, not current registry readiness. After the authored deadline but before the runtime ceiling, resolve returns SubjectUnavailable/VerifierUnavailable. The service discards this refusal, SQL OPEN sees the runtime duration and unfinished row, and Scribe accepts a fresh positive receipt for an expired execution. This is not an ACK/deadline overlap race. Baseline-not-ready supplies another source of the same erased refusal; it does not need another correction.

Materiality: the required original-expiration refusal must hold during ordinary worker downtime and registry lifecycle changes, precisely when the API performs its independent admission check. Correct behavior for a ready exact target does not justify widening an unknown original limit. The observable consequence remains the original FIND-008-3 defect: durable decision accepted after the execution's actual expiration. The existing new test never changes readiness and therefore misses this branch.

Smallest correction: preserve the existing target resolver's refusal and fail closed before fresh decision admission when the target cannot be resolved. Use an existing typed refusal; do not invent a deadline, new registry reader, stored clock anchor, background timer, or cross-store transaction. Already accepted identical receipt replay remains before this fresh-admission requirement. A small stopped-worker journey extends the current authored-timeout fixture with ordinary target unavailability and asserts no fresh accepted decision after authored expiry. No need for a new harness or broad lifecycle rewrite.

### DATA-R2-002 — REGRESSION: a cold decision holds one pool connection while waiting for another

New finding proposal (assign next stable FIND ID during independent validation). Location: `components/verification/service/approvals.rs:122–145`; producer/consumer source: `verification/cache.rs:276–307`, `wyrd-sql/src/postgres.rs:182–201`.

The remediation acquires a `TenantConn` from `self.state.postgres.wyrd()` and keeps it alive for `open_for_decision`. While holding it, target resolution uses `Db::Pool` of that same WyrdPostgres. On a cold cache or disconnected invalidation listener, `VerifierCardCache::load` calls `postgres.conn().await`, which acquires a second connection from the same `app` pool. `WyrdPostgres::tenant_conn` and `conn` both use that exact pool.

Supported failing case: only one application pool slot remains available after ordinary other traffic/listeners; a fresh approval takes it, then its cold target read waits for another pool slot until configured acquisition timeout (five seconds by default), returning registry unavailable although its held connection can perform the required lookup. Multiple concurrent cold decisions can likewise occupy all available slots with their first transaction and mutually wait for second connections. A listener reconnection/cold cache is explicitly supported by cache.rs:18–28, so this is not an invalid cache state. Pool bounds are operator configuration (`PoolConfig::from_lookup`, WYRD_DB_MAX_CONNECTIONS/MIN_CONNECTIONS); the defect is nested resource acquisition under supported bounded capacity, not a demand to tolerate arbitrary synthetic host load.

Materiality: ordinary approval decisions unnecessarily fail during cache coldness and pool contention, and retain scarce database transactions during the timeout. This added path did not exist before remediation. It is distinct from authored-timeout refusal and needs no new product/concurrency decision.

Smallest correction: resolve through the existing `Db::Conn(conn.transaction())` variant, as the runner already does, so the one tenant-bound connection performs the lookup and eligibility query; alternatively resolving before acquiring the transaction avoids nesting, but reusing the existing connection directly is sufficient. Preserve exact UIDs, tenant binding, existing SQL predicate, transaction commit and ACK ordering. Focused proof should force a cold resolution with only one serving connection available and show a decision does not wait for a second connection. Reuse existing pool/approval integration owners; no dependency, lock, semaphore or retry layer is warranted.
