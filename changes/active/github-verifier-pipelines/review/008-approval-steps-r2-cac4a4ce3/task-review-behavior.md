## Proposed finding DISC-008-8 — Cold approval acceptance holds one pool slot while requesting another

Classification: **REGRESSION**. Obligation: preserve usable ordinary approval/restart paths and bounded shared resource use (REQ-010/011/017); the remediation must correct expiry without introducing shared-service starvation.

Exact changed location: `crates/wyrd/wyrd-server/src/components/verification/service/approvals.rs:124–147`. The handler acquires `TenantConn` at 124–130 and keeps it until commit at 156. It then invokes `VerifierCardCache::resolve(Db::Pool(...))` to determine the authored ceiling. On a cold/invalidated cache, `verification/cache.rs::load:291–297` independently awaits `postgres.conn()` before reading `VerificationTargets`. Cache misses are normal after server restart, target invalidation or loss of the cache notification listener (`cached:310–318` refuses cache while not live).

Reachable failure: concurrent fresh approval requests each obtain one available tenant pool slot, then all cold resolves request a second slot from the same WyrdPostgres pool. None can release its first slot until the nested acquisition completes. At pool capacity this becomes a pool-wait cycle ending only in timeout/refusal. A pool with one available slot exhibits the issue with one request. There is no new token or malformed input requirement: parked executions decided on a restarted node are a required journey. The same saturation also delays unrelated operations sharing the pool. This is a material changed-path availability regression, not a request for speculative optimization.

Existing alternatives and smallest correction: reuse the existing target/cache owner and determine the effective ceiling before acquiring the decision tenant transaction, then open the short tenant-scoped `open_for_decision` transaction as before. Alternatively the cache already accepts `Db::Conn` for caller-owned connections, but no second pool acquisition is necessary. Prefer moving the preparation ahead of the transaction when retaining the existing pool-based resolver. Do not add a cache, pool, retry, reserved connection or scheduler. No new authority/clock semantics are needed; the exact UID lookup and PostgreSQL deadline comparison stay intact.

Focused proof: force a normal cold cache and leave only the caller's required pool capacity available (existing pool/connection controls), exercise fresh approval acceptance, and establish that it resolves the exact authored timeout and completes rather than awaiting a second connection while retaining the first. Include the short-authored-expiry case and existing replay/ACK behavior. This is one local ordering correction, smaller than introducing capacity machinery or weakening the timeout lookup.
