## DATA-009-1 — Overlapping delivery workers can duplicate remote objects and overwrite a completed Check

Classification: INCORRECT. Priority: high.

Violated obligations: original task RENDER requires one Check per execution, one COMMENT review, and a completed Check never returning to in_progress; DELIVERY permits a rare duplicate after a lost provider answer. REQ-013/014 and architecture/wyrd-design.md 2530–2558 retain these behaviors. Root AGENTS.md explicitly supports one logical server with multiple replicas.

Exact source: crates/wyrd/wyrd-server/src/components/github/delivery.rs:147–168 (lookup and mutation), :190–200 (independent spawn), :215–232 (recovery invocation), :279–326 (read/send/record without serialization), :517–528 (PR lock released before provider operations). Producers: verification/runner.rs:1531–1541 spawns independently after each park/settlement; app/server.rs:661–670 starts a recovery worker in each server. The provider adapter app.rs:720–745 issues ordinary unconditional POST/PATCH calls. GithubAppMock's handlers at crates/wyrd/wyrd-testing/src/github.rs:1338–1379 create a fresh Check for each POST and apply PATCH fields unconditionally.

Reachable failure A, requiring no provider fault: during a rolling restart, two replicas recover the same completed current execution with no recorded outcome. Both presented reads succeed and both recorded reads see no fence. Both Check lookups return absent before either POST is processed. Both POST normally and successfully create a Check with the same execution external_id. Both can likewise read an absent review marker and POST two COMMENT reviews. First-wins outcome recording afterward leaves one outcome but cannot undo either duplicate remote write. This is ordinary overlap, not the accepted lost-answer exception. The existing PR lock does not serialize this operation: it is committed before the lookups, so both workers can pass it.

Reachable failure B, same cause: a parked revision's delivery reads an existing in_progress Check, then pauses before its PATCH. Approval/evidence resumes the execution, a new accepted terminal revision settles, and a second spawned delivery updates that Check to completed and records its terminal outcome. The older task resumes and applies its prepared in_progress PATCH. The guard at line 154 consulted the earlier GET response and does not protect the later mutation. Recovery sees the terminal outcome and skips further correction, so the wrong remote status can persist. The mock applies exactly this stale mutation; no conditional provider update exists in the adapter. This also affects one replica because runner handoffs are detached tasks.

Material consequence: duplicate public reviews/Checks on routine rolling replacement, or a completed verification's Check regressing while execution inspection permanently reports successful terminal delivery. Bifrost outcome uniqueness alone does not enforce remote object uniqueness or revision ordering.

Smallest correction boundary: serialize all delivery entry points for one tenant/execution across processes before reading the accepted revision/outcome and performing lookup-and-write. Reuse the transaction-scoped advisory-lock mechanism already owned by VerifierExecutionQueue (pull_requests.rs::lock_pull_request and verifier_executions.rs::LOCK_REQUEST_KEYS_SQL demonstrate the existing mechanism), through TenantConn and caller-owned transactions. A delivery-specific per-execution coordination identity avoids holding the PR admission lock across provider waits or delaying sibling executions. Re-read accepted state/outcome after acquiring serialization; a delayed waiting task must not resume with a presentation captured before a terminal delivery. Preserve lookup-before-create, rare lost-answer duplication semantics, independent verdict settlement, existing access/current-generation checks, and existing Scribe outcome owner. No new table, column, payload mirror, lease ledger, finalizer or generic lock service is needed. A local Mutex is insufficient for replicas; another unlocked GET or the existing post-write Bifrost fence cannot close the race.

Focused proof requested from the orchestrator: use the existing local GitHub transport with deterministic barriers, with two delivery workers sharing Postgres/Bifrost, to force both through initial absent-object lookup under fault-free successful provider responses and assert one POST-created Check/review. Also hold a waiting update across terminal delivery and assert the Check remains completed after all workers finish, while terminal inspection stays delivered and no recomputation occurs. Do not substitute a test which waits for the waiting outcome before resuming the execution. The existing mock may need a small successful request barrier because stall_next_delivery_request deliberately returns 502; preserve that fault's existing behavior.
