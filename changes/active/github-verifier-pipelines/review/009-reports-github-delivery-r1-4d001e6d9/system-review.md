## Proposed material findings

### SYS-009-01 — INCORRECT: a GitHub cooldown consumes the shared server shutdown deadline

Violated boundary: recovery must remain isolated from unrelated shared server capabilities and preserve the existing supervised shutdown/drain lifecycle. The original task requires background recoverable delivery; it does not authorize delaying Bifrost shutdown for external GitHub availability. AGENTS protects required durability and resource ownership. The existing GitHub recovery owner expressly abandons active provider work on shutdown to preserve the shared drain budget.

Exact location: components/github/delivery.rs:214–237, especially 230–232, called by app/server.rs:661–670. attempt sleeps at delivery.rs:479 and deliver_retried sleeps at 262 without a shutdown token.

Reachable failure: restart with one current completed execution lacking its delivery outcome. The recovery scan reaches GitHub and receives Retry-After: 120, then sleeps inside deliver_retried. SIGTERM arrives during this wait. recover only checks shutdown before starting the execution, or after the entire scan returns; neither is reached during the cooldown. The supervised JoinSet cannot drain before the maximum configured 60s deadline (default 35s; config.rs:3441–3443, 4125–4131). app/supervise.rs:300–319 spends the entire deadline then aborts remaining workers. app/server.rs:898–917 consequently calls bifrost.abort and reports that the role drain never ran. Unrelated Scribe/Oracle/Forge work loses its normal drain opportunity solely because the external report recovery was waiting on GitHub. Unacknowledged outbox work is subject to the documented shutdown-loss boundary.

Existing alternative and smallest correction: reuse the cancellation boundary already used by GithubConnections::run_delivery_recovery (components/github/pull_requests.rs:563–586), selecting shutdown against the active report recovery scan/delivery. An unfinished report has no outcome and is already restart-recoverable; no new progress store, worker type or finalizer is needed. Preserve bounded retries and already-issued remote IO semantics. Cancellation belongs at this supervised background component, not at the whole process or verdict boundary.

Focused closure proof: start actual report recovery with a current no-outcome execution, hold it in provider IO or a cooldown longer than the configured drain, cancel the worker's shutdown token, and assert prompt worker completion without releasing the provider hold or expiring the cooldown. Exercise the existing bound-server shutdown path and assert the Bifrost role-drain phase is reached with remaining budget. The current successful restart test does not establish this property.

### SYS-009-02 — INCORRECT: recognized rate limits are retried before the provider's cooldown ends

Violated obligation: REQ-014 and TASK-009 DELIVERY require honoring provider cooldowns and bounded retries; AC-009 explicitly requires rate-limit cooldown proof.

Exact locations: components/github/app.rs:855–870 and components/github/delivery.rs:471–479 (COOLDOWN_MAX at 78–79).

Reachable failures: (a) GitHub's normal exhausted primary quota returns 403, x-ratelimit-remaining: 0 and a future x-ratelimit-reset without Retry-After. answer correctly recognizes a rate limit but discards the reset deadline and substitutes 60s. With reset still 30 minutes away it retries five times before reset, then permanently records failed/github_unavailable for that revision. (b) Retry-After: 1800 is decoded correctly, then reduced to 900 seconds by min(COOLDOWN_MAX), so the next request runs 15 minutes early. Both are ordinary provider rate-limit responses, not malformed hostile input. Early retries waste the finite retry budget and amplify provider throttling across current executions and replicas. A recorded failed revision will not be automatically redelivered after the actual reset, because recorded() short-circuits it.

Provider contract independently checked in GitHub's primary documentation, “Rate limits for the REST API” and “Troubleshooting the REST API”: Retry-After specifies the minimum wait; zero remaining quota requires waiting until x-ratelimit-reset. No quoted source text is necessary to establish the local code path.

Smallest correction: in the existing answer owner derive Cooldown from Retry-After, otherwise from the reset deadline for a zero-remaining response, using the existing fallback only when no applicable valid provider timing exists. In attempt preserve that minimum delay instead of reducing it. Keep five attempts, existing safe outcome reasons, current-access/generation checks and the cancellation boundary from SYS-009-01. This needs no shared scheduler, cross-replica rate-limit ledger, new dependency, configuration option or SQL state. A bounded attempt count does not require shortening the provider's minimum pause.

Focused closure proof: local transport responses for both a primary-limit reset without Retry-After and a Retry-After exceeding 15 minutes. Assert computed retry eligibility is no earlier than the provider deadline, using deterministic time rather than a real long sleep; retain the existing two-second connected proof and finite-attempt refusal/outage behavior.
