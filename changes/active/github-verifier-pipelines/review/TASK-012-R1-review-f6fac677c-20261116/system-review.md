## Proposed finding SYS-R1-1 — active settlement escapes the cancellation barrier

Retain stable FIND-012-1; classification INCORRECT. This is incomplete closure of the original dropped-future ownership defect, not a new requirement. Violated obligations: original task OBL-3 and required composition; R1-1 explicitly covers speculative discard and original expiry before disposition/checkpoint/terminal progress. The R1 task also explicitly requires the original deadline expiring during work/settlement.

Exact correction boundary: crates/vala/vala-verify/src/blocks/tools.rs:142–150,190–205,274–280. Consumers: engine.rs:1105–1133,883–889,1943,2066 and runner.rs:762–772. `drain` pops the Settlement from shared storage before `settlement.await`. While Pending, that future exists only in the cancellable drain stack. ToolCallsOwner::drop transfers only the remaining vector, so it cannot retain the active future. HostWork has the identical problem. An empty vector is also treated as completed while another consumer owns a pending popped settlement.

Reachable failure paths:

1. A declared Agent starts fs.extract. Its authored attempt timeout, session halt or returned error ends the tool/model wait while actual blocking extraction remains. Engine attempt reaches tool_calls.settle, which pops the registered TaskTracker wait and blocks. The original execution deadline then drops drive (or a speculative guard cancels that step). The active settlement is dropped and its vector is empty. Owner Drop adopts nothing; HostWork::settle returns immediately. The direct DeadlineExceeded result, queued timed_out outcome or speculative disposition is accepted while actual extraction still runs. This path uses the existing SettlingToolset stopped/direct cases, but lets the original execution deadline pass instead of releasing work first.
2. A speculative discard adopts queued work correctly, and its disposition starts HostWork::settle. If the original deadline passes while that wait is pending, dropping drive discards the popped settlement. run's later HostWork::settle and queued compute's outer drain see no entry and return while actual work remains.
3. Two speculative dispositions share HostWork. Tasks::next polls their futures together. One drain can pop the remaining work and wait; another sees the now-empty vector and records its disposition before that work settles. With multiple entries, a faster drain can similarly empty its subset and finish while another owns a pending entry. This violates the new shared owner's claimed completion barrier and can release downstream work/checkpoints prematurely.

Observable system consequence: terminal or checkpoint progress advertises settlement before started host work ended. Tracked blocking ownership still protects some bytes/writer permits; that does not satisfy the explicit sequencing boundary. This does not imply shared-server failure or require terminating unrelated requests, Scribe, Oracle, or gateway traffic. The consequence is material because ordinary authored timeout plus execution expiry, and supported speculative cancellation/concurrency, are explicitly required lifecycle cases.

Smallest correction: keep active settlement completion owned by the existing ToolCallsOwner/HostWork lifecycle until it has actually completed; cancellation of a waiter must not destroy or hide unfinished settlement, and all concurrent waiters must observe unfinished in-flight work. Extend this existing owner and its tracker completion mechanism; do not add a scheduler, persistence wait, service, new per-tool guards or timeout extension. Only transferring queued futures at Drop is insufficient. A fix only at runner or only at disposition repeats the same broken ownership rule and misses direct/check consumers.

Focused closure proof: extend existing settling-toolset/engine tests to confirm the per-attempt settlement has begun, then expire the original execution deadline or decide a false speculative guard while held work remains. Also let an already-waiting speculative disposition cross the original deadline, and cancel two speculative steps with independently held work. Assert no corresponding disposition/checkpoint/result/queued terminal progresses until its required host work ends; assert no settlement signal is dropped and no consumer mistakes another active waiter for completion. Release work and retain original timeout classification, withheld output, spend and producer identity. Reuse the current held-work/tracker fixtures; no host load, benchmark, broad journey, new dependency or external harness is needed.
