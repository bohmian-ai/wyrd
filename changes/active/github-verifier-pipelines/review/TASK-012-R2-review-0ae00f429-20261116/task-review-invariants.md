## Media bound trace

Let P be the provider-shaped bytes for one occurrence and E the returned base64 source. Production admission promises `N + E + 6P` per input (P is multiplied by actual occurrence count). The raw buffer ends when media returns; retaining its charge is conservative.

The source `MediaRef` E and its new binding payload coexist during binding. OpenAI Chat images/PDFs use `data:<mime>;base64,` via prompt.rs:1911–1953. Responses supported images use the same prefix; Anthropic and Google clone bare E and MIME rather than producing a larger encoding. Each binder replaces matching isolated text parts. Counting other serialized matching leaves can overestimate, not omit an actual bound part; the request has already split authored media placeholders before this count.

At run_prompt the Arc-backed bound Prompt is one P, rendered template adds P, and extracted seeds add P (loop_runtime.rs:220–254). During rebuild, `seed_messages.to_vec()` adds P; Chat/Anthropic/Gemini clear their previous message vector before cloning replacements, so this phase peaks at four P. Responses builds replacement items while retaining old input, reaching five P (request_builder.rs:122–135,215–263). The temporary messages disappear before hooks. The session hook receives `template.clone()` (loop_runtime.rs:418–449), so bound Prompt + template + seeds + hook request is four P. Render with text substitution also transiently serializes the already-bound payload but occurs before seeds exist. Six P therefore conservatively covers these phases; the maximum rebuild and hook counts must not be summed as though simultaneously live. Transport/body charges remain their independent existing owner; the Wyrd gateway provider forwards a borrowed request.

The new held-provider test has no declared tools (`agent(prompt(), &[])`); it does not execute the `before_model` session branch. That limits runtime proof, but the actual hook clone is covered by the static conservative bound above. No missing quantitative test alone is promoted into another material production finding.

## Proposed retained finding

### INV-R2-01 — result promise is smaller than the representation built before it is fitted

Retain stable ID **FIND-012-2**. Classification: **INCORRECT**, incomplete prior correction. Exact producer: crates/wyrd/wyrd-server/src/verification/runner.rs:1627–1636; representation owners results.rs:317–341,618–623; state.rs:356–359 supplies the compact-JSON-plus-512 decision size.

The additional promise uses `charge.bytes()`, the selected decision's retained compact JSON length plus 512. `result()` immediately builds the output Variant and both staged rows. Only after construction and dropping the selected decision does `fit` grow the promise to `ScribeSink::weight(write)`. Compact JSON size is not an upper bound on these result bytes.

A concrete ordinary supported output proves materiality: one captured step returns a JSON array of 100,000 zeros, with empty input evidence and otherwise small outcome fields. `StepResult.output` accepts JSON Value (wyrd-spec execution.rs:818–825); no exotic input or failed parser is needed. The array's compact JSON is 200,001 bytes. The pinned production Variant encoder emits Int8 zero as two bytes (primitive tag plus value), then a list header and one offset per element. With 200,000 data bytes, offsets are three bytes each. The array alone therefore encodes to `200000 + 1 + 4 + 100001*3 = 500008` bytes. Outer result objects, metadata, cell arrays and repeated identity fields add more. The decision promise for that minimal outcome is approximately 200 KiB, leaving approximately 300 KiB of independently materialized result bytes unpromised while result building runs. Larger valid numeric outputs scale this gap. This is representation demand, not allocator-capacity or exact-RSS speculation.

Pinned encoder source inspected: Cargo.lock bohmian-parquet-variant revision `394d4b0757488d70df9a78c0c271ab3c8fbc2928`; local checkout parquet-variant/src/builder.rs:46–52 (`int_size`) and :182–185 (`append_int8`), builder/list.rs:154–198 (`finish` count/offset/header layout). Wyrd's own variant.rs:218–230 serializes directly into that builder; serialize.rs:151–200 narrows integers and forwards them, and list serialization finishes the actual list. This calculation does not rely on a different registry version or assume an intermediate JSON copy.

Observable consequence: concurrent hosted/Bifrost admissions on other runtime threads can reuse the missing promise while this supported queued result is being encoded. Later infallible growth makes the ledger accurate only after the allocation. R2 explicitly required before-allocation accounting for result materialization; satisfying the postconstruction reservation lifetime does not close that earlier boundary. Both normal terminal selection and recovered/redelivered selection use the same conclude path.

Smallest correction boundary: retain the existing common queued result handoff and ByteCharge/Reservation mechanism. Before `result()` builds, calculate a conservative bound for its actual output-Variant and row representation from the borrowed selected/frozen inputs, and take that promise first; reconcile downward to actual weight afterward. Reuse the existing nonallocating serialization/counting pattern and actual format/schema bounds rather than treating decision JSON bytes as a representation bound.
