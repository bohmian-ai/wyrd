## Deployed and failure paths

1. A direct verification on combined/direct reaches the existing VerificationControl, computes its deadline from request arrival, performs the bounded target load, then binds the shared HostedBlocks engine. Its model/tool, Python and file work remain actual work. A direct call on worker or Bifrost targets returns the stable wrong-target refusal before authorization/admission. Queue-only publishing/extraction/deferred work remains refused for direct execution.
2. A queued submission or webhook runs only on combined/worker; engine_workers never constructs the claim runtime for direct or Bifrost targets. Both direct and queued calls on combined bind the same sandbox/workspace/model-call owners. There is no idle queued reservation.
3. A Python timeout or dropped operation discards its checkout. Lease::drop leaves the envelope in Workers, and reap removes that PID's charge only after alive reports it gone. A subsequent invocation can run; it does not require taking down Scribe, Oracle, registry or other verification requests. Idle-worker pressure reaping does not replenish the live worker's charge prematurely.
4. A filesystem tool or snapshot may outlive a cancelled Rust future because blocking work cannot be stopped by dropping the wait. Invocation::blocking moves its writer/concurrency ownership into the tracked task; ToolSession settlement closes and waits for the tracker before attempt resource release. Workspace::freeze similarly moves writer ownership and its Arc into tracked work. This prevents a concurrent writer or retry from seeing unsettled host work.
5. An unavailable Scribe holds bounded outbox custody and retries the same writes; queued terminal/park computation ends before canonical ACK and its claim remains owned until settlement. A full terminal path stops new claims rather than rerunning completed computation. Existing direct work remains available. On restoration the queued owner publishes/settles its retained state, subject to the unchanged loss of unaccepted progress on process death.
6. Shutdown stops transports/new claims first, drains supervised work, then gateway accounting, MCP and the sandbox, then Scribe outbox and Bifrost and submissions. app/server.rs:818–936 uses the same deadline for later phases and reports failure if live work or role drain exceeds it; it does not manufacture a clean drain after abort. Forge loop failures remain owned by restarting_worker, not process-terminal tasks.
7. A workspace cleanup IO failure differs from the correctly fenced paths above: it is logged but no custody remains for its disk bytes after Drop. New work can consume the false free scratch while those bytes remain. The same filesystem also serves Oracle/Forge spill, so the affected capability is shared scratch admission, not just the invocation that ended.

## Proposed finding SYS-012-1

Classification: INCORRECT.

Violated obligations: TASK-012 OBL-6 requires scratch release only after deletion or ownership transfer. architecture/bifrost-design.md:1902–1910 requires a charge to return only once its owner has settled the bytes and identifies deletion as the scratch release boundary. Task OBL-7 and REQ-015 share that scratch authority across hosted verification and Bifrost.

Exact changed location: crates/wyrd/wyrd-server/src/verification/hosted/workspace.rs:465–505, especially the failed-empty branch at 487–490 and remove at 503–506.

Producer and consumer trace: HostedBlocks::start binds Workspaces to the one ProcessResources ledger at blocks.rs:133–138. HostedTools::open obtains Workspaces::open at tools.rs:175–185. That open creates a ScratchRoot-charged Workspace, and successful construction marks its root recyclable at workspace.rs:287–290. reserve/admit_write charge its inputs and work before mutation. Invocation/session and tracked host work own its Arc until normal completion, failure or cancellation. Its last drop calls empty_root; on error it calls remove, whose failure is only logged, then unconditionally drops scratch. A refused/cancelled partial open takes the non-recycle branch and has the same problem when remove fails. New Workspaces::open/admit_write and Oracle/Forge spill admissions consume the now-falsely-free shared ledger.

Reachable failure and consequence: while a charged workspace holds files, its local filesystem refuses cleanup, for example because the scratch volume becomes read-only or reports an IO error. Both empty_root and remove_dir_all fail, leaving bytes present. Dropping scratch returns those still-present bytes to the ledger. If the filesystem resumes writable service without restarting this process, the next workspace/spill can be admitted against the false capacity and fill the shared filesystem beyond its promised scratch limit. The code explicitly implements and logs this failure branch; success-only cleanup tests do not remove it. Repeated end-of-invocation failures can accumulate uncharged bytes.

Materiality: this is the explicitly required failure boundary for hard-bounded shared scratch, not an additional availability guarantee or hypothetical input-hardening rule. It can make a local workspace cleanup error affect later verification and Bifrost spill availability on the shared process/filesystem. Refusing subsequent scratch use is correct; terminating the shared server is not necessary.

Smallest testable correction: keep this responsibility in Workspace cleanup. Return the workspace charge only after cleanup establishes that its charged files are gone, or transfer the charge to an owner that actually retains/retries them. For an unrecoverable cleanup failure, retain that charge for the remaining process lifetime and log the retained-byte failure, following the already-present ChargedSpillFile::drop behavior at oracle/spill.rs:231–249. Do not enqueue another cleanup framework or change process failure policy. Preserve successful root reuse, cancellation settlement and off-thread cleanup. Apply the same rule to successful opens and partially materialized/refused opens; do not add independent downstream admission guards.

Correction burden: one existing cleanup owner and its fallible removal result plus a focused failure-path assertion. Removing accounting or assuming boot cleanup is insufficient: the process can continue after cleanup failure. A new service, retry worker or process-wide shutdown policy is unnecessary.

Focused closure proof: force a charged workspace's cleanup to fail with bytes still present; after drop/cleanup completion assert those bytes remain charged and another request for that scratch refuses. Restore cleanup and verify normal successful deletion/reuse still releases exactly once. Exercise both the recycled-root and partial-open removal outcomes through the existing workspace test owner. No broad journey or benchmark requirement is added.
