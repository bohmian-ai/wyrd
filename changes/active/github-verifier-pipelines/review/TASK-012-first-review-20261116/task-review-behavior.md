## Proposed findings

### BEH-012-1 — speculative cancellation discards the settlement owner

Classification: INCORRECT. Violated obligations: TASK-012 OBL-3 and required composition; inherited code-mode REQ-012. Changed location: crates/vala/vala-verify/src/blocks/engine.rs:1870–1917 and :2021–2040; affected existing cancellation consumer :1086; crates/vala/vala-verify/src/blocks/tools.rs:180–206.

Producer-to-consumer proof: AgentExecutor::invoke registers the session settlement into the block's ToolCalls at agent.rs:453. Production HostedTools::open puts TaskTracker::close/wait into that settlement at hosted/tools.rs:214–228. Invocation::blocking starts real blocking filesystem/extraction work at hosted/tools.rs:436–441; dropping its awaiting future does not stop spawn_blocking, and the closure continues holding its workspace/writer/concurrency ownership. The engine keeps ToolCallsOwner only in its action or judge future. Normal completion awaits it, but drive observes a false speculative guard and calls tasks.cancel at :1086. Tasks::cancel in src/walk.rs:119–120 removes and drops the future, including its ToolCallsOwner and unpolled settlement. drive then schedules the disposition control/checkpoint and can finish or release dependents while the blocking extraction continues. There is no per-run retained owner or draining path for that cancelled block.

Reachable scenario: an authored speculative Agent starts fs.extract on its mounted document; an independent guard step finishes false before that bounded extraction ends. Discarding speculation is supported dynamic-pipeline behavior. The extracted result cannot become the selected contribution, but the computation/checkpoint/terminal path now outruns the explicitly required host-work settlement. The ordinary action/check timeout tests do not enter this branch, and the dropped-model test proves no later model request rather than settlement of started blocking work.

Consequence/materiality: the engine records a discarded contribution and may select/return its outcome while host work from that invocation is still running. This breaks the task's specific promise that dropping borrowed block futures does not certify settlement and that settlement precedes checkpoint/result selection. Retaining byte charges inside the blocking closure avoids early memory release but does not satisfy the required sequencing. This is an explicit acceptance failure, not a demand for unbounded cancellation hardening.

Smallest correction: keep ownership of every started block's host settlement across the engine's own cancellation of that block, reuse the existing ToolCallsOwner/ToolSession settlement mechanism, and finish that cleanup before accepting the speculative disposition/checkpoint or selecting the execution outcome. Preserve B's borrowed walk scheduling, immediate stop of further tool/model dispatch, speculative visibility rules, retained resource charges and normal retry/deadline classifications. A new dispatcher, scheduler or persistence wait is unnecessary. This needs a bounded engine lifecycle correction, not another guard in fs.extract or every individual tool.

Focused closure proof: extend the existing blocks_agent settling-toolset integration seam with a speculative Agent whose already-started host work is held while its guard resolves false. Assert that no disposition/checkpoint/result outruns release, then that the discarded contribution remains withheld and cleanup/resources settle. Use its existing integration target and a focused exact selector once the implementation assigns the test name. No full journey suite or benchmark is needed for that correction.

### BEH-012-2 — the live queued execution state is outside the process memory ledger

Classification: MISSING. Violated obligation: TASK-012 OBL-7 and REQ-017's retained-memory ownership. Exact locations: crates/wyrd/wyrd-server/src/verification/state.rs:272–322, :635–660, :367–371, :464–477; crates/shared/wyrd-runtime/src/outbox.rs:584–595.

Producer-to-consumer proof: RunState::at installs recovered ExecutionState directly in Held.state. RunState::change mutations retain publications, invocation settlements, captured output/reason/data and terminal selections in that live state. Neither Held, Writer nor RunState holds a memory ledger or charge. The only state charge is Checkpoint::weight, constructed after held.state.clone() in Writer::flush. Checkpoint::COPIES explicitly covers frozen state, JSON tree, Variant and prepared row, rather than an independently retained live owner. send_reserved attaches that weight to the process ledger only at stage, after the clone. Once the outbox write completes, its charge returns; Held.state still retains every value for live dependency/publication reads and terminal tracking. Background coalescing and an item reservation do not charge those bytes.

Reachable scenario: a queued Agent publishes bounded JSON or a step settles a large bounded output, the background checkpoint is acknowledged while other graph work remains running or the terminal awaits later queue settlement. The live state still owns that content, but the only corresponding outbox charge has ended. A recovered accepted state starts in the same uncharged condition even before any new revision. Bifrost/hosted/request admission therefore sees those bytes as free and can promise the same process memory to other work.

Consequence/materiality: aggregate resource accounting omits retained queued state, defeating the explicit one-ledger contract under ordinary queued workloads and recovery. The current proof asserts checkpoint bytes only while staged; it cannot prove the live-state promise. The clone-before-stage interval also contradicts the requested charge-before-copy ordering. This is required task scope rather than an objection to the existing infallible admission policy.

Smallest correction: give the existing live RunState/Writer custody a charge on the same process ledger, initialized for recovered state and updated with retained content as state mutates, without serializing/copying the growing state per engine transition or waiting for persistence. Keep its charge until the live owner drops/transfers, independently of the frozen/encoding/outbox charge. Charge snapshot custody before allocating its clone and preserve the current background/outbox owner and ACK-before-retirement semantics. Do not create a second ledger, fixed idle reservation, SQL payload store, downstream admission guard or persistence wait. Incremental accounting at the existing state owner is required because charging only staged snapshots leaves the real retained owner invisible.

Focused closure proof: use existing state/outbox tests to retain a nontrivial live accepted or recovered state after all staged writes settle; assert its bytes remain on the shared ledger until live custody ends and a new consumer cannot treat them as free. Hold checkpoint capacity while triggering a frozen copy to assert the extra copy is charged before allocation/custody transfer. Run only focused state/outbox selectors covering the change.
