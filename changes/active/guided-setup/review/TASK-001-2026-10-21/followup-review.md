## Diagnostic boundary: retain the finding, narrow its correction

`_middleware.py:25–29` constructs a new diagnostic by interpolating arbitrary non-Wyrd exception text. Its complete caller set is `_start` cleanup warning (107), `_drain` log/result (115–116), state startup failure (125), and raw application startup exception conversion after receiving startup (151). There is no sanitization in these paths. The original exception's arbitrary body can therefore enter a new Wyrd-owned ASGI failure message or middleware log. REQ-022 explicitly requires a scrubbed diagnostic. The broad standards-review PASS does not establish this property: its error/secret rows examine stable errors and general credential ownership, but do not account for the unrestricted fallback here. BREV-002 and INVREV-003 share one confirmed source-local diagnostic cause.

REQ-022 starts with state writer/telemetry startup; REQ-023 separately requires the application's lifespan and failures to remain failures. Neither requires Wyrd to replace a wrapped application's failure output or redact framework-owned tracebacks. The ASGI protocol explicitly makes the application failure `message` the server's log/print input. Sanitizing every forwarded failure message would change application diagnostics, including those generated by Starlette, and goes beyond the smallest demonstrated correction. The existing C5 assertion at `test_asgi_integration.py:195–201` intentionally preserves the application refusal text. Keep it. BREV-002's assertion that this path proves an additional Wyrd leak and its requirement to sanitize forwarded messages should be removed; retain INVREV-003's ownership distinction.

Existing projection owners are useful but are not a generic secret scrubber. `crates/shared/wyrd-utils/src/py.rs::build_wyrd_py_exception` derives the Python WyrdError fields from the canonical problem projection. Python AGENTS treats that structured exception as the expected public boundary. Its `py_err_to_wyrd_error` fallback itself carries arbitrary exception text, so wrapping an unknown exception through it is not a scrubbing solution. `RedactionPolicy`/`Redactable` describe structured field redaction, not reliable removal of secrets from free text; adding a blacklist is unnecessary and cannot meet this property.

The smallest correction boundary is the existing adapter `_diagnostic` and its callers: retain canonical Wyrd code and safe public diagnostic fields; replace arbitrary fallback exception bodies with a static phase/classification diagnostic. Preserve the original application exception/failure where the adapter already propagates it. No new error catalog, sanitizer framework, dependency, or lifecycle owner is required. Do not classify every ImportError as a missing telemetry extra: the specific safe install guidance already belongs to `wyrd.otel._EXPORTER_EXTRA` (lines 199–202), used by `_start_telemetry` and exporter import guards. Reuse that established diagnostic for the known missing-extra condition; keep arbitrary ImportError bodies out. This preserves the explicitly required `pip install 'wyrd-ai[otel]'` remedy without treating arbitrary exception strings as safe.

Focused proof: unexpected startup/cleanup/drain exception bodies containing a synthetic token, DSN and newline do not enter adapter-generated messages/logs; a Wyrd refusal retains its code; actual missing-extra startup retains the established installation guidance; an application's explicit failure message remains its message and remains failed. No real-secret corpus or new server harness is needed for this adapter projection property.

## Pre-first-receive exception: standard compatibility is real; detection is ambiguous

Read the primary [ASGI lifespan specification](https://asgi.readthedocs.io/en/stable/specs/lifespan.html), Scope and Startup Failed sections. It defines exception-based compatibility for applications without lifespan, including exceptions when called with the lifespan scope or startup message. Deliberate startup refusal uses startup.failed. It supplies no exception type or separate capability marker distinguishing unsupported lifespan from broken application initialization. Consuming the first receive is likewise no standard capability negotiation.

The candidate's `pending` check (148–154) is a heuristic, not proof that an exception meant unsupported lifespan. INVREV-001 correctly demonstrates that a configuration error before first receive becomes startup.complete. However, the proposed universal correction also rejects the standard non-lifespan ASGI app (for example an HTTP-only callable that raises on the lifespan scope). REQ-021 explicitly supports wrapping any ASGI application, and the task-review skill requires standard/conventional behavior rather than additional protocol assumptions. A counterprobe using an arbitrary early exception cannot establish which of those intents the wrapped app has.

Accordingly, do **not** independently confirm INVREV-001's proposed bounded remediation to turn every pre-receive exception into startup.failed. It resolves one interpretation by removing compatibility behavior for another supported application. Preserve explicit application startup.failed/shutdown.failed as failures and the adapter's own state-startup failure signaling. The real app failure in INVREV-001 and an unsupported-lifespan app are indistinguishable at this boundary using the standard protocol. If the approved requirement is interpreted to demand rejection of *all* such exceptions despite standard unsupported-lifespan compatibility, that is an explicit product/compatibility policy decision to clarify, not an exception-type inference or new adapter option to invent during remediation. This follow-up finds no source-grounded way to require automatic reliable distinction.

This does not excuse the separately demonstrated missing drain on abnormal exit after startup.complete (BREV-001/INVREV-002); that established active lifecycle is a different state with an existing shutdown owner. It also does not claim that a post-receive exception is definitive proof of lifespan support: the standard's compatibility wording includes startup-message exceptions. Avoid expanding this follow-up into a new protocol redesign.
