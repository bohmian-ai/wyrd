## Material findings

### BREV-001 — INCORRECT: abnormal application lifespan shutdown bypasses the final Wyrd drain

- **Obligation:** REQ-023 and AC-014; task scenario 4 requires final drain after the application's shutdown, with failures preserved.
- **Location:** `sdks/wyrd-sdk-python/python/wyrd/integrations/asgi/_middleware.py:143–147` (producer of the skipped cleanup); terminal-message cleanup at lines 133–141 is the sibling path.
- **Reachable path:** a supported plain ASGI application consumes startup, sends `lifespan.startup.complete`, consumes shutdown, records final evidence, then raises instead of sending a terminal reply. `app_send` has already set `replied=True`, so the exception handler immediately rethrows. `_drain` never runs. Cancellation of an active lifespan likewise bypasses `except Exception` entirely. The public contract explicitly supports wrapping any ASGI application; it is not restricted to Starlette's exception-to-message conversion.
- **Evidence:** a read-only probe imported the actual candidate public middleware and used a minimal state counter. With the sequence above it returned `RuntimeError('application shutdown failed')`, `started=True`, `closed=False`, and only the startup-complete message. The ordinary message-based failure tests cannot reach this branch. `PyWyrdState::shutdown` is the existing single owner that flushes telemetry then drains the writer; there is no later cleanup caller in this adapter.
- **Consequence:** a routine application shutdown exception strands queued evidence and active SDK resources until process exit, despite the middleware being the advertised owner of the final drain. Application failure may remain visible while the distinct drain is silently skipped.
- **Required correction:** keep existing `WyrdState.shutdown` as the lifecycle owner and ensure a successfully started middleware-owned lifecycle receives its final bounded off-loop drain on abnormal application lifespan exit as well as terminal messages. Preserve the primary application exception/cancellation and avoid double-draining already settled paths. Do not add another queue, resource supervisor, or durability promise.
- **Focused proof:** extend lifespan coverage with a plain ASGI app raising after consuming shutdown without sending a terminal message, and an interrupted active lifespan; assert the existing state is drained/closed and the original failure remains observable. Keep the existing final-application-evidence ordering assertion.

### BREV-002 — VIOLATION: startup diagnostics copy secret-bearing exception text without scrubbing

- **Obligation:** REQ-022 explicitly requires a scrubbed startup diagnostic with the Wyrd code when present; task preserves credential safety. `agent_docs/errors.md` disallows leaking raw transport/database/provider/filesystem strings into public payloads.
- **Location:** `_middleware.py:25–29`, used at lines 107, 115–116, 125 and 151; sibling wrapped-app failure messages are forwarded unchanged at lines 133–141.
- **Reachable path:** an application startup dependency raises an exception containing a DSN, authorization value, or other secret. A plain ASGI app that consumes startup then raises is formatted by `_diagnostic`; a FastAPI/Starlette startup failure already becomes a message containing its traceback and is forwarded by `app_send` without any sanitation.
- **Evidence:** a read-only candidate probe raised a RuntimeError containing a synthetic PostgreSQL password and bearer token. `lifespan.startup.failed.message` contained both verbatim, including a newline. `_diagnostic` performs only interpolation. The C5 application error assertion expressly checks that arbitrary exception text survives and supplies no secret-safety check. No existing Python redaction owner is reused here.
- **Consequence:** ASGI server logs and startup protocol consumers receive application credentials or dependency payloads from a new SDK diagnostic boundary. Scrubbing only `_diagnostic` would leave the wrapped-app message path exposed.
- **Required correction:** enforce safe diagnostic projection at the middleware's lifespan failure boundary for both locally constructed and forwarded failure messages. Retain safe Wyrd codes and actionable missing-extra installation guidance; do not publish arbitrary exception/traceback text or introduce a speculative blacklist scrubber. Keep the primary exception behavior required by the task.
- **Focused proof:** startup failures through both a raw ASGI exception and wrapped FastAPI failure message containing synthetic DSN/token material must send failure, preserve an applicable Wyrd code/actionable extra guidance, and disclose no synthetic secret through the forwarded message or middleware logs.
