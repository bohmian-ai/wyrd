## Proposed material findings

### INVREV-001 — INCORRECT: pre-receive application startup failures become successful startup

- Obligation: REQ-022/023 and AC-014 require wrapped application startup failure to remain failure, and partial started Wyrd resources to be cleaned.
- Location: `sdks/wyrd-sdk-python/python/wyrd/integrations/asgi/_middleware.py:153–162`.
- Producer-to-sink evidence: `_start` succeeds before calling the wrapped app. If the app raises before its first `receive` (for example, lazy middleware construction/configuration fails while building the app stack), `pending` still contains startup. The catch treats every such exception as unsupported lifespan, discards the error and sends `lifespan.startup.complete`. It later reports shutdown complete. No exception type establishes that startup succeeded or that the app intentionally lacks lifespan.
- Reachable consequence: a broken app is reported ready and can begin accepting requests; the primary startup error disappears. A source-loaded read-only probe wrapping a pure ASGI app whose first operation raises `RuntimeError('application configuration broke')` produced exactly startup.complete followed by shutdown.complete.
- Existing owners/siblings: the adjacent post-receive startup branch already drains and sends startup.failed; Starlette's explicit startup.failed path also drains. No state lifecycle change is necessary.
- Smallest testable correction: remove the invented success inference for arbitrary pre-receive failures; retain the primary app startup failure and use existing `_drain` cleanup. Add a startup-before-receive failure to the existing lifespan test, asserting failed signaling, no completion and closed state. Preserve normal wrapped-app lifespan and explicit failure replies. The published ASGI lifespan protocol explains why explicit startup.failed is needed to prevent servers from treating exceptions as unsupported lifespan: [ASGI lifespan protocol](https://asgi.readthedocs.io/en/stable/specs/lifespan.html). The Wyrd requirement is stronger than merely propagating an exception.

### INVREV-002 — MISSING: raw wrapped-app shutdown exceptions bypass the final state drain

- Obligation: REQ-023/AC-014 require final Wyrd shutdown after the application and preservation of application failures. Queue admission is not durability acknowledgement (existing Python/shared state shutdown docs).
- Location: `_middleware.py:143–147`, with terminal cleanup currently conditional on `app_send` at lines 133–141.
- Producer-to-sink evidence: app receives startup, sends startup.complete (`replied=True`), receives shutdown, performs final work, then raises without sending a terminal shutdown message. The handler immediately reraises because `replied` is true. `_drain` is never called. The SDK writer and managed provider are still owned by state; no other adapter path finalizes them. A pure ASGI app is an explicitly shipped supported surface, so reliance on Starlette translating exceptions into shutdown.failed is insufficient.
- Observable consequence: pending request/final application evidence is not drained, telemetry is not flushed, and the wrapper exits without shutdown.failed. In a read-only source-loaded probe, the state recorded startup but zero shutdown calls; replies contained only startup.complete and `RuntimeError('shutdown broke')` propagated.
- Existing owners/siblings: explicit app startup.failed/shutdown.complete/shutdown.failed use `_drain`; normal FastAPI lifespan error handling generally supplies a terminal reply. Direct wrapping and app middleware failures must reach that same existing shutdown owner too. No new queue, timeout policy, state lifecycle or worker supervisor is justified.
- Smallest testable correction: ensure every completed/exceptional wrapped lifespan exit after successful Wyrd start attempts the existing bounded state shutdown, while preventing duplicate drain/terminal replies on the existing explicit-message paths and preserving the primary app failure. At the pure-ASGI boundary, report the appropriate failed phase when the app has not already done so. Extend the existing lifespan test with a raw app shutdown exception after queueing final evidence; assert final drain is attempted, failure stays failure and the loop remains responsive. Do not change hard-kill/expired-timeout delivery guarantees.
