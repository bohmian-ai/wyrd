## Proposed finding SEC-001 — unrelated saved deployment is detected only after issuing an unsavable tenant key

- Classification: **INCORRECT**.
- Violated obligation: spec REQ-002 requires an unrelated saved deployment/tenant to be refused with WYRD_CONFIG_HOME guidance rather than overwritten/adopted; REQ-008 requires preflight protected persistence before credential issuance and retaining a newly issued key whenever possible. INV-004 requires honest identity/persistence across partial setup.
- Changed location: `crates/wyrd/wyrd-cli/src/server/dev.rs:295–317` (`DevArgs::resolve`), with the reachable consequence at `DevServer::run` lines 508–511 and `save_tenant`; existing final refusal in `crates/shared/wyrd-client/src/global_config.rs:229–236`.
- Producer/state: use a normal existing user configuration for another server: `[client].http_url = "https://other.example"`, protected `[default].api_key` for that deployment, and no `[dev]` table. Supply complete local setup inputs for a fresh managed Postgres database. This is a supported client configuration, not a malformed or manually forged key.
- Evidence: `resolve` loads the default key but its only saved-tenant comparison is conditional on `saved_tenant` being Some. With no `[dev]`, it passes. `validate_saved_login` consults the requested local origin only, so it does not identify the unrelated configured remote origin/default key. The differing `[client].http_url` only sets `configured = false`; it does not refuse. `run` starts/migrates, `save_settings` writes the new `[dev]` settings and database URLs, and `provision` issues the local tenant's one-time admin key. `ProvisionedTenant::credential` chooses that newly issued key and accepts its prefix. `GlobalConfig::save_local` then correctly refuses replacing the unrelated default key. The new key is dropped on the error; no local owner has persisted it.
- Observable consequence: a deterministic preflight conflict causes durable tenant provisioning followed by loss of its one-time administrative key, requiring authorized recovery before the new deployment is usable. The previous configuration also acquires local `[dev]`/database settings despite the required unrelated-deployment refusal. In the variant with an unrelated selected HTTP endpoint but no default key, setup proceeds and replaces the selected client endpoints rather than refusing.
- Existing owner/sibling paths: `GlobalConfig::save_local` already owns the final no-key-replacement guarantee and must retain it. `CredentialsFile` owns safe persistence; `SavedLogins::select` owns login selection. `DevArgs::resolve` is the one preflight owner used by installed CLI projections and should prevent this known unrelated-deployment state before `DevServer::run`. Do not add a second issuance/recovery mechanism or relax the existing key-conflict check.
- Smallest testable correction: complete the local-setup identity preflight using the already loaded selected client endpoint, saved development selection, and existing protected key/login owners. Refuse a positively unrelated saved deployment with WYRD_CONFIG_HOME guidance before local settings writes, migration or provisioning. Preserve legitimate existing local setup, normal restart and explicit corresponding-setting overrides; retain `save_local`'s final conflict check for races. Do not automatically replace the unrelated key or rotate the new tenant as recovery from this avoidable condition.
- Focused closure proof: extend the installed CLI local-dev test with an unrelated existing selected endpoint and protected default key but no `[dev]`, then run complete unattended local setup. Assert early refusal/guidance, byte-preserved credentials/configuration, and no new root/tenant provisioning in the fresh database. Cover the no-default-key selected-endpoint variant without overwriting endpoints. Keep the ordinary restart and partial-failure assertions. This needs the existing CLI/Postgres harness, not a new harness.
