## Proposed findings

### SYS-001 — INCORRECT: local setup falsely guarantees rollback after an uncertain apply result

- **Obligation:** REQ-006 explicitly allows lost response after commit and forbids claiming failure proves nothing committed; INV-004 requires honest persistence and failure reporting.
- **Location:** `crates/wyrd/wyrd-cli/src/server/dev.rs:1059–1063`, `DevInputs::configure_gateway`.
- **Producer → consumer evidence:** HTTP/MCP use `GatewayAdministration::apply_deployments`; it commits at `service.rs:386`, then constructs/returns the response. `CredentialWriter::send` uses shared `http.request_json`, which can fail on response transport or decoding after commit. `apply_deployments_with` passes that error through. Every such error reaches unconditional `"Gateway setup failed and nothing was applied"`. CredentialWriter's own new rustdoc already acknowledges lost-response uncertainty. The other CLI caller (`deployment put`) returns the shared error and does not make this no-commit assertion.
- **Reachable consequence:** a transient response disconnect or malformed/truncated response after successful commit makes the user believe credentials/deployments stayed unchanged, even when an existing credential has rotated. CLI then stops its owned server and tells the user that skipping gateway is an alternative. This is misleading recovery guidance for persistent state, not merely wording preference.
- **Smallest correction:** remove the blanket rollback assertion at this local reporting boundary and describe uncertain completion with existing list/reapply guidance. Preserve transaction owner, named-upsert convergence, original typed error, existing server settlement, and tenant setup. Do not add receipt state, automatic compensating rollback, a new retry protocol, or infer failure from a later failed read.
- **Focused closure proof:** exercise the CLI-facing apply-error path with a response lost after the real operation commits; assert unsuccessful setup and owned-child settlement, confirm committed resources remain readable after restart, and assert output says completion may have committed and supports inspection/safe reapply. Existing local HTTP/provider fixtures and named upserts suffice; no paid call is required.

### SYS-002 — INCORRECT: initial concealed-input interruption bypasses terminal restoration

- **Obligation:** REQ-001 adds usable concealed terminal input; REQ-003/AC-007 require controlled interruption during startup. Terminal's new contract explicitly says cancellation restores saved terminal attributes.
- **Location:** `crates/wyrd/wyrd-cli/src/server/dev.rs:131–135` (supervision starts after `resolve`); `terminal.rs:90–97` (echo disabled while awaiting answer), `terminal.rs:28–32` (restoration only on Drop).
- **Producer → consumer evidence:** native `main.rs` and shared `run_cli_code` install no signal handler. `DevArgs::run` first awaits `resolve`; the missing database branch awaits `Terminal::conceal` at `dev.rs:251–254`. `interruption()` is only created after resolution and is first polled by the later installer select. While waiting at the first hidden prompt, SIGINT/SIGTERM therefore use default process termination rather than cancelling the input future. Rust destructors do not run on that termination, so `EchoGuard` cannot restore the saved termios state. Later gateway/host prompts do have signal observation and do not share this defect.
- **Reachable consequence:** an ordinary Ctrl-C or TERM at the initial hidden database prompt exits without restoring the invoking PTY's echo state or the command's controlled interruption path. In a direct terminal/PTY consumer, subsequent typing remains hidden unless an outer controller happens to repair the terminal; the CLI must not rely on that repair.
- **Smallest correction:** extend the existing single interruption/cancellation boundary to include input resolution, before concealed input may disable echo. Reuse `interruption` and Terminal/EchoGuard; ensure cancellation drops the pending input and restores attributes, while retaining incomplete unattended-input behavior and no server-side setup effects. No new signal subsystem or terminal abstraction is needed.
- **Focused closure proof:** use the existing real-terminal Python journey harness, wait for the hidden DSN prompt with missing database input, send INT (and TERM as supported by the existing interruption owner), then assert controlled exit, restored PTY termios attributes, no leaked DSN, and no migration/provisioning/key issuance. This needs no database mutation or install download.
