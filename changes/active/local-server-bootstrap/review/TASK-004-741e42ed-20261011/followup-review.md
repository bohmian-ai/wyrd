## Source path and prerequisites

1. `wyrd-cli/src/server/dev.rs:193–205` successfully binds and retains the requested loopback HTTP address through memory detection and migration. An already-occupied address fails before setup. It then drops the reservation and launches the installed serving child.
2. `wyrd-server/src/app/mod.rs:78–88` awaits `build_state` before constructing and serving `WyrdServer`. `boot/mod.rs:516–534` and `:1331–1416` show actual database, storage, Bifrost composition/reconciliation, federation, secret rewrapping, and operator-key checks before binding. These are genuine asynchronous boot work. An alive child therefore does not prove that it has bound HTTP.
3. `wyrd-cli/src/server/dev.rs:335–347` checks child exit and accepts a successful HTTP `/readyz` response. It does not establish which process answered. `wyrd-server/src/app/server.rs:283–295` binds HTTP itself and refuses a competing listener. `http/router.rs:43` explicitly leaves health/readiness unprotected, consistently with their existing operational role.
4. `wyrd-cli/src/server/dev.rs:269–286` invokes the installed `setup` against that HTTP origin. `wyrd-server/src/main.rs:261–278` first reads the actual external database and returns immediately for an already-active tenant. Thus an ordinary retry for the active tenant does **not** exchange the platform root at this step.
5. For first use, or another absent tenant with an existing root credential supplied, `main.rs:280–298` obtains the root and constructs the existing shared platform client. `boot/init.rs:119–170` writes the generated root's hash and grants and commits only after its captured disclosure succeeds. `platform/handle.rs:79–99` calls `TokenExchange::platform_session`; `auth.rs:309–325` and `:478–505` send the credential as a form-encoded `subject_token`. No database access by the responding HTTP peer is required merely to receive that request. Existing root without `WYRD_PLATFORM_CREDENTIAL` fails before the exchange.

The discovery's confidentiality scenario is therefore possible at the source level **if** another local process wins the released port while the genuine child is still booting, supplies a successful `/readyz`, and receives the later exchange before the genuine child exits or the startup is cancelled. The bootstrap need not announce success for that hypothetical recipient to obtain the root. Another tenant's saved file and successful later authentication do not close this hypothetical path. There is no evidence that this exploit was executed.

## Local failure versus hostile local impersonation

The ordinary supported conflict is an already-running listener: the reservation rejects it before migrations and provisioning. A listener that starts during the release-to-bind interval makes the genuine server's bind fail; startup observes child exit, or setup against an unrelated service fails. The existing command then settles its child and reports redacted partial-progress recovery. Committed root initialization before a later setup failure is an expressly supported partial-progress case (REQ-010). These paths do not independently establish an authentication bypass, tenant credential replacement, or successful deployment to the wrong server.

To turn the interval into SEC-001's administrative credential theft, the claim introduces a hostile local actor deliberately claiming the selected address, impersonating readiness, and collecting the token-exchange body. The task and its loopback/plaintext development topology do not specify hostile co-users as a bootstrap acceptance case. No actual ordinary local conflict, trace, or existing fixture demonstrates that claimed confidentiality failure. Treating the source-level possibility alone as a mandatory remediation would add hostile-host transport assurance to this local command.

`architecture/wyrd-security-posture.md:14–15` governs authentication/authorization at receiving boundaries; it does not prescribe subprocess socket attestation. Actual Wyrd token and permission checks remain authoritative. `architecture/operations/deployment-and-release.md`, “Network and TLS boundaries,” explicitly allows loopback development plaintext, and spec INV-003 excludes **remote** plaintext. Those rules do not make an unauthenticated readiness response a verified server identity, but they also do not supply an approved requirement for a new local process-identity protocol. The security posture's closing guidance says standards alignment does not substitute for deployment-specific threat modeling. The user's scope clarification resolves that missing context toward ordinary local development.

## Existing owner and correction assessment

`WyrdServer::bind` owns listener creation; `BoundServer` owns the bound listener and passes it directly into the supervised serving transport (`app/server.rs:689–695`). In-process tests use that existing ownership without rebinding. The CLI owns installed-child lifetime and the temporary preflight reservation. A repository search found no socket-activation environment, inherited-listener import, cross-process listener handoff, or authenticated startup acknowledgment available for this installed binary contract.

Holding a duplicate pre-bound socket across the CLI/server process boundary could address the initial substitution interval, including preventing another process from taking the address when the child dies. It would require new inherited-descriptor acceptance and lifetime behavior in the installed server and compatibility handling in the CLI. It is not a current helper to reuse. A new readiness nonce, PID response, extra liveness check, sleep, or success-body parser would either add a protocol or leave check/use windows. Moving tenant creation into the CLI or bypassing the authenticated platform API would violate server authority and the existing authorization/audit workflow.

No such machinery is warranted as TASK-004 remediation on the evidence and clarified deployment scope. If hostile local co-user resistance becomes an explicit product requirement, that needs an approved threat/resource-ownership decision first; this review should not prescribe it implicitly or return `SPEC_REVISION_REQUIRED` merely to introduce it. The existing scope can be assessed without that expansion.
