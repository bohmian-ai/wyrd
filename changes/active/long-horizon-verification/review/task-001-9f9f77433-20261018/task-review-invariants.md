## Proposed findings

### INV-R4-01 — INCORRECT — a replayed source execution becomes new group activity

**Obligation:** REQ-001 idempotent enqueue/replay and REQ-004 deduplicated execution/result identities; AC-001 judges the whole group once and replay counts once. Source executions, not duplicate physical copies, determine activity and coverage.

**Location:** `crates/wyrd/wyrd-server/src/verification/groups.rs:512–547,600–617`; production chain at `components/verification/service.rs:610–647`, `verification/results.rs:293–354`, `scribe_outbox.rs:827–837`; sink `wyrd-sql/src/queries/verifier_executions.rs:995–1007`.

**Producer → sink proof:** A keyed enqueue derives the same execution ID from the same canonical request. Each invocation nevertheless creates a fresh `now` and writes it as `recorded_at` in its input row before background acceptance replays the existing execution. ScribeSink hashes the Arrow IPC, including recorded_at, so a later invocation is a distinct batch even though execution identity is the same. Bifrost identity is batch-level, not an execution_id upsert; its managed ingest timestamp is new. Existing queue acceptance correctly avoids running the source twice, but cannot remove the already-acknowledged analytical duplicate.

Sources::decode keeps each physical row in `read.rows`; only payload choice and `members` deduplicate. Ended::judge calculates `through` and idle from the maximum of every physical row's ingest time. A later duplicate input therefore changes through with unchanged members and unchanged selected values. GroupState::covers fails its time comparison, and the poll enqueues a new whole review after the first has settled. The existing serial fence prevents simultaneous reviews, not this successive duplicate. Before settlement a replay can also postpone idle. All input slots and outcome slots share these row times; no sibling layer repairs the classification.

**Reachable consequence:** after a completed review, retrying the same keyed turn within finality causes another review/provider call of unchanged evidence; repeated retries postpone idle. This violates group replay/nonduplication even though the source queue execution itself replays correctly. Current replay stories stage both copies before first review, so they do not establish this boundary. Current unit duplicates have identical timestamps.

**Smallest correction:** keep logical deduplication in the existing Sources/Ended source-row owner, and make first/newest/end/coverage consume the same canonical identity activity used by list ordering and member counting. Duplicate input rows of one execution must retain its original activity time rather than the latest copy; similarly preserve result identity semantics. Do not change the public managed timestamp, producers, queue/Scribe durability or introduce a receipt. The existing earliest-row payload/list selection already supplies the intended canonicalization direction; reuse it rather than adding a consumer guard in queue/runner/SDK. Preserve same-statement membership/payload and the payload ceiling.

**Focused closure:** a real grouped keyed submission → first review settles → replay exactly that submission later under PostgreSQL-managed ingest time → source execution unchanged and no second review after idle, with snapshot IDs/values/history unchanged. A focused Ended/decode test with duplicate identity at different times should also pin the canonical activity. A deliberate different execution remains new activity. No new harness/dependency or broad suite is required.

### INV-R4-02 — INCORRECT — not-yet-accepted queued input is treated as direct evidence

**Obligation:** REQ-001/005 source eligibility and idempotency-conflict exclusion, REQ-009 capacity over eligible executions, immutable judgments under INV-004. A conflicting submission that never executes cannot become source evidence.

**Location:** `verification/groups.rs:141–144,430–477`; `wyrd-sql/src/queries/verifier_executions.rs:250–258,1693–1733`; producer/handoff at `components/verification/service.rs:610–647`, `verification/results.rs:293–354`, `scribe_outbox.rs:892–929`, `verification/submissions.rs:88–126`.

**Producer → sink proof:** enqueue records `queue_execution=true` on the input row. ScribeSink submits/acknowledges that row first and only afterward stages its Submission on the separate asynchronous SubmissionOutbox. SubmissionSink later opens a Postgres transaction and calls accept_submissions, which decides conflict/refusal and commits. The input can thus be visible while that transaction is pending, backed off after failure, or absent after handoff loss. This is the existing explicitly accepted handoff topology, not hypothetical external corruption.

GroupPoller reads group_submissions before its Bifrost statement. Only committed queue rows appear; the queued source in this gap appears in neither refused nor selected. Sources::surfaces drops the existing queue_execution marker. Sources::read excludes known refused IDs but retains every unknown input and treats a missing queue entry as direct authority. A group already max_age-due (or idle beyond the small configured duration during handoff retry) can pin that input before accept() settles it as an idempotency conflict. The query and queue transaction need not fail. A competing/paused handoff produces the same gap even without an outage.

Once refusal commits, later reads correctly remove the row. That does not repair the immutable bad snapshot. Moreover, if a valid group's earlier review counted that extra row, removal lowers members and does not increase through; covers can suppress a corrected whole snapshot indefinitely until unrelated new activity. The same prematurely admitted ID can falsely trip the source-execution ceiling. The current refused-at-ceiling and refused-first-finality tests call Support::turn, which waits for an execution row, so they cover settled refusals only.

**Reachable consequence:** a rejected conflicting turn can affect an immutable group verdict or turn a valid at-ceiling group inconclusive, despite never executing. Correct later refusal does not retract it. Queue claims/unique group fence and result-selection logic do not close input-acceptance authority.

**Smallest correction:** reuse the existing input `queue_execution` discriminator and the existing queue acceptance classification in GroupPoller/Sources. A submitted input with no accepted queue identity must not be produced as eligible direct evidence; a genuinely direct input remains eligible without a queue row. Do this before capacity, timing, payload membership and coverage, preserving the one Bifrost statement and no producer lookup/write. Reuse the selected/refused group map rather than inventing pending-turn state, waiting for terminal outcomes, adding a queue or durable inventory. Missing result values for an accepted running source remain null as approved. The correction is at the source owner, not downstream rollback/SDK/evaluator guards.

**Focused closure:** with the existing bound-server/queue seam, make a queue_execution=true input visible while its submission has no queue row, alongside a real due group. Poll must not list/count/read it or falsely overflow. Commit its existing conflict/refusal without republishing, and the next snapshot remains clean. Also prove that subsequently accepted pending/running submission inputs join without waiting for result terminality, and direct queue_execution=false input still joins immediately. Existing ResultPayloadBuilder plus accept_submissions can express the state without live commit fault injection or a new public control.
