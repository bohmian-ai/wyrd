## Proposed findings

### DC-001 — INCORRECT: discovery excludes uncovered retained evidence before source coverage is checked

**Violated obligations:** REQ-003/004: arrivals while a review is outstanding coalesce into the next whole-group snapshot after settlement; a late-visible row within finality remains discoverable; failed discovery remains retryable. AC-006 explicitly requires publication lag, retry/restart and uncovered-source coverage.

**Locations:** `crates/wyrd/wyrd-server/src/verification/groups.rs:217`–`240` (`candidates`); `:53`–`57` (hard slack), `:158`–`175` (downstream coverage); existing correct comparison `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:992`.

**Evidence and reachable consequence:** Discovery joins group results and admits a candidate only if `MAX(source.at) > MAX(group_result.ended_at)`. Result completion time does not identify the source snapshot. Start a review from E1; while it is pending/running, record E2; then let the review complete. If E2's source timestamps precede review completion, subsequent discovery rejects the group even though E2 is absent from the pinned snapshot. The durable `GroupState` would detect increased source count/through, but it is never called. The same loss occurs for a source row flushed late with an older activity timestamp. No later judgment or verdict-change reaction occurs unless an unrelated newer source row happens to arrive.

There are two related discovery-completeness failures at this same selection boundary. First, the fixed `clock - idle - 1h` lower bound permanently hides an unjudged retained group after a scheduler outage longer than that window. This is explicitly admitted by the source comment, but no approved requirement authorizes an additional one-hour evidence lifetime. Second, `ORDER BY newest ... LIMIT 64` restarts at the same first page every poll. Sixty-four groups with post-finality activity newer than their last review repeatedly qualify for discovery, then fail the existing eligible-coverage check; a later eligible group cannot enter the page. No pagination/progress mechanism advances past them. These are source selection problems, not missing downstream guards.

**Required correction outcome:** Keep discovery bounded while ensuring retained uncovered groups reach the existing queue coverage check and are eventually examined. Compare selected source coverage, not review wall-clock completion, and do not introduce an unapproved retention horizon. Extend the existing binding discovery/queue mechanism so covered, post-finality or otherwise ineligible first-page groups cannot indefinitely monopolize it. Preserve one outstanding execution, immutable snapshots, exact tuple isolation, no producer Postgres IO, and no lifecycle/revision table. Do not merely widen the one-hour constant or add a sleep/retry at the consumer.

**Focused closure proof:** Hold a group review outstanding, add another eligible source before that review's completion timestamp, settle and flush the review, and verify exactly one subsequent immutable whole-group snapshot containing the new source. Independently flush an older-timed eligible source after the review and prove it is not falsely covered. With a backdated retained source and due binding cursor, prove restart/discovery still reviews it beyond the current slack. Exercise a candidate page occupied by already-covered/post-finality groups and prove a subsequent due group makes progress with bounded reads. These are normal-volume deterministic fixtures, not synthetic host load.

### DC-002 — INCORRECT: the source-execution ceiling does not bound which payloads are fetched, and a second row cap can suppress the required result

**Violated obligations:** REQ-006/009 and TASK-001 scenario 4: detect the distinct source-execution ceiling before payload collection, read nothing for an over-limit reference, and produce an explicit `inconclusive/source_execution_limit_exceeded` result rather than judge truncation or silently skip.

**Locations:** `crates/wyrd/wyrd-server/src/verification/groups.rs:159`–`162`, `:263`–`273`, `:293`–`308`, `:376`–`404` and the analogous results loop `:409`–`438`.

**Evidence and reachable consequence:** `snapshot` correctly builds `readable` from tuples within the ceiling, but `payloads` does not place those execution IDs in SQL. Both payload statements read every eligible tuple of the group up to 100001 rows; `readable.contains` filters only after full Arrow payloads have been transferred into API memory. For a declared group with source A above the ceiling and source B below it, B makes `readable` nonempty and A's payloads are fetched anyway. This defeats the explicit per-reference no-read bound even though evaluation later returns inconclusive. It also unnecessarily reads refused submissions and later arrivals outside the pinned identity set.

Separately, identities are limited and counted as raw input/result rows before deduplication or source-ceiling evaluation. A group exceeding 100000 physical rows is logged and skipped forever while those rows remain, rather than receiving the specified over-ceiling result. For example, 50001 completed executions produce at least 100002 ordinary input/result rows; at the configured ceiling 20 they should produce the explicit inconclusive judgment. Duplicate physical rows can also trigger this unrelated cutoff without increasing distinct source executions. This extra raw-row rule has observable result-loss behavior and is not the approved source-execution ceiling.

The payload SQL also treats reaching its LIMIT as ordinary complete success: it never checks a sentinel count. New rows/overlapping physical rows visible between the identity and payload queries can fill that limit before all selected payloads are returned; missing selected values become null and are pinned as a complete snapshot. `ScheduledQueryCaller` correctly validates stream completeness, but cannot distinguish a complete SQL LIMIT result from an application-truncated selection.

**Required correction outcome:** Make the existing source selection owner enforce the bound on distinct eligible execution identities for each resolved tuple before payload reads, preserving finality and refused-submission exclusion. Fetch only payloads for the pinned readable IDs through existing Bifrost query machinery. An over-ceiling tuple must not cause payload reads for itself; it must reach the existing explicit ceiling outcome. Remove the unrelated silent raw-row skip or replace its effect with bounded distinct selection that preserves the approved result. Any limit that cannot establish complete selected coverage must defer/retry without enqueueing a partial judgment. Preserve aligned null semantics for genuinely absent results, queued authoritative result selection and deterministic ordering.

**Focused closure proof:** One group with two declared source tuples, one over ceiling and one below, must produce the explicit inconclusive result while query evidence proves the over-limit source payloads were never fetched. Cover both input and outcome sources. Duplicate physical rows must not consume distinct-source capacity; a large logical group must not disappear behind a raw-row cutoff. Force a payload-limit/incomplete-selection path and verify no partial judgment is enqueued, then retry successfully using the same existing terminal-safe query boundary. Prefer narrow source-selection/SQL integration proof plus the focused existing journey over a new harness or broad suite.
