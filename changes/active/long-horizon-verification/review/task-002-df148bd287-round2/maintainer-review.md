## Ownership and reuse comparison

The only new production helper is `decode<T>` beside the existing kind dispatcher. It operates solely on its supplied JSON value and retains no state, so a concrete service or utility struct would add no owner. The existing dispatcher already serves Card deserialization and `Spec::from_kind_and_value`; extending it gives both paths the same refusal message instead of adding a removed-field scan to loaders and server handlers. Its dependency is the already resolved serde path decoder, not a new validation engine.

The remaining production changes predominantly delete a second representation: `ScheduledInput`, `validate_schedule`, projected binding inputs, claim `schedule_inputs`, and the runner's optional-slot filter. Existing `EffectiveSpecs`, `BindingProjector`, SQL projection/claim owners and `DriftEngine` continue to perform their complete workflows. No competing graph store, traversal, cache, transport, registry loader or lifecycle owner was introduced.
