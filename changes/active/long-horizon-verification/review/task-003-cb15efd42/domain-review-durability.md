### Why the sentinel is an observation barrier here

Each replay source send completes before its response, and the sequential sentinel call sends later on the same process and tenant. OutboxWriter appends received items in order, permits only one write per tenant, and retries failed slices before that tenant's later waiting work. After successful slice processing ScribeSink iterates original items in order to spend their downstream reservations. SubmissionOutbox uses that same ordering owner, and SQL accepts the batch in order before one commit. Thus visibility of the distinct sentinel means the preceding replay has been processed in that transaction or an earlier committed transaction. Waiting for the recovered ID would not provide this proof because its older row already exists. `flush_bifrost` alone only settles the source outbox and is not a submission SQL barrier.

Capacity 3 has two reservable Scribe slots. The pre-replay source flush leaves capacity for replay plus sentinel, while audit uses the separate unreserved share. Each enqueue already holds its downstream slot. The test releases its only injected stall, uses valid small inline inputs and the existing registered table, keeps both writers alive through sentinel observation, and injects no subsequent terminal refusal. This proves healthy post-drain replay processing without claiming delivery through terminal encoding/rejection, abrupt process death or deadline expiry. The `(3,1)` source assertion remains before accepted replay, so it does not impose source-row deduplication on an accepted replay.
