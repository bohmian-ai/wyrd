## Caller-to-result falsification and reuse assessment

**Refused ordinary invocation.** Authorization and its audit still happen first. Direct verification then reserves both source writes. A full reserved share returns the stable retryable error before resolving/running/staging the source; an error after reservation drops unused capacity. Enqueue constructs its existing deterministic Submission/input payload, then reserves downstream and source. If either is full, no source send occurs, and RAII releases any earlier downstream reservation. A refusal's separate authorization audit is not a forbidden source row. No language-specific admission mechanism or durable lookup was introduced.

**Successful enqueue under slow Scribe or Postgres.** The source reservation remains charged through queue, wait, retry and actual Scribe write. The downstream reservation is already carried inside the write, so a successful source ACK cannot discover an unbounded or full handoff. Scribe excludes terminally lost input items and spends surviving reservations in original item order. SubmissionSink commits the existing ordered accept_submissions transaction with TenantConn. Existing RequestKey/SQL acceptance handles equal request replay and conflicting keys. No new replay algorithm is needed. A bounded Tokio channel alone would release ownership too early; the added Admission/Reservation state is justified by the task's whole-pending invariant and reuses the existing writer.

**R2 replay observation.** A response alone cannot order a later queue SELECT after ACK/SQL acceptance. The new sentinel fixes that at the existing test caller: sequential HTTP sends establish source order; generic Outbox receives/appends FIFO and allows one in-flight tenant slice, preferring a failed old slice; Scribe hands surviving submissions off in item order; the same generic downstream owner serializes their tenant; SQL processes the slice in order and commits once. Observing the new sentinel through visible_execution therefore follows healthy processing of the earlier replay. It cannot be satisfied by the recovered ID's old row. The new durable count four has a concrete population: two fill executions, recovered identity and sentinel. The source-input count remains before accepted replay, so it does not incorrectly demand deduplication of retained inputs for distinct accepted sends.

This ordering proof relies on the actual healthy post-drain path exercised: the stall is released, the valid fixture remains present, both writers stay alive, and no subsequent terminal failure is injected. It adds no receipt or guarantee that a terminally rejected/lost source row must become a durable execution.

**Result and audit siblings.** The queued runner reserves one result slot before engine execution and defers without attempt consumption when full. Fenced completion stages it once only when the lease transition applies. A stale lease drops the unused slot; retry/terminal paths drop it as well. Audit, span and capture stay on unreserved stage with finite overflow count/log semantics. ClaimLoop's added cap bounds retained tasks, which hosted execution-step permits did not bound. Operator's existing permit owner is preserved. No duplicate scheduler or queue was added.

**Continued offered traffic.** Each language story starts B's completion wait, then drives normal A submissions before checking whether that wait finished, and preserves held A work throughout. Repeated normal A work uses at most one slot, leaving the declared resource-qualified progress path. All offers are reconciled. The stories do not establish an arbitrary-load fairness or throughput guarantee, and neither task nor this review claims one.
