## Material proposed finding

### SYS-001 — Required slow-group/cron availability proof does not exercise cron work or production loop wiring

- **Classification:** MISSING; important verification gap.
- **Obligation:** REQ-004 requires ordinary cron scheduling and group preparation to run as separate loops so a slow group read cannot stall cron. TASK-003a locked decision 7, Scenario 2 and C13 specifically require proving ordinary cron work is scheduled while the group query is blocked, using actual invocations/state.
- **Exact changed location:** `crates/wyrd/wyrd-server/tests/integration/pg_verification_groups.rs:692–704`.
- **Producer → consumer evidence:** Support::start registers only `fixtures/cards/verify_in_real_time/support.yaml` (:91–111), whose two bindings are caller-driven turn-check and group_end conversation verification, with no scheduled binding. The test manually joins `batched.group_pass(&stop)` with `batched.pass(&stop)` (:693–701), then only asserts that the latter returned `Ok` (:703). It never invokes `VerificationScheduler::run`, whose new `tokio::join!(cron_loop, group_loop)` is the production mechanism (`scheduler.rs:136–137`), and never asserts that a cron occurrence became a durable execution. Existing C12 proves scheduled Drift separately, not this blocked-group seam.
- **Reachable consequence:** This test can remain green with an empty cron due list and with production run-loop wiring regressed back to sequential polling. The required availability boundary therefore has no focused regression proof despite the reported A11/C13 PASS. This is a proof defect, not a claim that the current separate-loop implementation is incorrect.
- **Smallest correction:** Extend the existing integration test to register and make due one ordinary scheduled binding, run the actual scheduler `run` owner, hold its group query through the existing schema-stall control, and observe the cron execution durably enqueued while the group is still blocked. Then cancel/join the owner and retain the assertion that the blocked group remains pending. Reuse the current server, Postgres, scheduling fixture/queue helpers and fault seam; no new framework, loop or capacity mechanism.
- **Focused closure proof:** Run C13's existing exact focused command under the managed Postgres wrapper. The assertion must fail if `run` serializes group preparation before cron scheduling. Keep C12 as already-existing separate scheduled-Drift evidence; no broad journey rerun is needed solely to close this test gap.
