## Findings

### INVREV-001 — INCORRECT: pending work is consumed without a successful execution handoff

- **Obligation:** revision-17 REQ-004; original task locked decision 7 and A11. A successful enqueue or identical-snapshot conflict consumes pending work; failures retain it. `architecture/wyrd-design.md:1300` likewise says the transaction enqueues the ordinary execution and deletes its scheduling row, while failures roll back.
- **Location:** `crates/wyrd/wyrd-server/src/verification/scheduler.rs:361–388`, especially `None => None`, `Ok(outcome) => Some(outcome)` and the unconditional `consume_group`.
- **Producer → sink:** `ScribeSink::write` acknowledges evidence, `schedule_groups` calls `record_group_activity`, and its SQL creates the sole pending notification. `claim_due_group` derives `due.owner` through `binding_activity`; that gate returns no owner when the Service/principal is inactive or its last exchange is older than the default 86,400-second activity window. `hand_off_groups` then deletes and commits the pending notification even though no poll or enqueue occurred. The other path treats `EnqueueOutcome::Refused` from `enqueue_group` as successful handoff and also deletes the row, although that enum explicitly means nothing was created (`verifier_executions.rs:729–737`).
- **Reachable consequence:** use a valid `after: 2d`, acknowledge grouped evidence, and let the Service's authentication activity expire before the group becomes due. The first due pass deletes the notification without an execution. A subsequent Service exchange restores eligibility but does not recreate group pending work: `record_machine_authentication` now arms only `activation = 'schedule'` bindings. With no new source evidence, the acknowledged group is never handed off. No crash, query-visibility race, retention loss, or extra recovery guarantee is involved. An enqueue refusal likewise commits notification loss instead of retaining the existing work.
- **Sibling tracing:** ordinary cron work uses `schedule_due` and advances an occurrence cursor when inactive; later cron occurrences exist independently. That is not equivalent to deleting the only notification for a finite group. All grouped input/result writers share `ScribeSink::schedule_groups`; neither the runner nor authentication recreates consumed pending items. Query errors already return `Ok(None)` inside the preparation future, dropping the uncommitted connection and ending the tenant pass. This existing branch is the correction pattern to reuse.
- **Minimum correction:** consume only `Enqueued` and `AlreadyEnqueued`. If owner authority is unavailable or enqueue refuses, leave the transaction uncommitted and end that tenant's group pass. Do not run unauthorized work, add a recovery worker, add state, or scan historical groups. Correct the task appendix's implementation-owned decision to consume these items; it does not override the approved handoff contract.
- **Required proof:** in the existing server integration owner, expire an owner before a due handoff, assert no execution and the same pending item remains, renew its activity, and prove handoff then succeeds without new source evidence. Force an enqueue refusal and assert pending survives and no execution is created. Existing C13 does not exercise either branch.

### INVREV-002 — DRIFT / INCORRECT: an undocumented finite duration ceiling changes the declared Trigger

- **Obligation:** REQ-004, A1, and locked decisions 1–2: keep existing `TriggerDuration`, and compute `due_at = statement_timestamp() + binding.after`. No new authored limit or different duration is approved.
- **Location:** `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:191–210`, `GROUP_AFTER_MAX_SECONDS` and `LEAST(EXTRACT(EPOCH ...), $5)`; bound at `record_group_activity`.
- **Producer → sink:** `TriggerDuration::parse` accepts nine-digit positive counts in s/m/h/d (`crates/wyrd-spec/src/card/trigger.rs:100–124`). Registration preserves `after` in `GroupEndSettings`; every grouped input/result ACK enters the common SQL upsert. The new SQL silently substitutes 3,155,760,000 seconds for any larger authored duration. Claiming then observes that substituted due time, while inspection still reports the original Trigger.
- **Concrete consequence:** `after: 100000d` is valid and representable as a PostgreSQL future timestamp, but its pending item is due after roughly 36,525 days. Thus the mismatch is already observable by reading `due_at`; it does not require waiting a century. The clamp also turns the retained largest-duration `forever.yaml` case into the same finite duration. The comment's assumption that nobody waits longer is not authority to alter this contract.
- **Sibling tracing:** both input and result notifications use this one SQL owner; no SDK, registration validator, schema, or documentation declares this ceiling. `TriggerDuration` is also a shared contract and should not acquire a new arbitrary global cap merely to justify this SQL.
- **Minimum correction:** delete the arbitrary 100-year cap and preserve the authored duration for representable due dates. Handle dates beyond PostgreSQL's representable range using its native range/infinity behavior without silently replacing valid representable durations with an unrelated finite bound. Preserve the existing largest-duration no-expiration behavior; no new setting or ledger is necessary.
- **Required proof:** extend the existing SQL activity test with a representable duration above the cap, asserting `due_at - statement_timestamp()` matches its authored duration; retain a largest-duration case that schedules without overflow and does not become spuriously due.
