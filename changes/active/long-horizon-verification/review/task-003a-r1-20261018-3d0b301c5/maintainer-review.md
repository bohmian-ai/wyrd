## Existing-owner and machinery comparison

1. **Inline parsing.** The previous derived untagged decoder already owned all four authored forms but discarded inner errors. `TriggerDuration::parse` cannot repair a message discarded above it. The new implementation stays in `InlineableRef`, tries reference and sibling first, then the inline spec and string path. Its current instantiations are owned Prompt, Agent, Trigger and Operator specs; no current borrowed-spec caller was found whose lifetime contract requires the old generic bound. Buffering through installed `serde_json::Value` adds no dependency. Restoring derive would lose the required inline rejection diagnosis; adding a Trigger-only parallel parser would duplicate the owner. No deletion finding.
2. **Input slots.** `SourceText` deliberately accepts any string and defers grammar validation to the owning spec validator. Map/string dispatch preserves that split. The tagged remote mirror keeps serde's existing tag, defaults and unknown-field validation while avoiding the source fallback masking a typed-map error. It constructs existing variants, so it does not introduce another domain representation or validator. Schema generation remains attached to the canonical `InputSlot`; no new schema system. The changed decoder needs the documentation correction below, not another abstraction.
3. **Group handoff/read.** `VerificationScheduler` already owns polling cadence and accepting transactions; `GroupPoller` already owns source selection; `ScheduledQueryCaller` already owns authenticated query admission and stream settlement; `VerifierExecutionQueue` already owns durable queue transitions. The candidate extends these owners. `Reader` only collects successful statement batches, while `Sources`, `Visible` and `Payloads` express the required exact tuple selection, earliest logical-row deduplication and aligned values. They are not independent schedulers, SQL capability owners or public clients. Existing drift windows read different shapes and grant rules, so replacing the group selector with drift orchestration would not supply this outcome.
4. **Terminal recording.** Refusal uses the existing execution table/status/error projection, binding latest ID, and SYSTEM attribution. It does not synthesize accepted authority, evidence or an evaluation result. SQL writes remain caller-transaction-owned and only the scheduler decides consumption after a successful outcome. The extra handoff variant is a closed real outcome used by tracing/metrics and tests, not a one-implementation trait.
5. **Cross-runtime proof.** The existing Rust C1 owns the shared server, bundle, credentials and group. Local subprocess scripts add the two missing SDK contributors to that workflow. Separate parity journeys cannot replace that composition. A general subprocess harness, runtime interface or additional server would add maintenance cost; none was introduced.
