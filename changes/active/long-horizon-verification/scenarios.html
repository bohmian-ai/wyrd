Group verification scenarios

Four scenarios written as the Card YAML and SDK code a team would author, matching spec revision 12.  Highlighted  code is proposed; everything else is Wyrd today.

Three new primitives. Each one exists because the server does something with it.
PrimitiveThe user writesThe server uses it to
group_id= on verify / submitTheir own ID for the unit of work: a conversation, order, issue or detection event.Write it, plus the caller's owner Service card_uid (copied from the token, no lookup), into nullable columns on the existing execution_inputs and results rows. No Postgres write on the hot path.
Input verifiers.<name>.inputs.<slot> or verifiers.<name>.requirements.<id>.outcomeExactly which recorded data the group Verifier receives.At group end, read that Verifier's executions in the group, but only those recorded under its binding on the same Service. Each reference becomes an ordered list, one element per execution. Unbound and other-Service calls are filtered out.
Trigger kind: group_end with idle, max_age, finalityWhen a group counts as over.The existing scheduler polls the binding on its cursor and queries Bifrost. A group is due when its newest row is older than idle or its first row is older than max_age. New rows after a result make it due again (the next revision) until finality.

Two fixes ride along: an assert each over an empty list is inconclusive (today it passes), and a reference over more source executions than the deployment ceiling is inconclusive with source_execution_limit_exceeded. Group bindings react with on_verdict_change; the first result is the baseline.

Customer chatbot

A storefront assistant answers shoppers and can hand off to a human. Each turn is checked as it happens. Once the conversation goes quiet, the whole conversation is judged once.

turn-verifier.yaml (today's syntax)
apiVersion: wyrd/v1
kind: Verifier
metadata: {name: turn-verifier, version: 1.0.0, space: storefront}
spec:
  inputs:
    turn:  {type: json}
    trace: {type: trace}
  requirements:
    - id: on-topic
      statement: The reply stays on the shopper's order
      check: {kind: agent, agent: {ref: topic-judge@1.0.0}, inputs: {turn: inputs.turn}}
conversation-review.yaml
apiVersion: wyrd/v1
kind: Verifier
metadata: {name: conversation-review, version: 1.0.0, space: storefront}
spec:
  inputs:
    turns: verifiers.turn-verifier.inputs.turn                    # every turn, in order
    topic: verifiers.turn-verifier.requirements.on-topic.outcome  # every turn's verdict
  requirements:
    - id: resolved
      statement: The shopper's problem was resolved
      check: {kind: agent, agent: {ref: resolution-judge@1.0.0}, inputs: {turns: inputs.turns}}
    - id: every-turn-on-topic
      statement: No turn went off topic
      check: {kind: assert, each: inputs.topic[*], operator: eq, expected: passed}
storefront-chat.yaml (Service)
apiVersion: wyrd/v1
kind: Service
metadata: {name: storefront-chat, version: 1.0.0, space: storefront}
spec:
  components:
    - alias: agent
      ref: ./chat-agent.yaml
      verified_by:
        - verifier: ./turn-verifier.yaml            # run directly by verify/submit
        - verifier: ./conversation-review.yaml
          runs_on:
            kind: group_end
            idle: 30m
            max_age: 24h
            finality: 30d
          on_verdict_change:
            - ./notify-support-lead.yaml
chat backend (Python); the human console and order service pass the same group_id
run = state.run()
with run:
    reply, trace_id = agent.answer(message)
    run.for_card("agent").observe.verify(
        "turn-verifier",
        turn={"role": "assistant", "text": reply},
        trace=trace_id,
        group_id=f"{order_id}/chat",
    )
  1. Each turn's verify returns its on-topic verdict immediately.
  2. The shopper leaves and returns within 30 minutes. The console and the order service add turns with the same group_id. Nobody coordinates a Wyrd ID.
  3. 30 minutes after the newest row, the scheduler finds the group due and queues one conversation-review with every turn in recorded order.
  4. A direct verify of turn-verifier by a principal with no binding still runs, but its row is left out of turns.

Refund three days later

An agent promises a refund on day 0 and the group passes. On day 3 the payment service reports the refund never went out.

payment service, day 3
run.for_card("agent").observe.submit(
    "refund-turn",
    fact={"kind": "refund_overdue", "order": "456"},
    group_id="order-456/refund",
)
  1. Day 0: the group result R1 is passed. As the first result it is the baseline, so no Operator fires.
  2. Day 3: the new row arrives after R1 and within finality: 90d, so the group is due again. max_age has already passed, so it does not wait another idle.
  3. refund-review runs over all facts, old and new, and returns R2 failed. R1 stays as history.
  4. passed → failed dispatches on_verdict_change once. Another failed later dispatches nothing.

Coding agent

A coding agent works an issue: prompts, tool calls, edits, test runs and a final diff. The producer may not use tracing at all.

coding-review.yaml
spec:
  inputs:
    turns:     verifiers.coding-turn.inputs.turn
    secrets:   verifiers.coding-turn.requirements.no-secrets.outcome
    trace_ids: verifiers.coding-turn.inputs.trace     # recorded trace ids only
  requirements:
    - id: no-secrets-anywhere
      statement: No turn wrote a secret
      check: {kind: assert, each: inputs.secrets[*], operator: eq, expected: passed}
    - id: task-done
      statement: The issue is fixed and the tests pass
      check:
        kind: agent
        agent: {ref: task-judge@1.0.0}        # declares the bifrost.query tool
        inputs: {turns: inputs.turns, trace_ids: inputs.trace_ids}
  • Each turn is a verify or submit to coding-turn with group_id="issue-812/attempt-1". A secret written in one turn fails that turn right away.
  • A trace reference gives the group Verifier trace ids, never spans. The judge Agent reads spans itself with the existing bifrost.query tool when it needs them, under the caller's bifrost:query:read. Spans are read live, not frozen in the snapshot.
  • A test run still queued at max_age appears as null in its position. When its result lands within finality, the group is judged again.

Sampled frames from a detection system

The user's own system detects a person at door-42 and samples 20 frames. Wyrd does not detect, sample or receive video; it verifies what it is sent. This is fan-out: N ordinary calls sharing one group_id.

detector (Python)
camera = run.for_card("camera").observe
camera.verify("event-fact", event={"event_id": event_id, "detected": True}, group_id=event_id)
for frame in sampled_frames:                                   # the app picks how many
    camera.submit("frame-verifier", frame=verify.File(frame, filename="f.jpg"), group_id=event_id)
event-review.yaml
spec:
  inputs:
    outcomes: verifiers.frame-verifier.requirements.person-wearing-badge.outcome
    event:    verifiers.event-fact.inputs.event
  requirements:
    - id: badge-in-every-frame
      statement: The person wears a badge in every sampled frame
      check: {kind: assert, each: inputs.outcomes[*], operator: eq, expected: passed}
# bound with runs_on: {kind: group_end, idle: 2m, max_age: 30m, finality: 30d}
CaseResult
20 frames, all passpassed
One frame failsfailed; the failed frame stays in the list
Event sent, zero framesinconclusive, empty_selection
Worker dies mid-frameThe existing queue retries that one frame; the other 19 are not redone
Another Service sends frames with the same group_idExcluded
Ceiling set to 20, 21 frames arriveinconclusive, source_execution_limit_exceeded; never a judgment on the first 20

The event-fact call matters: with zero frames and no other row, there is nothing to discover, so no group exists.

What stays the same

  • verify runs now; submit queues. Neither gains a Postgres write. A drift submit still records a sample.
  • Anyone with verifier:run can still invoke any Verifier. Binding only decides what reaches a group Verifier.
  • Cross-conversation trends stay on today's drift Verifiers and schedule Triggers. Schedule bindings lose their duplicate inputs map; the Verifier's slots own the features.
  • No session Card, append verb, step-level fan-out, checkpoints, video segmentation or budget system.
  • Capacity: bench:capacity gains five cases and a target of p99 < 1 ms engine overhead for an assertion-only synchronous verify.
