## Proposed findings

### TASK-REV-001 — INCORRECT: a candidate can be stamped tested without proving its callback or client authentication

- **Violated obligation:** The packet-local contract requires `test` to validate discovery, issuer, callback, client authentication, and screened network behavior before stamping the exact revision. Scenario 2 requires unsafe or unsupported configuration to fail closed; REQ-004 and INV-004 require only validated provider configuration to become active.
- **Exact location:** `crates/wyrd/wyrd-auth/src/connections.rs:574-603` and `:606-659`.
- **Evidence:** `probe_callback` accepts every non-4xx/non-5xx response, including an arbitrary redirect whose location is unrelated to the configured callback. `probe_client_auth` rejects only HTTP 401, OAuth `invalid_client`, and `unauthorized_client`; it treats a 2xx, redirect, 404/non-JSON body, or any other OAuth error as proof that client authentication succeeded. `probe` then returns the JWKS URI and `test_candidate` stamps the revision. A syntactically valid discovery document can therefore point at screened but non-OIDC/static endpoints and still produce an activatable candidate. The Keycloak journey at `identity_e2e.rs:1855-1885` covers only Keycloak's explicit wrong-secret response and cannot falsify these accepted branches.
- **Observable consequence:** An administrator can receive a successful test stamp and activate a connection whose registered redirect or client credentials were never accepted by the provider; the first real login then fails. This defeats the task's safety gate rather than merely producing a less-helpful diagnostic.
- **Required testable correction:** Make both probes fail closed on responses that do not positively demonstrate the intended condition. Reuse the existing screened client and OIDC response parsing; accept only a narrowly defined authorization response that demonstrates the client/callback request was recognized and, for the token probe, the expected OAuth grant failure that occurs only after the configured client authentication was accepted. Add one focused provider-backed test where discovery/JWKS are valid but authorization or token endpoints return ambiguous responses (at minimum a redirect to an unrelated location and a 404/non-OAuth body); assert `CONNECTION_NOT_TESTED`, no test stamp, and activation refusal. Keep the existing wrong-secret journey green.

### TASK-REV-002 — INCORRECT: real login ignores the callback URL that administration displays and tests

- **Violated obligation:** The connection contract fixes the callback as configured public origin plus `/auth/callback`, read-only, and Scenario 2 requires the shown callback to match the deployed public origin. The tested connection must be the connection real login uses; request headers may not replace the deployment-controlled callback contract.
- **Exact location:** `crates/wyrd/wyrd-server/src/auth/login.rs:84-105` and `:126-140`.
- **Evidence:** After resolving the Active connection, `try_initiate_login` calls `callback_redirect_uri(headers)`, which constructs the OAuth `redirect_uri` from untrusted `Host` and `X-Forwarded-Proto`. The management owner instead derives and tests `HumanConnections.callback_url` from `WYRD_PUBLIC_ORIGIN`. Thus a connection may be shown and successfully tested with `https://public.example/auth/callback`, while a login request with another accepted Host or forwarded scheme asks the provider to redirect elsewhere. The journey hard-codes a Host equal to `PUBLIC_ORIGIN` (`identity_e2e.rs:1428-1433`), so it masks the split contract.
- **Observable consequence:** A correctly configured and successfully tested connection can fail at real login because Wyrd sends a different redirect URI. Where proxy/header policy admits variation, the provider-facing redirect is also request-controlled instead of deployment-controlled.
- **Required testable correction:** Use the existing deployment-derived callback owned by `HumanConnections` when preparing tenant login and remove the header-derived callback path for this flow. Add a focused server journey that configures/tests a connection under one public origin, initiates login with a differing Host and forwarded scheme, and asserts the emitted authorization request still carries exactly the configured callback. Keep tenant resolution behavior outside this correction unchanged.
