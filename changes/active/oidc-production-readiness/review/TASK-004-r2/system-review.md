## Recovery and proof assessment

- **Replica neutrality:** the device authorization, login binding, sealed completion, poll cadence, denial, and one-use redemption are durable Postgres state. A request may move between replicas as long as replicas share the configured keyring, signing configuration, and database, which the approved deployment contract already requires.
- **Dependency isolation:** IdP and Postgres failures refuse the affected login or renewal request. They do not disable existing access-token verification, API-key/workload exchange paths that do not need the failed IdP, or unrelated server components.
- **Cancellation:** CLI cancellation saves nothing and relies on the ordinary ten-minute device-code expiry. SDK request cancellation does not start a second refresh in the same process; the pending blocking mint remains joinable. The file lock is released by process exit or normal task completion.
- **Crash durability:** server-side one-use transitions are transactional. Local writes are atomic replacements. The one unavoidable uncertain window—server rotation succeeded but the local replacement did not—is explicitly accepted by revision 8 and safely contains reuse at the server, at the cost of requiring login again.
- **Lock contention:** the plain blocking OS lock is the approved standard mechanism. The candidate correctly removed the custom timeout/error/generation protocol rather than replacing it with another nonstandard coordination layer.
- **Revocation:** logout prioritizes eliminating the local reusable secret, then attempts the conventional best-effort server revoke. Failure is visible. Current access tokens retain only their existing bounded lifetime, and unrelated login chains remain intact.
- **No nonstandard resilience machinery:** no replica-local state, background device poller, custom recovery journal, tombstone, generation protocol, lock timeout, compatibility route, or separate credential file survives revision 8.
