## Persistence and failure-path trace

`PUT /platform/oidc/connection` authorizes first and opens the audited operator transaction, parses the issuer, then calls the process-owned `PlatformLogin::relying_party().discover` (`crates/wyrd/wyrd-server/src/components/platform/identity.rs:196-244`). `RelyingParty::discover` fetches standard discovery plus JWKS and inserts the resulting provider only after both succeed; a failure leaves the existing cache entry unchanged (`crates/shared/wyrd-auth-oidc/src/relying_party.rs:397-435`). The handler seals the secret, writes the singleton row through the same open decision, and commits once (`components/platform/identity.rs:246-282`; `wyrd-sql/src/queries/platform/identity.rs:76-124`). Thus a failed fetch or seal changes no durable row, and a failed write/commit cannot leak a candidate secret or make it authoritative. The preceding cache refresh contains only public provider metadata/JWKS keyed by issuer; begin still reloads the durable connection before selecting that issuer and client (`wyrd-auth/src/platform_login.rs:143-181`).

Platform removal and replacement remain database-authoritative. Every begin and complete reloads the singleton connection. An issuer-changing replacement invalidates an in-flight state by comparing the consumed state's issuer to the current connection (`platform_login.rs:261-285`); removal makes the connection unavailable. Process-local cache entries do not confer platform authority and are unreachable without a matching durable connection.

Tenant candidate testing uses fresh discovery, persists login state under the tenant connection, and only stamps the exact candidate revision after the real callback succeeds. Promotion re-checks the tested revision and recovery principal under the tenant slot lock before committing (`wyrd-auth/src/connections.rs:342-388,404-513,546-603`). The RLS-backed tenant boundary and the platform `OperatorPool` boundary remain distinct.

## Material finding

### PERSIST-TEN-R3-001 — DRIFT: persisted human JWKS TTL surfaces are inert after the shared relying-party migration

- **Violated obligation:** TASK-009 says operator-visible behavior does not change, replaces human verification with one small per-issuer cache, and prohibits a new cache setting. Standing human direction requires Wyrd to use the standard/conventional mechanism and classifies an extra setting or mechanism as DRIFT. A public or durable option must either govern behavior or not exist.
- **Exact location:** the effective cache lifetime is the fixed `PROVIDER_TTL` used by `RelyingParty::new` at `crates/shared/wyrd-auth-oidc/src/relying_party.rs:49-57,364-374`. The platform request/view still accept and report `jwks_ttl_secs` at `crates/wyrd-spec/src/auth/platform_identity.rs:37-78`; the handler and SQL still persist it at `crates/wyrd/wyrd-server/src/components/platform/identity.rs:262-281` and `crates/wyrd/wyrd-sql/src/queries/platform/identity.rs:21-44,59-124`; the original platform table retains the column at `crates/wyrd/wyrd-sql/migrations/20260601000023_platform_identity.sql:41-53`. The tenant human view, staging/inheritance logic, decoder, and table retain the sibling value at `crates/wyrd-spec/src/auth/human_connection.rs:116-155`, `crates/wyrd/wyrd-auth/src/connections.rs:235-300,786-815`, `crates/wyrd/wyrd-auth/src/pg_resolvers.rs:535-571`, and `crates/wyrd/wyrd-sql/migrations/20260925000000_auth_human_connections.sql:100-128,146-156`.
- **Evidence:** ordinary tenant login and callback call `HumanConnections`' single `RelyingParty::{cached,redeem}`; platform begin and complete call `PlatformLogin`'s single `RelyingParty::{cached,redeem}`. That cache is built once with `PROVIDER_TTL = 5 minutes` and has no per-entry TTL input. Neither path reads `TrustedIssuer::jwks_ttl` or `PlatformOidcConnectionRow::jwks_ttl_secs` when caching or refreshing provider metadata/JWKS. The platform API can therefore accept `jwks_ttl_secs = 1` (or another value), persist and echo it, while still caching for five minutes. Tenant views likewise describe a “JWKS key-cache lifetime” that does not control the human cache. The selected OIDC library and cited OIDC requirements require discovery and key verification, not this Wyrd-specific per-connection option; TASK-009 selected the one fixed process cache and explicitly rejected another cache setting.
- **Observable consequence:** operators receive a configuration/view that claims a cache lifetime which the running human login paths ignore. A provider metadata or key-set change may remain cached according to the fixed five-minute policy even when the durable platform value says otherwise, so the stored control-plane state and effective runtime behavior disagree. Persisting and inheriting the unused values also leaves a second apparent cache policy for maintainers to preserve even though there is only one real policy.
- **Required testable correction:** keep the conventional fixed, process-local `RelyingParty` cache selected by TASK-009 and delete the inert human-login TTL option/projections and their durable plumbing from the platform connection and tenant human-connection surfaces. Preserve the workload trusted-issuer TTL, which still belongs to and is consumed by `ExternalVerifier`/`JwksCache`. Add no per-entry cache policy, second cache, compatibility option, migration preflight, or permanent check.
- **Focused closure proof:** prove the platform configure request no longer accepts or returns a human `jwks_ttl_secs` field, the tenant human connection view no longer reports one, and the corresponding human-only SQL rows/writes no longer carry the unused value. Run the existing focused relying-party cache tests plus the narrowest contract/codegen, platform identity SQL, tenant human-connection, and served platform configure tests covering the changed write set. Full identity journeys and all-language sweeps remain final change-review evidence under standing direction and are not required for this remediation round.
