## Material findings

### MAINT-010-1 — The published endpoint requests omit their required OAuth client identification

- **Changed location:** `crates/wyrd/wyrd-server/src/components/auth/routes.rs:107-123`, `crates/wyrd/wyrd-server/src/auth/cli_login.rs:54-72`, `crates/wyrd/wyrd-server/src/auth/cli_login.rs:279-291`, `crates/wyrd-spec/src/auth/token.rs:1-19`, `crates/wyrd-spec/src/auth/device.rs:17-24`, and `crates/wyrd-spec/src/auth/device.rs:49-54`. The changed OpenAPI proof at `crates/wyrd/wyrd-server/tests/pg_openapi_contract.rs:284-339` checks only form media and the authorization-code variant.
- **Governing principle:** Wyrd's public HTTP contract must be sufficient through typed schemas and machine-readable documentation (`architecture/wyrd-design.md` client/server doctrine; `architecture/references/architecture/patterns.md` typed HTTP and generated-contract rules). The maintainer guide requires public parameter types and generated declarations to describe the same operation; prose cannot replace a missing field or authentication shape. TASK-010 requires RFC 6749 `client_secret_basic` for `wyrd-ui` and the `client_id` form parameter for `wyrd-cli`.
- **Evidence:** `TokenRequest` deliberately excludes client identification, and `DeviceAuthorizationRequest` and `TokenRevocationRequest` explicitly describe themselves as parameters *besides* client authentication. The handlers then read `client_id` from `OAuthForm` or HTTP Basic before decoding those types. Nevertheless, the three OpenAPI operations publish those partial types as the complete form request and clear security with `security(())`. The served document therefore exposes neither the accepted `client_id` parameter nor the standard HTTP Basic client-auth scheme. The existing global OpenAPI assertion at `pg_openapi_contract.rs:514-551` further treats any second scheme as an error, a premise that became stale when this task added OAuth client authentication.
- **Concrete maintenance cost:** A maintainer or generated client following the declared operation cannot discover or construct the request the handler requires for authorization-code redemption, device authorization, refresh, or revocation. A future change can keep `codegen:check` and the current OpenAPI test green while changing the real client-auth wire, because the generated contract owns only the grant-specific remainder. This is a public-contract consequence, not a placement or wording preference.
- **Smallest testable correction:** Keep the existing RFC 6749/7009/8628 behavior and registered clients, but make each affected OpenAPI operation describe its complete accepted form and standard client-auth alternatives: the `client_id` form parameter where the public client uses it and HTTP Basic where the confidential client uses it. Do not add another Wyrd authentication mechanism or compatibility path. Update the focused served-OpenAPI test to assert those fields and the standard Basic declaration on the applicable operations, while preserving anonymous access-token semantics. `mise run test:principals:integration` and `mise run codegen:check` are the narrow closure lanes.

## Calibration notes

- `TokenExchange::exchange(&TokenRequest)` now sends every request as `wyrd-cli`, although the enum also contains the UI-only authorization-code grant and UI refresh is confidential-client behavior. Current callers use only the public-client or client-independent variants, and TASK-012 owns the client-library migration, so this is recorded as API-shape calibration rather than a second TASK-010 blocker. A later owner should avoid documenting the method as a client-neutral grant operation unless its type can express the client-auth boundary.
- `AuthError` rustdoc still describes server errors only as `application/problem+json` even though the changed decoder also maps RFC 6749 error bodies. That is stale wording with no separate behavioral consequence; standing direction makes it nonblocking.
- The fully qualified return types in `TokenGrants::issuer` and `tenant_from_unverified_access_token` are less locally readable than imports, but they do not change discoverability enough to justify a finding and have no behavioral or public-contract consequence.
- The long refresh and callback workflows remain cohesive around one transaction and one owning capability. Splitting them merely to meet a line-count preference would make the state transition harder to follow.
- No changed item inspected was missing substantive rustdoc. The new owners and state transitions explain invariants, refusal behavior, and transaction/audit consequences rather than restating syntax.
- Deleted `/internal/bff/v1` consumers are intentionally excluded under TASK-011 direction. No alias for that route or for `grant_type=wyrd_api_key` should be restored.
