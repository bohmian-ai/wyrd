## Affected capabilities and recovery assessment

- Postgres is the sole transient-grant authority. Authorization codes, device approvals, refresh families, and audit staging survive replica restart and are not cached as pod-owned authority.
- Provider discovery/token/JWKS outages consume only the affected login attempt. They do not crash `wyrd-server` or stop machine grants, refresh, revocation, or unrelated tenant operations.
- Database or canonical-audit outages fail the affected issuance/revocation request closed. Transaction drop/cancellation releases row/advisory locks and leaves no partially committed credential.
- Horizontally scaled replicas share all security state through Postgres and can redeem work begun on another replica when signing keys and static OAuth-client configuration match.
- The candidate does not require the TASK-011 BFF consumers to compile or pass in this task round, per the approved task boundary.

## Material proposed findings

### FIND-SYS-1 — The shared in-process auth governor turns the gateway into one noisy-neighbor identity and is not fleet enforcement

- Classification: **INCORRECT / REGRESSION**
- Violated obligation: Supported deployments put multiple `wyrd-server` replicas behind one gateway, and the gateway owns rate-limit integration (`architecture/operations/deployment-and-release.md:8-24`). RFC 8628 user-code throttling must not make one client or tenant able to deny unrelated authorization, callback, token, refresh, revoke, metadata, or key-issuance traffic.
- Location: `crates/wyrd/wyrd-server/src/components/auth/routes.rs:50-83`; serving connect info at `crates/wyrd/wyrd-server/src/app/serve.rs:7-24`; official proxy boundary at `docker/official/extras/nginx/nginx.conf.template:40-58`.
- Evidence: `GovernorConfigBuilder::default()` in locked `tower_governor` 0.8.0 uses `PeerIpKeyExtractor`, which reads the TCP peer address and explicitly does not use forwarded client headers. In every supported proxied topology that peer is the gateway. The candidate then places every auth route in one 20-request burst / 10-request-per-second bucket. The official nginx forwards `X-Real-IP` and `X-Forwarded-For`, but this extractor ignores both. Each server replica also owns an independent in-memory bucket, so the mechanism is simultaneously a shared gateway-wide throttle per replica and not a fleet-wide brute-force control.
- Observable system consequence: modest concurrent login/renewal traffic behind one gateway, or one caller flooding any cheap auth route, returns `429` to unrelated tenants and to recovery-critical token/revoke calls on the selected replica. Load balancing across replicas changes the effective threshold and permits bypass of the intended device user-code control. The existing journey helper masks this by retrying every governor `429` from one synthetic peer (`wyrd-server/tests/identity_e2e.rs:1229-1258`), so green journeys do not establish production behavior.
- Smallest correction: delete the shared server-side governor layer. Enforce the RFC 8628 verification/user-code attempt limit at the existing gateway-owned rate-limit boundary, keyed by the gateway's real client address, while retaining the durable per-device polling interval already enforced in Postgres. Do not put metadata, callback, token, refresh, revoke, or key issuance into one common admission bucket, and do not add a compatibility setting or another server-local rate-limit mechanism.
- Focused closure proof: through the existing gateway path, exhaust one client's device-verification allowance and prove a second client can still reach the authorization and token endpoints; distribute the first client's attempts across two backend replicas and prove the gateway applies one limit. Run only the narrow gateway/config check and the focused auth test that owns this behavior; full identity journeys remain change-review evidence.
