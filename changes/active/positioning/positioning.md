# Wyrd — Real-Time-First Positioning

## Messaging foundation \| November 2026

# Positioning decision

Wyrd leads with real-time verification, not an inventory of infrastructure. It enables developers to establish their own standards and workflows for determining whether applications behave correctly, including while those applications are running.

# Category claim

## The only real-time verification system built for your applications.

This is the intentionally bold, approved category-defining claim. It is a positioning claim, not a conclusion that a comprehensive competitor audit has proven absolute exclusivity. Every public use must be backed by a precise definition, working demonstration, and documented competitive distinctions.

# Developer pain

## You built the system. How do you know it's behaving correctly?

Every application has its own requirements, workflows, and definitions of correct behavior. Turning those expectations into reliable, repeatable checks often means stitching together observability, evaluations, custom scripts, and data pipelines. Those tools tell developers useful things; they do not automatically establish whether an application met the requirements that matter to it during execution.

# Product promise

Wyrd provides the open-source building blocks for creating your own verification systems. Declare requirements. Observe real behavior. Verify while your applications run, during execution, and continuously over time.

## Declare. Observe. Verify.

# How Wyrd works

Declare — Describe what correct behavior means through versioned services, requirements, and composable verifiers.  
Observe — Capture the execution evidence and application data needed to establish what actually happened.  
Verify — Evaluate evidence against declared requirements, produce reasoned verdicts, and let applications or teams act on the results.

# What developers can build

Development verification workflows — Check local applications and coding agents against developer-defined requirements.  
Agent and workflow verification — Verify actions, prerequisites, intermediate steps, and outcomes, rather than just final responses.  
In-execution decision workflows — Make a verification API call part of an application request or business workflow.  
Custom evaluation platforms — Compose deterministic checks, model-based judgments, and domain-specific rules.  
Continuous production verification — Check real services and production evidence over time.  
Team verification standards — Declare, version, reuse, and evolve requirements across applications.

# Priority audiences

Primary: developers and engineering teams building real customer-facing agentic and traditional applications who lack repeatable standards and workflows for knowing whether those systems behave correctly.  
Secondary: local developers and coding-agent users who want to verify work or agent behavior without inventing one-off checks for every task.

# Differentiation boundaries

Not just observability: telemetry shows what happened; Wyrd evaluates observed behavior against developer-declared requirements.  
Not just offline evaluations: Wyrd supports verdicts during execution and continuous checks after deployment.  
Not just guardrails: Wyrd is not restricted to a predefined set of inline blocking rules; developers compose their own verification workflows.  
Not a workflow engine for customer applications: Wyrd provides verification results; the application decides what to do.

# Language rules

Lead with the question developers have, then the real-time capability and the building-block solution. Keep Declare. Observe. Verify. as the organizing language.  
Say 'real-time verification', 'during execution', 'developer-defined requirements', 'composable building blocks', 'evidence-backed verdicts', and 'continuous verification' where accurate.  
Avoid opening with 'AI assurance layer', 'verification factory', OLAP warehouse, durable workflow engine, or code review. Those are supporting architecture, concepts, or specific applications, not the lead promise.

# Proof required for the headline

Show a real application request → declared requirement → observed evidence → synchronous verification call → pass/fail/inconclusive verdict → application decision, with working code and exact API semantics.  
Document the difference between synchronous verify, queued submit, and scheduled continuous verification. Define timeout, missing-evidence, and failure behavior. Never imply Wyrd independently blocks actions or controls execution.  
Evidence for any 'only' claim must identify the exact comparison scope and be reviewed as competitors evolve. The boldness is intentional; substantiation is mandatory.
