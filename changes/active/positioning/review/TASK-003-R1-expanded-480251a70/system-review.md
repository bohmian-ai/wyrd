## Process topology and ownership

Python applications configure one loaded state, whose Rust client resolves credentials and selected Service context. `PyWyrdState::configure` fixes native context before calling the existing Python installer. That installer owns process-global tracer, meter and logger providers, stock OTLP exporters, and their background SDK workers. The installed managed handle is stored only on its creating state. Ordinary Runs use the existing context correlation owner; state flush/shutdown reaches only that stored handle and the state's native Bifrost lifecycle. A sibling state with managed telemetry disabled has an independent native context and no managed handle.

TypeScript applications await configure before starting the writer or accepting requests. Its wrapper fixes native context, asynchronously imports the existing OTel module, creates a tracer provider and stores that provider on the state. Stock exporter headers use the client's shared refresh owner. The changed support-desk application awaits configure before startBifrost and server.listen; the small support-desk and refund programs likewise await configure. No request or Run hot path gained an exporter flush, retry, sleep, or provider-install wait.

ASGI middleware continues owning writer startup before application lifespan, calls the renamed private installer, and drains after application shutdown. Explicit prior configure of the same Python state is compatible because the private installer remains idempotent. The finance example instead loads one state per server lifespan and passes it through request-local dependency injection; it does not implicitly enable managed telemetry or create a writer per request.

## Failure boundaries and recovery

Missing SDK packages or an existing application provider can now make explicit default configure fail application initialization. This is approved fail-fast behavior, with telemetry:false selecting application ownership; swallowing that error would violate the approved contract. Native context is already frozen after failure. Restart after correcting code/dependencies is the approved recovery path, so retrying configure on that state is intentionally not a repair mechanism.

A backend/exporter outage is different: setup constructs the existing pipeline; exports occur through the stock SDK. The explicit flush barrier reports managed flush failure and still attempts native drain. Shutdown retains the existing managed-provider lifetime rather than shutting down application or sibling telemetry. Existing bounded Python flushing and stock TS forceFlush bounds are reused, with no new waits in request paths. Abrupt process exit remains outside successful explicit drain guarantees.

Inspected Python's multi-signal installer loss-of-registration path: it disposes providers constructed by that attempt, not a provider owned by the competing application/state. Concurrent startup and native phase interleavings remain assigned to invariant-rev; no independent system finding is inferred merely from a failed install requiring the explicitly approved process restart.

No cross-process recovery, server retry loop, new resource admission owner, auth bypass, tenant propagation change, or durable acceptance protocol is introduced by these SDK setup changes. Existing operations and security boundaries remain applicable at the original native/server owners.
