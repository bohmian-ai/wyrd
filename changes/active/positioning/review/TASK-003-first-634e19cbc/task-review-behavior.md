## Proposed material finding

### BEH-001 — MISSING: schedule tutorial omits required reader setup

**Violated obligation.** Scenario 3 and task acceptance require an independently runnable source-backed guide with explicit prerequisites, reader-native commands and proof on each presented language; spec REQ-012/AC-011 and INV-004/005 preserve those requirements. docs/AGENTS explicitly requires reader tools and the Setup page tells Python readers to run the CLI as `uv run wyrd`, TypeScript readers as `pnpm wyrd`.

**Locations.** `docs/src/content/docs/build-and-verify/verify/monitor-drift.md:16`, `:30`, `:39`, `:68`; `examples/scheduled-check/results.ts:3`.

**Reachable failing path and source evidence.** A reader completes only the declared prerequisite, Setup. Its TS install at `docs/src/content/docs/get-started/setup.md:46` adds only `wyrd-ai@0.4.2`; the SDK package declares apache-arrow and optional provider/OTEL peers, not zod. The schedule page never adds zod, although its embedded `results.ts` imports it. Consequently `node results.ts` cannot resolve zod in that reader's project. Quickstart does explicitly install zod, but is not a schedule prerequisite. The investigation guide supplies its own `pnpm add zod`, demonstrating the existing local solution. Before readback, Python and TypeScript readers also encounter bare `wyrd declare`, `wyrd pull` and `wyrd principal ...` commands even though Setup installs the CLI inside their project and explicitly directs them to `uv run wyrd`/`pnpm wyrd`; it does not install a global `wyrd` executable. This same guide has lost the per-language CLI invocation pattern used by the changed request tutorial.

**Why the green journeys miss it.** The TS subprocess executes the script from `examples/scheduled-check`, so package resolution finds `examples/package.json`'s already-declared zod. Giving that process an empty working directory does not relocate its imports into a clean reader project. Python/Rust/TS schedule tests perform declaration/pull/principal creation through SDK calls, so none tests the published command spelling. The actual program/scheduler proof remains valuable but does not prove installation/invocation completeness.

**Observable consequence and materiality.** A supported direct Setup → schedule reader cannot follow the procedure through retained readback without discovering additional installation/command requirements. This blocks a required tutorial rather than an unusual domain input or an optional convenience.

**Smallest testable correction.** At the existing schedule guide owner, add the existing `pnpm add zod` instruction to its TypeScript setup and spell the three CLI operations through the reader's language tool, using the same existing language-tab convention as the request tutorial. Do not add a dependency, wrapper, global installation or prerequisite detour to the finance application. Check the declared Setup → schedule instructions from a project whose direct dependencies match those instructions; resolving imports from a repository-resident example is insufficient for this narrow setup proof. Preserve the existing real scheduler/actual-program assertions. Regenerate derived published text through its existing generator.

**Correction burden.** Bounded guide/setup edits and focused reader/import/command proof. Existing project components and installed packages suffice; no new harness or runtime behavior is required.
