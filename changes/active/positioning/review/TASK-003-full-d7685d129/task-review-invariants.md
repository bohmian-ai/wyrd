## INV-FULL-001 — TypeScript's first implicit-start sample loses its producer span

Classification: **REGRESSION**. Violated obligation: positioning REQ-017 adds first-write startup while preserving existing observation behavior, and `architecture/wyrd-design.md:1036–1043` explicitly requires each queued Bifrost write to record a `bifrost.enqueue` PRODUCER span in the caller's own tracer, with the consumer linking that producer.

Changed location: `sdks/wyrd-sdk-ts/native/src/cards.rs:1073–1082`, together with `crates/shared/wyrd-client/src/observe/mod.rs:435–448,474–480`.

Reachable producer-to-consumer path:

1. An ordinary Node application configures managed telemetry and calls a bound window Verifier's `observe.submit` without `startBifrost`, precisely the newly approved scheduled-record flow.
2. Native submit calls `observe.stage` inside `crate::trace::traced`. With no writer, `record_or_stage` validates the sample and returns `Staged { evidence: Window(...) }`; no queue call occurs in this scope.
3. The synchronous scope ends. `trace::spawn` starts the asynchronous `enqueue_staged` future. Its implementation (`native/src/trace.rs:78–86`) propagates only the active caller's `TraceContext` through `with_caller_trace`; it does not propagate the producer callback. The callback contains a JavaScript Env and is intentionally callable on the JavaScript thread only.
4. `Observe::finish` starts the writer and calls `drift_value`. `WriterPool::insert_rows` calls shared `transport::trace::producer`. With no PRODUCER callback, that function returns CALLER directly when a caller span exists (`transport/trace.rs:124–128`). No Node `bifrost.enqueue` span is created. Without an active caller, the Rust fallback cannot create a span in Node's managed tracer either.
5. The row can still land with correct run/card identity, but its batch links to the application span instead of the required producer span; the first sample's producer is absent from the retained action timeline. Concurrent first samples staged before startup completes take the same defective branch. Warm samples remain synchronous under the callback and are unaffected.

This is a supported-use trace regression, not a speculative cancellation guarantee. The candidate advertises removal of explicit startup for exactly these programs. Existing TypeScript `action-timeline.test.ts:93–155` checks producer/consumer links after `await state.startBifrost()`, so its passing result cannot establish the cold branch. Python's analogous caller retains the scope around blocking completion and does not share the cause. Native TypeScript run-evidence submission does not enqueue drift rows; its asynchronous staging is unaffected. Caller-table writes have a pre-existing asynchronous trace bridge and are not folded into this new regression without evidence of a new defect there.

Smallest safe correction boundary: preserve the Node-created producer context for cold staged window evidence at the existing TypeScript/native staging and trace boundary, and apply that context to the eventual sample enqueue. Reuse the existing Node span source and shared trace-context plumbing; do not move Node callbacks onto Tokio workers, add another tracer/provider, replace the lifecycle, or give startup requests the producer's context in place of their caller's context. Warm samples, run-evidence grouping, one-writer startup, admission errors and all-or-none rows must remain intact. A captured context is sufficient; a new lifecycle or generalized callback transport is unnecessary.

Focused closure proof: extend the existing TypeScript action-timeline setup to submit a window sample before explicit writer startup, then assert its `bifrost.enqueue` producer exists under the active application span and the resulting `bifrost.gate.write` consumer links its span ID. Include a later warm sample in the same check to preserve the existing path, and assert the expected two logical records. Use the established real-server timeline/test fixture, not a new harness.

## Wait and ownership audit

Warm sample submission adds a phase mutex/Arc snapshot and then uses the existing synchronous projection/producer enqueue. Warm caller-table writes return from `bifrost_writer` before the async start gate. Existing named-table cache hits return before `describe_gate`. There is no new external wait in these warm paths.

Cold first-use calls wait for the state start gate, then the existing client's connected/authentication path, gRPC connection, optional explicit/sole-declared table description, and fixed Drift table description; a named write may then describe its named destination. These are the approved first-write startup operation from REQ-017, reuse existing transports/caches, and admit no sample/row before successful startup. Concurrent startup followers wait on the same startup gate. Holding that async gate across connect/describe is bounded to startup; phase mutexes are never held across await. No schema/transport/client/pool is rebuilt per warm write. Writer flush/shutdown retains its existing off-runtime blocking-drain strategy.

The maintainer's designated hot paths are VerificationEngine/hosted executors, VerificationControl direct execution, GatewayInvocation/gateway, Oracle query, and Scribe append. None of their request-wait implementations is changed by this SDK lifecycle work. The shared client submit Run-evidence branch still calls the same target enqueue after the same projection; the change only routes that branch through `finish`. Window/sample paths are caller preparation plus the existing background writer, not Scribe's append implementation. The capacity client-queue driver does call window submit, but benchmark caller reachability does not turn that background writer/client preparation into the explicitly defined engine hot path. Consequently no engine benchmark is required for this reviewed boundary. No engine performance improvement or VALID benchmark result is claimed.
