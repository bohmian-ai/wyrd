## Failure and recovery analysis

| Credible interruption | What stops, retained state, and recovery |
| --- | --- |
| Missing/corrupt credentials or required exchange refused | Eager connection returns the existing error before a handle is published. Python lazy construction and local selection still succeed; the first server-needed operation gets the connection error. A failed lazy attempt stores nothing and a later operation can retry. An explicit client remains retained; an omitted client can resolve usable ambient configuration on that later unsuccessful-initialization retry. After success no operation clears the handle or retargets ambient configuration. |
| Auth endpoint unavailable or slow | Existing TokenExchange sets a request timeout (`wyrd-client/src/auth.rs:254-266`). The auth cache's existing async mutex owns single-flight refresh (`:840-888`). Eager connection adds no polling loop, health probe or alternate cache. Dropping a Rust connection future releases its lock/future; failure does not publish a handle. Request/handle refusal is the boundary, not SDK-process or server-process termination. |
| gRPC endpoint unavailable | Existing `GrpcConnection::connect` has bounded attempts/backoff and configured connect timeout (`transport/grpc.rs:75-105,176-178`). The existing transport error propagates. An explicitly supplied client's completed exchange may remain cached for reconnect; no writer is assembled before successful dial. |
| Concurrent Python first use, including a failed attempt | `LazyConnection::get` checks OnceLock before and after the GIL-detached mutex gate (`src/client.rs:129-145`). Exactly one successful handle is published. Failure returns before publication; queued callers can attempt sequentially, without an autonomous retry loop or new fan-out. The gate is dropped before Python reattachment. |
| Concurrent local table change during first use | Connection is made with no initial table (`src/bifrost/mod.rs:568-580`). After success, the first caller takes the binding lock and transfers the current `Binding::Local` into the retained native client exactly once (`:582-585`). A concurrent `use_table` either updates Local before that transfer or updates Native afterward under the same lock (`:697-703`). The lock is never held during connect/await. A failed connect returns before transfer, preserving the latest local binding for retry. Every server-operation caller passes this transfer before using the native handle. |
| Asyncio availability | Constructors, `table`, `use_table`, counters and Cards view selection perform no connection IO. AsyncBifrost's awaited connect and IO methods use existing `asyncio.to_thread` (`python/wyrd/bifrost/_client.py:1074,1092-1297`). The inherited synchronous first `insert` may perform setup; its public first-use qualification now states that behavior (`_client.py:707-726,1045-1050`). The prior validated ledger rejects a new preconnection buffer/queue or awaitable insertion requirement; that rejected redesign is not reopened. |
| Asyncio task cancellation / abandoned JS promise | `to_thread` work can outlive the await, retaining the native bound method/object; eager connection has admitted no ingest data. Native JS futures own their client clones. Neither bridge newly promises cancellation of already-running worker IO. No changed lost-row path or dangling runtime borrow was established. |
| Credential expiry or protected-call refusal after connection | AuthMiddleware's existing bearer/cache/renewal and force-refresh paths remain reachable (`auth.rs:840-910`). A first protected call can refuse a presented bearer even though eager HTTP connection made no probe. Connection retention does not suppress later renewal or replace the selected identity. Platform keeps its existing access-only session lifetime. |
| Ingest outage, flush/shutdown, restart | Existing transport attempt budgeting and WriterPool retain responsibility. `bifrost/facade.rs:694-731` retains the writer Arc in the blocking drain task. Table swaps reuse the existing native pool; previous producers keep their pending rows (`:301-318`). Process restart loses ordinary client memory; this change adds no durable client state or claim that unacknowledged data survives abrupt SDK death. Server durability/recovery is unchanged. |
