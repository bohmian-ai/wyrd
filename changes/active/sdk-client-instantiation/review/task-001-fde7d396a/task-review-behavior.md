### BEH-001 — INCORRECT: local Python accessors connect before a server operation needs the connection

- Priority: Important.
- Violated obligations: REQ-007, REQ-008, INV-001; Scenario 3's explicit first-server-use timing and preserved local behavior.
- Locations: `sdks/wyrd-sdk-python/src/bifrost/mod.rs:662`, `:682`, `:893`, `:899`; `sdks/wyrd-sdk-python/src/state/mod.rs:1728`, `:1744`, `:1760`, `:1776`.
- Reachable path: `Bifrost(table=config).table`, `Bifrost().use_table(config)`, `AsyncBifrost().producer_count`, or `Cards().prompt` calls `handle(py)`/`cards(py)` immediately. Those call `LazyConnection::get` (`sdks/wyrd-sdk-python/src/client.rs:119`), which executes the complete shared native `connect`, including credential resolution/exchange and Bifrost gRPC dial. These are local state inspection/binding or typed-view selection, not operations requiring the server. The shared Rust Bifrost `table`/`use_table` remain local operations; Python's `_BifrostBase` directly calls the native methods (`python/wyrd/bifrost/_client.py:677`, `:696`, `:739`, `:746`), and `AsyncBifrost` inherits those synchronous methods.
- Consequence: an offline application cannot inspect the table passed to its IO-free constructor, change the local write binding, inspect zero counters, or select a Card registry view without credentials/network. Accessing an AsyncBifrost local property can now block the event-loop thread on exchange/dial. It also fixes the ambient identity earlier than the specified first server operation; a view selected before credentials are installed fails instead of being usable later.
- Counterevidence considered: eager factories correctly must connect; the constructor itself correctly performs no IO; after successful initialization these getters reuse the handle. Neither fact justifies initialization by a local getter. `tests/unit/test_sdk_client_instantiation.py:23` expressly chooses `producer_count` and `Cards.data` as first-use failure triggers, so the present tests encode the premature connection rather than challenging it.
- Smallest safe root correction: keep pre-connection local Bifrost binding/counters local, and let typed Card views retain the parent's deferred connection until an actual registry operation; continue using the same shared native connection and client afterward. Do not add transport/authentication implementations or per-view independent connections. Initialization remains required for operations that actually need server resources.
- Focused closure proof: with no credentials/unreachable endpoint, construct Bifrost and AsyncBifrost, inspect/set their local table and counters, and select every Cards typed view successfully. Then install valid ambient configuration and perform a real operation through those same objects/views, proving that initialization occurs there and all views share the selected client. An async heartbeat should continue while the local AsyncBifrost operations run.
