## Proposed finding

### SYS-001 — The added rotation instructions omit pre-staging the new key across replicas

- Classification: INCORRECT; medium operational consequence.
- Changed location: `docs/src/content/docs/operate/deploy-wyrd-for-a-team.md:72`, the new `WYRD_SEALING_KEY_FILE` row.
- Violated obligation: REQ-007 requires the existing deployment keyring rotation lifecycle. The existing `SealingKeyring` contract (`crates/shared/wyrd-crypt/src/lib.rs:188-191`) and `AuthConfig::sealing_key` contract (`config.rs:2344-2348`) require distributing the new key as retained to every replica before changing the write key. The supported topology includes multiple replicas; deployment-and-release requires contract-critical configuration agreement before readiness.
- Reachable failure: start two replicas holding only K1; follow the new table's instructions, installing K2 as write key and retaining K1 during a rolling restart. The first restarted replica runs the boot pass and rewrites every managed credential to K2. The still-serving K1-only replica cannot open these rows, so its Gateway calls fail before dispatch until it is also restarted. The file mount changing does not repair the running process: its keyring was loaded into memory at boot. The same premature rewrite affects sibling stored client secrets covered by the shared pass.
- Why this is introduced/reachable: this table is the candidate's new operator-facing setup and rotation procedure. It tells the reader to install the new write key and list the old retained key, but never to distribute/restart with K2 as a retained reader key first. The source can perform a safe rollout already; the new instructions do not describe it completely.
- Smallest correction: correct this existing documentation entry (or link it to one complete existing-authority runbook) to name the two phases: first distribute K2 as retained while K1 remains the write key and restart every serving replica; then switch writers to K2 while retaining K1. Retire K1 only after every writer uses K2 and a subsequent complete pass reports zero remaining. Reuse the current keyring and boot rewrap; no runtime changes, new configuration, coordination mechanism, or compatibility work are needed.
- Focused closure proof: compare the corrected instructions to the existing keyring and rewrap contracts and walk the two-replica sequence, verifying both loaded keyrings can open K2 before any rewrap writes K2. Run the docs check for the documentation write set. Do not add a runtime harness solely to prove a prose correction.
