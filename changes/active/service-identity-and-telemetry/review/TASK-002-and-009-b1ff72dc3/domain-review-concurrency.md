## Proposed material finding

### CONC-001 — MISSING: Python and TypeScript application-owned exporters cannot use the configured state's environment

**Obligation.** Spec revision 15 requires configured context to survive telemetry and tells callers refused automatic global startup to use state-bound exporters with their application provider. TASK-009 scenario 2 explicitly calls that existing integration the remediation; its implementation reference requires extending existing exporter/correlation owners for all signal surfaces, without exporter-specific configuration copies. Architecture Configured Service context requires the same environment on all three telemetry signals. This is a client transport/context gap, not TASK-003's deferred persisted projection.

**Locations.** `sdks/wyrd-sdk-python/python/wyrd/otel.py:226–240` and factories at 346–406; `sdks/wyrd-sdk-ts/wyrd/src/otel.ts:25–59`. Producer evidence: shared `state.rs:778–785` creates the environment-bound client privately; Python state `src/state/mod.rs:231–237` and TS `wyrd/src/index.ts:3147–3154` expose it only to automatic telemetry startup. Public Python `src/client.rs:244–274,364–381` and TS `wyrd/src/index.ts:1589–1599,1620–1641` have no state-environment binding operation. State stubs/public class provide no exporter accessor and intentionally no public client accessor.

**Reachable behavior.** A Python/TS application already has an OpenTelemetry provider. It loads a state using client C, configures `deployment_environment="prod"`, and calls automatic startup: the required typed provider conflict occurs. Following the prescribed remediation, it adds `span_exporter(C, workload_uid=state.root_ref.uid)` / `spanExporter(C, {workloadUid: state.rootRef.uid})` to its provider (same for logs/metrics). These factories only rebind the original C to a UID. C was intentionally never mutated by `configure`; its environment is still null. Consequently `_session`/`config` omit `x-wyrd-deployment-environment`, despite the state's frozen value being prod. The public client environment getter is read-only; clients originate from a constructor/connect, UID rebinding or delegation, none of which can acquire the state's environment. The only public state adapter that retains the bound client is HTTPX/fetch and is not consumed by OTLP factories.

**Consequence.** The advertised application-provider path, including a second differently configured state after the first installs telemetry, cannot export with the configured immutable environment through these SDK factories. Logs/metrics have the same gap. Passing a UID preserves root but does not preserve configured context. Reading the new `client.deployment_environment` property at the consumer is ineffective when public callers cannot produce such a client.

**Smallest correction boundary.** Complete the existing exporter integration so the factories can obtain the state's already pinned native client internally in Python and TS, while retaining their existing plain-client use. Reuse `WyrdState::client`, current token renewal and the existing stock exporters. Keep `state.client` private and do not add independent environment settings, a second provider pipeline, or mutable global Service context. The implementation should select the smallest thin projection of that existing state-owned capability; no new authorization or durable behavior is necessary.

**Focused closure proof.** In each language construct two configured states over one unmodified client with distinct environments, attach their existing span/log/metric exporters to application-owned providers or drive the stock exporters against a local OTLP receiver, and assert per-export workload/environment headers remain tied to the intended state before and after token renewal. Automatic startup against the existing provider must still refuse without replacing/flushing it. A client with no state must retain its existing rootless behavior. This can be proven at transport/header level without TASK-003 table changes.
