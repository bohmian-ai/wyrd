## Existing-owner and standards comparison

The changed grant entry points continue to use the existing `TenantTokenIssuer`, `ExchangeApiKey`, external verifier/JWKS owner, and bounded graph resolver. Request-root selection adds a shared narrowing step at the real trust boundary; it does not create another signature verifier or permission system. Federation changes the mapping target from Card-derived identity to a stable account while retaining the existing trusted issuer and subject-verification path. Gateway extends the existing cache key with the root instead of creating another credential store.

Compared the applicable processing rules with [RFC 7523 §3](https://www.rfc-editor.org/rfc/rfc7523.html#section-3), [RFC 8725 §3](https://www.rfc-editor.org/rfc/rfc8725.html#section-3), and [OIDC Core §3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation). The changed workload path uses the existing RFC 7523 assertion verifier: required/pinned issuer and audience, expiry, present `nbf`, asymmetric JWKS signature and mapped subject, followed by explicit workload policy and server mapping. Optional RFC 7523 `iat`/`jti` and assertion replay prevention were not turned into invented mandatory requirements. Human OIDC ID-token validation, nonce/authorization-response binding and its existing relying-party owner are not replaced by the changed account issuance. The cumulative changes to human connection/browser/refresh consumers preserve their existing identity and human-only renewal selection; no parallel workload ID-token validator is introduced. The tenant token profile remains separately typed from platform tokens and external assertions, with fixed EdDSA validation and audience confinement.
