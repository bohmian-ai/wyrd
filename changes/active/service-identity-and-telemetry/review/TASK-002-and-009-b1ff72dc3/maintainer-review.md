## Existing-owner comparison

- **Graph resolution:** `resolve_workload_scope` extends the pre-existing bounded auth scope walk, preserving `scope_child_card_refs` and the depth/member bounds. `CardGraphPuller` and the hydrated state index own client IO/bundle loading, not server authentication; substituting those owners would cross the client/server boundary. Reusing the existing auth walk is sufficient here; another graph store is unnecessary.
- **Identity resolution:** `TenantTokenIssuer::resolve` remains the current account/roles authority. `ResolvedContext` supplies the selected Card authority; direct-key authentication and scheduled acceptance reuse it. `AuthenticatedPrincipal::select_root` adapts the shared signed-root selection to HTTP/gateway. The native database-free ingress appropriately does not grow another registry resolver.
- **Cache/orchestration:** `AuthMiddleware`, `GatewayApiKeys`, Bifrost `ClientScope`, and `VerifierCardCache` existed before this change. Extending their keys/lifetimes is clearer than introducing parallel caches. However, a correct dependency-owning cache does not justify the replacement occurrence-matching rule in MAINT-01.
- **Binding identity:** existing `Run.alias`, `BindingProjector::freeze`, `NewBinding::subject_occurrence_key`, `GroupSource::subject_occurrence_key`, and `verification_bindings` already distinguish occurrence from Card UID. The new `binding_environments` traversal uses a different, weaker identity. Extending the existing occurrence contract is required; sharing only UID lookup is insufficient.
- **Accepted work:** existing `Submission`, `AcceptedAuthority`, `ClaimedExecution`, runner dispatch and leased recovery already carry immutable accepted facts. The new environment must cross that same handoff rather than existing only in `ExecutionStatus` for result presentation.

## Material findings

### MAINT-01 — INCORRECT: binding resolution introduces a weaker parallel identity

**Changed location:** `crates/wyrd/wyrd-server/src/verification/cache.rs:168-203`, especially the UID-only component scan and conversion to `BTreeSet<Option<String>>`; invocation at `components/verification/service.rs:687-708`. Producer/caller evidence: `wyrd-client/src/state.rs:887-938`, `observe/mod.rs:363,468,504,515-524`, and `wyrd-spec/src/verification/execution.rs:39-67`.

**Rule:** maintainer guide “put a workflow with its owner” and “types carry the contract”; AGENTS requires fixing a shared owner instead of adding a parallel contract. Approved REQ-052/INV-004 and TASK-009 Scenario 3 explicitly require the exact binding occurrence to survive invocation and acceptance.

**Evidence and reachable consequence:** a Run already retains its alias, but `bound_verifier` receives only the subject CardRef and name, gathers every component referencing that Card, and returns only verifier UID, subject UID and spec. The wire request has no occurrence. The new server traversal repeats that weaker selection and aggregates selectors from all matching component occurrences and the Agent's own bindings. Two legal aliases can reference the same exact Card (the state alias tests explicitly support shared holders). If those sites bind the same Verifier under `prod` and `staging`, a Run selecting either alias is refused because `bound.len() > 1`, even with its matching configured environment. If selectors are equal, the invocation silently loses which binding it selected. Direct/submitted paths also retain `binding_id: None` (`service.rs:739` and direct result construction), so acceptance cannot recover that choice afterward.

**Concrete maintenance cost:** there are now three related interpretations of binding identity: registration/group projection keeps occurrence, client invocation discards it, and cache evaluation merges it. A change to one binding can reject work for a different binding on the same subject; consumers cannot repair this because the producer discarded the differentiating value.

**Smallest testable correction:** retain the selected occurrence from the existing Run/`bound_verifier` owner through the existing request/submission/accepted-work contracts, and validate/reconcile the one selected occurrence against the owning Service and exact subject/verifier. Reuse the existing occurrence key/natural-key semantics; use an existing projected binding ID where one exists, without inventing Trigger activation for explicit-only bindings. Replace the aggregate selector scan with resolution of that selected binding. Keep unrelated explicit rootless verification supported and do not infer a chosen occurrence from shared subject membership. Add focused direct and queued tests with two aliases of one Card and the same Verifier but different selectors; each alias must use its own selector and retain its occurrence through accepted recovery, and a forged occurrence must fail before staging. Equal selectors must also preserve distinct occurrences.

### MAINT-02 — MISSING: accepted environment is stored for status but absent from claimed work

**Changed location:** `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:104-133` (new submission storage), contrasted with `CLAIM_SQL:410-425` and `ClaimedExecution:1324-1370`; `components/verification/service.rs:231-234` (new result presentation). Consumer evidence: `verification/runner.rs:405-470` and `hosted::blocks::Execution` construction.

**Rule:** maintainer guide requires types to carry the contract and a workflow to remain with its owner; REQ-052/053 and TASK-009 Scenario 3 require accepted context through gateway-backed calls and worker restart, independently of Task003's eventual table projection.

**Evidence and consequence:** enqueue computes and stores `deployment_environment`, and `ExecutionStatus` reads it for `get_execution` to add to the returned result. The claim query does not return that column, `ClaimedExecution` has no such field, and dispatch constructs its engine/gateway context solely from that claimed value and accepted authority. Accepted authority carries authentication facts, not the configured environment. Consequently a queued gateway-backed check cannot carry its originating configured environment into its actual work after claim/restart. The status response can nevertheless show the expected environment because it reads the column separately. The added restart proof substitutes a scripted engine outcome and reads status, so it cannot detect this missing handoff.

**Concrete maintenance cost:** the public result presentation and execution context now obtain “accepted environment” by different paths. A maintainer can change or test the status field successfully while the runtime never receives it. There is no type-level route by which a worker could preserve the promise.

**Smallest testable correction:** carry the persisted effective environment through the existing claim/decode/`ClaimedExecution` and execution/gateway invocation context owners, preserving the same value across retry and restart. Retain the existing status readback. Do not add another ambient environment source, token claim, queue, or table projection here. Extend the restart proof with a real gateway-backed engine path/local provider mock and inspect the accepted invocation context at that existing seam, so a status-only patch cannot satisfy it. Task003 can separately prove canonical warehouse columns.
