## Proposed findings

### INV-DIRECT-001 — VIOLATION — direct verification bypasses the signed Card-access limit

**Location:** `crates/wyrd/wyrd-server/src/components/verification/service.rs:490` (shared owner `authorize_run`, lines 930–974).

**Obligation:** TASK002 scenarios 2/3/7; auth supplement “Verification, queues, schedules, and activity”; Security Request principal and root_required rules; INV001–002/005. Direct Card-sensitive verification must check effective Card authority, including root_required, even with operation wildcard grants.

**Producer to sink:** issuance produces a rootless family principal with CardAccess::RootRequired, or a selected-root principal with Scoped UIDs. HTTP/MCP extract that principal unchanged. run_direct calls authorize_run with `subject=None`; authorize_run's only Card-access refusals require Some(subject), so the permission check alone passes. resolve then reads the requested registered subject/Verifier; VerificationTarget::refusal checks readiness and subject existence, not caller scope or root membership. The engine and result staging therefore execute as if the subject were admitted. The same unchecked subject can enter GatewayCallAttribution::Resolved from a hosted Agent check, whose downstream admission intentionally trusts the originating operation.

**Reachable consequence:** a family Service with workload/verifier:run (or wildcard) can POST /v1/verification/execute rootless and verify any available tenant subject; a rooted caller can supply an out-of-graph subject. This violates the new unresolved-family requirement and can record false workload-owned evidence. This is required acceptance work even though the prior direct call also supplied None: RootRequired is a new authority state introduced by this cumulative task.

**Sibling callers/owner:** enqueue already calls the same authorize_run with Some(request.card_uid). HTTP and MCP both use VerificationControl; do not fix them separately or add a downstream gateway scope check to compensate for unvalidated server-resolved attribution.

**Minimal correction:** pass and enforce the requested subject through the existing shared authorization owner on direct execution before reservation/engine work. Preserve authorized rootless AnyRegistered behavior and normal operation grants; do not re-resolve live roles or credential state.

**Focused closure:** real direct HTTP/MCP calls with a rootless family token return workload_context_required; rooted scoped and empty delegated scopes reject outside-subject UIDs; an AnyRegistered User with the grant succeeds. Assert no execution/input/result/provider dispatch from rejected calls. No new harness is needed.

### INV-BINDING-002 — MISSING / INCORRECT — the bound invocation loses its exact occurrence before acceptance

**Locations:** `crates/shared/wyrd-client/src/state.rs:934`; `observe/mod.rs:511`; `crates/wyrd-spec/src/verification/execution.rs:26`; `crates/wyrd/wyrd-server/src/verification/cache.rs:168`; `components/verification/service.rs:740,801`; SQL `verifier_executions.rs:105`.

**Obligation:** REQ015/052 and INV004; TASK002 scenarios 3/7 and TASK009 scenario 3 explicitly require exact binding occurrence across direct/submitted/retry/restart, and Task009 specifically directs preserving the occurrence rather than returning only Verifier/subject. Task003 warehouse projection deferral does not defer invocation/accepted-authority context.

**Producer to sink:** bound_verifier scans Service/component/Agent bindings and returns the first name match, but returns only verifier UID, subject UID and spec. Observe's target/request therefore cannot identify which binding was chosen. The server cache rereads Service/Agent specs and gathers every binding matching owner+subject+verifier into a set of environments. That is a lossy interpretation: two occurrences with different selectors are rejected wholesale (`bound.len()>1`), even when the caller intended one valid occurrence; equal-selector occurrences are indistinguishable. Direct/input ResultRun use binding_id None, and submitted SQL omits owner_card_uid/binding_id entirely. Restart cannot restore an identity that was never accepted. Moreover, no binding match is required for a rooted direct call: empty binding_environments is accepted, so arbitrary Verifier/subject pairing can be stamped with the selected owner rather than validating the claimed binding relation.

**Existing owner and siblings:** SQL verification binding projection and verifier_executions::resolve_binding already own exact occurrence/owner/subject/verifier/Trigger resolution for scheduled/grouped paths. Those paths retain binding_id and owner_card_uid. The new cache's all-occurrences environment scan duplicates part of that workflow while omitting its durable identity. SDK bound invocation, public HTTP/MCP and queued acceptance are the affected producers/consumers; this is one lost-identity cause, not separate SDK, response and queue issues.

**Observable consequence:** supported bindings are spuriously refused or silently collapse; direct/submitted evidence cannot be tied to the selected occurrence and cannot prove truthful binding ownership. The task's own residual-risk statement “explicit work records no binding id” describes this unmet requirement; it does not waive it.

**Minimal correction:** retain the resolved occurrence from state/Run through the existing invocation/accepted request handoff; use the existing server binding authority to validate owner, subject and Verifier and reconcile only that binding's environment. Preserve rootless explicitly unbound verification and existing scheduled/grouped semantics. Remove the lossy aggregate interpretation once the exact occurrence is represented; do not add a parallel binding registry/resolver or infer ownership from shared-subject membership. Keep the accepted occurrence through queue retry/restart. This is existing approved behavior, not a proposal for another binding model.

**Focused closure:** use two occurrences for the same subject and Verifier with distinct binding selectors, plus two roots sharing a subject. Exercise state-selected direct and submitted calls and restart; assert the selected binding/owner survives. Refuse a forged owner/binding/subject combination and preserve separately authorized unbound User verification. Existing real server/runtime and SDK journey owners suffice; no warehouse schema/readback requirement is added here.

### INV-ENV-003 — MISSING — accepted environment is a status echo and never reaches execution

**Locations:** SQL `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:410` (CLAIM_SQL) and ClaimedExecution at 1325; server `verification/runner.rs:454`; `components/verification/service.rs:534`; `verification/hosted/blocks.rs:62`. Scheduled binding resolution/insert at SQL lines 56–83 is another writer of the same lost context.

**Obligation:** REQ052–053, TASK009 scenario 3 and acceptance row REQ014–017/052–053 explicitly require frozen originating environment through accepted execution, gateway-backed work and evaluation. Auth supplement configured context and storage supplement's population/trace boundary are normative. Task003 owns table projection; Task009 still owns carrying the context to the evaluator and existing gateway call handoff.

**Producer to sink:** enqueue computes the effective environment and stores it in request and the verifier_executions deployment_environment column. get_execution reads that column to populate the response. But CLAIM_SQL never returns it, ClaimedRow/ClaimedExecution never represent it, ExecutionInput/AcceptedAuthority do not carry it, and runner reconstructs Caller/Execution without it. Hosted Execution and GatewayCallSubject also have no environment field. Direct execution computes the effective value then uses it only in VerificationResult; its engine is built from the original caller/inputs with no effective environment. Scheduled resolve_binding and INSERT_SCHEDULED_SQL do not select/store the binding's environment at all. Thus retry/restart cannot dispatch under that context, and gateway-backed checks cannot receive it. The evaluator's drift population owner rows_in selects subject/series/time only; no accepted environment ever reaches that owner. Whole-trace reads must remain unfiltered, as the supplement requires.

**Observable consequence:** a submitted prod invocation can return `deployment_environment=prod` after restart while its actual hosted model/evidence operations have no prod context. An explicitly scoped scheduled deployment population is neither frozen nor filtered before judging. A truthful API echo is insufficient proof of execution context. No Task003 column projection change alone can repair the missing SQL-claim-to-runtime value.

**Minimal correction:** carry the already accepted effective selector through the existing claimed execution and hosted/gateway execution context; scheduled/grouped acceptance must freeze their binding's effective selector through the same owner. Apply it at the existing server-read deployment population owner before evaluation while preserving whole-trace fetch semantics, unscoped/mixed null behavior, authority, deadlines and group identities. Direct execution must pass its reconciled value to the same execution context. Coordinate population projection with Task003 rather than inventing a second schema; at this task boundary prove runtime handoff and evaluator selection, not canonical warehouse rows.

**Focused closure:** extend the existing configured acceptance/restart seam with an actual gateway-backed check that observes the accepted environment at dispatch after retry/restart, rather than merely reading status. Cover binding-only effective environment for scheduled acceptance and distinguish two deployment populations before judging. Assert conflict admits no inputs/work. Retain whole-trace behavior unchanged. Current configured_service_context_survives_acceptance_and_restart assertions read SQL and result echo; they do not falsify this lost-handoff path.
