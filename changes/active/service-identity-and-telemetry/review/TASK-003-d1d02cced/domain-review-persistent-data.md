## DATA-001 — Native replay accepts a different managed origin as the same batch

Classification: **INCORRECT**. Material persistent-attribution/idempotency failure.

Violated obligation: TASK-003 scenario 4 explicitly requires changed-owner batch replay refusal; the telemetry supplement says a native retry never acknowledges a partly changed batch, and the storage supplement requires one accepted attribution across retries for both system and dynamic tables. REQ-024/028/034 require that the new managed workload and account/subject envelope cannot bypass accepted-batch idempotency.

Changed source boundary: `crates/vala/vala-bifrost-redux/src/tables/managed_columns.rs:101` adds workload to the universal managed set. Its consumer `scribe/preprocess.rs:629–645` skips every managed field in the logical digest, including that new workload plus subject/Run/principal pair. The same candidate adds/extends stable originating context on native frames without closing this identity consumer.

Reachable producer-to-consumer path:

1. `Gate::dispatch_native_frame` (`gate/mod.rs:1053–1120`) accepts a caller-provided UUIDv7 batch ID and table version, authorizes the request, resolves the request's context, and forwards that same batch ID. It does not bind principal/workload into it.
2. `prepare_and_dispatch_under` (`scribe/ingress.rs:721–734`) passes the accepted workload, attribution and dimensions to decode. `managed_arrays` (`execution_lanes.rs:1440–1468`) stamps workload and principal pair into managed fields. A dynamic table has no required dimensions, so changing its workload affects only managed fields. Two permitted accounts can likewise change only the managed principal pair even on a system table.
3. `logical_data_identity` skips all managed columns. `prepare_slice` (`preprocess.rs:929–943`) passes only that digest and length into the WAL identity; `PreparedAppend::logical_identity` folds schema fingerprint, slice ordinals, digest and length. No principal or workload participates elsewhere.
4. `committed_duplicate_rows` (`shards.rs:1138–1151`) compares tenant, batch ID, FQN, version, that digest and slice count. A repeat with unchanged user rows but a different accepted workload therefore immediately ACKs as a duplicate. If this cache is absent, `accepted_retry_rows` (`ingress.rs:833–861`) and SQL `ExistingScribeBatchCommit::matches_logical` (`scribe_batch_commits.rs:123–126`) use the same incomplete identity. WAL location/request fields select the original attempt; they do not add an accepted account/workload check to the logical match.
5. `correlation_data_identity` already hashes stable managed correlation, but its only production caller is `otlp_batch_id` (`gate/mod.rs:143–144`). Native explicit IDs never use that protection.

Concrete supported case: register a dynamic table with fixed event-time user rows. A permitted User sends native batch B with validated Service A, then resends exactly the same user rows/table version/B under validated Service B (or switches from rootless to Service A). Both contexts are individually authorized. The second request is ACKed as if it were the original batch, although its accepted workload differs; the table contains only the first origin. Repeating under another permitted account also loses the second origin. This is a contradiction/refusal gap, not an unauthorized write or a claim that arbitrary UUID collision is likely. The task expressly requires detecting changed-context reuse, and request reconfiguration/retry is supported.

Why current proof misses it: `native_signal_values_and_attribution_are_validated_before_ack` at `verification_runtime.rs:5267–5270` changes rootless signal rows to a Service plus `staging`. That changes non-managed service/environment/subject dimensions, which the logical digest does bind. It does not establish that the managed context itself is bound. Dynamic tables deliberately have no such dimension columns.

Smallest correction boundary: extend the existing Scribe logical identity owner to bind stable accepted managed correlations, reusing `correlation_data_identity` or its declaration-driven selection. Keep volatile frame request ID and ingestion timestamp excluded so honest retries continue to converge. Feed the complete identity through the existing slice/WAL/fence/cache path; no new identity store, per-row SQL, transport-specific workaround, or lifecycle engine is necessary. This is a local hash-input correction under already approved exact-retry semantics, not a new persistent-data policy.

Focused closure proof: public native dynamic-table journey with fixed user event time/data and one explicit batch ID. An exact replay succeeds once; the same ID under a different valid workload, account pair, subject or Run refuses before ACK and leaves the original rows/origin unchanged. Exercise at least the workload case after Scribe restart or cache eviction to cover the durable fence, alongside the in-process duplicate cache. A focused unit check may additionally pin that only request/admission time variations leave the accepted identity equal.
