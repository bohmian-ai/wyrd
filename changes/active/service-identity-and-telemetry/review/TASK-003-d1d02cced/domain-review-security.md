## Material finding

### SEC-001 — INCORRECT: delegated native/OTLP writes use the subject's root instead of the acting Service's root

**Violated obligation.** REQ-022 requires workload stamping from validated execution context; REQ-024 preserves accepted-batch idempotency across ingress paths; INV-003–004 preserve independent exact execution ownership through delegation. The authentication supplement's “User A calls Service B” flow explicitly selects the outer Service actor's exact root as current owner. The storage supplement requires direct writes to retain validated context and Service descriptors to match that workload.

**Changed locations.** `crates/vala/vala-bifrost-redux/src/scribe/ingress.rs:728`; `crates/vala/vala-bifrost-redux/src/gate/attribution.rs:90`; `crates/vala/vala-bifrost-redux/src/gate/mod.rs:992`.

**Producer-to-consumer proof.** `DelegateToken` in `wyrd-auth/src/exchange_api_key.rs:295` keeps `subject_workload_uid` independent of `actor_workload_uid`. `TenantGrant::Delegation` in `issuance.rs:293` puts the former in top-level `workload_uid` and the latter in `act`. `AccessTokenClaims::into_verified` preserves that top-level subject root on `Principal` and `flatten_act_chain` preserves the current actor root in the last delegation step. `Principal.workload_uid` explicitly documents this distinction, and `wyrd_runtime::owning_root` is the existing owner of the selection rule. HTTP OTLP and gRPC OTLP/native preserve the verified principal and chain in `AuthContext`.

The new Gate paths instead describe and hash `auth.principal.workload_uid`. Public frames then pass only that subject principal to Scribe, whose new workload source is `frame.principal.workload_uid`. Consequently an ordinary rootless User delegated to a rooted Service writes `workload_card_uid = null`; a rooted subject delegated to another rooted Service writes the subject's root. In the latter case canonical Service dimensions can describe the wrong Service. Resource labels remain fallback values when the subject has no root, even though a validated acting Service exists. Gateway public calls already use the correct `owning_root` helper, so the same accepted delegation is attributed differently by surface.

**Reachable material consequence.** A User delegates to one stable Service account running releases R1 and R2, then both delegated contexts export identical uncorrelated OTLP payloads under the same environment. This is supported credential reuse and delegation. Both have the same subject/actor account pair and top-level subject root, so the new `otlp_batch_id` still collapses the two distinct acting roots onto one fence. Both requests can ACK while only one row set exists, and neither has truthful execution ownership. An ordinary single delegated export already loses its required workload attribution. No malicious token or forged selector is required.

**Smallest correction boundary.** Resolve accepted public write ownership with `wyrd_runtime::owning_root(&auth.principal, &auth.delegation_chain)` at Gate admission, and carry that accepted owner through the existing public frame/stamping path. Use that same owner for descriptor resolution and OTLP batch identity. Preserve the subject principal/root and delegation chain as distinct auth facts; do not rewrite them to masquerade as the actor. Keep trusted per-row frames' carried owners, scopes, account pair, tenant, Run and request semantics unchanged. This needs a small extension of the existing accepted-frame context, not another resolver or repeated transport-specific guards. Changing only the hasher or descriptor resolver leaves persisted rows incorrect; changing only stamping leaves root-separated exports deduplicated incorrectly.

**Focused closure proof.** Extend the existing delegated OTLP attribution journey to use one Service account with two validated roots and the same User subject. Export identical payloads through HTTP and gRPC under both roots, retry each, and assert two row sets with their exact actor workload/Service dimensions, original subject/actor account pair and exactly-once retry behavior. Cover native admission under a delegated root with exact persisted workload readback. A rooted subject whose root differs from the current actor provides a focused assertion that the implementation selected the actor, rather than merely filling a null. Existing `negative::identical_exports_from_two_principals_each_keep_their_own_attribution` exercises different actor accounts and asserts account/Run fields, so it does not distinguish this failure.

## Verification and limits

This is independent static source validation. No Cargo, database, provider, or broad capability commands were run. The orchestrator requested exclusive build-slot coordination; source inspection was sufficient to prove the finding without a build. Supplied task evidence records passing native-refusal, OTLP, gateway, trusted-origin and lifecycle journeys; those results were not rerun or treated as independent acceptance. Inspected proof includes `configured_gateway_headers_are_authorized_and_captured`, native signal forgery coverage, and the existing delegated publisher test. Their assertions support the passing boundaries but do not exercise current-actor root ownership across releases.

No cross-tenant read/write bypass or provider credential leak was established. No optional hardening is proposed. Runtime failure/recovery testing and complete storage acceptance remain outside this specialist report.
