## Proposed material finding

### TENANCY-001 — INCORRECT: promotion accepts contradictory composite partition evidence

**Obligation.** REQ-037 and AC-013 require complete typed tuples to remain truthful through publication and Forge. Original TASK-004 scenario 3 requires corrupt or contradictory evidence to fail closed; scenario 4 requires promotion to preserve the physical partition. Bifrost maintenance authority requires revalidating the exact file-list/object evidence before catalog mutation.

**Locations.** `crates/vala/vala-bifrost-redux/src/forge/scribe_promotion.rs:387` (`validate_promoted_object`, through line 426), and `:485` (`read_promotion_demand` identity comparison). Its producer is `scribe/file_list_writer.rs::build_inserts`; its omitted SQL authority is `vala-sql/src/queries/file_list.rs::{PromotableHotFileRow,HotFileCatalog::list_promotable}` at lines 37 and 153. The manifest value is built in `scribe/promotion.rs::ScribePublishedHotFileV1::data_file`.

**Evidence and reachable path.** Scribe writes the accepted full partition twice in one transaction: the time columns plus new `partition_dimensions` column, and `promotion_record.partition`. The promotion query returns only ID, path, checksum, size and JSON evidence, so it cannot compare those two copies. `read_promotion_demand` checks row identity, path, checksum, tenant and table only. `validate_promoted_object` verifies that the spec/order exist and that footer metrics agree, then calls `record.partition()?.time()`: it discards `values` and `time_index` before its only partition validation. None of the footer metrics compared by `first_metric_disagreement` bind the claimed transformed partition tuple. Finally `record.data_file()` constructs the manifest partition from the unverified full tuple and `revalidate_promotion` returns that `DataFile` for fast append.

A concrete case is an identity-partitioned file containing `customer = 'alpha'`: change only the persisted JSON's partition value to the valid same-type value `'beta'`, retaining the SQL dimension bytes, checksum, schema, time, spec and all metrics. The existing production path accepts the JSON and unchanged object bytes. This is the same durable-evidence corruption boundary already exercised by `tests/integration/forge/promotion.rs`'s record/metric/time mutations, newly extended to additional dimensions by this task; it does not require a public caller to alter SQL or a broader authentication threat model.

**Observable consequence.** Forge can publish unchanged alpha rows into an Iceberg manifest claiming beta. An equality filter on alpha may prune that file and lose accepted rows, while unfiltered scans still see them. This is source-integrity failure within the owning tenant, not a demonstrated cross-tenant disclosure.

**Smallest testable correction.** Preserve the existing accepted publication owner: project the complete durable file-list partition through `HotFileCatalog::list_promotable`, decode it with `PhysicalPartition`, and refuse any mismatch against promotion evidence before catalog work. Do not recompute historical partitions under current metadata, introduce another ledger, or weaken footer/checksum checks. The production producer already writes the authoritative complete tuple; consuming and comparing it closes this specific contradictory-evidence gap. Keep the existing retained-spec validation and time-bound physical proof.

**Closure proof.** Extend the existing promotion mismatch integration proof with a composite identity/null dimension. Mutate only a valid same-type dimension value (and separately null versus literal) in `promotion_record`; promotion must refuse before catalog append, leave the existing hot source queryable, and preserve snapshot/file-list settlement state. The intact record must still promote under its retained spec. A malformed JSON test or a nonexistent spec-ID test does not cover this failure.
