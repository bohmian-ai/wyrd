## Proposed material finding

### SYSTEM-001 — INCORRECT — Retry recovery is evaluated under the current revision before consulting accepted identity

**Obligation:** REQ-038 / AC-013; TASK-004 scenario 3 explicitly requires accepted work to resolve before current-write rules and retries across alteration/restart/publication to retain their original binding without duplication. This is request-level refusal correctness, not grounds for stopping a process or weakening conflict checks.

**Changed location:** `crates/vala/vala-bifrost-redux/src/scribe/ingress.rs:225–235`, with retry detection at `:592–593`.

**Producer-to-consumer evidence:**

1. `resolve_logical_frame` unconditionally loads `committed_revision` and selects its schema, partition spec and revision for every frame, without looking up the tenant/table/batch's accepted binding.
2. `prepare_and_dispatch` prepares rows under this current schema and calls `prepare_append` before either the in-memory duplicate lookup or durable fence reconciliation. `execution_lanes.rs:575–611` conforms/validates against that current schema, checks its expected fingerprint, then stamps current field IDs.
3. `preprocess.rs:830–840` splits the exact rows under the selected current partition scheme. `PreparedAppend::logical_identity` folds these slices; `LogicalBatchDigest::push_slice` at `:1022–1032` binds slice ordinal, schema fingerprint, per-slice row digest and length.
4. `shards.rs:1128–1143` accepts the fast duplicate only if this newly formed logical digest and slice count match. Otherwise the request takes the normal shard path. The SQL owner `vala-sql/src/queries/scribe_batch_commits.rs::matches_logical`, `record`, and `resolve` requires the original slice digest and count and refuses mismatches.
5. The existing durable `ScribeBatchCommit` records the logical digest/count, WAL coordinates and request/ingestion identity, but no schema/spec/order binding from which this path could select the original accepted revision. No alternative accepted-layout lookup exists in ingress. WAL and staged carriers preserve the original revision for replay/sealing, but that does not fix incoming retry validation, particularly after publication/WAL retirement.

**Concrete reachable failure:** accept one native batch containing two same-hour rows with the same customer and distinct `shard` values under `(hour(event_time), identity(customer), identity(shard))`; commit the compatible spec revision that removes `shard` through the provided catalog seam (the production harness `commit_spec_revision` already performs exactly this operation). Resend the same table/batch ID and identical original payload. The first acceptance created two partition slices; the retry creates one. The in-memory duplicate misses and durable fence refuses the different count/digest, even though the caller sent the same batch. A schema rename/addition can similarly reject the original request before deduplication, through current-schema validation or changed fingerprint. Restart/publication does not repair the binding gap.

**Observable consequence:** a caller recovering from response loss or cancellation cannot reliably recover its accepted batch across an allowed table revision. It receives an identity/schema refusal instead of the existing accepted result. Existing data is not shown to be lost by this finding; required idempotent recovery is broken.

**Sibling owners inspected:** native and canonical ingress both converge in `prepare_and_dispatch`; both use current `LogicalFrameContract`. In-memory duplicate index, normal shard fence record/reconciliation, WAL replay fences, staged restoration and retained write recipes were traced. The defect is upstream selection of current admission rules, not separate missing guards in each consumer.

**Smallest correction boundary:** extend/reuse the existing accepted-batch/fence authority so ingress can resolve an already accepted tenant/table/batch's original schema/layout binding before current-schema conformance and physical partition planning. Keep the original row/schema conflict verification, accepted time/origin and ordinary permission/tenant checks. New batch IDs continue to use the committed revision. Do not add another acceptance ledger, query engine, retry scheduler, compatibility path or process-level failure policy; do not simply acknowledge every existing ID without comparing the payload.

**Focused closure proof:** use the existing real catalog seam and append fixture to accept the two-row example, remove the extra partition dimension, resend the identical batch and require successful acknowledgement and exactly two original rows. Repeat after restart and after publication/WAL retirement. Add an ID-preserving schema rename/nullable addition variant using the original accepted payload. In every phase a modified payload must still refuse, with no extra visible rows and unchanged original ingestion/origin identity. A sort-only revision is insufficient because it does not change splitting or source-schema validation.
