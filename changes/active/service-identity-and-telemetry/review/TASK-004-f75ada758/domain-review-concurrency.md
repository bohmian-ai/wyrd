## Material proposed finding

### CONC-R2-01 — REGRESSION: Python's first describe can overwrite a completed replacement binding

**Obligation.** Preserve existing client binding/lifecycle behavior while adding bind-time version resolution. The public Python `use_table` contract carries a pre-operation binding into the connection and says a swap loses nothing (`python/wyrd/bifrost/_client.py:679`). The existing owning `Bifrost::handle` handoff explicitly preserves targets bound concurrently with connection; revision-13 writer binding must retain the selected declaration and version rather than silently substitute another declaration.

**Location.** `sdks/wyrd-sdk-python/src/bifrost/mod.rs:584–607`, especially the FQN-only test at line 605. Sibling writer: `use_table` at lines 725–734. Consumers: `table` at lines 747–753, `insert` at lines 771 onward, and native `TableConfig::{bind_version,writer_table}` / `Bifrost::insert`.

**Reachable producer-to-consumer schedule.**

1. A lazy Python Bifrost has a declared config A. Its first server operation enters `handle`, clones A at lines 584–588, and starts `resolve_table` at line 594. The binding lock is deliberately released, and `block_on` releases the GIL during the describe.
2. Another Python thread calls the public `use_table(B)`. B is a different config for the same FQN, for example an already-described correct schema replacing an earlier mismatched declaration. `Binding` is still Local; `use_table` replaces A with B and returns successfully.
3. The describe resumes. `handle` takes the current local B but compares only `local.fqn() == table.fqn()`. It consequently installs the resolved old clone A and discards B.
4. `table` now exposes A, and subsequent records use A's declared columns. `bind_version` only sets A's version; it intentionally preserves A's user schema. Correct rows for B can therefore fail sealing/schema validation after the supposedly successful replacement. This needs no metadata edit, TASK-005 API, process failure, or unsupported mutation.

The mutex prevents simultaneous memory access but does not make the asynchronous resolution result belong to the latest binding. This regression is introduced by the candidate's clone/describe/FQN merge; the base handoff moved the actual latest local config under the mutex.

**Smallest correction boundary.** Correct the existing Python `handle` handoff so an in-flight describe is applied only to the exact declaration it resolved, and a newer selected binding remains authoritative. Resolve whichever selected declaration still needs a version through existing native `resolve_table`, with no binding mutex held while releasing/reacquiring the GIL. Do not replace declarations merely because names match, add a second client, or hold the mutex over network IO. Preserve current describe errors and the existing behavior of unresolved/unregistered declarations.

**Focused closure proof.** A public Python threaded test delays the initial describe, replaces the binding with a different already-described config at the same FQN, resumes the describe, and proves `table` retains the replacement's schema/resolution and a correct row for that binding writes and drains. This must exercise Python/GIL lifetime behavior, not emulate it in Rust. The current sequential language journeys and admission-count unit test do not exercise this handoff.
