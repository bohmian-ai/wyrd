## Minimal counterexamples and limits

### Required, source-established no-op counterexample

1. Register a valid dynamic table with Bloom declaration `["service"]`; native definition and retained reference are at version 1.
2. Through the explicitly required R2 catalog revision seam, offer the identical serialized Bloom declaration plus `wyrd.bifrost.table-version=2`. Existing `commit_bloom_revision(..., &["service"])` produces exactly this transaction; alternatively the native SQL property-edit helper can offer those two properties directly.
3. `requested_table_version` sees a requested version and one other property, so its only accompanying-update check passes. Current version 1 satisfies requested 2. ApplyUpdates and the metadata builder preserve this transaction. `update_table` publishes a new pointer and inserts retained reference 2.
4. No schema, default spec, sort order, Bloom declaration or other writer/layout setting changed. Only bookkeeping/version metadata changed. Authority explicitly calls this a no-op, yet the committed version advanced.

This is a static source counterexample to an explicitly required seam behavior. It does not claim that an existing production HTTP client can issue PATCH today, or that the current Bloom journey already calls this duplicate case. It cannot be dismissed solely as test-helper misuse: R2 expressly requires the native seam's failed/no-op version semantics, and the fixture submits the same ordinary versioned property action used for effective Bloom edits. Fixing only the fixture to avoid offering the case would leave that required seam behavior and proof missing.

### Missing-bump SetProperties/RemoveProperties counterexample: source fact, limited reachability

A raw native transaction changing/removing `wyrd.bifrost.bloom-columns` without setting the version passes `requested_table_version` with `requested=None` and `definition_updates=0`. The native catalog updates its pointer without inserting a new retained reference. This demonstrates that the catalog does not itself classify Wyrd properties as definition-bearing. With cache refresh/restart followed by another legitimate version edit, current and retained descriptions could then disagree about the earlier version.

However, no current Wyrd production caller generating that transaction was established. `commit_table_revision` always adds the bump; public registration/builtin owners do not edit; remaining raw property setters are setup helpers. The authority describes committing **validated** complete edits, and TASK-005 supplies that mutation orchestration. Its future caller must commit definition properties and next version together. The observed native permissiveness alone does not justify a separate mandatory guard over all arbitrary properties, a property registry/configuration API, or migrating every unrelated fixture in this review. Treat this half of INV-05 as unproven for a separate reachable-production finding, rather than as another confirmed effect of the no-op path.

## Proposed finding for independent validation

**FOLLOWUP-01 (narrows INV-05), INCORRECT: a no-op Bloom declaration consumes a native committed table version.** Location: fork `catalog.rs:529–574,1331–1408`, consumed by Wyrd `catalog/iceberg_sql.rs:44–49` and the existing revision seam above. Violated obligation: revision-13 identical-declaration no-op semantics and R2's explicit catalog-seam failed/no-op proof. Observable result: version/reference 2 becomes committed with exactly the same effective definition, so a writer bound to 1 becomes stale despite there having been no definition edit.

Required correction outcome: at the existing catalog definition-publication owner, an unchanged effective definition offered with next-version intent must consume no committed version/reference. Preserve effective ordered Bloom changes, native schema/spec/order edits, expected-version conflict behavior, pointer/reference atomicity and uncertainty handling. Ordinary data/snapshot/housekeeping commits stay unversioned. Reuse the existing native metadata/update owners; no second allocator, ingest SQL, general property classification service, or duplicate PATCH workflow is warranted by this diagnosis. The distinguishing input is the effective definition excluding the version and metadata/snapshot bookkeeping, not merely presence of another update.

Smallest focused proof: extend the existing native catalog version test/seam with an exact repeat of an already committed Bloom declaration plus requested `r+1`; assert unchanged committed version and retained-reference count. In adjacent existing cases, assert reordered Bloom declaration advances once and actual changed declaration still participates in the existing one-winner CAS. Preserve the existing unversioned data-only case. This report does not require executing TASK-005's future public API or adding a broad property-misuse suite.

No additional independent finding is proposed. The missing-bump concern remains useful source context for the future validated mutation owner, with the reachability limit recorded above.
