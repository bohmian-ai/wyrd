## Proposed material findings

### MNT-004-1 — Public SDK descriptions expose wire strings instead of the approved native version type

Classification: **INCORRECT**. Locations: `sdks/wyrd-sdk-ts/wyrd/src/index.ts:1457`, its `TableDescription` import at line 7, generated `src/card-types.ts:5757`; `sdks/wyrd-sdk-python/python/wyrd/bifrost/_client.py:1416`, sync/async describe returns at lines 1036/1294, and native Python `src/bifrost/mod.rs:958`.

Revision 13's single-version contract and AC-010 require TypeScript SDK values to be `bigint`, converted directly from canonical wire strings; Python retains exact integers. Maintainer style requires public types to carry the actual contract. The Rust JSON serializer correctly emits a string, and the generated wire `TableVersion = string` correctly describes that wire. However, TypeScript aliases the public description directly to the generated wire type and returns `lifecycleValue<TableDescription>(...)` without conversion. Python similarly returns the serde JSON object unchanged and declares `table_version: str`. The new TS journey explicitly expects `"1"`, so this is established runtime behavior, not a declaration-only guess.

Concrete consequence: a caller using the approved SDK contract cannot perform version arithmetic or pass a native version value onward without inventing a per-caller conversion, and the public declarations teach the wrong contract. Large-version fidelity alone does not satisfy the promised native type. The server-side JSON representation must remain a string.

Smallest correction: convert once at each existing public language boundary, keep generated wire declarations as wire declarations, and expose a public description whose version is `bigint`/`int`. Update authored Python typing and the public TS projection together with their runtime conversions. Do not hand-edit generated wire declarations or change protobuf/JSON semantics. Prove the public describe result at 1, above `2^53`, and `i64::MAX`, using the existing boundary/unit fixtures; assert native types and exact values. Keep malformed/numeric wire refusal at the shared contract owner.

### MNT-004-2 — Python resolves declared bindings only before the first connection transfer

Classification: **REGRESSION**. Locations: `sdks/wyrd-sdk-python/src/bifrost/mod.rs:581–613,725–731`; public caller `python/wyrd/bifrost/_client.py:679–694` (shared by sync/async facades).

The R2 declared-writer correction resolves a declared existing table through the shared `NativeBifrost::resolve_table` owner before writing, and Python's public `use_table` remains a local operation. The new `handle` logic snapshots/describes only `Binding::Local(Some(table))`, then permanently changes the wrapper to `Binding::Native`. Later `use_table` calls in that state call the synchronous Rust `use_table` directly. That method deliberately does no describe, so a newly declared config has neither `resolved` nor `bound_version`; subsequent `handle` calls skip resolution, and `insert` always returns `NoActiveTable` from `TableConfig::writer_table()`.

Reachable sequence: register table T through one writer; on another query-only `Bifrost.connect()` client, call `use_table(TableConfig(T, matching schema))`, then `insert`. The equivalent declaration bound before the first server operation describes and writes successfully. The existing swap journey uses `use_table_by_name`, so it does not cover this transition. The native initial-bind resolver was added precisely because declarations previously wrote without a resolved version; this leaves that same regression on a supported subsequent binding path.

There is a related reachable overwrite within the new transfer: describe releases the GIL outside the binding lock; another thread can replace the local config with a different declaration of the same FQN. The transfer checks only FQN equality and reinstalls the old snapshot, losing the newer declaration. The existing Rust `register` method instead compares the complete declaration request before applying a response, which is the nearby repository pattern.

Concrete maintenance cost/consequence: one binding operation has different validity depending on whether an unrelated earlier read connected the client, and the wrapper's second binding state machine can install a declaration other than the caller's current one. Writes either refuse persistently or are encoded against the wrong locally selected schema.

Smallest correction boundary: keep local `use_table` local, but make the existing next-operation resolution/transfer cover every pending declared binding, including an already-connected client, through the existing shared `resolve_table` owner. Apply a describe result only to the exact declaration still selected; a concurrent replacement must remain selected and get its own resolution before its first write. Preserve the GIL/lock ordering, denied-writer errors, existing queue draining and Rust's synchronous `use_table` semantics. No new binding service or network call per row is needed. Add a Python-lifetime regression for connect/read → declared existing-table swap → insert/flush/read, and a blocked-describe same-FQN replacement case that proves the new declaration survives. Run these in Python, not a Rust imitation of Python concurrency.
