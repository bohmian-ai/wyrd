**Obligation.** REQ-037/038; revision-13 single-version contract; original scenarios 3 and 4; R2 accepted retry/admission section. Canonical built-ins use a versioned server projection. **Locations.** `gate/mod.rs:944–975`; `scribe/ingress.rs:232–272,434–465,621–642,684–714`; `scribe/committed_batches.rs:28–36,76–99`; `scribe/shards.rs:1138–1151,3798–3850`; `vala-sql/src/queries/scribe_batch_commits.rs:123–127,296–311,497–525`; `scribe/execution_lanes.rs:575–596`; catalog registration `bifrost_catalog.rs:1753–1784`. Existing supported evolution producer: `wyrd-testing/src/bifrost/revisions.rs:165–223,376–419`.

**Producer-to-result counterexamples.**

1. A canonical OTLP request is accepted at version 1. A compatible Bloom-only (or sort/spec) edit is committed through the task's existing catalog seam and current descriptor evicted. Retry exactly that canonical request. Gate derives the same deterministic batch ID but still sets `table_version: None` (`gate/mod.rs:944–964`). `resolve_logical_frame` selects current version 2 for `None`; admission conforms/stamps/partitions with version 2 before consulting the mirror. Even when Bloom-only evolution leaves every slice/data byte equivalent, `committed_duplicate_rows` requires version equality and misses the version-1 entry. The SQL fence's `matches_logical` also rejects the offered version 2. There is no branch that returns the original fence version and re-prepares the retained request. This honest retry is refused as an invariant contradiction. A cold mirror and restart do not fix it: the same current-first path reaches the same fence comparison. Changed partition grouping or names can fail still earlier.
2. Native caller sends an accepted ID under a current version after cache-cold current preparation (R2 expressly treats this preparation as provisional). The existing conflict read returns classification/error, not the accepted binding to retained comparison. The test at `write_read.rs:1539–1545` deliberately expects refusal of the identical accepted payload under current version. Replay suppression now correctly recovers from its provisional WAL attempt, but it does not make the live accepted retry successful.
3. A dynamic table is created with `customer`, then its existing native catalog seam performs the supported stable-ID rename to `client` plus nullable `note`. That producer commits native metadata/version and evicts caches; it does not update the creation SQL fingerprint. Fresh version-current input with `client`/`note` conforms to `current_definition.schema`, then `decode_rows` compares its new schema fingerprint against `table_registration`'s old SQL fingerprint and returns `FingerprintMismatch`. Even old-version native retries cease to be coherent if the mutable SQL fingerprint is later refreshed: the retained schema and current-registration fingerprint would disagree. This is why the selected R2 remedy removed fingerprint-as-definition authority while retaining structural validation and strict source conflict proof.

The existing V7 journey commits that schema edit but only queries afterward (`write_read.rs:1611–1625`), so green read projection does not prove new admission. The native accepted-revision journey covers a sort-only edit and explicitly resends the old version; it avoids canonical projection and fingerprint changes. These are the same accepted/current-definition binding deficiency as prior FIND-1, not separate findings per caller.

**Observable consequence.** Honest canonical delivery retries fail after a supported definition edit; accepted current-prepared retries cannot recover their original acceptance; fresh valid writes after supported schema evolution are refused. TASK-005 owns exposing/propagating edits, but TASK-004 already owns this shared catalog-seam evolution capability and its caller behavior. No PATCH endpoint or future cache broadcast is required to exercise these failures.

Use the bounded committed mirror's original binding before interpretation; on a cold path keep ordinary preparation provisional, return retained acceptance facts from the existing conflict read, roll back the tenant group's fresh fences on contradiction before comparing the retained source outside SQL, and resume only after equality. Recover from earlier preparation refusal through only the already approved exceptional accepted-ID path. Canonical and native payloads must use that same owner, with canonical projection bound to the accepted version on retry. Retain source/accounting ownership without a new whole-payload copy/hash pass on fresh writes. Resolve actual validation/schema/layout from one selected descriptor; remove the stale SQL fingerprint as a competing definition authority without dropping type/nullability/value/reserved-column checks or source-schema/payload/count/order conflict proof. Keep no extra successful-fresh-ingest SQL call, existing cancellation ownership, grouped rollback, canonical replay coordinates and tenant authorization.

**Closure proof.** Extend the existing accepted-revision and canonical fixtures: accepted unchanged canonical request across a Bloom-only edit; warm and cold retries across a partition-removal change; old native retry and new-current native write after stable-ID rename/nullable addition; original acceptance/origin and exact rows after restart/publication/WAL retirement. ### BR-004-3 — REGRESSION — connected declared rebind bypasses the new binding handshake

**Obligation.** Revision-13 native writer binding/transport; original public-consumer regression boundary; R2 “Every writer retains that binding” and shared bind-time resolution correction. The existing language declared rebinding methods are callers to close, not new API work.

**Locations and path.** Shared `Bifrost::connect_with` correctly awaits `bind_table` (`facade.rs:174–181`), but `use_table` merely replaces `active` (`:347–352`); `insert` now refuses any config whose `writer_table` is absent (`:711–718`). Python `src/bifrost/mod.rs:725–732` routes `use_table` directly to `native.use_table` once `Binding::Native`; subsequent `handle` only resolves a declaration while `Binding::Local` (`:584–611`). TS `native/src/lib.rs:797–802` also routes directly to shared `use_table`, and its existing public `useTable` (`wyrd/src/index.ts:1172–1175`) exposes that path. Neither adapter reaches shared `bind_table` through this call.

Create an existing registered table with one client. Connect a second client with no active table (or force the first Python connection through any operation), then call its existing `use_table(TableConfig(...))` / `useTable(TableConfig.fromJsonSchema(...))` for that registered destination and insert a valid row. The fresh declaration has neither `resolved` nor `bound_version`; this path never runs `resolve_table`, so insertion immediately raises `NoActiveTable`. Binding the same declaration before first Python operation or supplying it to initial `connect` works, making behavior depend on prior connection state. Before the version rollout, those declared rebindings supplied the FQN/schema that the producer used successfully. Existing public language descriptions still promise binding the new write target and retaining the old producer; no registration-before-insert prerequisite is stated there.

**Calibration.** Rust's synchronous `Bifrost::use_table` now explicitly documents that an unresolved declaration requires register or the existing asynchronous `bind_table`. That documented low-level setter is not itself a demand for synchronous network IO. The regression is that the existing language facades still use that low-level setter while presenting their established declared-binding workflow, and have not closed it through the available resolving boundary.

**Consequence.** Existing applications switching a connected writer using a declared schema cannot enqueue into an already registered table. Initial-connect and lazy-first-operation repairs do not close sibling bind callers.

**Smallest correction boundary.** Close existing declared-binding adapters through the already introduced shared `bind_table` / `resolve_table` owner, retaining previous producers and queued versions. Do not add a separate binding implementation per SDK or require recreating the client. Python can reuse its existing binding transfer and GIL-released resolution boundary. For TypeScript, the concrete recommended contract is to make the existing `useTable` binding operation await shared resolution before returning its previous binding, matching the already asynchronous named-binding operation; do not invent another public method or describe on every row. If the existing synchronous `useTable` return is a separately locked contract, that timing/signature choice needs explicit specification resolution before remediation. Do not introduce an ad hoc runtime to conceal the mismatch. The required outcome remains support for the existing declared-binding workflow; this finding does not prescribe a new API.

**Focused proof.** With a real already registered table, bind a fresh declaration after connection and write; switch between two such tables with buffered rows and verify each row once. Preserve wrong-declaration server validation refusal. Exercise Python and TS existing public binding methods, plus the corresponding shared resolving owner. Initial-bind-only success is insufficient. No PATCH or configuration edit is involved.
