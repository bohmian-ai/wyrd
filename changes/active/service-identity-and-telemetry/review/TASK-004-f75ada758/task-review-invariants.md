## Proposed findings

### INV-01 — INCORRECT — FIND-TASK-004-1 remains open at the accepted-binding producer

**Obligation:** AC-013; R2 “Client alignment and admission”; architecture `bifrost-design.md:603–620`. Canonical and native retries must resolve the fence's original definition and acceptance facts; a mirror miss must not add a read on normal fresh ingest.

**Locations:** `gate/mod.rs:953–967`; `scribe/ingress.rs:229–269,577–665,699–733`; `scribe/committed_batches.rs:30–42,96–112`; `scribe/shards.rs:1138–1153,3801–3847`; `vala-sql/src/queries/scribe_batch_commits.rs:94–138,285–316,487–513`.

**Producer-to-sink evidence:** Gate's deterministic canonical `batch_id` is based on the same original canonical content and attribution, while its frame always supplies `table_version: None`. `resolve_logical_frame` binds None to the current definition. `prepare_and_dispatch` materializes/stamps/splits first and only then asks the mirror for an equality match against that *prepared* version/digest. The mirror has no method returning its accepted binding/time before preparation. At a canonical resend after even a Bloom-only definition edit, the original accepted ID is prepared as version 2, cannot match version 1 in the mirror, and has `retry_only: None`, so the stale exception does not run. The existing fence's `classify` calls `matches_logical`, which requires version equality, and returns an internal identity mismatch. It never returns version 1 and acceptance facts to the CPU comparison owner. A partition edit also changes digest/cardinality; a schema rename/addition can fail before the mirror/fence is reached. The same branch handles native accepted IDs that arrive under a current binding and exceptional current-contract failures have no accepted-binding recovery.

The original-version native resend is a useful supported subset and now works, including cold `is_accepted`. It does not repair the common producer: that SQL query returns only a boolean and requires the caller to have already reproduced the original version/digest. Replay suppression is independently fixed, but successful later replay does not make the failed live retry meet the contract. The supplied journey now *asserts failure* for current-version same-ID, and changes only sort order; it does not test the required changed-grouping/canonical/before-preparation recovery paths. Neither mirror nor SQL load carries original `ingested_at` back to response/preparation.

**Consequence:** An at-least-once canonical exporter resending identical accepted content after a valid definition edit receives failure; changed current grouping/schema can prevent original acceptance recovery. This is a reachable existing Gate path, not a request for TASK-005's public PATCH or cross-replica invalidation.

**Minimum correction:** Finish the approved R2 retained-binding flow at the existing mirror/fence/admission owners: a warm lookup supplies the original version and acceptance facts before preparation; a cold current preparation remains provisional and the existing grouped conflict read returns the original binding/facts. Roll back the tenant group's fresh fences before retained-definition CPU comparison and resume only for a proven identical retry. Add exceptional recovery only when current preparation/stale validation refuses; unknown IDs retain the refusal. Preserve auth, limits, source conflict checks, tenant rollback, shard completion ownership and zero additional fresh-ingest SQL. Retain exact canonical-attempt replay suppression. No recipe blob, second ledger, new cache or read before every batch is needed.

**Focused proof:** Extend the existing accepted-revision/canonical fixture to accept at r1, change grouping, resend identical canonical content with no version claim and original native content with warm/cold state, and include rename/nullable-addition preparation failure, publication/WAL retirement and restart after a provisional attempt. Assert success once, original acceptance/time/origin, changed-content refusal, unknown-ID refusal, no fresh grouped fences on contradiction and unchanged normal SQL counts.

### INV-02 — INCORRECT — admission pairs the selected native schema with the creation fingerprint

**Obligation:** REQ-035/038 and R2's coherent current descriptor; architecture `bifrost-design.md:397–415`. This is substrate conformance, not TASK-005 edit orchestration or cache broadcasting.

**Locations:** `scribe/ingress.rs:228–269`; `catalog/bifrost_catalog.rs:1374–1381,1757–1787`; `scribe/execution_lanes.rs:574–595`; fixture `wyrd-testing/src/bifrost/revisions.rs::commit_schema_revision`.

**Evidence and reachability:** `resolve_logical_frame` separately reads `(registered_fingerprint, _) = table_registration(...)`, selects the current/retained `TableDefinition`, and combines the old SQL fingerprint with that definition's schema/scheme. `registration` gets fingerprint directly from `lookup_table_row`; eviction removes caches, not the creation SQL projection. `decode_rows` conforms new rows to the selected native schema and then compares their renamed/extended user shape to that old fingerprint. The supported `commit_schema_revision` seam commits stable-ID `customer` → `client` plus nullable `note` and evicts the definition, but never mutates the registration SQL row. A fresh writer following describe at that version sends its new schema and reaches `FingerprintMismatch`. The historical mixed-spec journey makes its last write *before* this schema change, so successful historical reads do not exercise the failure.

**Consequence:** After the explicit in-baseline schema seam used by TASK-004, valid fresh rows following current describe cannot be admitted. Even if TASK-005 later updates its SQL projection, retained-version retries would still be tested against whichever fingerprint that projection currently holds.

**Minimum correction:** Derive the admission source contract from the same selected immutable native definition used for conformance/stamping; reuse existing schema/fingerprint/conformance owners and keep mandatory reserved-field/type/value checks. The SQL registration remains useful for UID/existence/permission resolution, but cannot supply a different definition's expected schema. Update describe fingerprint projection if it exposes the same stale fact. No new normal-ingest SQL or hash of full layout JSON.

**Focused proof:** At the existing catalog evolution seam, rename/add nullable column, describe and submit fresh rows at the new version, then submit identical accepted r1 content under retained r1 and changed-content negatives. Verify original rows/IDs and new values exactly. This is a narrow extension of the existing schema evolution journey.

### INV-03 — MISSING — selected table version is discarded at hot publication and Forge output lineage

**Obligation:** REQ-037/038; R2 carrier matrix; architecture `bifrost-design.md:150–155,1249–1262,1284–1302,1404–1409`. Promotion and rewrites must persist the selected version beside exact native file evidence and resolve that version's native definition.

**Locations:** `scribe/file_list_writer.rs:230–269,359–377`; `scribe/promotion.rs:176–245`; `forge/scribe_promotion.rs:331–363,995–1000`; `forge/managed/policy.rs:106–126,178–196`; `catalog/layout.rs:533–565`; `forge/managed/executor.rs:263–290`; rewrite snapshot evidence in `forge/publication.rs`.

**Producer-to-sink evidence:** Assembly and staged records correctly retain `key.table_version()`. `build_claim_inserts` receives that key but passes only partition and sort ID into `PublishedArtifactFacts` and `PublishedHotFileIdentity`. `ScribePublishedHotFileV1` consequently has no `table_version` field. The resulting SQL promotion JSON is identical in definition identity for two Bloom-only versions sharing schema/spec/order. Forge validates membership in the *current metadata's* schema/spec/order histories; footer decoding picks the newest schema whose names/IDs match, not the accepted version's exact retained definition. No retained-definition version lookup is possible because the durable record dropped the version.

Rewrite policy likewise carries schema/spec/order IDs and fixed `writer_recipe: "v2"`, not `TableVersion`; `forge_data_location` uses `/data/forge/v2`, and rewritten output/snapshot lineage never records an output `table_version`. The source tree has no version read in those Forge rewrite owners. This is not fixed by pinning a native table object for the attempt: the selected definition still disappears from durable outputs.

**Consequence:** Ordinary demonstrated Bloom-only edits create physically distinct accepted definitions that promotion/rewrite lineage cannot distinguish. After staged/WAL retirement, those files cannot be mapped unambiguously back to the accepted definition; Forge has reverted to native descriptor inference at exactly the boundary revision 13 replaced. A record with a retained but wrong sort ID can pass membership checks rather than being refused for disagreement with its version. This breaks persisted identity/truth even when exact reads and Bloom membership tests happen to pass.

**Minimum correction:** Preserve the existing version once at the current source of each carrier: pass assembly version into promotion evidence and preserve it through SQL evidence/lineage; resolve the version at Forge's existing revalidation owner and compare its schema/spec/sort/partition with the existing durable/footer proof. For rewrites retain the explicitly selected output version in the existing attempt policy and publication evidence/path mechanism, using it for writer policy rather than the fixed competing recipe. Keep current checksum, footer metrics, fences, native compaction grouping/execution, ambiguity reconciliation and data-file retention behavior. Do not invent another history store or rewrite old files automatically.

**Focused proof:** Extend the current complete/partial/empty/reordered Bloom journey and promotion corruption fixture to assert persisted accepting/output versions even when native schema/spec/order IDs coincide; a contradictory version/native-descriptor pair refuses before append, intact older versions still promote, and a rewrite records its selected version without relabeling input lineage.

### INV-04 — INCORRECT — deployment changes can reinterpret an existing table version's writer target

**Obligation:** Complete definition includes writer/layout settings and resolved defaults; storage supplement “Native metadata publication”; architecture `bifrost-design.md:131–135,1284–1292`.

**Locations:** `catalog/bifrost_catalog.rs:1214–1227,2021–2032`; `forge/managed/policy.rs:153–160`; `forge/compact.rs::ForgeConfig.default_target_file_size_bytes` and `forge/managed/policy.rs` deployment-default tests.

**Evidence:** Creation persists a target only when explicitly provided. Omitted `CompactionRegistration` writes none. `ForgeTablePolicy::extract` then calls `declared_bytes(..., config.default_target_file_size_bytes)` every time an attempt is planned. The current tests intentionally demonstrate the same metadata producing a different target under another deployment default. Thus creating a normal default table at version 1 and restarting/reconfiguring Forge changes that version's target without a definition edit or new retained reference.

**Consequence:** `table_version` does not identify complete writer behavior: replicas/deployments can write different file targets under the same supposedly immutable definition. This is an actual existing configuration path, not a hypothetical new edit API.

**Minimum correction:** Resolve the existing authorized deployment/table default at table-definition creation (and effective edits when supplied later), persist it in native metadata, and make versioned writer resolution read that committed value. Reuse the current target property and validators; do not retune it, add a setting or introduce a second counter. Preserve scheduler/admission controls that are not definition policy.

**Focused proof:** Create with omitted target under the normal configured default, reload the same native definition with another Forge deployment default and assert its persisted target/writer behavior remains unchanged. A newly created table can take the new authorized default. Existing policy tests suffice as the test owner.

### INV-05 — INCORRECT — native version boundary validates update syntax instead of an effective definition

**Obligation:** AC-021; R2 atomic native publication; specification revision 13 “One table version.” Bloom-only edits must advance once, and no-op must not allocate a committed version. The required supported catalog seam is explicitly in TASK-004 scope.

**Location:** pinned Iceberg SQL `a34f3885c`, `crates/catalog/sql/src/catalog.rs:529–574,1331–1348` (`requested_table_version`, `update_table`).

**Evidence:** Only `SetCurrentSchema`, `SetDefaultSpec`, `SetDefaultSortOrder` increment `definition_updates`. `SetProperties` and `RemoveProperties` increment only `other_updates`. Consequently a `SetProperties` for the already-supported `wyrd.bifrost.bloom-columns` without `table-version` is accepted as data-only, publishes another native document with the *same* version, and leaves the retained version reference at the old definition. Conversely sending the existing identical Bloom value together with `r + 1` satisfies `other_updates > 0` and allocates a new reference despite no effective definition change. The existing fixture's `commit_bloom_revision` can invoke the identical-list case directly; this requires no hypothetical API. Native current-ID requirements and pointer CAS do not decide effectiveness or protect the version invariant against these operations.

**Consequence:** The publication owner permits one version to identify two different complete definitions, or consumes a committed version for a no-op. Current and retained lookup can disagree about the same version. TASK-005 cannot repair already-supported catalog publication by refreshing a cache.

**Minimum correction:** At the existing native publication boundary compare the effective pre/post definition (including Wyrd writer/layout properties) rather than counting arbitrary updates. Reject a changed versioned property without the one-step version update and refuse/no-op an ineffective requested edit without allocating a reference. Keep data/snapshot/housekeeping changes unversioned and preserve current atomic transaction, pointer CAS, conflict semantics and immutable references. Use the existing configured version/property owner; no independent Wyrd ledger or additional ingest SQL.

**Focused proof:** Native catalog tests: changed Bloom-only set/remove without bump is refused with unchanged pointer/reference; identical Bloom declaration plus requested bump consumes no version; reordered Bloom list is effective and advances once; ordinary data-only commits do not advance; competing valid property edits still yield one winner.

## Scope and limits

The audit followed shared producers through Gate canonical/native frames, catalog registration/current/retained definitions, CPU conformance/stamping, request partition union, mirror, grouped SQL fence and canonical-coordinate replay, seal/WAL/staged carriers, recovery recipe resolution, full-key capture, SQL publication evidence, Forge demand/worker/footer validation, native grouping, rewrite policy/execution/publication, retention and SDK writer binding. Integration seams affected by generated schema/contract changes were considered; the authorized merge itself is not evidence of unrelated scope drift. Existing permission and tenant ownership were preserved in the traced paths.

No new current-edit cache race finding is proposed: TASK-005 owns production committed-edit refresh. No table-recreation finding is proposed without a production drop/recreate caller. Conservative definition retention is acceptable without an established retry horizon. More benchmarks, a new cache/ledger, speculative guards and optional refactors were skipped.

The overall FAIL is based on the source-reachable acceptance and persisted-definition failures above, not missing runtime reruns or unmeasured throughput. Independent validation should retain prior FIND-TASK-004-1 and allocate new stable IDs only to confirmed new causes.
