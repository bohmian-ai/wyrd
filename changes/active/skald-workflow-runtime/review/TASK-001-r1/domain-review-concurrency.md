# Concurrency, Cancellation, and Runtime-Lifecycle Review

## Review Findings

### Important

- **CONC-001 — A cancelled scheduled step can be terminalized with zero attempts.** `WorkflowExecutor::execute` marks a step `running` before spawning its task (`crates/skald/skald-workflow/src/workflow.rs:212-228`). The attempt counter is not advanced until the child is polled (`workflow.rs:370-380`). Cancellation or total-deadline expiry can win in that interval, abort the `JoinSet`, and route the cancelled join through `RunLedger::step_cancelled` with the still-zero atomic counter (`workflow.rs:249-285`; `run.rs:166-172`). That produces `status: cancelled`, a start/end time, and `attempts: 0`, contrary to the approved snapshot invariant that cancelled active steps have at least one attempt and that unstarted steps alone have zero. The existing cancellation test waits until the provider attempt has been running for one second, so it cannot cover this race (`workflow.rs:1112-1148`). **Observable consequence:** the same cancellation request can yield two contract-distinct snapshots depending only on Tokio polling order. **Required correction:** make the running/attempt-begun transition one coherent owner-visible transition, or terminalize a scheduled-but-never-begun task as `unstarted` with neither timestamp; add a deterministic test that cancels after scheduling but before the first attempt is polled and asserts all status/timestamp/attempt invariants.

- **CONC-002 — Valid public timeout values can panic the executor.** `WorkflowStep.timeout_seconds` accepts the full `u64` wire range and `WorkflowSpec::validate` does not constrain it (`crates/wyrd-spec/src/card/workflow.rs:85-104,224-250,349-354`). Planning converts that value directly to `Duration` (`crates/skald/skald-workflow/src/plan.rs:278`), then execution performs unchecked `Instant + Duration` arithmetic for both run and step deadlines (`crates/skald/skald-workflow/src/workflow.rs:188,382`) and again for the Agent deadline (`workflow.rs:436-444`). Tokio delegates `Add<Duration>` to `std::time::Instant`, which panics when the resulting instant is unrepresentable; `timeout_seconds: 18446744073709551615` reaches this path before a portable terminal `WorkflowRun` can be returned. `WorkflowExecutionLimits.deadline` exposes the same unchecked path to local Rust callers. **Observable consequence:** authored YAML or a local options value can unwind the caller/runtime instead of producing validated failure or bounded execution, violating the public-input panic rule and the task's terminal-snapshot contract. **Required correction:** handle deadline construction with checked arithmetic at the owning execution boundary (and reject an unrepresentable authored timeout through the existing field-specific validation path if rejection is required), then add focused maximum-value tests proving no panic and the selected stable outcome.

- **CONC-003 — The retry counter overflows for an accepted retry policy.** `WorkflowRetryPolicy.max_retries` accepts every `u32`, with no validation ceiling (`crates/wyrd-spec/src/card/workflow.rs:85-104,360-368`). `StepTask::run` increments its `u32` attempt counter before checking exhaustion (`crates/skald/skald-workflow/src/workflow.rs:368-378,412-427`). With `max_retries: 4294967295` and an immediate retryable failure, the required `max_retries + 1` attempt cannot be represented: debug builds panic at the final increment and release builds wrap to zero, after which the exhaustion comparison permits further attempts. `RunLedger::terminal_reserve` already acknowledges the arithmetic problem by saturating the advertised maximum attempt count (`crates/skald/skald-workflow/src/run.rs:331-340`), but execution does not. **Observable consequence:** an accepted local Workflow can panic or fail to terminate according to its declared retry count, and its attempt accounting cannot satisfy the approved exact invariant. **Required correction:** reject a retry count that cannot be represented by `WorkflowStepResult.attempts` at the pure contract boundary, then test the highest accepted value and the rejected overflow case; do not add a downstream wrap/saturation guard that silently changes declared retry semantics.
