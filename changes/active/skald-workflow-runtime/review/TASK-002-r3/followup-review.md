## 2. REPO-R3-12 versus system bounded assessment

**RESOLVED: retain a narrow standards violation at the shared facade; no demonstrated starvation/outage or shared-server failure.**

AGENTS §6 states “Do not block inside async request paths without an explicit blocking strategy.” `architecture/references/languages/rust-core.md:473–474` prescribes `spawn_blocking` for CPU-bound work inside an async runtime and says “never block the async worker.” The same reference keeps parsing/validation synchronous; this does not authorize synchronous filesystem IO on an async polling thread. Wyrd design `:417–432` expressly requires the async Rust client facade, lazy registry composition, and reuse of existing loader/Skald owners. Making the public method synchronous or turning the loader into an async parser would violate or unnecessarily expand those boundaries.

`crates/shared/wyrd-client/src/workflow.rs:51–64` directly executes `wyrd_loader::load(path)` and `path.canonicalize()` before its first await. The loader is synchronous and performs actual filesystem IO: `wyrd-loader/src/parse.rs:68–77` calls `std::fs::metadata` and `std::fs::read`; sandbox/discovery also resolve/read local paths. These calls execute on the thread polling `Workflow::from_path`. Local bundles never reach the registry await. The facade owns no explicit offload boundary.

Reachable callers are concrete, not hypothetical: Rust public journey `workflow_loading.rs:293,310` awaits from multi-thread Tokio tests; the shared facade unit test `workflow.rs:281` also awaits it. Node `sdks/wyrd-sdk-ts/native/src/workflow.rs:113–114` awaits it in its exported native async function, and public TS `Workflow.fromPath` calls that native operation (`wyrd/src/index.ts:1353`). Python `src/workflow.rs:504–506` uses `py.detach` and the shared `wyrd_runtime::runtime().block_on`; that releases the GIL and avoids an ad hoc runtime, but supplies no offload for the shared Rust/Node future. No server request handler calling this facade was found; this is a client-runtime standards finding.

An existing mechanism already covers the missing boundary: Tokio's blocking pool, used inside the same shared client at `auth.rs:600–610` (`RenewableMint::mint_into`) and `bifrost/facade.rs:529–551` (`ProducerDrainer`), plus shutdown at `bifrost/handle.rs:553`. These are different capability owners and should not be repurposed as a generic loader service. `wyrd-runtime/src/lib.rs` provides a runtime singleton, not a generic blocking helper. There is no need for another runtime, dedicated pool, trait, configurable loader or SDK-specific workaround.

**Smallest supported proposal:** keep `Workflow::from_path` as the composition owner, move its existing synchronous bundle load and entry canonicalization together onto `tokio::task::spawn_blocking` with an owned PathBuf, await their result, then continue the same request-local body/ref hydration and lazy registry reads. Keep ordinary synchronous parsing/validation synchronous. Preserve loader diagnostic mappings; handle the join outcome with the existing public error channel rather than an external-IO unwrap. Document that an already-started blocking read may finish after future abandonment and cannot publish a partial Workflow or write durable state. Confirm this boundary statically and rerun the actual Rust/Node loading journeys; no synthetic host load or starvation test is warranted.

The system report's request-local read-only/no-durable-state assessment remains valid. It describes filesystem work and cancellation honestly but does not establish conformance to the separate blocking-worker rule. Conversely, REPO-R3-12 establishes direct blocking work on the polling thread, not measured scheduler starvation, unbounded registry retry, process termination, or a server availability regression. Retain only the standards claim and bounded correction.
