### REPO-R3-12 — VIOLATION: async file loading runs blocking filesystem work on the caller's executor

**Rule:** AGENTS §6 requires an explicit blocking strategy in async request paths; rust-core.md Async (`473–474`) says never block the async worker. The required async client facade is not an exception.

**Location/evidence:** `crates/shared/wyrd-client/src/workflow.rs:51–64` calls `wyrd_loader::load(path)` and `path.canonicalize()` directly before its first await. The existing synchronous loader performs filesystem discovery/reads and YAML parsing; `crates/shared/wyrd-loader/src/parse.rs:68–77` concretely performs `std::fs::metadata` and `std::fs::read`. The public native Node `load_workflow_from_path` at `sdks/wyrd-sdk-ts/native/src/workflow.rs:113` awaits this future, as do async Rust callers. Python's detached block_on releases its GIL but supplies no blocking isolation for the shared facade used by Rust/Node.

**Consequence:** a slow local/transitive bundle read holds the executor thread polling this future until filesystem work finishes; unrelated work and cancellation cannot progress on that thread. This is a directly reachable structural runtime violation, not a claim from a synthetic host-load test.

**Smallest testable correction:** isolate the existing synchronous bundle load/canonicalization behind the shared facade's ordinary blocking boundary, retaining the synchronous loader and exact lazy registry composition. Do not add a parser, executor or dedicated pool. Verify the actual Rust/Node loading journey after the change and confirm the shared async method no longer performs filesystem work on its polling thread; preserve loader diagnostics and documented cancellation/no-partial-write semantics.
