## Local finding

### SYS-001 — Python registry selector refusal is classified as DataCard validation

**Classification:** INCORRECT. **Obligation:** Revision 12 INV-007 stable error semantics and repository error guidance (errors describe the actual operation and relevant field). The non-Workflow consumers below are additionally within the user's explicit supplemental request, even though their historical implementation is not claimed to originate in this diff.

**Exact locations:** `sdks/wyrd-sdk-python/src/state/mod.rs:2611–2620` (new Workflow load); `:3010–3045` (`selector_for_kind`); `:3051–3070` (shared space/name/version parsers). Producer is `crates/wyrd/wyrd-interfaces/src/error.rs:62–73`, whose `validation` is explicitly a DataCard-specific constructor. Public metadata is `wyrd-spec/src/error.rs:1912–1922`.

**Reachable trace:** Workflow load invalid UID, incomplete/mixed selector, or malformed named field calls this Data-specific constructor directly or through shared parsers. For the supplemental boundary, Model get (`state/mod.rs:2383`), Prompt get (`:2549`), all typed delete views via `delete_registry:2037`, and resolve-latest/query field parsing call the same selector/parsing owners. Their malformed selector is refused before network IO, then `From<WyrdPyError> for PyErr` preserves the constructed catalog error unchanged.

**Observable consequence:** A malformed Workflow/Model/Prompt registry selector raises `WYRD_DATA_400_VALIDATION`, title `DataCard validation failed`, remediation `Fix the DataCard schema, artifact, stats, or interface metadata.` None of those DataCard artifacts was examined. The TS Workflow selector instead uses the existing request `WyrdError::Validation`. The committed Python journey explicitly asserts the wrong domain at `test_cards_crud.py:589,592`; documenting that emitted value does not correct its semantic ownership. This is a diagnostic/agent recovery-contract defect, not an integrity bypass: invalid selectors still fail before reads/writes and sibling server availability remains intact.

**Minimum testable correction:** At the SDK's generic registry selector/parsing boundary, use existing derive-backed `WyrdError::Validation` and preserve relevant field details; route all existing selector consumers through that corrected boundary. Do not redefine `wyrd_interfaces::WyrdPyError::validation` globally: it legitimately owns DataCard schema/interface validation and changing it would alter unrelated Data behavior. Preserve generic selector rules, exact/version/UID assertions, read ordering, GIL/runtime mechanics and server errors. Correct new Workflow direct selector failures at their same owning boundary; update item-local docs/generated declarations and retained journey expectations. No new catalog, parser, transport or compatibility alias is needed.

**Closure proof:** Through the Python runtime and public Cards views, malformed space/name/version and incomplete selectors on Model/Prompt (and Data registry selectors) report generic request validation before registry IO; Workflow mixed/versionless/malformed UID/field selectors do likewise. Assert code, title/remediation and field details, while a genuine DataCard schema/interface refusal continues to return DataValidation. Reuse current Python unit/journey setup, then run affected owning lanes. This reviewer did not execute those checks and does not claim the excluded follow-up closes this finding.
