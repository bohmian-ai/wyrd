## Proposed material finding

**SYS-001 — INCORRECT: successful Card compensation clears repair state without recording its physical deletion.**

Obligation: REQ-018 requires the existing lifecycle's deletion to be reflected in the same inventory; TASK-001 explicitly owns deletion recording and cleanup agreement. Location: `components/cards/service.rs:1952` and `:2295`, with the completion condition in `commit_card_failure:2670–2673`.

Reachable path: declare a Card with two files; complete the first through the public storage completion route, which ACKs a completed inventory fact. Leave the second upload incomplete until its existing expiry. The existing reconciler enters `reconcile_card_claim` because `manifest_needs_cleanup` recognizes the expired unfinished upload; `cleanup_card_artifacts` physically deletes the first completed file. It then passes `cleanup_succeeded=true` to `commit_card_failure`, which transitions the Card to Failed and immediately clears reconciliation. Neither this path nor `abort_card` records `record_card_deletion`. The completed inventory fact survives indefinitely, and delayed completion facts still have no tombstone to dominate them. The Failed Card remains eligible for `get_card_by_uid` (`queries/cards/get.rs:17` excludes only Deleted), so `list_card_artifacts` can continue returning the first file even after the lifecycle deleted its bytes. Public SQL inventory and direct `ObjectInventory::card_objects` also see the stale completion.

Sibling enumeration: `cleanup_card_artifacts` has four callers: `reconcile_card_claim`, `abort_card`, `finish_card_delete`, and `reconcile_cleanup_claim`. The latter two record the existing Card-wide tombstone; the former two omit it. This is one cleanup-completion cause, not separate per-caller defects. The older SQL path also omitted a cleanup delete on these successful-compensation branches; the finding is the explicit new inventory/deletion obligation, not an unrelated historical availability claim.

Material consequence: the sole completed-object authority advertises an available object after authorized lifecycle cleanup removed it, and the durable cleanup owner considers work finished so process restart does not repair it. This violates an explicit acceptance boundary and affects ordinary interrupted multipart/multi-file declarations.

Smallest safe correction: reuse `record_card_deletion` for successful compensation cleanup before reconciliation is marked successful. If recording fails or is cancelled, preserve the Failed transition and existing pending cleanup reconciliation so `reconcile_cleanup_claim` retries; do not introduce a queue/repair scan or move physical deletion into inventory reading. Preserve existing best-effort cleanup and per-Card failure isolation. A local guard in listing would hide invalid authority rather than record the required deletion.

Focused proof: exercise the existing reconciler on a multi-file declaration after one file completes and another upload expires; assert successful physical deletion is followed by a dominating inventory deletion, including after replay of the old completion. Hold/refuse the deletion ACK and assert the Card failure remains durable with cleanup retry pending, then release/retry and assert reconciliation clears only after recording. Cover the sibling abort path through the same cleanup-completion boundary where applicable.
