## BEH-001 — Envelope hydration bypasses missing completed-object inventory

Classification: **INCORRECT**. Violates REQ-004/005/013, INV-001, and V1/V3's obligation that envelopes and hydration resolve through the one inventory, with missing inventory retryable.

Exact locations: `crates/wyrd/wyrd-server/src/components/cards/service.rs:341` and `:371`; producer/readback evidence in `crates/wyrd/wyrd-server/src/components/storage/inventory.rs:282`, `:331` and Cards `write_card_blob` at `:2839`.

The producer writes an envelope completion fact and waits for its Scribe ACK. The approved contract explicitly permits that acknowledged row to remain temporarily unreadable. `card_objects` returns `CardObjects { envelope: None, ... }` on an empty query (and on table-not-found). `card_files` requires only completed manifest files. For an Active metadata-only Card there are no manifest files, so it accepts the empty result. `hydrate_card` then takes `row.card_blob_uri`, reads backend bytes and returns the Card without consulting `inventory.envelope` at any point. The same bypass happens if file rows are visible but the envelope row is not. All three Card getters share this path. There are no other production consumers of `CardObjects.envelope`; only the added test consumes it.

Observable consequence: Card hydration succeeds using a Postgres object pointer despite unavailable completed-envelope inventory. This contradicts the express pointer allowance: pointers may identify an object, but cannot supply an alternate inventory when its Bifrost record is unavailable. This is a supported normal delayed-visibility case, not an invented malformed database input.

Smallest safe correction: have the existing hydration owner require the expected completed envelope from its already-resolved CardObjects, retaining the SQL URI for identity/consistency checking and existing tenant/Card binding and blob integrity checks. Missing required envelope must return the existing retryable visibility code. No additional lookup, cache, query barrier, hashing or new error family is necessary. Ensure envelope-derived paths remain validated at the read boundary. This has a small local correction burden; a separate envelope resolver would duplicate existing readback.

Focused proof: through the existing Card read API, make a metadata-only Active Card's envelope row unavailable while the SQL pointer and backend bytes remain; assert the exact retryable visibility code, then restore visibility and obtain the same Card. Also preserve a file-bearing Card's normal hydration and path validation. V1's normal-presence assertion does not exercise this gap.

## BEH-002 — Successful initial compensation deletes bytes without recording deletion

Classification: **MISSING**. Violates REQ-018 and the task's instruction to own deletion recording and preserve consistent cleanup/inventory state.

Exact locations: `crates/wyrd/wyrd-server/src/components/cards/service.rs:1952`, `:2295`, and `:2671`. Relevant changed deletion integration: `:1995`, `:2255`, `record_card_deletion` at `:2577`.

Realistic path: a multi-file declaration completes file A and records its inventory fact; upload B fails, is aborted, or expires before Card activation. The existing declaration saga explicitly leaves partial progress for server reconciliation (`crates/shared/wyrd-client/src/cards/saga/mod.rs::declare`). `reconcile_card_claim` detects B through `manifest_needs_cleanup`, then `cleanup_card_artifacts` deletes A's completed bytes. On successful cleanup it calls `commit_card_failure(..., true)`, which marks the Card Failed and marks reconciliation succeeded. Neither branch records a deletion. Initial abort cleanup has the same omission. Only explicit delete and the separate retry-cleanup entry point record deletion, so success on the first cleanup attempt permanently skips recording and prevents a later retry from repairing it.

Sibling writers/callers inspected: all four `cleanup_card_artifacts` callers (`reconcile_card_claim`, `reconcile_cleanup_claim`, `finish_card_delete`, `abort_card`), its completed/pending artifact cleanup, both `commit_card_failure` callers, `fail_card`, and `mark_card_reconciliation_succeeded`. The common difference is initial failure compensation versus retry cleanup, not independent defects per caller.

Observable consequence: the sole inventory continues reporting an available completed object whose bytes the authorized lifecycle removed. Failed Cards are not hidden by SQL `get_card_by_uid` (only Deleted Cards are filtered), so Card artifact listing can still return A and download initialization can issue a plan for bytes already removed. Public Bifrost inventory readers also retain the false completed state. No later completion replay is required to demonstrate the inconsistency.

Smallest safe correction: make the existing successful cleanup boundary account for its Card deletion fact before cleanup is marked durably succeeded, reusing `record_card_deletion` and existing cleanup reconciliation. Cover both initial failed-declaration paths and retain the already-correct explicit/retry-delete paths without double ownership. An inventory failure must leave cleanup retryable; preserve the Failed transition, current physical deletion authority, and existing retry semantics. No new scanner, queue, retention rule or per-file tombstone mechanism is warranted. Merely changing listing would hide stale authority and would not close the root cause.

Focused proof: complete A on a pending two-file Card, force/abandon B through the supported lifecycle, let the first reconciliation cleanup succeed, and assert bytes gone, Failed Card retained, inventory deleted and empty, and cleanup success only after its fact is accepted. Exercise the initial abort sibling if it cannot be covered through the common corrected boundary; retain the V2 stale completion assertion. Failure of the inventory write should preserve cleanup retryability.
