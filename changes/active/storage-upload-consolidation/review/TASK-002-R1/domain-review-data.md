## DATA-001 — Expired File sessions never leave the shared sweeper queue

- **Classification:** INCORRECT / REGRESSION.
- **Violated obligation:** TASK-002 requires a File to use the shared full upload lifecycle; REQ-003 and its outcome explicitly include shared initialization/transfer/completion. The approved change preserves existing coordination and reconciliation, rather than introducing an unreclaimable session class. This also regresses the existing shared cleanup capability for Card uploads when File rows occupy its bounded batch.
- **Changed producer location:** `crates/wyrd/wyrd-storage/src/service.rs:202` (`file_upload_init`), particularly 209–224, and `crates/wyrd/wyrd-sql/migrations/20261029000000_file_upload_sessions.sql:4`.
- **Failing consumer:** `crates/wyrd/wyrd-storage/src/sweeper.rs:297`; bounded selection at `crates/wyrd/wyrd-sql/src/queries/storage/admin/multipart_uploads.rs:60`–68.

**Reachable producer-to-consumer path.** Planning now inserts ordinary `storage_multipart_uploads` rows with NULL Card UID and `<tenant>/evidence/sha256/<digest>` paths. Abandon a File transfer, or terminate initialization after `insert_initiating_upload` commits and before backend initialization/pending persistence. After its existing expiry or initialization grace, `expired_uploads_batch` selects that row exactly like a Card upload. `Sweeper::abort_one` validates the path with `tenant_path::validate`, whose `FULL_PATH_RE` accepts only `<tenant>/cards/<card>/<relative>`. It rejects every evidence path before backend abort or `mark_aborted_if_open` runs. `sweep_expired_uploads_batch` logs the error and proceeds, leaving that File row pending/initiating and eligible on every later tick.

**Observable consequence and materiality.** Abandoned remote multipart uploads keep their provider resources, File coordination rows never reach the existing aborted state, and an orphaned initiating File continues occupying the active storage-path unique index. Re-initializing that File cannot clear an initiating row because `find_pending_for_dedupe` only selects pending rows, so subsequent planning conflicts persist. Additionally, the cross-tenant discovery query orders oldest expiry/grace first and applies `LIMIT batch_size`; once that many abandoned File rows accumulate (default 100), every later expired Card or File row is excluded indefinitely. This is normal cancellation/restart recovery for the newly supported upload class, with a concrete shared-service regression, not speculative payload garbage collection.

**Smallest testable correction.** Extend the existing sweeper and its discovered row shape to retain the persisted Card/File ownership, then apply the same owner-directed Card versus evidence path validation used by request-side lifecycle operations. Keep strict tenant validation, existing provider abort, tenant status mutation, and reconciliation semantics; do not add another worker or GC policy. A small shared validation owner may be reused if needed; broad path acceptance without checking persisted ownership is insufficient. Deleting the sweeper or skipping File rows leaves the resource/status leak and starvation invariant unresolved.

**Focused closure proof.** Extend the existing PostgreSQL sweeper integration coverage with File-owned pending and orphaned initiating rows, proving each is marked aborted. With a deliberately small batch, put an expired Card after older expired File rows and run successive existing ticks: File rows must retire so the Card is reclaimed. Verify an initiating File can be planned again after reclamation, and retain existing malformed/foreign path refusal. For remote multipart, existing backend-abort coverage should establish that the accepted evidence path reaches the same abort operation; no new harness is necessary.
