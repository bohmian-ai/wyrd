## 1. RunEvidence::pin describes the wrong durable state

At `crates/shared/wyrd-client/src/verify/mod.rs:484–489`, the added cancellation contract says a transfer failure leaves the failing session open and later Files unplanned. Both assertions are false on supported paths:

- `Target::execute` and `Target::enqueue` call `run.pin(client)` at lines 423/450 before execution/submission. `pin` prepares all distinct file descriptions, sends one complete plan request at lines 532–536, and only then iterates the returned uploads at lines 538–555. `FileSource::open` and each shared upload can fail before the next iteration.
- HTTP `components/verification/routes.rs:137–147` and MCP `mcp/verification.rs:205–214` both enter `VerificationControl::evidence`. Its full body (`components/verification/service.rs:351–409`) inventories and initializes every missing File before returning the response. Each `file_upload_init` reaches the separately committed initiating and pending transitions in storage `service.rs:286–396`. Therefore, for three missing Files A/B/C, once the plan returns and B's transfer fails, C already has its pending upload session. Dropping the client future never aborts C. The same is true when reopening B's path fails after planning.
- The shared client (`storage/mod.rs:114–160,222–235`) transfers and then sends completion. Storage `upload_complete`/`finish_upload` (`service.rs:546–647`) can mark a failed completion terminal Failed, or commit Completed before the client observes a response. `mark_failed` (`:1558–1587`) commits the failure; `verified_object_head`/`verify_object_head` call it on verification failure. Consequently the failing/current session is not necessarily open, and an ambiguous completion/cancellation can already have completed it.
- Cancellation while the plan request is in flight can leave the prefix of independently committed server sessions without any response. The server's own new cancellation prose at `components/verification/service.rs:346–350` already explains that prefix correctly. Local validation/hash failure before the request creates no server sessions.

**Consequence and minimum correction.** The required rustdoc currently gives a maintainer the wrong recovery/resource-ownership model: serial transfer does not mean serial session creation. Replace only this paragraph with phase-accurate prose: all missing Files are planned before serial transfer; earlier acknowledged completions survive; untransferred plans remain open for expiry reclamation; the interrupted session may remain open or have reached a terminal state; a lost plan response may leave initialized sessions. A fresh invocation consults completed File inventory and initializes independent sessions for the remaining files rather than resuming abandoned sessions. Do not promise immediate inventory visibility or infer rollback from an error. No new cancellation handler, retry loop, abort behavior, lifecycle change or runtime test is necessary.

## 2. Initializer recovery prose falsely includes terminal Failed rows

`crates/wyrd/wyrd-storage/src/service.rs:185–190` expressly says an initiating row “or a row marked failed” is reclaimed by the sweeper after grace. The File sibling at `:232–235` similarly assigns a session left by failure after initiating commit to sweeper reclamation without distinguishing its terminal state. The internal initializer's `:280–285` cancellation prose should remain consistent with the same phase distinction.

The producer is `drive_backend_init_or_mark_failed` (`:1221–1252`): backend initialization refusal calls the full `mark_failed` body, which commits SQL status Failed, then returns the refusal. SQL `multipart_uploads::mark_failed` (`crates/wyrd/wyrd-sql/src/queries/storage/multipart_uploads.rs:568–593`) sets terminal state only from initiating/pending. The consumer `admin/multipart_uploads::expired_uploads_batch` (`:46–88`) selects only expired Pending or grace-aged Initiating. `Sweeper::abort_one` consumes exactly those rows; it does not select Failed rows. A pending transition may also already have committed when a response or later lock-transaction commit is interrupted, so “after initiating commit” alone cannot promise Initiating state.

**Consequence and minimum correction.** The public Card and File initialization docs incorrectly promise recovery of terminal failures by a worker that will not select them. In the existing initialization doc inventory, describe only open Initiating/Pending rows as eligible for their existing grace/expiry sweep; identify persisted Failed as terminal without promising its reclamation. Preserve the internal explanation that an unrecorded backend upload may rely on provider expiry. Concise shared-owner wording or a link to accurate internal semantics is sufficient; do not add Failed to the sweeper, delete terminal records, or invent payload-GC/retention behavior.
