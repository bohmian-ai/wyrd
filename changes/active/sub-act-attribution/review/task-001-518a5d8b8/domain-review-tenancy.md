## Proposed finding

### TEN-001 — SYSTEM creation records SYSTEM as its own subject

- Classification: **INCORRECT**.
- Violated obligations: spec INV-002 (SYSTEM never appears as `sub`), REQ-001/005 creator attribution on `wyrd.auth_service_accounts`, REQ-002 registration convention and INV-007 immutable creation attribution.
- Exact changed location: `crates/wyrd/wyrd-sql/migrations/20260601000028_system_principal.sql:79` (the new pair is populated with `candidate, candidate`). Reachable producer: `crates/wyrd/wyrd-server/src/components/platform/provisioning.rs:456`.
- Evidence and reachability: authenticated tenant creation passes `Attribution::direct(caller.principal_id())` through `establish_and_promote` into `establish_tenant_administration`. That owner uses its `attribution` for administrator and API-key inserts. Its SYSTEM insert instead calls the existing `provision_system_principal(&mut conn)` owner, whose SQL takes no creator context and stamps the new SYSTEM id into both columns. Every newly provisioned tenant therefore has a live inventory row with SYSTEM as subject, and the true creating principal is lost permanently. Repeated provisioning preserves this wrong pair through `ON CONFLICT DO NOTHING`. Fixture seeding and the defining migration's existing backfill also invoke this same provisioning owner.
- Observable consequence: the standardized creator contract is false for a production principal row, and an attribution query reports internal execution as the subject instead of the principal that created the tenant. This does not grant SYSTEM authorization or expose another tenant's data.
- Smallest correction boundary: extend the existing provisioning owner to retain the already available creator Attribution from authenticated tenant provisioning, as neighboring administrator/key creation does. Keep its same-tenant transaction, one-SYSTEM uniqueness, idempotent return, active/tokenless constraints and original creator on retry. Update all callers together; do not add a second provisioning/identity-resolution path or a read-time rewrite. For genuinely callerless migration/fixture bootstrap, do not silently invent another production sentinel convention: preserve the approved invariant and establish whether approved authority already defines the bootstrap creator; otherwise explicitly route that unresolved mapping to specification authority. The production caller needs no new product or security decision.
- Focused proof: extend the existing tenant-provisioning integration path to read the created SYSTEM row through the tenant connection and assert its stored pair equals the authenticated platform creator pair and differs from the SYSTEM id; repeat provisioning and prove the pair and SYSTEM id remain unchanged. Keep the existing seeded-active-SYSTEM assertion. Use the exact selector for that owning test when executing remediation; no new harness or broad journey suite is needed.
