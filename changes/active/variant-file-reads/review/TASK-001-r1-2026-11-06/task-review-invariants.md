## Proposed finding

### INV-001 — VIOLATION: eager query allocations bypass the admitted memory pool

**Obligation.** TASK-001 explicitly requires temporary query allocations to remain governed and releasable. `architecture/bifrost-design.md`, Resource and failure invariants, requires hard-bounded Oracle memory and bounded Wyrd-owned buffers. This applies to the new expression evaluation and retained output, independently of the original generation's ownership.

**Changed location.** `scribe/memtable.rs:2293–2310` invokes `AdaptedRequirements::evaluate` for every captured batch; `:2573–2577` allocates filtered physical/logical copies and `:2604–2622` materializes computed output arrays. `ReadableSource::project` appends each result to the complete output vector rather than yielding it. `LiveCapture::read:1990–2023` retains all those results and returns only `Arc::clone(&source.charge)` as accounting ownership.

**Reachable producer-to-consumer path.** A supported ordinary SQL computed projection, such as `SELECT value + 1 FROM table`, or the task's covered `v ->> 'a'`, is absorbed by `LiveScribeExec::try_swapping_with_projection`, signed into the placeholder, parsed by `signed_requirements`, and passed by `ScribeTailResolver::resolve` into `FetchLiveTailRequest`. `LiveTailSource::open` directly calls synchronous `FetchLiveTailService::open_capture`; that calls `LiveCapture::read` and executes the new evaluator across every in-range batch before returning. A computed arithmetic/text result creates new Arrow buffers. Those outputs survive in `CapturedRead`, then `LiveTailBatches`, then the follower's `MemtableSource::inner` for the plan's lifetime. A partial filter can additionally copy the physical closure before evaluating outputs.

**Why existing ownership does not cover this.** `scribe/memory.rs:353–385` defines `RetainedArrowCharge` as the exact original generation bytes transferred at retirement. It never grows to cover a query's newly computed/filter-copied arrays. `ScribeTailResolver::live_leaf:498–521` forwards those original charges unchanged. `ReadRequirements`, `AdaptedRequirements`, `LiveCapture::read` and `FetchLiveTailRequest` carry no execution pool or allocation reservation. The existing admitted envelope is a ceiling on a `MemoryPool`; it does not intercept Arrow allocation. `resources.rs:3951–3991` implements query memory ownership through explicit `MemoryConsumer` registration and `try_grow`; the evaluator makes no such call. Holding the source charge keeps source buffers safe but cannot debit the new buffers against that query ceiling.

**Observable consequence and materiality.** A query over many canonical numeric batches now retains a fresh output array across the entire captured partition before its first stream batch. Previously the canonical source projection shared original arrays and the computed `ProjectionExec` evaluated on pull. The new retained allocation scales with all captured rows and can exceed the query's granted memory even when the SQL consists of an ordinary arithmetic projection. Concurrent admitted queries multiply the excess while all remain under their recorded pool usage. This is a supported-use resource-governance failure with shared-process availability consequences, not a request for arbitrary-expression hardening or a benchmark optimization. Existing whole-root reconstruction costs do not establish permission to add ungoverned eager computed outputs.

**Sibling tracing.** The unchanged `requirements: None` path and shard/persistence callers do not need the new computed-output allocation. Local and remote followers use the same `ScribeTailResolver`/tail owner and both are affected. Staged siblings evaluate requirements through the existing Filter/Projection/DataFusion Parquet plan; published siblings keep their existing plan. `MemtableSource` retains original charges through cloning and projection rewrites, so changing its generation-charge meaning would wrongly change sibling ownership. Leader output-drain reservations occur after source resolution and cannot govern the Scribe's earlier retained materialization.

**Smallest required correction.** Reuse the existing admitted query memory-pool/reservation mechanism for newly allocated retained expression/filter/fallback buffers at the shared memory-read owner, keeping original generation charges separate and unchanged. Carry the corresponding query allocation ownership with every retained result/plan/stream that can outlive resolution, release on errors and cancellation, and refuse growth at the existing pool ceiling. Bound the evaluation workspace as part of that same existing execution budget. If retaining all evaluated batches cannot fit, the source must fail with resource exhaustion rather than allocate outside the grant. No new resource root, resident representation, generic execution framework, public API, or concurrency protocol is required. Merely charging returned output on the leader, counting bytes after the complete allocation, or retaining more copies of `RetainedArrowCharge` does not close the failing boundary.

**Focused closure proof.** At the existing follower/memory owner, use the existing bounded query pool with multiple captured batches whose computed output collectively exceeds the grant; establish typed resource refusal and no reservation residue. Also prove a fitting computed/filtering read increases the query's accounted allocation and releases it after read/plan/stream drop or cancellation, while original source charges remain held through retirement until the last source holder drops. These checks can extend current owner tests; no new test harness or broad journey lane is needed for this correction.

## Concurrency and verification limits

No materially new concurrency protocol was found: capture selection, read-lock ordering, registry leasing, retirement and charge handoff remain unchanged. New evaluation is synchronous over immutable captured sources. A separate concurrency-domain reviewer is therefore not required on this evidence. The existing cancellation journey starts its pause after source evaluation, so it proves eventual ownership release of an open producer, not allocation-budget enforcement during read construction.

No optional hardening or unrelated pre-existing debt is proposed. This review does not claim independent runtime validation or TASK-002 staged lifecycle/performance completion. The single correction concerns already-required query memory governance and does not require a specification change.
