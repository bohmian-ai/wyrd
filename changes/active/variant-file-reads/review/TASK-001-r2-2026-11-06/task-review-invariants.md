## Producer-to-consumer accounting trace and alternatives

The production producer is the Scribe peer's admitted `OracleExecution`, issued from the process's composed Scribe capability. `request_session(execution)` and `OracleExecution::session` preserve its runtime memory pool. The resolver forwards that exact `Arc<dyn MemoryPool>` through `FetchLiveTailRequest.memory` to `FetchLiveTailService::open_capture` and `LiveCapture::read`. Registration goes through `GovernedMemoryView::register`; `try_grow` checks the existing view ceiling, reserves from `BifrostResourceGovernor::try_reserve_pool_memory`, grows the one shared `TrackConsumersPool<FairSpillPool>`, and rolls back on refusal. There is no second resource root or independent query tracker in the remediation.

The result owns the query reservation alongside generation charges. `live_leaf` moves it into the source, all rewrite/pruning paths preserve it, and stream wrapping pins it independently of plan lifetime. Construction failures drop pending results and reservations. During synchronous capture evaluation cancellation cannot interrupt a Rust stack frame, but failure/return still transfers or drops its owners; this is the existing execution shape, not a new cancellation protocol. Query/view teardown retains the core root until the last consumer drops. Generation retirement continues to transfer its original lease into `RetainedArrowCharge`, separate from query allocations.

Existing alternatives were compared. `RetainedArrowCharge` already solves original-buffer ownership and must remain unchanged; it cannot represent query-created filtered or computed arrays. `unshared_arrow_bytes` already solves buffer alias exclusion and should be reused, rather than adding another size walker. `MemoryReservation::new_empty` already creates a workspace consumer under the same core-backed view, so no tracker, allocator hook, resource framework or pool redesign is necessary. The existing `MemtableSource` owner is sufficient for returned batches; moving execution into a second source workflow is unnecessary. The remaining gap is local to what the existing evaluation owner includes in its workspace reservation.

## Proposed retained finding

### FIND-TASK-001-1 — VIOLATION — filtering workspace remains outside core accounting

**Disposition:** partially closed; retain this stable ID. No distinct new finding is proposed.

**Violated obligation.** Original task requires temporary query allocations to remain governed and releasable. The validated remediation specifically requires current-batch evaluation/fallback workspace to be bounded within the existing execution budget, and every affected allocation to use the one core accounting source. Bifrost resource authority bounds Wyrd-owned buffers and preserves sibling service capacity. Limiting an uncharged allocation to one batch is not the specified budget enforcement.

**Exact affected locations.** `scribe/memtable.rs::ReadableSource::project:2335–2358,2394–2399`; `AdaptedRequirements::evaluate:2640–2674,2710–2716`.

**Reachable failing path.** Consider supported `SELECT COUNT(*) FROM table WHERE value > 0` over a canonical captured integer batch containing both negative and positive values. The signed closure contains `value`; the ordered outputs are empty, as the existing filter-only COUNT behavior requires. `ReadRequirements::adapt` successfully rewrites this ordinary filter against the same canonical schema. In `evaluate`, `mask(adapted, &physical)` succeeds, so the logical callback is never invoked and the workspace reservation remains zero. `filter_record_batch` materializes the selected integer values in `physical`, which the Wyrd evaluator explicitly holds until it finishes the batch. The zero-output loop adds no arrays; the result has the surviving row count and zero columns. After `evaluate` drops that filtered closure, `project` measures the empty result and calls `query.try_grow(0)`. The filter's materialized closure therefore never appears in either the query pool or the authoritative root.

This is not merely a hypothetical kernel-internal scratch buffer. It is a named Wyrd-held `RecordBatch`, produced and retained by its own evaluator. The pinned Arrow fork is `ca5feff3b1c523640a03acaa437096b8934c3749` (`Cargo.toml` patches); its `arrow-select/src/filter.rs::filter_record_batch` applies its predicate to each batch column, and partial selection of a primitive array creates new selected values. The existing owner test `covered_variant_paths_avoid_unrelated_reconstruction` already exercises the same empty-output/partial-filter shape, including learned data; its unbounded pool simply does not test governance.

**Observable consequence and materiality.** With core capacity consumed by sibling Scribe/Oracle/Forge holders, this supported query can still create and retain the filtered copy and succeed without any positive reservation or resource refusal. Multiple accepted queries can do so concurrently. The architecture does not promise interception of every dependency allocation or freedom from OOM; this finding does not demand either. It concerns the explicitly included Wyrd-owned evaluation workspace, for which the existing remediation already requires accounting. Returned-output cleanup and a zero post-drop counter cannot prove that missing peak accounting.

**Smallest safe correction boundary and burden.** Extend the existing `ReadableSource::project` / `AdaptedRequirements::evaluate` workspace ownership to include the newly materialized physical/filter closure while it lives, through the same supplied core-backed pool. Reuse the existing `MemoryReservation` and alias-aware sizing. Refuse workspace growth when that view/root cannot cover it, and release or transfer workspace ownership when outputs take over shared allocations so the same buffers are not charged twice. Preserve original-generation charges, staged leases, exact filtering and zero-column cardinality. This is a bounded local completion of the existing workspace mechanism; do not change resource owners, introduce a second ledger, intercept arbitrary Arrow internals or add a new source workflow. Removing workspace enforcement or charging only final outputs cannot close the explicit gap.

**Focused closure proof.** Extend the existing core-backed owner test with an ordinary successful adapted partial filter and empty outputs. Use a source batch whose filtered physical allocation exceeds the view's remaining capacity: the read must refuse and leave neither pool nor core-root residue. A fitting case must return exact zero-column cardinality and release all workspace at completion. Check source inspection or an existing narrow observation that the workspace was charged while held; a final zero counter alone is insufficient. The fixture can reuse the present `value` batches, composed resources and `ReadRequirements`; no new server journey, dependency or harness is needed. Retain the existing multi-batch computed-output/refusal tests.
