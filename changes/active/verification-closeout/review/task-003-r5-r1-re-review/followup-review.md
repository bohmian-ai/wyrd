## Oracle shutdown: headroom-only child is reachable

`crates/vala/vala-bifrost-redux/src/resources.rs:2458-2525` gives each admitted Oracle query a private view of the process pool with `MemoryHolder::Oracle`, but the admission slot itself reserves no bytes. Its `OracleExecution::memory_pool()` can be retained by a child after the admission envelope drops; the new admission test at `oracle/admission.rs:2521-2589` demonstrates precisely this child-after-slot lifetime with **fallible**, governed growth. The pool's `MemoryPool::grow` reaches `GovernedMemoryRoot::grow` (`resources.rs:3624-3660,3489-3512`), which calls `reserve_pool_memory_infallible`. That method charges `min(growth, shared free capacity, remaining query ceiling)` as governed Oracle bytes and places the rest in the **global** `infallible_headroom_bytes`; it adds only the governed portion to `oracle_query_memory_used_bytes` (`resources.rs:2670-2711`). A Forge rewrite view also uses this infallible path with `MemoryHolder::Forge` (`resources.rs:1902-1921`), so adding the global headroom counter to Oracle shutdown would count sibling bytes.

A concrete path is: Forge already holds the shared cap, Oracle acquires a slot (which precharges no bytes), its child calls infallible `grow(4096)`, and the admitted Oracle envelope drops while that child retains its pool. Then `active_queries == 0`, Oracle governed query bytes `== 0`, and Oracle infallible headroom is `4096`; the existing resource test at `resources.rs:4731-4759` establishes that growth past the query grant enters headroom. `oracle/admission.rs:739-790` enables both wakeups correctly but checks and reports only `oracle_query_memory_used_bytes`, so it may finish and report a clean drain before the child releases its real Oracle bytes. `wyrd-server/src/state.rs:684-700` accepts that report. This is the residual of prior **FIND-TASK-003-2**, not a new independent issue. The smallest correction boundary is Oracle-attributed infallible bytes in the existing pool/governor owner, consumed by the existing shutdown predicate/report; preserve global capacity, sibling exclusion, and both wakeups. A focused headroom-only child test can prove the gap.

## Forge restart: startup recovery precedes quiescence ownership

`crates/vala/vala-bifrost-redux/src/forge/worker.rs:2166-2192` awaits `start_and_drain` **before** creating the stop-token drop guard and calling `ForgeLoopQuiescence::enter()`. The shared flag begins `true` (`worker.rs:704-735`), and the server restarts a joined failed worker future using a clone that retains that flag and the same owner (`wyrd-server/src/app/supervise.rs:119-180`, `boot/mod.rs:1244-1270`). Startup's `drain_recoverable_work` invokes `reconcile_one_prepared` and `execute_one_recoverable_cleanup` (`worker.rs:2219-2266`); the latter invokes the ordinary `execute_claim` path (`worker.rs:2293-2335,3976-4022`). Its single-attempt pool can start a detached plan (`worker.rs:5983-6020,6194-6224`); both ordinary claim execution and Prepared reconciliation can spawn heartbeat tasks (`worker.rs:5270-5300,4593-4647,8350-8400`). Dropping the parent future on panic or abort does not join the spawned plan or heartbeat, and the process shutdown token passed to recovery is not cancelled by the absent guard.

If this interruption happens during startup recovery, the predecessor flag remains `true` despite possible child work. The successor's startup passes `Some(self.owner)` to `reclaim_attempts` (`worker.rs:2227-2244`), and `vala-sql/src/queries/forge_tasks.rs:883-903` selects same-owner `claimed`/`running` attempts even before lease expiry. Exact-attempt and table fences constrain later writes, but they do not prove physical quiescence before the self-reclaim required by prior **FIND-TASK-003-7**. The added unit test at `worker.rs:9140-9174` manually calls `enter()` before its panic, so it cannot detect this startup window. The smallest correction is to extend the existing quiescence and cancellation ownership across startup recovery while using the predecessor's prior state for the initial reclaim choice, and mark joined only after this incarnation's child work has stopped. Keep fast reclaim after a genuinely joined predecessor and lease-expiry recovery otherwise. A focused interrupted-startup recovery test is the direct proof.
