## Proposed findings

**SYS-R1-001 — INCORRECT Oracle drain predicate and residual report omit live Oracle headroom.** `oracle/admission.rs:752,773,784-790` uses only `ResourceSnapshot::oracle_query_memory_used_bytes`. `resources.rs:2688-2707` records infallible query growth beyond the managed cap or query grant in `infallible_headroom_bytes`, and deliberately adds only the governed part to `oracle_query_memory_used_bytes`; `resources.rs:3489-3513` shows that `MemoryConsumer::grow` reaches this path. The existing resource test at `resources.rs:4731-4758` confirms a live Oracle query can have both counters, while `:1745-1752` says the shared reserved total includes the headroom. In a mixed pod with the shared cap already occupied, an Oracle child can grow entirely into headroom, outlive its admission slot, and leave `active_queries == 0` and `oracle_query_memory_used_bytes == 0`. Shutdown then reports zero Oracle residual bytes and finishes before that child's memory returns, violating the bounded Oracle drain and truthful residual report required by the task; this can let subsequent process teardown overtake an Oracle child. **Smallest correction:** make the existing resource governor expose exact Oracle query resident bytes including its infallible portion, and have Oracle shutdown use that owner-attributed figure. Preserve the global cap, both enabled wakeups, and exclusion of Scribe/Forge headroom. **Focused proof:** hold an Oracle child with only infallible headroom after its admission slot drops while another role has governed bytes; verify shutdown reports/waits for the Oracle bytes, then completes when the child drops without waiting for the other role.

**SYS-R1-002 — REGRESSION recovery panic bypasses Forge's quiescence guard.** `worker.rs:2174` runs `start_and_drain` before `quiescence.enter()` and the stop-token drop guard at `:2183-2192`; `ForgeLoopQuiescence::new()` starts true (`:713-735`). Yet `drain_recoverable_work` can claim and execute a cleanup (`:2285-2322`), `execute_claim` can spawn a plan runner (`:3976-4020,6194-6222`) and a claim heartbeat (`:5270-5300`), and Prepared reconciliation spawns a heartbeat (`:4593-4647`). If recovery panics or its task is aborted after those spawns, child work may keep running because the process shutdown token is not cancelled and the run is dropped before its event-loop guard exists. The supervisor then joins the failed run and restarts a clone with quiescence still true; `:2234-2244` passes this same owner to `reclaim_attempts`, whose SQL at `vala-sql/src/queries/forge_tasks.rs:883-902` clears unexpired Running attempts. That reopens the exact overlap/fencing risk FIND-TASK-003-7 sought to remove, this time during startup recovery. **Smallest correction:** cover the entire worker run, including startup recovery, with the shared quiescence state and an unwind/abort cancellation token that its recovery children observe; mark joined only after owned work has actually stopped. Keep ordinary lease-expiry recovery after an unjoined predecessor. **Focused proof:** arrange a recovery claim with a live plan or heartbeat, abort/panic its parent before join, and assert the next supervised clone does not immediately self-reclaim that unexpired attempt and old child stops or loses its lease; the current flag-only unit test cannot prove this path.
