# Resume verification workflow UI tasks 005–007

Status: finalized design for task revision, 2026-11-23. The maintainer's request
to revise tasks 005–007 selects these recommendations. The subsequent explicit
instruction to revise, approve and commit approves specification revision 8;
runtime qualification and task acceptance remain separate.

## Recommendation and outcome

Revise the permission wording in the UI specification, then revise the three
remaining tasks around the implemented Repository-parent authorization model.
Keep the approved centralized visual design and reuse the existing loaders,
execution inspector, host actions and public reads. Do not rebuild discovery,
introduce another permission evaluator, or finish unrelated onboarding first.

The resulting journey is: a person granted one Repository opens its latest PR
review set, selects an earlier set or exact member execution, inspects retained
judgments/progress/outputs, decides a pending approval if separately permitted,
and distinguishes GitHub delivery from the recorded verification verdict.
Another Repository contributes no rows, counts, facets, history or downloads.

TASK-003 is implemented, as confirmed by the maintainer. Its stale task header
does not reopen it. Existing implementations from tasks 001–004 and supplements
are inputs; narrowly affected shared code may change under 005–007.

## Maintainer agreement — retained status correction

On 2026-11-23 the maintainer agreed to correct the existing backend execution-status
projection so a retained PR execution keeps its PR association, generation and
GitHub delivery outcome after its PostgreSQL scheduling row is removed. Reuse
the retained Bifrost records and existing status response; no new endpoint.
The bounded first scenario of TASK-007 must prove the same PR/generation,
verdict and delivery state after supported queue cleanup, with Repository-scoped
read success and inaccessible-reader not-found. This does not restart TASK-003
or make every TASK-005/006 activity wait on that correction. The agreed backend
scope is recorded in approved specification revision 8 as REQ-021/AC-014;
this design record alone never substitutes for the specification.

The storage distinction is retained execution facts versus control-plane data,
not a PostgreSQL-free UI/server. Execution history, inputs, outcomes, progress,
approval receipts and delivery records belong in Bifrost; file bytes use the
storage owner with retained publication associations. Registry definitions,
current identity/grants/sessions and live scheduling/coordination retain their
PostgreSQL owners. The UI uses server APIs and never databases directly. Retained
inspection must not require leftover scheduling rows or current source Cards;
that does not promise the entire request works while PostgreSQL is unavailable.
Recording lag is explicit availability, not permission to serve evidence from
PostgreSQL. This follows the existing verification/security/Bifrost authorities.

## Proposed TASK-005 revision: PR review sets and readable execution navigation

### Connected flow

1. A tenant-bound PR link supplies Repository identity and PR number, optionally
   an exact generation. Existing retained `execution_inputs` rows supply trusted
   parent identity, provider host/ID, source pins, selected policy, recorded_at,
   generation and complete frozen member IDs. These records, not GitHub inventory
   or a currently readable policy Card, are the history input.
2. Through the existing `bifrost.query` Node/MCP executors, select bounded current
   or earlier generations for that PR. Use the retained observation time for
   current selection, never head SHA, row arrival or the dashboard's time picker.
   A pinned generation that is absent must not silently switch to latest.
3. Read the selected generation's members and summaries through the same managed
   tables. Reuse existing execution/result selection logic: a checkpoint-selected
   result supplies queued-work verdicts, not whichever result row arrived last.
   Do not directly reuse the dashboard's fixed time-range/slack assumptions for
   arbitrary old sets. Keep member/query bounds explicit and show truncation or
   incomplete retention rather than claiming a visible subset is the complete set.
4. Extend shared UI schemas/loaders/components, the host PR route and URL state,
   Repository activity and existing Verify filters/columns/groups. General PR
   links follow current; explicit set/execution links stay exact. Back/copy/refresh
   preserve those choices. No per-member detail/status hydration to render lists.
5. Opening a member reuses `loadExecution`. Keep its separate definition lookup.
   If that lookup fails, retain its refusal and offer selection of recorded
   requirements, invocations and outputs within the same inspector. Use existing
   compact judgments, bounded invocation/publication reads and node/producer URL
   state. Do not fabricate declared nodes/edges from partial execution records.
   Avoid the current skip of completed recorded progress solely because a
   definition was unavailable when that progress is needed for selection.

Exact route names, query decomposition, page sizes and private helpers remain
implementation-owned. Extend the existing `execution.ts`, `observe.ts`,
`schemas.ts`, loaders/catalog, `verify-host.ts` and Repository host owners as
needed; adding another executor or generic orchestration framework is unnecessary.

### Proof to add around existing behavior

- Actual PR admission with multiple Verifiers, same-head fresh generation and new
  head: current resolution, bounded older sets and frozen IDs are correct.
- Mixed/all-refused and delayed member retention: membership is not reduced to
  successful runnable work, and incomplete retained state is explicit.
- Two Repositories sharing a Verifier: a family-scoped reader and a minimal custom
  Card-read role see only their Repository's sets/counts/facets/pages. Table-only
  permission does not disclose hidden managed rows; exact-version scope does not
  follow another policy version. Inaccessible exact links are ordinary not-found.
- No GitHub configuration or Verifier-definition grant: PR navigation and recorded
  outcomes/outputs remain usable, definition stays refused. Grant/removal while
  the session remains signed in affects the next authoritative reads.
- A historical set outside the Verify range, source change during refresh, Card
  deletion where retained authority remains valid, and bounded/empty/error states
  cannot repin selection, fabricate completeness or erase readable evidence.
- Real browser PR → older set → member → output → return, plus Node/MCP/custom/
  built-artifact read parity. The no-definition selection surface needs an
  approved mock supplement; the ordinary authorized graph stays unchanged.

## Proposed TASK-006 revision: inspect and decide exact approvals

Use `status.waiting` and `status.approvals` independently of completed details and
definition availability. Render a reached occurrence by execution ID + approval
ID, step/item/iteration, message and recorded state/receipt. Pending occurrences
and missing inputs can coexist with running peers. Expiration remains a recorded
server outcome, with no separate browser deadline or invented requested/expiry
timestamp. Make occurrences reachable without a readable graph definition.

Add one typed UI host-action intent for deciding an occurrence. The component
emits the exact decision and optional reason; the host validates it and invokes
the existing HTTP decision route as the browser session, TS `Execution.decide`,
or MCP `verification.decide_approval` where the host supports authorized writes.
Reuse the cancel forwarding/action-state pattern and existing input validation,
safe problem projection and session/CSRF boundaries. Keep writes out of the read
executor. Unsupported hosts report unavailable and issue no write. Existing MCP
write-scope/tool exposure rules continue to apply.

For action presentation, recommend existing host availability plus current coarse
operation hints where provided: missing approve operation can explain read-only
state; its presence never proves permission on this exact occurrence. With no
reliable hint, a supported host can submit and display the server's refusal.
Do not promise all unauthorized controls are pre-disabled without an authoritative
target-specific availability projection; do not add one just for this UI.

Guard submission per exact occurrence. After a receipt, read authoritative state
and keep the same execution; a durable receipt does not mean continuation has
completed. After an ambiguous answer, read that occurrence before allowing an
explicit retry of the same decision/reason. Never automatically submit a fresh
decision or transfer an answer to a newly selected occurrence. Keep cancellation
and completion races at their existing backend owner.

Prove parent-reader without approve, exact-Verifier approver without parent read,
wrong-Verifier approve, both grants, custom role, revoked grants, foreign IDs,
approved/rejected/expired/conflicting/replayed decisions and lost-answer readback.
Include repeated/fanout occurrences, running peers, unavailable details/definition,
one durable decision followed by same-execution continuation, and supported/
unavailable host actions. Existing approval durability tests are prerequisite
evidence; new browser/host tests prove this consumer rather than duplicating the
engine's restart machinery.

## Proposed TASK-007 revision: display existing GitHub delivery facts

Project `ExecutionData.status.github_delivery` in the existing execution/PR context.
Render pending/delivered/skipped/failed, its recorded reason and sanitized anchor
problems independently of the verdict. Non-PR executions have no delivery section.
No GitHub configuration grant, provider credential, direct GitHub request or
additional delivery endpoint is needed to read it. Outputs remain equal ordinary
publications; there is no specialized finding dashboard or UI retry operation.

Use the existing page refresh rather than introduce delivery polling. Preserve
exact execution association across current/history selection. A `failed` delivery
does not change passed verification; `pending` is not failed; a status-read
refusal is not a provider outcome. Preserve independently readable loaded parts
where the existing loader can do so, without promising an unavailable separate
delivery read or displaying revoked content as current.

TASK-007 first corrects and proves the required retained projection at the
existing backend owner under revision-8 REQ-021/AC-014, then its UI consumes
that output. Queue-free status
currently has the PR/delivery limitation listed above. Reconstruct those facts
from retained records using the existing response and delivery semantics, under
the maintainer agreement above. The approved specification explicitly records
this bounded scope. Do not rebuild delivery in the
browser or extend the correction into unrelated runtime behavior.

Prove actual provider-controlled success, permanent refusal, lost-answer/retry and
superseded/access-removed skips. Status/verdict/output identity stays fixed while
delivery changes; another Repository remains hidden. Test production browser and
existing host read parity, absent/delayed details, history selection and the
required retained-read boundary. Backend retry tests supply the provider behavior;
UI tests must consume their actual recorded outcome rather than a disconnected
fixture. Ordinary unit fixtures cover presentation variants cheaply.
