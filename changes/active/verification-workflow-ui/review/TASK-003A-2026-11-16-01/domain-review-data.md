## Adversarial checks and limits

Checked cancellation racing claim, completion, retry/exhaustion and admissions. The claim timestamp is captured while its transaction still holds the execution lock; a later cancellation can stage first but sorts after that running occurrence. Settlements that lose their token return no status. Principal-fence cancellation loops cannot duplicate the same row when both subject and actor are inactive because the first update removes it from the unfinished predicate. PR deactivation filters do not emit a cancellation for completed/errored history. Group completion failures do not reach the staging call.

Event times use producer wall clocks; cross-replica skew and equal timestamps are not a new causal ordering guarantee. Event loss on process loss is explicitly accepted; no durable handoff or reconciliation is required. No optional hardening or new persistence machinery is proposed.

Behavioral verification above is source/assertion review, not an independently executed test result. No Cargo, PostgreSQL, benchmark, or gate command was run by this reviewer; the orchestrator owns serialized execution and final command evidence. Explicit cancellation/revocation rollback has construction proof (commit succeeds before stage), not a dedicated runtime rollback test. Release-after-retry is covered by the exact returned SQL status and mapping, not an independently inspected dedicated lifecycle test.

These execution-order violations are retained and are not repaired by green tests or mutation checks. The boundary PASS does not erase that task-level history or supply an overall task verdict.
