### FIND-TASK-003A-2 — Hosted acknowledgement tests assume ordering absent from shared frames

- **Status:** REVISED. **Sources:** SYS-1, FUP-1. **Classification:** INCORRECT verification setup.
- **Obligation:** REQ-015 preserves checkpoint/revision/queue behavior; AC-010 and original task scenario 4 retain meaningful passing acknowledgement/recovery proof. These two existing tests were modified specifically to preserve that boundary after running status was introduced.
- **Locations:** `crates/wyrd/wyrd-server/tests/integration/pg_deferred_evidence.rs:621–636` and `:725–740`, inside `a_parked_execution_releases_compute_before_its_park_is_acknowledged` and `a_finished_execution_releases_compute_before_its_terminal_is_acknowledged`.
- **Producer-to-consumer evidence:** runner `process` stages running before compute (:1476). State changes start an independent background writer (`state.rs:411–525`); they do not wait for running delivery. Both payloads hash to the execution lane (`scribe_outbox.rs:2109–2156`), and 50 ms linger can collect both in one slice. `frames` (:1500–1560) creates a keyed checkpoint frame and a separate ordinary status frame. `submit` (:1924–1960) drives frames concurrently, including independently scheduled encoding; `tally` (:2044–2074) acknowledges a checkpoint when its own frame succeeds. Native `pause_admitted_ingest_for_test` (`scribe/ingress.rs:1031–1043`) takes one table stall out of its mutex before awaiting release, allowing other frames through.
- **Reachable failure:** running and checkpoint enter one slice; running takes the first stall, while checkpoint passes before the test arms the second. The park/terminal can therefore acknowledge and settle; its later waiting/completed status can take the second stall, causing the unchanged running assertion to fail. Alternatively the intended next checkpoint may already have passed with no remaining write to enter the barrier. Encoding may also let checkpoint consume the first stall. No lane rule orders these frames. This requires ordinary asynchronous scheduling, not unusual user input. It is source-proven possibility, not a reproduced failure in this sandbox.
- **Consequence/materiality:** mandatory owner fault tests can fail or hang under valid production scheduling and cannot rely on the documented first-status/second-state setup. Existing assertions ordinarily detect post-settlement status selection. Do not claim a silent false PASS or production integrity defect. A historical green run does not establish the missing happens-before relation.
- **Decision-complete minimal correction:** retain the real hosted Python/workspace/resource scenario and fix its producer ordering with the already exposed `WyrdTestServer::occupy_hosted_memory`, `wait_for_hosted_waiters` and `settle_bifrost_outbox` (`wyrd-testing/src/server.rs:1292–1319,2979–3015`). Hold hosted memory before opening the execution, observe its one hosted operation waiting, drain earlier outbox writes including running, arm one events stall, and release the memory hold so the real step runs. Keep all original scratch, worker, model permit, running/lease and eventual wait/resume/completion assertions. Replace the two-stall explanation in source/task evidence with the actual invariant. Do not change production frame batching, lane ownership, checkpoint acknowledgement or queue behavior.
- **Budget/control feasibility:** both fixtures set `monty_min_workers=0`, execute one tiny `measure` function with no declared code input mappings, and create no competing hosted operation before the assertions. `Sandbox::exec` (:392–415) first charges retained source/globals then waits for the session envelope. Default `monty_memory_bytes` is 256 MiB (`hosted/mod.rs:153`); envelope calculation includes twice the allocator ceiling plus worker resident bytes (`sandbox.rs:175–180,650–662`). Leave **64 MiB**, which admits this tiny retained request and shared Scribe/Oracle work but is below that session envelope; the nearby capacity fixture uses this exact budget (`pg_hosted_artifacts.rs:1542–1546`). Assert with existing `Sandbox::envelope_bytes` that the fixture's envelope exceeds the chosen leave budget, and observe the waiter before draining/arming, so future limit changes cannot silently replace waiting with refusal. Zero free bytes would refuse retained inputs and is not a valid substitute. Both flows retain a five-minute execution limit; do not widen the existing code/owner test timeouts.
- **Why the control is sufficient:** running is staged before the engine can reach the hosted waiter, so draining there excludes status interception. Any pre-step state writer that stages after that drain is still a checkpoint, not a status; holding it prevents the writer's later park/terminal revision from acknowledging because each execution has one in-flight frozen revision (`state.rs:430–473`). The operation can finish its real computation and release resources while the runner retains the claim. No other execution producer is active in these fixtures. Public PR delivery lifecycle facts occur after accepted terminal custody, not before this checkpoint gate.
- **Burden/smaller alternatives:** local fixture sequencing and one existing-budget invariant suffice. Deleting the tests/assertions would lose required proof; increasing sleeps/timeouts does not create ordering. A new checkpoint-discriminating Scribe stall, payload parser, shared helper/harness or serialized production delivery is larger and unnecessary. Keep the two already sound scripted fixes unchanged.
