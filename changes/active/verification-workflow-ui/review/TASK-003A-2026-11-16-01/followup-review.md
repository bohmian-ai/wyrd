## Source trace resolving the uncertainty

1. Claim processing stages the new `running` status before computing (`verification/runner.rs:1476,1510–1528`). RunState recovery itself merely constructs the live writer (`verification/state.rs:691–746`); it does not wait for running-status delivery. Actual state changes schedule a background writer (`state.rs:411–417`), which freezes current changes and stages an `ExecutionState` revision (`:430–525`). Changes can coalesce; no requirement separates the status and first checkpoint into different dispatch slices.
2. Status and checkpoint share the execution lane (`scribe_outbox.rs:2109–2156`), but that is **slice serialization**, not serialization of every frame. The 50 ms linger (`:143–151`) allows both writes in one slice. `frames` gives `ExecutionState` its own keyed checkpoint frame (`:1508–1521`), while status uses the ordinary shared frame (`:1524–1559`). `submit` drives up to eight deliveries concurrently (`:1924–1960`), including independent blocking encoding (`:1985–2020`). Thus the earlier staged status need not reach the test barrier before a checkpoint, and a held status does not stop another frame from that slice reaching Scribe.
3. The hosted tests use **native Scribe IngestStall**, through `WyrdTestServer::stall_next_bifrost_write_into` (`wyrd-testing/src/server.rs:2960–2967`), not PublicationFault. `pause_admitted_ingest_for_test` takes the one matching table stall out of its mutex and then awaits release (`vala-bifrost-redux/src/scribe/ingress.rs:1031–1043`). It does not hold another frame out. Arming the second stall after observing the first entry cannot catch another frame that has already passed.
4. PublicationFault is relevant to the scripted tests: `sent()` settles the composed runtime outbox (`verification/fault.rs:91–98`); FaultScribe records each frame, consumes a matching one-shot hold, then waits before forwarding (`:172–196`). `ScribeSink::tally` acknowledges an accepted checkpoint independently of other frames (`scribe_outbox.rs:2044–2074`). Do not infer that a checkpoint waits for a held status merely because both are in the same slice.
5. Parking calls `state.wait` and awaits persistence before returning its queue transition (`runner.rs:580–620`); terminal selection similarly persists before result/settlement (`:1656–1714`). State mutations are asynchronous from Scribe delivery. The hosted fixtures therefore permit a final park/terminal checkpoint to be staged while running status remains in the outbox.

## Proposed FUP-1

- **Classification:** INCORRECT verification setup; same root cause as SYS-1, not a second production defect.
- **Obligation:** approved REQ-015 keeps checkpoint/revision/queue behavior unchanged; AC-010 and TASK-003A require existing checkpoint/write/recovery proof to remain valid and passing. These two existing fault tests were changed specifically to preserve their held-revision contract. A task-induced nondeterministic owner-lane failure is material to that mandatory proof.
- **Locations:** `crates/wyrd/wyrd-server/tests/integration/pg_deferred_evidence.rs:621–636` and `:725–740`.
- **Reachable schedule:** stage running and the park/terminal checkpoint in one slice (linger or delayed writer polling permits it). Running consumes the first stall. The independently delivered checkpoint passes Scribe before the asserting task arms the second stall. Its acknowledgement can advance persistence; after releasing running, later `waiting`/`completed` status can consume the second table stall. The test then observes a settled execution where it requires running and fails. If checkpoint delivery wins the first stall, releasing it can likewise allow the later status to consume the second barrier. No particular row ordering follows from the lane. This schedule requires no unsupported input or production fault, only normal asynchronous scheduling.
- **Consequence/calibration:** the two tests can fail under valid production behavior. Their unchanged running assertions ordinarily detect selecting a post-settlement status; this review does **not** establish a silent false PASS or production checkpoint-integrity failure. A passing run may still hold a useful revision, but a green run does not prove the setup selects one deterministically. I have not reproduced the race; Docker denial prevents the owner rerun in this environment.
- **Smallest correction boundary:** fix these fixtures' producer ordering using existing controls, preserving the real Python/workspace/resource scenario and production batching. Existing `WyrdTestServer::occupy_hosted_memory` plus `wait_for_hosted_waiters` (`wyrd-testing/src/server.rs:2975–3017`) can keep the actual Python operation waiting for its session envelope, while `settle_bifrost_outbox` (`:1292–1304`) drains earlier status/state writes. Arm one events stall while that producer is held, then drop the memory hold and let the real step run. Leave enough memory for the retained request and less than the session envelope; zero free bytes can refuse admission instead of creating the intended waiter (`hosted/sandbox.rs:183–223,385–415`). These APIs expose an existing production-owner gate and drain, without replacing the engine, removing scratch allocation, adding a new harness, or changing Scribe semantics. Keep all original resource/lease/outcome assertions; establish the barrier captures a post-release state write before queue settlement. The validator should verify the fixture's exact retained/envelope budget and absence of another active producer rather than accept a guessed constant.
- **Correction burden:** local test sequencing with existing APIs is sufficient in principle and smaller than adding checkpoint-payload discrimination to the shared barrier. A new checkpoint-aware stall is therefore not presently justified. Sleeping, extending timeouts, removing running/resource assertions, serializing production frames, or changing lane/batching behavior does not correct the cause within scope.
- **Focused closure proof:** hold the real hosted operation, observe its waiter, drain earlier writes, arm once, release the producer; demonstrate running while the intended state write is held and preserve scratch/worker/model release and eventual wait/resume or completion assertions. Run the two exact hosted selectors and the two existing scripted selectors; no new broad gate or benchmark is needed for this test-only correction.
