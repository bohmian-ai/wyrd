## Proposed finding SYS-1

- **Classification:** INCORRECT verification; changed recovery-proof setup relies on ordering the outbox does not provide.
- **Obligation:** AC-010 preserves checkpoint recovery proof; TASK-003A requires existing write/recovery boundaries remain passing, and the test changes claim to restore the actual held revision rather than merely a status row.
- **Changed locations:** `crates/wyrd/wyrd-server/tests/integration/pg_deferred_evidence.rs:621–636` and `:725–740`.
- **Producer to consumer evidence:** `runner.rs:1476` stages running before executing. Hosted state mutations schedule the background flush (`state.rs:413–425`), and freezing/staging the first revision does not await running delivery. Both hash the execution to the same lane (`scribe_outbox.rs:2128–2132`). The dispatcher can collect both during its 50 ms linger or before its next poll (`outbox.rs:1102–1112,1235–1257`). `frames` makes a keyed checkpoint frame separately from the ordinary status frame (`scribe_outbox.rs:1508–1559`), and `submit` drives up to eight frame deliveries concurrently (`:1924–1960`), including concurrent blocking preparation (`:1990–2020`). The native Scribe stall consumes one matching table write and releases its mutex before awaiting its barrier (`scribe/ingress.rs:1031–1043`). It does not serialize subsequent frames. Therefore a shared lane serializes successive slices, not frames within a slice.
- **Reachable failure schedule:** running and a first checkpoint are staged before dispatch (the existing linger and independent scheduler allow this; no test barrier prohibits it). The slice contains both frames. One consumes the first table stall; the other can enter Scribe before the asserting test arms the second stall. If the checkpoint passed and no later revision remains to be produced, `stall.wait_entered()` never receives an edge; if the first stalled frame was the final checkpoint instead, releasing it can permit settlement/status delivery and the second barrier can capture a display-status row. The two tests do not inspect their held payload, and their assertion that the first frame is running is not enforced. A slow/fast scheduling variation can therefore hang/fail the owner lane or change which state the test proves. This is a test synchronization finding, not evidence that production checkpoint integrity fails.
- **Materiality/limits:** These are required existing fault/recovery tests changed to clear a task-induced failure. Their central setup must target state custody reliably. No failure was reproduced in this review; the exact-candidate owner rerun is unavailable in this environment. An independent focused reviewer should challenge the schedule and materiality before retention. Passing once does not establish a happens-before edge absent from source.
- **Smallest correction boundary:** Keep production batching, lanes, acknowledgements and durability unchanged. Fix selection at the existing test barrier/fixture owner so a checkpoint is selected explicitly and the status event passes, then arm the checkpoint barrier once before opening the hosted execution. Reuse the existing Scribe stall mechanism with the narrow test-only discrimination needed for checkpoint payloads; do not add a new delivery path or sleeps. This removes the two-stage assumption. A proven existing producer barrier that settles running before any checkpoint production would also eliminate the race, but no such barrier was found in these two tests. The correction should be chosen after the focused follow-up validates the path.
- **Focused proof:** Drive running and checkpoint writes into the same outbox slice, verify the barrier selects the checkpoint and passes the status, retain the original compute/lease assertions, then rerun the two named hosted tests. No benchmark or full journey expansion is required for a test-only correction.
