Maintainer-locked initial runtime architecture, not current implementation. Existing table names are marked EXISTING; dashed red-bordered boxes name tables this change must create. This remains a style-direction draft because the canonical Wyrd stylesheet is absent from this checkout. The change specification projects this control flow.
Client boundary. state.start_bifrost(...) connects one state-owned Bifrost facade and describes the fixed Drift and Eval system tables once. A scoped run.observe.drift(...) or run.observe.eval(...) call projects fixed-schema rows before insertion through its pooled queue. run.observe.record(table, value) names a user table; Bifrost describes it on first use and reuses its cached schema. Every insert routes by explicit table without mutating a shared active table. Shared wyrd-client and wyrd-queue never interpret a Verifier kind; the queue only buffers, builds Arrow IPC, and publishes generic rows. No separate Bifrost handle or table is passed to run().
Public control-plane boundary. The existing GET /v1/cards/by-uid/{kind}/{card_uid} exposes Verifier baseline status and owner binding IDs. GET /v1/verification/bindings/{binding_id} exposes activity/readiness and schedule status. POST /v1/verification/runs enqueues a bounded manual Drift run for a binding or a direct analysis-only Verifier target; GET /v1/verification/runs/{run_id} exposes run and Operator delivery status. Result rows remain in Bifrost and are read through existing query APIs. No separate result, dispatch, or Alert endpoint exists. A state-owned Bifrost writer starts once; a failed shutdown retries on the same handle, and a successfully closed state is not restarted.

01 / Registration

Data and Verifier Cards: what is created?

The baseline fitter is the one implementation-specific background helper. Eval and Custom Drift have no fit job.

On the YES branch, the server's Drift baseline fitter reads the exact registered Parquet artifact, produces the existing FittedBaseline, and updates drift_baselines. Registration returns before fitting finishes. A failed fit is visible as status, not a failed Verifier judgment.

02 / Registration

Service or Agent: how is the binding populated?

Nothing runs merely because a Card was registered. Runtime identity is exact Card UID/version, never a name lookup.

At the first successful token exchange, the server updates the proposed last_authenticated_at column on wyrd.auth_service_accounts. Only scheduled bindings initialize next_run_at to the next cron boundary. Refresh while active does not move that cursor. The current name-only service-account uniqueness must be fixed to allow two UID-distinct A/B versions.

03 / Runtime gate

Authentication activates a scheduled binding

Authentication is a gate, not a Drift window clock. No per-request activity write and no idle token-refresh timer.

For a running service, a later request with an expired token invokes the existing exchange again. The scheduler considers the principal eligible only while last_authenticated_at is within the configured 24-hour activity TTL. If it becomes inactive, a subsequent exchange re-arms the schedule from the next boundary; missed slots are not backfilled.

04 / Runtime: scheduled Drift

Observation → cron decision → one fixed-window run

Scheduler logic is generic across Verifier kinds. Drift-specific logic starts only inside the Verifier implementation.

For an hourly trigger due at 01:00, the run reads [00:00, 01:00) even if claimed at 01:03. A manual trigger records an explicit requested window and does not move the cron cursor. The Drift runner reads the fitted profile from the proposed drift_baselines store; registration fitting is shown above. The run then joins the common runner in section 6.

If the baseline is still pending or failed, the cron occurrence is skipped without launching a Verifier. Fitter failure is retried by the fitter, not counted as a Drift judgment.
05 / Runtime: automatic Eval

Eval observation commits first; enqueue is best-effort

Eval has no cron schedule. Its verifier_runs insert happens asynchronously after Bifrost commits and cannot delay or roll back normal ingest.

eval(...) completes the EvalRecordObservation and fixed-row projection before inserting through the state-owned Bifrost facade and its pooled queue. Bifrost describes the fixed input table at startup and reuses its user schema; the final Eval physical projection remains an open spec decision. Generic wyrd-client/wyrd-queue plumbing publishes through the canonical IPC path to Gate and Scribe. The Scribe batch fence remains part of ordinary ingest; Eval adds no Postgres dependency to that path. A failed post-commit run insert or process crash can lose the Eval run while preserving the observation. This is the explicitly accepted fail-open behavior; a durable outbox may be added later.

06 / Generic runtime

Claim → execute → persist result → settle or retry

The runner accepts a typed Verifier input and returns a typed result. Only the selected implementation knows whether it is Drift, Eval, HTTP, MCP, Python, Workflow, or code review.

A failed judgment is a completed run, not an engine exception. The Bifrost summary is the authoritative verdict; child details join on (data_tenant_id, result_id). The server writes detail then summary as separate Arrow batches through the existing Bifrost gRPC/Scribe path. It settles the run and inserts Operator dispatches only after both ACKs. An unacknowledged sealed batch may be retried with the same ID and bytes; a fresh write call is not deduplicated replay. A crash can leave partial rows and an errored run; no cross-table atomicity or per-table crash repair is promised.

06 → 07 / Durable handoff

The same Postgres rows connect runner and Operator worker

The runner does not call the Operator. Its committed insert makes dispatch rows visible; a separate worker polls and claims them.

07 / Operator worker

Each failed result fans out independently

The generic runner creates dispatch rows after a failed verdict. An Operator may send an alert; no separate Alert table or Alert-polling loop is needed.

Each dispatch has its own status, lease, retry count and deadline. One failed Operator does not block siblings. Retry exhaustion retains that dispatch's error; it does not re-run the Verifier or alter the Bifrost failure result. External delivery is at-least-once after an ambiguous crash unless the destination honors the stable dispatch key. Each failed run remains independent; later passes do not resolve earlier failures. The unused vala.drift_alerts table is deleted.

Input identity: client principal writes an observation under the observed subject Card; the authorized binding identifies the Verifier. Result identity: the tenant-scoped SYSTEM principal writes through wyrd_client::Bifrost to Gate/Scribe under the exact Verifier Card; result rows also retain subject, owner, binding and run IDs. Result queries: verification dashboard → vala.verification.results alone; Drift dashboard → that table JOIN vala.drift.result_features; Eval dashboard → that table JOIN vala.eval.result_items. Both joins use (data_tenant_id, result_id). All five verification Bifrost tables (Drift/Eval observations, canonical results, and both detail tables) partition by UTC day on managed wyrd_event_time; one result uses the same event timestamp in summary and details. An hourly cron window does not require an hourly physical partition. The summary adds Bloom filters for result_id, subject_card_uid, and binding_id to the existing managed floor (run_id, card_uid, principal_id); both detail tables Bloom-filter result_id. Raw Drift observations and Eval inputs are analysis inputs, not result-detail tables. The unused vala.eval.runs, vala.eval.assertions, and vala.drift_alerts tables are deleted, not retained as alternate paths.
The server boundary is Registry/Auth for registration and activation, Gate/Scribe for observation commits, and one generic VerificationRuntime containing Scheduler, VerifierRunner, and Operator worker. Only the Drift baseline fitter is kind-specific background plumbing. There is no new Alert table or Eval outbox in this initial flow. Fanout to 0..N Operators requires a contract change from the current single on_failure value. All proposed tables and seams need approval and implementation; this diagram does not say they already exist.
