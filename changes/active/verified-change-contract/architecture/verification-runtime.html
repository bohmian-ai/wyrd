The rule for continuous bindings: Trigger creates binding activation, which creates a run. VerifierRunner executes it. A completed failed verdict may enqueue an Operator. An execution error retries the same run and does not alert. Direct/offline runs use the same runner without a Trigger or automatic reaction.

Only scheduled bindings have a cron cursor. First authentication or reactivation after inactivity starts at the next occurrence; a refresh while still active updates activity without moving that cursor. Continuous Eval has no next_run_at. A token is re-exchanged automatically on the next authenticated request that needs it; expiry or an idle open process does nothing by itself.
Nighttime example. A Service authenticates at 09:00 and emits Drift observations during the day. Its midnight cron is eligible because the last exchange is within the configured 24-hour window. A version whose principal aged out creates no activation, run, or Bifrost query; reactivation never backfills inactive cron occurrences.

PSI and SPC baseline path

  1. Data Card authoring from Pandas, Polars, or Arrow registers Parquet. Verifier registration resolves that exact Data identity and queues fitting without blocking.
  2. Status exposes pending → building → ready/failed. Only ready PSI/SPC Verifiers can score; each run loads the persisted exact fitted baseline.
  3. PSI compares server-counted window bins to fitted baseline distribution. SPC evaluates ordered subgroup means against fitted control limits. Empty or insufficient windows become inconclusive, not drift.

Custom metric and manual path

  1. Custom validates its scalar baseline and threshold at registration; it has no Data baseline reference, fitting job, or persisted fitted profile.
  2. Server selects the named raw numeric series in the same fixed window, computes its mean, and calls the existing custom scorer.
  3. A direct Verifier request selects an explicit bounded window and is analysis-only. A manual binding invocation also supplies an explicit window, leaves the cron cursor unchanged, and may dispatch its configured on_failure.
Window rule: first scheduled window is [owner becomes runtime-active, first cron); later windows are [previous cron, current cron). A run is eligible at window_end + allowed_lateness. Oracle filters DriftRecordObservation.created_at within that stored half-open window; retries reuse the same window. Missed occurrences for an active owner are materialized separately in bounded batches; occurrences while inactive are skipped, never backfilled.

Continuous Eval decisions

  1. Only a committed observation routed to an active exact binding creates work; Scribe's commit and activation insertion share the tenant-scoped control transaction.
  2. Sampling is applied before task execution. A sampled-out activation terminates without tasks or dispatch. Trace-dependent records use the existing AwaitingTrace retry/dead-letter lifecycle. Task execution error is not an assertion failure.
  3. The authored EvalSpec.pass_gate alone decides failure. An executed Eval without a gate persists EvalResults but creates no dispatch. Context capture changes stored evidence, not the verdict.

Offline Eval is a separate entry path

  1. Register EvalScenarioCollection as a Data Card backed by a Bifrost table; EvalSpec.dataset references it.
  2. An explicit offline run loads those scenarios and executes the existing Eval workflow against the selected subject—no observations-ready trigger and no cron.
  3. Persist complete EvalResults plus the common Verification Result with exact dataset, subject, Verifier, and run identities.

06 / Failure semantics

When does a verifier retry?

Engine completed

Passed / inconclusive

completed → persist result → no Operator

A pass means criteria were met. Inconclusive means the completed analysis could not decide, such as insufficient Drift samples. Neither retries merely to seek a different verdict.

Engine completed

Failed verdict

completed + failed → persist result → optional dispatch

Drift detected or the Eval pass gate failed. This is a valid judgment, not an execution failure. Do not rerun the verifier automatically. Only a binding-created run with on_failure dispatches an Operator; external delivery retries separately.

Engine did not complete

Execution error

running → retry_wait → same run_id → dead_lettered

Transient Oracle/LLM/HTTP outage, timeout, worker crash, or unavailable dependency retries with bounded attempts and backoff. Permanent invalid input/configuration ends errored. No Operator/Alert is created.

queued → running (claim token + expiry) → completed [passed | failed | inconclusive]   OR   retry_wait → running → … → dead_lettered
RUN CLAIM

No long database lock

Worker claims a row with an expiring token and commits. Settlement checks the same token. A crashed worker's claim expires and another worker retries.

RESULT REPLAY

No duplicate result

Result batch identity derives from run_id. If Bifrost append succeeds but Postgres settlement crashes, retry replays the same batch and Scribe deduplicates it.

DELIVERY RETRY

Independent lifecycle

A failed Slack delivery retries delivery work, not the Operator dispatch or Verifier run. The Alert and Verification Result remain durable and unchanged.

Durable stageRetry after transient failureTerminal / observable outcome
Binding activationSame activation identity; recover expired claimOne Verifier run or activation dead letter
Verifier executionSame run_id, exact Card versions and input window; idempotent result replayCompleted verdict, permanent error, or run dead letter
Operator dispatchSame dispatch identity; never rerun VerifierAction completed or dispatch dead letter
External Notify deliverySame delivery identity; respect provider rate-limit responseDelivered or delivery dead letter; Alert remains
Recommended starting policy (not yet approved): three total attempts per stage, with 30-second then 2-minute backoff; expiring claims recover worker crashes. Invalid configuration and unauthorized input are permanent errors, not retries. A provider call with an ambiguous outcome can be delivered more than once unless that provider accepts the stable delivery id as an idempotency key. Persist attempt count, next-attempt time, last error, and terminal state for status queries; set per-attempt execution timeouts by implementation.
Spec conflict: REQ-064 says exhausted retries produce inconclusive, while REQ-063 reserves verdicts for completed executions and REQ-079/089 require inspectable dead-letter outcomes. The terminal mapping needs one explicit rule before implementation; this diagram does not silently turn an execution error into a failed subject verdict.

NOTIFY

What is recorded?

One proposed Alert per failed run/Notify dispatch, carrying its bounded findings and link to the immutable Bifrost result. External delivery has its own status and retry identity. Later passing runs do not resolve old Alerts.

HTTP / WORKFLOW

What is not recorded?

These actions use the same dispatch lifecycle but do not manufacture Alerts. They receive bounded run/result context, not raw observation tables.

Decision conflict to resolve: the change spec expects one Alert per failed run, while the Drift logic document says one Alert per finding. This diagram recommends one per failed run with findings attached; that is not yet an approved spec revision.

09 / Decision ledger

Fixed direction and remaining choices

AGREED DIRECTION

One runtime, three owners

Scheduler creates scheduled Drift runs. VerifierRunner executes Drift/Eval and later implementations. Operator executes reactions. Baseline fitting is an internal helper.

AGREED DIRECTION

Activity gates scheduled work

Successful exchange activates or renews the exact owner version. Default inactivity cutoff: 24 hours. No per-observation writes; token expiry alone is not an exchange.

AGREED DIRECTION

Retry execution, not judgment

Execution errors retry same durable run; completed failed verdicts dispatch the Operator once. Operator delivery retries separately.

TO LOCK IN SPEC

Baseline pending at cron

No PSI/SPC run before the exact fitted baseline is ready. Define whether pending-baseline cron occurrences are skipped or caught up; a terminal fit failure exposes status and starts no run.

TO LOCK IN SPEC

Alert granularity

Recommend one independent Alert per failed run/Notify dispatch, containing all findings. Reconcile the change spec with Drift logic.

TO LOCK IN SPEC

Retry budget and windows

Approve or change the proposed three-attempt retry default; specify per-implementation timeout, allowed lateness, missed-cron catch-up, overlap, and fitted-baseline serialization/size limit before planning.
