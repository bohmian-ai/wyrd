### Important

- **TASKREV-006-001 — INCORRECT — REQ-077 exact committed event time is not replay-stable.** Obligation: every observation-created run must freeze the exact server-managed `wyrd_event_time` assigned to the committed row, including idempotent replay. Location: `crates/vala/vala-bifrost-redux/src/scribe/ingress.rs:346-357,578-582`, `crates/vala/vala-bifrost-redux/src/gate/mod.rs:956-963,979-993`, and `crates/vala/vala-bifrost-redux/src/tables/eval/observations.rs:104-120`. Evidence: every ingress attempt generates a fresh `receipt_micros`; after durable acknowledgement Gate passes that fresh value to the observation hook, which substitutes it whenever the original client frame omitted `wyrd_event_time`. Scribe exact-batch replay deduplicates the stored row, but this callback has only the new attempt's receipt, not the receipt stamped into the already committed row. The SQL idempotency test exercises a caller-supplied fixed `event_time`; the real-server fail-open journey never retries the sealed batch. Observable consequence: if the initial post-ACK enqueue fails and a transport retry of the identical sealed batch later succeeds, the new run can freeze a different `input_event_time`. Across a UTC boundary, `BifrostReader::record` prunes the wrong day and the durable run retries to `errored` even though its observation is committed; before the boundary, the frozen provenance is still false. Testable correction: make the durable Scribe admission/replay result expose the authoritative event time originally committed for rows that omitted it, and pass that value to the hook on both first acceptance and exact replay. Add a real Gate/Scribe/Postgres test that forces the first enqueue to fail, retries the identical batch after a different receipt day, and proves the sole run's `input_event_time` equals the stored row and the run can read it.

- **TASKREV-006-002 — INCORRECT — `every_nth` sampling is computed from mutable visibility and can change between attempts.** Obligation: REQ-083/INV-010/AC-016 require sampling before execution with durable restart/retry behavior; one run must make the same sampling decision after retry, lease recovery, or restart. Location: `crates/wyrd/wyrd-sql/src/queries/verifier_runs.rs:269-279,1295-1312` and `crates/wyrd/wyrd-server/src/verification/eval.rs:169-198`. Evidence: each attempt recomputes the ordinal as the count of currently visible prior runs ordered by `(created_at, run_id)`. Under concurrent enqueue, transaction A may insert an earlier `created_at` row but remain uncommitted while later transaction B commits and B's run computes ordinal 1. After A commits, a retry of B computes ordinal 2. This contradicts the source claim that durable creation order makes every attempt read the same position. The unit test covers only the pure modulo calculation; no concurrent or retry test covers the SQL ordinal. The count also grows over all historical observation runs and is repeated on every attempt. Observable consequence: an `every_nth` run can execute on one attempt and become sampled out on a later attempt (or the reverse), so restart and retry alter user-visible result production. Testable correction: freeze one per-binding observation ordinal as part of idempotent run creation under binding-scoped serialization, then read that stored value on every attempt; do not derive it from a later count of visible rows. Add a PostgreSQL concurrency test that holds the earlier insert uncommitted, commits the later insert, then commits the earlier insert and proves the later run retains one ordinal and sampling decision across attempts.

- **TASKREV-006-003 — INCORRECT — media reads do not enforce the byte bound on the bytes actually sent.** Obligation: REQ-131/AC-027 require bounded media bytes and oversized media to fail as an execution/input error. Location: `crates/wyrd/wyrd-server/src/verification/eval.rs:729-752`. Evidence: `TenantMedia::resolve` checks `object_len`, then separately calls `get_object` and base64-encodes the returned bytes without checking their length. An object can be replaced or grow between the metadata and read operations; the existing test only checks an object that is already oversized at the metadata call. Observable consequence: a mutable backend object can bypass `MEDIA_LIMIT_BYTES`, causing an unbounded allocation/base64 expansion and sending oversized content to the provider. Testable correction: enforce `MEDIA_LIMIT_BYTES` against the returned byte buffer (or use an existing storage API that performs one bounded read) before encoding. Add a resolver test with a storage double or coordinated backend mutation that reports an allowed length but returns more than the limit, and assert a terminal oversized-media error and no provider invocation.
