## Material proposed findings

### DEPLOY-001 — INCORRECT: local development-cluster image path cannot start

**Obligation:** The R3 remediation requires a complete development Kubernetes startup journey, including one-off migration and serving, while revision 41 permits a locally built official image. **Location:** `docs/src/content/docs/self-hosting/kubernetes-development.svx:30-39,91-101,125-153`. **Evidence:** The page says `mise run docker:build` produces local image `wyrd`, then offers `kind load docker-image wyrd` with `imagePullPolicy: Never`; the following Job and StatefulSet instead specify `registry.example.com/wyrd@sha256:…` and neither sets `imagePullPolicy: Never`. Kind loading the `wyrd` tag does not create the displayed registry-digest reference. **Observable consequence:** A developer following the advertised local-cluster route cannot start the migration Job or server pod, so the journey stops before setup. **Testable correction:** For the local-cluster branch, tell the operator to use the loaded image's actual reference and `imagePullPolicy: Never` in *both* Job and StatefulSet; retain the registry-digest branch for a cluster that pulls from a registry. A rendered manifest check or one local kind walkthrough that runs migrate then reaches `/readyz` is focused proof.

### DEPLOY-002 — MISSING: production HPA example has no metric collection path

**Obligation:** The R3 production Kubernetes guide must include a concrete successful-read-rate autoscaling example and the credential/network setup needed to run it. **Location:** `docs/src/content/docs/self-hosting/kubernetes-production.svx:19-23,179-212,279-304`. **Evidence:** It enables `WYRD_METRICS_BIND` and shows an adapter rule selecting `wyrd_http_requests_total{namespace!="",pod!=""}`, but never arranges for Prometheus to scrape the Wyrd pods or attach `namespace` and `pod` labels. The actual passing kind proof explicitly uses `wyrd.ai/scrape-port` pod annotations (`deploy/kubernetes/kind/wyrd.yaml:29-32,101-104`) and pod discovery/relabeling (`deploy/kubernetes/kind/infra.yaml:110-126`) to create those series; neither mechanism appears in the production example. The prerequisite merely names an installed metrics pipeline. **Observable consequence:** Following the shown production pod and adapter examples on a cluster with Prometheus and prometheus-adapter yields no matching per-pod series, so the HPA cannot scale on successful reads. **Testable correction:** Document the minimum pod scrape configuration (or equivalent ServiceMonitor/PodMonitor for the installed pipeline) and the namespace/pod relabels that feed the existing adapter rule. Reuse the proven kind configuration as the example and keep production thresholds operator-measured. A config/manifest walkthrough showing the adapter API returns a value for a Wyrd pod is focused proof.
