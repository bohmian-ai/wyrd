### FIND-TASK-006-19 — CONFIRMED / INCORRECT — tenant policy drift can pass readiness

**Source:** DATA-R4-1. **Obligation:** REQ-157, AC-035, and R3 FIND-19 require readiness to reject security-deficient policy drift. **Location:** `crates/wyrd/wyrd-sql/src/schema_check.rs:222-259`.

`OperatorPool::verify_tenant_isolation` accepts `^\\([a-z_]+ = wyrd\\.current_tenant\\(\\)\\)$` for the policy's `USING` expression, and requires `WITH CHECK` to equal it. The actual migrations use `data_tenant_id`; `wyrd.auth_users` also has another UUID column, `id`. An owner can alter the named policy to `USING (id = wyrd.current_tenant()) WITH CHECK (id = wyrd.current_tenant())`, preserving its other checked attributes. `wyrd_sql::verify_schema` and `vala_sql::verify_schema` call this method; production `wyrd-server migrate` calls both after migrations, and `WyrdPostgres::validate_schema`/`ValaPostgres::validate_schema` call them before serving. The existing mutation proofs rename or remove a policy, not substitute a column. The resulting database can report ready with tenant access governed by the wrong key.

**Smallest correction:** In the existing shared `OperatorPool` check, require the tenant policy's `USING` and `WITH CHECK` to compare `data_tenant_id` with `wyrd.current_tenant()`; preserve forced RLS, policy role/command/permissiveness checks. Do not introduce a general policy parser or another readiness layer. **Focused proof:** mutate one migrated table's policy to use its other UUID column and show both owner post-migration and serving validation refuse; restore it and show both pass in the existing Postgres mutation test and SQL/startup lanes.

### FIND-TASK-006-20 — REVISED / VIOLATION — new raw-pool migration API

**Source:** SR-1. **Obligation:** `architecture/agent-rules.md` bans raw `PgPool` in new library signatures; R3 FIND-20 explicitly requires no new raw-pool library signature. **Location:** `crates/wyrd/wyrd-sql/src/lib.rs:85`; callers at `wyrd-server/src/main.rs:207`, `wyrd-sql/src/lib.rs:279`, the shared fixture, and SQL migration tests.

The public `MigrationLease::acquire(owner: &PgPool, wait)` detaches a raw pool connection to hold the correct database-wide owner-session advisory lock. Its full body bounds lock wait, detaches the session, resets the timeout, and returns the lease; the owner-only migration, fixture, and tests call it. The lease behavior is necessary, but publishing `&PgPool` as the library entrypoint bypasses the required handle boundary; `check:from-pools-allowlist` checks pool construction, not this signature.

**Smallest correction:** Move acquisition behind the existing SQL migration owner (`SqlStore`, which already owns a pool and migration entrypoint) and have the one-off server migrate path call that typed owner. Keep the same detached owner session, bounded wait, ordered Wyrd/Vala migrations, post-validation, and release behavior. Adapt fixture/tests through their existing test-owned pool setup; do not turn the owner migration login into `OperatorPool` or make serving processes receive it. **Focused proof:** no new raw-pool library signature remains; rerun the competing-migrator exact test, `test:sql`, startup, and `check:from-pools-allowlist`.
