### SR-R6-1 — Production pods become ready before ingress policy exists

- **Rule:** `architecture/operations/deployment-and-release.md:28–32` requires authenticated, encrypted gateway-to-server traffic and confines plaintext to an enforced local transport boundary.
- **Location:** `docs/src/content/docs/self-hosting/kubernetes-production.svx:234–242,421–426`.
- **Evidence:** The guide applies `wyrd-core.yaml`, waits for its rollout, applies `wyrd-oracle.yaml`, waits for its rollout, and only then applies `wyrd-netpol.yaml` and `wyrd-mesh.yaml`. Pod injection alone does not establish the guide's STRICT mTLS or gateway-only `AuthorizationPolicy`; no earlier default-deny policy is specified. The Services and ready pods therefore exist during a period when an ordinary in-cluster pod can reach ports 8080/50051 under the cluster's default network behavior.
- **Consequence:** Following the printed production steps exposes plaintext public listeners to other cluster workloads until policy reconciliation finishes. The later denied-probe evidence shows the final state, not this boot interval.
- **Testable correction:** Apply both existing network and mesh policies before creating the core and Oracle workloads, then apply the edge route after rollout. Their label selectors can exist before any selected pod. A walkthrough should probe the protected ports during initial pod rollout or otherwise prove policy is established before endpoints become ready.

### SR-R6-2 — Database credentials enter operator command arguments

- **Rule:** `architecture/wyrd-security-posture.md:374–375` prohibits credentials through command arguments or checked-in files.
- **Location:** `docs/src/content/docs/self-hosting/kubernetes-production.svx:105–119,133–136`; `docs/src/content/docs/self-hosting/kubernetes-development.svx:83–86`.
- **Evidence:** Shell expansion places password-bearing Postgres URLs directly in `psql` and `kubectl --from-literal` argv. The surrounding prose offers secret-provider integration, but the executable path shown to operators uses argv.
- **Consequence:** Local process inspection and command auditing can capture the owner, app and platform-admin database passwords even when the guide's Kubernetes Secrets are later stored correctly.
- **Testable correction:** Keep password-bearing values out of argv in both walkthroughs: use libpq environment or a restrictive local credential file for the `psql` checks, and create Kubernetes Secrets through the named secret-provider path or a restrictive local file/stdin path. Preserve all three verify-full DSNs and the provider CA. Inspect the example command arguments and a followed walkthrough for absence of password values.
