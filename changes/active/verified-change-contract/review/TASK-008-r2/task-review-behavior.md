For revision 58 I also traced the production runner path. `VerificationRuntimeBuilder::build` constructs `VerifierRunner`; `ClaimLoop` spawns unbounded claimed executions; `VerifierRunner::execute` loads the Card, `ResultPublisher::publish` mints the result-write token, and `VerifierRunner::attempt` settles the run. Those three Postgres phases acquire from the shared application pool independently, with no shared runner-specific connection bound. A settlement acquisition failure is logged as `settlement_failed` and the run remains leased until expiry.

Likely consumers are operators invoking `bench:capacity`, automation consuming its Markdown/JSON verdict, HTTP/MCP/SDK traffic sharing the application Postgres pool with the verification runtime, and the focused fairness/exactly-once journeys used as correctness proof outside the benchmark.

## Proposed findings

### BHV-R2-001 — MISSING / VIOLATION: the candidate predates approved revision 58 and leaves runner Postgres work unbounded

- **Violated obligation:** Approved revision 58 REQ-178 requires the Verifier runner's Card-load, result-token-mint, and settlement Postgres phases to share one in-process limit equal to half the configured application pool, requires settlement acquisition failures to retry with backoff within the lease, and prohibits charging an attempt for connection unavailability. The task must be reviewed against the current approved revision.
- **Exact location:** candidate `changes/active/verified-change-contract/spec.md:1-4`; `changes/active/verified-change-contract/tasks/task-008-closeout.md:1-18`; `crates/wyrd/wyrd-server/src/verification/runner.rs:149-198,305-328,449-457,638-671`; `crates/wyrd/wyrd-server/src/verification/publisher.rs:185-200`; `crates/wyrd/wyrd-server/tests/pg_verification_runtime.rs:1330-1401`. Approved requirement: commit `e202e1f272c101f93d13dcc9d0b2a7edc1320f74`, `spec.md` revision 58 REQ-178 and revision-history entry.
- **Evidence:** The candidate frontmatter is revision 57. `VerifierRunner` owns no semaphore or other shared Postgres-phase capacity. Each of the three named phases calls `tenant_conn` directly. `attempt` invokes settlement once; on any acquisition/transaction error it records `settlement_failed` and relies on lease expiry. The fairness proof was reduced from the revision 58-required 200-run burst to 60 and checks eventual completion but not attempt 1 for every run or absence of settlement failures.
- **Observable consequence:** A queued-run burst can consume the shared application pool, starving HTTP, MCP, and audit work. Token-mint acquisition failure is handled as a publication retry and can consume a run attempt; settlement acquisition failure strands already-executed work until the ten-minute lease expires. The candidate also presents a stale revision-57 task/spec packet despite the caller's approved revision-58 authority.
- **Required testable correction:** Update the candidate packet and task mapping to approved revision 58. In the existing verification runtime/runner ownership, derive one shared Postgres-phase bound from the configured application pool and apply it only to Card load, result-token mint, and settlement; keep claims, leases, and engine execution permit-free. Settlement connection acquisition must retry with bounded backoff while the current lease remains valid, without consuming an attempt. Restore the focused 200-run, 8-connection-pool proof and assert every run completes on attempt 1 with no `settlement_failed` outcome, while a separate focused concurrency proof shows runner Postgres phases never exceed half the configured pool.
