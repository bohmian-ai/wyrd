Verifier building blocks: call to verdict

Runtime-flow companion to spec revision 6 (approved). Follow the arrows. Rectangles are operations or durable writes; diamonds are decisions; red dashed arrows are retries; green dashed arrows are data reads or writes. Store boxes distinguish required tables from internal detail projections.

Proposal, not current implementation. Aligned with spec.md revision 6 (approved), incorporating the five agreed rules. Supporting context: proposal.md and example.md. The approved specification governs this flow; private implementation names below are illustrative.
One correct way. verify is real time. submit is all background work. submit routes on check type through CheckKind::evidence(), an exhaustive match: Run checks get a queued execution; Window checks (drift) record rows that the bound schedule Trigger judges. There is no other entry point: observe.drift, observe.eval, and observations_ready are deleted.
No Postgres write on the request path. Admission writes nothing. Run inputs and results go through ScribeOutbox. Queue rows are inserted in batches by ExecutionRequestOutbox after Scribe acknowledges submitted inputs marked queue_execution=true. Inputs recorded by verify have queue_execution=false and never activate the queue. Both are instances of the one generic wyrd_runtime::outbox::Outbox; there are two because Bifrost and the Postgres execution queue are two destinations.

01 / Contract

A Verifier is inputs + steps + requirements + decide

Anything under steps produces data. Anything under check produces a verdict. There are no Verifier kinds.

apiVersion: wyrd/v1
kind: Verifier
metadata: { space: marketing, name: deck-spec, version: 1.0.0 }
spec:
  inputs:
    deck: { type: media, formats: [pptx] }
  steps:
    - id: structure
      action: { kind: extract, from: inputs.deck }
      requirements:
        - id: slide-titles
          statement: Every slide has a title
          check: { kind: assert, each: steps.structure.output.slides[*].title,
                   operator: not_equals, expected: null }
    - id: review
      action:
        kind: agent
        agent: { kind: Agent, name: deck-reviewer, version: 2.0.0 }
        inputs:    { outline: steps.structure.output }   # injected
        workspace: { /inputs/deck.pptx: inputs.deck }    # read with fs.read
  requirements:
    - id: on-brand
      statement: Tone matches brand guide v3
      check:
        kind: agent
        agent: ./agents/brand-judge.yaml                 # no tools
        inputs: { claim: requirement.statement, outline: steps.structure.output }
  decide: all

#[derive(strum::EnumDiscriminants)]
#[strum_discriminants(name(CheckKind))]
pub enum Check { Assert { .. }, Trace(..), Agent { .. }, Code(..), Drift { .. } }

pub enum CheckEvidence { Run, Window }

impl CheckKind {
    pub const fn evidence(self) -> CheckEvidence {
        match self {
            Self::Assert | Self::Trace | Self::Agent | Self::Code => CheckEvidence::Run,
            Self::Drift => CheckEvidence::Window,
        }
    }
}

02 / Authoring model

One scope document; data flows forward, verdicts flow to decide

What a Verifier author reasons with. Everything a Verifier reads is a reference into one document that grows as the execution runs. Worked examples: example.md.

Green dashed: data (references). Black: verdicts to decide. Red dashed: the only place a verdict is read before decide, by a later step's when or action inputs. Checks never read verdicts.

inputs:                        # caller (verify / submit) or schedule window
  diff: { files: [...] }
steps:                         # one record per finished step
  scope:
    status: succeeded          # succeeded | failed | skipped
    output: { changed_lines: 412, files: [...] }
    requirements:
      reviewable-size: { outcome: passed, reason: ... }
requirement:                   # only while a check runs
  statement: Every behavior change has a covering test

Step requirement: checks one step's result right after that step runs, so a later step can react to it. Verifier requirement: checks the work as a whole, once, after every step. If the claim is about one step's result, attach it to that step; otherwise attach it to the Verifier. Requirements never feed each other: every verdict goes to decide once. Preserve skip causes through dependencies. pass_rate includes inconclusive results in its denominator; below threshold, any inconclusive result makes the verdict inconclusive, otherwise failed. With no applicable requirements, return inconclusive.

Step and requirement IDs share one namespace and must be unique across the entire Verifier. A route override names exactly one block; no qualified-ID syntax is needed.

03 / Registration

What registration validates and creates

Registration validates the authored contract; input, permission, evidence, and execution failures are also checked at their owning runtime boundaries. Registering a Card does not execute its Verifier.

Binding registration on a Service or Agent (verified_by) is refused when evidence() == Window and runs_on is not a schedule Trigger or when the explicit binding inputs map cannot fill a required slot. The map selects existing feature/metric sources by slot name. A Run Verifier needs no binding to be called; a binding only names Operators for its background failures.

04 / Client entry

Two methods; check type decides the route

Resolution and routing are local. A refused call sends nothing.

05 / Evidence

Files go to object storage before the call

Only for File inputs. Content-addressed, so dedupe is a storage HEAD. No Card, no upload row, no bytes through the server.

The server never trusts the declared digest or format: the engine recomputes sha256 and sniffs MediaFormat when it reads the bytes (sections 06 and 09), and a mismatch fails the step. A file that is a component (policy PDF, reference deck) is an Artifact Card passed as wyrd.ArtifactRef. Evidence garbage collection and regulated erasure are out of scope; no new deletion policy is implied.

06 / verify

Real time: execute in the request

No queue row and no Postgres write. The outcome is returned immediately and staged through ScribeOutbox; staging does not guarantee persistence.

verify never dispatches Operators: the caller already holds the verdict. A failed verdict is a normal 200. Engine errors return the stable error; the caller decides whether to call again.

07 / submit · Run evidence

Background: stage inputs, return, queue after Scribe ACK

The request path ends at 202. The queue row is created in batches, after the inputs are durable, so the runner never claims an execution whose inputs are missing.

202 means accepted, not durable. As with every Wyrd outbox, staged work lost to abrupt process death is counted (outbox_events_lost_total) and surfaces to wait() as a timeout. A completed row may also lack a visible or retained result; wait() polls for the actual result within its timeout, or returns a terminal execution error. HTTP retries reuse Idempotency-Key, scoped by tenant, subject, and actor: the same request reuses its execution ID; different content has a distinct submission ID and is rejected asynchronously by the batched writer. That submission becomes terminal errored with the existing idempotency-conflict code; status() exposes it and wait() raises it. The original execution stays unchanged. No per-request Postgres reservation is added. Scribe batch IDs and queue insertion deduplicate internal retries; they do not replace HTTP replay protection.

ExecutionInputsAck, ExecutionRequestOutbox, and ExecutionRequestSink are today's ObservationEnqueue, ObservationRunOutbox, and ObservationRunSink retargeted: the key changes from (binding, record) to (tenant, execution_id), and the writer-Card binding fan-out is deleted. Accepted caller authority and delegation survive acknowledgment, claim, retry, and restart without credentials; manual submissions do not switch to binding-owner or SYSTEM authority.

08 / submit · Window evidence

Drift: record rows; the schedule judges the window

Drift is never real time. submit runs today's drift_value body unchanged; the scheduler and window semantics are unchanged.

The scheduler insert is not on a request path, so it stays a direct short transaction. The samples slot is mapped on the binding. Window rules, missed-occurrence handling, and PSI/SPC/Custom scoring are unchanged.

09 / Background runtime

Claim → load inputs → execute → settle or retry

One runner for submitted and scheduled executions. A failed verdict is a completed execution, never an engine error.

Retries re-execute the whole execution; steps are read-only, so this is safe. Step-level checkpointing is deferred until retry cost on long agent graphs is measured. Operators fire for failed verdicts of background executions on a subject whose binding names them; the existing Operator worker, dispatch lease, and retry policy are unchanged.

10 / VerificationEngine

Stages of steps, requirements after each step, decide at the end

Today's vala-eval stage executor, generalised: actions instead of assertions, requirements per step, step failure recorded instead of aborting.
