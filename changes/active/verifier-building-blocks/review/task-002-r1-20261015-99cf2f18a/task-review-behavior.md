## Caller-to-result and regression traces

1. **No preparation:** public `blocks::VerificationEngine::run` → existing `VerifierSpec::plan` → `drive`'s final requirement stage → shared `walk` → `requirement` resolves Scope bindings → deterministic comparator, trace adapter, injected Agent/code check, or drift adapter → `Judged::report` → shared capture rule → one `decide` fold. No server, registry read, database, provider or interpreter is required by this path.
2. **Preparation graph:** the existing planner supplies topological stages. `drive` adds contract-specific requirement positions but does not own fanout, settled-state mutation or the stage barrier. `walk` prepares against previous settlements, runs one JoinSet and commits in stage/declaration order. Consequently a dependent sees both its upstream output/status and completed upstream judgments; completion scheduling cannot reorder the public result.
3. **Missing/failed evidence:** producer `Attempted::settle` writes `Settled::NoOutput` with `Missing::failed`; descendant selection returns that cause, `resolve_all` keeps the strongest gap, and `prepare` records a skipped descendant with the original failure cause. At a requirement, its implicit owner gap and explicit binding gaps meet before the executor. The consumer is inconclusive with the failure reason, even when the owner was intentionally skipped; all/pass-rate never silently removes it.
4. **Custom completeness:** supplied raw batch → configured metric-column null check → existing unscored report → `scored` keeps drift detail/window → `Judged::checked` → Inconclusive requirement → aggregation. A complete population still reaches the unchanged scorer; unrelated nulls cannot alter the selected population. PSI/SPC readiness and scoring remain their existing owner behavior.
5. **Retained scenarios:** `ScenarioScoring::score_scenario` → `execute_scenario:212` → `execute_plan:328` → same `walk`. `score_record` also calls that `execute_plan`. Legacy preparation still checks registry membership, first skipped dependency in declared order and condition evaluation before running. Each stage snapshot is rebuilt from the original context plus successful earlier ledger outputs; this preserves the old cumulative view and media/trace context through `ContextSnapshot::extend`. Old skips stay skipped, executor/condition errors propagate, joins map to `DagInvalid`, and comparisons remain results. The legacy output adapter still emits `TaskRunOutcome::Ran/Skipped`; passenger scenario scoring is untouched.
6. **Shared walker cancellation/error:** prepare errors occur before spawning that stage; task/join errors leave through `?` and drop its JoinSet, aborting unfinished siblings. Dropping the outer deadline future likewise drops the same owner. The new Verifier adapter turns only block-local failures into settled results; old `execute_plan` preserves its prior abort-on-executor-error behavior. Sharing scheduling therefore does not impose new result semantics on scenarios.

`RunLedger` is publicly re-exported but repository consumers were confined to executor internals before this change. Its generic parameter earns its place because two live result contracts share state ownership; `Done` boxes large payloads while Scope borrows the one ledger. The `Block` map adapts existing globally unique IDs to the immutable spec and is not another graph authority. Concrete `VerificationEngine` retains executors and permit state; `DriftChecks` retains resolved samples/baselines/window. No additional abstraction or dependency is needed to explain either workflow.
