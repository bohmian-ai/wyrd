### MNT-003-01 — Bounded Python print collection can panic on ordinary Unicode

- Classification: INCORRECT; blocking.
- Changed location: `crates/wyrd/wyrd-server/src/verification/hosted/sandbox.rs:196`, `Sandbox::exec` print callback.
- Governing obligation: INV-007 bounded output and safe isolation; maintainer guide's requirement that edge cases preserve error handling and remain safely changeable.
- Evidence and reachable path: direct `code` execution and hosted `code.run` both call `Sandbox::exec`. Its print callback slices `text` at `min(text.len(), budget - output.len())`, an arbitrary byte count. For a remaining byte budget of one and printed `é`, the chosen index is one, inside the UTF-8 character. Rust string indexing panics. With the default 65,536-byte budget, printing 65,535 ASCII bytes followed by `é` reaches the same case. The callback executes in the parent, so a valid sandbox program unwinds its server task instead of returning bounded output. The current real-worker flooding test prints ASCII only.
- Concrete maintenance cost: this duplicates truncation policy unsafely while `workspace.rs::truncate` already demonstrates the character-boundary invariant; changing output limits or supporting non-English output unexpectedly turns output collection into a panic path.
- Smallest testable correction: truncate at the largest UTF-8 character boundary at or below the remaining byte budget before appending (standard string boundary support, or reuse the existing character-safe truncation implementation). Preserve the byte ceiling and existing handling of later print events. Add one real-worker case where a multi-byte printed character crosses the remaining budget; assert no panic, valid bounded UTF-8, and continued sandbox service.
