## Proposed material findings

### STD-001 — Execution readback helpers treat a result identity as an execution identity

Classification: **INCORRECT**. Governing rule: AGENTS §§2/9 public surfaces project the same typed contract; `architecture/patterns.md` Client Pattern; r7 REQ-012 distinguishes execution identity, and REQ-015 explicitly makes SQL `execution_id` the execution correlation field. Public aliases are not authorized.

Changed locations:

- `sdks/wyrd-sdk-rust/tests/integration/support/mod.rs:291–320`: `Retained.result_id: String`, query selects `result_id`, then `ExecutionId` parsing asserts “result ID is an execution ID”.
- `sdks/wyrd-sdk-python/tests/integration/support.py:165–194`: Retained/result query has the same substitution and reconnects it as an Execution.
- `sdks/wyrd-sdk-ts/wyrd/tests/support/server.ts:96–101`: same query and `Execution.connect(row.result_id)`.
- Changed direct attribution readers `sdks/wyrd-sdk-rust/tests/integration/verify_in_real_time.rs:209` and `sdks/wyrd-sdk-python/tests/integration/test_verify_in_real_time.py:77` filter `r.result_id` with a value explicitly supplied as `execution_id`.

Producer-to-consumer evidence: the current separate analytical identity is `ResultPayload.result_id: VerificationResultId` in `crates/wyrd/wyrd-server/src/verification/results.rs:108`; queued runner `runner.rs:740` mints it independently. Direct execution intentionally reuses its UUID in `components/verification/service.rs:529–550`, which explains why a direct-only path could disguise this assumption. Those server owners are Task-005's cutover responsibility; no approved contract says its new execution identity becomes an alias for `result_id`. r7 instead names the field the SDK journeys should consume: `execution_id`. The helpers produce a string from the wrong column; the shared `Execution` client sends it to `/v1/verification/executions/{id}`, and schedule/attribution consumers depend on that identity being correct.

Sibling consumers inspected: Rust `observe_a_run`, `verify_in_real_time`, `scheduled_drift_alerts_operator`; Python corresponding journeys through `scheduled_result`; TS corresponding journeys through `scheduledResult`. The common helpers own the bad projection, so patching each story would repeat the defect. Older unchanged Bifrost result-detail joins also use `result_id` for actual result identity; those legitimate result joins must not be mechanically renamed. This finding is the changed code using a result column as an execution identifier.

Observable consequence: authored scheduled journeys can reconnect the wrong/unknown execution (or fail if the old column is retired); attribution readers can return no matching row. They do not prove the r7 contract and unnecessarily constrain Task-005 to preserve an undocumented identity equivalence.

Smallest correction: in these new/changed execution-correlating readers, select/filter the approved `execution_id` field, name the deserialized value accordingly, and pass it to the existing shared Execution owner. Preserve actual result-detail identity, table permissions, fitter/scheduler/flush and independent delivery checks. Do not change server identity semantics to accommodate the tests.

Focused proof: existing runtime unit/type/compile checks plus a small fixture-based assertion of the helper readback identity using distinct execution/result identifiers if an existing test seam supports it; otherwise prove the SQL/source projection statically now and execute the already-authored focused scheduled journey after Task-005 as already coordinated. Do not add a new server harness or broaden to whole journeys for task remediation.
