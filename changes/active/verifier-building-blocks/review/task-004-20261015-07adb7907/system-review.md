## Proposed finding

### SYS-001 — INCORRECT: waiting is not bounded by its caller deadline

**Violated obligation.** REQ-012 says wait tolerates delayed visibility *within its caller-supplied timeout*; REQ-013 requires a bounded wait timeout for lost staged work/results. TASK-004 scenario 2 requires bounded polling and timeout proof. The handle's own rustdoc promises `WYRD_SDK_504_VERIFICATION_WAIT_TIMEOUT` when that timeout passes first.

**Changed location.** `crates/shared/wyrd-client/src/verify/execution.rs:108–145`, particularly `self.status().await` at line 113 and the result return at line 115.

**Reachable producer-to-consumer evidence.** `Execution::wait` computes an absolute deadline but awaits the complete `status()` call before testing it. `status` invokes shared `request_json` (lines 78–86), which invokes `send_with_retry`; GETs are replay-safe and the transport can perform three attempts plus backoff (`transport/http.rs:977–1091`). Its configured per-attempt deadline is independent of the wait budget; the default is 30,000 ms (`transport/config.rs:150,200–207`). A stalled status read can therefore keep a 20 ms wait alive for the transport deadline/retries; an otherwise successful response delayed 200 ms is returned as a successful result even though the 20 ms deadline expired first. Sleeping until the exact deadline also enters another status read, since the next iteration has no leading deadline check. Authentication renewal and response-body decoding are inside that awaited operation as well.

**Observable consequence.** During a server/proxy outage, slow response or credential dependency delay, callers cannot use `wait(timeout)` to bound latency or release local waiting work. A successful late response can be reported instead of the promised timeout. This affects Rust directly, Python `PyExecution::wait`, TS `NativeExecution::wait`, and the support-desk examples through the same shared owner. It does not cancel or corrupt the server execution, and it provides no reason to restart or fail the shared server.

**Smallest safe correction boundary.** Enforce the absolute caller deadline around the complete status-poll operation in `Execution::wait`, including transport retries/auth/body reads, and stop starting another read after expiry. Expiry must return the existing `SdkVerificationWaitTimedOut`, preserving execution ID/last-status details. Keep the existing shared transport, retry-key policy, standalone `status()` semantics, terminal-error projection and server execution unchanged. No wrapper-local deadlines, new transport setting, polling runtime, server cancellation or fresh submission are needed. The handle owns the timeout invariant, so its deadline guard is at the correct owner.

**Focused closure proof.** Extend the existing wiremock-based owner tests in `observe/tests.rs` with a status response deliberately delayed beyond a shorter wait budget. Assert the existing timeout code and completion before the response, including when that late response contains a real result. Also exercise a status retry/backoff that would outlive the wait budget, and an expired budget that does not start an additional status read. Reuse the current mock/client helpers; no new harness/dependency or full journey suite is necessary. Run exact selectors for the new owner tests and existing `observe::tests::enqueue_replays_its_key_and_wait_returns_only_a_real_result` / `observe::tests::wait_raises_terminal_errors_and_times_out_without_a_result` through the repository mise toolchain. Existing tests only use prompt status responses for the 300 ms timeout (`observe/tests.rs:1096–1149`), so their reported green result does not establish the missing boundary.
