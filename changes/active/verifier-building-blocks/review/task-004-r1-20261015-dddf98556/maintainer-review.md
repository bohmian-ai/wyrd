## Proposed material finding

### MNT-R1-001 — lazy Python wait performs its initial credential IO outside the wait deadline

- **Classification:** INCORRECT; prior `FIND-004-1` closure is incomplete at the newly introduced `FIND-004-2` first-use path. Keep this cause consolidated during validation rather than reporting each credential flavor separately.
- **Changed location:** `sdks/wyrd-sdk-python/src/verify.rs:199` (`PyExecution::wait`), with `handle` at lines 125–134. Existing owner: `src/client.rs:140–157` (`LazyConnection::get`).
- **Obligation:** R1 requires the caller deadline to win over credential/status/retry/body IO, and spec r8 retains Python lazy construction and wait within its caller-supplied timeout. Maintainer-style requires public signatures and actual behavior to describe the same operation and meaningful lifetime state to have one owner.
- **Producer to consumer:** `Execution(id, client)` retains an unconnected LazyConnection. First `wait(timeout)` evaluates `self.handle(py)?` before creating the shared wait future. `handle` calls `LazyConnection::get`, which waits for its synchronous first-connection gate and uses the shared runtime to complete `Execution::connect[_with]`. Those factories await `WyrdClient::connected` / `connect_ambient`; `connected` awaits `access_token`, including `/auth/token` for an API key, renewable saved login, workload JWT or delegated credential. Only after that finishes does shared `Execution::wait` establish its `Instant::now() + timeout` at `crates/shared/wyrd-client/src/verify/execution.rs:112`. Its correct `timeout_at` cannot bound work already completed outside it.
- **Reachability:** the newly public lazy constructor is expressly required, and the authored `test_execution_constructs_offline_and_connects_on_first_read` confirms real credential exchange on first use. For an uncached API-key client, `Execution(id, client).wait(0)` still performs `/auth/token`; a slow/refused exchange can consume the transport's timeout and return a connection error instead of the caller's already-expired wait timeout. Two concurrent first uses can additionally wait on the same connection gate before the wait budget begins. Eagerly connected and queued handles do not have this first-use gap, because their inner handle is already present.
- **Concrete maintenance/user cost:** an identically typed `wait(timeout)` has different deadline semantics depending on how the same Execution was obtained. A caller cannot use it as a bounded operation after lazy reconstruction, and the shared owner's correct deadline test does not cover the wrapper's prelude.
- **Smallest correction boundary:** retain existing LazyConnection, shared Execution polling, credential owner and runtime. Make lazy connection acquisition and polling consume one caller deadline, including time waiting for another first connection; do not add a new token resolver, background connector or language polling loop. Preserve lazy/eager/queued client retention, failed-initialization retry and standalone status behavior. An expired/zero wait must not begin a new connection operation.
- **Focused closure proof:** extend the existing Python execution-server tests with a held/delayed initial exchange and `wait` as the first operation. Assert deadline wins, the stable wait-timeout code is returned, zero budget sends no request, and retry/reuse still works. The existing shared wait/replay tests continue to cover polling. No real-server journey suite is necessary for this boundary-lifetime proof.
