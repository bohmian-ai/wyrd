## Proposed finding INV-R1-01 — first lazy Python wait excludes connection from its caller deadline

- Classification: **INCORRECT**; retain under prior **FIND-004-1**, since this is the same caller-deadline invariant, exposed by FIND-004-2's remediation.
- Obligation: REQ-012/013 caller-bounded wait and original FIND-004-1's explicit requirement to bound credential resolution and transport IO; INV-002 preserves semantics across languages. Python's new constructor deliberately defers that IO to its first server operation.
- Exact location: `sdks/wyrd-sdk-python/src/verify.rs:198–202`, especially `self.handle(py)?.wait(timeout)`; producer/owner chain `verify.rs:121–128`, `src/client.rs:140–158`, shared `wyrd-client/src/client.rs:111–132`, shared `verify/execution.rs:111–117`.
- Evidence and reachability: `Execution(id, WyrdClient(url, api_key)).wait(0.02)` first evaluates `self.handle(py)?` synchronously. LazyConnection::get takes its mutex and block_on's Execution::connect_with. The shared eager connector calls client.connected -> access_token -> credential exchange before returning. Only after this finishes does shared Execution::wait calculate Instant::now()+timeout. A slow `/auth/token` therefore consumes its transport budget outside the 20 ms wait budget; a refused exchange may return an auth error after expiry, and a successful exchange may then start a fresh 20 ms polling budget. Even wait(0) connects first. Concurrent first-use gate waiting is likewise outside the budget. This is a concrete cold API-key-client path, not dependent on server engine work or a full journey.
- Siblings: Rust/TS connect and Python eager connect complete exchange before callers start wait, as designed; queued Python handles use ready and avoid first connection. Standalone Python status has no caller deadline. LazyConnection also serves other Python handles and must preserve their existing lazy/eager/cache/retry semantics. No global transport or polling setting needs changing.
- Consequence: Python callers using the explicitly approved lazy lifecycle still cannot bound the local wait during an auth dependency outage, despite the corrected shared polling implementation. The new lifecycle reintroduces the same observable timeout gap at the boundary before that owner runs.
- Smallest testable correction: keep one shared polling owner and existing LazyConnection owner, but make first lazy initialization and subsequent shared wait consume the same caller timeout. Bound first-use connection (including contention on first initialization) without changing eager connect, status, ready handles, token reuse, or unrelated LazyConnection consumers. Do not add Python polling, change global transport timeouts, or cancel server execution. Exact mechanics belong to implementation.
- Focused closure proof: extend the existing public Python local execution-server fixture with a delayed token exchange. A lazy short-budget wait must return the existing wait-timeout code before the exchange's larger delay, and a zero-budget wait must not begin connection/status IO. Preserve eager connection, first-use retry/cache and returned-connected behavior. Run that exact Python runtime test plus narrow Python/native type/lint checks; no server journey or gate is needed.
