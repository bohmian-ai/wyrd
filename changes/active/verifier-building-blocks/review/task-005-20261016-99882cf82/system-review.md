## Proposed findings

### SYS-001 — REGRESSION — Reclaimed attempts publish different outcomes under the same result ID

**Obligation:** REQ-012 returns a real execution result; REQ-013 preserves fenced settlement and original execution/result identity without inventing a durable recovery system. TASK-005 Scenario 3 explicitly requires immutable result identity and real outbox/lease/visibility proof. The permitted loss of a result is not permission to return an abandoned attempt's outcome as the completed execution's result.

**Changed source:** `crates/wyrd/wyrd-server/src/verification/results.rs:209–216` derives `result_id` solely from `execution_id`. Producer/consumer chain: `runner.rs::result` builds this payload; `VerifierRunner::settle` at approximately lines 417–470 stages `ScribeWrite::Result` after the SQL complete update but **before** `conn.commit()`. Its own cancellation/commit documentation explicitly acknowledges that a failed commit followed by lost lease leaves the staged result for an execution another claim re-executes. `verifier_executions.rs:221–247` reclaims expired running executions under a new token. The new attempt builds another payload with the same `execution_id` and hence the same `result_id`. `components/verification/service.rs:264–267` reads `WHERE result_id = ... LIMIT 1` without any attempt distinction.

**Reachable failure:** attempt A produces a failed Agent judgment and stages its result; its settlement transaction rolls back during a database/network interruption, while Scribe retains the staged result. The worker stops or loses renewal before committing. Attempt B reclaims the still-running execution and gets a passed judgment (remote model calls are expressly not exactly-once or deterministic across crashes). B settles successfully and publishes a second result with the same `result_id`. The two payloads differ in timestamps/outcome, so Scribe's content-derived batch fence does not deduplicate them. A reconnecting `status()`/`wait()` can return A's failed breakdown while PostgreSQL/Operator context represents B's passed completion, or vice versa. Drift feature joins can also combine rows from both attempts under the same result identity.

**Existing owner / sibling paths:** the base runner already minted one `VerificationResultId::new_v7()` per produced attempt payload and retained it for retries of that settlement. The existing SQL queue already persists the selected result ID and passes it into Operator frozen context. Production builder callers are queued `runner::result`, `VerificationControl::stage_direct`, and enqueue's inputs-only mapping; tests/fixtures also use the builder. Direct runs do not reclaim and inputs-only mapping does not need to mint a result. No alternate result store is necessary.

**Smallest correction:** restore a distinct immutable result ID for each produced attempt payload, carry it through the existing builder, SQL settlement and status lookup, and keep `execution_id` as the separate shared correlation field. Repeated publication/settlement of one payload retains its ID; a re-executed attempt gets a different ID. Preserve the current pre-commit staging and approved result-loss semantics; do not add a durable outbox, change acknowledgment guarantees, or try to select a winner by query ordering.

**Focused closure proof:** force rollback/interruption after A has staged, expire/reclaim its lease, complete B with a different verdict, retain both payloads, and prove the queue's selected result ID and real execution read return B only; verify the same chosen ID reaches Operator context and feature joins. Existing ACK replay test remains useful but alone cannot prove this switch.

### SYS-002 — INCORRECT — Runtime saturation consumes queued executions as inconclusive results

**Obligation:** approved specification Deployment limits, lines 945–952: bound in-process waiters; when full refuse additional in-process admission; background executions remain in the existing queue until runtime capacity is available. TASK-005 Scenario 6 requires real startup/admission proof that saturated background work remains queued.

**Source chain:** `VerifierRunner::new` constructs `ClaimLoop::new(postgres.clone(), None, ...)`, and the runner documentation explicitly says it claims without execution-count permits. All claimed executions share `HostedBlocks`' one sandbox/workspace capacity. `hosted/sandbox.rs:174–178` uses `admission.try_acquire()` and returns `BlockError::Retryable("the Python sandbox is at capacity")` immediately when live workers plus bounded waiters are full. `vala-eval/src/blocks/engine.rs:408–409` turns every check executor error into an inconclusive requirement. A step's admission error only retries within authored `step.retries` and then becomes a failed step (`engine.rs:350–365`), causing inconclusive dependent checks. `runner.rs::dispatch` maps every successful engine outcome to `EngineOutcome::Completed`, so these resource refusals settle the execution and permanently consume the work. The production `Deferred` path is used by drift input admission, not sandbox refusal; its runtime tests inject `EngineOutcome::Deferred` through the test script.

**Reachable consequence:** enough real submitted code checks to fill this process's configured workers/waiters cause the next claimed checks to complete inconclusive without running their code. Freeing workers later cannot resume them. This is normal load/backpressure, not missing evidence or malformed provider output. The problem affects both `code` actions/checks and Python invoked through Agent `code.run`; workspace capacity has the same need to distinguish capacity refusal from completed check evidence. There is no requirement to create synthetic host load to prove it: a small configured pool with deliberately held operations suffices.

**Existing owner / smallest correction:** preserve capacity refusal as an admission outcome at its existing hosted resource owner, then use the existing runner/ClaimLoop deferred-and-refunded queue transition. Do not solve it by enlarging/unbounding the in-memory waiter list or by adding another scheduler/queue, and do not blanket-promote all `BlockError::Retryable` errors: genuine check-isolated provider/infrastructure failures still need the approved inconclusive semantics. Ensure resource-specific saturation remains distinguishable through code actions, checks and `code.run` so a queued execution is not falsely settled. Direct in-process calls retain bounded existing capacity/error behavior; siblings need not stop or crash.

**Focused closure proof:** configure a tiny real shared pool, hold its admitted operations, submit another real queued Python execution, and prove it remains pending/retrying/deferred without spending its attempt budget or publishing a completed inconclusive result. Release capacity, then prove the same execution ID finishes with its actual code outcome. Cover at least a check and the Agent `code.run` propagation boundary; retain cancellation/deadline release proof. A scripted engine `Deferred` result does not prove this.
