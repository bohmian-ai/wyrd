## Proposed material finding

### BEH-R2-01 — INCORRECT: a keyed conflict disappears when its changed target is absent in the caller's tenant

**Violated obligation:** REQ-013 explicitly requires the batched writer to record a conflicting submission as terminal errored under its own identity, expose the conflict through status, and make wait raise the existing conflict error. TASK-005 Scenario 2 and AC-006 require that observable negative flow. The permitted process-death/drain loss model does not permit knowingly consuming a successfully acknowledged conflict without its outcome.

**Exact location:** `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:117` (`INSERT_SUBMISSION_SQL`, especially 125–132), `:1138` (conflict insert), and `:1205` (insert result ignored). `server/verification/submissions.rs:95–113` then commits and consumes that Conflict outcome. This code is newly introduced in the cumulative range.

**Reachable producer → consumer path:**

1. An unbound authenticated caller with the appropriate Verifier grant submits request A with valid Verifier V, subject S and key K. The writer accepts A.
2. The same subject principal and actor use K with request B whose `card_uid` is a syntactically valid but nonexistent or foreign-tenant UID, with V unchanged. The principal is unbound, so the signed-scope gate appropriately does not reject this at `VerificationControl::enqueue:570`. Enqueue does no Card read and returns B's distinct derived execution ID after staging.
3. Scribe's server-internal frame derives permitted correlation UIDs from the already-staged rows (`scribe_outbox.rs:414`), so there is no registry-existence validation preventing this ACK/handoff. B reaches the existing submission queue.
4. `VerifierExecutionQueue::accept` takes the scoped K lock, finds A with a different request hash, and decides Conflict **before** target resolution. It calls `insert_submission` with the conflict error and no key.
5. That shared INSERT selects `wyrd.cards v, wyrd.cards s`. Under caller-tenant RLS there is no matching S row, so zero rows are inserted. `insert_submission` never checks affected rows; accept still returns Conflict. SubmissionSink commits successfully, logs the conflict and permanently consumes B.
6. `get_execution` always returns 404 for B. All SDKs' shared `Execution::wait_until:130–167` retry that 404 until `WYRD_SDK_504_VERIFICATION_WAIT_TIMEOUT` instead of the promised structured idempotency conflict. A remains unchanged, but B's required terminal outcome is absent.

**Sibling callers/writers and existing alternative:** both conflicting and ordinarily refused submissions use this same conditional insertion; their only production writer is SubmissionSink after the common Scribe ACK handoff. HTTP and MCP enqueue converge in VerificationControl, and SDKs share HTTP plus the same wait implementation. Scheduled queue insertion is separate and already refuses before returning an execution identity. The existing queued-error/status projection is the outcome mechanism to reuse; neither SDK polling changes nor per-transport guards can manufacture its missing authoritative row. The SQL test at `pg_verifier_executions.rs:774–787` explicitly establishes that an absent target selects no row, but it does not test the keyed-conflict case required here.

**Observable consequence:** a valid authenticated retry with conflicting target content receives an ID whose promised conflict can never be inspected or raised. This occurs with healthy Scribe/Postgres, no crash, no timeout during acceptance, and no outbox loss; increased wait time cannot fix it.

**Required testable correction:** make the existing batched queue conflict decision produce a durable terminal record readable under B's returned ID even when B names a Card absent under that tenant's RLS. Keep A unchanged and make B nonclaimable/nondispatching; retain exact tenant/principal scoping, no request-path Postgres writes, no foreign Card disclosure, asynchronous acceptance and existing loss guarantees. Reuse the current execution queue/error/status owner; do not introduce receipts, a second queue/store, fake passing results, or broaden tenant authorization. Private row/column organization is explicitly implementation-owned by the original task. Validation should select the smallest representation change within that boundary; merely checking zero inserted rows or repeating the same INSERT does not close it.

**Focused closure proof:** extend the existing keyed queue test with valid A and B changing only the subject to a fresh unknown UID (and, if useful, one foreign-tenant UID). After commit, B's returned ID reads errored with the canonical conflict code, A retains its identity/state and there is no executable or dispatchable B. One existing route/shared-client negative case should verify that HTTP 202 followed by status/wait exposes the terminal conflict rather than a polling timeout. No new harness, live provider, broad gate, or all-language rerun is needed for the shared cause.
