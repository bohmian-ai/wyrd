## Proposed finding

### BEH-R3-01 — Deployment per-file limit is absent from execution admission

**Proposed stable ID:** FIND-TASK-005-14 (new cause; prior FIND-10 concerns declared-slot conformity and FIND-11 combined accounting). **Classification:** MISSING / INCORRECT. **Obligation:** approved Deployment limits specify `WYRD_VERIFICATION_FILE_MAX_MIB` as maximum bytes in one input file and prohibit a slot from raising that limit (`spec.md:928–950`); REQ-002 requires size-invalid evidence refusal; AC-006 requires cross-boundary oversized rejection. Current runtime reference also promises a file over FILE_MAX yields `WYRD_VERIFICATION_413_INPUT_TOO_LARGE` before anything runs.

**Exact owner:** `crates/wyrd/wyrd-server/src/verification/hosted/evidence.rs:333–379::TenantEvidence::admit`, especially `:340–370` deriving either original File declared size or authorized selected Artifact size, followed only by the combined bound at `:371–379`. Engine `conform` at `crates/vala/vala-eval/src/blocks/engine.rs:921–974` knows authored slot max, not Deployment max. The only actual per-file Deployment guard remains `TenantEvidence::stored` at `evidence.rs:261–263`, after a consumer chooses to read bytes.

**Reachable caller-to-result counterexample:** use the valid spec already registered by `pg_verification_routes::direct_execution_refuses_nonconforming_evidence` (`:1089` onward). It declares required integer `x`, optional JSON `note`, and optional media `pages` accepting PDF with no slot max. Requirements inspect only `x` and `note`. Send raw HTTP/MCP execute with x=1, no note, and pages File declared at **21 MiB**. Default per-file max is 20 MiB; combined max is 100 MiB. The envelope is typed-valid, `conform` accepts the media kind/format and absent slot max, host admission accepts the 21 MiB sum, and neither assertion reads bytes. It returns a **passed 200 result**. The existing test's oversized case uses 200 MiB, caught by combined accounting, and misses this interval.

This does not depend on lying about stored bytes: select the fixture's real registered 11-byte `notes.txt` Artifact with configured `file_max_bytes=4`, `files_max_bytes=20`, a text media slot without a lower max and an independent valid JSON requirement. `artifact_file` retrieves the true authorized 11-byte inventory, admission accepts it, and the assertion-only run passes. Artifact registration is not the evidence-plan path. Existing File evidence retained when startup limits decrease likewise cannot rely on a past upload plan. Normal fresh SDK upload preparation checking file size does not enforce authoritative execution admission for these callers.

**Siblings traced:** direct execute and queued dispatch both obtain their engine through `HostedBlocks::engine`, which installs this same evidence reader. Enqueue does not resolve inputs on its hot path, so the background engine has the identical omission. Extract/native-media/workspace/citation consumers eventually use `stored` and reject an oversized read, but then produce block-local failure/inconclusive rather than a structured pre-block refusal and may already have performed sibling work. Code Artifact sources are a separate code-source/read path and do not justify removing their existing read guard. The correction belongs at original evidence admission, not each consumer or SDK.

**Consequence:** configured file limits can be bypassed by present original evidence and a subject can receive a passing verdict for a request the server promises to refuse; read consumers expose inconsistent error/timing and can run other work before recognizing the same size violation. No unbounded-body memory claim is needed to establish this contract defect.

**Smallest testable correction:** after deriving each File/selected-Artifact size at the existing `TenantEvidence::admit` owner, enforce current `limits.file_max_bytes` using existing `EngineError::InputTooLarge`, before combined accounting/drive. Retain slot limits, checked combined addition, authorized Artifact lookup, later digest/length/sniff/read guards, per-workspace restrictions and no-byte admission. Reuse current direct 413 and queued terminal input_invalid mappings. Do not add a loader, shared foundational dependency, upload session, new endpoint/error or request-path SQL call.

**Focused proof:** extend the existing direct raw request fixture with one file above file_max but below files_max and no authored slot max, while requirements need not read it; expect 413 and no block/result. Extend the existing tiny hosted Artifact admission fixture with true inventory size in that interval and an assertion-only valid control. Include the same submitted original input through existing queued runtime proof: terminal errored/input_invalid with no verdict/Operator or authored retry, and below-limit control completes. Preserve current oversized slot/combined, missing required/optional and repeated-read assertions. Run exact new selections and only their owning narrow route/hosted slice; no broad journey/gate/live provider run or new harness is required.
