## Material proposed finding

### INV-R3-01 — Execution admission still accepts a file above the deployment's per-file cap

**Classification:** INCORRECT / MISSING. **Stable-ID relationship:** residual of FIND-TASK-005-10's authoritative evidence-size refusal; do not create a separate new ID merely for File versus Artifact consumers. FIND-11's aggregate-total correction itself is closed.

**Violated obligation:** REQ-002 refuses evidence outside size constraints; approved Deployment limits (`spec.md:928–949`) define `FILE_MAX_MIB` independently of `FILES_MAX_MIB` and say slot limits may lower, never raise deployment limits. INV-006/007 and original task Scenarios 1/5/6 apply. Current published runtime reference (`reference/verification-runtime-limits.md:93`) explicitly promises the existing 413 before blocks for this cap.

**Producer/consumer evidence and reachable consequence:**

1. Public typed HTTP/MCP VerificationRequest accepts a File declaration directly, with no prerequisite plan call. Artifact evidence follows the existing authorized Card/inventory path. Upload-plan validation is not execution admission: `VerificationControl::evidence` checks `file_max_bytes`, but direct `execute` and queued `enqueue` do not invoke that operation. Artifact inventory files need no evidence upload plan at all.
2. `vala-eval/src/blocks/engine.rs:945–963::conform` checks File format and only the optional slot `max_bytes`. A valid media slot can omit that lower cap; it can also have an authored cap above the current configured deployment bound. Artifact metadata is deliberately checked later by the host.
3. `wyrd-server/src/verification/hosted/evidence.rs:333–381::TenantEvidence::admit` obtains a size for each File or authorized selected Artifact, validates Artifact format/slot cap, then tests only the sum against `files_max_bytes`. It never compares the individual size to `file_max_bytes`. Both direct and queued HostedBlocks engines attach this same reader before `drive`.
4. With defaults, a text File declaration of 21 MiB is below the 100 MiB aggregate limit but above the 20 MiB file limit. Supply it to an optional or required media slot with no `max_bytes` plus a valid JSON slot used by an ordinary passing assertion. Admission succeeds and the result passes while retaining the oversized declaration. No read is needed; the same no-read behavior is deliberately supported by the new admission tests. A selected authorized Artifact of this size has the same path using real inventory metadata, even though its bytes were registered independently of evidence planning.
5. If an extract/native-media/workspace/citation consumer does read it, `TenantEvidence::stored` at `evidence.rs:261–262` finally refuses the size as **BlockError::Terminal**. The action is then a normal failed preparation, or the check is inconclusive, rather than the execution-level size refusal before blocks. This prevents an oversized body read, but does not satisfy authoritative admission or the public error/result contract.

Thus the issue is a missing admission predicate, not an unbounded storage read or a reason to prefetch bytes. It is shared by all supported byte consumers; patches in each consumer or SDK are unnecessary.

**Smallest testable correction:** in the existing TenantEvidence admission owner, after obtaining each original File/Artifact size and before charging the aggregate or running blocks, refuse `size > self.limits.file_max_bytes` with the existing EngineError::InputTooLarge. Preserve the slot check, checked aggregate sum, metadata-only Artifact authorization, later length/digest/sniffing, code-source reads and existing errors. This uses the already known size and requires no loader, dependency, public error, request PG write, or upload session.

**Focused closure proof:** reuse the tight hosted fixture with a per-file cap below the selected registered notes file's actual size and an aggregate cap above it. Cover both a raw File declaration and authorized Artifact in a slot with no lower `max_bytes`; a spec whose otherwise-passing assertion does not consume that media must still refuse before actions. Include a consuming control and a within-limit success. Direct must expose the existing 413; queued must terminally error with no result/verdict/Operator and no provider/authored retry. The shared owner plus narrow route/runner seam proof suffices; no live uploads of tens of MiB or broad journey suite is needed.

The new tests currently exercise unknown name, wrong declaration kind, JSON schema, format, authored slot cap, combined total and repeated reads. They do not exercise this independent deployment per-file cap at execution admission.
