**Recommend one process-wide resource broker in `wyrd-runtime`, with dynamic leases and capability-specific adapters.** Keep only justified server/Bifrost baseline reservations. A suspended Python session must retain its memory and scratch charges; it can yield runnable CPU capacity.

The central issue is independent promises, rather than universal preallocation. Bifrost already shares much of its memory dynamically, but hosted execution, HTTP buffering, recording, caches, and scratch do not share one complete ledger.

2. **What can safely be reclaimed**

- **Caches:** evictable, but removal does not necessarily free memory immediately: callers retain cloned `Bytes`. Today eviction also leaves the standing root reservation intact. [range_cache.rs:41](../../../../crates/vala/vala-bifrost-redux/src/storage/range_cache.rs:41)
- **Oracle/Forge memory:** can shrink, spill or fail cooperatively. Already-owned data cannot simply be revoked. DataFusion’s infallible growth can exceed the governed cap and is recorded as headroom, so this is not a strict RSS ceiling. [resources.rs:2824](../../../../crates/vala/vala-bifrost-redux/src/resources.rs:2824), [resources.rs:3683](../../../../crates/vala/vala-bifrost-redux/src/resources.rs:3683)
- **Live Python:** resident interpreter state is non-preemptible during normal execution. The checkout remains held across nested tools; Python waits while the child Oracle query needs additional resources. [sandbox.rs:224](../../../../crates/wyrd/wyrd-server/src/verification/hosted/sandbox.rs:224), [sandbox.rs:339](../../../../crates/wyrd/wyrd-server/src/verification/hosted/sandbox.rs:339), [tools.rs:291](../../../../crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:291)
- **Scratch and asynchronous work:** retain charges until writers settle and files are actually removed. Cancellation alone is insufficient; hosted blocking work already retains permits until settlement. Spill cleanup can fail and currently logs that failure. [tools.rs:332](../../../../crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:332), [resources.rs:4300](../../../../crates/vala/vala-bifrost-redux/src/resources.rs:4300)

Monty supports resetting healthy workers, but Wyrd currently drops each checkout. Checkout drop kills the worker and releases pool-count capacity before background reaping finishes. A free pool slot therefore does **not** prove memory has disappeared. [checkout.rs:1191](../../../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/monty-pool-1.1.0/src/checkout.rs:1191), [checkout.rs:2110](../../../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/monty-pool-1.1.0/src/checkout.rs:2110), [pool.rs:336](../../../../../../../../.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/monty-pool-1.1.0/src/pool.rs:336).

**Inference:** nested work needs separate accounting for retained parent state and runnable child work. Releasing parent memory on suspension would double-promise it; indefinitely waiting for child memory can deadlock.

`crates/shared/wyrd-runtime` fits the neutral broker responsibility. It already owns cross-cutting runtime shells, has light dependencies, and both server and Bifrost depend on it. Keep DataFusion, Oracle classes, Monty and server policy in their adapters. The current Bifrost resource owner imports those Bifrost-specific concepts, so moving it wholesale would preserve the wrong coupling. Current policy specifies **1 GiB server headroom, a 4 GiB supported-process floor and 256 MiB free-disk floor**. These are documented policy values, not demonstrated physical minima. The resulting 3 GiB Bifrost budget on the smallest process is not a distinct necessary reservation. Cache budgets may be zero; Oracle’s 256 MiB query ceiling and 32 MiB slot quantum are not resident allocations. 4. **Production patterns — external evidence**

| Pattern | Guarantees, reclamation and overload | Nested work and replicas |
|---|---|---|
| **Velox memory arbitration** | Shared query pools borrow free capacity, reclaim at safe points, spill, then potentially abort a victim and wait for completion before reuse. Non-reclaimable sections remain protected; spilling itself needs headroom. [Official design](https://facebookincubator.github.io/velox/develop/memory.html) | Accounting follows pool hierarchy; arbitrary Python-parent admission is not covered. Limits remain local to each node. |
| **Spark unified execution/storage** | Execution and cache share one region; either can use it when the other is idle. Execution evicts borrowed cache, while protected storage resists eviction. Active execution cannot simply be taken back; allocation can return less for spilling. [Tuning](https://spark.apache.org/docs/latest/tuning.html), [implementation](https://raw.githubusercontent.com/apache/spark/master/core/src/main/scala/org/apache/spark/memory/UnifiedMemoryManager.scala) | Task fairness includes waiting for memory to return. It does not establish arbitrary nested-call safety. Each executor manages its own heap. |
| **Ray logical admission plus physical-pressure recovery** | Resource vectors guide placement but do not enforce consumption. Object data spills; heap pressure can require worker termination. Its fixed memory divisions do not satisfy Wyrd’s requirement unchanged. [Resources](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html), [spilling](https://docs.ray.io/en/latest/ray-core/objects/object-spilling.html), [OOM handling](https://docs.ray.io/en/latest/ray-core/scheduling/ray-oom-prevention.html) | A parent blocked on `ray.get` yields CPU while retaining GPU resources because state remains live. Scheduling and pressure handling are node-local. [Nested tasks](https://docs.ray.io/en/latest/ray-core/tasks/nested-tasks.html) |
| **Kubernetes requests and burst** | Requests protect admission minima; surplus is usable. CPU can throttle, whereas memory/disk pressure may require terminating holders. Disk reclamation precedes workload eviction. [Resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/), [pressure eviction](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/) | It cannot see in-process nested dependencies. Replicas add capacity on their nodes. Its kernel enforcement mechanisms are excluded by Wyrd’s portability rules. |
| **Mesos/DRF multi-resource fairness** | Dominant-resource fairness orders allocations across resource vectors; quotas provide minima. Unused offers can return, but running-task resources require completion/failure. Fairness does not itself reclaim memory. [DRF paper](https://www.usenix.org/legacy/event/nsdi11/tech/full_papers/Ghodsi.pdf), [roles/quotas](https://mesos.apache.org/documentation/latest/roles/), [allocator lifecycle](https://mesos.apache.org/api/latest/c%2B%2B/classmesos_1_1allocator_1_1Allocator.html) | Offers preserve node identity. DRF provides no general nested-work deadlock solution. This is historical production evidence. |

5. **Recommended design — inference**

Use one broker tracking **memory bytes, scratch bytes per filesystem, and runnable CPU capacity**:

- Charge ownership before allocation; transfer leases with buffers instead of charging the same buffer twice. New encodings/copies need additional charges.
- Let every capability borrow unused capacity. Charge caches by retained allocations and shrink idle workers; keep operation/security limits separate from reserved capacity.
- Treat live Python sessions as bounded, non-preemptible holders. Until worker allocation supports parent-approved growth, conservatively reserve their enforceable peak envelope at checkout and retain it through confirmed teardown.
- On nested calls, yield CPU but retain parent memory/scratch. Try to acquire child capacity atomically after safe reclamation; fail within the existing deadline when progress cannot be guaranteed. Never indefinitely queue a child behind its own parent.
- Reclaim caches, spill, flush or cancel only through owner-safe mechanisms. Reuse capacity after settlement. Bound waiter metadata and preserve fairness without fixed capability shares.

This follows Velox’s explicit reclamation and Ray’s CPU/state distinction. Its tradeoff is conservative admission for non-preemptible workers: temporarily unused space inside a live grant cannot safely be promised elsewhere.

Across replicas, each broker needs a **disjoint assigned process budget**. Host totals and filesystem free-space observations cannot provide that assignment. Current detection uses host RAM and filesystem availability; it also calls `cgroup_limits()`, conflicting with the repository’s locked prohibition. [resources.rs:4468](../../../../crates/vala/vala-bifrost-redux/src/resources.rs:4468), [resources.rs:4527](../../../../crates/vala/vala-bifrost-redux/src/resources.rs:4527).

Implementation reaches runtime broker/export, Bifrost resource/cache/spill adapters, boot composition, hosted sandbox/worker/workspace/tools, outbox, HTTP buffering/uploads and config. Capacity wording in the specification/task must reflect the authoritative maintainer requirement.

Prove it with accounting invariants plus real mixed-capability journeys: Bifrost alone borrows the available budget; mixed workloads exchange capacity; nested calls complete or fail promptly; cancellation retains charges until settlement; shared-filesystem spill cannot oversubscribe; worker reaping and cleanup failures cannot release resources early. Measure process-plus-worker memory and disk against ledger totals, including transient copies and reclamation headroom.
