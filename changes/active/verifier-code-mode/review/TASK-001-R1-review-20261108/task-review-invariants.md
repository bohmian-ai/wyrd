## Producer-to-consumer traces and owner comparison

### Started work and settlement

`HostedTools::open` (`hosted/tools.rs:139–179`) creates one `Invocation` with a `TaskTracker` and installs a settlement future on `ToolSession`. `Invocation::blocking` (`:303–319`) takes the current Dispatch permit through `hold_permit` and moves both it and the optional owned writer into the actual blocking closure. FsSearch, FsList/FsRead/FsExtract, and code mount setup use that shared method. Extraction still reaches the original `Workspace::extract`, including its shared room calculation and `persist_noclobber`; no alternative extractor or publication path was introduced.

The existing Workspace writer was correctly extended from a borrowed guard to an owned guard. An Arc to Workspace alone did not serialize mutation; the owned guard now does. Likewise, simply aborting a Tokio blocking JoinHandle could not stop a running extraction. Installed TaskTracker supplies appropriate settlement without a new runtime or worker service. The task-local permit transfer belongs to Dispatch, the existing active-operation owner, rather than a second semaphore in extraction.

`AgentExecutor::invoke` (`blocks/agent.rs:410–421`) drops the running Agent future when Halt wins and awaits `ToolSession::close`; `close` consumes and awaits the installed settlement future (`blocks/tools.rs:231–249`). Thus normal return and a host stop that reaches this close path wait for started blocking work. The closure owns writer/permit/workspace throughout; a dropped nested Delivery cannot publish a late value. Those are substantive improvements.

The engine owns additional exit boundaries that do not pass through that close path: `Engine::attempt` times out the whole executor future (`blocks/engine.rs:675–684`), then may retry immediately (`:687–690`); `Engine::run` times out its drive (`:359–376`); a dropped run aborts its running blocks. The queued runner also selects abandonment/lease loss against execution (`verification/runner.rs:891–896`). A session-local settlement future is dropped with any of those futures. There is no parent settlement owner draining it after drop. `HostedBlocks::shutdown` (`hosted/blocks.rs:96–101`) drains only Sandbox, not Invocation trackers. This is the remaining shared-owner defect, detailed below.

### Admission and records

Direct `RecordedTool::invoke` and nested `ToolBridge::call` still converge on `Dispatch::call`. Name resolution and bounded object encoding precede its `ToolCalls::start`; the slot now exists before permit waiting (`blocks/tools.rs:538–576`). A cancelled admitted waiter is therefore present in `ToolCalls::settled`, whose unfinished-slot representation supplies no digest, zero bytes and cancellation (`:138–156`). Engine action/check result consumers continue taking that list (`blocks/engine.rs:696,788`), with the same retry-spanning ToolCalls owner. No new record store or downstream result patch was added.

`Dispatch::permit` waits on both shared capacity and Halt and checks Halt again after acquisition (`blocks/tools.rs:633–645`). This closes the already-spent waiter race without another budget spend or capability-specific guard. Successful ordinary non-code operations hold the existing semaphore; code holds no child permit. Moving a permit into blocking work correctly retains that allowance inside the same session. Its cross-attempt weakness is caused by missing cleanup, not by this permit transfer.

### Honest nested delivery

`Dispatch::call` bounds/encodes the result and returns a `Delivery` without completing its slot (`blocks/tools.rs:579–614`). Dropping it leaves the existing unfinished/cancelled slot. `Delivery::refuse` clears output evidence via `failed`, while `deliver` commits the successful bounded JSON digest/size (`:682–727`). Direct calls deliver through the existing tool return. Nested calls go through `Sandbox::answer` (`hosted/sandbox.rs:501–539`), whose conversion failure refuses the delivery and produces the safe catchable problem. Successful values remain pending in `answered` until ResolveFutures, and the driver delivers them at the existing resume boundary (`:373–393`). Program exit before that branch drops them unpublished. An already-published child retains its successful slot if the program subsequently fails.

This is an earned publication handle around the existing ToolCalls owner, not a second result ledger or a worker acknowledgement protocol. The prior correction explicitly selected the driver resumption boundary and did not require an acknowledgement that Python inspected each result. No speculative IPC acknowledgement hardening is proposed here. The unsigned-range repair uses the installed Monty representation and does not change this lifecycle owner.

### Code setup deadline

`Invocation::code` reserves from the existing shared Python time budget, derives the earlier operation/invocation deadline, and now wraps writer wait and mount setup in `timeout_at` (`hosted/tools.rs:337–364`). The reservation still charges elapsed wall time on drop. A writer waiter expires before reaching Sandbox; started mount work runs through the same tracked blocking method. The timed-out setup receives a typed host stop. Its successful explicit-close behavior passes; outer engine drop is the same settlement defect, not a separate deadline finding.

## Retained finding

### INV-R1-001 — FIND-TASK-001-2 remains open when the engine drops the attempt

Classification: **INCORRECT**, incomplete remediation of the prior shared cleanup cause. Violated obligations: approved REQ-012 and AC-009/018; original TASK-001 explicitly requires cleanup to await started blocking extraction, and R1 explicitly requires all exit causes through the same cleanup owner. REQ-011 also suffers when a logical invocation retries before old active work ends.

Exact changed location: `blocks/agent.rs:419–421` awaits `ToolSession::close` only after Agent completion/Halt; `blocks/tools.rs:242–249` keeps the sole settlement future inside that cancellable executor future. Relevant consumers: `blocks/engine.rs:675–690,359–376`, queued `verification/runner.rs:891–896`, and hosted shutdown `hosted/blocks.rs:96–101`.

Reachable scenario: an Agent step starts a bounded fs.extract, then its configured per-attempt timeout expires while the blocking extraction is still running. `timeout_at` drops the entire Agent executor future, including ToolSession/close or an in-progress close. The extraction continues in TaskTracker's blocking closure. Engine::attempt proceeds to its retry or settles the timed-out step; it does not await any tracker. With a retry, a new ToolSession has a new Dispatch semaphore and workspace, while the prior operation still owns its old permit/workspace. At cap 1 the retry can begin a second actual non-code operation, or can be refused workspace capacity held by the previous attempt. At an execution deadline, the engine can return its timeout before the old mutation ends. After checkout drop, Sandbox-only shutdown does not see that blocking work.

Observable consequence and materiality: a supported timeout/retry or shutdown can advance past the invocation cleanup boundary while authorized host work continues, with concurrent old/new attempt work or falsely completed drain/accounting. This is an explicit lifecycle guarantee, not an improbable input or a request for rollback. Retaining the directory/writer/old permit prevents the original same-workspace race, but does not await cleanup or make the old operation visible to the next attempt's allowance. The R1 evidence itself acknowledges engine timeout drops the session without awaiting settlement.

The decisive case is the result-producing per-attempt timeout: the engine itself retains control, can settle the step or retry, and currently does so without settlement. This does not depend on requiring a cancelled public request to return a result or on making arbitrary Rust future destruction asynchronous. Execution-deadline/runner abandonment are affected sibling owners to preserve during correction, not separate demands for a durable cancellation journal. The Sandbox shutdown trace establishes that it is not an existing fallback drain for these tasks; it is not a request to redesign process shutdown.

Required correction boundary: retain the existing owned writer/permit and TaskTracker, but make its settlement belong to the existing attempt/execution/host lifecycle that survives dropping the timed Agent future. The owner applying an attempt timeout must cancel execution, settle its already-started bounded work, and only then retry or report cleanup/terminal completion. The execution cancellation and shutdown owners must retain and drain that same work rather than relying on a dropped session future. Reuse the current engine/host/runner lifecycle and installed tracker; do not add a second extraction executor, durable journal, OS cancellation mechanism or blocking async Drop. Preserve ordinary request timeout outcomes and no-result semantics, allowed extraction completion during cleanup, no-overwrite and partial scratch behavior, unrelated service availability, and existing queue lease safety.

Correction burden: moving guards alone is now done and cannot close this consumer boundary. Awaiting close only inside AgentExecutor cannot survive its owner's `timeout_at`; increasing deadlines or detaching another cleanup future without a retained/drained lifecycle owner also cannot establish completion. A bounded ownership correction at existing timeout/cancellation consumers is warranted by the explicit requirement. It does not require a new product decision or changes to extraction mechanics. Consolidate all these callers under FIND-2 rather than separate findings for each timeout/runner/shutdown path.

Focused proof: extend the existing held-extraction/engine seam with a configured attempt timeout while extraction is held. Assert no retry/terminal-cleanup completion until release; release it, then assert cancellation record/no late returned value, cleanup completion and fresh capacity. Inspect affected outer-deadline/cancellation/shutdown owners to ensure the same work remains tracked and the correction does not weaken their existing behavior; do not invent a cancellation-result guarantee. Existing manual tracker-wait and same-session permit tests remain useful assertions but are not substitutes for this caller-boundary proof. Do not repeat the whole journey matrix or introduce synthetic load.
