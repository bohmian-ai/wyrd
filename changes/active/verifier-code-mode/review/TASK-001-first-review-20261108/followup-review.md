## (a) BusyCode yields before refusing

**Supported cause:** the old fixture could return Busy on its first poll, before the pending sibling's invocation body ran. At the base, `BusyCode::invoke` immediately constructed and returned its Busy error. Candidate `crates/vala/vala-verify/tests/integration/blocks_agent.rs:1118` instead first awaits `tokio::task::yield_now()`. The response places `code_run` before `bifrost_query` (`blocks_agent.rs:1231`). Skald polls the tool futures through `buffer_unordered(concurrency_cap)` and collects them (`crates/skald/skald-agent/src/loop_runtime.rs:699`); parallel admission does not promise that both invocation bodies start before the first completes.

The candidate's `RecordedTool::invoke` spends before dispatch (`crates/vala/vala-verify/src/blocks/tools.rs:693`), and `Dispatch::spend` refuses when Halt is already raised (`tools.rs:453`). A Busy tool result raises Halt through `Halt::observe` (`tools.rs:411`, called from `Dispatch::call` at `tools.rs:559`). `AgentExecutor::invoke` races the loop against that halt (`crates/vala/vala-verify/src/blocks/agent.rs:410`). Consequently, an immediate refusal can prevent the sibling from entering `PendingQuery::invoke`; no `DropFlag` is then constructed, and its false flag cannot diagnose a failure to cancel an actually pending query. The sibling only creates that flag inside its invocation body (`blocks_agent.rs:1172`).

**Observation preserved:** the required observation is cancellation of an *already pending* sibling, prompt Busy, and no retry or additional model call. Yielding establishes the test's precondition; it does not change production scheduling or relax the assertions. `blocks_agent.rs:1317` onward still checks Busy, elapsed time below the step deadline, exactly two untouched provider responses, and the drop flag. The root reports an independent rerun of this exact test: 1 selected/1 passed, run `2d815474-0929-4e90-a227-59c75c00c32b`. I did not run it myself. A yield alone is not a universal scheduler ordering guarantee, but the unchanged drop-flag assertion detects failure to establish/drop this precondition in the actual run.

## (b) Scope drops the pinned step's owner

**Supported cause:** `tokio::pin!(step)` shadows the future with a `Pin<&mut Future>`; dropping that reference is not dropping the underlying stack-owned future. `Cargo.lock:8426` selects Tokio 1.52.3. Its installed `src/macros/pin.rs:125` explicitly expands to an owning `let mut step = step;` followed by a shadowing `Pin::new_unchecked(&mut step)`. Thus a hypothetical `drop(step)` after the macro consumes the pinned reference while the hidden owner remains alive until the enclosing scope ends.

Candidate `crates/wyrd/wyrd-server/tests/integration/pg_hosted_artifacts.rs:2328` scopes both owner and pin, waits until the real nested query has stalled, and leaves the block before waiting for resources to release at `:2337`. `CodeAgent::call` directly awaits the executor (`pg_hosted_artifacts.rs:1769`); the executor directly awaits/races its model loop (`blocks/agent.rs:410`), and hosted `bifrost.query` directly awaits `BoundedQuery::run` while holding a cancellation-token drop guard (`crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:248`). Ending the owner's scope therefore performs the cancellation the test intends to stimulate. The bridge/query futures are not detached at these seams.

**Observation preserved:** this makes the cancellation trigger real. The test still waits for actual Oracle resources, checks both admitted records have no digest/zero bytes/cancellation errors, and checks the later read never dispatched (`pg_hosted_artifacts.rs:2337–2363`).
