## Governing range and whether refusal is permitted

Approved revision 2 `changes/active/verifier-code-mode/spec.md:114–121` requires preserving “integer values in the existing wire range” and refusing **out-of-range** integers. TASK-001:139 requires wire-range integers to survive exactly, and :405–412 expressly requires pure conversion proof in both directions. `architecture/wyrd-design.md:300–304` makes typed wire contracts authoritative for clients, :479–488 exposes Experiment `default_parameters: ParameterValue`, and :1883–1893 requires the existing tool contract with lossless JSON.

The existing range is not limited to `ParameterValue::Int(i64)`. `crates/wyrd-spec/src/card/common.rs:13–24` separately exposes `ParameterValue::Json(serde_json::Value)`. `ExperimentSpec::default_parameters` uses that enum (`card/experiment.rs:24–26`), and full Card reads return that same Card (`registry/reads.rs:17–24`). The locked serde_json is 1.0.150 (`Cargo.lock:7507–7508`); its installed `src/number.rs:28–35` stores `PosInt(u64)` and `NegInt(i64)`, and :132–160 distinguishes `as_i64` from `as_u64`. No arbitrary-precision feature is configured in the workspace. Consequently the lossless integer range of these JSON wire values is **i64::MIN through u64::MAX**, not merely i64::MIN through i64::MAX. This identifies the actual existing typed contract rather than inventing a new arbitrary-precision JSON promise. The `Int(i64)` variant does not restrict integer leaves inside the distinct `Json` variant.

A safe failure is correct for an integer below i64::MIN or above u64::MAX. It is insufficient for a valid in-range u64 value: preservation is an explicit acceptance obligation. The candidate's own test labeling u64::MAX as refused cannot override it.

## Exact defect and installed mechanism

- `sandbox.rs:722–724`: Python integers use `ObjectRef::as_int() -> Option<i64>` only. Installed `monty-types-1.1.0/src/object.rs:477–483` returns BigInt only when `to_i64()` succeeds.
- `sandbox.rs:799–803`: `to_python` accepts `number.as_i64()` and then explicitly excludes `number.is_u64()` from the float arm, rejecting all positive integers greater than i64::MAX. This avoids rounding but still violates preservation.
- `sandbox.rs:900–902`: existing conversion proof incorrectly requires refusal for `json!(u64::MAX)`; its supported case (:845–856) tests only signed endpoints.

Monty already supports this without a new dependency or transport: `monty-types-1.1.0/src/object.rs:100–104` provides `MontyObject::bigint`; `unstable::node(ObjectRef)` (`object/unstable.rs:61–66`) exposes the existing BigInt node when the signed accessor does not fit. Exact checked conversion to u64 uses the installed BigInt conversion implementation, with no decimal formatting or float conversion. Constructing the BigInt from a u64 can use the existing inferred `Into` accepted by `MontyObject::bigint`. `monty-proto-1.1.0/src/wire.rs:395,849` already encodes and decodes BigInt nodes across worker IPC. No parallel codec or new numeric contract is necessary.

## Narrow follow-up: does integer correction remove the record defect?

**No. A separate supported pre-delivery exit remains established by source.** This conclusion does not rely on deep JSON or on the mere existence of a fallible `to_python` return type.

I did not establish a supported depth-overflow result. In particular, the ordinary Card blob is parsed by serde_json's default recursion-limited parser (`hydrate_card`, service.rs:419); `cards.get` adds one response wrapper. It is insufficient to assert that a hypothetical 129-level Card can be returned. Bifrost query collection uses `JsonResultBuilder` and Arrow streams rather than reparsing a complete JSON document, but this focused pass did not establish a complete accepted SQL/schema producer exceeding BRIDGE_DEPTH. Do not retain depth overflow as a proven scenario from this report.

The established alternative is a **settled host call whose future is never resumed because the program fails before awaiting it**:

1. Python creates a pending bridge call, performs ordinary local computation or mounted-file work before awaiting its future, and fails during that work. The intended later await is never reached. A small authorized `fs.list` call is a concrete producer of a normal bounded result here; no integer edge case is needed. Creating a future and awaiting it later is Monty's documented async pattern (`monty-1.1.0/src/run_progress.rs:185–195`). The bridge itself always returns `ResumeValue::Future` (`sandbox.rs:340–360`), and Monty's VM stores that awaitable independently of whether it has yet been awaited (`bytecode/vm/async_exec.rs:825–855`). This is not a synchronous result API: the program has an awaitable, with no delivered result. Approved REQ-011 explicitly supports Python concurrency; REQ-012 expressly covers failing/returning with unresolved futures, and REQ-015/AC-012 cover retained records during later program failure.
2. While Python continues or processes a mounted-file event, `Sandbox::drive` polls the pending `Calls` concurrently (`sandbox.rs:435–447`). An ordinary ready `fs.list` can finish while the worker continuation is still pending. `Dispatch::call` (`vala-verify/src/blocks/tools.rs:485–568`, full body inspected) immediately encodes its ordinary bounded result, installs a digest/nonzero byte count, and calls `self.calls.finish(slot, record)` before returning it to `drive`. `drive` puts the resulting JSON in `answered` in the parent. At this point Python has received only the future, not the value.
3. `answer`/`resume_futures` are called exclusively in `TurnEvent::ResolveFutures` (`sandbox.rs:361–385`). If local work raises first, the worker continuation returns an error through `drive(...).await?`; if the program returns first, `TurnEvent::Complete` exits immediately (:252). Both leave `answered` to be dropped. There is no alternate resumption or record correction on either exit. `ToolCalls::settled` (`blocks/tools.rs:138–155`) marks only unfinished records as cancelled; this record was already marked finished, so it survives as successful with digest and returned bytes despite no Python delivery.

This is an allowed scheduling path through ordinary operations, not a guaranteed outcome of every such program. A normal fast child can settle during independent Python work; an exception or timeout before that work reaches its await prevents any value publication. The approved lifecycle/record contract explicitly covers this ordering. It is materially distinct from whether JSON can be converted, but shares the premature successful-settlement root cause of the proposed honest-record finding.

Consequently, adding u64 support closes the integer-preservation finding but does **not** alone establish REQ-015/016 record honesty. Retain the existing record finding with this supported path in addition to the candidate's demonstrated integer-conversion failure; no new finding ID or new product decision is necessary. The correction must keep successful child delivery pending until the driver publishes the bounded value to the Python future, and must settle admitted but unpublished calls as no-value failures/cancellations when the program exits. This does not require a new worker acknowledgement protocol, durable journal, raw result retention, or pretending that Python must inspect/consume a successfully resumed value. The existing resumption boundary is the relevant publication boundary.

Focused proof can stop a worker continuation after an ordinary child has settled into `answered`, terminate the program before `ResolveFutures`, and inspect the existing settled records: zero bytes/no digest and a safe failure for that unpublished child. Pair it with the existing successful-await case and the existing completed-and-delivered-before-later-failure case, which must keep its successful digest.
