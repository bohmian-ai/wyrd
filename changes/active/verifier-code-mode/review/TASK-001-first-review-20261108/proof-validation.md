## Capacity equivalence — REVISED

A missing named queued test alone is not a blocker. The existing proofs compose correctly **for a typed hosted Busy**: `capacity_refusal_is_busy_at_every_hosted_consumer` (`pg_hosted_artifacts.rs:1022–1186`) proves workspace/worker refusal, no subsequent model turn and recovery; `busy_queued_execution_is_deferred_until_capacity_frees` (`:1201–1311`) proves real queue release/no judgment/one counted attempt after recovery. Vala `AgentExecutor` (`blocks/agent.rs:411–423`) converts the shared Halt to BlockError, engine maps Busy without an authored retry (`blocks/engine.rs:687`), and runner maps it to Deferred then releases the claim (`verification/runner.rs:1049–1052`, `:694–708`). Queue execution has no distinct origin-specific branch. Repeating that same typed Busy in an Agent-authored queue fixture would not itself expose an unproved queue mechanism.

However, the claimed nested-capacity extension is not a refusal produced by a nested protected operation: its two parallel outer `code_run` requests compete for one worker. The catching Python program's nested `fs.read` does not produce Busy; a sibling outer program does. The accepted spec explicitly includes downstream hosted process capacity, caught exceptions and queued execution (REQ-009 at spec:153–160, AC-010 at :363; TASK-001 Scenario 4 at :263, :271–282). There is a concrete supported downstream path that does not join the proven Busy seam:

1. A legitimate declared `bifrost.query` awaits a pod whose bounded Oracle queue is already full. Production `Oracle::admit_sql_query` calls `admission.admit_for_attempt` (`vala-bifrost-redux/src/oracle/mod.rs:2540–2563`). That calls `admit_with_attempt_id` then `enqueue_waiter` (`oracle/admission.rs:807–845`). `enqueue_waiter` returns `BifrostError::QueryQueueFull` when `state.queued >= state.queue_capacity` (`:913–925`). This is expressly immediate retryable pod-capacity refusal, not a query's intrinsic memory ceiling (`wyrd-spec/src/vala/error.rs:82–94`). It is a realistic shared-server overload condition; no synthetic host load is needed to exercise it.
2. Query service returns that owner error (`wyrd-server/src/query/service.rs:210–233`); BoundedQuery propagates its opening error (`query/collect.rs:220–260`). Hosted `Invocation::call` maps it with `tool_error` (`verification/hosted/tools.rs:241–253`). That function creates `ToolError::StructuredInvocation`, retaining the catalog problem but no typed BlockError cause (`vala-verify/src/blocks/tools.rs:318–328`).
3. `Halt::observe` only recognizes `ToolError::Invocation { cause: Some(...) }` downcasting to `BlockError::Busy` (`blocks/tools.rs:409–420`). StructuredInvocation therefore does not stop the session. `Sandbox::answer` resumes Python with a catchable RuntimeError when the bridge is not halted (`hosted/sandbox.rs:489–512`). Python can catch queue-full and return a successful value; the model can then publish a final judgment. A queued execution receives no EngineError::Busy and cannot take the proved deferral path.

Disposition: the broad claim that existing hosted Busy plus queue composition proves **all required nested downstream-capacity behavior** is weaker than the actual requirement. Retain the typed-Busy composition as acceptance evidence, but revise this candidate from an absent-test complaint to the specific downstream capacity producer/consumer mismatch. This refinement was sent to the orchestrator for separate validation before inclusion as a final blocker; this report must not independently bless a different new finding discovered during validation.

Smallest credible correction/proof, subject to that independent validation: preserve the existing downstream owner's exact capacity error/record and translate actual retryable process-capacity refusal at the existing hosted adapter/session stop seam into the existing invocation Busy stop. Do not change Oracle policy, treat every 429/503 as Busy, reclassify intrinsic query ceilings, or duplicate queue scheduling. Deterministically fill/hold the actual bounded admission owner, run a nested query inside catch-all Python while another host operation is pending, assert Busy/no subsequent model turn and sibling settlement; queue the same bounded fault, assert no result/no consumed authored attempt, release capacity and observe success. This directly establishes the previously missing producer-to-stop seam and reuses the unchanged queue proof. No spec revision is needed for that behavior: it is explicit approved scope. Deleting a task-private test name does not resolve it.

## Combined direct/nested concurrency — REJECTED as an additional blocker

The literal mixed-origin runtime experiment is absent from the two inspected concurrency tests: `code_bridge_shares_the_recorded_path` uses Script's two nested reads at caps 1 and 2 (`vala-verify/tests/integration/blocks_agent.rs:1703–1735`, `:1797–1839`), while the hosted test drives nested gather. Do not describe these as an already-executed simultaneous direct+nested test.

The behavior nevertheless has non-weaker structural evidence. `ToolSession::resolve` constructs exactly one `Arc<Dispatch>` per resolved attempt, with one semaphore, and gives every direct RecordedTool that same Arc (`blocks/tools.rs:273–305`). Its code branch constructs ToolBridge by cloning `self`, the very same Dispatch (`:530–540`). Direct invoke calls `self.dispatch.call(..., Model)` (`:690–698`); bridge invoke calls `self.dispatch.call(..., Code)` (`:588–591`). `Dispatch::call` selects permit ownership solely by BuiltinTool::CodeRun versus all other tools (`:502–511`), before any recipient-based record construction. Recipient never selects a scheduler or semaphore. Mixed origin therefore cannot multiply capacity through a second owner; both contend on the identical semaphore by construction. The cap1/2 runtime test exercises that semaphore and no-permit outer code behavior, including peak active counts and absence of deadlock. This is not merely two similarly named helper implementations.

No source-proven supported failing mixed-origin path or distinct fault beyond this covered shared owner was found. Requiring another scenario solely to change one call's recipient would repeat the same mechanism rather than close a material unproved contract. Preserve the source-equivalence explanation and accurately label the runtime test limitation. No implementation or task/spec correction is needed on this question.
