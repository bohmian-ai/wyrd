## Proposed material findings

### SYS-001 — INCORRECT: Python host timeout becomes a repairable tool error and the Agent can publish a judgment

Violated obligations: REQ-009 host failures stay host failures; REQ-012 and AC-009 no further dispatch after timeout; TASK-001 Scenario 4 host stops cannot be caught to continue/manufacture judgment.

Location: `crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:328–334`, with timeout producer `hosted/sandbox.rs:391–394` and stop consumer `crates/vala/vala-verify/src/blocks/tools.rs:412–418`.

Reachable path: a Python program awaits `bifrost.query` longer than code timeout/cumulative reserved Python time while invocation/step deadline still has time left. Sandbox drops the query future and worker and returns Terminal("Python exceeded its time limit"). Invocation preserves a typed cause only for Busy; the timeout becomes cause-less ToolError::Invocation. Halt ignores it, so the Agent sees an ordinary tool error and may request more direct tools or return a judgment. Spent Python time merely makes subsequent code calls another ordinary error. A check may therefore receive model judgment after execution hit the required host bound.

This is not hypothetical: `pg_hosted_artifacts.rs:2379–2398` expects the model to answer after the time limit and confirms a subsequent code request; `sdks/wyrd-sdk-rust/tests/integration/verifier_building_blocks.rs:1953–1956` expects `StepStatus::Succeeded` for the stalled-query/time-limit phase. Query-resource cleanup is good, but does not make the resulting judgment valid under the approved stop contract. The public “pending cancellation” phase is implemented as a recoverable timeout instead of the required stopped execution observation.

Smallest testable correction: preserve timeout/cumulative Python-stop identity from the hosted owner to the existing session Halt/AgentExecutor stop boundary. Stop this Agent invocation only; keep ordinary tool/domain errors catchable, Busy deferrable, server/sibling availability and no-result cancellation guarantees unchanged. Do not add a runtime/service or crash the shared process. Adapt existing stalled-query proofs so a supplied next tool/final-answer response remains unread, no further call dispatches, the action fails/check becomes inconclusive (or existing outer cancellation path returns its established status), resources release, and a fresh invocation succeeds. No new harness is required.

### SYS-002 — INCORRECT / MISSING: interrupted extraction detaches blocking mutation and releases serialization before settlement

Violated obligations: REQ-012 explicit blocking-extraction cleanup, REQ-013 serialized scratch mutation, AC-009 and TASK-001 Scenario 4 required interruption proof.

Location: `crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:263–277`; late mutation sink `hosted/workspace.rs:720–760`; operation future-drop boundary `hosted/sandbox.rs:387–394`.

The writer guard is an async stack local at lines 267–270, outside the `spawn_blocking` closure. When a suspended program times out, returns with pending work, fails, or is cancelled after extraction starts, dropping its pending host future drops this guard and the JoinHandle. Already-started blocking work continues through extraction and `persist_noclobber`; it is neither joined nor cancelled. The async call's Dispatch permit also drops. The closure's Arc keeps the directory and workspace admission alive, but cleanup has already returned without waiting for it.

With a code-operation timeout/error and a continuing Agent, the next model turn can use the same Invocation/workspace while the old extractor mutates it without the writer lock. Even after SYS-001 stops timeout continuation, invocation cancellation/return still does not await extraction settlement, so retained workspace capacity and background mutation outlive cleanup. The safe no-overwrite primitive prevents replacing an existing destination, but does not serialize competing space checks or prevent late publication. This is the exact explicitly required interruption boundary, not additional extractor hardening.

Smallest testable correction: keep blocking-extraction writer ownership through its actual settlement and make existing hosted invocation cleanup account for started blocking operations before releasing the workspace/declaring cleanup complete. Stop accepting/delivering late results; preserve bounded extraction and the existing extractor/no-overwrite/budget owners. Merely moving the writer guard into the closure repairs serialization but alone does not prove the required cleanup settlement. Do not block an async runtime thread or create a second extraction service. Add the planned deterministic extraction barrier case: interrupt once extraction has started, observe cleanup remains pending/owns workspace until settlement, release it, assert no late result/ongoing writer, then recover capacity and run healthy work. Current healthy extraction tests and Arc lifetime reasoning are insufficient.

### SYS-003 — INCORRECT: workspace setup waits can exceed the Python operation deadline

Violated obligation: REQ-012 expressly includes workspace coordination and worker waits inside operation timeout and cumulative wall-clock Python budget.

Location: `crates/wyrd/wyrd-server/src/verification/hosted/tools.rs:304–316`.

Reservation computes the operation deadline before mounting, but neither `workspace.writer().await` nor the blocking mounts JoinHandle is raced against it. The deadline only reaches Sandbox after these waits. In a supported concurrent model turn, a direct `fs.extract` can hold the workspace writer while sibling `code.run` waits. If extraction exceeds the shorter code timeout/reserved budget, code remains pending until the writer and mount operation finish (or the longer outer step/execution timeout fires). It can then be classified as a worker-readiness Busy at an already-expired deadline rather than the elapsed Python operation's host stop. Accounting elapsed duration later does not enforce the time bound.

Smallest testable correction: enforce the already-computed deadline over code workspace coordination/setup as well as Sandbox execution, preserving SYS-002's started-blocking settlement rule and existing Busy classification for actual capacity refusal. Reuse the existing timeout/deadline owner; no new setting or generalized scheduler is warranted. A deterministic held-writer test with a shorter code timeout must show that code stops at its operation deadline, never dispatches Python/children or reaches the next model turn, settles owned setup work, and permits later healthy execution.
