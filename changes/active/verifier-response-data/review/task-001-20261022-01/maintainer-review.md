## Material finding

### MNT-001 — Arbitrary TypeScript parser failures can escape as TypeError

- **Classification:** INCORRECT; public error-contract consequence, blocking.
- **Changed location:** `sdks/wyrd-sdk-ts/wyrd/src/index.ts:282`–283, inside `typedResult`; supported parser boundary declared at lines 262–264.
- **Governing obligation:** Maintainer guide, “Any/unknown only at a genuinely open boundary; narrow it there.” TypeScript `AGENTS.md` requires wrappers to preserve error semantics. Approved REQ-012 requires *any mismatch* from the supported `parse` parser to return `WYRD_SDK_422_VERIFICATION_DATA_INVALID` through the normal Wyrd error type; field-path extraction is diagnostics, not a requirement on a parser's exception representation.
- **Source and reachability:** `VerdictDataParser<T>` constrains only `parse(value: unknown): T`, not what a rejection throws. `typedResult` catches that unknown exception but merely casts it to a Zod-like structure. Access to `.issues` occurs before the normal Wyrd error is built. `throw null` or `throw undefined` therefore throws a new `TypeError`; a thrown `{issues: [{path: "score"}]}` reaches `.map` on a string and also throws `TypeError`. These are legal exceptions from a conforming parser. The new helper is called by all three public typed operations: `Observe.verifyTyped` at line 2423, `Execution.waitTyped` at line 2346, and `Execution.statusTyped` at line 2330. Each runs its ordinary operation before the shared conversion, so this defect is entirely local to decoding and does not require or justify changing execution or storage.
- **Concrete maintenance/user cost:** Callers implementing a small custom decoder, rather than Zod, cannot reliably catch the documented Wyrd error and branch on its stable code. Adding another parser requires knowing an undocumented exception shape; a TypeScript cast hides this runtime dependency from the maintainer.
- **Independent narrow reproduction:** Ran `mise exec -- node --input-type=module` against the existing compiled SDK facade with `verify.Execution.fromNative` supplied an ordinary `valueJson` status result containing one requirement with data. Calling `statusTyped({parse() { throw thrown; }})` for the three values above returned `TypeError` in every case, never `WyrdError`. The compiled helper's `error.issues?.[0]`/path mapping was checked against the reviewed source. No server, credentials, network, or source edits were involved. The declared interface accepts these parsers; the existing Zod-only mismatch journey cannot disprove this path.
- **Smallest safe correction:** Correct the shared `typedResult` error-normalization boundary once. Always create the existing `WyrdError` for a parser rejection. Treat a Zod-shaped field path as optional diagnostics and read it only after narrowing its unknown structure; otherwise use the empty path, as the other SDK fallback does. Do not constrain parsers to Zod, introduce a dependency or new error type, or change ordinary execution, transport, result ownership, or persisted results.
- **Focused closure proof:** Extend the existing typed-result mismatch proof with a custom parser rejecting via `null`/`undefined` and a non-array optional path. Assert the exact Wyrd code and requirement ID with a safe empty fallback path; retain the existing Zod field-path assertion. One public typed read exercises the shared correction; source tracing establishes the other two callers use it. Keep ordinary readback and the no-rerun assertions in the existing test rather than creating another harness.
