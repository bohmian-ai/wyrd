## Proposed findings

### INV-001 — INCORRECT: schema composition changes the declared schema's root and dialect

- Obligation: REQ-001 unsupported schema combinations must be refused without weakening; REQ-002 supports object schemas with nested arrays/constraints; REQ-007 requires validation against the exact declared schema.
- Changed location: `crates/wyrd-spec/src/verification/execution.rs:598–620`, `Verdict::response_format`.
- Producer and reachability: Python/TS/YAML authors supply the standalone `data` schema. The resolver meta-validates it, removes `$schema`, hoists definitions, and embeds remaining contents in the canonical draft-07 Verdict. Root-relative references other than the hoisted definition paths are not relocated. Both compiled Agent schemas and code `response_schema` consume this same output; both executions pass it to `verdict_from`.
- Concrete evidence: public Python `Prompt.openai_chat('gpt-test', messages=['Judge'], response_format={'kind':'verdict','data':schema}).render().model_dump()` succeeds for a schema with `properties.score={type:number}` and `properties.copy={$ref:'#/properties/score'}`. Its rendered envelope still contains `#/properties/score`, but envelope `/properties/score` does not exist. Data `{score:1,copy:2}` is valid under the authored schema and cannot validate under the embedded one.
- A second manifestation: a supported draft-2020-12 data schema with `properties.scores={type:array,prefixItems:[{type:number}]}` is accepted and rendered under the canonical draft-07 `$schema`, with the data `$schema` removed. `{scores:['wrong']}` is rejected by the original schema and accepted by the rendered schema because draft 7 ignores `prefixItems`. The actual public render output and installed Python `jsonschema` dependency reproduced both facts; Rust source independently establishes the same dialect selection/composition used by server `jsonschema::validator_for`.
- Observable consequence: valid declared outputs become inconclusive, or invalid outputs become real failed/passed requirements with retained data. This is not merely invalid authoring error text.
- Smallest correction boundary: keep `Verdict::response_format` as the shared owner and preserve schema-resource root/reference and supported draft semantics during composition. Reuse the installed JSON Schema machinery/conventional resource semantics; do not add executor-specific guards, alternate validators or new schema options. Refuse an actually unsupported provider/schema combination before persistence instead of silently weakening it. Both ordinary and typed readers must continue receiving the same accepted data.
- Focused closure proof: add resolver/validation cases with a valid root-local property reference and a supported later-draft constraint; run the shared execution validator against both matching and mismatching outputs. At least one real code and Agent execution should pin the resulting acceptance/rejection. Verify no authored format/hash changes and keep existing definition-model cases green.
