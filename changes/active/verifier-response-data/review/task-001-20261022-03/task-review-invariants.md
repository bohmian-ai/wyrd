## Proposed finding

### INV-1 — The hosted-code undeclared-data case still is not exercised

- **Classification:** MISSING (verification); residual prior **FIND-TASK-001-5**, not a new production defect.
- **Violated obligation:** REQ-002/007, AC-004, and R1's explicit requirement to execute undeclared data through hosted code. The plain contract must refuse any envelope `data` even if the object is otherwise valid.
- **Exact locations:** `fixtures/cards/verifier_building_blocks/scored-review.yaml:95–104,131–132`; corresponding negative marker tables at Rust `verifier_building_blocks.rs:1530–1538`, Python `test_verifier_building_blocks.py:670–678`, TS `verifier-building-blocks.test.ts:729–737`.
- **Evidence and root cause:** Every negative marker executes `well-formed`, whose check always declares expanded `response_format` with required object data and closed data properties. `EXTRA-DATA` changes that object to `{score,category,extra:"s3cr3t"}`. It therefore tests an undeclared **property within declared data**, not an undeclared **envelope data member** for a plain check. The marker's description and Rust test doc claim the latter. All three SDK consumers use the same fixture and cannot expand its coverage by repetition. Plain fixture requirements `polite` and `on-topic` are Agent checks, not hosted code. The server route's code fixture and MCP code fixture likewise always declare expanded data.
- **Consequence:** The specific check-only default/plain-format regression boundary required by the accepted remediation remains unprotected in the real code-execution/result path. A change that accidentally defaults plain code checks to allowing `data` could pass all these claimed closure cases. Source presently appears to reject it correctly through `CodeCheck::response_schema` → `verdict_from`; this finding does not allege an actual retained invalid object.
- **Smallest correction:** Extend the existing checked-in building-block fixture with a plain/default code check whose selected negative case returns a valid object in envelope `data`. Reuse the existing three focused negative-story tables to assert that code requirement becomes inconclusive, has no retained data, and returns a safe reason while valid siblings survive. Keep the existing extra-property case because it covers a separate trust-boundary error. No new harness, validator, per-executor guard, option or production change is justified by this evidence.
- **Closure proof:** The existing focused `invalid_custom_verdict_data_is_inconclusive` selectors, against the repository-managed WyrdTestServer/Postgres setup, must observe the new plain-code refusal through ordinary SDK readback. The test fixture source must actually omit or use a plain `response_format` on that code check. Retain the already-added exact-boundary/readback cases.
