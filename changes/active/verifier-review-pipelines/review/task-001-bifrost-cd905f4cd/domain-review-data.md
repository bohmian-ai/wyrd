## Producer-to-consumer map

- Engine checkpoint calls and hosted publication acceptance mutate `RunState::Held`; `StateScribe::write` serializes a complete `ExecutionState`, obtains a reserved existing outbox slot, builds an execution-events checkpoint row and supplies `ScribeStateAdvance` for that execution/revision.
- Existing Scribe ingress/preprocessing preserves that advance. A state-fenced built-in requires a state claim; a general table refuses one. The existing shard WAL append/sync path produces a `ScribeBatchCommit` carrying the advance.
- `scribe_batch_commits::record` inserts batch fences and advances state heads in the caller's single `TenantConn` transaction. `ShardOwner::commit_batch_control_fences` commits only a fully acceptable offered group. Refused offers are removed and the remaining group is offered in a new transaction.
- `RunState::claim` commits writer installation, obtains the accepted head revision and loads exactly that revision through `InputResolver::state`. Public inspection uses the non-mutating `RunState::accepted` head read and the same exact-state loader.
- Recovery reconstructs engine checkpoint input from invocation settlements. Hosted evidence/publication readers use the recovered publication associations. Terminal replay builds delivery from the selected result identity and outcome, rather than selecting a result by time.
- The existing queue still owns claims, renewal, deadlines, retry/release, admission and accepted input custody. State heads contain no invocation, publication or terminal payload. Existing File upload/completion and result/outbox machinery remain the owners of their physical bytes/delivery.

## Challenged hypotheses

**Refunded attempts and generation reuse.** `runner.rs::state` uses `run.attempt` as claim generation, while queue `RELEASE_SQL` refunds that attempt. Thus the SQL API intentionally permits an equal-generation writer replacement. I traced the production path before treating this as a stale-claim defect: there is one state claim per `execute`; execute completion precedes release, and abandon drops the executing future before settling release. A dropped claim before its COMMIT cannot persist writer installation; an already submitted COMMIT still owns the state-head row lock, which the replacement claim must acquire. No supported path was established where an old equal-generation claim is newly committed after the replacement writer's claim. No finding retained and no new generation machinery prescribed.

**Generic payload/fence mismatch.** The low-level state advance is separate from the Arrow payload and ingress does not itself decode `ExecutionState`. The production producer in `StateScribe::write` supplies the same execution and revision to both representations, and the internal capture transport preserves them. I did not establish a supported producer that binds another execution/revision or accepts untrusted caller-authored checkpoint rows. A hypothetical forged trusted-peer frame is not sufficient for a persistent-data finding here.

**Migration refusal versus destructive conversion.** The migration deliberately does not reinterpret legacy progressed SQL custody as fresh Bifrost state. An installation with such rows is refused before mutation. This preserves custody, although it limits upgrade applicability; the supplied newer-Bifrost-format test is not a test of this legacy migration guard. No unapproved dual-store compatibility system or destructive row deletion is prescribed by this review.

**Listing cut versus status snapshot.** The public contract fixes insertion membership, not an invocation's forever-frozen status. Reading a later settlement for an already-inserted invocation therefore does not by itself violate pagination. The changed page owner retains insertion identity and excludes later insertions.
