## Actual topology and failure boundaries

* Direct execution lives in its request future: `VerificationService::run_direct` resolves/authenticates, reserves the process outbox, claims a fresh RunState, runs the shared engine and selects terminal state. It has no queue row or direct resumption scheduler. Dropping the future stops request execution; already staged immutable writes remain outbox-owned.
* Submitted, scheduled and group work retains the existing admission, queue, poller and lease owners. `VerifierRunner::attempt` registers renewal, races execution against lease loss/abandonment, delivers a selected result, then commits the queue transition. The original deadline comes from the first queue claim and is not extended by renewal (`runner.rs:993–1050`, `verifier_executions.rs::CLAIM_SQL`).
* `RunState` owns live memory plus one pending shared checkpoint. Memory mutation and snapshot bookkeeping have short locks; lease confirmation and acceptance waits occur outside them. One frozen pending operation can be driven by surviving waiters. A failed receipt breaks that RunState; it does not terminate the process or globally disable verification.
* Every execution shares the existing process Scribe outbox with audit, gateway capture and tenant spans. Execution-keyed lanes and bounded writer/chunk limits remain. A state frame gets its own acknowledgement through `ScribeSink::tally`; result acknowledgement remains after all result frames and group scheduling. Local Scribe or peer-plane routing uses the existing delivery path; peer requests have a finite timeout. Reserved outbox capacity and writer deadlines prevent checkpoint callers from treating enqueue as success.
* A durable checkpoint is local-volume WAL plus the batch/state-head transaction and authoritative active insertion. `scribe_state_heads` records accepted position and writer, not the execution payload. A head at revision zero authoritatively establishes no accepted checkpoint even if a Scribe is offline; a positive head requires that exact revision through `InputResolver::state`. Missing or incompatible exact state fails/defer; it never loads an older row or initializes fresh.
* On restart, state-fenced WAL commits without an accepted control fence are suppressed (`scribe/shards.rs:1879–1920`); accepted commits retain the established replay path. Takeover and advancement serialize on the head row. Permanent loss of an acknowledged local Scribe volume is outside the approved durability guarantee; the operations runbook requires retained-volume recovery or incident restore, not a fresh empty node.
* Verification capabilities are supervised separately (`verification/mod.rs:338–393`). Fitter, submission/schedule/group machinery and Operator worker remain distinct owners; the runner is composed only with hosted blocks and a configured Scribe route (`mod.rs:550–600`). A checkpoint refusal affects its writer/attempt, while unrelated capability tasks continue. The current scope supplies no reason to tie all runtime health or unrelated service readiness to one execution's Bifrost failure.

## Proposed material findings

### SYS-1 — Direct verification acknowledges success before its input/output/result delivery

Classification: **INCORRECT**. Obligation: REQ-055, DUR-004/DUR-007; supplement “How results are recorded” requires all necessary final-record acknowledgements before terminal success, with partial delivery recoverable.

Locations: `crates/wyrd/wyrd-server/src/components/verification/service.rs:673–693` and `:849–911` (`run_direct`, `stage_direct`); affected consumer `direct_execution` at `:302–369`; existing receipt owner `scribe_outbox.rs:1870–1889` and queued caller `runner.rs::deliver` at `:1087–1135`.

Reachable path: a direct request runs and durably accepts its terminal checkpoint. `stage_direct` then enqueues `ExecutionInputs` and `Result` with `acked: Mutex::new(None)`, and `run_direct` immediately returns `Ok`. Hold the result/output frames after accepting the state frame, or let Scribe become unavailable at that point: the user receives terminal success before those records are durable. Abrupt server death then loses the memory-only records. Direct has no queue or authorized background resume to repair that loss. Its public status reader joins the input and result/output records (`InputResolver::direct`, then `direct_execution`), so an acknowledged execution can remain unfindable. Separately, encoding failure in `stage_direct` is only logged and still returns success.

This is a required terminal durability boundary, not a demand for a new scheduler or stronger storage durability. Persisted selection is necessary but does not replace the contract's input/output/results records. Queued execution already has the relevant receipt-bearing result delivery pattern, so the two entry paths demonstrably differ at this boundary.

Smallest correction boundary: retain the existing builder, reservation and outbox; make direct final delivery return encoding/refusal/timeout errors and wait for the required final record acceptances before returning success. Reuse the existing Scribe result receipt and extend the existing input-delivery acknowledgement mechanism only as necessary to cover direct input custody. Do not reuse the queue lifecycle, add a finalizer, or block unrelated capabilities. A result receipt alone is insufficient if an independently rejected input record can still be omitted.

Focused proof: extend the existing direct/shared-state integration seam to accept terminal state while holding final output/result and input delivery separately. The direct future must remain pending; rejection/encoding failure/deadline must release no success. After acceptance, verify public readback of the same identity. Exercise partial final delivery and process loss through the existing fault machinery. No broad new harness is needed.

### SYS-2 — A queued checkpoint already staged before cancellation remains acceptable afterward

Classification: **INCORRECT / REGRESSION**. Obligation: REQ-057, DUR-009, supplement “Queue leases and stale-worker protection,” and Bifrost design's execution acceptance contract require cancellation/expiry protection at acceptance, explicitly even when no replacement has run.

Locations: `state.rs:231–235`, `:253–299`, `:631–695`; `runner.rs:481–490`; `crates/vala/vala-sql/src/queries/scribe_state_heads.rs:147–160`; cancellation writers `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:612–628`.

Reachable path: queued writer A passes `HeldLease::confirm`, freezes a revision and stages it on the outbox. Hold that frame before its acceptance, then commit `VerifierExecutionQueue::cancel` (or `cancel_principal` during revocation). The queue becomes cancelled, but neither cancellation writer changes the state head. The staged frame owns its immutable payload and survives cancellation/drop of its waiter. On release, `scribe_state_heads::advance` still sees A's unchanged writer, next revision and an original deadline in the future; it accepts the revision. No takeover is needed or eligible because the queue is terminal. The same separation leaves lease expiry untested at acceptance when a supported lease is shorter than the original deadline.

Observable consequence: progress/publication/terminal state can become accepted after the authority that permitted it was cancelled, and retained inspection can expose that late progress. A still-running waiter can also receive its durable receipt until cancellation detection. This does not assert that external calls can be recalled; the violated promise is precisely the authoritative acceptance boundary. The old SQL begin/settle/publication transitions checked current execution status and unexpired lease while holding the queue row, so moving only a preflight confirmation is weaker.

The current cancellation test (`pg_durable_verifier_work::cancelled_work_keeps_checkpoints_and_fences_stale_writes`) cancels first, then calls `begin`; confirmation correctly rejects that ordering. The takeover test rejects an old writer only after installing a new head. Neither covers an already staged current-writer frame after queue cancellation or expiry. A second caller-side confirmation immediately before staging would leave the same race and would not fix an outbox retry.

Smallest correction boundary: preserve PostgreSQL as the lease/cancellation authority and extend the existing declared queue-to-Bifrost acceptance/fence boundary so cancellation/expiry and state advancement have an authoritative order. Acceptance must reject the staged revision if invalidation won, while inheriting progress accepted first. Apply it to both cancellation writers and queue expiry/takeover consumers through their existing owners; retain generic Bifrost replay suppression and direct's queue-free path. Do not put private Wyrd queue queries in Vala, introduce another lease scheduler, or stop the whole shared runtime. This requires a real acceptance-boundary correction; deleting preflight confirmation or adding more downstream guards is insufficient. The exact owner integration should be independently checked against the repository's committed-handoff rule before prescribing mechanics.

Focused proof: hold a real checkpoint after confirmation and before fence acceptance, commit cancellation (and separately principal cancellation / lease expiry), release the frame without replacement, and assert that the head, recovered publications and terminal state do not advance. Restart on the retained Scribe volume and assert the rejected frame remains absent. Retain the converse ordering where checkpoint acceptance wins first. Extend the existing cancellation and retained-root lifecycle seams rather than adding an independent recovery harness.
