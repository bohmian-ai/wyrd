## Proposed findings

### BEH-1 — MISSING: canonical state lacks immutable read identities; recorded results disappear after source Card deletion

**Obligation.** REQ-052/056 and scenario 6 explicitly require recorded identities/readback independent of source Card deletion. `architecture/wyrd-design.md:1924` requires dedicated reads without source Card retrieval or leftover queue rows.

**Locations.** `crates/wyrd-spec/src/verification/state.rs:30–43`, new state producer in `crates/wyrd/wyrd-server/src/verification/state.rs:74–91,245–274`; consumers `components/verification/service.rs:260–278,325–334` and `service/inspection.rs:259–273`.

**Reachable failure.** Complete an ordinary direct verify or queued submission and retain its accepted terminal state/results. Delete its subject or Verifier through the supported Cards API. A subsequent authorized execution GET still calls `Self::card`; the shared registry `queries/cards/get.rs:17` excludes deleted Cards. Queued GET returns completed status with no result; direct GET returns `None`, becoming execution-not-found, despite accepted Bifrost state and retained result. Invocation/publication operations additionally refuse before consulting that state if the queue row is absent. These are required task scenarios, not a request to broaden retention.

**Producer-to-consumer cause.** The new state does not retain exact Verifier/subject `CardRef` identities or accepted execution context needed to reconstruct the public result independently. Checkpoint row dimensions hold UIDs, not the full required identity. The primary GET path was not adapted to the new state owner and still uses SQL-selected result/registry reconstruction; only invocation/publication readers were partially migrated. Direct and queued result readers are sibling consumers of the same missing immutable identity authority. Recovery also rebuilds target/context from queue/live Cards before reading state; this omission is broader than changing one not-found branch.

**Consequence/materiality.** A normal lifecycle action removes access to already recorded verification evidence; direct reads falsely report deletion. This directly violates an explicit acceptance criterion and core retained-evidence behavior.

**Smallest correction.** Retain the required immutable execution identities/context through the existing canonical execution-state/input owner and make execution/inspection readers reconstruct from that recorded authority, retaining current Verifier authorization and audit. Keep ordinary Card read/deletion semantics unchanged; reading deleted registry tombstones or fabricating references is not the approved fix. Preserve queue coordination and independent delivery; no new archive/tombstone/cleanup service. The context/identity producer and its two reader consumers need one cohesive correction; a fallback only in direct GET leaves queued/inspection behavior incomplete.

**Focused proof.** Extend the existing real-server execution read test to complete direct and queued runs, delete each source Card, and assert identical recorded result identity/references/outcome with current read grants and cross-tenant refusal. Assert inspection still reads recorded accepted state independently of obsolete payload parents. This is source-proven; no new executable reproduction was run here.

### BEH-2 — MISSING: terminal errors and control outcomes never enter canonical recoverable state

**Obligation.** REQ-054 requires canonical state with selected result/full sanitized error for every outcome; supplement state table includes execution status/cancellation/termination. Scenario 6 requires all outcomes/full errors without legacy SQL payload dependency; architecture requires complete sanitized errors in canonical verification data.

**Locations.** `crates/wyrd-spec/src/verification/state.rs:82–90`; `verification/runner.rs:436–446,795–804`; `components/verification/service/inspection.rs::cancel`.

**Reachable failure.** A supported queued run whose evidence is invalid, whose required capability is unavailable, or whose original deadline expires returns `EngineOutcome::Terminal`. At line 446 the runner creates `Transition::Terminate` without writing the terminal decision/error to `RunState`; `settle` writes the error only through `queue.terminate`. Cancellation similarly updates only the queue. New state can remain a running checkpoint, or have no accepted revision for a pre-engine failure, although the public execution has terminated. `TerminalSelection` cannot represent these outcomes at all. `execution_status` supplies the full error from `wyrd.verifier_executions.error`, so Bifrost cannot reproduce it as required.

**Cause and affected writers.** The new checkpoint contract models only a completed `VerificationOutcome` and its result ID. Ordinary engine termination, retry exhaustion, pre-engine refusal and user cancellation remain sibling terminal writers outside that contract. Merely changing a GET fallback cannot recover information no canonical producer writes.

**Consequence/materiality.** Canonical retained execution data is incomplete for ordinary negative flows; recovery/inspection cannot reproduce the committed terminal state/full typed error independently of the coordination row. This is an explicit missing behavior, rather than speculation that all SQL must disappear: queue coordination may remain, but it cannot be the only retained terminal payload owner.

**Smallest correction.** Extend the existing canonical state/terminal selection ownership to retain the existing sanitized terminal status/error variants and route the actual terminal producers through it while preserving PostgreSQL's lease/cancellation coordination and existing public errors. Do not create another finalization service or copy independent Operator state. Handle expiry/cancellation at their existing owner boundaries rather than granting a stale writer another successful checkpoint. Any required acceptance ordering not already authorized must be surfaced, not invented as a cross-tier transaction.

**Focused proof.** Exercise queued invalid evidence and timed-out work plus repeated cancellation; verify exact sanitized status/error retained by canonical accepted state and reconstructed by execution reads, and preserve unchanged result meanings for completed failed/inconclusive verdicts. The current terminal-inspection test covers a failed *verdict*, which is not an execution error.

### BEH-3 — VIOLATION: full checkpoint JSON preparation bypasses bounded writer preparation

**Obligation.** Revision 1 selected correction 6 requires frozen checkpoint JSON/Arrow preparation through the existing bounded writer preparation path. `agent_docs/rust.md` prohibits blocking async request work without an explicit blocking strategy.

**Location.** `verification/state.rs:245–274` (`StateScribe::write`); compare existing `scribe_outbox.rs:1670` preparation via `spawn_blocking` within bounded frame work.

**Reachable failure.** Every checkpoint waiter that first drives its shared future synchronously serializes the entire growing `ExecutionState` with `serde_json::to_value`, builds/encodes the checkpoint Variant, and only afterward requests outbox capacity. Ordinary multi-step runs retain full settled outputs and publications, so this CPU/allocation work runs repeatedly on the request/runner Tokio worker, outside the existing bounded writer preparation path. Moving the mutex does not move this work off that worker or bound preparation across executions.

**Materiality.** This is an explicitly selected concurrency/resource obligation, not a claim that a particular benchmark already regresses. The candidate's evidence itself discloses the JSON limitation; source confirms it. Large retained state is supported, so the unbounded inline preparation defeats part of the requested independent-run protection.

**Smallest correction.** Reuse the bounded existing writer preparation owner for frozen JSON/Variant as well as Arrow preparation, encoding once per frozen checkpoint while preserving ticket coverage, immutable retry identity, byte accounting, reserved capacity, per-frame receipts and caller cancellation. Do not add a per-run worker/task/service or another unbounded preparation queue. A detached `spawn_blocking` per mutation alone would not satisfy the existing bounded-owner requirement.

**Focused proof.** Extend the existing bounded outbox/checkpoint tests to observe frozen preparation admission and cancellation with concurrent runs, and record encoded snapshot bytes/counts as required by Revision 1. Do not generate host load or add a benchmark framework.
