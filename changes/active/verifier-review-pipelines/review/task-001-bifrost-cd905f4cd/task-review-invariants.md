## INV-1 — Direct success escapes before required final delivery

**Classification:** INCORRECT. **Obligation:** TASK-001 scenario 6 and Revision 1 item 5; REQ-055; DUR-004 and DUR-007; supplement's final flow requires acknowledgements before returning the selected result.

**Locations:** `crates/wyrd/wyrd-server/src/components/verification/service.rs:674` (`run_direct` selection, staging and immediate completed response), `:850` (`stage_direct`), especially `:894` (`ScribeWrite::Result` with `acked: None`).

**Producer → consumer proof:** `RunState::select` correctly waits for the terminal state checkpoint. `run_direct` then calls synchronous `stage_direct`, which stages input and result writes and cannot report delivery or encoding failure. The result acknowledgement field is `None`; immediately afterward the caller receives `Ok(VerificationResult)`. Holding or rejecting `execution_outputs` after the checkpoint therefore leaves direct success observable before the summary/detail are durable. Encoding failure is also logged and discarded while the same success response is returned. The durable terminal selection does not satisfy this barrier: existing result tables must retain their meanings, and `direct_execution` reads those tables rather than returning the selection payload.

**Reachable scenario / consequence:** a normal direct assertion verification completes while Scribe accepts its checkpoint but stalls/refuses the result frame. The caller sees success; a status read lacks the required result/input records. A process loss may leave no complete canonical result delivery, with no direct-resume API to finish it. This is an explicit durability boundary, not speculative outage hardening.

**Sibling owners checked:** queued `runner::deliver` already attaches a oneshot receipt and awaits it; `ScribeSink::write` acknowledges `Result` only after required slice processing. `stage_direct` is the direct staging caller. Both direct final writes share existing execution lanes.

**Smallest correction:** use the existing reserved outbox/result receipt lifecycle for direct final delivery and propagate encoding/refusal/deadline failure before returning success. Retain queue-free request ownership and drop cancellation; add no background direct continuation, finalizer or alternate store. Include the input-record acknowledgement in the same required completion boundary through the existing outbox contract rather than assuming enqueue equals WAL acceptance. The correction is local delivery plumbing using owners already present, not a second service.

**Focused proof:** hold final output/result acceptance after terminal checkpoint acceptance; the direct future must remain pending. Release and observe the same selected result; refuse/expire and observe no successful response. Exercise the input record boundary as well. Existing selected-state-after-flush proof cannot establish this ordering.

## INV-2 — Incomplete canonical terminal/identity state leaves inspection dependent on live Cards and SQL payloads

**Classification:** MISSING. **Obligation:** REQ-054/056, AC-048 and TASK-001 scenario 6; `architecture/bifrost-design.md` execution-events ownership and `architecture/wyrd-design.md` dedicated reads explicitly require full sanitized errors and recorded immutable identities without source Card retrieval.

**Locations:** `crates/wyrd-spec/src/verification/state.rs:31` (`ExecutionState`), `:83` (`TerminalSelection`); `crates/wyrd/wyrd-server/src/components/verification/service.rs:266` and `:325`; `crates/wyrd/wyrd-server/src/verification/runner.rs:444` / `:799` (non-completed transitions bypass state terminal retention).

**Producer → consumer proof:** the new complete state records format, sequence, invocations, publications and an optional terminal successful/failed verification verdict. It has no full terminal execution error/status or exact Verifier/subject Card references. `StateRow` contributes UIDs to checkpoint rows, but not the retained exact references required to build a `VerificationResult` after deletion. Timeout/error/cancel transitions remain SQL state/error mutations; they do not create a matching terminal record in this model. Deleting the SQL event projector removes the earlier projection path as well.

The main public reader is not switched to canonical accepted terminal metadata: `get_execution` reads SQL status and calls `Self::card` for Verifier and subject. If either is absent it returns the status without the result. `direct_execution` performs the same live Card reads and returns `None` when either is absent, which becomes execution-not-found. `Self::card` explicitly translates Card-not-found to `None`. Invocation/publication page conversion cannot repair this main status consumer.

**Reachable scenario / consequence:** complete a supported direct or submitted execution, then delete its subject or Verifier Card under the established retention lifetime. A direct result becomes not-found, or a queued completed result loses its result body even though its accepted terminal selection and result records remain. Separately, an errored/timed-out/cancelled execution has no complete terminal status/error in its purported canonical recovery source, so its inspection remains dependent on SQL payload custody. Both manifestations arise from the same omitted canonical metadata producer; adding only a read-side fallback would not preserve the missing facts.

**Smallest correction:** extend the existing versioned execution metadata owner to retain the explicitly required immutable execution identities and terminal execution statuses/full sanitized errors, then route existing status/result projections through that accepted metadata and the existing input/result reader. Preserve current permission/audit checks against recorded UIDs, feature scopes, queue coordination and result-table semantics. Remove reliance on live Card retrieval for historical identity. No tombstone, archive handoff, payload mirror or replacement reader service is warranted. This is required contract completion; optional identity enrichment is excluded.

**Focused proof:** through the existing execution read API, read completed direct and queued results, delete source Cards, and require the same exact references/body under current read grants. Also inspect error/timeout/cancel records from canonical state with full sanitized errors and typed unavailability when required state is inaccessible. The inspected terminal test currently asserts invocation/publication names and selected-ID reuse only.

## INV-3 — Queue exhaustion can discard a durably selected terminal result

**Classification:** INCORRECT. **Obligation:** DUR-007; REQ-058; TASK-001 scenario 6; supplement recovery rule: persisted terminal result with lost caller/queue completion returns the recorded outcome and finishes bookkeeping without executing steps again.

**Locations:** `crates/wyrd/wyrd-server/src/verification/runner.rs:416`, `:438`, `:1114`; `crates/wyrd/wyrd-sql/src/queries/verifier_executions.rs:412` (`CLAIM_SQL` exhausted branch), `:3050` (`retry` exhaustion).

**Producer → consumer proof:** a completed engine first durably selects one terminal result; result delivery then acknowledges its rows before queue completion. The existing recovery branch in `execute` can reuse that selection only if a new execution claim reaches it. If the completing attempt is the queue's last allowed attempt and its queue completion commit is lost/rolls back, `CLAIM_SQL` marks the expired running execution `errored` whenever `attempts >= max_attempts`. It never loads accepted state. No later claim reaches the recorded-selection branch. This holds even when the result detail and summary were already durably acknowledged before the failed completion transaction.

A sibling path has the same ownership mismatch: after selection, final-result refusal maps to ordinary `Retry`, whose SQL `retry` terminalizes at the attempt ceiling; result acknowledgement timeout maps directly to SQL `TimedOut`. None reconciles the existing selected terminal with the public terminal it commits. The old exhaustion policy governs unfinished computation, but is being applied to bookkeeping for an already selected result.

**Reachable scenario / consequence:** repeat the existing failed-settlement recovery fault on the final allowed attempt rather than the first. The saved result/outcome survives in Bifrost, but polling ends `errored` with no selected public result and no required delivery completion. The implementation's ordinary attempt-1→2 recovery test does not cover this boundary. For timeout, the current `completion_waits_for_the_durable_result` test explicitly expects `timed_out` after selection; green evidence therefore does not establish the new selected-terminal contract.

**Smallest correction:** make the existing queue/runner final-delivery lifecycle distinguish selected-terminal recovery from unfinished engine-attempt exhaustion. Resolve accepted terminal selection before permanently exhausting such work; finish existing selected-result delivery/completion without another provider execution or replenishing provider attempts/deadline. Preserve cancellation and current-writer fencing and do not manufacture a new verdict or silently turn a selected result into a different execution terminal. Reuse the existing accepted loader and result delivery owner; a second finalizer/store or indefinitely increased attempt budget would be the wrong boundary. Independent validation should reconcile timeout handling with the approved original-deadline rule; the final-attempt fully-durable-result/failed-completion case alone establishes the defect without extending execution time.

**Focused proof:** adapt the existing failed-settlement test so selection and result frames become durable on the last allowed attempt, then fail queue completion and expire/reclaim. Require the original result identity/outcome, no engine/provider entry, and successful completion bookkeeping. Add the focused final-delivery-refusal boundary to ensure it cannot become an ordinary engine-budget exhaustion. Do not repeat broad journey suites for this bounded correction.
