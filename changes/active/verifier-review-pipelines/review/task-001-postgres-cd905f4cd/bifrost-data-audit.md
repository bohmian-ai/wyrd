## Existing machinery to reuse, and its actual limits

The smallest correction is deletion of SQL execution-head authority and extension at the existing Bifrost read/record boundary, using the current writer/outbox/WAL/replay path. It is not relocation of `claim`/`head`/`advance` to a background task. Preserve complete versioned `execution_events.value`, accepted publication descriptors and final selection; continue to use live memory for dependencies. Leave generic catalog, membership, batch-fence and publication operations above in their current roles. Add no replacement SQL execution table or columns that reconstruct the same head under another name.

The source does **not** justify a mechanical substitution of `MAX(sequence)` over visible rows for `RunState::accepted`:

- `InputResolver::state` (`inputs.rs:265–282`) currently requests exactly the SQL-provided revision. A missing exact row becomes `StateError::Unavailable` in `state.rs:450–465`; no head in `accepted` currently becomes `None`, while revision zero creates fresh state. Removing the SQL call removes this distinction unless the Bifrost owner supplies it.
- Generic `scribe_batch_commits` has table/batch identity and WAL coordinates, **no execution UUID or execution revision**. `StateScribe::write` currently chooses a fresh random UUIDv7 checkpoint batch (`state.rs:284`). Therefore an existing batch lookup cannot directly answer an execution's last accepted revision merely by reusing its current query.
- Existing published-source metadata identifies physical artifact coverage and publication revisions; it says nothing by itself about all unpublished checkpoints. Existing live membership excludes expired/unready owners. `bifrost-design.md:649–660` explicitly permits omission of a Scribe unavailable before discovery; `cluster_nodes.rs:219–220` implements the live filter. A successful empty or older ordinary query is consequently insufficient proof of execution absence/latest state. This limitation exists at the base; the new head is how this candidate avoids relying on ordinary discovery for the accepted revision.
- Existing replay already binds exact canonical attempts to batch fences and suppresses published duplicates. It does not persist execution claim tokens or next-revision state in WAL; the candidate adds only `state: None` to reconstructed replay fences. Its new state-specific suppression relies on SQL atomic advance. Do not infer a replacement execution lease protocol from this generic replay owner.

Decision-complete correction boundary: the existing Bifrost recovery reader must return complete compatible accepted state, authoritative absence, or explicit retryable unavailability based on the **existing durable batch/source metadata plus canonical records**. Never fall back to empty/older visible state because required owner data is missing. Reuse the same WAL identity/reconciliation and exact publication coverage; introduce no second registry, sidecar, service, queue or lease system. Any internal extension must be justified against those existing owners. Fresh direct execution IDs can initialize fresh without a SQL claim, because concurrent direct resumption is expressly excluded. Queued retry and retained inspection still need authoritative recovery.

The concrete coverage boundary is the tenant's logical verification table and its already-durable batches/source streams, not a new SQL index from execution UUID to checkpoint. Existing `scribe_batch_commits` table/batch/WAL identities identify acknowledged durable work; `file_list` exact stream/range/artifact coverage identifies published work; `BifrostCatalog::read_cut` / `OracleTableCuts::read` select the published Iceberg/hot cut and node publication revisions; existing `RegistryTailStreamDiscovery` and Scribe live/staged capture read surviving unpublished sources; `ShardOwner::resolve_replayed_commit` and `resolve_published_replay_batches` reconcile the same facts after restart. Extend these existing Bifrost owners so a required durable source not covered by publication and not reachable for the recovery read produces unavailability. Canonical checkpoint records then supply execution identity and revision. SQL continues to describe batches and physical sources; it must not regain the execution-specific accepted-position role. This deliberately names the established reuse boundary without prescribing a new service or an execution index.

That complete-recovery coverage is **missing implementation of an already approved owner extension**, not by itself a new material decision or a reason to seek approval again. The inspected candidate does not already contain a general SQL-head-free reader that can simply be called. Implementing the coverage/read extension using existing metadata is within scope even when it needs an additional existing-owner query or method. A genuinely new decision would be stronger durability after permanent unpublished-disk loss, a new persistent authority/store, a public freshness/resume surface, or stronger exclusion of the accepted rare worker gap; none is needed or proposed by this report. If source evidence establishes a specific retained guarantee is impossible within those boundaries, report that contradiction rather than treating implementation difficulty as proof or inventing machinery. Do not claim ordinary query success suffices, and do not silently waive unrelated missing-owner/exact-state behavior.
