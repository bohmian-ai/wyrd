## USER-PG-001 — directed removal, not discovered finding

The new migration `vala-sql/migrations/20261107000000_scribe_state_heads.sql` establishes per-tenant/table/execution ownership, generation, revision and accepting batch. `claim`, `head`, `advance` in `vala-sql/src/queries/scribe_state_heads.rs` are the sole SQL operation family. `batch_id` is returned but not used by RunState to locate the record: current readers use the SQL `revision` to choose Bifrost state. Absence/revision zero in SQL is therefore authoritative fresh state, not harmless metadata.

Remove this authority entirely. The existing owners to extend/reuse are engine RunState for live logical state, canonical execution_events for persisted checkpoints, ScribeOutbox for bounded pending snapshot/retry identity, ShardOwner/WAL/batch commits for durable write/retry, and existing Bifrost query/source owners for exact recovery reads. No new table, worker, queue, lease, registry or authority-handoff protocol is justified by this instruction. Preserve the human-accepted delayed-old-worker timing gap rather than using that gap as a reason to rebuild the rejected head under another name.

Removal reach, including consumers that otherwise keep the design alive:

1. `verification/state.rs` imports, StateWriter SQL generation/ownership uses, fresh/claim/accepted and ScribeStateAdvance construction; direct service, queued runner and inspection callers must get recovery position/absence through Bifrost instead.
2. `vala-sql::queries` export and head migration/query module; state field and advance/refusal branches in scribe_batch_commits. Preserve generic batch identity columns and normal replay resolution.
3. Redux contracts re-exports, ingress frame state field, prepared/admitted append propagation, state-fenced table flag/default/inventory, ExecutionEventsTable flag, ingress required-state validation, shard refused_states/control-fence branches, and replay suppression assumption. Keep state payload writing and normal shared-writer acknowledgements.
4. Capture peer and remote outbox encoding/decoding, IngestCaptureState proto/message, routing of state metadata, error catalog/mapping (`StateRefused`) where only the rejected protocol needs them. Do not leave a wire-only shadow ownership protocol.
5. SQL state-head tests, lifecycle tests that mutate the head, integration mocks constructing state offers and fixtures initializing every new frame field; replace guarantees with proof of the approved Bifrost lifecycle rather than asserting SQL heads.
6. Wyrd migration commentary and test/docs assertions that say state is fenced by `vala.scribe_state_heads`; reconcile immutable migration handling with SQL AGENTS (do not rewrite a migration already applied).

Focused proof: direct execution and queued retry still produce/recover canonical state while no state-head table/query exists; accepted checkpoint exactness, authoritative absence/unavailable sources, publication custody, input admission ordering and ordinary queue cancellation/deadline/renewal remain covered. Test normal WAL crash-before-fence recovery and acknowledged write recovery with the retained generic machinery. Do not demand the withdrawn global takeover ordering or direct result ACK.

## ES-01 — execution terminal/error and result selection still use queue SQL

Classification: **MISSING / VIOLATION**, proposed for independent validation.

Obligation: spec Execution ownership says PostgreSQL “does not hold a competing recovery copy of ... final-result selection”; supplement state table requires “Execution status, cancellation/termination decision, selected result identity and final outcome”; TASK-001 section 6 requires “all outcomes/full errors ... without legacy PostgreSQL payload rows.”

Producer-to-consumer proof:

- `ExecutionState` (`wyrd-spec/src/verification/state.rs:31–103`) contains only format, sequence, invocations, publications and `terminal: Option<TerminalSelection>`. TerminalSelection only represents successful engine completion with result_id/times/outcome. There is no full execution error/cancel/refusal representation.
- Runner::execute returns `Transition::Terminate` before state initialization for unavailable targets (runner:397), or after engine terminal failure (runner:446). It does not checkpoint that terminal outcome. Runner::settle writes it to queue TERMINATE (runner:800–804). Queue CLAIM final-attempt exhaustion, admission/group refusal, cancel and principal cancellation likewise write SQL error only.
- `execution_status` (queue:3209–3262) exposes SQL `error` directly. `get_execution` (service:243–290) uses SQL status/result_id rather than the recovered selected terminal state. It never calls RunState::accepted for this public read.
- Candidate migration drops old event triggers/tables, but keeps error/result_id/status and the stored batch completion function. Thus there is no remaining canonical Bifrost execution event for those terminal errors. This is an affected pre-existing dependency the migration was required to replace.

Concrete supported consequence: a queued engine planning/target error or a cancelled execution has its complete error only in its queue row; the accepted Bifrost state cannot reproduce that terminal execution. A reader with retained Bifrost data but no leftover queue row cannot inspect the recorded error; public result selection is likewise controlled by the queue pointer rather than canonical selected identity. This breaks the expressly required historical-read and single-authority boundary, independently of the accepted rare late-worker gap. SQL retry timestamps/status do not make a full error message a scheduling value.

Smallest correction boundary: extend the existing logical/canonical execution record and common reader to retain and read terminal execution identity/decision/full sanitized error and exact selected result. Cover pre-engine refusals, exhaustion and cancellation as well as normal runner outcomes through existing lifecycle/writer owners; do not introduce a second service or require an engine checkpoint before queue admission. Keep SQL queue fencing/status/retry bookkeeping and any narrow completion pointer needed for idempotent delivery/group comparison; those fields must not be a competing historical read/recovery authority. Audit both single COMPLETE and `complete_verifier_executions` consumers, not only the Rust statement. Preserve independent Operator frozen failure_context and group comparison metadata.

Closure proof: record one non-completed terminal engine error and one queue-origin terminal/cancel decision, then read their exact sanitized errors from canonical retained execution data without queue payload dependence. Recover terminal selection after result delivery before queue completion and read exactly that result. Verify repeated terminal cancel and original queue settlement/retry behavior remain intact. A test that asserts queue.error alone cannot close this finding.

## ES-02 — historical inspection still requires queue membership and live Card identity

Classification: **MISSING / VIOLATION**, proposed for independent validation.

Obligation: wyrd-design lines 1925–1932 explicitly requires recorded immutable identities “without requiring source Card retrieval or leftover queue rows”; TASK-001 section 6 specifically requires source Card deletion proof.

Producer-to-consumer proof:

- StateRow/checkpoint metadata records UID strings, but neither ExecutionState nor TerminalSelection retains the exact Verifier/subject refs needed to build the public result independently of Cards. `ResultPayloadBuilder` records UIDs/version rather than the complete immutable identity projection used by dedicated reads.
- `get_execution` reads STATUS first; queued responses retrieve `card` by both UIDs (service:264–265), then return status without a result if either Card is absent. Its direct fallback also calls both `card` operations and returns None if either is absent (service:324–333). `card` delegates to `wyrd_sql::queries::cards::get_card_by_uid` (service:1145), which queries current `wyrd.cards`, not recorded execution identity.
- `inspection::authorized` (inspection.rs:282–306) requires a queue row before authorizing the exact Verifier and reading state. All invocation/publication/content/download paths use this prerequisite. Direct verification is queue-free, so accepted direct publications cannot be inspected with those paths even though they persist through the same state/publication adapter.
- Without a queue row, `get_execution` only falls back to `InputResolver::direct` (inputs.rs:476), whose query filters input.origin='direct'. Retained queued executions cannot use that path. Their Bifrost state and exact accepted publications remain unreachable through the dedicated APIs.

Concrete consequence: after deletion of a source Card, a retained direct completed execution becomes not-found and a queued completed result becomes absent; after queue-row removal queued invocation/publication reads fail before consulting retained canonical state. Accepted direct publication content is also inaccessible through the queue-only authorization gate. The issue is material historical evidence loss at an explicitly required inspection boundary, not an argument to eliminate ordinary registry/auth SQL.

Smallest correction boundary: persist the necessary immutable execution identity/feature authorization context in existing canonical execution data at the point it is known, and reuse one accepted-state/exact-reference reader for status, invocation pages, publication and content reads. Authorize the current caller against that recorded identity. Keep current principal/SYSTEM security lookup and queue cancellation mutation with their existing owners; separate the necessary queue mutation from read-side existence/identity authority. No alias routes, backend selector, archive service or new retention store.

Closure proof: complete direct and queued executions with a publication, remove source Cards in the supported test setup, and show exact result/refs, pages and content still read with correct current grants. Exercise a retained queued execution without its payload/queue parent, denied grants/cross-tenant IDs and unavailable Bifrost sources (retryable failure, not not-found). Keep stable page cut and exact producer/File descriptor selection. This is focused closure of an explicit task obligation, not a new retention policy.
