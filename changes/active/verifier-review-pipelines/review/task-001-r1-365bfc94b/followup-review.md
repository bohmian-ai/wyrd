A normal queued execution can complete while Scribe is slow: its SQL commit finishes while Result remains in process memory. Abruptly stop that process before durable Scribe acceptance (including before either detail or summary lands). Restart using the surviving database and storage. The execution remains completed with the selected ID; claim recovery ignores it; event projection supplies history only; result reads remain empty. Even if some rows landed, the required three-way assembly can remain permanently incomplete. This is source-proven absence of a recovery owner for this interval, not an inference that query lag itself loses results.

The two completion paths and the reader share one missing producer-side durable handoff. The issue does not require changing every inspection consumer, broad server shutdown, or a second recovery executor. Direct synchronous verification is outside this queued-completion obligation.

## Proposed finding and bounded correction

**FUP-001 — MISSING, corroborates SYS-001: queued completed state can outlive its only final-result payload.** Violated obligations: REQ-013, AC-007/008, Task 001 durable completion/scenario 2 and its authorized architecture amendment. Exact boundary: `completions.rs:198–242` and `runner.rs:670–760` commit completed after volatile stage, with no result durability acknowledgement or durable replay custody. Material consequence: a routinely supported process restart during Scribe delay can permanently lose the selected verification result, leaving completed executions unresolvable through SDK/API readback.

Required testable correction belongs at the existing runner/completion/Scribe handoff: completed may commit only once the exact selected result is durably accepted by Scribe, or existing approved committed recovery custody demonstrably guarantees its delivery. Reuse actual Scribe ACK; the existing event/object ACK notification patterns demonstrate that acknowledgement can be reported through the current outbox rather than adding ingestion machinery. Retain batch SQL settlement, current lease/cancel fencing, exact selected result identity, tenant authority, no transactions spanning external IO, current detail-before-summary semantics, non-blocking audits and unrelated capability availability. A rejected/dropped result must never be mistaken for durable acceptance. Update the owning completion paragraph to the approved contract in the same remediation.

The smallest correction need not make completed rows claimable again, reconstruct results at read time, add SQL analytical payloads, or wait for Iceberg visibility. Such proposals add burden without fixing the earliest invalid completed state. Detailed private ordering and notification choices remain implementer decisions, but proof must establish durability before terminal acknowledgement, correctness on lost ACK/commit/restart, and no repeated committed action/requirement work. There is no unresolved product or storage-policy choice needed to require that ordering.

## Proof assessment

That is useful checkpoint/readback evidence but cannot cover a crash after completed SQL commit before result Scribe ACK. No tests were executed here.

Focused closure proof should delay result ingress before durable ACK, permit action/checkpoint settlements, interrupt without draining/flushing the pending final write, and restart with the same durable backing. Assert there is no premature unrecoverable completed state, the selected final result eventually reads back once, and committed provider work is not dispatched again. Also cover rejected/lost result acknowledgement without converting unrelated service work into a process-fatal failure. This proof stays within the existing queued execution journey and Scribe fault boundary.
