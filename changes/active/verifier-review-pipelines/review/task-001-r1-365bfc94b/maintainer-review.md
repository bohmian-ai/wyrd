## Proposed findings

### MNT-001 — Required snapshot backend performs filesystem traversal and reads on the async worker

- Classification: **VIOLATION**.
- Changed location: `crates/wyrd/wyrd-server/src/verification/hosted/workspace.rs:565` (`Workspace::freeze`, particularly lines 575–636).
- Governing rule: `agent_docs/rust.md`, Async: “Never block inside an async request path without an explicit blocking strategy.” The maintainer guide also requires workflow stages to remain followable through the owning type.
- Source path: required `Publications::path` (`hosted/publications.rs:113`) awaits `workspace.freeze(path)`; freeze acquires the async writer lock and then calls synchronous `symlink_metadata`, `read_dir`, and `std::fs::read` for the whole tree without yielding or using the blocking pool. Defaults permit 50 MiB and 10,000 entries (`hosted/mod.rs:137–144`). The same owner's existing materialization uses `spawn_blocking` (`workspace.rs:159`), and hosted filesystem reads/extract use it while retaining writer exclusion (`hosted/tools.rs:248–265`).
- Concrete cost/consequence: a filesystem stall or a large required snapshot occupies a Tokio worker for the complete walk/read, delaying unrelated request/lease/cancellation work scheduled there; a future timeout cannot preempt that poll. Maintainers adding the Task 3 tool would reasonably assume this async backend follows the neighboring workspace IO strategy, but it does not.
- Reachability/materiality: the trusted publication backend is explicitly required by Task 001 and exercised through `VerificationFixture::publish` and the real storage tests. There is **no production Agent publication-tool caller yet**; that is intentionally Task 3. This proposal concerns safe execution of this task's required backend, not adding a new tool or a speculative call path. Independent validation should retain this distinction when applying materiality.
- Smallest correction: keep strict snapshot/confinement at Workspace and run the blocking snapshot work through the existing blocking-pool strategy while preserving writer exclusion for the entire snapshot, including cancellation. Do not add a worker service, queue, filesystem abstraction or replacement walker subsystem. Deleting snapshotting cannot preserve the task; reusing best-effort `walkdir` would violate all-or-nothing behavior.
- Focused proof: retain directory completeness/refusal and held-writer assertions in `directory_snapshot_is_complete_or_rejected`, plus file immutability/replay tests. Verify the actual synchronous walk/read runs in the blocking boundary and that cancellation cannot release writer exclusion while a detached snapshot still reads. No synthetic host-load test is requested.

### MNT-002 — Python's download-plan declaration loses the server's required expiry field

- Classification: **MISSING** / declaration parity.
- Changed location: `sdks/wyrd-sdk-python/python/wyrd/verify/__init__.pyi:463` (`DownloadPlan`).
- Governing rules: maintainer guide “Python and TypeScript: types carry the contract”; Python AGENTS requires authored declarations to match the native API; REQ-049/public-contracts requires first-class thin projections of the existing File download-plan shape.
- Producer-to-consumer evidence: `wyrd-spec/src/storage/download.rs::DownloadPlan` has required `get_url` **and `ttl_secs`**; `wyrd_storage::service::download_plan` always fills expiry (zero for local, presign TTL for cloud); inspection returns this exact `DownloadInitResponse`; `PyExecution::download` serializes it without filtering. The new Python `DownloadInit.plan` refers to a TypedDict that declares only `get_url`. Generated TypeScript DownloadPlan correctly retains `ttl_secs`.
- Supported failing scenario: after `plan = execution.download(producer, name)`, a typed Python caller reading `plan["plan"]["ttl_secs"]` to honor a cloud URL's expiry is accessing an undeclared TypedDict key, even though that key is required in the actual response. A literal fixture of the true returned plan is likewise rejected as having an unknown fixed key. This denies Python users a typed part of the promised shared download contract.
- Concrete maintenance cost: runtime and authored declaration now describe different fixed records; callers must suppress typing or cast away the contract to use valid expiry data. The current Python journey does not perform a successful download, and the unchanged `tests/typecheck/verify_contracts.py` does not pin the new response shape, so recorded green typechecks do not cover this omission.
- Smallest correction: add the required `ttl_secs: int` field to this existing TypedDict, documenting cloud expiry and local zero as the owner does. No new type/export or runtime implementation is needed.
- Focused proof: extend the existing typecheck contract fixture to accept the actual returned plan and assert expiry access has type `int`; use the ordinary narrow Python typecheck lane. A new server fixture or cloud service is unnecessary for this declaration-only correction.
