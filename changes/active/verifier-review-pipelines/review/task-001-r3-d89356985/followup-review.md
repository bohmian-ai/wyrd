## Actual terminal producers and recovery reachability

1. **User cancellation.** `wyrd-server/src/components/verification/service/inspection.rs:687–790` authorizes, executes `queue.cancel`, reads SQL status, optionally obtains live Card identity, commits, and only then calls `retain_cancellation`. That helper reads accepted state, falls back to the fetched identity, constructs a queue-free `RunState::at`, and calls `fail` with a 30-second deadline. Failure is logged. A process crash immediately after `conn.commit()` prevents even outbox enqueue. A repeated cancel sees `cancelled == false` and does not call this retention helper. The response's cancelled status therefore cannot establish canonical retention.
2. **Principal revocation.** `wyrd-auth/src/revoke.rs:51–113` suspends the principal and calls `VerifierExecutionQueue::cancel_principal` on the same caller-owned connection. User refresh-family revocation participates in that transaction too. `CANCEL_PRINCIPAL_SQL`, `verifier_executions.rs:615–622`, updates every affected unfinished execution to cancelled with `principal_revoked`; no server RunState/outbox delivery accompanies it. The caller's commit must continue retiring authority and work together.
3. **Admission racing earlier revocation.** `VerifierExecutionQueue::fence_principals`, `verifier_executions.rs:2040–2072`, share-locks submitted/accepted principals and invokes the same `cancel_principal` for inactive identities before admission commits. Submitted/scheduled/group admission can therefore commit directly as cancelled, before a runner has created any checkpoint. `SubmissionSink::write`, `wyrd-server/src/verification/submissions.rs:235–340`, commits admissions then sends replies/notifies the runner; it has no terminal projection step or persistent terminal retry ownership.
4. **Refused group before accepted execution.** `wyrd-server/src/verification/scheduler.rs:593–665,706–814` consumes pending work and commits a refused terminal handoff. `VerifierExecutionQueue::refuse_group`, `verifier_executions.rs:2580–2621`, uses `INSERT_GROUP_ERROR_SQL:306–321` to insert errored status/error/identity from binding/Card rows. It explicitly has no accepted authority, input, or snapshot and is never claimed. No canonical terminal delivery is staged. This covers inactive/rejected authority and the existing overdue-incomplete-snapshot terminal refusal, not just engine failures.
5. **Runner pre-state failures.** `VerifierRunner::execute`, `wyrd-server/src/verification/runner.rs:388–412`, immediately terminates on target-resolution or SYSTEM-principal failure before constructing RunState. `settle:759–845` writes the terminal SQL decision. `attempt:1038–1039` can also convert exhausted release/retry/defer outcomes after `execute` returns. These paths are not all covered by `retained`.
6. **Engine/error/exhaustion with a RunState.** `runner.rs:1375–1396` calls `state.fail`, but logs failure and returns the terminal transition anyway; queue settlement still commits. Thus an unavailable/unacknowledged state write can leave the same SQL-only terminal state. This subset can be repaired locally by retaining existing runnable retry custody until canonical acknowledgement; that does not solve the queue-owned cancellation/refusal commit boundary.

**Why another worker cannot currently repair these facts:** `CLAIM_SQL`, `verifier_executions.rs:410–447`, considers only pending/retrying rows and expired running leases. `RUNNABLE_TENANTS_SQL:685–724` has the same eligible states. Cancelled/errored/timed-out rows have no due time or live lease. `CANCEL_SQL:606–612` and principal cancellation remove both. A stale worker is correctly stopped by `HeldLease::confirm`, `wyrd-server/src/verification/leases.rs:67–77`, and cannot serve as the cancellation lifecycle owner. Final-attempt reconciliation changes computation recovery for expired running rows, not terminal-row eligibility.

## Input and identity custody, including source deletion

The accepted input handoff is real, but is insufficient terminal custody. `wyrd-server/src/components/verification/service.rs:710–757` builds submitted input, stages it, and carries only coordination identity to admission. `verification/results.rs:195–205,399–440` stores input declarations/routes/key/digest/authority and Verifier UID; it does not store complete exact Verifier and subject CardRefs. Group/schedule selectors likewise do not supply those exact references. `InputResolver::record`, `verification/inputs.rs:233–240,459–492`, only decodes origin/inputs/activation. Exact `ExecutionIdentity` is currently constructed from resolved live targets during runner state creation (`runner.rs:483–505`), so pre-checkpoint cancellation/refusal can lack it entirely. Refused groups have no accepted input at all.

Capturing the required immutable identity in existing canonical input/lifecycle records is already directed by FIND16/R3 and is a bounded fix. It must preserve the distinction between identity custody and accepted runnable inputs: refused work must not acquire invented authority or inputs. Capturing identity alone does not record a later revocation/cancellation/error decision.

Card deletion is a real retained-read requirement, rather than a license to use deleted registry rows as historical authority. The current cancellation fallback calls `Self::card` and can fail to reconstruct identity after source deletion; group/owner/run fields are also omitted by its fresh fallback. Existing physical queue FKs are non-cascading and Card deletion is soft deletion (`wyrd-sql/src/queries/cards/delete.rs`). I found no production `DELETE FROM wyrd.verifier_executions` retry/cleanup owner. Consequently this report does **not** assume ordinary Card deletion physically cascades away queue rows or invent a new deletion race. R3 nevertheless expressly requires retained evidence after coordination-parent removal; once canonical identity/terminal facts exist, that is independent of SQL retention. Queue-only terminal facts cannot meet it.

## Existing delivery owners and the smallest proposed extension

The following existing mechanisms do not close the crash interval:

- `ScribeSink::write`, `wyrd-server/src/scribe_outbox.rs:1865–1911`, retries stable frames already submitted through the process outbox and signals acknowledgements. Its process-memory loss boundary is explicit at lines 19–32. Scribe WAL/replay starts after ingress acceptance; it cannot recover a cancellation never submitted before the crash.
- `SubmissionSink::write` owns the already declared **Bifrost input ACK → queue admission** order. Replaying its admission cannot independently recover later revocations, and not every terminal producer traverses it.
- `VerifierRunner::deliver`/`settle` and `verification/completions.rs:1–15` own **Bifrost selected result ACK → queue completion**. Queue retry can reconcile already canonical results while rows remain running. Completions' bounded channel is process memory; it does not persist or enumerate terminal decisions.
- Scheduler pending-group rows are consumed in the same commit that inserts the refusal. Reusing the scheduler after that commit requires a new source of terminal delivery eligibility; the consumed pending row cannot provide it.
- HeldLease renewal and ClaimLoop provide existing bounds, fairness, draining, and execution lease mechanics, but neither enumerates terminal work or knows how to publish its sole SQL terminal decision.

The concrete smallest candidate is to extend `VerifierExecutionQueue` and `VerifierRunner`/ClaimLoop so committed terminal rows remain discoverable delivery work, reconstruct identity from canonical admission/lifecycle custody, write the existing terminal checkpoint through the existing Scribe outbox under stable identity, and retry after crash until canonical acceptance. It adds no separate writer/service and can leave cancellation atomic. **It is nevertheless not an in-scope recommendation under the present authority.**

The distinction is semantic, not the name or storage size of a new field: after cancellation/refusal commits there is no computation, admission, or Operator action left. The remaining work is deriving the historical canonical terminal event from the sole SQL decision/error. A restart scan therefore makes the terminal SQL rows an event projection backlog. Scanning all terminal rows forever avoids a marker but retains the same backlog and adds repeated unbounded history work. A bounded due/lease/acknowledgement extension needs durable terminal-delivery eligibility and retirement semantics. Those would declare the SQL-terminal → Bifrost handoff currently absent and explicitly excluded at `bifrost-design.md:469–474`; an acknowledgement flag cannot be assumed harmless merely because it is called queue coordination. Reading SQL terminal status forever as a fallback also preserves the forbidden historical dependency.

Prewriting a final canonical cancellation before the SQL transaction commits reverses the defect: rollback can leave a canonical cancellation that never occurred, while waiting for Bifrost would make security cancellation depend on storage availability. Making a staged canonical fact tentative until a SQL commit proof is checked introduces another persistent protocol/authority. Neither is the existing selected-result completion path or permitted rare old-worker overlap.

## Decision required and correction burden

The exact unresolved **contract decision** is: **what durable owner carries an atomically committed queue-owned terminal decision until canonical Bifrost acceptance, and when is that custody discharged?** The technical uncertainty is resolved: no current declared owner does it.

The authority must select between allowing that specific terminal-only SQL-to-Bifrost committed handoff within the existing queue/runner (including delivery eligibility, acknowledgement/retirement, and identity custody), or explicitly accepting best-effort canonical retention of those queue-owned decisions after their atomic commit and revising the full-retention promise. A stronger cross-store commit protocol would also require a new decision and is currently expressly excluded. This report selects none of those changes.

The local engine/pre-state/identity omissions are material, bounded implementation gaps. They should not obscure the separate architecture decision at cancel/revoke/admission-refusal commit. A remediation that merely says “reuse durable retry” is not decision-complete. A source test must first be able to crash immediately after each actual SQL commit and before enqueue, restart with no original request task, preserve atomic revocation/cancellation, and eventually read exact canonical terminal facts after the queue/source dependency is removed. The owner selected by an approved contract must make that proof possible.

No new finding ID is proposed. Carry FIND-TASK-001-17 forward with the above narrower correction-burden conclusion; this follow-up does not authorize code changes or a new persistence mechanism.
