## Proposed finding

### MNT-R3-001 — deferred checkpoints undercharge ordinary retained settlements and final outcomes

Classification: **VIOLATION / REGRESSION**. This is an incomplete FIND-TASK-001-22 correction, not a new request for a memory-governance framework.

Changed location: `crates/wyrd/wyrd-server/src/verification/state.rs:379–400`, `Checkpoint::weight`; consumers `scribe_outbox.rs:363–367,1821–1830`. Governing obligation: R3 FIND-22 requires preserving capacity/byte accounting and stable retry/lifetime ownership while the existing bounded writer prepares the frozen state. Revision 1 likewise preserves existing reservation/byte ownership. Maintainer-style requires a stateful owner to retain its invariants so callers can safely reason about its behavior.

Producer-to-consumer proof:

1. Ordinary requirement execution retains variable content. `vala-verify/src/blocks/engine.rs:1384–1399` builds a `RequirementResult` including captured actual value, reason, custom data, citations, detail and check configuration; `Judged::checked` also keeps provider/check reason and custom verdict data. `VerificationEngine::commit` at lines 405–425 passes that full result through the existing Checkpoints interface.
2. `RunState::settle` (`state.rs:945–961`) clones the supplied settlement into the invocation record. `RunState::select` also retains the full final `VerificationOutcome`. These are required recovery payloads, not dormant or forged state.
3. `Checkpoint::weight` charges only `512 * (1 + invocation_count + publication_count + object_count)` plus twice the JSON-publication retained bytes. It ignores every variable settlement field, selected final outcome, and failure body. For one requirement whose captured actual value is a 64 KiB JSON string and no publications, the charge remains 1024 bytes, exactly the same as for an empty actual value. Such an input is an ordinary supported full-context requirement, not an excessive host-load scenario.
4. `ScribeSink::weight` and `Part::bytes` both trust this result. Existing `wyrd-runtime/src/outbox.rs::send_reserved` (lines 540–562) adds it to `reserved_bytes`, and reservations use that counter to apply the configured byte share. No later preparation step corrects the charge. Unlike the previous prepared-row `owned_bytes` charge, the new estimate therefore allows supported large settlements/outcomes to consume retained memory without corresponding byte backpressure. The prepared row is also kept in the Checkpoint's OnceLock while its original state remains held.

Concrete maintenance and availability consequence: the shared writer's byte-limit invariant now depends on every state producer avoiding variable payloads that its public types and normal engine explicitly retain. A maintainer adjusting outbox limits or adding a valid settlement field cannot rely on the existing accounting owner; concurrent supported executions can accumulate much larger frozen/prepared snapshots than the byte counter represents. The existing Result payload's separate accurate charge does not account for its additional Checkpoint copy. No machine-independent OOM threshold or throughput claim is required or made.

Smallest correction boundary: keep the existing Checkpoint/Outbox/Part preparation workflow and repair the stable Checkpoint charge to conservatively include its retained variable state and prepared representation, including settlements and terminal outcome, rather than estimating their payload solely from entry count. Preserve serialization on the existing bounded preparation path; moving it back to the caller, creating a new writer/governor, dropping recovery fields, or merely increasing the fixed per-entry constant does not close this input-dependent gap. A precise allocator inventory is unnecessary; a stable conservative charge that follows supported variable payload growth is sufficient. Reuse existing retained-value/byte-accounting mechanisms where applicable.

Focused proof: extend the existing state/outbox charge proof with a frozen checkpoint containing a sizeable captured requirement value/reason/custom data and a selected outcome. Show its charge grows with those bytes, remains stable across preparation/retry, and is the amount admission releases. Retain the existing reservation and bounded-preparation tests. `staged_writes_charge_their_owned_memory` already supplies the nearby pattern for a 64 KiB result reason, but currently omits ExecutionState. No new dependency, harness, host-load test or benchmark project is needed.
