## Material findings

### SYS-R3-17 — FIND-TASK-001-17 remains incomplete across terminal production, custody and recovery

Classification: MISSING / INCORRECT. Obligations: REQ-054/056/058, AC-048, supplement recovery sequence and terminal-state table; R3 explicitly requires pre-engine, queue refusal/exhaustion, retry termination and principal cancellation through their actual lifecycle owners.

Exact locations and reachable paths:

* `runner.rs::execute:390–400` returns terminal target-resolution/SYSTEM failure before constructing RunState. A queued execution whose Verifier is deleted before claim is an ordinary supported negative flow; it settles only queue status/error. No canonical identity/error is produced. `verifier_executions.rs::cancel_principal:3174–3193` similarly writes queue cancellation only, including its `fence_principals` admission caller. These terminal rows cease being runnable, so ordinary runner recovery cannot later fill the gap.
* `runner.rs::retained:1377–1405` logs a failed `state.fail` and returns the terminal/retry transition unchanged. `settle:760–858` then permanently terminates/exhausts the queue. Hold or reject the terminal checkpoint until deadline while allowing queue SQL: after restart the accepted state remains running or absent, and there is no retained terminal retry. User cancellation has the same lifetime gap: `inspection.rs::cancel:726` commits cancellation before `retain_cancellation`; lines 751–790 log any source/admission/receipt failure and return success. Kill the process after the commit, or make the required WAL owner unavailable during that read, and no retry owner remains for the canonical cancellation. This is not the accepted rare old-worker overlap: even with no competing worker, the only terminal fact can stay in SQL forever.
* `runner.rs::execute:420–442` reads only `snapshot().terminal`, never `snapshot().failure`. Accept a canonical engine TerminalFailure, inject failure in its queue settlement COMMIT, expire the lease and reclaim within the remaining attempt budget. Recovery loads the failure but dispatches the engine again. A subsequent completed outcome can call `RunState::select:609–630`, which checks `terminal` but not `failure`, recording both despite the type's documented exclusivity. Retained status then prefers Completed (`inspection.rs:231`) over the accepted failure. The supplement explicitly requires terminal error replay without executing steps.

Consequence/materiality: supported deletion, principal revocation, cancellation, timeout or ordinary engine error can remain SQL-only; after coordination removal its full historical error is lost. A failed settlement can instead revive a canonically terminal execution and replace its user-visible disposition. This directly defeats the task's central terminal custody and recovery behavior, not optional outage hardening.

Minimum correction boundary: complete the existing canonical terminal lifecycle once at its actual producers/consumer. Make recorded failure a terminal recovery branch before dispatch and preserve exclusivity with selected success. Retain pre-engine/queue-owned terminal facts using accepted identity/context and existing shared writer/delivery owners. Ensure an unavailable write or crash between control commit and canonical custody retains a retry path at that owner; logging plus making the queue terminal cannot be the sole delivery mechanism. Preserve immediate permission revocation and queue cancellation, do not authorize stale workers, add a new finalizer, introduce a SQL execution payload/head, or add distributed fencing. This requires producer/lifetime correction; adding reader fallbacks would merely preserve the rejected SQL authority. Reuse existing committed delivery/retry ownership rather than a new service.

Focused proof: extend existing real-server negative flows with (a) Verifier removal before first claim and principal cancellation, no prior checkpoint; (b) required-source/writer failure across cancellation and terminal error, followed by process restart and recovery, requiring canonical exact identity/full sanitized status/error independently of queue payload; (c) accepted TerminalFailure then failed queue settlement, requiring the same failure and zero engine entries on reclaim. Assert no state can contain success plus failure. Existing success-only/readback tests do not establish these paths.

### SYS-R3-19 — FIND-TASK-001-19 still terminalizes durable work when reconciliation is temporarily unavailable

Classification: INCORRECT. Obligations: REQ-055/058, AC-049, supplement unavailable-state and terminal-result/reply-loss recovery; R3 final-attempt reconciliation.

Locations: `runner.rs::execute:405–418`, `state_failure:1231–1248`, `attempt:1037–1041`, `settle:809–815`; queue exhausted claim handling `verifier_executions.rs::CLAIM_SQL:407–455`.

Reachable path: final attempt durably accepts its selected checkpoint and result/output frames, then queue completion COMMIT fails (the new test's existing supported fault seam). After expiry a runner claims `exhausted=true`. Make the acknowledged WAL owner temporarily unavailable, or merely fill the result-reserved outbox share. `execute` returns Defer from `state_failure` or capacity admission before it can inspect the selected result. `attempt` unconditionally rewrites every exhausted Retry/Defer to `exhausted()`. `settle` permanently writes `errored/lease_expired`. When the dependency recovers there is no runnable queue work to finish bookkeeping/delivery. No provider call or ambiguous late-result policy is involved: all result records were already durable before the outage.

Consequence/materiality: an ordinary temporary recovery dependency outage discards the required final-attempt reconciliation opportunity and strands the already completed result/dispatch coordination. Canonical polling may later show Completed while the queue and downstream completion effects remain errored/absent. The newly added test proves only a healthy reclaim and therefore misses the original failure under the materially changed recovery path.

Minimum correction boundary: preserve the exhausted, non-computing claim for retry when accepted-state reconciliation or required delivery is temporarily unavailable. Permanently exhaust only after readable authoritative state establishes unfinished computation. Keep original attempts/deadline, cancellation and identity; use existing claim/lease expiry/retry ownership. Simply allowing the ordinary Defer→release path is insufficient because RELEASE_SQL refunds an attempt; an exhausted claim must neither refund nor spend a computation attempt. No SQL query into Bifrost, new scheduler/store, or generalized time extension is needed.

Focused proof: add a required-owner/read unavailability window and separately reserved-outbox admission refusal to the existing final-attempt failed-settlement test, restore availability, and require identical completed result and completion side effects with zero engine entries and unchanged attempt count. Keep the genuine unfinished final-attempt exhaustion test. Do not rely on a new post-deadline provider/delivery policy to prove this already-durable-result case.
