## Findings

### INVAR-R3-17 — INCORRECT: canonical terminal producer coverage remains incomplete

**Prior identity:** FIND-TASK-001-17. **Obligation:** REQ-054/056; R3 explicitly requires each existing engine, pre-engine and queue-owned terminal producer to retain sanitized status/error/identity through canonical verification data. The user exception for rare old-worker overlap does not waive these terminal records.

**Locations and producer-to-consumer evidence:**

- `runner.rs:395–403` returns target-unavailable/no-system-principal termination before a `RunState` exists; only `settle` writes it. `runner.rs::retained:1376–1396` runs only on later engine/exhaustion branches.
- `wyrd-sql/src/queries/verifier_executions.rs::cancel_principal:3174–3196` updates SQL with `principal_revoked` and returns a count. Its actual admission sibling `fence_principals:2048–2071` invokes it too; no canonical terminal writer receives the affected identities. Principal-revocation terminal history therefore remains SQL-only.
- Ordinary cancellation writes canonical state only after committing cancellation, through `inspection.rs::retain_cancellation:743–807`. A failed read/stage/ACK is logged and forgotten; repeat cancel obtains `cancelled = false` and does not try retention again (`cancel:695–731`). This produces the same missing canonical terminal custody, not a request for stronger old-worker fencing.
- `service.rs::get_execution:233–253` starts with `queued.state.clone()` and replaces its error only when canonical `.failure` exists; `Retained::status` likewise falls back to queue state. Without a queue row, `retained` requires recorded state identity; pre-state failure becomes not-found, and progressed principal-cancelled work becomes `running` with no error (`inspection.rs:228–244,350–369`).

**Reachable consequence/materiality:** Ordinary target deletion before claim or principal revocation ends the execution in SQL but leaves no canonical terminal error. Removing its coordination row/source Cards loses the outcome or reports an unfinished execution. A transient Scribe/read outage during an otherwise successful cancel creates the same gap and a repeat cancel does not repair it. These are explicit existing terminal paths, not malformed inputs or hypothetical workload concerns.

**Smallest correction boundary:** Finish prior FIND-17 at the existing lifecycle producers and common retained reader. Retain full sanitized decisions and immutable identity through their existing shared-writer capability; include the actual pre-engine and revocation/admission cancellation owners, not a stale runner. Preserve queue coordination, permission/revocation transaction ordering and the recorded user exceptions. Do not add a head table, scheduler, finalizer or queue-to-Scribe acceptance protocol. A reader fallback or fabricated failure after queue deletion cannot reconstruct the missing original decision. The remaining correction is producer wiring and preservation of the existing canonical payload, not a new persistence design.

**Focused proof:** Extend existing terminal/inspection negative flows for target-unavailable before first checkpoint and principal cancellation of progressed work; remove queue row and source Cards, then verify original sanitized status/error/identity with existing authorization. Exercise one cancelled-record write refusal and a repeat cancellation/recovery path so a successful control response cannot permanently strand its only history in SQL. Existing seeded-error and normal-cancel tests do not prove these paths.

### INVAR-R3-22 — REGRESSION: checkpoint byte admission omits retained settlement/outcome values

**Prior identity:** FIND-TASK-001-22's explicitly preserved byte-accounting/admission obligation. **Location:** `state.rs::Checkpoint::weight:381–403`; consumers `scribe_outbox.rs::Part::bytes`, `ScribeSink::weight:1822–1831`, shared `wyrd-runtime/src/outbox.rs::send_reserved:545–558` and reservation byte threshold.

The new estimate charges 512 bytes per invocation/publication/object plus twice *publication* JSON bytes. It charges no variable bytes for invocation settlements, terminal outcome, captured actual/data, check configuration, reasons or File descriptor strings. A normal Full context-capture requirement preserves an actual JSON string verbatim (`vala-verify/src/assertion.rs::capture_actual:106–118`; engine `Judged::report:1381–1401`). Engine `commit:405–425` clones this into `InvocationSettlement::Requirement`; `RunState::settle` puts it in the frozen checkpoint. With one 64 KiB actual string, no publications and one invocation, the entire snapshot is charged 1,024 bytes irrespective of the string length. A selected outcome copies requirement data again without changing the estimate. `Checkpoint::row` then retains the prepared row beside the frozen state.

**Consequence/materiality:** Existing shared reserved-byte backpressure now admits large frozen snapshots as tiny writes. The byte threshold can remain below its configured limit while retained memory exceeds it by orders of magnitude across ordinary captured requirement results. Bounded encoder task count does not bound these queued payload bytes, and measuring only JSON-publication workloads misses the defect. This is a lost admission invariant, not a throughput or exact-allocation benchmark demand. The preceding implementation charged prepared row owned bytes.

**Smallest correction boundary:** Keep deferred bounded preparation and one stable charge per checkpoint, but account for the complete retained state including variable settlement/terminal values using existing size accounting or a conservative traversal before admission. Do not restore inline JSON/Arrow preparation or add a second queue. Ensure admission and release use the same charge, and that lazily retained prepared payload has accounted capacity. Counting only entry overhead cannot preserve the required byte bound.

**Focused proof:** Add one small existing state/outbox test with a large captured actual/data value and no publication. Assert the charge grows with those bytes and reserved byte admission backs off under a deliberately small configured byte budget; keep one-row preparation, retry identity and cancellation coverage. No synthetic host load or benchmark harness is needed.

### INVAR-R3-26 — INCORRECT: accepted terminal failures are ignored on runner recovery

**New source-local proposal; final stable ID belongs to validation.** **Obligation:** REQ-058 and supplement's explicit load flow: terminal state returns its recorded result/**error** without executing steps. `ExecutionState.failure` promises it is never recorded beside `.terminal` (`wyrd-spec/src/verification/state.rs:54–59`).

**Locations:** `runner.rs::execute:417–428`, `RunState::select:609–628`; producer `runner.rs::retained:1376–1396`. The new producer durably records an engine terminal failure before queue settlement. If the process/lease is lost before that settlement commits, the ordinary queue reclaims the same execution. `RunState::recover` restores `.failure`; `execute` tests only `.terminal`, then enters exhausted handling or dispatches the engine again. None of `change`, `begin`, `settle`, or `select` treats the recovered failure as terminal. A subsequent successful outcome writes `.terminal` alongside `.failure`; inspection chooses Completed because its terminal check precedes its failure check, while `get_execution` can still expose the old failure error.

**Reachable consequence/materiality:** A non-final-attempt terminal error, such as unavailable hosted capability, is acknowledged in Bifrost and then interrupted before queue termination commits. On reclaim, if that capability is now available, computation can run and select a different outcome for an execution already terminal. Even a repeated deterministic planning failure still violates reuse of the recorded terminal decision. This is the same supported failed-settlement/reclaim lifecycle the task already tests for successful results, and is introduced by adding the failure state without adapting its recovery consumer.

**Smallest correction boundary:** At the existing runner recovery decision, handle accepted failure together with accepted selected result before exhaustion/engine dispatch, returning its recorded sanitized terminal transition without new computation. Preserve the single RunState terminal invariant so outcome selection cannot add an outcome after a failure. Reuse existing terminal-status mapping; no new persistent type, protocol or service is needed. This is separate from FIND-17's missing producers: it fails even when the producer has correctly persisted the complete failure.

**Focused proof:** Adapt the existing failed-settlement/reclaim test to retain a terminal failure, interrupt queue settlement, reclaim, and assert identical recorded status/error and zero engine/provider invocation, including final-attempt recovery. A focused state assertion should verify failure cannot be followed by an accepted selected outcome. Preserve ordinary successful-result redelivery.
