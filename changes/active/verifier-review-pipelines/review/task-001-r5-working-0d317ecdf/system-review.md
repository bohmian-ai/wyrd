## Deployed paths and failure propagation

The existing runner owns both attempt and delivery claims. `VerifierRunner::claim` (`verification/runner.rs:1166–1260`) obtains queue claims and target/custody within a tenant transaction. `process` dispatches attempts to `attempt` and terminal-only claims to `deliver_owed`. No new service or writer was introduced. The existing process outbox still owns prepared writes, bounded reservation and retry; PostgreSQL owns discoverability and queue coordination, while Bifrost remains canonical state.

The common decision/result operation is `conclude` (`runner.rs:1480–1513`). Normal execution and record-only recovery reach it with an accepted/selected/failed offer. `RunState::decide` checks and changes terminal disposition under one memory lock and waits for a revision containing that decision. An accepted success or failure wins over a new failure. A failure becomes `Terminate` only after state ACK; a failed/unacknowledged failure write becomes `Owe`. A selected outcome goes through the existing `ResultPayloadBuilder::build_as` using the selected result ID and interval, then `deliver`, which confirms an attempt lease and waits for the result receipt. `ScribeSink::write` writes detail frames before summaries and emits that receipt only when every required frame survives and group-activity recording commits (`scribe_outbox.rs:1847–1905`). Rejected/dropped/missing result ACK maps to Defer rather than completed delivery.

`settle` then applies the attempt transition in the existing tenant transaction (`runner.rs:977–1085`): acknowledged failure terminates with `TerminalDelivery::Acknowledged`, not a second owed pass; unacknowledged failure terminates with Owed. Success retains existing batched `Completions`/queue completion and its atomic group/Operator effects. Failed settlement retries under the same lease; death/loss leaves reclaim eligible. An exhausted claim that cannot recover/read/admit maps Defer/Retry/Release to LeaseLost (`attempt:1369–1375`), leaving expiry-based reconciliation without refunding or spending an extra computation attempt. A readable, undecided exhausted claim alone offers the lease-expired failure before dispatch.

Request cancellation now commits only the immediate control/custody transaction (`inspection.rs:685–704`); its separate canonical writer/retirement shortcut is gone. SQL cancellation, principal revocation/inactive admission and refused group/admission producers leave `delivery_due_at` durable. A crash before any staging therefore leaves discoverable record-only work. The common `record` (`runner.rs:624–687`) recovers authoritative state before deciding, preserves accepted identity or uses existing exact Card custody, and defers/owes when internal authority, identity, capacity or state is unavailable. It never starts providers. Missing SYSTEM does not restore revoked user authority. P4 exercises actual cancel/revoke/inactive admission/pre-target refusal/refused group producers, including no checkpoint, a dead delivery claim, unavailable fence reads, missing SYSTEM and a failed retirement commit.

For terminal-only work, `settle_delivery` retires only Complete/Terminate; every other result makes the delivery due again. `SETTLE_DELIVERY_SQL` matches execution and claimed due instant, so an older delivery claim cannot retire a replacement claim. Cancellation changes status and clears the computation lease; a stale attempt completion/termination does not match running state and cannot retire its delivery. No stronger pre-acceptance cross-service fencing is claimed. A failed delivery retirement retries with backoff; death or shutdown leaves the moved due instant to expire. SQL/Bifrost outages fail or defer the claim/operation, rather than crashing the shared server or taking unrelated capabilities offline. These paths retain normal existing capability supervision.

## Selected-result replay and consumers

Two forms of replay must remain distinct. A shared outbox retry resends its sealed slice with the same physical batch/frame identities; Scribe deduplicates that retry. A later runner/delivery claim rebuilds the selected result into a new outbox slice. It preserves logical `result_id`, execution identity and selected interval; it can append additional physical rows under that logical ID. R5 does not promise one network send or one physical row across independently restaged deliveries. P5 intentionally observes multiple sends under one result ID; the existing lost-result-ACK test separately pins identical sealed-batch dedup.

The affected consumer paths tolerate the supported logical replay: `InputResolver::result` (`verification/inputs.rs:409–462`) joins by the exact selected result ID and reads one equivalent output/summary; retained execution inspection selects from accepted state rather than result-row recency. `GroupPoller`'s source decoding records physical result duplicates by result ID at earliest ingestion (`groups.rs:549–579, 646–659`), then selects logical executions. Outbox `schedule_groups` can refresh the pending generation after replay, but existing snapshot digest/admission idempotency prevents an unchanged population from minting another group execution. Group comparison and Operator dispatch still live in queue completion, not every result-frame ACK: `complete/complete_many` keep their existing replay checks and unique dispatch key (`verifier_executions.rs:3022–3150`, `INSERT_DISPATCH_SQL:530–565`). Thus a retry of a committed completion does not duplicate its dispatch. Cancellation's control status remains cancelled; record-only delivery of its earlier selected result does not revive the computation or run completion effects as a fresh success.

No requirement for global row-level uniqueness, a new result dedup store, or exactly-once external Operator/provider effects is inferred from these retries. Ordinary raw SQL can observe physical repeat rows; consumer identities/dedup remain the existing contract. No material changed-consumer regression was established from that fact.

## Proposed findings

### SYS-R5-01 — MISSING: the explicitly required reserved-share outage recovery proof is absent

Obligation: R4 scenario 4 explicitly requires separate source and reserved-share outages for a final attempt whose selected result is durable but queue COMMIT failed. R5 scenario 2 expressly carries and repeats that capacity case; R5 cannot declare it unauthorized merely because the current harness lacks a convenient hook. `changes/implementation-execution.md` permits narrow private fixtures/support adaptations within the owner.

Location: `pg_verification_runtime.rs:2242–2286`, `exhausted_reconciliation_survives_source_and_capacity_outage`. The full test changes only the tenant fence-read grant. No reservation is refused and no reserved capacity is occupied. Its name and recorded PASS therefore cover only the source case. This is not a claim that source inspection shows an incorrect Defer mapping: `execute:570–572`, `busy:1761–1766` and `attempt:1369–1375` support the intended behavior. It is a missing explicit failure/recovery observation at a real resource boundary that previously caused permanent false exhaustion.

Consequence/materiality: the required completion gate remains unproved for normal outbox backpressure after a failed final-attempt settlement. A healthy/source-only run cannot detect a regression that refunds/spends the exhausted attempt or retires it when `reserve(1)` actually fails. This is the existing FIND19 closure proof, not a new failure policy or broader performance test.

Smallest correction: extend that existing integration scenario to force an actual refusal of the runner's reserved share, observe that final-attempt record-only responsibility survives without computation or budget change, release the held capacity, and require completion with the original selected identity/effects. Reuse outbox reservations and existing runner construction; `Outbox::reserve(slots)` is an atomic slot charge and retains no synthetic payload (`wyrd-runtime/src/outbox.rs:435–458`), so do not fill 1 GiB of data or generate host load. A bounded test-owned composition/seam is sufficient if the runtime fixture does not expose its outbox. No public configuration, new service, production capacity policy or durability mechanism is warranted.
