## Real limits and concurrency interpretation

`hosted/mod.rs:132–162` defaults are: 20 MiB per input/published file, 100 MiB cumulative retained publication bytes, 1,000 accepted publications per execution, 10,000 publication tree entries (through the reused archive entry ceiling), 250 MiB workspace scratch, 50 MiB work budget, 64 KiB tool result/accepted JSON publication, and 16 live workspaces per process. Publication depth is 32. These limits describe different resources; they must not be combined into an asserted process RAM ceiling.

`skald-agent/src/run.rs:12–35` defaults to 10 iterations and 8 concurrent tool calls; `loop_runtime.rs` uses buffer_unordered for that bound. Those are configurable defaults, not an aggregate byte reservation or cumulative call ceiling. A workspace serializes writers/snapshot reads, but snapshot buffers survive outside the lock during upload. Thus several publish calls can retain distinct frozen copies concurrently. Illustratively, 16 workspaces × 8 in-flight calls × 50 MiB tree snapshots is about 6.25 GiB of raw snapshot bytes before other allocations if those operations overlap; this is an envelope calculation, **not** measured resident memory, a guaranteed attainable steady state, or an OOM finding. The accepted 100 MiB budget is checked after uploads and does not reserve staging memory. Prior resource/security/concurrency findings are not waived by these defaults.

Workspaces::open uses try_acquire_owned rather than an unbounded admission wait queue. Workspace writers and blocking snapshots share the existing owner. Snapshot upload and durable ACK waits do not hold the workspace writer; unrelated workspaces do not share its lock. RunState staging/ACK happens outside its memory mutex. These are useful throughput properties that the task preserves.

## Findings and limits

No new performance finding met the task-review threshold. The meaningful costs to measure are repeated scratch accounting, concurrent frozen-tree memory, and full-state checkpoint copying; none is concealed as zero-copy or constant-time. Deleting the snapshot, skipping durable ACK, dropping provenance, or caching scratch bytes only at fs.write would violate required semantics. A different serializer, parallel uploader, cached index or second state owner is not justified solely by conventional performance preference.

No latency, QPS, peak-memory or saturation result is claimed.
