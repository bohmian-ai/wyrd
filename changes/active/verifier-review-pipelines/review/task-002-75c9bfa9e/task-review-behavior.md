## Whole-workflow reuse and regressions

The preexisting `ToolRegistry`/`ToolResolver`, `Agent` loop, `ToolSession`, `RecordedTool`, `Workspace::writer`, `Publications`, shared File completion and `RunState` remain the actual owners. The new `invoke_call` seam supplies identity missing from ordinary `invoke`; defaulting to `invoke` preserves sibling tool implementations. RecordedTool forwards that identity while retaining its existing bounded-result/recording behavior. `Role` carries either existing citation slots or the step Producer and does not create a second executor. `HostedTools::with_execution` binds the existing state, and `Invocation::publish` is a stateless adapter to Publications rather than a snapshot/replay lifecycle. `Workspace::write` is the owner of the new safe create/replace operation and shares its existing writer with code, extraction and snapshots. Extending these owners is sufficient; no concretely unearned replacement machinery was found.

The upload service's StorageCaller intentionally contains only the tenant; request/domain admission is its caller's responsibility. Verification File operations use `verifier:run` in architecture, not a separate invented File scope. Existing caller admission and exact tool permission therefore must not be mistaken for a missing new File permission merely because there is no `files:write` grant. The narrowed-scope journey does not prove live role removal during a delivery; its evidence is initial narrowing/delegation and execution cancellation. No new live role-refresh mechanism is prescribed by this review.
