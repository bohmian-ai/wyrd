### FIND-003-1 — Check attempts are durably charged before capacity admission

**Status:** CONFIRMED. **Discovery:** BEH-003-1, INV-003-1, CONC-002. **Classification:** INCORRECT.

**Violated obligation.** TASK-003 Scenario 1 expressly requires no pre-dispatch spend during capacity waits; REQ-008 counts Agent actions/checks/retries and conserves actual invocation spend across recovery. Root/architecture require existing admission and one accepted checkpoint owner, not queue waiting represented as invocation work. This is ordinary bounded multi-check execution, not an invented tenant quota or fairness promise.

**Exact source and producer-to-consumer proof.** In `crates/vala/vala-verify/src/blocks/engine.rs:1490–1514`, the prepared `requirement` future calls `spend`, constructs a producer, and awaits `begin` before entering `judge`. `judge` acquires engine/run capacity only at `:1660`. The complete `admit` body at `:493–506` waits first on run capacity, then shared engine capacity. `RunState::begin` (`crates/wyrd/wyrd-server/src/verification/state.rs:991–1003`) accepts the unsettled invocation record exactly as supplied; it cannot tell that the check is still waiting. `with_checkpoints` (`engine.rs:370–390`) restores every recorded producer's highest attempt, `agent_attempts` (`:460–484`) counts Agent requirement IDs from both step and whole-Verifier declarations, and `run` (`:719–731`) initializes the new cumulative budget from that total. A restored unsettled requirement has no reusable settlement, so it returns to the same spending branch.

**Reachable consequence/materiality.** Declare no steps, a slow code requirement followed by an Agent requirement, `limits.concurrency: 1`, and `max_agent_invocations: 1`. The first check holds the run permit; the second future records and spends before its permit wait, without any Agent executor call. Interrupt/reclaim during that wait. Recovery counts the recorded Agent attempt as the only spent invocation and returns BUDGET_SPENT/Inconclusive before that Agent has ever run. Arbitrarily long capacity waiting, rather than the necessary narrow accepted-begin-to-dispatch interval, manufactures durable invocation spend and changes a supported verification result.

**Sibling/owner audit.** `attempt` (`:1548–1632`) already admits before spending/beginning action work. Whole-Verifier requirements enter via `prepare`; per-step/per-item/per-iteration checks enter through `instance_requirements`; all share `requirement`, and `judge` has that one production caller. The checkpoint store and recovery accounting correctly preserve supplied identities. Changing storage, refunding all interrupted attempts or filtering them during recovery would weaken real interrupted-work accounting.

**Smallest correction and burden.** Relocate the existing check admission acquisition into the prepared requirement's invocation boundary, before budget spend and durable begin, retaining its permits through execution and settlement. Remove the later duplicate acquisition from `judge`; do not acquire twice. Reuse the current `admit` run-before-shared ordering. Preserve settled/missing-evidence fast paths, Agent-only charging, non-Agent checks, accepted begin before external dispatch, typed Busy/unavailable forget behavior, original deadlines and cancellation. This is a local ordering correction in the existing owner, with one focused checkpoint regression. No marker, second budget, durable schema, scheduler, SDK behavior or refund protocol is earned.

**Focused closure proof.** At the existing engine/checkpoint test seam, control one slow code check holding the only run permit and poll the sibling Agent check into its wait. Before interruption assert no begun record and no executor call for the waiter. Restore that accepted state with the one-invocation cap; the Agent must execute once after capacity frees. Keep the existing genuinely dispatched/interrupted-action budget assertions. The existing `agent_budget_counts_retries_and_is_never_replenished` proves dispatched retries, check charging and active-action recovery, but not this waiting-check state; `waiting_blocks_release_unrelated_permits` proves permit ordering, not durable accounting. One controlled check test is enough; no provider/server journey is needed to prove the local gap.

### FIND-003-2 — Nested Busy propagation abandons already-dispatched sibling checks

**Status:** CONFIRMED. **Discovery:** CONC-001. **Classification:** INCORRECT.

**Violated obligation.** REQ-008 requires capacity refusal to defer without spending an attempt and recovery to conserve accepted work/budgets; TASK-003 extends the same action/check settlement path to every member. The existing engine's Busy contract at `engine.rs:873–876` and `settled` at `:2148–2162` explicitly preserve dispatched siblings before deferral. The reported defect violates that existing behavior at a newly nested owner.

**Exact source and producer-to-consumer proof.** `member` (`engine.rs:1287–1413`) settles its action, then awaits `instance_requirements`. That function (`:1422–1449`) collects concurrent requirement futures in its local `Tasks`, but consumes each completion at `:1441–1444` with `result?`. A Busy requirement first forgets its own refused producer (`:1503–1505`), then the question mark returns from the inner function and drops its other futures. `Tasks` owns those futures in a Vec (`crates/vala/vala-verify/src/walk.rs:95–165`); dropping the set cancels them, and the earlier accepted begin records remain unsettled. Outer `members` (`engine.rs:1268–1270`) and `drive` (`:970–971`) both use Busy-aware `settled`, but cannot drain futures already destroyed inside `instance_requirements`. The runner maps Busy to Deferred (`crates/wyrd/wyrd-server/src/verification/runner.rs:1705–1710`), then recovery reuses the settled action and treats the cancelled sibling check as an interrupted invocation.

**Reachable consequence/materiality.** An ordinary successful code step has two independent checks. Its first Agent check is admitted and waits for its provider; a sibling code/Agent check encounters the process workspace/sandbox capacity refusal. With sufficient engine permits both checks can reach their hosted owners concurrently. The inner Busy return cancels the first check although its own capacity never failed. On reclaim it must be dispatched again and charged again; a one-Agent-invocation ceiling can instead refuse it permanently. This is avoidable loss of dispatched work on an ordinary admission refusal, distinct from an actual worker crash. FIND-003-1 does not close it: even correctly admitted/charged siblings would still be dropped by this consumer.

**Smallest correction and burden.** Use the existing Busy-aware `settled` handling when the inner requirement owner consumes its completed result, so its still-owned siblings commit before the Busy is propagated. Keep normal non-Busy error behavior and outer cancellation/deadline ownership unchanged. A downstream drain cannot repair dropped futures; adding a new task registry/retry policy/store is unnecessary. The correction is one existing-owner call pattern plus a focused regression; do not broaden `settled` to new error families or redesign fanout.

**Focused closure proof.** One already-settled code action, a controlled running Agent check, and a sibling capacity-refused check suffice. Assert Busy is not returned before the running check is allowed to finish and accepted settlement exists; the refused check's attempt is absent. Restore that checkpoint: only the refused check executes, and the settled Agent check spends no new invocation. Existing `capacity_refusal_stops_the_execution_without_judging` covers a single check; `capacity_refusal_lets_dispatched_work_settle` covers outer action/member siblings. Neither tests this inner owner.
