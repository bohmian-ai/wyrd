Fixed `ResponseTemplate::set_delay` cannot prove event ordering. Existing GC `PacedUpstream::start/answer` (`:447–565`) owns preconstructed completion/SSE payloads, frame timing and bounded send-time observations; it does not execute these existing wiremock request/turn scripts or forward them. Extending it to run these scripts would couple stream-capacity behavior to a separate forwarding/hold workflow and would still need that workflow. Deleting the explicit hold mechanism restores the diagnosed nondeterministic proof.

`HeldUpstream` is a narrow test-only extension beside that owner: it forwards to existing scripts and preserves recording, then watch-gates chosen responses by body fragments. Rust SDK and MCP share it. Installed axum/reqwest/watch suffice; no generic scheduler, replacement model-script framework, new dependency, server API or persistent state is earned or added. Python extends the existing threaded Event responder pattern; TS extends the existing Receiver callback to a promised Reply instead of building another server. HTTP forwarding need only preserve the local scripted provider's status/body/content type; no production streaming/header contract is claimed.

Success paths release all selected holds before waiting for the final result; Python and TS also release in `finally`. TS Receiver still closes all connections during teardown. A currently held response is therefore ultimately bounded by the test runtime teardown, rather than proven force-closed synchronously by `HeldUpstream::drop`. This creates no demonstrated required-behavior failure in current callers: they own the fixture for the entire isolated test runtime and release holds on successful paths.
