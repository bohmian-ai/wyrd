## Proposed material findings

### SYS-REPO-LEASE — INCORRECT: repository work outlives its lease and continues consequential work after reclaim

**Obligation:** REQ-028 monotonic generations/supersession, REQ-030 one reconciled Check and no terminal regression, TASK-004's existing effect fencing and bounded provider/backlog/recovery requirements. Multi-replica operation is supported authority, not hypothetical deployment expansion.

**Locations:** `crates/wyrd/wyrd-server/src/verification/repositories.rs:70–71,327–435,921–930,1227–1248,1320–1329`; `crates/wyrd/wyrd-sql/src/queries/repository_reviews.rs:35–70,490–522,652–667,780–791`.

**Producer-to-consumer trace:** Both claims grant `LEASE_MS = 120_000`. `PullRequestIntake::process` passes no lease into `handle/review`; the lease is checked only when settling the delivery. Its trusted configuration/provider/declaration work has neither a complete-attempt deadline nor lease renewal/loss cancellation. Review admission and `supersede_repository_reviews` mutate by PR identity without testing the intake claim. `CheckPublisher::process` similarly watches only shutdown abandonment. Its remote write can follow arbitrarily much earlier IO; the false result from `mark_check_create_ambiguous` is discarded before create.

The pinned provider does not bound the *complete worker attempt* to 120 seconds. `github.rs:250–261` permits three 60-second requests and waits up to 60 seconds each; `exchange:1963–2014` retries reads/rate-limit refusals accordingly. One ordinary temporary provider outage is sufficient to cross the lease. The SQL reclaim statements then permit another replica to start while the old future remains active.

**Reachable system consequence:** Worker A reads PR head H1, then its pinned-base archive request experiences retryable delays beyond 120 seconds. The PR advances to H2. Worker B reclaims the delivery, reads current H2 and admits its review. A's archive succeeds and A resumes H1 admission; its unconditional supersession cancels B's newer review/execution. The eventual failed token-fenced *settlement* does not undo those committed side effects. The same cause permits an old Check attempt delayed in credential acquisition to resume after B has reclaimed and created its Check: the old claim's ambiguity-mark returns false, but A still sends create, producing a second remote run. SQL delivery fencing cannot undo remote effects. A delayed stale update can likewise send its previously captured running projection after another worker has delivered terminal state.

**Existing owners/sibling comparison:** `OperatorWorker::process` (`verification/operators.rs:495–501`) wraps the whole delivery attempt in a timeout; `RuntimeLimits` documents that the attempt timeout is shorter than its lease (`mod.rs:195–200`, defaults 30/45 seconds). The Verifier runner instead uses `LeaseRenewal`/`HeldLease` (`leases.rs:1–12,59–84,115–145`) to cancel on lost authority. ClaimLoop itself supplies neither mechanism. The only two new LeasedWork consumers are intake and publisher; both share this missing ownership boundary. No new scheduler, lock hierarchy or replacement execution queue is required.

**Smallest correction boundary:** Keep a repository attempt's consequential work inside its current claim lifetime, using the existing bounded-attempt pattern with a deadline safely preceding reclaim (including elapsed time since claim), and stop when claim fencing refuses an effect. Honor the boolean create fence. Apply the lifetime rule to both intake and Check publication, preserving durable retries, ambiguity reconciliation, separate verification/delivery responsibility and sibling service availability. Merely extending the fixed lease or adding a check after remote IO does not fix the producer. If renewable repository work is chosen instead, it must provide actual lost-lease cancellation and effect confirmation; this is not a request for an availability redesign.

**Focused closure proof:** Hold A after its old PR snapshot, make the SQL claim reclaimable, run B against a new head, release A, and assert H2 stays current/not cancelled and A cannot admit/supersede. Repeat around pre-create work and assert a stale ambiguity-mark refusal causes no create and only one external association exists. Exercise a slow retryable provider path through the complete attempt bound and assert unrelated repository work still succeeds. Existing fixture/server/SQL seams suffice; do not wait two real minutes or synthesize host load.

### SYS-CHECK-STATUS — MISSING: exhausted Check delivery is invisible on execution inspection

**Obligation:** REQ-030 explicitly requires “A terminal delivery failure is visible on execution status and does not change its verdict.”

**Locations:** `crates/wyrd/wyrd-sql/src/queries/repository_reviews.rs:832–865`; `crates/wyrd/wyrd-server/src/components/verification/service.rs:255–305`; `crates/wyrd-spec/src/verification/execution.rs:204–236`.

**Evidence and consequence:** A Check attempt error is retried by `CheckPublisher::process`; the tenth failed attempt sets only `repository_checks.delivery = 'failed'`, clears its next attempt, and stops claiming it. `get_execution` constructs its response from retained execution state plus the existing queue/Operator dispatch projection. It never reads the execution's repository Check delivery. The public execution shape has error/result and Operator dispatches, but no repository delivery projection. Thus a completed passed verification whose Check can never be delivered still returns exactly the completed success inspection, with empty Operator dispatches and no delivery failure. The repository Checks endpoint exposes failed delivery, but that separate endpoint does not satisfy the named execution-status requirement.

**Materiality:** This is the specified way a caller polling its execution learns that the independently retried external result failed to reach GitHub. Verdict stability alone satisfies only half the obligation. The available Check journey proves recovery from a small number of refusals, never exhaustion plus execution inspection.

**Correction outcome/burden:** Project the existing repository delivery control state into authorized execution inspection without changing lifecycle status or the retained verdict, and without adding another delivery store or retry owner. Reuse repository_checks and the existing execution inspection boundary. Resolve the precise response representation against the approved shared public contracts; if those fixed contracts prohibit any representation of this explicitly required outcome, route that contradiction to specification correction rather than silently treating the separate Checks endpoint as acceptance. This review does not invent an SDK-specific field.

**Focused closure proof:** Complete one ordinary repository execution successfully, exhaust its Check delivery attempts with deterministic provider refusals, and assert execution inspection exposes the delivery failure while preserving the same execution/result/verdict and without additional verification calls. The repository Check view should still report failed delivery.
