## 1. Repository bindings — RESOLVED

The existing owner is `wyrd.verification_bindings`, `queries/verification.rs::NewBinding/project_bindings`, and `VerificationBindingStatus`. It does **not** accept repository rows unchanged: migration `20260601000027_verification_bindings.sql:55-90` requires owner/subject Card UIDs, Service/Agent owner kind, one Trigger identity, and schedule/observations_ready/group_end activation. Its natural key includes exact Verifier UID. Repository branch identity instead needs tenant/host/repository/ref/Verifier family, with exact Verifier/configuration in a revision.

That mismatch earns an **extension**, not a parallel owner. The approved spec explicitly says extend existing bindings (`spec.md:119-122`, REQ-037 at `:827-850`); it already approves repository subjects and revisions. Extend the existing table with mutually exclusive Card/repository identities and repository activation/revision/digest/retirement fields and a repository natural key. Keep Card constraints conditional on the Card arm. Extend the existing projection/read contract with a typed repository arm; Card registration must retain immutable projection semantics. Repository reconciliation still needs its distinct update/retire behavior, housed with that binding owner. No fake Card/Trigger is necessary.

Actual paths:

The owner FK has no cascading delete. Repository retirement can retain rows in the existing table; Card-specific schedule/activity/group queries must continue filtering their own activation/owner arm.
