## Findings

### M-01 — DRIFT: new delivery scheduler duplicates the existing claim-loop lifecycle

Location: `crates/wyrd/wyrd-server/src/components/github/worker.rs:80`, `:96`, `:114`; runtime wiring in `src/verification/mod.rs:558`.

Rule: approved ownership amendment says GitHub delivery extends the existing dispatch owner; TASK-004 explicitly requires reuse of `ClaimLoop`/`LeasedWork`, bounded dispatch and cancellation, and excludes another scheduler. Maintainer style requires behavior to remain with its existing owner.

Evidence: `run` adds its own pass/sleep/stop loop, `pass` awaits each tenant's `next` serially, and `next` claims, processes provider IO and settles directly. Compare `verification/claims.rs:52` (`LeasedWork`) and `:108` (`ClaimLoop`), whose existing `run`/`claim_round` own capacity, fair tenant rotation, spawn/reap, stop-after-claim release and bounded drain. `OperatorWorker` already supplies domain-specific claim/process/settle behavior through this owner (`verification/operators.rs:183`, `:441`). The new worker receives only lease and polling durations from runtime construction rather than that shared lifecycle.

Consequence and maintenance cost: a slow provider call in tenant A prevents this worker from even starting tenant B during the pass; shutdown cannot reach the loop's cancellation select while A is inside `next`. Future fairness/shutdown fixes must be maintained in two scheduling implementations. This is a concrete loss of required unrelated-repository progress, not a preference for a shorter file.

Smallest correction: retain integration-specific delivery records, decoding, processing and fenced settlement, but remove the custom `run`/`pass` scheduling owner and adapt that work to the existing claim loop. Its present `pub(super)` visibility is a local module boundary to adjust, not justification for duplicating the lifecycle. Do not add a third generic worker framework or route GitHub work through failure-Operator semantics. GitHub-specific PR ordering/authority still needs its domain implementation; claim-loop reuse does not magically supply it.

Closure proof: one blocked provider operation while another tenant/repository progresses under bounded capacity, plus shutdown during claim/provider work showing existing release/drain semantics. Reuse the claim-loop test seam rather than build a second scheduler harness. Route to the repository automation successor if TASK-004 is narrowed.

### M-02 — INCORRECT: trusted-suite acquisition stops at a single-root Card graph, before required artifact acquisition

Location: `crates/wyrd/wyrd-server/src/components/github/automation.rs:150–180`, with downstream `:327–334`; existing owner evidence in `crates/shared/wyrd-loader/src/lib.rs:256`, `:333`, `:435`, and `src/order.rs:13–47`.

Obligation: REQ-035/038 and TASK-004 Scenario 2 require registered-only suites, multiple selected Verifiers, and transitive local artifact/Agent/Prompt imports. O-13–16 are one adoption outcome, not separate invitations to invent loaders.

Source-proven paths:

1. A valid root TOML containing only a registered Verifier produces no local `entries`. `trusted_configuration` nevertheless invokes `load_source_tree` with the empty slice. `finish_load` invokes `order_cards`, whose first branch rejects an empty tree. The error names no missing file, so `Files::wanted` is empty and adoption returns invalid configuration. The simplest advertised shared-Verifier journey cannot run.
2. Two independent selected local Verifiers are passed together to that same single-root Card graph loader. `order_cards` calls canonical `graph::pick_root`; independent roots are invalid Card composition even though they are a valid repository suite. A suite is not one synthetic parent Card.
3. For one local Verifier importing an Artifact Card, the acquisition loop ends when Card YAML resolves. `validate_tree` validates artifact manifests, not artifact source bytes. `build_source_tree_declaration_stages` later calls `collect_declaration_input`, where `resolve_regular_file` first asks for the artifact body. `declare_local` converts that missing-file diagnostic directly to `ConfigurationFailure::Invalid`; it never goes back through `Files::wanted`. A normal `policy/policy.md` which is not itself imported as Card YAML is never fetched, and its blob is absent from the supposedly complete trusted digest.

Proof gap: `source_tree_tests::tree` pre-inserts `policy/policy.md` (`lib.rs:719`), so its later stage/stamp assertions cannot establish the provider acquisition path. The Rust test named `trusted_target_configuration_reuses_shared_declaration` currently proves repository targeting/authorization, not the complete local suite/import journey.

Smallest correction: keep the existing bounded byte source, canonical reference traversal, Card graph loader and declaration-source collector. Treat each selected local definition as its own rooted Card graph; registered selections require no local graph load. Finish required source collection inside the existing missing-blob acquisition boundary before freezing the trusted digest or performing publication. Do not invent a suite Card, synthetic graph parent, parallel import traversal or separate artifact fetch service. The same loader diagnostics already identify the missing source; the current caller simply stops using them too early.

Closure proof: through the provider-backed adoption path, exercise a registered-only suite, two independent local Verifiers, and one local transitive artifact graph whose body was not preloaded. Assert fetched base-commit bytes, active declarations/publisher attribution and a digest change when only the artifact blob changes. Preserve complete-suite refusal before admitting any member. Route to the trusted-configuration successor if TASK-004 is narrowed.
