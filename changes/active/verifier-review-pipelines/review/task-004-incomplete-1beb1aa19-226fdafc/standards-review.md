## Material proposals

### STD-01 — VIOLATION — enforce tenant-qualified durable parentage in the GitHub SQL owner

Authority: security §Postgres tenant binding requires tenant rows to reference `platform.tenants`, and tenant children to carry tenant-qualified foreign keys to their parents. RLS is not a replacement for referential integrity.

Locations: `migrations/20261109000000_github_app_connections.sql:21-22,62-65`, `20261109000200_github_repository_bindings.sql:15-20`, `20261109000300_github_deliveries.sql:13`, and `20261109000400_github_checks.sql:12,22,35-36` (all beneath `crates/wyrd/wyrd-sql/`). The migrations give connection/setup principal IDs no parent FK; bindings' `verifier_card_uid` has no Card FK; Check `execution_id` has no execution FK and its repository has no repository FK. New binding/delivery/Check tenant columns also omit the explicit tenant FK required by the authority. Some ancestry is transitively protected (binding→repository→tenant), but deliveries have none.

Source-proven scenario: `record_check(&mut TenantConn, &NewCheck)` accepts an existing local binding paired with any non-null execution UUID. The database accepts an execution belonging to a different tenant or no execution at all: the only FK is `(data_tenant_id, binding_id)`. Similarly, `reconcile_bindings` accepts arbitrary Verifier UUIDs, and connection rows can retain principals without tenant-qualified parentage. Supported workers write through these APIs; this is a mandatory integrity gate, not a claim that the current browser handler already permits an exploit.

Consequence: durable provenance can name a foreign/missing parent even while each row passes RLS. Correct the migrations at the SQL owner using existing tenant-qualified targets (`auth_service_accounts`, `auth_users`/owning principal representation as appropriate, `cards`, `verifier_executions`, `github_repositories`) and explicit tenant FKs. Preserve intended retained provenance/deletion semantics; do not add a second application authorization model. If migrations have been applied, use a later migration. Focused PG assertions must reject foreign/missing principal, Verifier and execution parents and allow valid same-tenant rows. This is one schema correction boundary, not one finding per column.

### STD-02 — VIOLATION — trusted artifact import fails on supported cloud storage

Authority: root locked deployment/platform rules require one behavior across supported deployments; design §Heavy artifacts requires the normal predeclaration/upload/completion lifecycle.

Location: `crates/wyrd/wyrd-server/src/components/github/automation.rs:423-449`, specifically `435-438`. `declare_local`→`declare_stage` declares the selected graph, receives upload plans, then rejects every plan other than `UploadPlan::LocalFs` with `WYRD_GITHUB_503_UNAVAILABLE`. The new helper `components/storage/routes.rs:486` writes through `upload_local_blob`, so it cannot fulfill cloud plans.

Scenario: a team on a supported object-storage deployment selects a local Verifier importing an Artifact/code source. Trusted loading and declaration succeed, then upload deterministically returns 503. The delivery worker retries and eventually settles unprocessed; the identical repository works with local storage. This affects ordinary approved local graph imports, not an unusual optional backend.

Correction: route imported bytes through the existing storage backend/upload owner for each supported plan while preserving authorization, manifest identity, completion and inventory recording. Reuse existing `StorageHandle`/upload lifecycle rather than introducing a parallel importer or HTTP self-call. Prove one artifact-bearing repository declaration against the existing cloud emulator lane plus the local path. The mandatory behavior cannot be waived by the explicit shortcut comment.
