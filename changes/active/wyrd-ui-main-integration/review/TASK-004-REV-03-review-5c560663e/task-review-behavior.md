## Proposed findings

### BEH-1 — INCORRECT: password JSON rejections escape the stable public error contract

**Obligation:** Task Public contracts requires all new invalid wire values to use the existing validation problem; spec revision19 explicitly retains JSON/problem+json and strict schemas. Root agent-surface/error rules require stable errors.

**Location:** `crates/wyrd/wyrd-server/src/auth/browser.rs:579`, `:625`, `:675`, `:729`; shared password DTOs in `crates/wyrd-spec/src/auth/browser.rs`.

**Producer → consumer:** All four DTOs deny unknown fields and require secret strings. A client submits a valid-origin password request with an extra field, a missing password, a null password or a boolean password. Bare `Json<T>` extraction rejects it before the handler executes, so `WyrdErrorResponse` and the existing `http/error.rs::body_rejection` mapper never run. This is Axum's JSON rejection response (for data-shape mismatch, 422/plain text), not the published `400 WYRD_SPEC_400_VALIDATION` problem. No response conversion layer was found for successful extractor rejection responses; tower error conversion is for tower errors and does not cover this path.

**Consequence/materiality:** A real HTTP/agent caller cannot interpret these invalid inputs using the approved stable error protocol. This is an explicit public-boundary obligation, not a preference for a different private handler signature. Existing new invitation and credential handlers already correctly retain the JsonRejection and call the shared mapper.

**Smallest correction/proof:** Reuse that existing boundary mapper for these four new operations without changing SSO/recovery contracts. Test wrong type, unknown field and missing required secret against actual HTTP, asserting status400, problem+json and stable validation code; no secret values in diagnostics. No new abstraction or dependency is needed.

### BEH-2 — MISSING/INCORRECT: the password forms omit reveal and constrain a different character unit

**Obligation:** Task Local signup explicitly requires password-manager autocomplete/paste, visible policy explanation and an accessible reveal control; policy is 15–128 Unicode characters after NFC, case/spaces retained.

**Location:** UI `src/routes/t/[tenantKey]/login/+page@.svelte:15`, signup `+page@.svelte:16`, reset `+page@.svelte:14`, account `+page.svelte:62–64`; shared `Entry.svelte` renders snippets but provides no reveal behavior.

**Failing scenario:** Every password remains a fixed `type="password"` field with no button, toggle state or accessible reveal action in any of its owners. A reader using a long passphrase cannot perform the explicitly required reveal action. Signup/reset/account additionally impose native `maxlength="128"` and `minlength="15"`, whose HTML length unit is UTF-16 code units; server policy uses normalized Rust `.chars().count()`. A password containing 65 supplementary Unicode characters fits the raw-byte ceiling and server maximum, but the new-password forms cannot accept its full value through ordinary typing/paste. Conversely, decomposed input can be rejected before the server normalizes it.

**Consequence/materiality:** Missing requested accessibility/usability behavior and a client restriction on explicitly valid chosen credentials. The ordinary production password workflow reaches these exact forms; this is not speculative parser hardening.

**Smallest correction/proof:** Add a keyboard-accessible named reveal action at the existing password form owner(s), preserve autocomplete/paste and case/spaces, and ensure browser bounds do not preempt the server's Unicode/NFC policy. Reuse a current local control if available; no form framework is warranted. Browser proof should reveal/conceal without changing value, use the control by keyboard, and submit a supplementary/decomposed password accepted by Rust. Keep server validation authoritative.

### BEH-3 — INCORRECT: the BFF strips retry information from password throttling

**Obligation:** Task rate refusal is stable429 with retry information, and forms forward the typed Rust-owned password workflow truthfully. Security authority browser-session section specifies 429 and Retry-After.

**Location:** UI `src/lib/server/auth/browser-sessions.ts::refuse`, `src/lib/server/problem.ts::problemKind/safeProblem`, login action, `Entry.svelte`; generated `crates/wyrd-spec/schemas/ui_problem_examples.json` passwordAttempts entry.

**Producer → consumer:** `Windows::admit` creates `PasswordAttempts` with the actual remaining `retry_after_seconds`; Rust HTTP mapper adds `Retry-After`. BFF `refuse` reduces the response to a problem kind, `reject` constructs the static generated example, and `safeProblem` constructs it again. The example's details are `{}`. The login action returns `fail(429,{problem,username})` without the retry header. Entry renders remediation literally: “Wait `details.retry_after_seconds` until the fixed attempt window ends, then try again.” It renders neither a value nor a calculated delay.

**Consequence/materiality:** An ordinary user hitting the expressly supported failure window gets a variable placeholder and no usable retry time, despite Rust supplying one. It affects both repeated login and password-change refusal through the shared BFF path.

**Smallest correction/proof:** Preserve the approved numeric retry metadata/header through the existing safe error projection, using an allowlisted numeric field rather than forwarding arbitrary diagnostics. Render the actual retry duration. Extend the existing BFF/browser negative test to exhaust the fixed window and assert429 plus useful retry data without credential echo. No second limiter, timer service or state store is needed.
