## Proposed findings

### INV-1 — Read-only admission allows an arbitrary queued burst past the account/source failure budget

- Classification: **INCORRECT**; security/availability boundary.
- Violated obligation: specification revision 19 Abuse and recovery and task Bound password work and guessing require shared, atomic 10/account and 100/source fifteen-minute admission before KDF work on every verification path. Security posture states further attempts are refused with 429 after the failure threshold.
- Exact locations: `crates/wyrd/wyrd-auth/src/passwords.rs:534-548`, `608-624`, `738-768`; `crates/wyrd/wyrd-sql/src/queries/auth/local_passwords.rs:227-248` and `258-286`.
- Producer-to-consumer proof: login and password change call `Windows::admit`; that method only SELECTs existing failures. The transaction commits before `check_password` acquires a KDF permit. A wrong-password result counts failure only afterward in a fresh transaction. Start many requests for one username/source before any derives finish: all read fewer than the limit, then wait behind four KDF permits and continue running even after preceding failures exhaust the window. Atomic increment prevents lost counts, but does not bound verification admission. Multiple replicas multiply simultaneous work and share the same defect. No consumer rechecks or owns a reservation.
- Observable consequence/materiality: the explicitly approved guessing budget can be exceeded by an arbitrarily large queued burst, which also keeps password KDF work running after the account/source should be throttled. This is ordinary concurrent unauthenticated login traffic, not an unusual schema-only input.
- Siblings inspected: password change repeats the same read/commit/verify/refuse sequence; a new login for key creation is ordinary password login; unknown/missing/suspended credentials use this same path for known tenants. Counter producers are confined to `Windows::refuse`. Signup/reset derive a new verifier and are not current-password verification paths.
- Smallest correction boundary: fix shared password-window admission at its producer so one bounded attempt is atomically admitted against both current budgets before it can consume verification work, across replicas and through cancellation; preserve fixed deadlines, generic refusal, success/failure accounting, and the existing SQL/BrowserSessions ownership. A second route-only check or process-local lock cannot fix cross-replica queued admission. The task already requires atomic cross-replica limits; no new auth service is warranted.
- Focused closure proof: deterministic concurrent admission at the last available account slot, and the equivalent shared-source/different-account case, must bound accepted verification work and return stable 429/Retry-After for excess attempts. Exercise login and the shared change path, and expiry recovery. Existing V2's ten sequential requests do not falsify this race. Do not generate host load; use controlled synchronization around the existing owner in tests.

### INV-3 — Cancellation returns KDF capacity before the blocking derivation releases its resources

- Classification: **INCORRECT**; explicit bounded-work invariant.
- Violated obligation: the approved password policy/task caps KDF operations at four per process, including failure paths. Root guidance requires resource ownership to follow actual work.
- Exact location: `crates/wyrd/wyrd-auth/src/passwords.rs:228-235` (`bounded`). Reachable cancellation owner: `crates/wyrd/wyrd-server/src/http/router.rs:122-143` merges auth into the protected edge; `http/middleware/edge_timeout.rs:143-180` drops the handler future on timeout.
- Producer-to-consumer proof: `_permit` lives in the async `bounded` future, while `work` is moved into a distinct `spawn_blocking` task. Dropping the handler releases the permit immediately. It does not stop already-running blocking work. Installed Tokio documentation confirms this (`tokio-1.53.3/src/task/blocking.rs:106-120`), and awaiting the join does not transfer ownership of the permit. A later request takes the released permit while the previous Argon2 allocation remains live; repeated timeouts/cancellations admit more than four jobs. This also applies to new-password hashing in signup/reset/change and dummy-verifier/rehash work through the same owner.
- Observable consequence/materiality: the server's explicit CPU/memory concurrency bound can be exceeded precisely during timeout/overload handling, affecting other tenants/capabilities in the shared process. The supported request-timeout path establishes reachability without assuming that every client disconnect cancels an Axum handler.
- Smallest correction: transfer the existing permit into the blocking closure and retain it through completion of `work`; the static semaphore can supply a permit with the needed lifetime. Do not introduce a worker service or dependency. Keeping the permit in the caller or merely aborting the join handle does not preserve the invariant.
- Focused closure proof: a small in-module test using controlled blocking closures should occupy all permits, cancel their async waiters, and assert a fifth closure cannot begin until one original closure releases its work. No synthetic host load or long real Argon2 timing test is needed.
