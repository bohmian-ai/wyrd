## Material finding

### DATA-01 — Index suppression drops supported native Run contexts

Classification: **INCORRECT / REGRESSION**, medium severity. Changed correction boundary: `tables/metrics/series.rs:492–543` and `scribe/series_index.rs:178–197`.

**Violated obligation.** REQ-058 requires promoted/attribution columns with the same meaning as the point; REQ-060 requires index reads under the same WHERE. Bifrost's existing native correlation contract permits a `run_id` column independently of OTLP attributes. The new index cannot silently discard that supported context while durable points retain it.

**Supported producer-to-consumer path.**

1. Public Rust `Bifrost::write_batch` (`crates/shared/wyrd-client/src/bifrost/facade.rs:760–797`) sends a batch verbatim against a described table, expressly delegating contract enforcement to the server. Python `AsyncBifrost.write_batch` (`sdks/wyrd-sdk-python/python/wyrd/bifrost/_client.py:1230`) exposes the same supported native workflow. This is a first-class canonical write path, not an unused parser branch.
2. The writable-description journey explicitly treats `run_id` as a writer-supplied correlation column (`crates/wyrd/wyrd-testing/tests/bifrost/scribe/describe.rs:94–142`). Gate's native dispatch (`gate/mod.rs:1056–1118`) passes the IPC to Scribe, and `execution_lanes.rs::caller_run_id_column` (`1208–1226`) preserves its Utf8 values without requiring a matching `wyrd.run_id` attribute. `stamp_correlation_columns` installs that admitted correlation separately from user columns.
3. Write the same ordinary canonical gauge and unchanged resource/scope/point attributes in one UTC hour for two application Runs A and B, using distinct batch IDs and native `run_id` A/B. `series_ids` hashes the explicitly specified identity fields, excluding `run_id`, so both points correctly share a series id. Both native inputs are supported and both points persist their distinct Run correlation.
4. `series_rows` asks once per `(hour, id)` (`series.rs:532–543`), copies only its first row, and the process `SeriesSeen` check suppresses the later batch's same pair (`series_index.rs:182–183`). This also drops the second context when A/B occur in one batch. The index keeps only A; no B row is produced.
5. `SIGNALS.metrics.filters` includes `run_id` (`wyrd-ui/packages/ui/src/lib/schemas.ts:103,147–153`). `metricNamesQuery` filters the series index directly (`observe.ts:900–907`), and group-key/series-label reads use the same index predicate (`552–584`). Selecting Run B therefore presents an empty rail/pickers despite durable matching metric points. This is loss of queryable index coverage, not point data loss.

**Sibling producers and common cause.** OTLP projection obtains Run correlation from retained record attributes (`metrics/projection.rs:763`), so changing `wyrd.run_id` there already changes the series id. Native correlation does not have that property. Workload, environment and registry-derived dimensions can also be stamped after series-id derivation; `execution_lanes.rs::stamp_dimensions` (`1355–1408`) shows those columns are not universally fixed by the hashed attribute sets. The common cause is treating the attribute-derived series identity as proof that all copied query dimensions are fixed. It affects both the within-batch distinct-key set and cross-batch process cache; changing only one does not repair it.

**Authority contradiction and smallest correction.** The new spec/Bifrost paragraph asserting that every copied column is fixed because correlation comes from point attributes is valid for OTLP correlation but contradicts existing native writes and accepted envelope stamping. Preserve the documented `series_id` encoding and existing native/OTLP correlation semantics. At the series-row production/suppression owner, retain a row for each distinct admitted queryable context of a series/hour, and suppress only repeats whose copied query dimensions agree. Continue to aggregate reader totals by `series_id`, retain the bounded cache and series-before-points durability order, and include the same context discrimination in deterministic derived-batch identity where necessary. Update the inaccurate authority statement with that behavior.

This changes the index's stated logical granularity from one context per series/hour to coverage of the contexts actually admitted for that pair. It is a persistent index-semantics correction, not merely replacing a private cache implementation. The caller explicitly authorizes potential spec deviations, so no new approval gate is proposed. Adding correlation to `series_id` would instead change the approved stable point identity and is unnecessary. Removing native correlation support would regress existing clients. Disabling dedup and indexing every point would violate the approved series-scaled cost requirement. The smallest safe boundary is the existing row/key production plus its cache/batch identity, without new schema columns or a second index service.

**Focused proof.** Through existing native SDK ingestion, write identical canonical metrics in the same hour with independent run_id A/B, both within one batch and across two batches. Assert identical stored series ids, both point correlations, index visibility under each run predicate, and non-empty filtered rail for each. An exact context repeat must still add no index row/sync; restart/retry and failed-series-before-points behavior must remain intact. Extend the existing persistence/metrics journey fixtures rather than introducing a new harness. No source edit or reproducer was introduced during this immutable review.
