## Deployed topology and failure propagation

Production Scribe owns a fixed set of Tokio shard tasks and bounded Rayon execution lanes. A shard writes slices and COMMIT records, awaits its WAL sync, then follows the existing optional SQL fence, hot insertion and acknowledgement path. Request cancellation does not cancel admitted shard work; async-owner abortion does not cancel an already-submitted Rayon filesystem job. These are the previously identified reasons an outer-future drop was insufficient proof.

The candidate adds no normal-production execution branch: the held observation lives inside the existing `cfg(any(test, feature = "test-support"))` fault branch; watch subscription, retained-join extraction and abort-and-settle helper are `cfg(test)`. With test-support enabled but the fault unarmed, the normal branch is unchanged. With the fault armed, the same flag is consumed at the same post-sync point, the same group is retained and the same error returned. New work only copies held slice identities and publishes them after ownership moves; it neither acknowledges nor inserts nor retries the group. No permission failure or component error is promoted into a shared-server outage.

The two fixtures use `new_for_embedded_with_deps` → embedded configuration with `persistence: None`. There are no persistence worker owners, server background scanners or independent admitted clients in these tests. Replay is awaited before the admission under test begins. The original ingest future is the sole active ingress request; after the selected group is held, the helper drops it before stopping shard owners. The barrier is accepted for these concrete callers, not claimed as a new generic production process-shutdown API or persistence-worker join contract.

## Adversarial checks and materiality

Challenged whether watch publication fabricates a hold, precedes the durable operation or loses the response race. It is sequenced after the existing awaited sync and after retained ownership is installed; it is not the earlier AtomicBool swap. `send_replace` retains the value even if subscribers have not polled yet. The subscriber is installed before ingress is driven; fresh WalWriter faults start empty in each test. The prepared ACK sender survives in the retained state and no sibling admission in either fixture can trigger retry before the helper stops the owner. The new hook therefore observes rather than changes the production fault path.

Challenged whether taking joins drops abort authority, whether all started shard owners are included, whether lane completion can outlive the barrier, and whether an embedded persistence/background producer can submit later WAL work. Independent abort handles are preserved; every started shard is in the taken join vector; close + join precedes drain; execute_wal_io's filesystem work precedes its depth decrement; embedded constructors disable persistence and the fixture has no background producer. Ignoring JoinError does not permit a live task: both cancellation and panic are terminal JoinHandle outcomes. These facts close the prior lifecycle gap for the actual tests.

No new blocker, data-loss allegation, broader crash matrix, subprocess harness, second restart or storage-tier requirement is justified. One restart remains the explicit fixture limit accepted by the prior persistent-data review; ordinary production persistence/fence behavior is not newly established by this fixture.
