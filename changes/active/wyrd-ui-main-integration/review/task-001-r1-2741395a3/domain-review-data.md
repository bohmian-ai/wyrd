## Proposed finding

### DATA-001 — Logout can revoke a different tenant's session under the selected tenant's label

- Classification: **INCORRECT** (tenant-binding violation).
- Obligation: REQ-033 requires logout to revoke only the selected tenant browser session; cookie labels never establish tenant authority. Security posture likewise requires the selected tenant session only.
- Changed location: `crates/wyrd/wyrd-server/src/auth/browser.rs:498–500`; authority mutation owner `crates/wyrd/wyrd-auth/src/browser_sessions.rs:283–301`.
- Reachable path: obtain live sessions for tenants Acme and Beta. Send a same-origin `POST /auth/browser/logout` body `{"tenant":"acme"}` with `Cookie: wyrd_session_acme=<Beta's valid cookie value>`. Parsing supplies label Acme, so the handler calls `sessions.logout(value)`. That owner parses Beta's UUID from the value, opens Beta's `TenantConn`, and `revoke_browser_session` updates Beta's exact digest before commit. The response clears the Acme cookie. Subsequent ordinary Beta session resolution is refused even though Beta was not selected.
- Source proof: handler matches only the untrusted label against `request.tenant`; `BrowserSessions::logout` accepts no expected tenant and routes exclusively by `cookie_key`. RLS correctly scopes the resulting mutation to Beta; it cannot repair the earlier wrong tenant selection. This does not grant an attacker access to a session they do not possess; the observable violation is a logout naming one tenant mutating another presented tenant's durable session.
- Shared-owner/caller tracing: the HTTP logout handler is the production caller of `BrowserSessions::logout`; the UI reaches it via the existing auth forwarder. `live_view` verifies the resolved tenant against the label before metadata is returned, and `recover_in` already resolves the selected route slug and compares it to credential-established tenancy. The SQL revoke helper has one production caller, the lifecycle owner, and correctly uses RLS/digest. Neither SQL nor all read consumers need extra filters or guards.
- Smallest testable correction: enforce selected-route-to-cookie-tenant agreement at the logout lifecycle boundary before opening the revocation transaction, reusing the existing tenant route resolver as recovery does. Pass the selected tenant route key to that owner; malformed/unknown/mismatching values must revoke nothing while preserving idempotent cookie clearing and store-unavailable behavior. Do not require full current-principal/connection authorization merely to logout, and do not add manual SQL tenant predicates, new persistence or session machinery. This keeps the correction on the producer of the wrongly scoped mutation.
- Focused closure proof: extend the existing server/Postgres browser-session authority test to present Beta's live value under the Acme label, logout Acme, and then prove Beta's correctly labeled cookie still resolves and Acme's independent session remains unchanged. Keep the existing normal logout/key-survival assertions. Run through the repository-managed Postgres wrapper using the already registered exact selector:

```sh
mise exec -- scripts/postgres/with-test-postgres.sh -- cargo nextest run --locked -p wyrd-server --test integration -E 'test(=pg_browser_sessions::browser_session_authority_is_tenant_bound_and_revocable)'
```

This scenario is absent from the current test: its mislabeled-value cases target metadata reads, while logout uses only a correctly labeled Acme value.

## Concurrency and failure conclusions

A resolve already in progress may read authority before a simultaneous logout or revocation commits; it can finish as an in-flight authenticated request. The source provides next-request revocation and no token/permission cache, and approved authority does not require cancellation of admitted requests. I found no basis to demand request-long locks or a new revocation protocol. Logout's single-row update/commit cannot revoke sibling rows through SQL itself. Cancellation before commit rolls back; cancellation after committed creation can leave a harmless unreachable session until absolute expiry if the response cookie was not delivered. Callback cancellation after state consumption requires a fresh login, as documented.

The new schema is additive and does not rewrite/delete historical OAuth records. Sessions survive Rust/Node replacement because neither process owns the durable authority or an encryption secret needed to recover it. This source conclusion does not stand in for the required deployed restart execution.
