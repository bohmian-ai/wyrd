## Material proposed findings

### SEC-1 — INCORRECT: enumeration failure becomes successful stale signed-in metadata

- **Obligation:** REQ-033 metadata enumeration and current authority; security posture: store failure refuses the whole request and cannot become cached success.
- **Location:** `crates/wyrd/wyrd-server/wyrd-ui/src/lib/server/auth/browser-sessions.ts:262` (`BrowserSessions.metadata`), called by `src/routes/t/[tenantKey]/+layout.server.ts:11` after hooks resolve the selected session.
- **Producer → consumer:** Hooks successfully resolve the selected cookie. The tenant layout then asks Rust to enumerate all session cookies. Rust correctly returns `503` if resolving any cookie encounters a store failure, with no partial metadata. Node substitutes `[]` for every non-success response and unconditionally constructs a successful response containing the earlier session's subject, expiry and tenant. A `401` after revocation between these two calls follows the same stale-success path, even after the returned deletion cookie is relayed.
- **Observable consequence:** A protected layout renders signed-in identity/tenant metadata when the server explicitly refused the current enumeration. Other tenant availability is silently falsified; on a current-tenant revocation race the page still presents the revoked session as signed in. Subsequent API authorization still runs in Rust; this is not a write-permission bypass.
- **Smallest correction:** Keep the existing one enumeration call and cookie relay; propagate non-success using the existing `refuse`/problem mapping instead of manufacturing an empty successful response. Construct selected identity metadata only from an accepted enumeration. No cache, retry, new session owner or extra authority query is needed.
- **Focused closure proof:** Extend the existing UI browser-session unit test owner with an already-resolved selected session followed by enumeration `503` and `401`; assert rejection with the appropriate existing safe problem, no successful metadata, and preservation of cookies on `503`. Retain the live multi-tenant enumeration behavior. Run that focused test through the repository mise/pnpm runner. Root was asked to coordinate execution; no service/build mutation was started here.

### SEC-2 — INCORRECT: post-consume backend failure is presented as refused credentials

- **Obligation:** REQ-033: store outage is an unavailable error distinct from invalid/expired/revoked authority; existing stable error semantics must survive the browser adapter.
- **Location:** `crates/wyrd/wyrd-auth/src/callback.rs:233` converts every browser completion error into `LoginCompletion::Refused`; `crates/wyrd/wyrd-server/src/auth/browser.rs:283–300` (`login_refused`) then collapses it into `/login?login=failed` whenever the directory lookup succeeds.
- **Producer → consumer:** The browser state is consumed successfully. A later current-authority read/session insert/commit fails and maps to `AuthVerifyUnavailable`. The browser conversion retains that error internally, but the HTTP adapter discards its classification after a successful subsequent directory lookup. The redirected login page maps `login=failed` only to `unauthenticated`. A statement-specific/transient store failure followed by a healthy directory read is sufficient; total permanent database failure is not needed. The provider-unavailable error path is collapsed by the same branch as well.
- **Observable consequence:** The user receives a refused-sign-in flow instead of the required backend-unavailable error; a caller cannot distinguish a valid login interrupted by the store from rejected identity. No session is accepted through this path.
- **Smallest correction:** Preserve genuine sign-in-refusal redirects, the spent-state semantics, audit staging and cookie clearing. At the existing browser response adapter, preserve unavailable/server failure classification as the corresponding existing Wyrd error response rather than mapping all failures to `login=failed`. Do not retry the consumed transaction or move provider verification into Node.
- **Focused closure proof:** Exercise the existing browser callback response adapter with a known tenant and `AuthVerifyUnavailable` after a consumed transaction while directory lookup is healthy; require the existing unavailable status/code, no sign-in-refusal redirect, no session cookie, and cleared transaction cookie as applicable. Keep existing invalid-state/nonce/issuer/binding/provider-denial flows and CLI/device/provider-test responses intact. This is a focused response/failed-completion test, not a new full provider suite.
