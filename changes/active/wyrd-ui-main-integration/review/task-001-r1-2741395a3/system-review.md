## Proposed material findings

### SYS-R1-001 — INCORRECT: metadata enumeration converts refused/unavailable authority into successful stale page metadata

Violated obligation: REQ-033 enumeration and current-authority rules; security posture requires store failure to refuse the whole request, and only live proved tenant metadata may be returned.

Location: `crates/wyrd/wyrd-server/wyrd-ui/src/lib/server/auth/browser-sessions.ts:257–269`, especially `:262–263`. Live caller: `src/routes/t/[tenantKey]/+layout.server.ts:11`; producer: request hook calls `BrowserSessions.read` before route resolution. All metadata callers were searched; this is the sole production browser metadata caller. Sibling `read` already rejects a 503 and treats 401 as dead; `logout` already reports refusal.

Reachable path: hook resolves tenant A, then the database becomes unavailable before the layout's all-cookie enumeration. Rust correctly returns 503; `metadata` substitutes `[]`, unconditionally seeds A from the earlier BrowserSession, and returns successful authenticated metadata. A concurrent logout/revocation between those reads similarly returns 401 (and clears the dead cookie), yet the layout continues displaying the stale signed-in tenant/principal. A successful enumeration containing only tenant B after A was revoked also reinserts A. This is not a privilege escalation in subsequent Rust API calls, which reauthorize, but it breaks the explicit unavailable/refused UI behavior and treats an unproved current session as live.

Smallest bounded correction: use the current enumeration answer as the metadata authority. Propagate its unavailable/non-success response through the existing safe error mechanism; require the selected current tenant to be among the live views and derive returned identity/expiry/tenant list from that view/set. If it disappeared, return existing unauthenticated behavior rather than falling back to a sibling or the earlier BrowserSession. Keep cookies intact on storage failure and retain invalid-cookie clearing. No cache, retry, new session endpoint or lifecycle change is needed; the existing Rust enumeration already owns this decision.

Focused proof: extend `browser-sessions.test.ts` to cover a prior successful `read` followed by metadata 503, metadata 401, and a 200 listing only a sibling after current-session revocation. Assert unavailable/authentication failure, no fabricated current tenant, and expected cookie preservation/clearing. Existing tests cover read and logout outages but never invoke metadata. A small HTTP-level layout check can prove the unavailable answer reaches the page; no database outage orchestration or broad identity suite is needed for this local forwarding defect.

### SYS-R1-002 — INCORRECT: failed container journey skips owned-resource cleanup

Violated obligation: remediation verification section requires guaranteed fixture cleanup; existing startup lifecycle must be preserved on failure/interruption.

Location: `scripts/server/test-startup-identity.sh:16`; inherited behavior: `scripts/server/startup-common.sh:5` enables `set -Eeuo pipefail`, and `cleanup` owns app/Postgres, volumes, network, image tag, temporary files and failure logs.

Reachable path: the identity nextest command fails (or any operation after trap installation exits nonzero). EXIT trap removes the forwarder and executes `(exit "$status")`; with errexit still active that nonzero subshell aborts the trap before `cleanup`. The common lifecycle therefore never collects app diagnostics or removes the app/Postgres, volumes/network/image/temp directory. A rerun can also fail on the retained fixed gRPC host port. `with-identity-providers.sh` only owns the providers, so its outer cleanup cannot settle these resources. Successful runs take the zero-status path and conceal this defect.

Nonmutating reproduction executed in this review: a `bash -c` process with the same shell options, EXIT trap sequence, `cleanup(){ echo cleanup-ran; }`, and `exit 7` printed only `forwarder-cleaned`, exited 7, and never printed `cleanup-ran`. No Docker/shared service was touched.

Smallest bounded correction: let the existing `startup-common.sh` cleanup run unconditionally with the original exit status after best-effort forwarder removal. Preserve its original failure logs and final status. Extend the existing cleanup owner only as necessary to accept/preserve status; do not introduce another fixture lifecycle controller. The trap must not execute a failing command under errexit before invoking cleanup.

Focused proof: exercise the trap with stubbed Docker commands and deliberate child exit 7, asserting forwarder and common cleanup execute and status stays 7; also assert success remains 0. This can be a small assert-based shell check with the existing owners, without live containers or image builds.
