## Proposed findings

### BEH-R1-001 — INCORRECT — Native forwarding strips the authority required by public browser-session operations

Obligations: REQ-004 preservation of browser auth cookies, REQ-033 browser session enumeration/logout, AC-003/012. Location: `crates/wyrd/wyrd-server/wyrd-ui/src/lib/server/upstream.ts:69–75`; ingress caller `src/hooks.server.ts:12`; consumers Rust `src/auth/browser.rs::session` and `logout`.

A successful native login sets `wyrd_session_<tenant>` at the BFF origin. A browser subsequently calling `GET /auth/browser/session` sends that protected cookie to the BFF. The hook forwards the request, but `forwardAuth` keeps only `wyrd_login`; Rust therefore sees no session and returns 401. A same-origin `POST /auth/browser/logout` is worse: Rust receives the body tenant but no session, returns 204 and clears the browser cookie, while the durable row remains live. A saved copy of the opaque session can still authenticate. nginx routes `/auth/*` straight to Rust, so the same operation has different semantics there.

The producer is correct (Rust creates/cookies a durable session); the defect is the generic `/auth/*` forwarder's new blanket cookie removal, before the Rust owner receives its authority. Node's internal `BrowserSessions::{read,logout,metadata}` calls correctly forward selected/all cookies for their operation, so the page-action happy path and current native journey can pass while the public typed endpoint is broken. Sibling `forwardAuth` callers are the single auth hook and its tests; no other native auth router repairs this. `upstream.test.ts` explicitly expects only the login cookie for a token request and lacks these public session/logout cases.

Smallest testable correction: retain server-owned session cookies when forwarding the Rust browser-session operations, preserving the existing login-binding forwarding and trusted-origin/header/manual-redirect behavior. Let the existing Rust endpoint own enumeration versus selected-session behavior and refusals. Do not add token exchange, a session store, or another transport owner. Extend the existing forwarder/native production test to log in, read `/auth/browser/session` at the actual BFF public origin, POST logout there with correct Origin, then prove the previous opaque cookie no longer authenticates through existing tenant session/API read. Include two-tenant enumeration and selected logout preservation. A unit test alone can prove forwarding; the native public journey proves durable logout.

### BEH-R1-002 — INCORRECT — Metadata failures become successful signed-in output from earlier request state

Obligations: REQ-033 says no sessions means refuse authentication and store unavailability fails the request; INV-002 prohibits cached success after a failed/denied live request. Location: `crates/wyrd/wyrd-server/wyrd-ui/src/lib/server/auth/browser-sessions.ts:262–269`; consumer `src/routes/t/[tenantKey]/+layout.server.ts:9`.

The production tenant hook first calls `read`, producing a request-local `BrowserSession`. The tenant layout then calls `metadata`, sending all presented session cookies to Rust for current enumeration. If the store fails between these reads, Rust correctly returns 503. If the selected session is revoked between reads and no other sessions remain, Rust correctly returns 401 and clears its cookie. `metadata` relays cookies but maps both answers to `live=[]`, then unconditionally re-adds the earlier session's tenant and principal and returns normal signed-in layout data. The former path hides the outage; the latter renders a signed-in page after the authoritative session read explicitly refused it. Network exceptions already reject through `call`; only HTTP refusals are converted to success.

All siblings were checked: `read` refuses non-OK status (401 is unauthenticated), `logout` propagates non-OK through `refuse`, and `begin`/recovery also refuse. The shared cause is `metadata`'s ternary fallback, not SQL/session authority or a new need for a cache. Its one production caller is the tenant layout; the plain signed-in page uses that layout and is reachable without a settings API that might separately fail.

Smallest testable correction: propagate metadata enumeration failures through the existing problem/auth refusal mechanism before constructing page data; do not synthesize a selected tenant when the authoritative response contains no live sessions. Keep normal per-tenant separation and cookie relay. Extend the existing BrowserSessions tests with successful `read` followed by metadata 503 and metadata 401, asserting rejection rather than signed-in metadata (and appropriate cookie preservation/clearing). Exercise the tenant layout refusal at its existing route test seam; no new harness or broad identity suite is needed.
