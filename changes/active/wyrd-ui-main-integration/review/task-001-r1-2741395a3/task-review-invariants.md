## Proposed findings

### INV-R1-001 — INCORRECT: metadata converts refused or unavailable authority into a successful signed-in response

Violated obligation: REQ-033 browser HTTP/current-authority rules; INV-002; security posture's first-party browser-session rule that store failure refuses the whole request and cannot become cached success.

Location: `crates/wyrd/wyrd-server/wyrd-ui/src/lib/server/auth/browser-sessions.ts:262–269`, `BrowserSessions.metadata`. Reachable caller: tenant `+layout.server.ts:11`; producer of its earlier session argument: `hooks.server.ts:20` via `BrowserSessions.read`.

The hook first resolves the selected tenant cookie. The layout subsequently calls metadata, which sends all presented cookies to Rust's enumeration endpoint. That endpoint can return 503 when any required store resolution fails, or 401 if authority expired/revoked since the first lookup. Its result is deliberately authoritative and distinguishable. Line 262 turns every non-OK response into an empty list, and lines 263–269 unconditionally reintroduce the prior selected tenant/principal/expiry. The page therefore renders successful signed-in metadata after an explicit current request refusal. In the 503 case it can also silently erase otherwise-live switch choices. The 401 case can relay a clearing cookie and still display that same session as authenticated in the response.

This does not assert that subsequent protected Rust writes become authorized: they still verify independently. The observed defect is successful stale authenticated page metadata after refused/unavailable live authority, directly prohibited by the selected contract.

Sibling inspection: `read`, `begin`, recovery and `logout` already propagate server refusal/outage; `metadata` has one production caller, the tenant layout. `BrowserSession.context` is produced from the earlier selected read; no Node cache or alternate authority owner should be added. Rust's `session`/`live_view` correctly propagate storage failures, so the cause is the metadata consumer erasing the authoritative result.

Smallest correction: at this existing BFF metadata response boundary, propagate non-OK refusal/unavailability using existing safe problem/refusal behavior after relaying the returned cookies. Only return tenants/principal from successful currently proved metadata; require the selected session still to appear when building its signed-in projection. Do not weaken Rust enumeration, introduce cached/anonymous fallback or duplicate the session resolver. Preserve live sibling tenant choices and cookie cleanup.

Focused closure proof: extend the existing browser-session test owner using its existing fetch stub/cookie jar: selected read returns 200, subsequent enumeration returns 503; metadata must reject as unavailable without clearing otherwise-live cookies or returning signed-in data. Repeat with 401 and its clearing cookie, proving authentication refusal and cleanup. A successful enumeration in which the selected session has disappeared while another remains must not re-add it from the earlier argument. Existing positive enumeration keeps every independently proved tenant, with no permission/principal merging. No new dependency or service harness is needed.
