## Approved obligation

REQ-033 says `POST /logout` revokes the selected tenant session and clears its cookie, and that logout immediately revokes only that browser session. The R2 task specifically preserves normal selected logout, absent/already-dead idempotency, unavailable behavior, and forbids requiring live principal/connection permission just to log out. The preceding validated FIND-8 likewise says not to prevent safe logout of otherwise dead authority. The task's recommendation to reuse recovery's slug resolver is a private mechanism prescription, subordinate to these behavioral requirements.

The consequence below does not require logout to grant access while suspended, invalidate all sessions on suspension, alter suspension semantics, or add an endpoint. It requires the existing possession-based logout to durably revoke the selected possessed identifier as promised. Existing metadata/API admission must continue to refuse suspended tenants.

## Complete disputed path

1. A valid recovery session is created while the tenant is active. `BrowserSessions::recover_in` authenticates the key and commits `create_session`; the durable record has a twelve-hour absolute expiry (`crates/wyrd/wyrd-auth/src/browser_sessions.rs:221-268,425-450`, browser-session migration). The same outcome is possible for an otherwise unchanged human connection session; recovery is the simplest proof.
2. Suspension/reactivation is a real public operator workflow: `PUT /platform/tenants/{tenant_id}/status` accepts `suspended` and `active` and calls `TenantProvisioning::set_suspended` (`crates/wyrd/wyrd-server/src/components/platform/routes.rs:350-394`). That owner calls `set_tenant_suspended`, commits, and does not mutate browser sessions (`components/platform/provisioning.rs:353-405`). The SQL changes only `platform.tenants.status/updated_at`, expressly preserving rows, grants and credentials (`crates/wyrd/wyrd-sql/src/queries/platform/provisioning.rs:157-194`). No implicit logout occurs.
3. The caller can immediately submit same-origin public `POST /auth/browser/logout` with the saved matching tenant cookie and typed tenant body. `auth_router` mounts it without `AuthenticatedPrincipal` (`components/auth/routes.rs:56-71`); `auth::browser::logout` checks exact Origin, matches cookie label to requested tenant, and calls the lifecycle owner without a current-authority check (`auth/browser.rs:513-531`). No global tenant-session admission gates this handler. Native requests first pass `hooks.server.ts:12` and `forwardAuth`, which now carries the session cookie under `/auth/browser/*` (`wyrd-ui/src/lib/server/upstream.ts:67-94`). nginx routes auth to Rust under the established configuration; the Rust endpoint is sufficient to establish production reachability without claiming deferred image execution.
4. The internal UI path reaches the identical owner: root `?/logout` action at `wyrd-ui/src/routes/+page.server.ts:125-132` calls Node `BrowserSessions.logout` without requiring `locals.browserSession`. The root route has no `tenantKey` hook admission, and the method directly posts the selected cookie/body to Rust (`lib/server/auth/browser-sessions.ts:228-238`). Root layout has no live-session dependency. A prior tenant metadata read can clear a suspended cookie, but logout does not require that read and public logout remains independently reachable with the saved value.
5. `BrowserSessions::logout` parses the value's tenant/hash, then calls `resolve_tenant_slug` before opening revocation (`crates/wyrd/wyrd-auth/src/browser_sessions.rs:320-342`). `WyrdPostgres::resolve_tenant_slug` explicitly returns None for suspended tenants (`wyrd-sql/src/postgres.rs:179-205`); its actual SQL function requires `status = 'active'` (`migrations/20260601000000_platform.sql:69-85`). Therefore a matching suspended tenant is treated as a mismatch and returns `Ok(())` at line 335. HTTP returns 204 and clears the cookie; no revocation query runs.
6. Nothing beneath the former implementation would prevent the safe revocation. `TenantConn::acquire` binds only the tenant UUID (`wyrd-sql/src/tenant_conn.rs:47-59`); it performs no directory admission. Browser-session RLS checks only `data_tenant_id = wyrd.current_tenant()` (`migrations/20261020000000_auth_browser_sessions.sql:36-42`). `revoke_browser_session` updates the exact digest with `revoked_at IS NULL`, and commits through its caller; it does not require active grants/tenant/connection (`queries/auth/browser_sessions.rs:57-63,183-192`). In the previous candidate logout opened that transaction directly, so this failure is introduced by the selected-tenant remediation, not pre-existing behavior.
7. Reactivate the tenant before expiry, leaving its key/principal/grant unchanged. `live_browser_session` still finds the unrevoked digest (`queries/auth/browser_sessions.rs:40-55`); `BrowserSessions::authorize` invokes the current issuer (`wyrd-auth/src/browser_sessions.rs:375-405`), whose tenant admission now succeeds (`wyrd-auth/src/issuance.rs:600-608`). The saved identifier is accepted again by metadata and protected tenant APIs. A successful logout has consequently removed only the browser's local cookie, with durable authority restored on normal resume.

## Siblings, existing alternative, and minimum correction

The Rust HTTP adapter is the lifecycle logout's only production caller; the lifecycle owner is SQL revoke's only caller. Public native forwarding and the Node root action converge there. Session metadata `view` already obtains authoritative identity through `WyrdPostgres::tenant_directory_entry` (`wyrd-auth/src/browser_sessions.rs:349-371`). That helper calls existing `tenant_by_id` over OperatorPool; it includes suspended tenants and excludes deleted/unknown rows (`wyrd-sql/src/postgres.rs:227-258`, `queries/platform/tenants.rs:50-76`). It supplies precisely the route slug needed to compare with the requested tenant using the identifier already parsed from the possessed value.

Recovery's active-only `resolve_tenant_slug` is correct for creating new authority and must remain unchanged. Read/authorize current-state admission is likewise correct. OAuth/CLI token revocation and principal/key revocation are separate authority owners; none is called by browser logout, and none needs widening or replacement.

**Proposed FOLLOW-001 — REGRESSION, same correction boundary as FIND-8.** At `wyrd-auth/src/browser_sessions.rs:329-335`, successful selected logout fails to persist revocation while the matching tenant is suspended, allowing the saved value to authenticate again after ordinary reactivation. Violates REQ-033 immediate selected-session revocation and R2's preserved ordinary logout/idempotency boundary. Possession of the real high-entropy identifier and trusted Origin are still required; no arbitrary-session revocation or immediate suspension bypass is claimed.

**Smallest safe correction:** in the existing logout lifecycle owner, validate selected-route identity using `tenant_directory_entry` for the cookie's parsed tenant and compare its authoritative slug to the requested slug before the unchanged TenantConn/digest revoke/commit. Do not change the shared active-only resolver or authentication admission, add a status-neutral resolver/API, add raw SQL or manual tenant predicates, or require live principal/credential/connection permission. Unknown/deleted/mismatching values remain no-op cleanup; store failures remain unavailable. This substitutes an existing identity read for a mistaken admission read, retaining both cross-tenant binding and safe revocation. The prior private recovery-resolver prescription should be corrected accordingly; no new public/security/persistence decision is needed.

**Focused closure proof:** extend the existing registered HTTP/Postgres authority test `pg_browser_sessions::browser_session_authority_is_tenant_bound_and_revocable`: create a valid session, suspend its tenant, same-origin logout using matching label/value/body, assert 204/clear-cookie and durable `revoked_at`, resume the tenant, and prove the saved cookie is still 401 while an independent untouched session/key remains usable. Retain its existing relabeled-value rejection, active logout/idempotency and outage assertions. The current test suspends Beta and proves only its immediate read refusal (`pg_browser_sessions.rs:446-458`), then logs out active Acme (`:460-498`); it never logs out suspended Beta or resumes it, so the supplied green result cannot close this branch. Use the existing managed Postgres exact selector from R2; no new harness, broad suite, live IdP, or image execution is needed for remediation proof.
