## Existing alternatives and correction boundaries

The existing `ServerInstaller`, `DevServer`, build script and common startup cleanup already own their workflows; the candidate extends them. `check_payload` is a local invariant shared by all installer entry points, not a second installation mechanism. It deliberately does not attempt to parse or resolve a JavaScript import graph.

The previous Node session implementation cannot meet REQ-033 persistence/replica/current-authority requirements. The new Rust session owner is justified by that explicit requirement, but it composes the existing human-connection, authorization-code, API-key and issuer owners. `create_session` has no retained lifetime of its own: receiving a caller-owned `TenantConn` is appropriate so provider callback identity/roles/session commit together. Moving it to an artificial utility struct would not improve ownership.

`forwardAuth` is the existing public request relay; `BrowserSessions.call` is the existing selected-session BFF projection. Their cookie projection differs intentionally: enumeration accepts several proved sessions, while a tenant API call carries one. Replacing either with another transport or generic cookie framework is unnecessary. R2 logout likewise reuses `resolve_tenant_slug` and the existing tenant revoke query; it neither repeats SQL tenant predicates nor reauthorizes unrelated grants merely to log out.
