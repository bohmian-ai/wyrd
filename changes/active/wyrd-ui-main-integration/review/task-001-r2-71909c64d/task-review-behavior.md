## Diagnosis of the changed provider-replacement assertion

The task records a first native journey failure: the replacement activation action expected 200 but received 401, with `tenant human connection activated ... retired=Some(...) revision=3`. I independently traced the claimed cause:

1. Settings `activate` posts through `BrowserSession.api` to the existing connection API. `HumanConnections::activate` (`connections.rs:523–580`) retires old Active and promotes tested Candidate in one committed transaction. Its trace is emitted after that commit.
2. Alice's browser session is bound to the old connection's exact id/revision. `BrowserSessions::authorize` checks `human_connection_is_active`; the retired revision now fails. Rust metadata enumeration therefore returns no live selected session and clears its cookie.
3. Full page action rendering invokes tenant layout and the corrected `metadata` projection. The old projection silently fabricated earlier identity; the new projection refuses 401. Accordingly the 200 expectation was an assertion of FIND-4's defect, not an approved success contract.
4. The replacement journey still proves the durable result: Alice's saved old value fails on both replicas; the second realm signs in; the recovery owner lists the second realm as Active with the expected candidate id, deletes the retired connection, and the replacement session remains live. Those assertions prevent changing 200 to 401 from making an activation refusal look like success.

The expectation at `production-auth.integration.test.ts:748` is therefore behaviorally justified. The sibling `deactivate` path already tolerates its own session-ending render.
