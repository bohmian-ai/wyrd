## BEH-1 — Authored SQL text is mistaken for a range parameter

Classification: **INCORRECT**. Proposed finding, not yet independently validated.

**Violated obligation.** REQ-030 permits explicitly authored runtime SQL, specifies range binds for range-aware charts, and requires unchanged executed SQL/binds and truthful errors. REQ-025 permits table charts of any result shape. Original TASK-003 owns complete Chart loading, authored SQL preservation and the portable direct-component host. `ChartInputSchema` makes range optional and accepts `{type:'table', sql:"SELECT '$1' AS label"}`; `LoadContext.range` is also optional. An ordinary literal containing `$1` does not require a time range.

**Exact producer.** `ui/packages/ui/src/lib/loaders.ts:90–94`, particularly raw regex matching at line 91. The regex searches every character of SQL, including single-quoted strings, quoted identifiers and comments, without identifying SQL parameter tokens. With no range, line 93 returns canonical validation instead of allowing the valid query. With a range, it invents unused bind positions; a comment containing `$3` can also alter the exact planned bind list. The proven blocking consequence here is the range-free direct load, independent of how DataFusion handles unused supplied values.

**Reachable caller-to-result evidence.** A custom server may call the approved public `loadChart` directly or `loadPanel` with an executor and no range for a range-free table/stat. `loadPanel` validates the above input successfully, dispatches `loadChart`, which calls chartParams before executor.run and returns `result.state='error'`. No SQL reaches the existing query owner. The server's floor uses DFParser to accept read-only SELECT; Oracle::plan_logical performs actual parameter binding on parsed plans (`crates/vala/vala-bifrost-redux/src/oracle/mod.rs:3170–3175`). A string literal is not a placeholder there. No server change is needed.

**Independent artifact-free probe.** Ran pinned Node via `mise exec -- node --input-type=module` importing existing `ui/packages/ui/dist/loaders.js` (no build/generation). Passed SQL `SELECT '$1' AS label` to chartParams and loadPanel, with a counting executor. Both returned `WYRD_SPEC_400_VALIDATION`, detail `The SQL binds $1..$3 but no range was supplied.`; loaded state was error and executor call count was **0**. The emitted implementation and current source use the same regex. This is a logic probe, not a new live-server or browser result.

**Attribution.** `git show b0a05de50:.../loaders.ts` contains the same raw SQL regex and missing-range branch in the original foundation introduction. Cumulative git log attributes that file to TASK-003 foundation and its corrections. It is neither unrelated PR #205/main nor TASK-027 layout, and is distinct from closed explicit-range precedence FIND-003-1 and Date-representability FIND-003-13.

**Sibling consumers and existing alternatives.** chartParams has one production caller, loadChart. Direct custom page calls and `loadPanel` share it. loadPanel is consumed by WyrdView's local executor path and by both shipped/custom POST endpoints; MCP App → WyrdView → loadPanel shares the same producer. Chart's `executed` output is the sibling Open in Query consumer of the planned binds. No host-specific guard can correct these uniformly. Existing Rust floor/parser and Oracle binding remain the SQL authority; there is no existing portable TypeScript SQL-token helper in this package to reuse, and importing server/native parsing into a browser-safe loader would violate the approved boundary. Existing chartParams is already the narrowly scoped range-bind planner that needs correction.

**Smallest testable correction.** Correct range-bind recognition once at the existing chartParams planning owner so only actual `$1`/`$2`/`$3` parameter tokens count; SQL quoted data/identifiers and comments must not demand or manufacture range binds. Keep exact SQL unchanged, ordinary parameter order and existing range selection, executed values/action handoff, query floor, native collection, cancellation and host/credential boundaries. Use a small conventional lexical treatment inside this existing owner, without a new parser service, SQL-validation framework, dependency, transport or public input field. The correction is token recognition for parameter planning, never a replacement read-only validator.

**Focused proof.** Extend the existing `TASK-003: Dependent loads and safe actions` cases: quoted `$1` data/identifier and comment `$3` text with no real parameter executes once with empty params without requiring range; mixed actual placeholders plus inert text bind only the actual highest position; escaped SQL quoting/comment controls and existing real `$1..$3` range/error/unchanged-SQL assertions stay correct. Check loadChart/loadPanel output plus executed params, not the helper alone. Use the current scenario and UI check; no new live server, browser, native rebuild or test harness is required for this pure planning fix.
