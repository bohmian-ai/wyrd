## Proposed finding SEC-1 — original ceiling value is lost before admission

**Classification:** INCORRECT. **Prior ID:** FIND-003-11, same requested-budget admission invariant, not a new finding number.

**Violated obligation:** REQ-030 requires matching bounded collection ceilings and invalid-input behavior across Node and MCP. R4 explicitly requires refusing out-of-range supplied budgets rather than clamping them; TypeScript SDK documentation promises `WYRD_SPEC_400_VALIDATION` for a ceiling outside its range.

**Exact location:** `sdks/wyrd-sdk-ts/native/src/lib.rs:1382–1396`, specifically `max_rows: Option<u32>` and `max_bytes: Option<u32>` at the N-API boundary before `admit_ceilings`. Public producer/callers: `sdks/wyrd-sdk-ts/wyrd/src/index.ts:545–547`; UI `packages/ui/src/lib/contract.ts::WireRequest` and `node.ts` query case. Sibling surface: `wyrd-server/src/query/collect.rs::QueryArguments` and `validate`.

**Evidence and reachable consequence:** The public TypeScript options and WireRequest expose both ceilings as `number`, and forward them unchanged. The new shared rule correctly refuses zero and above-maximum *Rust* integers. However, the installed `napi-3.12.3/src/bindgen_runtime/js_values/number.rs:45–68` converts a JavaScript number to Rust `u32` with `napi_get_value_uint32`, without a check retaining the original double. This numeric conversion is not range admission ([Node-API number conversion](https://nodejs.org/api/n-api.html#napi_get_value_uint32)). The native method therefore receives an already converted value. In particular, an original row ceiling `4_294_967_306` becomes `10`, and byte ceiling `4_294_971_392` becomes `4096`; both then pass the new shared check. A tiny authorized query can succeed with either original out-of-range request, while MCP refuses the original row integer during `u32` deserialization or the original byte integer during range admission. Fractional values likewise lose information before the policy sees them. This is a source-traced inference from the binding conversion, not a freshly executed server reproduction.

The global retained-result cap remains bounded after this conversion; this finding does **not** claim a tenant escape or allocation above the newly enforced maxima. Its observable consequence is successful bounded collection for an explicitly forbidden requested budget, with Node/MCP disagreement and silently changed caller intent. The existing added test matrix covers 0 and maximum+1, all representable within `u32`, so it cannot detect this boundary loss.

**Smallest testable correction:** Preserve the original numeric value through the native SDK admission boundary, validate it as a finite integral value in the admitted domain before any narrowing integer conversion, and then reuse the existing shared ceiling policy/result collector. Put the correction at native collection, the owner every SDK/UI Node caller uses; do not add component, BFF or MCP-specific downstream guards. Keep the existing take/drop release on every refusal, `NativeQueryStep::failure`/SDK error projection, defaults, maxima, valid overflow, terminal validation and cancellation. MCP's existing integer contract and shared policy remain authoritative. This requires no new product/API concept or credential decision; generated TypeScript declarations continue to express numbers.

**Focused closure proof:** Extend the existing tiny-query SDK/MCP admission scenario with a row and byte budget above `u32::MAX` that wrap to valid small budgets, plus fractional budgets. Assert each path refuses original invalid input without usable rows; SDK refusals keep stable validation metadata and close the native stream, and a fresh ordinary query still works. Preserve the current zero/max+1/max/default/actual-overflow assertions. A direct existing native-backed SDK collection case is sufficient to prove the common Node boundary; no new harness or load generation is needed.
