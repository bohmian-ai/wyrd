### MAINT-1 — INCORRECT: ceiling admission sees a coerced integer instead of the requested budget

Stable finding continuation: **FIND-003-11**. Do not assign a new ID for another manifestation of the same requested-budget admission invariant.

- **Location:** `sdks/wyrd-sdk-ts/native/src/lib.rs:1382–1403`, particularly `max_rows: Option<u32>` and `max_bytes: Option<u32>` at lines 1384–1385; public caller `sdks/wyrd-sdk-ts/wyrd/src/index.ts:545–547`; existing test boundary `src/lib/ui-library.integration.test.ts:185–201`.
- **Governing obligation:** REQ-030 retains the same bounded result ceilings on SDK/MCP; TASK-003-R4 requires supplied budgets outside the existing domain to be refused rather than clamped. TS SDK AGENTS requires extracting and validating at the native boundary without forking errors/lifecycle. Maintainer guide requires types to carry the contract and unknown input to be narrowed at its boundary.
- **Producer-to-consumer evidence:** WireRequest's JS number passes unchanged through `nodeExecutor` to public `BifrostQueryStream.collect`, then into a napi `Option<u32>` before the body can call `admit_ceilings`. Installed napi 3.12.3 `src/bindgen_runtime/js_values/number.rs:45–68` uses `napi_get_value_uint32` for u32, with no lossless/integer guard. Node's implementation uses V8 `Uint32Value` for number values that are not already uint32 ([versioned primary source](https://github.com/nodejs/node/blob/v26.5.0/src/js_native_api_v8.cc#L2168-L2188)). That conversion wraps/truncates; it does not validate the original number. This is a static inference from the actual binding and Node conversion source, not a newly executed server journey.
- **Reachable consequence:** a tiny one-row query collected with `maxRows: 4294967297` reaches shared admission as `1` and can succeed. `maxBytes: 4294971392` becomes `4096` and can likewise succeed for a tiny result. Fractional `maxRows: 1.5` also becomes `1`. The same original JSON budgets cannot deserialize into MCP's `u32`/`usize` fields and are refused. Thus the promised refusal and SDK/MCP input-domain parity remain false despite centralized range checks. This does **not** claim that the new shared maximum can be exceeded after conversion; the concrete defect is silent normalization of invalid requested values and successful results where refusal is required.
- **Concrete maintenance cost:** both generated native declarations and the public wrapper advertise JS `number`, but the only policy check receives an already-different value. Maintaining the shared range rule alone cannot fix this input path; tests need to cross the actual native conversion boundary rather than only unit-test admitted Rust integers.
- **Sibling trace:** direct public SDK collection and `nodeExecutor` share this native method; BFF/custom-app chart reads currently omit the ceiling options. MCP QueryArguments uses deserialized integers and existing InvalidQueryArguments projection. JsonResultBuilder's only production clients are MCP ResultCollector and this native collection, both now sharing `admit_ceilings`. Ordinary next/return and general Arrow streaming are adjacent consumers and must remain unchanged. Do not add component or BFF guards.
- **Smallest safe correction:** preserve the supplied JS numeric value through the existing native collect boundary until finite/integer and permitted-range validation completes; only then convert to the shared admitted integer form. Reuse the shared constants/range policy and `NativeQueryStep::failure(WyrdError::Validation)`, rather than duplicating ceilings in hosts. The numeric-boundary guard belongs in napi because this is where information is currently lost. Preserve taking/dropping the stream on refusal, cancellation notification, positional encoding and terminal validation. Do not add a new transport, configuration, error family or general numeric wrapper. Generated declaration regeneration remains owned by the normal native build; a Rust numeric extraction change need not change the public JS `number` contract.
- **Focused closure:** extend the existing native-backed real SDK/MCP read scenario with a tiny query and one wrapping positive row budget, wrapping byte budget and fractional row budget. Both surfaces must refuse the original request with their existing envelopes and no usable rows; after direct SDK refusal a repeated native-backed collect remains closed and a later independent query works. Existing 0/max+1, exact maxima/defaults and actual result-overflow tests remain. No new test harness, dependency or broad suite is needed.
