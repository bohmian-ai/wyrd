## Proposed finding

### SYS-003-1 — INCORRECT: native bounded collection accepts ceilings that MCP refuses

**Violated obligation.** REQ-030 requires keeping the existing row/JSON-byte ceilings on both result paths and identical authorized executor reads. TASK-003 scenario 2 explicitly includes limits; existing bounded-tool admissible ceiling ranges are 1..10,000 rows and 1..16 MiB.

**Exact source and reachability.** `packages/ui/src/lib/contract.ts:46-60` publicly admits `bifrost.query.max_rows/max_bytes`; `node.ts:39` sends them unchanged into SDK `BifrostQueryStream.collect` (`wyrd/src/index.ts:544-552`). `native/src/lib.rs:1377-1392` accepts u32 values and directly constructs `JsonResultBuilder::new` with them. The builder (`wyrd-queue/src/json_result.rs:70-79`) retains whatever ceilings it is passed. In contrast, server `query/collect.rs:171-182` rejects zero and anything above `MAX_ROWS_CEILING` (10,000) / `MAX_BYTES_CEILING` (16 MiB), with MCP invoking that validation before execution (`src/mcp/bifrost.rs:236-243`). All numeric values in the following example are valid u32, so native conversion does not close the gap.

A caller of the explicitly public executors can send the same valid authorized query already used by the integration fixture, with `max_rows: 10001` (or `max_bytes: 16777217`). Node accepts the requested bound and returns the ordinary three-row result; MCP rejects the request before it executes. Native `max_rows: 0` with an empty result can likewise succeed where MCP rejects the argument. Current Chart loaders use defaults, so this is not a claim that a view document can inject larger ceilings through Chart input; the affected surface is the independently required public executor/SDK bounded read.

**Observable consequence.** SDK/Node and MCP no longer have the same bounded-result contract. A custom-app server can request retention well above the agent/page whole-result ceilings, increasing collection/encoding memory up to a larger engine response limit, while the same MCP request is refused. Existing engine-wide limits do not establish the smaller required collected-result ceiling.

**Existing owner, sibling coverage and smallest correction.** The new bounded collector is the producer accepting invalid state. Keep limits at the shared bounded-result/native collection authority, reusing existing constants and validation/error mechanisms; do not add guards to Chart, CardHeader, remoteLoader or each host. Ensure Node/native cannot construct a bounded collection outside the existing admissible ranges and preserves existing default values, result-size overflow errors, terminal validation and cancellation/resource release. MCP retains its existing externally advertised ranges and error semantics. This requires no new setting, dependency, transport, product or persistent-data decision. All sibling callers are SDK `BifrostQueryStream.collect`, Node executor, MCP `BoundedQuery/ResultCollector`; rendering consumes the normalized result only.

**Focused closure proof.** Extend the existing Node/MCP real query parity test with upper-invalid row/byte bounds and zero, plus valid boundary/default checks; assert refusal rather than successful data, and that failure leaves no usable partial result. Exercise the native/Node runtime, not Rust emulation of Node. Use the existing focused UI authorized-read scenario and narrow changed-owner checks, not a new harness or broad load test. This proposal is established by source trace; no new runtime probe was executed in this read-only review.
