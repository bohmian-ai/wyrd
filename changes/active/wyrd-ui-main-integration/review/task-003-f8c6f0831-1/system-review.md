## SYS-1 — A transient connection failure permanently poisons the Node executor

Classification: **REGRESSION / INCORRECT**. Changed location: `crates/wyrd/wyrd-server/wyrd-ui/packages/ui/src/lib/node.ts:16–19`, with consumers at lines 23–30 and 45–48.

Violated boundary: REQ-030 requires the reusable Node executor over the existing SDK for user custom apps and honest shared read behavior. TASK-003 adds the memoization owner; SDK credential/transport recovery remains with existing SDK/Rust owners. An ordinary first-connect outage must remain a failed load, rather than become permanent executor state that prevents subsequent caller-initiated reads from reaching the recovered SDK. This requires no automatic retry or stronger service availability promise.

Producer-to-consumer evidence:

1. `nodeExecutor` creates `cardsHandle` and `bifrostHandle` and sets each once with `??= ...connect({ client })`. A rejected Promise is non-nullish, so it is retained forever.
2. `Cards.connect` (`sdks/wyrd-sdk-ts/wyrd/src/index.ts:1670`) calls `NativeWyrdClient::cards` (`native/src/cards.rs:68`) -> existing `Cards::connect_with` (`cards/handle.rs:193`) to complete the credential connection. `WyrdClient::connected` (`crates/shared/wyrd-client/src/client.rs:131`) calls `access_token` for non-session clients; `AuthMiddleware::bearer` (`auth.rs:850`) exchanges an API key/workload/delegated/renewable credential as needed. `exchange_and_store` stores only after successful exchange; a transport error returns without installing a failed permanent cache entry. A later SDK connect may try again normally.
3. `Bifrost.connect` (`index.ts:1098`) calls native `connectBifrost` (`native/src/client.rs:200`), then Rust `Bifrost::connect_with` (`facade.rs:148`). It first completes authentication and, for ordinary custom-app clients, calls `assemble` (`facade.rs:248`) to dial existing gRPC ingest. A server/network outage can therefore reject initialization even with a valid user credential. Later SDK connect is a fresh fallible call, not a terminal handle state.
4. The rejected Cards promise blocks both exact get and list forever; the rejected Bifrost promise blocks query, list-tables and describe-table forever. Verification-execution reads use their independent connection path. No read retry can reach the existing reconnect owner because `read` awaits the same rejection before issuing the operation.
5. This is reachable on the explicitly required public custom-app surface: retain `const executor = nodeExecutor(client)`, pass it in successive `loadChart`/`loadPanel` or `loadCardHeader` calls, encounter one transient first-connection outage, then issue another load after service recovery. The executor's public `run` contract has no one-shot restriction. Reusing it is ordinary consumption, not an unused internal helper or new host feature.
6. All repository production callers were checked: the shipped BFF and example create a new executor for each HTTP/page request, avoiding poisoning across those requests. That limits the blast radius; it does not eliminate the required reusable package surface. The integration suite retains executors for repeated reads but does not fail then recover first initialization. Existing unit cancellation tests mock a successful connect and likewise do not cover the failed cache state.

An artifact-free probe extracted the exact two getter declarations from candidate `node.ts` and evaluated them with a connection function that rejects its first call and would succeed subsequently. For both getters, a second invocation rejected with the original error and `connect` was called only once. This establishes the producer state directly; source tracing above establishes required consumers and real connection failure causes. The probe ran through `mise exec -- node --input-type=module` and wrote no files.

Observable consequence: a transient auth-server or initial gRPC connection outage can disable all Card or all Bifrost loads for the lifetime of a retained custom-app executor. Users must recreate the executor or restart the retaining owner to recover, even though the same SDK client and recovered server support a new connection. No tenant exposure or persistent data loss is alleged.

Smallest correction: keep the existing Node executor/SDK ownership boundary and ensure failed initialization is not retained as a usable cached handle. Preserve any desired sharing of successful/in-flight initialization; after a failed initialization, a later caller-initiated `run` must reach the existing SDK connect again. Apply the same invariant to both Card and Bifrost caches at their shared producer. Do not add automatic retries, backoff configuration, a new reconnect service, a new SDK transport or consumer-level recovery guards; do not change browser-session authority, cancellation, query settlement or successful-handle behavior.

Focused closure proof: extend the existing Node executor mock test owner with a stable SDK failure on the first `Cards.connect`/`Bifrost.connect`, then success. First `run` returns the original structured problem. A later `run` on the same executor succeeds and calls connect again. Cover the sibling operations sharing each handle and preserve the existing stream-cancellation tests. No new harness/dependency/live-server requirement is necessary to prove failed-promise admission/recovery.
