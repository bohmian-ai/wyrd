## MAINT-R1-01 — A host column change combines new headings with old held rows

**Classification:** INCORRECT / affected-path regression. **Related prior obligation:** FIND-TASK-004-REV-02-2's coherent host state and preserved held-row behavior; original task requires truthful rows/counts and controlled column choice. This is newly reachable through R1's host-driven `oncolumns` extension, so inspecting the retained holding owner is within remediation scope.

**Exact locations and path:** UI `packages/ui/src/lib/components/RecordTable.svelte:48–69` snapshots only loaded rows/counts in `held` while `holding` remains true, then derives `columns` from the latest `input` through `shownColumns(input)`. New `toggle` at `:152–165` calls host `oncolumns`; Observe `+layout.svelte` passes it in each signal branch and navigates to new URL columns. The server `listInputs`/list loader reads the new columns and returns new result/input together, but `held` remains the old result. Rows render using `row[columnIndex(rows, column)]` in RecordTable's cell loop; new CSV shaping at `:174–182` does the same. `columnIndex` returns -1 for a column not in the held schema.

**Reachable scenario:** enable Live, open and close a record (the existing list stays explicitly held until Resume), then use Columns to add a previously unread column such as a log structure/attribute field. The successful new server response updates `input.columns`, but `opened`/`holding` still preserve the old row schema. The table shows the new heading while reading `row[-1]`; the value becomes undefined/blank and CSV exports an empty cell although the returned new data contains the value. The same path occurs with host-paused or focused/scroll-held tables. Removing/reordering columns may appear to work, which is why the ordinary toggle test misses adding a column.

**Materiality:** approved interactive Columns plus Live/held behavior is a normal investigation flow, and both the displayed/exported evidence become detached from their schema. It is not merely a label/placement preference or a request to optimize refresh.

**Smallest correction:** at the existing shared RecordTable held-state owner, distinguish same-investigation Live refreshes from an explicit requested column/schema change. An explicit new column projection must replace/reset the incompatible held snapshot coherently when its result arrives (or hold its matching input and rows together until an explicit, visibly pending commit); do not render a new schema over old rows. For the conventional chosen-columns workflow, apply the requested schema with its newly read data without requiring the user to infer that Resume repairs empty cells. Preserve automatic-refresh hold/new-row/count behavior for an unchanged projection. Keep CSV and Open in Query aligned to whichever snapshot is actually displayed. Do not add per-page row guards, blank missing cells silently, key/remount the entire table on every live read, or introduce another table/cache owner.

**Correction burden:** a bounded shared snapshot/transition correction, reusing the existing held owner. Disabling Live or deleting held behavior would violate the task, and only hiding missing cells would conceal the wrong data.

**Focused proof:** extend existing shared RecordTable interaction coverage: populated live list with one schema, hold via open/focus, host update to include a previously unread column with a nonempty returned value, then assert headings/cells/CSV use one coherent input/result snapshot. Verify an ordinary same-schema appended refresh still holds rows/counts and reports/resumes new rows. One component test and an affected conventional column interaction suffice; no full batch replay.

## MAINT-R1-02 — Preserved metric duplicates hit a duplicate keyed-marker error

**Classification:** INCORRECT / fix-induced regression. **Related prior obligation:** FIND-TASK-004-REV-02-3's no-implicit-sum/fold and duplicate-time correctness; original task explicitly requires duplicate-timestamp cases. The new metric shaping changed the invariant at the existing Chart consumer, making this a remediation seam rather than unrelated old debt.

**Exact locations and trace:** `packages/ui/src/lib/plot.ts:83–105::recordedSeries` now correctly keeps every recorded point, including equal `x` values within one identity. `Chart.svelte:84–95` selects that path when identity props are present. Its marker loop at `:345` still uses `{#each line.points.length <= 60 ? line.points : [] as point (point.x)}`. Two retained samples from one recorded series at the same timestamp therefore have the same key. The installed Svelte runtime `node_modules/svelte/src/internal/client/dom/blocks/each.js:357–363,758–777` throws `each_key_duplicate` in both development and production when keys repeat. Distinct nanosecond instants that `parseInstant` maps to the same JavaScript millisecond can also collide.

**Reachable scenario and consequence:** a metric read has one series with two scalar points at one instant and no more than 60 points. The approved non-summing planner passes both through. Instead of plotting retained evidence, client Chart rendering errors on the marker loop. The generic query shaper used to collapse each instant, so the loop's uniqueness assumption was previously true for that path; the new recorded path makes it false. Tests use 24 series but two distinct instants per series, so their green result does not cover this seam.

**Independent probe:** without changing a source or test file, imported the built `recordedSeries`, supplied two rows `2026-10-20T10:00:00Z / gauge / 1` and the same instant/identity with value 2, and asserted the function retained both. Extracted the installed Svelte `validate_each_keys` body and invoked it with the marker's exact key function `point => point.x`; `assert.throws(..., /each_key_duplicate/)` passed. This is a shape-to-actual-runtime-validator probe, not a claimed complete browser render. The runtime source proves both modes throw.

**Smallest correction:** adapt the existing shared Chart's retained-point marker identity to distinguish each preserved sample occurrence (or use an unkeyed/index occurrence render where appropriate). Keep line/series identity and every point; do not sum, discard or invent timestamps to satisfy the UI key. Generic authored-query shaping need not change. The tooltip/selection consumer should also not silently claim one equal-time point is the only retained value when it displays that instant; preserve or explicitly expose the retained evidence rather than reintroduce duplicate collapse.

**Correction burden:** small local consumer correction owned by the rendering component; this is a legitimate consumer invariant because the data owner must preserve valid duplicates. New metric identity columns, SQL deduplication or a generic chart framework are unnecessary.

**Focused proof:** render Chart with identity props and two same-series/equal-time points, asserting no runtime error and both retained markers/line coordinates remain; include equal-millisecond distinct precision if supported by fixture. Keep the >20-series/no-other-fold and generic authored-query tests green. Use existing Vitest/Svelte component owner; no new runner.
