## MAINT-01 — Conventional Observe uses the dynamic renderer instead of the existing server-load/component workflow

- **Classification:** VIOLATION.
- **Exact changed locations:** `crates/wyrd/wyrd-server/wyrd-ui/src/routes/t/[tenantKey]/observe/+page.server.ts:13–20`; sibling `+page.svelte:6`, `:13–17`, `:107–109`; `src/lib/observe-host.ts:146–187` produces documents for those consumers.
- **Governing obligation:** approved spec REQ-030, “Use case 1 — shipped UI” (`spec.md:900–904`): each `+page.server.ts` builds the session's Node executor, runs shared component loaders, returns props, and pages compose the existing components directly. The original task requires the complete conventional shell/Observe delivery through existing session/BFF/shared loaders. The UI skill's Server/client split also places authenticated page reads in server loads. The current user explicitly reiterates SSR/BFF.
- **Producer-to-consumer proof:** Observe server `load` returns only `{predicate}` and runs no signal loader at all. The page derives `observeView`/`detailView` documents, constructs `remoteLoader`, and renders two `WyrdView` instances. In the existing renderer, `panels` initializes to `[]` (`WyrdView.svelte:62`); `start` populates it and invokes loaders only from `$effect` (`:93–99`, `:252–274`). That effect does not run during server rendering. Thus an authenticated initial GET with the default Traces state returns the page controls plus an empty panel container; every meaningful signal read waits for hydration and a separate panel POST. Opening a direct trace/log link has the same problem for the drawer. `remoteLoader` then POSTs each panel to `/ui/load`, whose existing handler builds the session executor and invokes `loadPanel`.
- **Observable consequence and materiality:** required conventional content is absent from the initial server render, including the loaded/empty/denied/error outcomes. Network startup is unnecessarily serialized behind client hydration. More importantly for maintenance, the conventional page owns dynamic view-document layout/action/load orchestration rather than consuming typed component props; changes to its layout or loading lifecycle must go through the dynamic renderer protocol despite an explicit and already implemented conventional owner. This is an explicit approved boundary violation, not a preference for a different conventional style.
- **Existing alternative:** `loadPanel` or the exported typed `load*` functions already execute the portable planning/dependent-read/result shaping with `nodeExecutor`. `examples/ui-app/src/routes/+page.server.ts` resolves one range, calls existing loaders with one context, and returns props; its sibling page composes `CardHeader` and `Chart` directly. Retained settings also loads its page data server-side. The corresponding `/view` example shows where the document/remote-renderer path properly belongs.
- **Decision-complete smallest correction:** change this conventional Observe host to run the existing shared signal/chart/facet/list/detail loaders from its authenticated `+page.server.ts` using the existing session Node executor and one resolved effective range. Return their typed props and directly compose the existing `Chart`, `FacetRail`, `RecordTable`, `TraceWaterfall`, `RecordDetail`, `StatStrip` and `Drawer` as applicable to the approved boards. Keep URL parsing/navigation as app state; replace the document-only host planning only where no longer needed. Use SvelteKit navigation/invalidation for page data changes and bounded refresh, preserving shared component held/live behavior, stale-result cancellation, predicate refusal semantics, exact executed SQL/binds and tenant authorization. Server-side shared loaders remain the only planners/shapers; there must be no page-owned SQL, transport, or parallel query lifecycle. Preserve `/ui/load`, `WyrdView`, `remoteLoader` and their gallery/view-document/custom/MCP consumers. Do not add an SSR/preloaded-results protocol to `WyrdView` or place props/results in a view document: that expands the wrong owner, conflicts with the no-results document contract, and duplicates the existing conventional mechanism.
- **Correction burden:** bounded app composition/server-load work using existing functions and component props; no new dependency, wire format, renderer mode, or SDK API. Merely invoking a server predicate check is insufficient because it supplies no panel data. A downstream spinner or “SSR” flag cannot repair missing server reads.
- **Focused closure proof:** extend existing production-BFF/browser tests to inspect the authenticated initial response or use a JavaScript-disabled context for a populated Traces/Logs/Metrics page and an exact-detail URL; assert actual server-rendered content or truthful empty/denied/error state. With JavaScript enabled, change range/predicate/signal and navigate Back, proving all relevant props correspond to the same resolved range/predicate and that late previous results cannot overwrite the new state. Check that hydration uses the server props rather than replaying the entire initial panel load via `/ui/load`. Reuse existing tests and BFF fixture; no new runner or broad dev:full replay is needed to prove this correction.
