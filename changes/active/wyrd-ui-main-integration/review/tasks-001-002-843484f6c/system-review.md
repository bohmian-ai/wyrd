## Proposed finding

### SYS-001 — Marker-only package check can activate an unusable UI, and cached versions bypass the new check

- Task: TASK-001.
- Classification: **INCORRECT**.
- Violated obligation: REQ-002 explicitly requires incomplete/corrupt/incompatible UI not replace a usable install and a successful install contain a runnable BFF, rather than merely empty directories; scenario 1 and AC-001.
- Exact changed location: `crates/wyrd/wyrd-cli/src/server/install.rs:445` (`extract` runnable predicate); connected existing activation branch `install.rs:228–249` and `installed()` at `install.rs:190–202`. Relevant changed fixture `crates/wyrd/wyrd-cli/tests/server_install.rs:54–57`.
- Producer-to-consumer evidence: the bundle producer stages an actual production build and imports `ui/build/handler.js` (`scripts/build.sh:43–50`). The installer does not use the established loadability criterion: it accepts any regular `ui/build/index.js`, any regular `ui/package.json`, and any `ui/node_modules` directory. The changed signed positive fixture writes index.js as the empty string, package.json as `{}`, and an empty node_modules directory. A correctly signed malformed bundle with those entries passes extraction and is renamed/activated, even though Node immediately exits without any BFF listener. Equally, a real entry whose handler or dependency is omitted satisfies the predicate. Native `check_ui` only repeats the entry-file existence check; Node version does not repair the payload. UI readiness then fails after activation. This is an invalid publisher/package defect, not an untrusted-user code-execution hypothesis.
- Sibling/cache path: `install` skips download/extract entirely whenever the same-version directory contains wyrd-server, and `installed` similarly recognizes binary-only cached versions. An earlier binary-only install or locally incomplete cache can therefore bypass the task's new payload obligation; the recommended `wyrd server install` cannot repair the same cached release. This shares the incomplete-install acceptance cause and should be corrected at the existing installer boundary, not with another downstream readiness guard.
- Observable consequence: an update reports successful activation and loses the working current installation pointer while UI cannot run; repeat dev startup fails. Existing prior version bytes survive, but the documented automatic preservation promise does not.
- Smallest correction boundary: extend the existing ServerInstaller's pre-activation validity decision so newly extracted and reused candidate versions are validated for an actually loadable production BFF before current changes. Reuse the existing staged UI runtime-load smoke established by the producer, with the documented compatible system Node prerequisite and bounded process lifetime, rather than adding a manifest, new installer, lifecycle controller or post-activation rollback workflow. Preserve signature/hash checks, atomic publication, existing good current installation and all server setup behavior. Incomplete cached versions must not be activated or remain silently selected as runnable; correct/reinstall them through the existing staging flow without deleting the working current install.
- Focused closure proof: extend the existing installer regression with (1) signed marker-complete but empty/non-loadable UI, (2) actual UI missing a required imported runtime file/dependency, and (3) same-version cached binary-only candidate alongside a usable current installation. Failed replacement must retain the good current link. A legitimate staged production UI must load from its extracted root without checkout dependencies. Use the existing exact focused installer target/fixture and owning runtime proof; do not add a broad new harness or require the full identity suite for this correction.
