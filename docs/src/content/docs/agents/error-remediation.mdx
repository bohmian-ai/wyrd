# Error remediation

Wyrd errors carry structured data. An agent must preserve that structure and act on it directly, not collapse it to prose.

## Error shape

All Wyrd errors follow RFC 9457 Problem Details with Wyrd extensions. A policy-denial response looks like this:

```json
{
  "type": "https://wyrd.dev/errors/policy/denied",
  "title": "Policy check denied the request",
  "status": 403,
  "code": "POLICY_DENIED",
  "detail": "Card 'fraud-model-v2' failed the require-owner-approval policy on register.",
  "remediation": "Have an owner approve the card in the registry before retrying registration.",
  "context": {
    "card_id": "fraud-model-v2",
    "policy_name": "require-owner-approval",
    "operation": "card.register"
  },
  "request_id": "req_01hwz4k9m2e3f",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

### Field reference

| Field | Description | Always present |
|---|---|---|
| `type` | URI identifying the error class | Yes |
| `title` | Human-readable summary of the error class, stable across instances | Yes |
| `status` | HTTP status code as an integer | Yes |
| `code` | Wyrd-specific machine-readable error code, stable string; use this for programmatic branching | Yes |
| `detail` | Instance-specific description of what went wrong | Yes |
| `remediation` | Actionable guidance for the caller or agent | Yes |
| `context` / `details` | Structured key/value map with operation-specific fields (card id, run id, policy name, etc.) | When applicable |
| `request_id` | Server-assigned request correlation identifier | When the server can correlate the request |
| `trace_id` | Distributed trace identifier | When tracing is active |
| `instance` | URI identifying the specific resource or operation that failed | When applicable |

## What agents must do

- Preserve all structured fields from the error response; do not flatten or summarize them.
- Use `code` for programmatic branching. `title` and `detail` are human-readable and may change in phrasing.
- Surface policy and audit denials as explicit decisions, not generic failures. The `code`, `detail`, and `context` together identify what policy was checked and what triggered it.
- When `remediation` is present, include it verbatim in any human-readable output or escalation.
- Keep retries bounded and tied to idempotent operations only. Check the `code` before retrying.
- Preserve `request_id` and `trace_id` in any escalation or support request.

## What agents must not do

- Do not re-wrap a structured error as an untyped string or generic failure message.
- Do not treat `status` as the full error identity. Two errors can share the same status code and require different handling.
- Do not ignore `remediation` when it is present.
- Do not infer error semantics from `detail`; it is instance-specific prose and is not stable across releases.

## Policy and audit failures

Policy and audit denials are decisions, not transport errors. A `403` with `code: POLICY_DENIED` means Wyrd evaluated the request against a named policy and rejected it. This is different from a missing credential or a malformed request.

The `code` and `detail` identify the failing policy. The `context` map contains the card, run, or operation that triggered it (for example, `card_id`, `policy_name`, `operation`). An agent must not retry a policy denial without first satisfying the stated condition in `remediation`.

Audit failures follow the same shape. If a write is rejected because an audit record could not be committed, the `code` will identify the audit step and `remediation` will describe what the agent or operator needs to resolve before retrying.

## Authorization errors

Use the Wyrd `code` value, not HTTP status alone:

| Code | Agent action |
| --- | --- |
| `WYRD_AUTH_503_VERIFY_UNAVAILABLE` | Back off and retry the same operation. Do not re-authenticate; the credential was not rejected. |
| `WYRD_PERMISSION_500_ROLE_CORRUPT` | Do not retry. Surface the failure to a workspace admin; the stored role permission JSON must be fixed. |
| `WYRD_AUTH_401_INVALID_CARD_REF` | Re-issue the Service or Agent credential with `wyrd auth issue-key`. |
| `WYRD_AUTH_401_DELEGATION_DEPTH_EXCEEDED` | Do not retry. Contact the issuer; the token came from a non-conforming source. |
| `WYRD_AUTH_400_UNSUPPORTED_GRANT_TYPE` | Check the Wyrd version and exact `grant_type` value. |
| `WYRD_AUTH_404_PRINCIPAL_NOT_FOUND` | Verify the requested subject is a registered Service or Agent CardRef in the current tenant. User impersonation is not supported in this version. |

## Retry behavior

Retries are only safe for idempotent operations. The `code` field is the signal for retryability:

- Safe to retry: read operations (card lookup, schema inspection, run query, policy list). These have no side effects.
- Unsafe to retry without idempotency key: card registration, run creation, policy writes. Re-sending these without a stable idempotency key may produce duplicate records.
- Not retryable: policy denials, audit failures, authorization errors. These require a corrective action before a retry will succeed.

If the error response does not include a `code`, treat the operation as non-retryable until the cause is identified.
