# Concepts

<Aside title="TL;DR" data-variant="wyrd">
Wyrd has four core nouns: **Card**, **Spec**, **Run**, and **Observation**. **Policy** and **Audit** are card kinds when users need to declare them, and service behavior when Wyrd evaluates rules or records accountability. **Lineage** is a derived graph, not a separate public object model.
</Aside>

<dl class="wyrd-defs">
  <dt data-kind="model">Card</dt>
  <dd>The durable, versioned envelope for one thing Wyrd governs.</dd>

  <dt>Spec</dt>
  <dd>The typed payload inside a Card. One schema per kind.</dd>

  <dt>Run</dt>
  <dd>The record of an execution tied to a specific Card version.</dd>

  <dt data-kind="experiment">Observation</dt>
  <dd>A measured fact attached to a Run, Card, service, or workflow.</dd>

  <dt>Policy</dt>
  <dd>A Card kind for declared rules, plus a service that evaluates those rules.</dd>

  <dt>Audit</dt>
  <dd>A Card kind for audit scope or evidence, plus service-owned accountability history.</dd>

  <dt>Lineage</dt>
  <dd>The graph Wyrd derives from CardRefs and relationships.</dd>

  <dt data-kind="service">Service</dt>
  <dd>A Card kind that packages declared AI behavior into a deployable boundary.</dd>
</dl>

## How they connect

The diagram splits the model into three parts. Cards and specs are the declared
contract. Services turn those contracts into derived state, policy decisions,
audit history, runs, and observations. Lineage is the graph view over
relationships; it is not a fifth noun beside Card or Run.

<Aside title="What this isn't" data-variant="not">
Cards are **not** file-system artifacts, ORM rows, git blobs, or event records.
They are typed, versioned declarations Wyrd can register, inspect, govern, link,
install, and expose to people or agents.
</Aside>

## Why there is no core Event noun

Wyrd can use internal events, outbox rows, audit rows, trigger deliveries, and
replayable service logs. Those are implementation details unless users need to
declare, version, govern, browse, or link them as Wyrd objects.

The public contract uses more specific words:

| Concept | Use it when |
|---|---|
| Card | The thing declares durable intent and needs identity, versioning, governance, or installation. |
| Spec | The data gives a Card its kind-specific meaning. |
| CardRef | The data links one Card to another. |
| Relationship | The server-derived edge should be visible in lineage. |
| Run | The record is one execution of declared behavior. |
| Observation | The record is a measured or derived fact about a Run, Card, service, or workflow. |
| PolicyCard | The user declares a governable rule. |
| AuditCard | The user declares audit scope, requirements, source material, or an evidence package. |
| Audit history | Wyrd records who did what, when, why, and with what result. |
| Internal event | A service needs a signal, outbox message, replay log, or background-processing input. |

```
If it declares durable intent, model it as a Card or Spec.
If it links Cards, use CardRef and derive relationships.
If it records one execution, use Run.
If it records evidence or measurement, use Observation.
If it governs behavior, use PolicyCard plus the policy service.
If it explains accountability, use audit history or AuditCard.
If it only drives internal processing, keep it as an internal event.
```
