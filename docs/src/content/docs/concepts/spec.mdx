# Specs

<Aside title="TL;DR" data-variant="wyrd">
A Spec is the typed payload inside a Card. One schema per kind. It holds the durable facts Wyrd validates, stores, links, and exposes.
</Aside>

<dl class="wyrd-defs">
  <dt>Declared shape</dt>
  <dd>The kind-specific contract: data schema, model interface, prompt variables, policy rule, service package, and similar fields.</dd>

  <dt>References</dt>
  <dd>`CardRef` values that connect this Card to other Cards.</dd>

  <dt>Constraints</dt>
  <dd>Validation, runtime, policy, and operational limits that belong in the durable contract.</dd>

  <dt>Artifact links</dt>
  <dd>References to durable `ArtifactCard` records when a card owns or consumes bytes.</dd>
</dl>

Specs should hold operational truth. Free-form notes are useful for context, but
they should not be the only place a runtime rule exists.

<Aside title="What this isn't" data-variant="not">
A Spec is **not** a README. It is the typed contract Wyrd services and generated docs read from.
</Aside>

## Shape

Each Card kind has its own Spec schema. The Rust contracts in `wyrd-spec` are
the source of truth, and the docs generator publishes the generated reference
pages under [Card reference](/cards/) and [schema reference](/api/schemas/).

For Data cards, the generated reference is [Data](/cards/data/). The Python
`DataCard` local holder builds this spec metadata from built-in data interfaces
or custom Python `DataInterface` subclasses.

## Lifecycle

Specs are durable. Do not put live Python objects, open file handles, SDK
clients, temporary paths, or process state into a spec. Local holders can own
live state while user code is running; the serialized Card must remain valid
after another process reads it.
