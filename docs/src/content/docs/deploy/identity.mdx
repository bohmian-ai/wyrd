# Deploy identity config

Self-hosted Wyrd identity is declared in `server.toml`. All configuration
resolves at boot; a server restart is required after any issuer or binding
change.

## Config file location

The server searches for `server.toml` in priority order:

1. `WYRD_CONFIG_PATH` — explicit path from the environment variable.
2. `/etc/wyrd/server.toml` — system default.
3. `~/.config/wyrd/server.toml` — user default.

If none of these exist, the server starts with compiled defaults (no identity
configured).

## Required config for identity

At minimum, set `auth.tenant_slug` before adding any `[[trusted_issuers]]` or
`[[workload_bindings]]` entries. The server will fail validation at boot if
issuers or bindings are present without a tenant slug.

```toml
[auth]
tenant_slug = "acme"

[[trusted_issuers]]
issuer            = "https://idp.acme.com/realms/acme"
client_id         = "wyrd"
expected_audience = "wyrd"
client_auth       = { secret_post = "change-me" }
principal_kind    = "human"
```

The `tenant_slug` can also be supplied via the environment variable
`WYRD_SERVER_TENANT_SLUG`, which overrides any value in `server.toml`.

## Signing key

Wyrd mints its own access tokens after verifying a caller's IdP token. Those
Wyrd tokens are signed with an Ed25519 private key you provision. **In a
production deployment this key is required — the server fails to start without
it.** The matching public verification key is derived from the private key at
boot, so there is no separate public key to configure.

Provide the key (PKCS#8 PEM, Ed25519) through one of two environment variables:

1. `WYRD_SIGNING_KEY_FILE` — path to a file holding the PEM (primary).
2. `WYRD_SIGNING_KEY_PEM` — the PEM inline (fallback).

The file form is preferred: a mounted Kubernetes `Secret` keeps the PEM out of
the process environment and `env` dumps. Setting **both** variables is a
configuration error and the server will refuse to start.

```yaml
volumes:
  - name: wyrd-signing-key
    secret:
      secretName: wyrd-signing-key
containers:
  - name: wyrd
    env:
      - name: WYRD_SIGNING_KEY_FILE
        value: /etc/wyrd/signing-key/key.pem
    volumeMounts:
      - name: wyrd-signing-key
        mountPath: /etc/wyrd/signing-key
        readOnly: true
```

Generate a key with:

```bash
openssl genpkey -algorithm ed25519 -out signing-key.pem
```

Auth works the same way in every environment; only how the key is supplied
differs. The environment is selected by `APP_ENV` (`development`, `staging`, or
`production`). `staging` and `production` both run the hardened production
profile.

- **`staging` / `production`:** you must provision a stable signing key. The
  server **fails to start** without one. Use a stable key here so issued tokens
  survive restarts and verify across replicas.
- **`development`:** if no key is configured, the server **generates an
  ephemeral key at boot** so auth works on a fresh local run with no setup. That
  key lives only for the process lifetime — tokens do not survive a restart, and
  it is single-process only — so it must never be used in staging or production.
  Set `WYRD_SIGNING_KEY_FILE` or `WYRD_SIGNING_KEY_PEM` locally when you need
  tokens to persist across restarts.

## Secret handling

Do not put raw client secrets in `server.toml` in production. The options
by deployment pattern are:

**Kubernetes Secrets.** Mount a `Secret` as a file at `/etc/wyrd/server.toml`.
The file is only readable by the container; Kubernetes RBAC controls access
to the `Secret` object.

```yaml
volumes:
  - name: wyrd-config
    secret:
      secretName: wyrd-server-config
containers:
  - name: wyrd
    volumeMounts:
      - name: wyrd-config
        mountPath: /etc/wyrd
        readOnly: true
```

**Environment variable override.** For the tenant slug, use
`WYRD_SERVER_TENANT_SLUG` directly and mount only non-secret config in
`server.toml`. Secrets in `[[trusted_issuers]]` entries (the `client_auth`
inline value) must still come through the mounted config file because there is
no per-issuer env var override.

**Secrets manager injection.** Use an init container or a secrets-manager
sidecar (e.g. the Vault Agent Injector or AWS Secrets Manager CSI driver) to
write the rendered config to `/etc/wyrd/server.toml` at pod startup.

## Boot behavior

1. The server reads `server.toml` and applies environment variable overrides.
2. For each `[[trusted_issuers]]` entry, it fetches
   `{issuer}/.well-known/openid-configuration` to discover the `jwks_uri`.
3. The initial JWKS fetch populates the key cache. The TTL is `jwks_ttl_secs`
   (or the server default when absent).
4. Workload bindings are resolved against the tenant declared in
   `auth.tenant_slug` and held in memory.

If the OIDC discovery endpoint is unreachable at boot, the server will fail
to start. Ensure the IdP is reachable from the pod's network before the
server process launches. When `APP_ENV` is `staging` or `production`, the
server also fails to start if no signing key is configured (see
[Signing key](#signing-key)).
