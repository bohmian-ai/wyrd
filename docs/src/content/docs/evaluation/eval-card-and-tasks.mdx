---
title: "EvalCard and tasks"
description: "Define evaluation tasks, understand how the engine runs them, and build effective task DAGs."
---

An `EvalCard` is a versioned evaluation contract. It declares what to check, how to check it, and what counts as a passing run. The engine — `vala-eval` — executes that contract against records emitted by your agent.

## The EvalSpec

The spec body of an Eval card has one required field: `tasks`. Everything else is optional.

```yaml
apiVersion: wyrd/v1
kind: Eval
metadata:
  space: my-team
  name: support-eval
  version: 1.0.0
spec:
  subject_ref:
    kind: Agent
    name: support-agent
    version: 1.0.0
  pass_gate:
    kind: overall_pass_rate
    threshold: 0.9
  context_capture: full
  tasks:
    response_not_empty:
      kind: assertion
      id: response_not_empty
      context_path: "$.response"
      operator: has_length_greater_than
      expected: 10

    response_is_helpful:
      kind: llm_judge
      id: response_is_helpful
      judge_ref:
        kind: Prompt
        name: helpfulness-judge
        version: 1.0.0
      context_path: "$.score"
      operator: greater_than_or_equal
      expected: 4
      depends_on: [response_not_empty]
```

| Field | Required | Description |
|---|---|---|
| `tasks` | Yes | Map of `task_id → EvalTask`. Keys must match inner `id` fields. Max 512 tasks. |
| `subject_ref` | No (required for online eval) | The Agent card whose runs this eval judges. Required when records arrive via `run.observe.eval()`. |
| `pass_gate` | No | Run-level verdict. Options: `overall_pass_rate`, `per_judge_pass_rate`, `all_pass`. |
| `context_capture` | No | How `AssertionResult.actual` is stored: `full`, `hash`, or `redact`. Use `redact` for PII. |
| `dataset` | No | Reference to a `Data` card containing scenario definitions. |
| `sampling` | No | Record sampling policy for online evaluation. |

## How the engine runs tasks

Every record your agent emits passes through the same execution path regardless of how it arrives — online via the ingest route or offline via the CLI.

```
EvalRecordObservation.context (your JSON)
         │
         ▼
ExecutionContext
  └── ContextSnapshot
        └── base_context: Arc<Value>   ← your observation JSON
        └── task_outputs: HashMap      ← accumulates as stages run

         │
         ▼
execute_plan(plan, cx, registry, executors)
  └── for each stage in topological order:
        ├── skip check: is a dependency in the skip set?
        ├── condition gate: does EvalCondition evaluate to true?
        └── fan out concurrently by task kind:
              tokio::try_join!(
                assertions  → AssertionTaskExecutor,
                judges      → JudgeTaskExecutor,
                traces      → TraceTaskExecutor,
                agents      → AgentTaskExecutor,
              )
              → stage produces AssertionResult per task
              → snapshot.extend(new_outputs)  [Arc bumps, no clones]
```

The plan is built once from `EvalSpec.tasks` at startup via `validate_dag()`, which topologically sorts your task map. Each stage runs its four task buckets concurrently. After each stage, the snapshot is extended with the new outputs — downstream tasks can JSONPath into `$.task.<upstream_id>.passed`, `$.task.<upstream_id>.actual`, etc.

## Task kinds

### AssertionTask

Deterministic comparison against a value in the record context. Pure Rust, microsecond latency.

```yaml
tasks:
  response_not_empty:
    kind: assertion
    id: response_not_empty
    context_path: "$.response"
    operator: has_length_greater_than
    expected: 10

  tool_was_called:
    kind: assertion
    id: tool_was_called
    context_path: "$.tool_calls[*].name"
    operator: contains
    expected: "search"

  all_scores_pass:
    kind: assertion
    id: all_scores_pass
    item_context_path: "$.scores[*]"
    operator: greater_than_or_equal
    expected: 0.7
```

`context_path` selects a single value via JSONPath. `item_context_path` selects an array and runs the operator against each element — the result is the conjunction of all element verdicts.

The operator catalog has 56 variants. Common ones:

| Operator | What it checks |
|---|---|
| `equals` | Exact equality |
| `not_equals` | Inequality |
| `greater_than`, `less_than` | Numeric comparison |
| `greater_than_or_equal`, `less_than_or_equal` | Numeric comparison with boundary |
| `contains` | String or array containment |
| `not_contains` | String or array absence |
| `starts_with`, `ends_with` | String prefix/suffix |
| `matches_regex` | Regular expression match |
| `has_length_greater_than`, `has_length_less_than` | Length check |
| `is_json` | Valid JSON string |
| `is_not_null` | Non-null value |
| `is_empty`, `is_not_empty` | Empty/non-empty string or array |
| `in_range` | Numeric range `[lower, upper]` |
| `cosine_similarity` | Vector similarity with threshold |

### LlmJudgeTask

Semantic evaluation through a registered `Prompt` card. The engine renders the prompt with the record context, calls the judge model, and compares the structured response.

```yaml
tasks:
  helpfulness:
    kind: llm_judge
    id: helpfulness
    judge_ref:
      kind: Prompt
      name: helpfulness-judge
      version: 1.0.0
    context_path: "$.score"
    operator: greater_than_or_equal
    expected: 4
    max_retries: 2
    depends_on: [response_not_empty]
```

`judge_ref` must point at a registered `Prompt` card. The runtime dispatches through `SkaldJudgeInvoker` in production and `MockJudgeInvoker` when `--judge-mock` is passed to the CLI.

After a judge task runs, its output is available to downstream tasks at `$.task.<judge_id>.parsed` and `$.task.<judge_id>.raw`. This lets a downstream `AssertionTask` gate on a sub-field of the judge's structured response.

### TraceAssertionTask

Asserts against the assembled OTel trace document. No LLM calls.

```yaml
tasks:
  latency_budget:
    kind: trace_assertion
    id: latency_budget
    context_path: "$.spans[?(@.name=='agent.call')].duration_ms"
    operator: less_than
    expected: 2000

  no_retries:
    kind: trace_assertion
    id: no_retries
    context_path: "$.spans[?(@.name=='llm.call')].retry_count"
    operator: less_than_or_equal
    expected: 1
```

The `trace_id` on the record must match a committed trace in the analytical store. The executor waits up to the configured `trace_fetch_deadline` before marking the task as failed.

### AgentAssertionTask

Asserts against the assembled agent workflow envelope. No LLM calls.

```yaml
tasks:
  used_search_tool:
    kind: agent_assertion
    id: used_search_tool
    context_path: "$.tool_calls[*].name"
    operator: contains
    expected: "web_search"

  finish_reason_stop:
    kind: agent_assertion
    id: finish_reason_stop
    context_path: "$.finish_reason"
    operator: equals
    expected: "stop"
```

## Dependency chains and condition gates

`depends_on` creates an ordering constraint. Tasks within a stage run concurrently. Tasks in later stages receive scoped access to the outputs of their declared dependencies under `$.task.<id>`.

```yaml
tasks:
  format_check:
    kind: assertion
    id: format_check
    context_path: "$.response"
    operator: is_json
    expected: true

  field_present:
    kind: assertion
    id: field_present
    context_path: "$.response.answer"
    operator: is_not_null
    expected: true
    depends_on: [format_check]

  quality_judge:
    kind: llm_judge
    id: quality_judge
    judge_ref:
      kind: Prompt
      name: quality-judge
      version: 1.0.0
    context_path: "$.score"
    operator: greater_than_or_equal
    expected: 4
    depends_on: [field_present]
    condition:
      path: "$.task.format_check.passed"
      operator: equals
      expected: true
```

When `format_check` is skipped (because its dependency was skipped) or fails its condition gate, `quality_judge` is also skipped — no judge token spend on a malformed record. The `condition` field lets you express this gate explicitly.

`EvalCondition` supports `and` / `or` chaining with `combinator` and `subsequent`.

## Pass gates

`pass_gate` applies after all records in a run are aggregated. It produces a `PassGateVerdict` with `passed`, `observed`, `threshold`, and `reason`.

```yaml
spec:
  pass_gate:
    kind: overall_pass_rate
    threshold: 0.9
```

| Gate kind | What it checks |
|---|---|
| `overall_pass_rate` | `passed_tasks / total_tasks >= threshold` |
| `per_judge_pass_rate` | Min per-task pass rate across all subjects `>= threshold` |
| `all_pass` | Every task across every record must pass |

The CLI maps a failed gate to exit code `2` when `--fail-on-gate` is enabled (the default for local flows).

## Context capture

`context_capture` controls what gets stored in `AssertionResult.actual`.

| Value | Behavior |
|---|---|
| `full` (default) | Store the extracted value as-is |
| `hash` | Store a SHA-256 hex digest of the serialized value |
| `redact` | Store nothing — `actual` is absent from results |

Use `redact` when the record context contains PII that should not land in results artifacts. Use `hash` when you need deduplication without storing the value.
