Traditional model evaluation compares an output to a label. Agent evaluation is harder. The final response is one artifact of a process that includes tool calls, multi-turn dialogue, span behavior, and intermediate scores that all matter independently of whether the final answer looks right.

Wyrd eval gives you two views across the same run: what the user saw (the passenger view), and what happened under the hood (the mechanic view). Both use the same task engine and the same task definitions.

---

## Two evaluation modes

### Online — production monitoring

Your agent emits `EvalRecordObservation` records during inference. The server processes them asynchronously. No impact on your application's response time.

```python
# During inference, emit a record
record = {
    "record_id": new_uuid7(),
    "run_id": current_run_id(),
    "eval_ref": {"kind": "Eval", "name": "support-eval", "version": "1.0.0"},
    "context": {
        "query": user_query,
        "response": agent_response,
        "tool_calls": tool_call_log,
        "score": confidence_score,
    },
    "created_at": utc_now(),
}
run.observe.eval(record)
```

The server resolves the Eval card from `eval_ref`, runs the task DAG against `context`, and stores `EvalResults`. Use this to catch quality regressions and distribution shift after deployment.

### Scenario — CI and pre-deploy testing

You define test cases as scenarios. The server drives multi-turn conversations, your agent responds turn by turn, and the server scores the completed interaction.

```bash
wyrd eval run \
  --eval eval-cards/support-eval.yaml \
  --scenarios data/scenarios/support-smoke.json \
  --local \
  --agent-url http://127.0.0.1:9000/agent
```

Use this to gate releases, catch regressions before deployment, and establish the quality baseline you'll compare production samples against.

### Same tasks, both modes

Task definitions are identical across online and scenario modes. An assertion that gates a release can monitor production without changes. Write them once.

## Mechanic vs. passenger

Think of it like a car. A passenger only cares whether it got from A to B. A mechanic wants to know whether the engine ran correctly even if it did.

**Passenger view** — given this input, did the agent produce the right output? Scenario tasks run against the agent's final response. This is your end-to-end quality signal.

**Mechanic view** — did the run stay healthy underneath? Tasks defined in the `EvalSpec` run against `EvalRecordObservation` records emitted during execution — intermediate results, tool calls, trace spans, intermediate scores. A passing final response does not imply passing mechanic tasks.

A scenario passes only when both views pass. A run where the final response looked right but a tool call assertion failed is a `scenario_passed: false` result.

## Task types

Tasks are what the engine evaluates against each record. Four kinds, all composable in the same DAG.

| Task | What it checks | Cost |
|---|---|---|
| `AssertionTask` | Deterministic rules: values, thresholds, formats, patterns | Zero — pure Rust |
| `LlmJudgeTask` | Semantic quality via a registered `Prompt` card | One LLM call per record |
| `TraceAssertionTask` | OTel span properties: order, duration, retries, token budgets | Zero |
| `AgentAssertionTask` | Tool calls and response structure: which tools ran, with what args | Zero |

The common pattern is cheap-first. Run `AssertionTask` before `LlmJudgeTask`. If format validation fails, the judge never runs.

```yaml
tasks:
  response_not_empty:
    kind: assertion
    id: response_not_empty
    context_path: "$.response"
    operator: has_length_greater_than
    expected: 10

  helpfulness:
    kind: llm_judge
    id: helpfulness
    judge_ref:
      kind: Prompt
      name: helpfulness-judge
      version: 1.0.0
    context_path: "$.score"
    operator: greater_than_or_equal
    expected: 4
    depends_on: [response_not_empty]
```

`depends_on` creates a topological dependency. `helpfulness` only runs when `response_not_empty` passes.

## How the engine works

Every record — online or scenario — goes through the same path.

```
Your JSON context
      │
      ▼
ExecutionContext (one per record)
  └── ContextSnapshot
        └── base_context: your JSON
        └── task_outputs: {} (fills as stages run)
      │
      ▼
execute_plan(plan, context, registry, executors)
  └── stage 0: assertions run concurrently
  └── stage 1: judges run, assertions that depend on stage-0 outputs run
  └── stage N: ...
      │  (each stage extends the snapshot with new task outputs)
      ▼
EvalReport
  └── TaskRunOutcome per task: Ran(AssertionResult) or Skipped
```

Tasks in the same topological stage run concurrently within each stage — the four task types fan out as parallel Tokio tasks. After each stage, the snapshot extends with new outputs. Downstream tasks JSONPath into `$.task.<id>.passed`, `$.task.<id>.actual`, `$.task.<id>.parsed` (for judge outputs).
