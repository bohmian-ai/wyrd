## Where Wyrd fits

Wyrd is the control & operations layer that sits between the AI products you
build and the runtime you already use. Five capabilities — **define**,
**govern**, **observe**, **evaluate**, **react** — across the full AI lifecycle.

## Start with a local DataCard

```python
from pathlib import Path

import pandas as pd
from wyrd.data import DataCard, PandasInterface

path = Path("customer_churn_card")
data = pd.DataFrame({"customer_id": [1, 2], "churned": [False, True]})

card = DataCard(
    PandasInterface(data=data),
    name="customer-churn",
    version="0.1.0",
    labels={"domain": "customer", "stage": "example"},
    annotations={"example.com/source": "docs quickstart"},
)

card.save(path)

restored = DataCard.model_validate_json((path / "card.json").read_text())
restored.load(path)

print(restored.data)
```

Run the full example from the repo with
[`examples/python/datacard_local_workflow.py`](https://github.com/wyrd-ai/wyrd/tree/main/examples/python).
The [quickstart](/start-here/quickstart/) shows the exact setup command.

## What exists today

Wyrd's design doctrine defines 16 native Card kinds plus `External`; generated
schemas still include some implementation drift while `wyrd-spec` catches up.
The repository has generated reference pages and a Python DataCard surface for
local data materialization. The DataCard surface supports public `wyrd.data`
imports, built-in data interfaces, custom Python `DataInterface` subclasses,
local `save`, local `load`, labels, annotations, and structured Wyrd errors.

Registry, storage, HTTP, CLI, and MCP surfaces build on the same Card envelope.
When those services own durable registration, card objects still remain local
holders: user code runs, Wyrd records and governs.
