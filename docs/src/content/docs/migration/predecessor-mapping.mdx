# Predecessor mapping

Wyrd absorbs capabilities from earlier internal projects, but the public docs should not ask readers to learn those projects first.

Use this mapping rule when writing docs:

- Describe the Wyrd concept first.
- Mention migration status only when it changes what a developer can do today.
- Keep source-only names out of headings, navigation, examples, routes, and commands.
- Prefer card, spec, run, service, observation, policy, and audit vocabulary.
