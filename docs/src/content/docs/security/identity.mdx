# Identity

Wyrd authenticates requests as a `Principal`. A principal has a bare UUID
identifier plus a typed kind discriminator. The identifier string does not
carry the kind; code reads the kind from `PrincipalKind`.

## Principal kinds

| Kind | Used for | Durable binding |
| --- | --- | --- |
| `User` | Human users and local operator workflows. | `auth_users.id`; email stays on the database row. |
| `Service { card_ref }` | Deployed Service cards that call Wyrd. | Service card `CardRef` and card UID. |
| `Agent { card_ref }` | Agent runtimes that call Wyrd. | Agent card `CardRef` and card UID. |

Examples use UUIDs as plain UUIDs:

```text
9b6c8e84-3c2a-4f5e-b2d1-0f47a1c2e8d3
```

The kind lives beside the id in the typed value:

```rust
PrincipalKind::Agent { card_ref }
```

## Card-bound non-human identity

Service and Agent principals both carry the `CardRef` of the registered card
they represent. That symmetry matters because Wyrd must attribute calls from
deployed services and autonomous agents to durable card records, not to
anonymous API keys.

The API key is only a bootstrap credential. After exchange, the Wyrd JWT holds
the structured `principal.card_ref` claim, and the server reconstructs
`PrincipalKind::Service { card_ref }` or `PrincipalKind::Agent { card_ref }`
from that claim.

## User identity

User email is not copied into `Principal` and is not a JWT claim. Handlers that
need email fetch it from `wyrd.auth_users` through the server data path.

## Where clients see it

CLI, MCP, and Python clients receive the same server contract: a request has
one current Wyrd principal, and non-human principals are card-bound. Clients
should use the public API response and error shapes rather than parsing ids for
kind information.
