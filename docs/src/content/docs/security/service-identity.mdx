# Service identity

Service identity is how deployed Service and Agent cards authenticate to Wyrd.
The resulting principal is bound to the registered card, not to the machine
that happens to hold the bootstrap secret.

## Issue

Issue an API key for a Service card:

:::caution[Preview]
The `issue-key` route is pending JWT middleware for runtime principal extraction. Running this command against a current deploy returns `WYRD_AUTH_503_PREVIEW_DISABLED`.
:::

```bash
wyrd auth issue-key prod/Service/billing@1.0.0
```

The same command shape works for Agent cards:

```bash
wyrd auth issue-key prod/Agent/claude-code@1.0.0
```

The plaintext key is returned once. Store it in the deployment secret store and
redact it from logs.

Canonical CardRef text:

```text
{space}/{kind}/{name}@{version}[#{uid}]
```

The optional `#{uid}` pins a specific card UID.

## Exchange

Exchange the API key for Wyrd tokens:

```http
POST /auth/token
Content-Type: application/json

{
  "grant_type": "wyrd_api_key",
  "api_key": "wyrd_..."
}
```

Successful exchange returns a token pair:

```json
{
  "access_token": "eyJ0eXAiOiJKV1QiLCJhbGciOi...",
  "refresh_token": "eyJ0eXAiOiJKV1QiLCJhbGciOi...",
  "token_type": "Bearer",
  "expires_at": "2026-06-15T16:45:00Z"
}
```

The structured `card_ref` is inside the JWT claim. It is not duplicated on the
wire envelope.

## Authorize

Subsequent Wyrd API calls send the JWT in `X-Wyrd-Access-Token`. Wyrd does not
read the application-owned `Authorization` header for Wyrd identity.

## Rotation and audit

Rotate a Service or Agent credential by issuing a new API key, redeploying the
secret, and revoking the old key. PR 5.3 writes credential issuance and token
exchange audit rows in the same database transaction as the credential row.
