title: Storage setup
description: Configure Wyrd's blob storage backend — S3, GCS, Azure, or Local. Covers backend selection, credentials, encryption, integrity guarantees, and tuning.

Wyrd routes all artifact bytes through a single server-side storage subsystem. The client tier carries zero cloud SDKs; every presign, credential, and upload completion call runs on the server. This page covers how to configure each backend.

## Backend selection

Set `WYRD_STORAGE_BACKEND` to one of `local`, `s3`, `gcs`, or `azure`. This is always required; the server refuses to start without it.

| Value | Use case |
|---|---|
| `local` | Development and single-node deploys. Stores artifacts on the local filesystem. |
| `s3` | AWS S3 or any S3-compatible object store (MinIO, Ceph, etc.). |
| `gcs` | Google Cloud Storage. |
| `azure` | Azure Blob Storage. |

## Per-backend environment variables

### Local

| Variable | Required | Description |
|---|---|---|
| `WYRD_STORAGE_LOCAL_ROOT` | Yes | Absolute path to the local storage root. Must exist at boot. |
| `WYRD_PUBLIC_BASE_URL` | Yes | Base URL the server uses to mint local blob download URLs (e.g. `http://localhost:8080`). |

### S3

| Variable | Required | Default | Description |
|---|---|---|---|
| `WYRD_STORAGE_S3_BUCKET` | Yes | — | Bucket name without an `s3://` prefix. |
| `WYRD_STORAGE_S3_REGION` | No | SDK default | AWS region. Falls back to the SDK credential chain default when unset. |
| `WYRD_STORAGE_S3_ENDPOINT_URL` | No | — | Custom endpoint URL for S3-compatible backends. Enables path-style addressing automatically. |
| `WYRD_STORAGE_S3_FORCE_PATH_STYLE` | No | `false` | Force path-style bucket addressing. Set to `true` when using MinIO or Ceph behind a load balancer. |

### GCS

| Variable | Required | Description |
|---|---|---|
| `WYRD_STORAGE_GCS_BUCKET` | Yes | Bucket name without a `gs://` prefix. |

GCS credentials are resolved in this order (see [Credentials](#credentials)).

### Azure

| Variable | Required | Description |
|---|---|---|
| `WYRD_STORAGE_AZURE_ACCOUNT` | Yes | Storage account name. |
| `WYRD_STORAGE_AZURE_CONTAINER` | Yes | Blob container name. |

Azure credentials are resolved from the Azure default credential chain (see [Credentials](#credentials)).

## Credentials

Wyrd does not accept raw API keys as configuration. Each backend resolves credentials at boot via its SDK's standard chain so the same binary works under IAM roles, workload identity, and local dev without code changes.

### S3

The S3 backend uses the AWS default credential chain via `aws-config`. Resolution order:

1. `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` (+ optional `AWS_SESSION_TOKEN`)
2. Web Identity Token (`AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN`) — used for IRSA on EKS
3. ECS task role metadata
4. EC2 instance metadata
5. `~/.aws/credentials` profile

For Kubernetes, prefer IRSA (IAM Roles for Service Accounts) or Pod Identity. Neither requires long-lived keys in environment variables.

### GCS

The GCS backend resolves credentials in this order:

1. `GOOGLE_ACCOUNT_JSON_BASE64` — base64-encoded service account JSON. Preferred for containers that cannot mount secrets as files.
2. `GOOGLE_APPLICATION_CREDENTIALS_JSON` — raw service account JSON string.
3. `GOOGLE_APPLICATION_CREDENTIALS` — path to a service account JSON key file.
4. Application Default Credentials (ADC) — used automatically on GKE with Workload Identity when none of the above are set.

For GKE, configure Workload Identity and leave all three env vars unset. The server picks up the pod's GKE service account token from the metadata server.

### Azure

The Azure backend uses `azure_identity::create_credential`, which resolves credentials in this order:

1. Managed Identity (MSI) — preferred for AKS with Azure Workload Identity or VM-assigned identities.
2. Environment credentials: `AZURE_CLIENT_ID` + `AZURE_CLIENT_SECRET` + `AZURE_TENANT_ID`.
3. Azure CLI credentials (`az login`) — for local development.

Azure presigned URLs use **user-delegation SAS**, which requires token credentials (managed identity or service principal). Shared-key credentials are not accepted in the production credential chain.

## Encryption at rest

All three cloud backends encrypt every object at rest. This happens automatically with no Wyrd configuration.

The difference is key custody:

| Mode | Who holds the key | How to configure |
|---|---|---|
| Provider-managed (default) | Google / AWS / Azure | Nothing. All objects are encrypted automatically. |
| Customer-managed (CMEK / SSE-KMS) | You, via your KMS | Configure the bucket or container to use a CMEK/KMS key. Wyrd has no key configuration — encryption is enforced at the storage layer. |

For CMEK on GCS, create the bucket with a CMEK key set at the bucket level. All objects written to that bucket are encrypted with your key. Wyrd records the `kms_key_name` field returned by GCS on `HEAD` as the `sse_marker` for each upload, so the audit ledger captures which key was active at completion time.

For SSE-KMS on S3, set the bucket default encryption to use an AWS KMS key. Wyrd reads the `ServerSideEncryption` value from the `HEAD` response as the `sse_marker`.

For Azure, Wyrd reads `server_encrypted` from blob properties and captures the `encryption_scope` or customer-provided key SHA-256 when present.

### Enforcing encryption

Set `WYRD_STORAGE_REQUIRE_ENCRYPTION=true` to make Wyrd reject `upload_complete` calls when the object's `sse_marker` is absent. This ensures that uploads to a misconfigured bucket — one where encryption was accidentally disabled — are caught at completion time rather than silently stored unencrypted.

```
WYRD_STORAGE_REQUIRE_ENCRYPTION=true
```

This setting is only meaningful for cloud backends. The local backend always sets `sse_marker` to `"none"`, so `REQUIRE_ENCRYPTION` must not be set for local deployments.

## SHA-256 integrity guarantees

Wyrd stores the client-declared `expected_sha256` at `upload_init` and verifies it at `upload_complete`. The verification mechanism differs by backend.

| Backend | Guarantee | What it means |
|---|---|---|
| S3 | `server_verified_against_client` | Wyrd passes the declared SHA-256 to S3 at `CompleteMultipartUpload`. S3 rejects the commit if it mismatches. Independent of any client behavior after init. |
| GCS | `client_declared` | GCS stores CRC32c and MD5 in object metadata, not SHA-256. Wyrd records the declared hash at init and trusts it at complete. The integrity of the declared hash depends on the uploader. |
| Azure | `client_declared` | Azure Block Blob uses MD5 per-block for wire integrity. No SHA-256 enforcement path exists at the Azure API level. Same trust model as GCS. |
| Local | `server_computed` | Wyrd reads the written file and computes SHA-256 directly. |

For GCS and Azure, the uploader is responsible for computing a correct hash before calling `upload_init`. The declared hash is what appears in the audit ledger and artifact metadata.

The `VerificationGuarantee` value for the active backend is returned in `UploadInitResponse.verification_guarantee` so SDK consumers can surface this to callers.

## Tuning

| Variable | Default | Range | Description |
|---|---|---|---|
| `WYRD_STORAGE_PRESIGN_TTL_SECS` | `600` | 60–3600 | Presigned URL TTL. Values outside the range are clamped silently. |
| `WYRD_STORAGE_PART_SIZE_BYTES` | `16777216` (16 MiB) | 5 MiB–5 GiB, MiB-aligned | Default part size for S3 multipart and Azure block uploads. Must be a whole MiB. GCS uses this as the recommended chunk size. |

For large ML model uploads (10–100 GB), increasing part size reduces the number of part-URL round trips:

```
WYRD_STORAGE_PART_SIZE_BYTES=134217728   # 128 MiB
```

S3 limits multipart uploads to 10,000 parts. At 16 MiB per part the limit is ~160 GB. At 128 MiB it is ~1.28 TB.

## Sweeper tuning

The sweeper runs on one server replica (Postgres advisory lock) and cleans up expired and orphaned uploads.

| Variable | Default | Range | Description |
|---|---|---|---|
| `WYRD_STORAGE_SWEEPER_ENABLED` | `true` | `true`/`false` | Disable to run the sweeper externally or in a dedicated sidecar. |
| `WYRD_STORAGE_SWEEPER_TICK_SECS` | `60` | 10–3600 | Interval between sweep ticks. |
| `WYRD_STORAGE_SWEEPER_BATCH_SIZE` | `100` | 1–1000 | Maximum upload rows swept per tick. |
| `WYRD_STORAGE_SWEEPER_INIT_GRACE_SECS` | `30` | 5–600 | Age after which an `initiating` row is treated as orphaned and swept. |
| `WYRD_STORAGE_SWEEPER_IDEMPOTENCY_BATCH_SIZE` | `500` | 1–5000 | Maximum idempotency key rows deleted per tick. |

## Common boot failures

| Error | Cause | Fix |
|---|---|---|
| `WYRD_STORAGE_BACKEND` missing or unknown value | Backend env var not set or set to an unrecognized value. | Set to `local`, `s3`, `gcs`, or `azure`. |
| S3 boot probe failed | Credentials cannot access the bucket. | Check the AWS credential chain and bucket permissions. The bucket must exist and the role must have `s3:HeadBucket` at minimum. |
| GCS boot probe failed | Credentials cannot list objects in the bucket. | Check the GCS credential chain. The service account needs `storage.objects.list` on the bucket. |
| Azure boot probe failed | Credentials cannot access the container. | Check the Azure credential chain. The identity needs `Storage Blob Data Contributor` or equivalent on the container. |
| `WYRD_STORAGE_LOCAL_ROOT` not absolute or does not exist | Local root is a relative path or the directory is missing. | Use an absolute path and create the directory before starting the server. |
| `WYRD_PUBLIC_BASE_URL` missing for local backend | Local mode requires a base URL to mint download URLs. | Set `WYRD_PUBLIC_BASE_URL` to the server's externally reachable base URL. |
| `WYRD_STORAGE_PART_SIZE_BYTES` not MiB-aligned | Part size is not a whole multiple of 1 MiB. | Use a value that is divisible by `1048576`. |
