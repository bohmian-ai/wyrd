# What is Wyrd

<Aside title="TL;DR" data-variant="wyrd">
Wyrd is the AI layer for developers, engineers, and agents. Cards declare durable AI system components. Specs define each kind. CardRefs connect them. Relationships explain the graph. Status tracks lifecycle. Execution stays in your runtime.
</Aside>

## What Wyrd governs

<dl class="wyrd-defs">
  <dt data-kind="model">Models</dt>
  <dd>Versioned artifacts, interfaces, and the context needed to use them safely.</dd>

  <dt data-kind="prompt">Prompts</dt>
  <dd>Prompt content and the typed contract around its inputs and outputs.</dd>

  <dt data-kind="agent">Tools</dt>
  <dd>Runtime tool names resolved by Skald's tool registry, not Card kinds.</dd>

  <dt data-kind="agent">Agents</dt>
  <dd>Agent declarations Wyrd describes and governs but never executes.</dd>

  <dt data-kind="agent">Workflows</dt>
  <dd>Coordinated sequences of operators, tools, agents, or services.</dd>

  <dt data-kind="experiment">Evals</dt>
  <dd>Suites, scoring rules, and acceptance checks bound to a Card version.</dd>

  <dt>Policies</dt>
  <dd>Rules that decide whether a Card, Run, or action is allowed.</dd>

  <dt>Audits</dt>
  <dd>Reviewable events and decisions with durable provenance.</dd>

  <dt data-kind="service">Services</dt>
  <dd>Deployable surfaces with locked runtime rules and bills-of-materials.</dd>

  <dt data-kind="experiment">Observations</dt>
  <dd>Drift, eval scores, trace events, and other typed behavioral signals.</dd>
</dl>

## The shared envelope

Every registered AI system component in Wyrd is a Card. Cards share a common envelope: `apiVersion`, `metadata`, `kind`, `spec`, `relationships`, and `status`. The `spec` field is typed per kind, so a Model card carries a `ModelSpec` and a Data card carries a `DataSpec`, but the outer envelope is the same across all 16 native card kinds plus `External`.

This matters for operations. One envelope means one inventory, one policy entry point, one lineage graph, one audit model, generated contracts, and agent-readable docs. Agents do not need to guess which shape applies to which component before they can inspect or validate it.

```yaml
apiVersion: wyrd/v1
metadata:
  space: default
  name: customer-churn
  version: "0.1.0"
  labels:
    domain: customer
  annotations:
    example.com/source: docs
kind: Data
spec:
  interface:
    kind: Pandas
relationships: []
status: null
```

## Why point tools cannot solve this alone

Point tools each solve one slice: a registry tracks models, a prompt tool tracks prompts, an observability backend tracks traces. They usually do not share an envelope, a policy engine, or a lineage graph. The gap between tools becomes the failure mode: a model updates, the eval that validates it does not run against the new version, and no audit record ties the change to the service that packages both. Wyrd is the typed layer that keeps those connections explicit instead of inferred.

## The runtime boundary

Wyrd records, validates, governs, links, installs, observes, and exposes AI system components. Execution stays in the user or framework runtime. Wyrd does not:

- host user code
- run user agent loops
- serve user inference
- manage user containers or processes
- own training jobs

This boundary keeps Wyrd useful for teams that already have orchestration frameworks, inference servers, notebooks, jobs, and observability backends. Wyrd works beside those systems as the control layer, not as a replacement for them.

## What exists today

- The design doctrine defines 16 native Card kinds plus `External`.
- Current schemas include some implementation drift while `wyrd-spec` catches up to `architecture/wyrd-design.md`.
- This docs site, with generated reference pages for Cards, OpenAPI, schemas, and error codes.
- Python DataCard local workflow support through public `wyrd.data` imports.
- Built-in Data interfaces, custom Python `DataInterface` subclassing, local `save`, local `load`, labels, annotations, and structured Wyrd errors.

Registry, storage, CLI, HTTP, and MCP surfaces build on the same contracts as they land. Card objects do not register themselves; registry and client surfaces own durable registration.
